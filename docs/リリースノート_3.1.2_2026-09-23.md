# リリースノート 3.1.2（報告の口）

2026-09-23。設計は [設計 3.1.2](設計_3.1.2_報告の口_2026-09-23.md)（masaru の裁定 5 件はすべて「はい」）。版を 3.1.2 に上げた（2026-09-23 13:00・masaru「進めて」と裁定 5 件で配布）。

## なぜ

kopicha セッションの不具合の報告が、セッション間メッセージでは承認待ちのまま期限切れになり（09-21・09-23）、文書を人が運ぶ形になっていました。**報告は道具の中に置き、実装側が道具で読みます。**

## 利用者のセッションでの使い方（5 行）

1. 道具が断った・結果が期待と違った・欲しい形がある、のどれかなら `thth report file <account> --kind bug|request --title … --body-file … --by <名前>`（MCP は `thth_report_file`）を 1 回。
2. 返ってきた `report_id` を控える必要はありません。自分の project の報告は `thth report list <account|project>`（MCP `thth_report_list`）で並びます。
3. 実装側の返事は `thth report show <report_id>`（MCP `thth_report_show`）と、開始手順の `handoff-report --since-last-read` の `tool.reports.new_replies`（前回の栞から増えた分）に出ます。
4. 秘密らしき値（token・Bearer・`sk-`・32 桁以上の 16 進 等）が含まれていると `secret_detected` で置かれません。伏せてから置き直してください（sha は先頭 12 桁までで足ります）。
5. 断られたときの理由行の後ろ・`handoff-report --since-last-read` の `tool.report_channel`・`thth morning` の `limitations` の末尾に、この口の案内が 1 行出ます。

## 入ったもの

### 1. 記録（`thth report file|list|show`）

- 置き場は VM の私有（`$THTH_ROOT/state/_reports/<report_id>.json`・0600・ディレクトリ 0700）。**SNS の台帳には書きません。**
- 1 件の形は設計 §2 のとおり（`report_id`・`kind`・`title`・`body`・`repro`・`project`・`account`・`medium`・`reporter`・`via`・`tool_version`・`status`・`replies`・`closed`）。`report_id` は `r` + 日付 + `-` + 乱数 8 字。
- 長さ: title 120 字・本文 8,000 字・再現手順 4,000 字（`report_too_long`）。件数: 1 account につき直近 24 時間で 20 件（`report_rate_limited`）。同じ title と本文が同じ account で 24 時間以内にあれば `duplicate_report` と既存の id。
- 本文に `$THTH_ROOT` やホームの絶対パスがあれば、置く時点で `$THTH_ROOT`・`~` に畳みます。
- 変更ログ `report_filed`・`report_replied`・`report_closed`（presence-only・本文は入りません・通知もしません）。

### 2. MCP の利用者側（サーバ型の user credential）

`thth_report_file`・`thth_report_list`・`thth_report_show`。誰が置いたかは credential の `actor` です（要求の欄からは作れません・`actor` が無ければ `by_required`）。書く口（`writes`）の無い credential でも置けます。読めるのは自分の account とその project の報告だけです。

### 3. 実装側（`thth admin reports list|show|reply|close|export`・MCP `thth_admin_reports_*`）

全 project の報告を読み（既定は開いているものだけ）、返事（`reply`・秘密は置かない）と閉じる（`close`・理由 fixed／wontfix／duplicate／invalid と版）を書きます。`--by` 必須。`export --to <私有の dir>`（`--to` 必須・既定の行き先は無い）は開いている報告を 1 件 1 ファイル（`<report_id>_<題>.md`）で書き出し、前に書き出した報告が閉じていれば閉じた形に書き直します。応答にも書き出しにも絶対パスは出ません。**書き出しは私有の置き場へ。公開 repo には置きません**（THTH の repo は公開で、本文は利用者が書いた文です）。

### 4. 見落とさない口と受け口の案内

- `thth morning`（CLI＝管理者）の 0 段「道具」に「報告: 開いている n 件（新規 m 件・直近 24 時間）」、第 5 段「次の一手」に開いている報告 1 件につき 1 行（`kind: "report"`・`report_id` と種類と題の先頭 60 字だけ・本文は載せない）。サーバ型の利用者の 1 枚にはどちらも出しません。
- `handoff-report --since-last-read` の `tool` に `report_channel`（常に）と `reports`（自分の project の報告・前回の栞から増えた返事）。
- 断り（CLI の rc≠0・MCP の isError）の後ろに静的な 1 行 `report_channel: …`。成功の応答には載せません。
- サーバ型の利用者の `tools/list` で、各道具の説明文の末尾に「うまくいかなければ thth_report_file」。`thth --help` の末尾にも 1 行。

### 5. 退出で token が他の account と同じ値なら、遠隔で失効させずに終える（件 6）

2026-09-23 12:50 の実測: 同じ app で同じ利用者が認可すると Mastodon は既存の access token を返すので、kopicha-server-mastodon と kopicha-mastodon の token は値が同じでした。失効すると他方も使えなくなるので投げない、という判定は正しいのですが、退出が `worker_revoked` で止まっていました。この版から、token の値が他の生きている account と同じ（`token_shared`）なら、遠隔の失効を投げずに `remote: unconfirmed_shared` で台帳・state・env・managed repo の削除まで完了します（Mastodon・X）。**値だけの共有（別ファイル）なら自分の token file も消します**（消しても失効にはならず、相手は自分のファイルを持っています。退出した account の秘密を VM に残しません）。同じファイル（path・inode が同じ・app directory 配下）を共有しているときだけ、自分の token file を残します（`preserved: token_shared`）。他 account の token file には触りません。`leave` は「他 account と共有の接続です。運用者が解除対象を切り分けてください」の 1 行を出します。既に `worker_revoked` で止まっている退出は、同じ `leave` を打ち直せば完了します。`shared_credential_revoke_refused` が出るのは、共有なのに消す対象に token が残っているという矛盾のときだけです。

### 6. 退出の途中の台帳が未回答を潰さない（件 7）

2026-09-23 12:55 の実測: kopicha-server-mastodon が退出の途中（`stopped`）になった後、`thth unanswered kopicha-threads` が 0 件になりました（朝は 6 件）。「自分の handle」を集める所が停止中の台帳を読めないものとして扱い、すべての返信が「誰のものか判らない」になっていました。停止中の台帳は退出の読み手と同じ門で読んで handle を集めます（同じ本人の handle は退出の途中でも自分）。`unanswered`・`who`・`thth morning` の返していないものの段が同じ直しを通ります。本当に壊れた台帳は従前どおり読めないものとして扱います。
