# 設計: 店の変化の連動（台帳 → マップ・IG の投稿・ストーリー）（2026-11-19）

書いた者: THTH開発 第20。masaru 11/19「シナリオの拡張で、店舗運営スケジュールの更新と ig の投稿、ストーリーの投稿、マップの更新が連動すると良さそう」「（前もっての同意で自動の形）その形しかないでしょ」。

元になる物: [設計_実店舗_2026-11-13.md](設計_実店舗_2026-11-13.md) §6（きっかけ）・§6.4・§9.4（Google の決まり）、[計画_実店舗_2026-11-13.md](計画_実店舗_2026-11-13.md) 段 2・段 6、`thth/register/triggers.py`・`draft.py`、`thth/gbp/`（13cb747）。

## 1. 一言で

店の台帳の 1 つの変化（臨時の休み・時間、催し、営業の時間の変わり）から、**決めておいた出し先へまとめて出す**。出し先は Google マップ（臨時の時間・イベントの投稿）・IG のフィード投稿・IG のストーリー。**持ち主が前もって範囲を決めて書いた同意**があれば人の押下なしで出し、範囲の外は今までどおり 1 回ずつの二段確認。

## 2. Google の決まりとの合わせ方（原文: 設計_実店舗 §9.4）

- 「ユーザーの事前の具体的かつ明示的な同意なしに」店の編集などを自動にしない → 同意は**具体的に**書く: 店・出し先・種類（どのきっかけ）・期限・書いた人と日時。
- 同意は台帳の持ち主の手で書き、THTH は同意を書き換えない。取り消しはいつでも効く（次の回から止まる）。
- 変えたことは 48 時間以内に持ち主に知らせる → 出したら hub に 1 行（何をどこへ出したか）。
- Google が加えた変更を自動で元に戻さない → 台帳と Google が違ったとき、Google の側が台帳の前回の出した値から変わっていたら（Google が変えた・人が手で変えた）、自動では出さずに止めて持ち主に聞く。
- 読んだ中身は 30 日を超えて持たない（出した値の控えは、THTH が自分で書いた値なので持ってよい【推】。Google から読んだ値は持たない）。

## 3. 形

### 3.1 出し先の宣言（店の台帳ごと・持ち主が書く）

台帳に「この店の変化をどこへ出すか」と「どこまで自動でよいか」を書く。例（形は書き手が台帳の器の作法に合わせて決める）:

```yaml
outlets:
  - to: gbp:locations/6353608778993100589   # 臨時の時間・イベントの投稿
    triggers: [special_soon, event_soon]
  - to: ig:yamate-ig                          # フィード
    triggers: [special_soon, event_soon]
  - to: ig-story:yamate-ig                    # ストーリー（画像が要る）
    triggers: [special_soon]
consent:                                       # 前もっての具体的で明示の同意（無ければ全部 1 回ずつ承認）
  - to: gbp:locations/6353608778993100589
    triggers: [special_soon]
    until: 2027-03-31
    by: <持ち主の名前>
    at: 2026-11-19T12:00:00+09:00
```

### 3.2 1 つの変化 → 束

- きっかけ 1 つから、宣言した出し先の数だけの下書きを**1 つの束**として作る（束の id・元の行・行の指紋）。
- 束の中の 1 つずつに「同意あり（自動で出す）」か「承認待ち」を付ける。
- 承認待ちの物は、束ごと 1 回の二段確認でまとめて通せる。
- どれかが断られても残りは止めない。束の現在地（出た・待ち・断られた・止めた）を `thth scenario` の現在地に出す。
- 同じ行・同じきっかけ・同じ出し先は二度出さない（今の `same_exists` と同じ考え）。行が変わったら（指紋が違う）出し直しの束にする。

### 3.3 出し先ごと

- **gbp（臨時の時間）**: `special` の行 → `thth gbp special` と同じ PATCH（その日だけ足し替え）。
- **gbp（イベント）**: `event` の行 → localPosts の topicType EVENT（題・始まりと終わり・本文・リンク）。`thth gbp post --event …` を足す。
- **ig（フィード）**: 今の queue の下書き（`thth register draft` の形）。画像の要る媒体なので、行の画像か宣言の既定の画像を使う。
- **ig-story**: 新しい口。Graph API の `media_type=STORIES`（画像か動画・本文の字幕は無い）。画像は行に付ける（無ければ断る・前向きな断り）。告知の画像を THTH が作るのは別の段。
- 本文の下書きは今の `body_lines`（臨時・催しの言い回し）を使う。理由（休みの理由）は既定で書かない（計画 §6 の 2「家が空く知らせ」）。

### 3.4 どこで動くか

- 自動で出すのは VM の timer（今の queue の配信と同じ場所）。GBP の鍵を VM に置く道が要る（今は Mac の `~/.config/thth/google-gbp-token.json` だけ）。置き場と運び方は書き手が今の作法（VM の秘密の置き場）に合わせて作り、本物の鍵を運ぶのは私（開発セッション）が後でする。
- Mac からも同じ命令で回せる（自動でない 1 回ずつの承認の道）。

## 4. 作る順（段）

1. ig-story の口（アダプタと送る道・試験）
2. gbp のイベントの投稿（`thth gbp post --event`）
3. 出し先の宣言と同意の形・読み・点検（台帳の点検の柵に入れる）
4. 1 つの変化 → 束（下書き・同意あり／承認待ち・二度出さない・出し直し）
5. 束を出す命令（承認待ちは束ごと二段確認・同意ありは確認なしで出す）と、Google 側が変わっていたら止める柵
6. `thth scenario` の現在地に束を出す・hub への 1 行
7. 見本の店（試験の材料の架空の店・IG と GBP の両方を持つ）で、変化 → 束 → 出る、を通す試験

本物の店で通すのは、IG と マップの両方が THTH に入っている店ができてから（11/19 の時点では無い: S.o.h は IG だけ・学校は GBP だけ）。

## 5. 決めていないこと

- 本物で最初に通す店（IG と GBP の両方が要る）。
- 同意の期限の既定（推: 無期限にせず、最長 1 年）。

## 6. 書き手が決めたこと（段 1〜7・2026-11-19 書き手）

形の細部で、設計に無かったものを書き手が決めた。【推】は本物で確かめてから直してよい所。

- **宣言の置き場と形**: 台帳のフォルダの `.thth/linkage.json`（`thth.linkage/1`）。YAML にしなかったのは、publish の箱に PyYAML が無いため。中身は `outlets`（`to` = `gbp:<店>`・`ig:<口座>`・`ig-story:<口座>`、`triggers`、IG は既定の `image`・`image_alt`）と `consent`（`register`・`to`・`triggers`・`until`・`by`・`at`、取り消しは `revoked_at` を足すか項を消す）。
- **同意の範囲**: 同意は `register` が要る。別の台帳の名前の同意が 1 つでもあれば宣言ごと崩れたとみなし（`register_linkage_invalid`）、何も自動で出さない。期限は書いた日から最長 366 日（§5 の推に合わせた）。きっかけは名前で 1 つずつ書く（「全部」とまとめる書き方は無い）。`by`・`at` が欠けた同意も崩れとみなす。宣言が崩れていれば `thth register check` も断る。
- **命令**: `thth link check|consent|make|show|send|run`。`consent` は同意を二段確認で控える（§6.1）。`send` は `--bundle <束>`（二段確認・一段目は何も変えない）か `--auto`（今効いていて控えた同意のある物だけ確認なし）。`run` は make と send --auto を続けて回す（VM の timer 用）。
- **束の記録**: `register_state/<台帳>/linkage_bundles.json`（600）。物の状態は ready（同意あり）・waiting（承認待ち）・blocked（直す所がある）・sending（出している途中）・sent・unchanged（前に出た中身と同じ）・refused・stopped・unknown・superseded・expired。束の id と作り直しの決めは §6.1（外に出る中身の指紋と何代目か）。
- **同意の読み直し**: 同意は束を作るときでなく、出す回ごとに読み直す。取り消した・期限が切れた物は ready から waiting に戻す（次の回から自動で出ない）。
- **IG の道**: フィードもストーリーも `core.send_once`（`thth send` と同じ道・予行 → digest → 本番）。待ち行列と approve の道は使わない。ストーリーは `post_options.story` で `media_type=STORIES`・字幕と代替の文を付けない。画像が無いストーリーは `unsupported_attachment: instagram/story_no_media` で断る。
- **画像**: 行の頭の `image`・`image_alt` か、宣言の出し先の既定。台帳のフォルダの中の JPEG だけ（8 MB まで）。口座の repo の `register-media/<台帳>/<sha256 の頭 16>.jpg` に写して送る。
- **GBP の臨時の時間**: 1 日 1 項目で、最長 14 日【推】。超える行は `register_link_too_long` で断る。Google の今のその日が THTH の前に書いた値（前に書いていなければ今書く値）と違えば、自動では止める（`register_link_google_changed`）。持ち主の二段確認（`--bundle`）では一段目に「置き換えます」と注意を出して置き換えてよい。Google から読んだ値は残さず、digest にだけ入れる。
- **GBP のイベント**: `thth gbp post --event <題> --start <時刻> --end <時刻>`（3 つそろえる）。題は 58 字まで【推】。
- **休みの理由**: 本文は台帳の下書き（`draft.body_lines`）から作るので、`public_fields` に書かない限り出ない。
- **知らせ**: `thth events` に `link_published`（出た・1 件ずつ）と `link_waiting`（期限の前に承認待ち・止めた・分からない物がある束）。`thth scenario` の JSON に `links`。hub への 1 行は、events を読む既存の道に乗せた（hub に直接は書かない）。
- **柵**: release の関門の危ない所に `link_write`（`thth/link/*`）。束を出す回は `linkage.lock` で 1 本ずつ。
- **VM の鍵**: GBP の認可は既存の `THTH_GOOGLE_GBP_TOKEN`・`THTH_GOOGLE_ADS_CLIENT` を VM の秘密の置き場に向ける。本物の鍵を VM に運ぶのと、`thth link run` の systemd timer を置くのは、この段ではしていない（開発セッションのあとの手）。
- **【推】の残り**: ストーリーの縦横比は見ない（Graph の答えに任せる）・画像の代替の文の既定・14 日・58 字・ロックの形。

### 6.1 監査の直し（2026-11-19 書き手・監査役の 10 の穴と全件の 4 件）

- **1 件ずつ記録する**（穴 1）: 出す前に物の状態を `sending` にして束の記録を書き、出したらすぐ書く。前の回が途中で落ちて `sending` が残っていれば、次の回（make でも send でも）に `unknown`（詳細 `interrupted`）にし、自動では出し直さない。予期しない例外は止めずに上へ投げる（記録には `sending` が残る）。
- **出し先の店を台帳と結ぶ**（穴 2）: 店の行（`kind: store`・店.md）に `gbp_location: locations/<数字>` を足せるようにした。この欄を持つ店の行を認める操作は、種類によらず二段確認（`kinds.binds_outside`）。Google マップの出し先は、認めた店の行の `gbp_location` と一致する店だけ（違えば `register_link_store_unbound`）。IG の口座は、口座の `project` が台帳の `project` と同じものだけ（違えば `register_link_account`・詳細 `project_mismatch`）。どちらも状態は `blocked`（「直す所がある」・直すのは承認でなく店の行か宣言・直れば自動の回にもう一度確かめる・2 回目の食い違い）。
- **同意の控え**（穴 3・2 回目の B・G）: 命令 `thth link consent <台帳> --by <名前> [--confirm D]`（`--by` は必須）。一段目は控えていない同意の全文と digest を見せ、「控えると、この出し先には確認なしで出ます。前に THTH が書いた日を外すことも含みます」と言って何も書かない。二段目で同意の指紋（台帳・出し先・きっかけ・期限・書いた人と日時・取り消しから作る）を `register_state/<台帳>/linkage_consent.json`（600）に控える。自動に使うのは控えの指紋と合い、取り消していない同意だけ。ファイルだけの同意・控えたあとに書き換えた同意は承認待ち（`thth link check` が `register_link_consent_unkept` の注意を出す）。**取り消し**は `thth link consent <台帳> --revoke [--to 出し先] --by <名前>`（二段確認）で控えに取り消しの時刻・人・訳を足す（消さない）。出す回ごと（make と send のロックの中）に、ファイルから消えた控え（`revoked_at` を足して指紋が変わった物も）も取り消しとして記録する。取り消した指紋は二度と控えられず、同じ文を戻しても効かない（続けるなら、日時を書き直した新しい同意を控える）。控えが壊れたら `--reset`（二段確認）で `linkage_consent.json.broken-<時刻>` に退けて空から始める（消さない・控え直すまでどの同意も効かない）。`thth register remove` は束・控え・ロックのファイルも外す。
- **束は外に出る中身で決める**（穴 4・7）: 出し先ごとに外に出る中身の指紋（`outward`: 文・日・片づける日・イベント・画像の sha256・画像の説明。臨時の時間は日だけ）を持つ。同じ行・同じきっかけの最後の束と中身が同じなら作らない。違えば、その行の何代目か（`generation`）を入れた id で作る（A → B → A と戻しても、外が B なら A を出す）。出し先ごとに、その行で最後に出た物と中身が同じなら `unchanged`（出し直さない）。出す前の確かめも、行の字でなく外に出る中身で比べる。
- **臨時の日の片づけ**（穴 5・2 回目の A・C・F）: その行で前に Google へ書いた日のうち今の行に無い日を束の `clear` に入れて specialHours から外す。ただし**ほかの今使える（柵を通る）臨時の行が持つ日と、その日に最後に書いたのが別の行である日は外さない**（R1 を退役して R2 が同じ日を持つとき、R2 の値を消さない）。指紋に入れる `clear` は日付で切らず、過ぎた日は出すときに飛ばす（日が過ぎても同じ中身の束を作り直さない）。退役した・違うと言った・日を窓の外へ動かした行には片づけだけの束（`clear_only`）を作り、きっかけ `special_soon` の同意の範囲で出す。**行が見つからないだけのとき**は、消したのか読めないだけかを決められないので、同意があっても承認待ち（物に `hold: row_missing`・自動では選ばない）。認め直し待ちの行は片づけない。台帳がまとめての入れ替えの途中なら、make も send も `keep.refuse_if_pending` で断る。
- **一時の断り**（穴 6・2 回目の E）: IG の安全装置（`guard`・`locked`・`rate_limited`・`queued`）と、Google の `gbp_quota_exceeded`（429）・読む口の `gbp_unavailable`（503）・鍵がまだ無い（`gbp_token_missing`・`gbp_client_missing`・`gbp_token_refresh_failed`）は、状態を前のまま（同意ありは ready）にして次の回へ回す。回数は数えない。安全装置が次に出せる時刻（`next_at`）を返せば `retry_after` に置き、その時刻までは試しもしない。止めるのは時間で、束の出さない期限を過ぎたら `expired`（期限の無い物は最初の断りから `RETRY_HOURS`＝24 時間で `stopped`【推】）。書く口の 5xx は出たか分からないので前のとおり `unknown`。画像の無いストーリーは、画像を置けば外に出る中身が変わるので次の make で作り直す。Google の今の値が今書く値と同じなら「変わった」とみなさない。
- **書く直前の読み直し**（穴 8）: 臨時の時間を書く直前に店を読み直し、計画のときの読み（同じ回に THTH が書いた分は重ねて持つ）と違えば書かずに止める（`register_link_google_changed`・詳細 `between_read_and_write`）。
- **一段目に出す物**（穴 9・2 回目の D）: `--bundle` の一段目に、出たか分からなかった物は「先に thth gbp show（IG は thth inflight）で確かめて」、片づける物は「外す日: …」を出す。digest の中身にも `was_unknown` と `clear` を入れる。`thth link show` は片づけの束に「片づけの束」、物に「外す日: …」を添える。
- **束の記録の上限**（穴 10・2 回目の H）: 500 を超えたら、古い順に、外に出た物の無い閉じた束を落とす。出た物（`sent`・`unchanged`・`unknown`・`sending`）か開いた物を持つ束と、行ときっかけごとの最後の束は落とさない。まだ超えるなら古い束を要約に寄せるが、開いた物を持つ束は要約にしない（出すのに本文・日・画像が要る）。束の代は、その行の束の最大の代に 1 を足す（落としたあとも id が重ならない・重なれば代を進める）。
- **全件の 4 件**: README・README.en に `link` を足した。`thth --help` の `link` の説明から「→」を外した（道案内の 3 行と数えられていた）。IG の理由の表（`media_capabilities.REFUSALS`）に `story_options`・`story_no_media` を足した。
- **手元の読み書きの失敗**（2 回目の I）: 画像を読む・口座の repo に写す・置き場を作る ときの OSError は網に出る前なので `stopped`（詳細 `local_io`）にして、ほかの物を続ける（traceback で終えない）。網に出たあとの失敗は前のとおり。
- **知らせ**（2 回目の食い違い）: `link_waiting` に数えるのは 承認待ち・直す所がある・止めた・出たか分からない・画像が無くて断った 物。
