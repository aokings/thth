# 設計 3.3.1: inflight を道具が自分で解く・公開の 500 で止まらない

2026-09-23 19:00。材料: 運用セッションの障害報告（転送・記録は thth-notes の `記録/障害_asmon_inflight残留_2026-09-22-23.md`）。asmon-kanto-threads が 09-22 20:03 の公開で `threads_publish` から HTTP 500（`is_transient=true`・container は作成済み）→ 道具は「結果が分からない」で inflight を残し、**21 時間、毎 run が止まった**。媒体には出ていなかった。復旧は masaru が inflight.json を手で消した。3.3.0 の次の版。

## 0. 約束（1 行）

**結果が分からないまま止まるのは、媒体に問い合わせても分からないときだけ。** 問い合わせで決まるなら道具が決めて進む。決まらないなら人に知らせる（3.3.0 の held と同じ通知）。

## 1. 一次資料（Threads・2026-09-23 参照・troubleshooting）

- `GET /{threads-container-id}?fields=status,error_message`。status は `EXPIRED`（24 時間以内に公開されず失効）・`ERROR`（公開処理に失敗）・`FINISHED`（公開の準備ができている）・`IN_PROGRESS`・`PUBLISHED`（公開済み）。
- container の有効期限は 24 時間。問い合わせは「1 分に 1 回・5 分まで」を推奨。
- 同じ container を 2 度公開したときの振る舞いと、エラー後の再試行の指針は**文書に無い**（未確認）。

## 2. 公開の直後（`adapters/threads.py` の publish）

`threads_publish` が 5xx・timeout・接続断で終わったとき、inflight を残す前に container の status を最大 3 回（20 秒間隔）問い合わせる。

| status | 意味 | 道具がすること |
|---|---|---|
| `FINISHED` | 出ていない・まだ出せる | `threads_publish` を **1 回だけ**再試行。それも 5xx なら inflight を残す（下の自己解決に任せる） |
| `PUBLISHED` | 出た | 自分の最近の投稿（`GET /me/threads`・公開時刻の前後 10 分）から本文の指紋が一致する 1 件を探して post_id を書き戻す。見つからなければ inflight に `remote_state: published_unlocated` を書いて止まる |
| `ERROR`・`EXPIRED` | 出ていない・この container では出せない | inflight を解いて `publish_failed_remote_error` を runs に。原稿は approved のまま残り、次の run で新しい container から出る |
| 問い合わせ失敗・`IN_PROGRESS` のまま | 分からない | inflight を残す（従前どおり） |

- **2 度出す経路を作らない**: 再試行は `FINISHED` を確かめた直後の 1 回だけ。`PUBLISHED`・問い合わせ失敗・`IN_PROGRESS` で再試行しない。単変異で固定。

## 3. inflight の自己解決（毎 run の最初）

inflight が残っている run は、止まる前に同じ問い合わせを 1 回する（container_id が inflight にあるとき）。表の上 3 行で決まれば解いて進み、決まらなければ従前どおり止まる。止まり続けるなら 3.3.0 の `held`（理由 `inflight_unresolved`）で通知。

- Mastodon・Bluesky・X（container が無い）: 自分の最近の投稿を公開時刻の前後 10 分で引き、本文の指紋が一致する 1 件があれば書き戻して解く。0 件なら**解かない**（出ていないと言い切れない媒体がある）——`thth inflight resolve` で人が決める。

## 4. 人の口: `thth inflight <account> [show|resolve] --by <名前>`

- `show`: inflight の中身（file・started・container_id の有無・最後の問い合わせ結果）を出す。本文と token は出さない。
- `resolve --not-published --by`: 人が媒体で「出ていない」を確かめたときに解く（今回 masaru がファイルを消した操作の代わり）。控え `inflight.resolved-<日時>.json` を state に残し、変更ログ `inflight_resolved`。
- `resolve --published <post_id> --by`: 出ていたのを人が見つけたとき。post_id を書き戻して解く。
- MCP は出さない（`approve` と同じ線・人の判断）。

## 5. 通知が届かなかった件（報告の論点 1）

- 道具の側の記録: asmon の運用通知は SMTP 設定済みで、復旧時の通知（09-23 17:24・recovered）は SMTP が user と admin の両方を受領している。停止時の通知は、復旧の事象が作られた以上、停止の事象も作られていたはずだが、outbox から消えていて**送ったかどうかを今は言えない**。死活通知は監視サービスが受領している（配送先への到達は監視サービス側の設定）。
- 直し: outbox の事象を 30 日残し（今は消える）、`thth board` と `thth observe` に「最後に送った運用通知: <時刻> <状態> <受領した役割>」を出す。届いたかどうかを人が照合できるように。
- masaru の確認事項: 09-22 20:03〜21:00 の受信箱（迷惑メールを含む）と、監視サービスの通知先・閾値。

## 6. 試験

fake Threads: 5xx → FINISHED → 再試行 1 回で成功／再試行も 5xx で inflight／PUBLISHED で一覧から post_id を書き戻す／一覧に無ければ published_unlocated で止まる／ERROR・EXPIRED で解いて原稿は approved のまま／問い合わせ失敗で従前どおり。自己解決（run の最初）・他媒体の一覧照合（1 件なら解く・0 件なら解かない）。`thth inflight show|resolve` の往復と控えと変更ログ。outbox の保持と board の表示。単変異 5 本（PUBLISHED で再試行する／問い合わせ失敗で解く／他媒体の 0 件で解く／再試行を 2 回にする／控えを残さない）。

## 7. masaru の裁定（2026-09-23 19:45「全部推薦通りでOK」＝5 件ともはい）

1. 公開の 5xx は container の status を確かめ、`FINISHED` のときだけ 1 回再試行する。
2. inflight は毎 run の最初に媒体へ問い合わせ、決まれば道具が解く。決まらなければ止まって通知する。
3. 人の口 `thth inflight show|resolve` を足す（MCP には出さない）。
4. 運用通知の記録を 30 日残し、最後に送った通知を board と観測に出す。
5. 版は 3.3.1（3.3.0 の次）。
