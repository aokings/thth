# 設計 v3.1: 分析の磨きと、新しい採集

2026-09-18 夕。2.5.0（`e56b72e`）を配布した直後に masaru と決めた次の範囲。masaru の言葉: 「分析系をさらに磨くのを重ねたい」「全部良さそう。全部作りましょう」。
本書は**契約**（何を・どの条件で・何を言わないか）を先に固定し、実装は Codex が本書から行う。裁定が要る点は §5 に集めた。**§5 の裁定が出るまで、§3 の C3・C4 は着手しない。**

## 0. 変えない規律（設計 v1 §3.2.2・設計 v2・「自分の泉」§10・2.5.0 の監査で確かめたもの）

- 数値は出所と時間条件を連れて歩く。取れていない刻みは `null` であって 0 ではない。
- 母集団は「所有を確認できた実測台帳の根投稿」と「account 一致の絡みの台帳の返信」。SNS 上の全投稿ではない。
- 媒体・account をまたぐ合計・順位・率を作らない。並べるだけ。
- 差は観測の差。因果・推奨・成功/失敗を言わない。
- 他人の本文・username・人物像を残さない。残すのは自分の行為と反応、および件数。
- 24h の測定帯は「24 時間以上 30 時間未満・最初の適格観測・collapsed 不可」（`analytics_comparison._measurement_contract()`）。刻みを増やしても同じ形で帯を定義する。
- 読むだけ。レポートは台帳・原稿・承認・設定を書き換えない（cursor は §2-A4 の例外で、**読み手が明示したときだけ** 1 ファイルを書く）。

## 2. 分析の磨き（2.6.0・既存台帳だけ）

すべて `analytics_report` / `analytics_comparison` / `operations_handoff` / `study_report` の**追加の鍵**として入れる。**既存の鍵の意味・型・値は変えない。鍵を足すだけなので `schema_version` は 1 のまま**（形を変える鍵が出たときに初めて上げる）。足した鍵の一覧を各レポートの文書に「schema_version 1 で追加された鍵（2.6.0）」として載せる。

### A1. 速度の曲線（刻みごとの値）

- 材料: `collect` が既に採っている刻み `AGE_MARKS_HOURS = [1, 6, 24, 72, 168]`（`thth/collect.py`）。
- 出すもの: 根投稿ごとに `marks: {1: {...}, 6: {...}, 24: {...}, 72: {...}, 168: {...}}`。各刻みは 24h と同じ形の**帯**で最初の適格観測を 1 つ採る。帯は `[m, m×1.25)` 時間（1h→[1,1.25)、6h→[6,7.5)、24h→[24,30)、72h→[72,90)、168h→[168,210)）。帯の外・collapsed・未来・日時矛盾は `null`＋理由（既存の `rejected_observations` と同じ語彙）。
- 集計: 刻みごとに `n_eligible`・中央値（`min_n` 以上のときだけ）・§2-A5 の散らばり。**「1h→24h の伸び率」は出さない**（率を作らない規律）。`views_1h` と `views_24h` を並べるまで。伸びの読みは LLM。
- 言わないこと: 刻み間の差を「勢い」と名付けない。鍵名は `by_mark`。

### A2. 絡んだ枝ごとの帰結

- 材料: 絡みの台帳（`thth.engagement.v1`: `post_id`・`reply_to`・`root_post`・`author_key`・`topic`・`form`・`hour_band`・`posted_at`）と、その `post_id`（＝自分の返信）の実測行、返信台帳（相手が自分の返信に返したか）。
- 出すもの: `engagements.by_thread[]`——`root_post`（id のみ）ごとに、自分の返信の 24h 帯の views/likes/replies（A1 の刻みも）、`author_replied_back`（`true`/`false`/`null`＝返信台帳が未採取）、`first_reaction_hours`（自分の返信への最初の反応までの時間・無ければ `null`）。
- 層別: `topic`・`form`・`hour_band` ごとの n と中央値（`min_n` 以上のときだけ）。
- 言わないこと: 「この枝は効いた」。`author_key` は既存の仮名のまま。相手の本文・username は持たない（台帳に無い）。

### A3. 鮮度を本当に出す

- 材料: 採集の記録（`collect` が残す `run_id: collect-<時刻>` の行と成否）。
- 出すもの: snapshot と比較の `data_updated_at` を `null` のままにせず、**`collection: {last_success_at, last_attempt_at, last_attempt_ok, source: "runs"}`** を account ごとに添える。`data_updated_at` の意味（採用観測の最終時刻）は変えない——**別の鍵**にする。
- 記録が無ければ `collection: null`＋`cannot_say` に `collection_records_unavailable`。

### A4. 前回からの差分（cursor）

- `handoff-report ... --since-last-read` で、前回の cursor 以降に変わった項目だけを `changes_since` に先出しする（新しい投稿・承認待ちの増減・inflight の出現/解消・通知 outbox の新しい event・型外の増減）。
- cursor は **`state/<account>/handoff_cursor.json`**。`read_at` と `by` だけでは「承認待ちの増減」「inflight の解消」を比べられない（レビュー指摘・2026-09-18）ので、**前回の状態そのものを保存する**:
  ```json
  {"schema_version": 1, "read_at": "...", "by": "...",
   "snapshot": {"queue_counts": {"draft":0,"approved_waiting":0,"overdue":0,"malformed":0,"unattributed_malformed":0},
                "inflight": {"present": false, "since": null},
                "notification_last_event_id": null, "notification_recorded_state": null,
                "run_last_attempt_at": null, "run_recorded_state": null,
                "last_post_observed_at": null, "sent_count": 0}}
  ```
  `changes_since` は現在の値と `snapshot` の**差**（件数の増減・inflight の出現/解消・outbox の新しい event id・run の新しい試行・最後の投稿の更新・sent の増分）で作る。履歴からの再構成はしない（保存した snapshot と比べるだけ）。
- 書くのは `--mark-read --by <name>` を付けたときだけ。付けなければ何も書かない（既存の read-only を守る）。書くときは今回の `snapshot` で上書き（1 世代だけ持つ）。
- cursor が無い・読めない・`schema_version` が違う: `changes_since: null`＋`cannot_say` に `no_previous_session_cursor`（既存の文言と同じ意味）。壊れた cursor を黙って捨てない（`cannot_say` に `cursor_unreadable`）。
- HTTP（`serve-reports`）からは `--mark-read` に当たる操作を**受け付けない**（読むだけの入口に書く口を作らない）。

### A5. 中央値に散らばりを添える

- 中央値を出す全ての場所に `iqr`（第 3−第 1 四分位）・`min`・`max` を並べる。`n_eligible < min_n` なら全部 `null`。CI・ブートストラップは作らない。
- 四分位の定義は 1 つに固定して `measurement` に書く: **`quartile_method: "exclusive_median_of_halves"`**——値を昇順に並べ、下半分と上半分の中央値を Q1・Q3 とする。n が奇数のとき中央の 1 件は両方の半分に**含めない**（Tukey の hinge は中央を含める別の方法なので、その名前は使わない。2026-09-18 検収 P3-1 で訂正）。
- 標本が少ないとき: **n=1** は `min=max=値`・`iqr=null`。**n=2・3** は `min`/`max` は出すが `iqr=null`（半分の中央値が意味を持たない）。`iqr` を出すのは **n≥4** から。`null` の理由は `spread_reason`（`below_min_n` / `too_few_for_quartiles`）で添える。

### A6. 層別の比較

- `analytics-report --compare-previous` に `--by kind|hour_band|topic` を足す。層ごとに `previous`/`current`/`comparison` を A5 込みで出す。層の鍵は `after_cli` の既存語彙（`topics_mod.KINDS`・`HOUR_BAND_NAMES`・topic の正規化）。
- 小さな層は `min_n` で自動的に `null`。層の合計を全体と突き合わせる行を出す（`n_total` の和＝全体の `n_total`。`kind` 不明は `unknown` 層に入れて落とさない）。

### A7. 枝の形の推移

- 材料: `thth/threadshape.py`（枝の数・深さ・参加者・first_reply_min・author_reply_effect）と返信台帳の時刻。
- 出すもの: 根投稿ごとに `shape_at: {24: {...}, 72: {...}, 168: {...}}`——その時点までに採れた返信だけで形を計算する（返信台帳の `collected_at` で切る）。採取が無い刻みは `null`。
- 言わないこと: 「返信すると伸びる」。`author_reply_effect` は既存どおり n<3 で `null`。

### A8. `cannot_say` をコードにする

- **既存の `cannot_say`（文字列の配列）はそのまま残す**（レビュー指摘: 型を変えると「既存の鍵の意味と値を変えない」と両立しない）。隣に **`cannot_say_details: [{"code": "...", "text": "..."}]`** を足す。`text` は `cannot_say` の同じ位置の文と一致させる（テストで固定）。
- `code` は英小文字とアンダースコア。一覧を `docs/分析レポート_v1.md` に載せ、比較の `missing_reason`・`rejected_observations` の語彙と重ならないよう同じ表にまとめる。

### A9. 施策レポートの「いつ判断できるか」

- changed 群に未成熟があるとき `eligibility_forecast: {"posts_immature": n, "all_eligible_at": <最後の投稿+24h の時刻>, "basis": "posted_at_plus_24h"}`。採取が走る保証はしない（`cannot_say` に `forecast_assumes_collection_runs`）。

### A10. Bluesky・Mastodon で同じ絵が出るか

- 実装ではなく**検証**。masaru-bluesky / masaru-mastodon の実台帳で A1〜A9 を通し、views の無い媒体で `null` が `null` のまま並ぶこと、媒体をまたぐ集計が無いことを記録に残す（thth-notes）。
- 足りなければ直す。直した内容は本書に追記。

2026-09-18 A10 検証注記: VM既存台帳を未配布コード `3a3b4ef` のメモリoverlayで読み取り検証した。masaru-bluesky / masaru-mastodon は対象60日で所有確認済み根投稿・絡みが0件で、views=nullを保持したが非空の実台帳での確認には至っていない。A9は実採用宣言が無く合成fixtureのみ。VM書込・追加API採取・配布はしていない。詳細は [検証記録](検証_v31_A実装_2026-09-18.md)。

## 3. 新しい採集

### C1. 720h の刻み（2.7.0）

- `AGE_MARKS_HOURS` に 720 を足す。帯は `[720, 900)`。
- **採集の対象期間を刻みから導く**（レビュー指摘: 現行の `collect_days` 既定 14 日では 30 日後に届かない）。指標の刻み採集が投稿を見に行く窓は **`max(AGE_MARKS_HOURS) × 1.25 / 24` を切り上げた日数＝38 日**とし、設定ではなく刻みの表から計算する（刻みを足せば窓も伸びる・ずれない）。`collect_days`（既定 14 日）は**返信の取得の窓**として今の意味のまま残す。2 つの窓の役割の違いを `docs/使い方…` と `collect.py` の冒頭に書く。
- 増えるのは**正常時の指標採集が投稿 1 本につき 1 回**（30 日後）。失敗時の再試行（既存の due_marks の「未達の刻みを次回また見る」）と返信の取得は、この変更で回数を変えない。これを検収で数える（偽サーバで 1 投稿 40 日ぶんを回し、insights の呼出が刻みの数だけ・返信取得が `collect_days` の窓の中だけ）。
- 既存の行の `marks` の意味は変えない。`marks_collapsed` の判定も同じ。
- レポート側は A1 の `by_mark` に 720 が自然に増える。

### C2. 投稿行にフォロワー数を添える（2.7.0）

- 各観測行に `context` を写す。**「その日の値」ではなく「採集時刻以前で 48 時間以内の、最新の account 日次行」**を採る（2026-09-18 検収 P2-1 で訂正: 日次行は前日の日付を当日に書くので、「今日の日付の行」は常に存在しない）。形は `{"followers_count": <その行の値>, "followers_count_at": <その行の collected_at（時刻）>, "staleness_hours": <採集時刻との差>, "source": "insights_account"}`。48 時間以内に行が無ければ `context: null`＋`context_reason: "no_recent_daily_record"`。**率は出さない。**
- 新しい API 呼び出しは無い（日次はもう採っている）。書くのは collect の行（採取時点の文脈）で、後から補わない。

### C3. 絡んだ枝のその後（裁定 §5-4 と App Review の結果が先）

- 自分が返信した枝（相手の投稿）について、24h・72h に `/conversation` で**返信数と参加者数だけ**を採る。相手の本文・username は残さない。`author_key` は既存の仮名で。
- 置き場は絡みの台帳の隣（`data/sns/engagements/threads/<root_post>.ndjson` 等）。行は `{collected_at, mark, reply_count, participant_count, source}`。
- **他人の公開投稿の集計を保存する**ことになる。Meta Platform Terms の保存・第三者提供の条項と照合してから。

### C4. 語の定期観測（裁定 §5-4 と App Review の結果が先）

- `before_you_post` の観測（n・投稿者の異なり数・直近時刻・タグ率）を、台帳で決めた語のリストについて 1 日 1 回採り、**集計だけ**を `data/sns/observations/<語>.ndjson` に残す。本文は捨てる。
- C3 と同じ照合が要る。加えて `threads_keyword_search` の Advanced Access が前提。

### C5. Bluesky・Mastodon の刻みを揃える（2.7.0）

- 両媒体の own-post 指標（likes・reposts・replies・Bluesky は quotes）を Threads と同じ `AGE_MARKS_HOURS` で採っているかを確認し、揃っていなければ揃える。views が無い媒体は `null` のまま。

## 4. 検収の条件（Codex が出す・監査は同じ probe で再実行）

- 各項目に「意味を確かめるテスト」: 0 と欠測の区別、帯の外の除外、`min_n` 未満の `null`、媒体をまたがない、率を作らない。
- 変異: 帯の判定・`min_n`・cursor の書込条件・C2 の「後から補わない」を戻すと落ちること。
- 実台帳の smoke（VM・読むだけ）: kopicha・nigamilab・asmon-kanto・masaru-bluesky・masaru-mastodon。
- 文書に鍵と `cannot_say` のコード一覧、`schema_version` の上げ方を書く。対象は次の 3 本:

  - `docs/運用引継ぎレポート_v1.md`
