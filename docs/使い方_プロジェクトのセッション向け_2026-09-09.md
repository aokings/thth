# THTH の使い方 — 各プロジェクトのセッションへ（2026-09-09）

THTH（ThreadsThrower）は **Threads へ投稿するための道具**です。nigamilab・asmon 関東・kopicha・サテライトが共有します。作ったのは THTH セッション（統括 Fable）で、置き場は `~/Developer/thth`、実体は VM（`ssh wt` の `/srv/thth`）。

**この文書だけ読めば使えます。**設計書（`docs/設計_THTH_2026-09-08.md`）は作った側の記録なので、読まなくて構いません。

---

## 0. 呼び方（2026-09-10 に変わりました）

**`ssh wt '...'` はもう要りません。手元でそのまま `thth` と打ってください。**

```bash
thth board
thth queue nigamilab-threads
thth approve /srv/thth/repos/nigamilab/docs/sns/queue
```

`~/.local/bin/thth` が VM の `thth` を呼ぶ薄いラッパです。引数はそのまま渡ります。

**なぜ変えたか。** それまでは、安全で特定の作業をするために**いちばん鈍器な道具（生の `ssh`）**を持たせていました。そのため権限判定に何度も弾かれ、ループの形では止められ、承認 5 本が止まったままになりました。**道具を特定にすれば、許可も特定にできます**——いまは `Bash(thth:*)` の 1 行だけが許可されていて、**生の `ssh` は許可されていません**。

**パスは VM 側（`/srv/thth/repos/<プロジェクト>/...`）で書いてください。**手元の repo パスではありません。

**`*.md` のような glob は使わないでください。**手元のシェルが手元のファイルに対して展開しようとして失敗します。**代わりにディレクトリを渡してください**（`thth approve <queue ディレクトリ>` で、その中の `draft` を全部）。

---

## 1. THTH は何をして、何をしないか

**する**: 本文を受け取って Threads に出す。post_id を書き戻す。返信と数（表示回数・いいね・クリック等）を集めて repo に置く。Meta の上限（24 時間で投稿 250・返信 1,000）を超えないように止める。

**しない**: **何を書くかを決めない。** 文体の規約も、頻度も、時刻も、トピックの選び方も、あなたのプロジェクトのものです。THTH は渡された本文を**整形も切り詰めもせず**そのまま出します。

## 2. いま使える道（同席）

**masaru がその場にいて「これを出して」と言ったとき、すぐ出せます。**承認はその会話の中で済んでいるので、ファイルも承認欄も要りません。

```bash
# 本文をファイルに書いてから（引数で渡さない。シェルの履歴と引用の事故を避けるため）
scp 本文.txt wt:/tmp/post.txt
thth send <あなたのアカウント> --text-file /tmp/post.txt
```

- **`--production` を付けるまで出ません。** 付けずに実行すると「投げるはずの本文」と、末尾に**短い digest**（`digest: ab12cd34ef56` のような 12 桁）を表示して終わります。
- **本当に出すときは、その digest を `--confirm` に渡します**（外部レビュー対応・2026-09-09〜）:
  ```bash
  thth send <あなたのアカウント> --text-file /tmp/post.txt --production --confirm ab12cd34ef56'
  ```
  **`--confirm` を省略した本番、違う digest を渡した本番はどちらも拒否されます。**「見せた本文と送る本文が同じ」であることを機械が確かめるための一手間です。dry-run の出力をそのままコピペするだけで済みます。
### トピックの選び方（2026-09-10・実測にもとづく）

**フォロワーが 0 でも、トピックが合っていれば届きます。**逆に、トピックを外すと誰にも届きません。**新参者にとってトピックは唯一の入口です。**

実測（同じ日・同じ Threads・フォロワーはどちらもほぼ 0）:

| | 表示回数 |
|---|---|
| asmon `中学受験` 6 本 | **202〜574** |
| nigamilab `コーヒー好きな人と繋がりたい` | **1** |
| nigamilab トピック無し | **1** |

**約 400 倍です。**同じ `中学受験` の中での書き方の差は 202〜574（約 2.8 倍）。**トピック選びのほうが 2 桁効きます。文面を磨く前に、まずトピックです。**

#### 効いた形・外した形（実際に見てきたもの）

| | 例 | 何が起きたか |
|---|---|---|
| ✅ **人がいま実際にやっている行動の名前** | `中学受験`・`学校説明会` | 服装・個別相談・確約の実務話が数時間前から並ぶ。読者の関心とそのまま重なる |
| ✅ **物の名前** | `チョコレート` | 1.6万いいね級の投稿が並ぶ。母数が大きい |
| ❌ **分野・概念の名前（カテゴリ）** | `子育て`・`教育`・`学校選び`・`大学付属校`・`学校見学` | **どれも普通の日本語なのに検索結果 0 件。**「大きい語だから人がいる」は成り立ちません（kanto セッションが 6 語を確認・2026-09-10） |
| ✅ **当事者が使う略語** | `中受` | 4 日前に「親の伴走はどこまで」10 いいね 7 返信。**当事者は略語で集まります** |
| ⚠️ **抽象語・感覚語** | `苦味` | 人はいるが、話題が「臭い・香水」に流れる。**意味が拡散する** |
| ❌ **多義語の専門語** | `精製` | **レアアース・タングステン・重加工の場**だった。コーヒーの精製の話は別業界に落ちる |
| ❌ **漢語の専門語** | `六大茶類` | **台湾茶・中国茶の繁体字が主**。日本語の読者は少数 |
| ❌ **「〜と繋がりたい」型** | `コーヒー好きな人と繋がりたい` | **1 view。**X や Instagram の作法で、Threads では場になっていない |
| ❌ **自分で作った語** | `コピチャ観測所` | 誰も見ていない。**トピックは既にある場所に入るもので、作るものではありません** |

#### コツ

1. **人が既に使っている語を選ぶ。**トピックは「作る」ものではなく「入る」ものです。
2. **「大きい語なら安全」は成り立ちません。**`子育て`・`教育`・`学校選び` はどれも普通の日本語ですが、topic としては **0 件**でした。効いたのは `チョコレート` のような**物の名前**と、`中学受験`・`中受` のような**行動の名前**です。**分野や概念の名前（カテゴリ）は、大きくても場になっていないことが多い。**
3. **当事者の略語を試す。**`中受` は `中学受験` とは別の場で、当事者が集まっていました。**自分たちが読者だったら何と打つか**を考えてください。
4. **狭い語も人がいなくなります。**`エチオピアコーヒー`・`中学受験算数` のような複合語は、精度が上がるのではなく誰もいません。
5. **多義語は必ず確かめる。**`精製`・`焙煎`・`抽出`——コーヒーの語は工業の語でもあります。
6. **漢語の熟語は中国語圏に行きます。**`六大茶類`・`製茶` など。日本語で届けたいなら `お茶`・`紅茶`。
7. **散らすより寄せる。**asmon は `中学受験` 1 つで 6 本すべて 200 以上。**当たりを見つけたら繰り返してください。**28 本に 28 種は、当たりを 1 つも活用していない形です。
8. **探索は 1 本ずつで足ります。**差が 400 倍なら、1 本落として翌日 `thth topics <account>` を見れば分かります。
9. **1 投稿 1 トピック**（API の制約）。`.` と `&` は使えません。1〜50 字。

#### 確かめ方

**THTH からは確かめられません**（トピック検索の権限が降りてこない）。**Threads にログインした状態で**、ブラウザでこれを開いてください。

```
https://www.threads.com/search?q=<トピック>&filter=topic
```

**見るのは 3 つです。** ①直近の投稿が数時間〜数日前か ②話している人が自分の読者と重なるか ③言語が合っているか。**「何件あるか」より「誰がいるか」です。**数字だけ見ると `精製` は「人がいる」に見えます。

#### 確かめた結果は THTH に残してください

```bash
thth topics --note 精製 --verdict mismatch --audience "レアアース・重加工" --by "claude（<プロジェクト> セッション）"
```

`--verdict` は `alive`（合っている）／`mismatch`（人はいるが別の業界・言語）／`dead`（人がいない）。**全プロジェクトで共有されます**——`精製` が鉱物の場であることは、誰にとっても同じ事実だからです。

```bash
thth topics <account> --plan     # どのトピックに何本賭かっているか・未確認は何本か
thth topics <account>            # 実際にどれだけ見られたか（トピック別）
```

**承認の一段目にも判定が出ます。**未確認なら「未確認です」と言います。

- **トピックの効き目の範囲**（2026-09-10 追記）: 付けたトピックのページに、その投稿が並びます。**そのページを見ている人にだけ届きます。**THTH からはトピックを検索できない（権限が降りてこない）ので、**実在も規模も測れません**。数の収集（T3・T4）で測れるようになるのは「自分が付けたトピックの投稿がどれだけ見られたか」までで、「そのトピックに何人いるか」は測れません。**手をかけるなら、種類を増やすより「人がいることを確かめた少数」に寄せるほうが確実です。**
- **トピックに人がいるかは、付ける前にブラウザで確かめてください**（2026-09-10 追記）。THTH からは確かめられません（トピック検索の権限が tester に降りてこない・§3）。**Threads にログインした状態で `https://www.threads.net/search?q=<トピック>&filter=topic` を開くと、そのトピックの投稿が並びます。**0 件のトピックを付けても誰にも届きません（実際に「苦味」が 0 件でした）。ログイン前だと殻しか返らないので、必ずログインした状態で見てください。
- トピックを付けるなら `--topic 苦味`（1 投稿に 1 つ・1〜50 字・`.` と `&` は不可。先頭の `#` は機械が落とします）。トピックを変えると digest も変わるので、topic を付け忘れて dry-run した digest はそのままでは使えません。
- 返信するなら `--reply-to <相手の post_id>`。これも digest に含まれます。
- 出ると `post_id` が返ります。

**守ってほしいこと**: **masaru が読んだ本文と、出す本文を同じにしてください。**「だいたいこんな感じで」で送らない。表示 → masaru が読む → 出す、の順を崩さない。THTH 側は渡されたものをそのまま出しますし、`--confirm` の digest がその機械的な裏付けになります。

## 4. 留守中に出す道（**2026-09-10 から本番稼働**）

投稿を 1 ファイル 1 本で `docs/sns/queue/<日付>-<slug>.md` に書きます。

**手順は 3 つです。**

1. あなたが下書きを書く（`status: draft`）→ **commit して push する**
2. masaru が `thth approve` する（承認が commit として repo に入り、push されます）
3. `publish_at` の時刻を過ぎた最初の実行（10 分刻み）で出る

**THTH はあなたの repo の `main` に commit・push します**（承認・投稿後の書き戻し）。**あなたの着地スクリプトは、push の直前に必ず fetch してください**（`commit → fetch → rebase → push`）。2026-09-10 に、承認の push と着地が重なって main に取り残しができた事故がありました。**外部から同じ `main` に書く相手がいる**、というのが THTH で新しく増えた前提です。競合したら黙って上書きせず止めてください（`reset --hard` は静かに壊します）。

**commit して push してください。**THTH は「同期を確認した commit の中身と一致するファイル」しか出しません。作業ツリーに置いただけのものは `unverified_content` として board に出て、投稿されません（ファイルは消しません）。

```markdown
---
thth: 1
account: nigamilab-threads
publish_at: 2026-09-10T08:00:00+09:00
status: draft
approved_sha:
approved_at:
topic: 苦味
reply_to:
post_id:
posted_at:
---
# 経緯や下書きのメモ（THTH は読みません）

## threads

ここが実際に投稿される本文です。500 字まで。
https://example.com/
```

| 欄 | 誰が書くか | 意味 |
|---|---|---|
| `thth: 1` | 固定 | 書式の版 |
| `account` | あなた | 宛先。§6 の表のとおり |
| `publish_at` | あなた | **`+09:00` 必須。** この時刻以降の最初の実行で出る（刻みは 10 分） |
| `status` | あなたが `draft` まで／**`approved` は masaru が `thth approve` で書く** | `draft` → `approved` で「留守中に出てよい」 |
| `approved_sha`・`approved_at`・`approved_by`・`post_id`・`posted_at` | **THTH が書く。行ごと省略して構いません**（`thth approve` が無ければ足します）。テンプレを短くしたいなら書かないでください | 承認した瞬間の本文・account・reply_to・topic・publish_at から計算した hash と、承認した時刻・承認者 |
| `topic` | あなた | 省略可。**承認後に変えると `approved_sha` と食い違って出なくなります**（下記） |
| `reply_to` | あなた | 返信にするなら相手の post_id。これも承認後に変えると出なくなります |
| `post_id`・`posted_at` | **THTH** | 出たあとに書き戻す。付いたファイルは二度と出ない |

### 承認は `thth approve` で（2026-09-09〜・外部レビュー対応）

以前は `status: approved` と手で書くだけでした。いまは **masaru が `thth approve <ファイル>` を実行する**運用に変わりました:

```bash
thth approve /srv/thth/repos/<プロジェクト>/docs/sns/queue/2026-09-10-example.md
```

- 実行すると `status: approved`・`approved_sha`・`approved_at` の 3 行が書かれます。
- **承認したあとに本文・`account`・`reply_to`・`topic`・`publish_at` のどれか 1 つでも書き換えると、その投稿は出なくなります**（`approval_stale` として `thth queue`/`thth board` に理由付きで出ます）。承認は「そのときの中身」に結び付いています——書き直したら、もう一度 `thth approve` してください。
- **手で `status: approved` とだけ書いても出ません**（`approved_sha` が無いので同じ扱いになります）。
- 形式検査（`thth lint`）に通らないファイルは `thth approve` 自体が拒否します。
- **`thth approve` は、そのファイルを commit して push します**（2026-09-10〜）。承認した瞬間に repo の履歴に残ります。push できなかったときは「このままでは投稿されません」と述べて非ゼロで終わるので、その場で分かります。
- **queue ファイルは commit して push してください。**THTH は「同期を確認した commit の中身と一致するファイル」しか出しません。作業ツリーに置いただけ・commit していない変更が残っている投稿は、`unverified_content` として `thth queue`／`thth board` に出て、投稿されません（**ファイルは消しません**。commit すれば出るようになります）。撤回した投稿がどこかから復元されて出てしまう事故を防ぐためです。

### 承認は二段です（2026-09-10〜・**対話の中で承認できます**）

**あなた（各プロジェクトのセッション）が承認して構いません。** ただし**必ず二段で**行ってください。

```bash
# 一段目: 本文を全文表示して、何も書き換えずに終わります（exit 1）
thth approve <ファイル>
```

**一段目の出力をそのまま masaru に見せてください。**出す本文・account・publish_at・topic・reply_to と、末尾に `digest: ab12cd34ef56` が出ます。

```bash
# 二段目: masaru が「いいよ」と言ったら、一段目が出した digest を渡します
thth approve <ファイル> --confirm ab12cd34ef56 --by "claude（<プロジェクト> セッション）"
```

**この二段が防ぐのは「A を見せて B を承認する」ことです。**表示と承認の間に本文・account・reply_to・topic・publish_at のどれかが変われば digest が変わり、二段目は通りません。

**`--by` は必須です**（2026-09-10〜）。front-matter（`approved_by`）と commit に残ります。省略すると承認しません——以前は VM の unix ユーザー名（`wt`）が既定で入り、**masaru の判断が `wt` として記録されていました**。環境変数 `THTH_ACTOR` でも指定できます。

**名乗り方はそろえてください**: `masaru` / `claude（<プロジェクト> セッション）`。いまのところ機械では検査していないので、表記ゆれはそのまま残ります。

**承認済みのファイルにもう一度 `approve` を当てると、`--by` だけ更新できます**（本文・topic・publish_at を触っていなければ digest は同じ＝masaru が読んだ本文のまま）。表記ゆれを直す道として使えます。

**守ってほしいこと**: **本文を見せずに `--confirm` を渡さないでください。**digest はあなた自身でも計算できてしまうので、この仕掛けは masaru に見せたことを保証しません。**見せる責任はあなたにあります。**

**`thth approve` は VM 側の `git pull` を自分でやります**（2026-09-10〜）。承認の前に手で pull する必要はありません。同期できなければ承認を断ります。

### 複数本をまとめて承認する（2026-09-10〜）

**ファイルを並べても、ディレクトリを渡してもかまいません。**`thth lint` も同じです。**`*.md` は使わないでください**（手元のシェルが展開しようとして失敗します）。ディレクトリを渡すと、その中の `status: draft` の `.md` が対象になります（承認済みは対象外。何本外したかを一段目が述べます）。

```bash
# 一段目: 全部の本文を続けて表示し、最後に「束の digest」を 1 つ出す
thth approve /srv/thth/repos/asmon/docs/sns/queue

# 二段目: 同じファイルを並べて、束の digest を渡す
thth approve /srv/thth/repos/asmon/docs/sns/queue --confirm <束のdigest> --by "claude（asmon セッション）"
```

- **どれか 1 本でも中身が変われば束の digest が変わります。**保証は本数が増えても崩れません。
- **1 本でも lint に落ちる・`post_id` が付いているものがあれば、1 本も承認しません**（半分だけ承認された状態を作らないため）。
- `--json` を付けると**ファイルごとの digest** も返します。**どれが変わったかを知りたいときはこれ**（全部を一段目で回し直す必要はありません）。

**予定時刻を過ぎた原稿は、一段目が警告します**（2026-09-10〜）。起草する人と承認する人が別なので、承認までに時刻が過ぎるのは普通に起きます。

- `⚠ **承認するとすぐ出ます**` — 予定時刻を過ぎています。次の実行（10 分以内）で出ます。
- `⚠ **承認しても出ません**` — `stale_days`（既定 7）を超えています。`publish_at` を直してください。

複数本まとめたときは、末尾にも「予定時刻を過ぎているものが N 本あります」とまとめて出ます。

### 承認を取り消す（`thth revoke`・2026-09-10〜）

**出る前なら止められます。**Threads の投稿は API から削除できない（権限が降りてこない）ので、**これが唯一の安全弁**です。

```bash
thth revoke <ファイル> --reason "連載の順を変えた" --by "claude（asmon セッション）"
```

- `status` が `draft` に戻り、`approved_sha` などが消えます。**本文には触りません**——直してそのまま `thth approve` し直せます。
- `revoked_at`・`revoked_by`・`revoked_reason` が残ります。
- **もう出てしまったもの（`post_id` あり）は取り消せません。**その場合は Threads の画面から手で消してください。
- **意図して止めたもの（`draft` に戻る）と、うっかり書き換えたもの（`approval_stale` で要確認に出る）は board で区別できます。**
- **取り消したあと承認し直すと、`revoked_at`・`revoked_by`・`revoked_reason` は消えます。**front-matter は「いまの状態」を表す欄なので、これは意図した挙動です。**「一度引っ込めた」履歴は commit 側に残ります**（`git log -- <ファイル>`）。

### これから何が出るかを日付順に見る（`thth schedule`・2026-09-10〜）

```bash
thth schedule <あなたのアカウント> --days 14
```

承認済み（済）と下書き（未）の両方を、時刻順に並べます。時刻を過ぎているものには印が付きます。読むだけです。

- 本文は **`## threads` の節だけ**。その上には何を書いても読みません。
- 検査は先に走らせられます: `thth lint <ファイル>`。文字数・書式・トピックの不備を名指しで返します。**450 字を超えると警告**が出ます（絵文字の数え方が公式と厳密に一致する保証がないので、境界に座らないため）。
- 長すぎても**切り詰めません**。落として理由を返します。
- timer の unit（`.timer`）は手で書かず、`thth systemd <account>` が台帳（`tick_minutes`）から生成します。

## 5. 自分たちで決めてよいこと

台帳（`~/Developer/thth/accounts/<アカウント>.json`）の次の 5 つは**あなたのプロジェクトの判断**です。いま入っている値は統括の当て推量なので、合わなければ言ってください。

| 設定 | いまの値 | 意味 |
|---|---|---|
| `min_interval_hours` | **0（制限なし）** | 前の投稿からこれだけ空ける。**0 より大きくすると、あなたが書いた `publish_at` より間隔のほうが勝ちます**（9 時・12 時・15 時と書いても 12 時のものが出ません）。意図してそうしたいときだけ入れてください |
| `quiet_hours` | **null（制限なし）** | この時間帯は出さない。**入れると、その時間帯に指定した `publish_at` は出ません** |
| `max_per_run` | 1 | 1 回の実行で出す本数。実行は 10 分ごとなので、同時刻に何本溜まっていても 10 分おきに 1 本ずつ出ます |
| `stale_days` | 7 | **`publish_at` からこれだけ過ぎたものは出しません**（要確認として board に出ます）。VM が長く止まって復帰しても、**古い投稿が一気に出ることはありません**。長期の連載を組むときはここを見てください |
| `tick_minutes` | 10 | timer の刻み。`publish_at` の遅れの上限になる。変えたら `thth systemd <account>` で unit を作り直す |
| `hashtags` | 研究所のみ `false` | 本文中の `#` 語を許すか。**トピックとは別物** |

基盤が強制するのは **Meta の上限だけ**です。頻度も時刻も本数も、あなたたちの声の作り方です。

## 7. 困ったとき

- **「inflight が残っています」で止まる**: 前回「出たか出ていないか分からない」失敗があったということです。**勝手に消さないでください。** Threads の画面で出たかどうかを確かめて、統括（THTH セッション）に伝えてください。二重投稿を防ぐための止まり方です。「送った本文と repo の本文が食い違います」と一緒に出ているときは、公開している最中に本文が書き換わった合図です——同じく人が直すまで止まったままにします。
- **「既に実行中です」**: 別の実行と重なっています。少し待って再実行してください。同じ repo（clone）を共有する別アカウントの実行と重なっていても同じメッセージで止まります。
- **`approval_stale` で出ない**: 承認したあとに本文・トピック・返信先・予約時刻のどれかが変わりました。中身を確認して、必要ならもう一度 `thth approve` してください。
- **指定した時刻を 1 時間過ぎても出ていないものは `thth board` の要確認に出ます**（理由付き）。`rehearsal` は「台帳がまだ本番になっていない」、`min_interval`・`quiet_hours` は「あなたが入れた設定が指定時刻より勝っている」、`overdue` は「理由が無いのに出ていない」（timer が止まっている等）。
- **トークンの残り日数は `thth board` に出ます**（`token_state`・`token_remaining_days`）。更新は THTH が自分で行うので、あなたのすることはありません。`expired`・`no_token`・`refresh_failed` が出ていたら masaru に伝えてください（その状態では 1 本も出ません）。
- **`unverified_content` で出ない**: そのファイルが、同期を確認した commit の中身と一致しません（commit していない変更がある・追跡されていない・`.gitignore` されている・symlink になっている、など）。中身を確認して commit・push してください。
- **本文が長すぎる／トピックが弾かれた**: 理由が名指しで出ます。直して出し直してください。
- **それ以外**: `~/Developer/thth` の THTH セッションへ。設計と実装の責任はそちらにあります。

## 8. 頼みたいこと

1. **使ってみて、書きにくいところを言ってください。**書式はまだ 1 つの repo にも配っていないので、いま変える分には安いです。あとから変えると全 repo を直すことになります。
