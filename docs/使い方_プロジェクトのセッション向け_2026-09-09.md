# THTH の使い方 — 各プロジェクトのセッションへ（2026-09-09）

THTH（ThreadsThrower）は **Threads へ投稿するための道具**です。nigamilab・asmon 関東・kopicha・サテライトが共有します。作ったのは THTH セッション（統括 Fable）で、置き場は `~/Developer/thth`、実体は VM（`ssh wt` の `/srv/thth`）。

**この文書だけ読めば使えます。**設計書（`docs/設計_THTH_2026-09-08.md`）は作った側の記録なので、読まなくて構いません。

---

## 0. 呼び方（2026-09-10 に変わりました）

**`ssh wt '...'` はもう要りません。手元でそのまま `thth` と打ってください。**

```bash
thth board
thth queue nigamilab-threads
thth approve /srv/thth/repos/nigamilab/docs/sns/queue
```

`~/.local/bin/thth` が VM の `thth` を呼ぶ薄いラッパです。引数はそのまま渡ります。

**なぜ変えたか。** それまでは、安全で特定の作業をするために**いちばん鈍器な道具（生の `ssh`）**を持たせていました。そのため権限判定に何度も弾かれ、ループの形では止められ、承認 5 本が止まったままになりました。**道具を特定にすれば、許可も特定にできます**——いまは `Bash(thth:*)` の 1 行だけが許可されていて、**生の `ssh` は許可されていません**。

**パスは VM 側（`/srv/thth/repos/<プロジェクト>/...`）で書いてください。**手元の repo パスではありません。

**`*.md` のような glob は使わないでください。**手元のシェルが手元のファイルに対して展開しようとして失敗します。**代わりにディレクトリを渡してください**（`thth approve <queue ディレクトリ>` で、その中の `draft` を全部）。

---

## 1. THTH は何をして、何をしないか

**する**: 本文を受け取って Threads に出す。post_id を書き戻す。返信と数（表示回数・いいね・クリック等）を集めて repo に置く。**Meta の上限（24 時間で投稿 250・返信 1,000）は基盤では止めていません**（2026-09-12 訂正）。

**しない**: **何を書くかを決めない。** 文体の規約も、頻度も、時刻も、トピックの選び方も、あなたのプロジェクトのものです。THTH は渡された本文を**整形も切り詰めもせず**そのまま出します。

## 2. いま使える道（同席）

**masaru がその場にいて「これを出して」と言ったとき、すぐ出せます。**承認はその会話の中で済んでいるので、ファイルも承認欄も要りません。

```bash
# 本文をファイルに書いてから（引数で渡さない。シェルの履歴と引用の事故を避けるため）
scp 本文.txt wt:/tmp/post.txt
thth send <あなたのアカウント> --text-file /tmp/post.txt
```

- **`--production` を付けるまで出ません。** 付けずに実行すると「投げるはずの本文」と、末尾に**短い digest**（`digest: ab12cd34ef56` のような 12 桁）を表示して終わります。
- **本当に出すときは、その digest を `--confirm` に渡します**（外部レビュー対応・2026-09-09〜）:
  ```bash
  thth send <あなたのアカウント> --text-file /tmp/post.txt --production --confirm ab12cd34ef56
  ```
  **`--confirm` を省略した本番、違う digest を渡した本番はどちらも拒否されます。**「見せた本文と送る本文が同じ」であることを機械が確かめるための一手間です。dry-run の出力をそのままコピペするだけで済みます。

**thth は VM で動きます。** ファイルを渡す引数（`--text-file`・`lint`/`approve`/`preview`/`revoke` に渡すパス・`thth topics suggest` の `--article` 等）は VM 側のパスで書いてください——手元（Mac）のパスは VM には無いので、渡すと断られます。手元で書いた原稿は push してから、`thth pull <account>`（または `thth approve`）で VM に取り込まれます。取り込みがまだ済んでいなければ `thth queue` が遅れを教えます。

#### コツ

0. **一致より、人がいるかが先。**（kanto セッションの自己訂正 2026-09-11）

   > 8 語が 0 件だったのを「トピックの選び方が悪かった」と報告しましたが、**実際には『内容と一致する語を選ぶ』という私の方針そのものが間違っていました**（一致より、人がいるかが先）。

   `中学受験算数` は記事の内容と完全に一致します。**それでも 0 件です。**内容から語を作ると、たいてい誰もいない語になります。**先に人がいる場所を見つけて、そこに合う記事を出す。**順番が逆でした。

1. **人が既に使っている語を選ぶ。**トピックは「作る」ものではなく「入る」ものです。
2. **「大きい語なら安全」は成り立ちません。**`子育て`・`教育`・`学校選び` はどれも普通の日本語ですが、topic としては **0 件**でした。効いたのは `チョコレート` のような**物の名前**と、`中学受験`・`中受` のような**行動の名前**です。**分野や概念の名前（カテゴリ）は、大きくても場になっていないことが多い。**
3. **当事者の略語を試す。**`中受` は `中学受験` とは別の場で、当事者が集まっていました。**自分たちが読者だったら何と打つか**を考えてください。
4. **狭い語も人がいなくなります。**`エチオピアコーヒー`・`中学受験算数` のような複合語は、精度が上がるのではなく誰もいません。
5. **多義語は必ず確かめる。**`精製`・`焙煎`・`抽出`——コーヒーの語は工業の語でもあります。
6. **漢語の熟語は中国語圏に行きます。**`六大茶類`・`製茶` など。日本語で届けたいなら `お茶`・`紅茶`。
7. **散らすより寄せる。**asmon は `中学受験` 1 つで 6 本すべて 200 以上。**当たりを見つけたら繰り返してください。**28 本に 28 種は、当たりを 1 つも活用していない形です。
8. **探索は 1 本ずつで足ります。****差を測るなら経過時間を揃えてから**（上の訂正）。1 本落として翌日 `thth topics <account>` を見れば分かります。
9. **1 投稿 1 トピック**（API の制約）。`.` と `&` は使えません。1〜50 字。

#### 確かめ方

**THTH からは確かめられません**（トピック検索の権限が降りてこない）。**Threads にログインした状態で**、ブラウザでこれを開いてください。

```
https://www.threads.com/search?q=<トピック>&filter=topic
```

**見るのは 3 つです。** ①直近の投稿が数時間〜数日前か ②話している人が自分の読者と重なるか ③言語が合っているか。**「何件あるか」より「誰がいるか」です。**数字だけ見ると `精製` は「人がいる」に見えます。

#### 確かめた結果は THTH に残してください

```bash
thth topics --note 精製 --verdict mismatch --audience "レアアース・重加工" --by "claude（<プロジェクト> セッション）"
```

`--verdict` は `alive`（合っている）／`mismatch`（人はいるが別の業界・言語）／`dead`（人がいない）／`unknown`（未確認）。**全プロジェクトで共有されます**——`精製` が鉱物の場であることは、誰にとっても同じ事実だからです。

**観測は観測者ごとに並びます**（2026-09-12 に変えました）。以前は**語ごとに最後の 1 行**しか読んでいなかったので、**別のプロジェクトが同じ語を書くと、前の観測が画面から消えていました**。いまは消えません——**あなたの観測はあなたの名前で並びます**（観測者の鍵は `account`、無ければ `--by`、それも無ければ `(記録なし)`）。

**記録すると `記録 ID`（`note_id`）が返ります。間違えたら打ち消してください。**

```bash
thth topics retract-note <note_id> --reason "誤記録" --by "<あなた>"
```

**行は消えません**（打ち消しの行が 1 本増えるだけ）。読み口からは消え、`thth topics history <語>` に「**打ち消し済み**」として残ります。

```bash
thth topics history <語>         # その語を誰がどう見たか（全観測者・全行・新しい順）
thth topics <account> --plan     # どのトピックに何本賭かっているか・未確認は何本か
thth topics <account>            # 実際にどれだけ見られたか（トピック別）
```

**`thth topics <account> --advise --json` の鍵が変わりました。** `audience` / `audience_account` / `audience_by` は**廃止**し、`observations`（`note_id` / `audience` / `account` / `by` / `checked_at` / `status` / `kind` を持つ配列・最大 5 件・新しい順）と `observations_more`（**`--json` に載せなかった件数＝総数 − 5**）になりました。人向けの画面は **1 語 2 件＋「ほか k 件」**（総数 − 2。`observations_more` とは基準が違う別の数です）で、全部は `history` で読めます。

**承認の一段目にも判定が出ます。**未確認なら「未確認です」と言います。

**記事ごとに選ぶための道具が入りました**（2026-09-11 追記）:

```bash
thth topics suggest <queue ファイル>       # 何が足りないかを聞く（読むだけ・原稿も Git も触りません）
```

**位置引数はあなたの原稿そのものではなく、queue ファイルのパスです。** 記事本文は
`--article`（または `--article-json-stdin`）、候補比較は `--proposal`（または
`--proposal-json-stdin`）のフラグで渡します（正本は `thth topics suggest --help`）。
**queue ファイル 1 個だけを渡すと、`--article` が無いので `candidates: []` が返るだけです**
（`status: needs_article` で、次に要る資料が `required_actions` に出ます）。

記事本文と候補比較を渡すと、**引用が本文に在るか・観測が新しいか・投稿者が偏って
いないか**を検査して、`recommended / provisional / abstained` と**足りないもの**を
返します。**候補を作るのも順位を付けるのも THTH ではなくあなたです。**
判断のしかたの取り決めは `docs/手順_LLM_トピック選定.md` にあります。
既存の 22 語はそのまま使えます（語彙だけ `alive→suitable` 等に読み替わります。
**入れ直す必要はありません**）。

- **トピックの効き目の範囲**（2026-09-10 追記）: 付けたトピックのページに、その投稿が並びます。**そのページを見ている人にだけ届きます。**THTH からはトピックを検索できない（権限が降りてこない）ので、**実在も規模も測れません**。数の収集（T3・T4）で測れるようになるのは「自分が付けたトピックの投稿がどれだけ見られたか」までで、「そのトピックに何人いるか」は測れません。**手をかけるなら、種類を増やすより「人がいることを確かめた少数」に寄せるほうが確実です。**
- **トピックに人がいるかは、付ける前にブラウザで確かめてください**（2026-09-10 追記）。THTH からは確かめられません（トピック検索の権限が tester に降りてこない・§3）。**Threads にログインした状態で `https://www.threads.com/search?q=<トピック>&filter=topic` を開くと、そのトピックの投稿が並びます。**0 件のトピックを付けても誰にも届きません（実際に「苦味」が 0 件でした。**上の表は「人はいるが話題が拡散する」と書いていて食い違っています**——どちらが正しいかは確かめ直していません・2026-09-12）。ログイン前だと殻しか返らないので、必ずログインした状態で見てください。
- トピックを付けるなら `--topic 苦味`（1 投稿に 1 つ・1〜50 字・`.` と `&` は不可。先頭の `#` は機械が落とします）。トピックを変えると digest も変わるので、topic を付け忘れて dry-run した digest はそのままでは使えません。
- 返信するなら `--reply-to <相手の post_id>`。これも digest に含まれます。
- 出ると `post_id` が返ります。

**守ってほしいこと**: **masaru が読んだ本文と、出す本文を同じにしてください。**「だいたいこんな感じで」で送らない。表示 → masaru が読む → 出す、の順を崩さない。THTH 側は渡されたものをそのまま出しますし、`--confirm` の digest がその機械的な裏付けになります。

### 状態を見る

```bash
thth queue <あなたのアカウント>   # 数と「次に出るもの」
thth board   # 全アカウント＋トークンの残り日数
```

### 語で公開投稿を探す・言及・プロフィール（2026-09-14〜・v2.1）

```bash
thth topics <あなたのアカウント> --search <語> [--recent] [--json]   # 観測の材料（投稿者の異なり数・直近の時刻・タグ付きの割合）
thth mentions <あなたのアカウント> [--json]                          # 自分への言及（3 媒体・読むだけ。`collect` の inbox 採集は Threads のみ）
thth profile <あなたのアカウント> <username> [--json]                # 公開プロフィール（標準アクセスでは Meta 公式 4 つだけ）
```

- **`--search` の本文は画面に 1 行ずつ出すだけで、どこにも保存しません。**`--note … --status … --audience …` を記録するのは人です。

**絡みに行く先の指し方**（2026-09-15〜・`--search` の一覧に足しました）

1. `thth topics <あなたのアカウント> --search <語> [--recent] [--json]` で候補を並べます。一覧の 1 行は **投稿の時刻・@投稿者・`post_id`・返信・印** で、その下に **permalink と本文の先頭 60 字**（表示するだけ・保存しません）。
2. **返信の欄**は、数を返す媒体はその数、Threads の検索は `有` / `無` だけ（**数は返りません**）、判らなければ `—`。**`—` は 0 ではありません。** 上の要約にある「返信だった投稿」は別のこと（それ自体が返信である投稿の数）です。
3. **印**は、あなたの queue に `reply_to: <post_id>` を持つ原稿があるという意味です。`[返信済]`＝出た（posted）／`[承認済]`＝承認したが未送（approved）／`[下書き]`＝下書き（draft）。**印が無い行は「この queue に原稿が見当たらない」**で、「誰も返していない」ではありません。queue が読めないときは印を出さずにそう言います。
4. 絡むなら、下書きの front-matter に `reply_to: <post_id>` を書きます（§4 の書式。**他人の公開投稿にも付けられます**）。あとはいつもどおり `thth lint` → `thth approve`（二段）→ `thth throw`。
5. **（2026-09-16〜・v2.2 の次）出した結果を後で測れるようにする**: 一覧の `--json` にある `author_key`（相手の仮名・16 桁）を下書きの `reply_to_author_key:` に写し、`found_by: where_to_appear`（検索で見つけた）か `manual`（自分で見つけた）・`mention`（言及から）を書いておくと、出した瞬間に **絡みの台帳**（`data/sns/engagements/`）に「どの枝の・誰への返信か」が 1 行残ります（相手の本文・名前は残しません）。git への commit は投稿の commit とは別で、**次の採取（`thth collect`・最大 10 分の遅れ）**で入ります。あとから `thth after <account> --json`（project 全体は `thth after --project <project> --json`、MCP なら `after_you_posted`）で、所有を確認できた実測台帳の根投稿は `posts`、絡みに行った返信は `engagements` に分けて並びます。`--project` は `by_account` に節を並べるだけで、account をまたぐ合計・比率・順位は作りません。取れていない 24 時間の刻みや views は `null`（0 ではありません）。`--kind` は現在の topic shelf の分類で、原稿構成の `form` や投稿時点の型ではありません。どちらの鍵も任意で、書かなくても投稿は出ます。
6. 出した返信はあなたの投稿なので、`thth collect` が閲覧数・いいね・返信を採ります。どの枝に絡んだら反応があったかは `thth replies` と実測で追えます。**`thth replies` が読む返信の台帳（自分の投稿への相手の返信）は絡みの台帳とは別物**で、こちらは相手の `username` と本文をそのまま残します。
7. **どの投稿に絡むかを決めるのは THTH ではありません。** 道具が出すのは材料（誰が・いつ・どれくらい返信されているか・もう返したか）と門（承認）だけです。**Threads API に「いま盛り上がっている」を返す口はありません**——熱さは TOP 順・直近の時刻・返信の多さからの推測にとどまります。`--json` の `posts[]`（`post_id`・`permalink`・`timestamp`・`author`・`replies`・`has_replies`・`replied`）に本文は入りません。

## 4. 留守中に出す道（**2026-09-10 から本番稼働**）

投稿を 1 ファイル 1 本で `docs/sns/queue/<日付>-<slug>.md` に書きます。

**手順は 3 つです。**

1. あなたが下書きを書く（`status: draft`）→ **commit して push する**
2. masaru が `thth approve` する（承認が commit として repo に入り、push されます）
3. `publish_at` の時刻を過ぎた最初の実行（10 分刻み）で出る

**THTH はあなたの repo の `main` に commit・push します**（承認・投稿後の書き戻し）。**あなたの着地スクリプトは、push の直前に必ず fetch してください**（`commit → fetch → rebase → push`）。2026-09-10 に、承認の push と着地が重なって main に取り残しができた事故がありました。**外部から同じ `main` に書く相手がいる**、というのが THTH で新しく増えた前提です。競合したら黙って上書きせず止めてください（`reset --hard` は静かに壊します）。

**commit して push してください。**THTH は「同期を確認した commit の中身と一致するファイル」しか出しません。作業ツリーに置いただけのものは `unverified_content` として board に出て、投稿されません（ファイルは消しません）。

### 承認は `thth approve` で（2026-09-09〜・外部レビュー対応）

以前は `status: approved` と手で書くだけでした。いまは **masaru が `thth approve <ファイル>` を実行する**運用に変わりました:

```bash
thth approve /srv/thth/repos/<プロジェクト>/docs/sns/queue/2026-09-10-example.md
```

- 実行すると `status: approved`・`approved_sha`・`approved_at` の 3 行が書かれます。
- **承認したあとに本文・`account`・`reply_to`・`topic`・`publish_at` のどれか 1 つでも書き換えると、その投稿は出なくなります**（`approval_stale` として `thth queue`/`thth board` に理由付きで出ます）。承認は「そのときの中身」に結び付いています——書き直したら、もう一度 `thth approve` してください。
- **手で `status: approved` とだけ書いても出ません**（`approved_sha` が無いので同じ扱いになります）。
- 形式検査（`thth lint`）に通らないファイルは `thth approve` 自体が拒否します。
- **`thth approve` は、そのファイルを commit して push します**（2026-09-10〜）。承認した瞬間に repo の履歴に残ります。push できなかったときは「このままでは投稿されません」と述べて非ゼロで終わるので、その場で分かります。
- **queue ファイルは commit して push してください。**THTH は「同期を確認した commit の中身と一致するファイル」しか出しません。作業ツリーに置いただけ・commit していない変更が残っている投稿は、`unverified_content` として `thth queue`／`thth board` に出て、投稿されません（**ファイルは消しません**。commit すれば出るようになります）。撤回した投稿がどこかから復元されて出てしまう事故を防ぐためです。

### 承認は二段です（2026-09-10〜・**対話の中で承認できます**）

**あなた（各プロジェクトのセッション）が承認して構いません。** ただし**必ず二段で**行ってください。

```bash
# 一段目: 本文を全文表示して、何も書き換えずに終わります（exit 1）
thth approve <ファイル>
```

**一段目の出力をそのまま masaru に見せてください。**出す本文・account・publish_at・topic・reply_to と、末尾に `digest: ab12cd34ef56` が出ます。

```bash
# 二段目: masaru が「いいよ」と言ったら、一段目が出した digest を渡します
thth approve <ファイル> --confirm ab12cd34ef56 --by "claude（<プロジェクト> セッション）"
```

**この二段が防ぐのは「A を見せて B を承認する」ことです。**表示と承認の間に本文・account・reply_to・topic・publish_at のどれかが変われば digest が変わり、二段目は通りません。

**`--by` は必須です**（2026-09-10〜）。front-matter（`approved_by`）と commit に残ります。省略すると承認しません——以前は VM の unix ユーザー名（`wt`）が既定で入り、**masaru の判断が `wt` として記録されていました**。環境変数 `THTH_ACTOR` でも指定できます。

**名乗り方はそろえてください**: `masaru` / `claude（<プロジェクト> セッション）`。いまのところ機械では検査していないので、表記ゆれはそのまま残ります。

**承認済みのファイルにもう一度 `approve` を当てると、`--by` だけ更新できます**（本文・topic・publish_at を触っていなければ digest は同じ＝masaru が読んだ本文のまま）。表記ゆれを直す道として使えます。

**守ってほしいこと**: **本文を見せずに `--confirm` を渡さないでください。**digest はあなた自身でも計算できてしまうので、この仕掛けは masaru に見せたことを保証しません。**見せる責任はあなたにあります。**

**`thth approve` は VM 側の `git pull` を自分でやります**（2026-09-10〜）。承認の前に手で pull する必要はありません。同期できなければ承認を断ります。

### 複数本をまとめて承認する（2026-09-10〜）

**ファイルを並べても、ディレクトリを渡してもかまいません。**`thth lint` も同じです。**`*.md` は使わないでください**（手元のシェルが展開しようとして失敗します）。ディレクトリを渡すと、その中の `status: draft` の `.md` が対象になります（承認済みは対象外。何本外したかを一段目が述べます）。

```bash
# 一段目: 全部の本文を続けて表示し、最後に「束の digest」を 1 つ出す
thth approve /srv/thth/repos/asmon/docs/sns/queue

# 二段目: 同じファイルを並べて、束の digest を渡す
thth approve /srv/thth/repos/asmon/docs/sns/queue --confirm <束のdigest> --by "claude（asmon セッション）"
```

- **どれか 1 本でも中身が変われば束の digest が変わります。**保証は本数が増えても崩れません。
- **1 本でも lint に落ちる・`post_id` が付いているものがあれば、1 本も承認しません**（半分だけ承認された状態を作らないため）。
- `--json` を付けると**ファイルごとの digest** も返します。**どれが変わったかを知りたいときはこれ**（全部を一段目で回し直す必要はありません）。

**予定時刻を過ぎた原稿は、一段目が警告します**（2026-09-10〜）。起草する人と承認する人が別なので、承認までに時刻が過ぎるのは普通に起きます。

- `⚠ **承認するとすぐ出ます**` — 予定時刻を過ぎています。次の実行（10 分以内）で出ます。
- `⚠ **承認しても出ません**` — `stale_days`（既定 7）を超えています。`publish_at` を直してください。

複数本まとめたときは、末尾にも「予定時刻を過ぎているものが N 本あります」とまとめて出ます。

### 承認を取り消す（`thth revoke`・2026-09-10〜）

**出る前なら止められます。**出たあとは `thth retract`（下記・2026-09-14〜）で取り下げられますが、そちらは公開の側を変える行為なので二段の門を通ります。

```bash
thth revoke <ファイル> --reason "連載の順を変えた" --by "claude（asmon セッション）"
```

- `status` が `draft` に戻り、`approved_sha` などが消えます。**本文には触りません**——直してそのまま `thth approve` し直せます。
- `revoked_at`・`revoked_by`・`revoked_reason` が残ります。
- **もう出てしまったもの（`post_id` あり）は取り消せません。**その場合は Threads の画面から手で消してください。
- **意図して止めたもの（`draft` に戻る）と、うっかり書き換えたもの（`approval_stale` で要確認に出る）は board で区別できます。**
- **取り消したあと承認し直すと、`revoked_at`・`revoked_by`・`revoked_reason` は消えます。**front-matter は「いまの状態」を表す欄なので、これは意図した挙動です。**「一度引っ込めた」履歴は commit 側に残ります**（`git log -- <ファイル>`）。

### 出てしまったものを取り下げる（`thth retract`・2026-09-14〜・v2.1・Threads／X／Mastodon）

`post_id` が付いたものは `revoke` では止められません。**`thth retract` は公開済みの投稿を媒体から消します**が、承認と同じ二段です——一段目は本文と URL と理由を見せて digest を出すだけ（何もしない・rc=1）、二段目 `--confirm <digest>` で DELETE を 1 回呼びます。

```bash
thth retract <account> <post_id> --reason "誤字" --by "masaru"                    # 一段目: 見せるだけ
thth retract <account> <post_id> --reason "誤字" --by "masaru" --confirm <digest>  # 二段目: 取り下げる
```

- **記録は消しません。** queue の front-matter（同席送信なら `state/<account>/sent/<post_id>.json`）に `retracted_at`・`retracted_by`・`retract_reason` が足され、`thth posts`・`thth board` に「取り下げ済み」と出ます。
- 台帳に `production: true` が無ければ二段目でも DELETE を呼びません。手元に記録の無い `post_id`（THTH を通していない投稿）は取り下げません。トークンに取り下げの権限（Threads は `threads_delete`・X は `tweet.write`・Mastodon は `write:statuses`）が乗っていなければ「`thth auth <account>` をやり直してください」で止まります（rc=2）。Mastodon は 3.1.1 から対応。媒体に投稿がもう無いとき（404）は `post_missing` で止まり、記録は変えません。Bluesky は未対応（rc=2）。

### これから何が出るかを日付順に見る（`thth schedule`・2026-09-10〜）

```bash
thth schedule <あなたのアカウント> --days 14
```

承認済み（済）と下書き（未）の両方を、時刻順に並べます。時刻を過ぎているものには印が付きます。読むだけです。

- 本文は **`## threads` の節だけ**。その上には何を書いても読みません。
- 検査は先に走らせられます: `thth lint <ファイル>`。文字数・書式・トピックの不備を名指しで返します。**450 字を超えると警告**が出ます（絵文字の数え方が公式と厳密に一致する保証がないので、境界に座らないため）。
- 長すぎても**切り詰めません**。落として理由を返します。
- timer の unit（`.timer`）は手で書かず、`thth systemd <account>` が台帳（`tick_minutes`）から生成します。

## 5. 自分たちで決めてよいこと

台帳（`~/Developer/thth/accounts/<アカウント>.json`）の次の 7 つは**あなたのプロジェクトの判断**です。いま入っている値は統括の当て推量なので、合わなければ言ってください。

| 設定 | いまの値 | 意味 |
|---|---|---|
| `min_interval_hours` | **0（制限なし）** | 前の投稿からこれだけ空ける。**0 より大きくすると、あなたが書いた `publish_at` より間隔のほうが勝ちます**（9 時・12 時・15 時と書いても 12 時のものが出ません）。意図してそうしたいときだけ入れてください |
| `quiet_hours` | **null（制限なし）** | この時間帯は出さない。**入れると、その時間帯に指定した `publish_at` は出ません** |
| `max_per_run` | 1 | 1 回の実行で出す本数。実行は 10 分ごとなので、同時刻に何本溜まっていても 10 分おきに 1 本ずつ出ます |
| `stale_days` | 7 | **`publish_at` からこれだけ過ぎたものは出しません**（要確認として board に出ます）。VM が長く止まって復帰しても、**古い投稿が一気に出ることはありません**。長期の連載を組むときはここを見てください |
| `tick_minutes` | 10 | timer の刻み。`publish_at` の遅れの上限になる。変えたら `thth systemd <account>` で unit を作り直す |
| `hashtags` | 台帳ごとの値 | 本文中の `#` 語を許すか。Bluesky／Mastodon では `topic` の末尾タグ追加もこの設定に従う。Threads の topic は別扱い |
| `max_hashtags` | 省略時 3 | Bluesky／Mastodon の公開本文のタグ上限。`topic` で付くタグも含む。0 以上の整数 |

**基盤が強制しているものは、いまのところありません**（2026-09-12 訂正。Meta の上限も止めていません）。頻度も時刻も本数も、あなたたちの声の作り方です。

## 7. 困ったとき

- **「inflight が残っています」で止まる**: 前回「出たか出ていないか分からない」失敗があったということです。**3.3.1 から、道具は毎回の実行の最初に媒体へ 1 回だけ問い合わせ、決まれば自分で解いて進みます**（Threads は container の状態、他の媒体は自分の最近の投稿との照合）。それでも止まり続けるのは、問い合わせても決まらなかったときだけです。**`state/<account>/inflight.json` を手で消さないでください。** `thth inflight <account> show` で中身を見て、媒体の画面で出たかどうかを確かめ、統括（THTH セッション）に伝えてください。解くのは確かめた人が `thth inflight <account> resolve --not-published`（出ていない）か `--published <post_id>`（出ていた）に `--by <名前>` を付けて（二段確認・控えと変更ログが残ります）。二重投稿を防ぐための止まり方です。「送った本文と repo の本文が食い違います」と一緒に出ているときは、公開している最中に本文が書き換わった合図です——同じく人が直すまで止まったままにします。
- **「既に実行中です」**: 別の実行と重なっています。少し待って再実行してください。同じ repo（clone）を共有する別アカウントの実行と重なっていても同じメッセージで止まります。
- **`approval_stale` で出ない**: 承認したあとに本文・トピック・返信先・予約時刻のどれかが変わりました。中身を確認して、必要ならもう一度 `thth approve` してください。
- **指定した時刻を 1 時間過ぎても出ていないものは `thth board` の要確認に出ます**（理由付き）。`rehearsal` は「台帳がまだ本番になっていない」、`min_interval`・`quiet_hours` は「あなたが入れた設定が指定時刻より勝っている」、`overdue` は「理由が無いのに出ていない」（timer が止まっている等）。
- **トークンの残り日数は `thth board` に出ます**（`token_state`・`token_remaining_days`）。更新は THTH が自分で行うので、あなたのすることはありません。`expired`・`no_token`・`token_incomplete`（鍵が足りない）・`refresh_failed` が出ていたら masaru に伝えてください（その状態では 1 本も出ません）。期限を持たない媒体（Bluesky・Mastodon）は `token=ok/期限なし` で、これは正常です。
- **`thth board` に「未送信の採取」が出ていたら**: 数や返信を集めたものが、まだ利用者 repo に送れていません（origin に届かなかった等）。**投稿は止まっていません**——採取の commit は取り消してファイルに残してあるので、次の実行で送り直します。**何度も出続けるなら origin への push が通っていません。**手で直すなら:

```bash
ssh wt 'cd /srv/thth/repos/<プロジェクト> && git status --short -- data/sns && git push'
```

- **`unverified_content` で出ない**: そのファイルが、同期を確認した commit の中身と一致しません（commit していない変更がある・追跡されていない・`.gitignore` されている・symlink になっている、など）。中身を確認して commit・push してください。
- **本文が長すぎる／トピックが弾かれた**: 理由が名指しで出ます。直して出し直してください。
- **それ以外**: `~/Developer/thth` の THTH セッションへ。設計と実装の責任はそちらにあります。

### 2.8.0: Bluesky／Mastodon の `topic:` が末尾のタグになる

`docs/リリースノート_2.8.0_2026-09-19.md` を参照。要点: `topic:` はその媒体の末尾 `#語` として公開される・承認の指紋は公開本文で取る（旧承認は `approval_stale`）・タグは既定 3 個まで・`where`／`topics` の `by_tag`・`analytics-report --by tag`。

`hashtags: true` のときだけ `topic` を末尾へ追加します。同じタグが本文にあれば重ねません。`false` では追加せず、`topic` が効かないことを警告します。上限は台帳の `max_hashtags`（省略時 3）。以前の本文で承認した原稿が `approval_stale` になったら、公開本文を確認し直して再承認してください。

### 2.7.0: 観測時点のフォロワー数

新しく採った投稿指標行だけに `context` を添えます。採取時刻以前48時間以内で最も新しい account 日次行の `followers_count` と `collected_at`（JST時刻）、`staleness_hours`、source=insights_accountです。日次行の `date` は選定条件にしません。該当値なし・不正・同時刻の矛盾は `context: null` と `context_reason: no_recent_daily_record`。率にはしません。過去の観測行へ後から補いません。

日次採集は前日の閉じた日を採るため、通常は前日の日付を持つ直近行が文脈になります。新しいAPI呼出は追加しません。

Threads・Bluesky・Mastodonの本人投稿は同じ指標刻みを使います。Bluesky/Mastodonのviewsは存在しないためnull。likes/reposts/replies、Blueskyのquotesは各媒体の値を保持し、媒体を混ぜた合計・率を出しません。

### JSON を別の道具へ渡すとき

`--json` の標準出力は JSON だけです。進捗や診断は標準エラーへ出ます。SSH 自体の案内も除いて取り込みたいときは、たとえば `ssh thth-vm thth board --json 2>/dev/null` とします（診断も見えなくなるので、失敗時はリダイレクトを外して確認します）。

`send` の dry-run はロックを取らず、SNS 台帳へも書きません。本文を含まない最小の運用記録（runs）は従来どおり 1 行残します。`send --production`・`approve`・`replies --refresh`・`revoke`・`retract` は `--wait 5` のようにロックを待つ秒数を指定できます。省略時は従来どおり即座に断り、待機中に空かなければ送信・変更しません。

`approve`・`preview`・`lint`・`revoke` は repo 相対パスも使えます。現在の作業ディレクトリにそのパスがあれば優先し、無ければ登録された repo を探します。同じパスが複数の repo にあれば候補を表示して止まるので、VM の絶対パスで指定してください。手元の `/Users/…` の絶対パスは受け付けないため、VM の絶対パスまたは repo 相対パスで指定します。

`mentions` は Threads の言及、Bluesky の mention・reply・quote 通知、Mastodon の公開範囲の mention 通知を読みます。`post_id` が返信先です（通知 ID ではありません）。`replied` は返信記録が見つかれば object、見当たらなければ false、台帳を読めず判断できなければ null。SNS 台帳へは保存せず、本文や相手名を含まない件数の最小 runs 記録だけ残します。

`thth unanswered <account> --since 7d --json` は自分の根投稿に付いた他者の返信を、ローカルの返信・絡み・送信記録・queue と照合します。`--since` は `24h`・`7d`・`2w` または ISO 時刻。`--refresh` を付けたときだけ `replies --refresh` と同じ取り直しを行います。`verified: ledger_only` は枝の実体を読んだ確認ではなく、`cannot_say` と `collection_stale_hours` に欠けた根拠・採集の古さが出ます。`handoff-report` の `unanswered` は同じ計算の件数と最古経過時間です。

`thth approve <queue ディレクトリ> --account <name>` は、その account の draft だけを表示・二段承認します。VM のディレクトリを渡し、手元で展開される glob は使いません。`--status` はありません。


## 3.2.0: まだ出ていない自分の原稿への返信を先に仕込む（`reply_to_file`）

「今日は問い・明日は答え」のように、答えの原稿を問いが出る前に書いて承認まで済ませたいときは、答えの front-matter に `reply_to_file: 2026-09-23-q-decaf.md`（**同じ queue・同じ account の原稿のファイル名だけ**）と書きます。問いの原稿が出て post_id が書き戻されると、次の実行で答えがその投稿への返信として出ます。**問いが出るまでは待ちます。返信先の無い投稿（root）には落としません**——問いが取り下げられた・読めない・消えたときも出さず、`thth board` の要確認に理由付きで出ます。待っている答えは「時刻超過」に数えず「返信待ち」として、`thth board` の要確認・`thth morning` の予定の段・`handoff-report` の `queue.counts.waiting_reply` に名前と待ち先が出ます。`thth preview` の末尾に「返信先: <file>（未解決・待ち）」か「返信先: <file> → <post_id>」。`reply_to` との併用・自分自身・同じ queue に無い原稿・account 違い・スレッド連投（`thth: 2`）の原稿は `thth lint` が断ります。承認するのは「どの原稿への返信か」で、問いの post_id が出ても承認し直す必要はありません。サーバ型の下書き（MCP `thth_draft_put`）はこの版では `reply_to_file` を受けません。

自分が置いた開いている報告に書き足すときは `thth report add <report_id> --body-file <path|-> --by <名前>`（MCP は `thth_report_add`）。

## 3.8.0: 知見共有を回す（道具が読ませる・置く手間を減らす・持ち主の組）

**新しいセッションは最初に `thth plaza digest <project>` を読んでください**（MCP は `thth_plaza_digest`・読むだけ）。2 媒体以上で再現した施策・気づきの 1 枚で、再現しなかった媒体と試していない媒体も分母つきで並びます。

- **読む瞬間は道具が作ります。** `thth observe` の 0 段に「同じ持ち主の他の媒体の新しい書き込み 1 件」（1 日 1 件・読んだものは出さない）。`thth approve` の 1 段目と `thth lint` に、同じ goal か同じ topic の書き込みの題と id（本文は出ません）。`thth ask before-you-post <account> --topic <語> --goal <語>` に「同じ goal で他の媒体ではこうだった」の 1 行（道具が付けた観測があるときだけ）。`thth plaza show` で読んだものは控えられ、observe に再び出ません。
- **持ち主の組（owner の範囲）。** 同じ持ち主の project どうしで読み合うには、管理者が組を登録します（`thth admin plaza owner set <組の名前> <project> <他の project> --by <名前>`・既定は組なし）。組があれば `thth plaza post … --owner` で組の全 project に見せられます（一段・他の持ち主には見えない・組を解けば見えなくなる）。`thth plaza list` が 0 件か自分の書き込みだけなら、管理者に頼む命令の形の案内が出ます。
- **置く手間を減らす。**

```
thth plaza post kopicha-threads --kind finding --from after kopicha-threads --title "朝の返信" \
  --scope "Threads の朝の投稿" --body-file 解釈.md --by <名前>
thth plaza post kopicha-threads --kind measure --from study-report docs/sns/studies/問いの冒頭.json \
  --title "冒頭を問いに" --scope "Threads の朝の投稿" --by <名前>
thth plaza post kopicha-threads --from-doc docs/sns/運用メモ.md --scope "Threads の朝の投稿" --by <名前>
thth plaza post kopicha-threads --from-report <report_id> --scope "道具の使い方" --by <名前>
```

  `--from analytics-report|after` は道具が置く時点で計算を呼び直し、分母・期間・言えないことを観測の欄と本文の下書きに入れます。**observed は道具が付けた数字だけ**——あなたが本文に書いた数字は「本文」の欄のままです。`--from-doc` は元の文書のパスと commit を持ちます（先頭 4,000 字・commit していない変更があれば断ります）。`--from-report` は自分の project の閉じた報告の返事を道具のコツとして写します。
- **置くきっかけ。** 気づきに `--trial-due 2026-10-08` を付けると、期日に observe の次の一手に「追試の結果を足す」が命令の 1 行つきで出ます。施策の期間が終わったとき・配分を変えた週が閉じたとき（週の表）も「広場に置く」が出ます。置いた側の observe には「あなたの書き込みに 追試 n（再現 a・再現せず b）・賛否 m」が出ます。

## 3.7.0: 測り方と表示の直し（click を投稿単位で・確定待ち・手元のパス・where）

**click の投稿はリンク先を投稿ごとに分けてください。** あるリンク先を前後 72 時間で 1 本の投稿しか使っていなければ、そのリンク先のクリック（Threads の account 日次 `clicks_by_url`）を投稿のものとして出します。日次の粒度なので、72 時間は**投稿日（JST）を含む 3 暦日**の和です（`window: post_day_plus_2`）。

```bash
thth analytics-report kopicha-threads --compare-previous --by goal --json   # click に clicks_72h とクリック率
thth analytics-report kopicha-threads --weekly-goals --weeks 6             # 週の表（観察の表）
thth lint /Users/<you>/Developer/kopicha/docs/sns/queue/2026-09-25-a.md     # 手元のパスを VM のパスに読み替え
thth where kopicha-threads コーヒー --also 紅茶 --also tea                   # 同じ結果を絞るだけ
thth where kopicha-threads コーヒー 紅茶 --aggregate --lexicon words.json    # 数と時刻だけ・保存しない
```

- click: 同じリンク先を前後 72 時間に 2 本以上で使う（`url_shared_72h`）・リンクが無い（`no_link`）・プロフィールのリンクと同じ（`profile_link`・台帳の任意項目 `profile_links`）ときは言いません。リンク先の照合はスキーム・末尾の `/`・`utm_*` を外し、大文字小文字はホストだけ畳みます。クリック率は clicks_72h / views_24h（分母つき）。連投（`thth: 2`）も段ごとのリンク先が実行記録に残るので、照合に入ります（3.7.0 より前の連投は「リンク先が記録に無い」扱い）。`thth observe` の「前回の観測から」と `thth map show` の自分の層にも出ます。**本文に札（utm）を付けて書き換える形は入れていません**（承認の指紋の規律）——リンク先を投稿ごとに分ければ同じことが測れます。
- lint は、同じ account で同じリンク先を前後 72 時間に使う click の原稿が 2 本以上あると `warning: url_shared_72h` で知らせます（断りません。同じ日でもリンク先が違えば測れます）。
- follow の投稿が毎日出ていて出ていない日が無い（または min-n 未満）ときは `no_comparison_days` と事実の 1 行だけ（推奨はしません）。
- 週の表は週ごとの目的ごとの本数と followers の増分（前週の日曜と週の最終日の差・欠測は null）。因果とは言いません。
- **承認は確定するまで出ません。** `thth approve` の 1 段目で `state/<account>/approve_pending.json` に確定待ちの控え（相対パス・digest・時刻・中身の sha256。本文は残さない）を置き、queue・board・observe に「確定待ち n 本（最短の publish_at）」と出ます。publish_at まで 3 時間を切ると observe の次の一手に `confirm_due`（確定の命令の 1 行）、運用通知にも 1 回（増えたときだけ）。確定・取り消し・本文の変更で消えます。
- `thth account` は「run を止めるもの」（token・inflight・production など）と「run が自分で直すもの」（repo が upstream より遅れているだけ——次の run が取り込みます）を分けます。後者は「投稿できません」に入りません（board の `repo_sync` と同じ判定）。承認済みで出られない原稿は「出られない原稿（held）n 本: 名前」の段に出し、account は「投稿できます」のままです（数は board の `held_count` と同じ）。
- `thth observe` の返信の段に `collection_stale_basis`（根投稿ごとの最後の取得の成功のうち最も古いものから数える）と `collection_stale_since`、「返信の取得: …」の 1 行。
- `thth lint`・`preview`・`approve` は手元の Mac の絶対パスでも `…/docs/sns/queue/<file>` に切り出せれば VM のパスに読み替え、1 行言います。VM 側の clone が古ければ「VM 側は古い（thth pull で取り込めます）」。approve の digest は VM の本文（同期のあと）で出ます。
- `thth where`: `--also` は同じ検索結果のうち本文にどれかの語を含むものだけを残します（追加の検索はしません・observe の監視語には使いません）。0 件のときは `zero_or_filtered`（本当に無いか媒体が語を受け付けなかったかは区別できません）。`--aggregate` は語ごとの件数・期間・1 日あたり・問いの形・lexicon の分類ごとの件数だけを返し、本文・username・post_id は返さず、**保存しません**（保存するなら Meta への説明の申請のあとで・世間の層と同じ条件）。

## 3.6.0: 投稿の目的（goal）で束ねて比べる・つまずきの年表

**原稿ごとに目的を 1 つ、front-matter に書いてください。** 道具が目的ごとに、その目的に合う物差しで比べます。目的は人と LLM が決め、道具は推測しません（本文のメモ「目的: 誘導」は読みません）。

```yaml
goal: click        # reach（表示）| click（サイト誘導）| follow（フォロー）| reply（会話）。無ければ書かない（none）
```

```bash
thth lint docs/sns/queue/2026-09-25-a.md          # 4 語以外は goal_invalid
thth send kopicha-threads --text-file t.md --goal reply   # 同席の送信（digest には入らない）
thth analytics-report kopicha-threads --compare-previous --by goal --json
thth report timeline kopicha                      # つまずきの年表（読むだけ）
```

- 目的は承認の指紋に入りません。承認のあとに書き換えても出ます（`approval_stale` にならない）。書き換えは runs と sent に「目的の変更」として残ります。連投（`thth: 2`）は束の front-matter に 1 つです。
- 物差し: reach は 24h・72h の views（Bluesky・Mastodon は likes＋reposts）、reply は 24h の replies と返信した人の異なり数（自分の account を除く）。**click と follow は投稿単位の数字が一次資料に無い**ので「言えない」（`per_post_clicks_unavailable`・`per_post_follows_unavailable`）と出し、日次との並べ方（click の投稿が 1 本だけの日の clicks・follow の投稿が出た日と出ていない日の followers の前日差）は**観察の差（因果ではない）**の印つきです。
- 層は公開の時点の記録（sent・連投の実行記録）から作ります。3.6.0 より前の投稿（記録に goal の欄が無い）は `unrecorded`、3.6.0 からの目的の無い投稿は `none`（目的なし）。2 つは混ぜません。公開のあとに原稿の `goal:` を書き換えても過去の層は動きません。
- `thth observe` の「前回の観測から」に投稿ごとの目的が出て、主な物差しが先頭に並びます。`thth map show` の自分の層に「目的: reach 3 本（views_24h 中央値 …）」の 1 行。広場の施策にも `--goal` を付けられます。
- つまずきの年表（`thth report timeline <project|account> [--since]`・MCP `thth_report_timeline`）は、自分の project の報告とリリースノートの報告 id・「〜の実測から」を日付で並べ、始めて 2 週間の件数と閉じるまでの日数の中央値を出します。他の持ち主の報告は出ません。

## 3.5.0: 観測の地図（話題を選ぶ前に読む）

**話題を選ぶ前に `thth map show <project>` を読んでください**（MCP は `thth_map_show`・読むだけ）。点は人が決めた話題、線は包含（狭い語 ⊂ 広い語）と共起です。同じ点に、自分の投稿の数字（その topic で出した投稿の数と、views・likes・replies の中央値と n。`analytics-report --by topic` と同じ 24 時間の刻み・n が 5 に届かなければ null）と、広場の施策・気づき・問いの数と判定・追試の数（title か `--scope` に点の語を含む書き込み）が重なります。

```bash
thth map show kopicha                    # 点ごとの層・包含の線（既定は直近 30 日）
thth map show kopicha --node コーヒー --json   # その点と隣り合う点だけ
# 点と線は管理者が足す（あなたのセッションは候補を人に出すだけ）
thth admin map node add kopicha コーヒー --by <名前>
thth admin map edge add kopicha スペシャルティコーヒー コーヒー --by <名前>
```

- 点は project あたり 20 まで。@名前・URL・個人名らしき語（「〇〇さん」など）は点にできません（特定の人を観測する地図にしないため）。
- 世間の層（日ごとの検索の件数・異なり投稿者・上位 3 の占有率・点どうしの共起）は**既定で無効**です。無効のあいだは `world_layer_disabled` と出ます。有効にするのは管理者で、Meta への説明の申請と privacy ページを実態に合わせたあとです。
- `thth observe` の 0 段に「地図: 伸びた点・強まった線」が出ます（候補の列挙だけ・本文は作りません）。

## 3.4.0: 施策の広場（試したら置く・次を決める前に読む）

**施策を試したら広場に置き、次を決める前に他の媒体の施策を読んでください。どちらも作業の一部です。** 置いたものは同じ持ち主の全 account（媒体をまたぐ）だけに見えます。kopicha なら threads・bluesky・mastodon の 3 つのセッションが同じ広場を読み書きします。

```bash
# 施策（観測は道具が付ける。宣言は study-report の形で媒体ごとに 1 つ）
thth plaza post kopicha-threads --kind measure --title "冒頭を問いにする" \
  --body-file body.md --scope "3 媒体の朝の投稿・茶の話題" \
  --declaration question-threads.json --declaration question-bsky.json \
  --how "thth study-report question-threads.json" --by <名前>
# 気づき（細目は pattern・rule・pitfall・tool_tip）・問い
thth plaza post kopicha-mstdn --kind finding --kind-detail pitfall --title "夜より朝" \
  --body-file note.md --scope "Mastodon の夜の投稿" --evidence-level hypothesis --by <名前>
# 読む・返す・判定する
thth plaza list kopicha
thth plaza show <plaza_id> --as kopicha-bsky
thth plaza reply <plaza_id> --as kopicha-bsky --kind trial --result not_reproduced --text-file note.md --by <名前>
thth plaza update <plaza_id> --as kopicha-threads --verdict adopted --reason "Threads で差、Bluesky は差なし" --by <名前>
```

- `--scope`（媒体・企画の範囲・120 字）は全部の書き込みで必須です。読み手が読者層の違いを知るためです。
- 施策の数字は**道具が付けた観測だけ**を「観測」と表示します（study-report と同じ計算・両群の分母・`observational_difference`・欠測は null と理由）。本文に書いた数字は「本文」の欄に分けて出ます。`--evidence-level observed` は名乗れません（観測の列が取れたときに道具が付けます）。
- `--how` は数字を出し直せる thth の命令 1 行です（measure は必須）。道具は形と秘密だけを確かめ、実行はしません。
- 返信は `comment`・`agree`・`disagree`（理由必須）・`tried`（自分の施策の id が必須）・`trial`（追試。`reproduced`・`not_reproduced`・`not_tried`）。**再現しなかった追試も再現した追試と同じ重さで数えます**（一覧・1 件・比較の表・分母つき）。
- `thth observe` の 0 段に「広場: 新着 n（project）」と最近追試が付いた 1 件、次の一手に「返信の付いた自分の施策」「判定待ちの施策」「判定の付いた施策をまだ試していない媒体」が出ます（候補の列挙だけ・本文は作りません）。
- 秘密らしき値が含まれていたら置かれません。置き場は VM の私有で、SNS の台帳には書きません。

## 3.3.0: 開始手順は「セッションの始めと区切りごとに observe」

毎朝の一枚は **観測**（`thth observe <project|account> --json`・MCP は `thth_observe`）になりました。朝だけでなく、**セッションの始めと区切りごとに**引いてください。`thth morning`／`thth_morning` は同じものの別名で、JSON の `report_type` はどちらも `observe`、呼んだ名前は `invoked_as` に出ます。第 2 段は「前回の観測から」——前回の栞の時刻から今までに出した投稿（栞が無い・7 日より古いときは前日 JST。`window.basis` が `since_last_observe` か `yesterday_jst`）。以下の 3.1.0 の説明の `morning` は `observe` と読み替えてください。

### 3.3.0: 止まったら知らせる

- **承認済みなのに出られない原稿**（publish_at を過ぎたのに `approval_stale`・返信先の取り下げ・`stale`・型外などで要確認に落ちたもの）があると、`thth run` は「出すものが無い」ではなく `held`（理由 `approved_but_held: approval_stale 46` のような静的な符丁）として死活通知と運用通知に知らせます。運用通知は**本数が増えたときだけ**・0 に戻ったら「復旧」（`held_cleared`）。時刻前の原稿と返信待ち（`waiting_for`）は数えません。本番（`production: true`）で timer に載る account だけです。
- 名前は `thth observe` の予定の段 `held_items`（file・理由・publish_at・経過・`due`）と `next_steps` の`kind: "held"`（approval_stale は「再承認」の候補）、`thth board` の要確認（先頭 5 本と残りの本数）に出ます。時刻前の approval_stale も名前だけは出ます（通知はしません）。
- 承認の指紋の計算が変わる版では、`thth observe` の 0 段と `handoff-report` の `tool` に「この版で再承認が要る原稿: n 本（account ごと）」が出て、運用通知にも 1 回流れます。
- 死活通知（`HEALTHCHECK_URL`）と運用通知（SMTP）の**両方**が無い scheduled の account は `no_notification_route`、片方だけなら欠けている側を名指しして `notification_route_partial: healthcheck`（または `incident`）を、`thth observe` の 0 段と `thth doctor` が言います。
- `reply_to_file` の指した原稿が未公開のまま取り下げ（`status: withdrawn`）なら、待たずに `reply_to_unresolved: target_withdrawn` になります（出ません・held に数えます）。

### 3.3.0: 報告したくなる口

つまずき・迷い・期待との違いの報告は、利用者の作業の一部として歓迎します。小さいものも。重複は道具が束ねます。例: 「止まったのに気づかなかった」「断られた理由が分からなかった」「同じ操作を 3 回繰り返した」。

- 種類に `friction`（迷った・分かりにくかった・同じ操作を繰り返した）が増えました。提案が無くても置けます。
- 道具が断ると、断りの最後の行が**そのまま打てる報告の 1 行**になります: `report_channel: thth report file <account> --kind friction --from-last-refusal --title "<理由> で断られた" --by <名前>`。`--from-last-refusal` は、道具が account ごとに控えた直前の断り（`state/<account>/last_refusals.json`・直近 5 件・時刻・版・命令の名前・理由の符丁・account だけ。本文と引数の値は控えません）を再現手順に添えます。MCP は `thth_report_file {"account": …, "title": …, "from_last_refusal": true}`。
- 置いた報告が効いたかは `thth observe` の 0 段「あなたの project の報告: 開いている n・この版で閉じた m（題）」で見えます。

## 3.1.0: 開始手順は「まず毎朝の一枚」

**セッションの最初の 1 回は `thth morning <project|account> --json`**（MCP は `thth_morning`）。昨日から何があって今日なにをすればよいかが 6 段（道具・返していないもの・昨日の自分・世間・予定・次の一手）で返ります。`handoff-report --since-last-read` を含むので、**版の確認もこれ 1 回で済みます**。呼ぶと栞（前回読んだ時点）が進みます——進めたくないときだけ `--no-mark`。

取れなかった段は `0` ではなく `null` と理由 1 語（`provider_timeout`・`budget_exhausted`・`scope_missing`・`no_watch_words`・`not_supported`・`unavailable`）。3 段（世間）の監視語は**管理者が入れます**（`thth admin watch set <account> 語 … --by <名前>`・最大 5 語・1 語 40 字）。語が無い account は飛ばします——**道具は語を選びません**。5 段（次の一手）は候補の列挙だけで、**本文は作りません**。1 枚の読み方は [毎朝の一枚](使い方_毎朝の一枚_3.1.md)。

## 2.10.0: 版と入口の確認

**断られたら・結果が期待と違ったら・欲しい形があれば、報告の口へ**: `thth report file <account> --kind bug|request|friction --title … --body-file … --by <名前>`（MCP は `thth_report_file`）。1 回の呼び出しで道具の中に置かれ、実装側が読みます。返事は `thth report show <report_id>` と `handoff-report --since-last-read` の `tool.reports` に出ます。秘密らしき値（token・Bearer・`sk-`・32 桁以上の 16 進 等）が含まれていたら置かれないので、伏せてから置き直してください。

段だけを読み直すときは `thth handoff-report <account> --since-last-read --json`。`tool.changed_since_last_read` が true なら `tool.notes_root_local_hint` を手掛かりに、手元の THTH checkout で `tool.release_notes` の相対名を読む。CLI を含む全経路でサーバの絶対パス `notes_root` は返さない。旧 cursor や初回は前版・変化が null。既読を書き込むのは明示の `--mark-read --by <名前>` だけ。

`where <account> --recent 茶 --word コーヒー --since 7d --exclude-engaged --max-per-author 2 --json` のように語とオプションを混ぜられます。`since` は期間（1h・7d・2w）または timezone 付き ISO 日時。Bluesky は検索 API の sortAt 基準、Mastodon は返された投稿日時で絞ります。タグ観測は別の 24 時間窓です。表示件数は絞り込み後、除外数は `by_word.<語>.dropped` に出ます。Bluesky のサーバ側期間除外数は返されないので null。各行の `reply_count` は実測か null、`replied` は自分の返信の印です。

Bluesky の Web 投稿 URL は `thread`・`send --reply-to`・`after --reply-to`・`replies --post` に渡せます。handle は公開 resolveHandle で DID にし、内部で AT URI に揃えます。解決できない場合は停止します。`where` の人向け表示にもコピーできる `post_id` が並びます。`who` は 1 度に 1 人です。

`send` と `approve` の一段目は `文字数: 使用数/上限（媒体・単位）` を示します。超過時には digest を出しません。`send` dry-run はロックを取りません。書く口の `send --production`・`approve`・`replies --refresh`・`revoke`・`retract` は `--wait <秒>` で待てます（既定 0）。読む口は SNS 台帳を書き換えませんが、従来の最小運用 runs は残します。

`thth study add <施策JSON> <post_id|queueのパス> --by <名前>` は施策の `changed_post_ids` に追加し、`--baseline` 付きなら `baseline_post_ids` に追加します。queue に post_id が無い場合や別 account の queue は拒否します。同じ群への再追加は重複させず、両群へ同じ ID を入れることは拒否します。利用者の JSON を保存するだけで git commit・採用判断・投稿承認はしません。手元のラッパ経由なら JSON と queue は VM 側のパスです。

比較レポートの by_mark は likes・replies・reposts を含みます。Bluesky・Mastodon・Threads の採集済みの値を使い、欠測は null のまま、account・媒体を合算しません。

`tool.notes_reason: "notes_directory_unavailable"` は、インストール先の docs が存在しない、通常ディレクトリでない、または読めないことを示します。`release_notes: []` だけで「変更なし」と判断せず、`notes_root_local_hint` を手掛かりに手元の checkout でノートを確認します。docs が読める場合の `notes_reason` は null です。

### 2.11.0: 認可は masaru 側で開始する

[導入: 承認を押すだけ](導入_承認を押すだけ.md) に利用者と管理者の手順をまとめました。利用者は VM や Meta アプリを作りません。masaru が `thth auth <account> --by masaru` を始め、利用者は URL で本人と権限を確認して承認します。認可 URL を LLM に貼らないでください。Bluesky は別の App Password stdin 入口です。X は認可のみで投稿・採集を有効にしません。

`app set` も旧 flags を含め `--by` 必須です。JSON stdin の schema と秘密管理ツールの例は導入文書 §3/5。`doctor` の認可経路の時刻と probe の時刻は別で、管理レポートは応答 scope を優先し欠測だけ probe で推定します。接続ページ・退出・書く口の公開は後版です。
