# 精読: Generative UI と THTH の画面（2026-11-27）

THTH を Generative UI にできるか、を決める前の文献の精読のまとめ。読んだのは 3 体（Fable）で、A は MCP Apps と elicitation と OpenAI・Claude、B は宣言的な UI の仕様、C は Jev と規約と研究と安全。

- 深さ: **すべて「原文を取って読んだ」まで**。実機では何も動かしていない。json-render の Jev の口だけはコード（`experimental-composition-batch.ts`）まで読んだ。
- 元の答えの全文: このセッション群の共有の覚え書きの所に `精読A_*`・`精読B_*`・`精読C_*` として置いた（repo の外）。
- 書き手: THTH括り 第2（Generative UI の担当として。2026-11-27 masaru「Generative UI の方に力を注げますか」）。

## 結論（5 つの問いへの答え）

| 問い | 答え | 根拠の深さ |
|---|---|---|
| 1. 承認を「人が押した」とサーバが確かめられるか | **どの仕様でもできない**。画面から呼んだ道具も、サーバには AI が呼んだのと同じ形で届く。確かめは THTH のサーバ側の二段目（digest）に残す | 仕様の本文で確認 |
| 2. 承認の本文を AI に書かせない作り | できる。**本文の欄を持たない部品**にし、下書きの番号だけを受け、本文はサーバが台帳から引いて画面に渡す | 仕様からの当てはめ（推測を含む） |
| 3. 部品の表の形 | 正本を **JSON Schema の JSON** にする。A2UI 1.0 の表も MCP の道具の入力もそのまま JSON Schema で、Python の標準ライブラリで出せる | 仕様で確認・選びは推し |
| 4. Jev に「形だけ」渡せるか | できそう。json-render の口が送るのは依頼文・明示の context・候補の id と説明文だけで、state と props は送らない（コードで確認）。穴は 3 つ（下） | コードを読んだ・動かしていない |
| 5. 差し込み（プロンプト注入）となりすましの備え | 文献は「表に無い物は描かない」まで。**文字を受ける欄を減らす**のが THTH 側の柵。承認の画面は省略も折りたたみもせず全文を見せる | OWASP・Checkmarx・仕様 |

## 1. 人が押したか

- MCP Apps（安定版 2026-01-26・SEP-1865 は Final）: 画面は postMessage で host に `tools/call` を送り、host がサーバへ中継する。サーバに届く呼び出しに「画面から来た」印を付ける決まりは、安定版にも draft にも無い。OpenAI の Apps SDK も「AI の呼び出しと同じ形」と書く。
- 道具を `_meta.ui.visibility: ["app"]` にすると、決まりを守る host では AI の一覧に出ない（MUST NOT）。ただしこれは「AI が呼ばなかった」を host の実装に頼って言えるだけ。画面のコードは自動で押せるし、Claude は 11/10 から app tools（AI が画面の中で操作する道）に対応した。
- A2UI 1.0 の `requiresUserActivation` は描く側の決まりで、受け手に印は届かない。AG-UI は自分の印を「資格ではない」と明記。json-render の `confirm` は見た目だけ。
- いちばん強い道: **MCP の URL の形の elicitation**（2025-11-25）。サーバが URL を出し、人が会話の外のブラウザで開く。client と AI は中身を見られず、サーバは開いた本人を確かめる義務を負う。THTH なら thth.me の承認ページがそのまま受け皿になる。弱み: どの client が対応済みか未確認・会話の外へ一度出る・「新しく、変わりうる」と仕様に書かれている。

→ **推し**: 重い承認（投稿・予約の確定）は今の承認ページ（URL の形か、今と同じ案内）、軽い操作（一覧の絞り・並べ替え・読み直し）は MCP Apps の画面だけの道具。二段目の digest はどちらでもサーバが確かめる。

## 2. 本文を AI に書かせない

- MCP Apps の画面は、サーバが前もって登録した決まった HTML（`ui://`・`text/html;profile=mcp-app`）。AI が決めるのは道具の引数だけ。
- だから承認のカードを出す道具は、引数を下書きの番号だけにする。本文・宛先の口座・日時・digest はサーバが台帳から引き、道具の結果で画面に渡す。AI が引数に本文を入れられる作りにすると「見せた物＝承認した物」が崩れる。
- 画面だけに要る値（一度きりの番号など）を `structuredContent` に入れると AI にも見えうる。host ごとに AI に何が見えるかは実機で確かめる（未確認）。
- HTML は版ごとに固定し、外のドメインを宣言しない（既定の CSP）。取ったデータが画面から外へ出ないことを host に守らせられる。

## 3. 部品の表

| 仕様 | AI が出す物 | 表の形 | THTH との合い |
|---|---|---|---|
| MCP Apps | 道具の引数だけ（画面は決まった HTML） | 無し（道具の結果の JSON が接点） | 土台。Claude・ChatGPT とも対応 |
| A2UI 1.0（Google・11/11 安定版） | 宣言的な JSON（平らな部品の配列） | JSON Schema（`catalogId`・`components`・`functions`） | 合わせる先の推し。MCP に載せる口（`application/a2ui+json`）が公式 |
| json-render（Vercel Labs） | 平らな spec（`root`＋`elements`） | TS の zod | Jev の口がある。表が TS の中に住む |
| AG-UI | 運ぶ層で UI の仕様ではない | — | 使わない |
| OpenUI | 独自の短い記法 | zod | 解析器が JS。使わない |
| Vercel AI SDK | 道具を呼ぶだけ | 作り手の React 部品 | 考え方は MCP Apps と同じ |

→ **推し**: THTH の正本は「部品の名・説明・props の JSON Schema・出す事件・呼べる行動（params の JSON Schema）・版」の JSON 1 つ。そこから MCP Apps の画面（HTML）と、要れば A2UI の表・json-render の zod を起こす。部品は **文字の props を持たない**のが既定（数・日付・番号・列挙だけ）。文字は台帳の番号で指し、描く側がサーバから引く。

## 4. Jev（TypeSafe）に形だけ渡す

- Jev は文を書かない。決めた選択肢の中から選ぶだけ（型の誤りは出ないが、答えの正しさは保証しない、と docs）。`jev-1.14.0`・入力 100 万トークン $0.042・出力無料・多くが約 100ms。部品を選ぶだけなら速さと料金は障害にならない。
- json-render の Jev の口（実験版・core 0.21.0〜・`experimental_`）は、送るのが `user_request`（依頼文の全文）・`context`・`guidance`・候補の `id` と `description` だけ。型の注記に "The evaluator cannot modify its props or bindings."。
- **穴 3 つ**:
  - (a) 依頼文は全文が行く → THTH 側で「形だけの依頼文」（例「下書き 3 件の一覧と承認のカード」）に作り直してから渡す。会話の文や他人の投稿をそのまま渡さない。
  - (b) 候補の説明文と `context` に中身を書けば出る → 説明文は「部品の種類・欄の名前・件数」だけ、という決まりを柵（試験）にする。
  - (c) 評価器の既定は Vercel AI Gateway 経由で、Vercel も通る（Vercel の規約は未読）→ `evaluate` を自前にして TypeSafe を直に呼ぶ。
- 規約（TypeSafe）: 入力で学習しない（privacy）・DPA あり（処理者・72 時間の通知）・米国で運用・再委託先は AWS・Modal・Nebius・CoreWeave・Cloudflare・Azure・GCP・Stripe。**分からない**: 保持の日数（「必要な間」）、MCA 4.1(c) の不正監視と Telemetry の無期限の保持が API の入力にどこまで及ぶか、保持なし（ZDR）を小口で使えるか（enterprise の申し込み制）。
- 形だけでの選びの質（番号の名前・中身の無い説明でどこまで選べるか）は docs に無く、試さないと分からない。

→ 10/15 の線（THTH の取得物を外の AI に渡すのは条件つき）に照らすと、**形だけ（部品の種類・欄の名・件数）なら取得物を渡していない**と言える。ただし privacy の「THTH 自身は AI の提供者にデータを送らない」に、部品の選びのために形だけを TypeSafe に送る、の 1 文を足す要がある。文案は叩き台で出す。

## 5. 差し込みとなりすましの備え

- Checkmarx「Lies-in-the-Loop」（2025-09）: 承認の窓に出る説明を攻撃者の文が作り、長い文で危ない部分を画面の外へ押し出して押させる。
- OWASP LLM01: 高リスクの操作は人の承認・外の中身は分けて印を付ける・出力の形はコードで検査・最小権限。
- MCP Apps の仕様自身が「画面は誤解させる表示をしうる」「view の phishing」を挙げる。
- **THTH の柵（推し）**:
  1. 承認の画面の文は LLM に書かせず、THTH が台帳から直に描く（§2）。
  2. 投稿の本文・宛先の口座・日時は省略も折りたたみもせず、本文より先に宛先と日時を出す（長い文で押し出されない順）。
  3. 承認の道具は `visibility: ["app"]`。二段目の digest はサーバで確かめる。
  4. 取ってきた他人の投稿は「外の中身」として枠を分けて見せ、画面の行動の引数にしない。
  5. 画面からの呼び出しはすべて記録する（今の記録の名乗りに「画面から」を足す）。

## 次の一手（推し）

1. 叩き台を書く: 部品の表（JSON Schema・文字の props 無し）・道具の分け方（重い承認は承認ページ／軽い操作は画面だけの道具）・Jev に渡す形と privacy の 1 文・Meta の審査の説明に当たらないことの確かめ。
2. Pencil に画面の正本を描く（一覧・承認のカード・調べた結果）。
3. 部品の一式は Codex に 1 本で頼む（masaru 11/27「UI の部品作りは codex にお願いする前提」）。柵（本文が台帳と 1 字違わない・表に無い部品を断る・説明文に中身が無い）は先にこちらで用意する。
4. 実機で確かめる: Claude のデスクトップで、画面だけの道具が AI の一覧に出ないこと、`structuredContent` が AI に見えるか、URL の形の elicitation に対応しているか。
5. 規約の残り: TypeSafe の保持の日数と MCA 4.1(c) の範囲は問い合わせが要る（外への送信なので masaru の承認のあと）。
