# THTH 5.12.0（2026-11-05）

断りの文を「なぜ・通すには・もっと良く」の 3 つにそろえ、release の関門と共有アプリの柵を足す版。masaru の決定: 「まとめて全部やってから出しませんか？」（11/04）・段 E の数の既定は「推しで」（11/04）。

設計の正本は `docs/設計_監査と審査の機械化と前向きな断り_2026-11-03.md`（段 A〜F）。原則は `docs/原則_前向きな断り.md`。

## 契約の変わったところ（足すだけ）

- **断りの 2 行目から**: 目録にある符丁の断りは、1 行目（`符丁: なぜ`・MCP は符丁）のあとに `なぜ:`（1 行目が言っていないときだけ）・`通すには:`・`もっと良く:` の行が続く。1 行目は変わらない。遠くの道の CLI の断りでは、今までの `次の一歩:` の行が `通すには:` に替わった（文は目録の同じ文）。
- **`--json` の断り**: 今の鍵に `why`・`fix`・`better`・`next_at` を足した（同じ名の鍵があれば上書きしない）。
- **Worker（thth.me）の断り**: 4xx・5xx の `{error: 符丁}` に、目録の `why`・`fix`・`better` を足した（50 符丁）。Meta が呼ぶデータ削除の受け口（`/data-deletion`・`/data-deletion-status`）の答えは、今までと 1 バイトも変えない。
- **`thth dashboard --json`**: `refusal_meter`（断りの率と手順の飛ばし・0 なら鍵が無い）。
- **新しい符丁 `ramp_daily_limit`**: 招待で入った口座の慣らしの期間に、半分の数で断るときだけ出る。台帳の数でも当たるなら今までどおり `daily_limit`。
- **新しい命令 `thth media app-usage`**: 媒体ごとのアプリ全体の使った量の合計を見る（読むだけ）。
- 鍵の名前を変えたもの・消したものは無い。

## 変えたこと

1. **断りの文の正本を目録 1 か所に**（段 A の 2 つ目）。15 の説明の辞書（`remote.NEXT` など・229 項目）は目録から作る読むだけの見方になった。出る文は 1 字も変えていない（main と枝で 15 の辞書を書き出して突き合わせた）。
2. **3 つの口で同じ 3 つ**（段 B）。新しい `thth/refusal.py` が目録を引いて、CLI の文・`--json`・MCP に同じ「なぜ」と「もっと良く」を出す。「通すには」は口ごとに、その口で本当に打てる道（手元の CLI・遠くの道の CLI・MCP・Worker）。
   - 例 too_soon: 手元は原稿の `publish_at` を書いて `thth approve`、遠くの道は `thth schedule … --at <時刻>`、MCP は `thth_draft_put` と `thth_schedule_request`。
   - 返信の日の上限（`daily_limit` の `reply_daily`）は、通すにはともっと良くも返信の上限に合った文。
   - 穴に入れるのは形を検査した口座名と時刻だけ。時刻は `T` 区切りで日時とタイムゾーンがそろい、実在するものだけ。
3. **skill thth を地図に寄せた**（段 C）。断りの 3 行と重なる符丁ごとの直し方を落とし、「断られたら、断りの 3 行に従う」の節を置いた。大きさの上限 71,000 → 69,000（縮んだのは約 2%）。安全の決まりは残した。
4. **手数の計測**（段 F）。口座ごとに直近 7 日の断りの率（書く・送る・置く命令と lint の 100 命令あたり）と、手順の飛ばし 3 型（同じ断りを 10 分に 3 回・`--preview` なしで広場に置いた・lint も dry-run も無い `send --production`）を、observe の道具の段と `dashboard --json` に出す。0 なら出さない。
   - 控えは `state/<口座>/command_meter.ndjson`（0600・14 日・512 KiB を超えたら新しい 4000 行に詰める）。持つのは時刻・口座・命令の名前・結果・符丁・旗の名前だけ。外へ送らない。`thth account leave` で消える。
   - 読むだけの命令は、通ったときは書かない（断られたときだけ数える）。
5. **release の関門**（段 D）。`tools/release_gate.py` が、CI の緑・リリースノートと版の一致・危ない領域に触る版の監査の書・互換の柵を見る。欠ければ `release_blocked: <符丁>` と 3 行で止まる。tag の push の `publish` の前に `gate` の job。監査の書の頭の形は `docs/定型_監査の書.md`。危ない領域の表は `tools/release_gate.py` の `DANGER_AREAS`（MCP の口と遠くの道も入れた）。
   - privacy の数をコードの定数と突き合わせる柵（`tests/test_privacy_matches_code.py`）。
6. **ダッシュボードの理由の表を目録から作る**（`tools/render_refusals.py`・今の 4 本の HTML と 1 字も違わない）。
7. **安全装置の文を作るときに台帳を読まない**。目録を作る途中で `<口座>` の型のまま口座の台帳を読みに行っていた（試験の順番しだいで不正な名前の柵が赤になった）。

8. **共有アプリの柵**（段 E・`thth/shared_app.py`）。数の既定は masaru 11/04「推しで」。
   - **新しいテナントの慣らし**: 招待で入った口座は、入ってから 14 日のあいだ 1 日の公開の上限（`post.daily`・`entry.daily`）を台帳の値の半分にして安全装置が読む（切り上げ・1 未満にしない・台帳は書き換えない）。半分の数で断るときは `ramp_daily_limit` で、慣らしの期間とあと何日かを言う。運営者が `thth account add` で作る口座と、`RAMP_SINCE`（2026-11-05）より前に入った口座には掛けない。返信・削除・反応にも掛けない。
   - **全テナントの合計**: 媒体ごとのアプリ全体の上限に対して全口座の合計が 8 割に達したら、管理者の observe に 1 行出す（止めない・外に送らない・口座の名前と本文は出さない）。数があるのは X の投稿（10,000/24h）と X の読み取りの月の予算だけで、上限の数が台帳に無い媒体は「上限が分からない」と言う。
