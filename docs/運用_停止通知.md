# THTH が止まったときの通知

`thth run <account>` は、各 timer 実行の終わりに Healthchecks へ POST します。
投稿予定が無い正常な実行も成功 ping を送り、token 不在、投稿失敗、残った
`inflight`、未捕捉例外は `/fail` ping を送ります。開始 ping は送りません。
失敗中に開始 ping で一度 UP に戻り、同じ失敗でまた DOWN になる揺れを作らないためです。

## 承認済みなのに出られない（held・3.3.0）

run が成功して「出すものが無い」で終わっても、publish_at を過ぎた承認済みの原稿が要確認（`approval_stale`・返信先の取り下げ・`stale`・型外など）で出られないなら、状態は `held` です（本番で timer に載る account だけ・時刻前と返信待ちは数えない）。死活通知は `state: held` で `/fail` を送り（監視サービスは状態が変わらない限り再通知しません）、運用通知（メール）は**本数が前回の run より増えたときだけ**「停止・要確認」を送り、0 本に戻ったら「復旧」（`held_cleared`）を送ります。理由は `approved_but_held: approval_stale 46` のような区分と本数だけで、原稿名は入りません（名前は `thth observe` の `held_items` と `thth board` の要確認で見ます）。SMTP が無いときは本数だけを記録し、送る先の無い事象を outbox に溜めません。承認の指紋の版が上がった run では、再承認が要る本数を 「再承認が必要」として 1 回だけ送ります。

## inflight を道具が自分で解く（3.3.1）

`inflight` が残っている本番の run は、止まる前に媒体へ 1 回だけ問い合わせます（Threads は container の状態、container の無い媒体は自分の最近の投稿を公開時刻の前後 10 分で引いて本文の指紋が一致する 1 件）。出ていないと決まれば控え（`inflight.resolved-<日時>.json`）を残して解き、同じ run の select から（承認の検査を通り直して）新しく出し直します。出ていたと決まれば post_id を書き戻して解きます。決まらなければ従来どおり `/fail` で止まり、理由は `inflight_unresolved`、次の手順は `resolve_inflight_by_hand`（`thth inflight <account> show` で見て、媒体で確かめた人が `thth inflight <account> resolve` で解く）です。停止の運用通知（メール）は停止が始まったときの 1 通だけで、同じ停止が続く間は送り直しません。

## 設定

アカウント台帳の `env` が指すファイルへ、Healthchecks の ping URL を置きます。

```dotenv
HEALTHCHECK_URL=https://hc-ping.com/<check UUID>
```

アカウント env の値を優先し、そこに無い場合だけプロセス環境の
`HEALTHCHECK_URL` を使います。どちらにも無ければネットワークへ接続せず、run の
標準エラーと `thth board` に「未設定・通知は送っていない」と残します。

scheduled account ごとに別の Healthchecks check URL を設定してください。複数 account
で 1 本の URL を共有すると、止まった account の `/fail` のあとに別 account の成功 ping
が届き、障害中なのに check が UP へ戻ります。プロセス環境の値は一括設定用の fallback
なので、複数 account を動かす本番では各 account env の個別 URL を使います。

ping URL は check の秘密です。THTH は URL を通知本文、状態ファイル、board、例外文へ
保存・表示しません。通知先は HTTPS だけを受け付け、別ホストへの redirect は追いません。

## 監視サービスへ送る内容

失敗 ping の本文は次の 6 項目だけです。

- `account`: アカウント名
- `state`: `success`・`fail`・`held`（承認済みなのに出られない・3.3.0）
- `since`: inflight の開始時刻。読めなければ `null`
- `file`: 原稿の basename。無ければ `null`
- `reason`: 固定の日本語説明と診断コード
- `next_action`: 固定の次の手順と手順コード

投稿本文、token、ping URL、生の stdout、生の API 応答、生の例外文は送りません。
古い inflight と runs に共通の `run_id` が無い場合、同じ basename の投稿エラーは
「過去の候補・対応未確認」と表示し、元の原因だとは断定しません。

HTTP 200 だけでは受領成功としません。応答本文が空白を除いて正確に `OK` の場合だけ、
`thth board` に「監視サービス受領済み」と記録します。`OK (not found)` や
`OK (rate limited)` は配送失敗です。この表示が確認するのは Healthchecks による ping
受領までで、利用者の端末やチャットへ通知が届いたことまでは確認しません。
ping 本文は Healthchecks のログに保存されますが、選んだメール、モバイル、チャット等の
通知本文へ 6 項目が自動で転記される保証はありません。受信側のテンプレートを設定し、
実際の端末まで届くことをテストしてください。

Healthchecks は状態遷移に応じて連携先へ通知します。失敗が続く間も THTH は `/fail` を
送り続けますが、クライアント側で重複通知の timer は作りません。繰り返し通知が必要なら、
Healthchecks 側の reminder を設定します。

timer プロセスそのものや VM が止まると、THTH は `/fail` ping すら送れません。この停止は
Healthchecks の period と grace による「ping 未着」で検知します。10 分 timer なら、例えば
period 10 分・grace 10 分から始め、実際の実行時間と許容遅延に合わせて調整してください。

## 調べ方

`thth board` は資格情報や env ファイルを読まず、最後の run が保存した安全な状態だけを
表示します。`inflight` がある場合は開始時刻、固定の停止理由、次の手順も同じ画面に出ます。
「最後に送った運用通知」（SMTP が受領した時刻・状態・理由・受領した役割）も出ます。運用通知の
事象は outbox に 30 日残るので、停止のメールを送ったかどうかを後から照合できます。
通知が `未設定` または `配送失敗` なら、投稿の再実行より先に通知設定を直してください。
通知失敗は stderr に出ますが、投稿処理の exit code を変更せず、公開要求を再送しません。
