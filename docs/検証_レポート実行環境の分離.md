# レポート実行環境の分離検証

2026-09-18、開発版。一般公開サーバの検収ではない。

## 設定の事前検査

`thth.report_isolation.validate_environment(root, allowed_accounts)` は、明示された専用rootと実行環境の一致を検査する。rootは実行UIDの所有でgroup/other権限なし（通常0700）。account registryはroot/accountsに限定し、許可accountの名前とprojectが実定義と一致することを確かめる。

root内のsymlink（切れたものも含む）、hardlink、FIFO等の特殊ファイルを拒否。account定義のrepo/queue/replies/env/tokenと計算されたstate/dataの参照先がroot内に収まることを検証する。env/tokenはパスの検査だけで、秘密の内容を読まない。エラーは固定コードでパスや入力値を含まない。

これは信頼する管理者の誤設定検出である。走査後のファイル差し替えを防ぐOS sandboxではなく、同じUIDで動く不信コード、root権限の攻撃者、巨大な単一ファイルへの耐性を保証しない。実際の隔離には利用者単位のマウント名前空間とアクセス権が必要。

## Dockerによる実検証

再現用 `tools/check_report_container_isolation.py` は一時ディレクトリにダミー台帳だけを作り、2つのコンテナを並行実行する。実アカウント・秘密・ホストの運用rootを読まない。

```sh
python3 tools/check_report_container_isolation.py --image <ローカルにあるPython3.10以上のimage-id>
```

imageは明示し、pullしない。非root UID、read-only root filesystemとtenant mount、capabilities全削除、no-new-privileges、networkなし、CPU/memory/PID上限を付ける。アプリのPython packageと各利用者のダミーrootだけをread-onlyでmountする。Docker socketはmountしない。

同じaccount=`demo`、project=`project`を持つ2利用者について、実際のreport_service→operations_handoffが異なる件数1/2を返すことを確認する。相手のrootがmountされていないこと、tenantへの書き込みが失敗することも確認する。終了時はこの検証が作った名前付きコンテナだけを回収する。

2026-09-18 macOSのDocker Engine 29.2.1で成功。ローカルCI image `sha256:2b005134aad481da0016ba78c88feb6b8e2d03e85bbe9f0c1f53b564aefa82b5` のPython 3.12.3を使用。これは検証に使ったローカルimageで、THTHの配布imageではない。Python公式imageの取得が進まなかったため取得処理を終了し、既存imageの固定IDを使用した。

この試験のnetworkはnoneであり、HTTP/TLSの公開配線・プロキシ・本人認証・ホストの本番権限・バックアップ削除・障害復旧を確認したことにはならない。専用rootに秘密を置かずレポート用snapshotを供給する構成なら、レポートプロセスにSNS tokenを持たせずに済む。

参考: [Docker公式 Running containers](https://docs.docker.com/engine/containers/run/) のFilesystem mounts、Runtime constraints、Runtime privilege、User（取得2026-09-18、更新日表示未確認）。systemdの公式オンラインmanは403で取得できなかったため、今回は未確認のunitを本番用として追加していない。
