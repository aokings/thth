## 約束の固定（最優先）: 2 度出す経路を作らない

- 公開の要求（`threads_publish`）が 2 度目に飛ぶのは、`ThreadsAdapter._settle_ambiguous()` の中で container の status が `FINISHED` だと確かめた直後の 1 回だけ。`PUBLISHED`・問い合わせ失敗・`IN_PROGRESS`・知らない語では再試行しない。再試行が 4xx でも「出ていない」とは扱わず inflight を残す（1 度目が通っていた可能性を消せないため）。
- 毎 run の最初の自己解決（`inflight_resolve.self_resolve()`）からは公開の要求を 1 度も飛ばさない。出ていないと決めたら inflight を解き、同じ run の select から承認の検査を全部通り直して新しい container で出す。`FINISHED` の古い container は公開しない。
- 出たことが判っている inflight（`post_id`・`mismatch_fields` がある）・添付の inflight（`media`）・dry-run の run には自己解決が触らない。
- container の無い媒体は、一覧照合で指紋が一致する投稿がちょうど 1 件のときだけ解く。0 件・2 件以上・引けないときは解かない。

## 設計から外れた点・解釈した点

1. **自己解決で `FINISHED` を見たら、古い container を公開せず inflight を解いて select からやり直す**（§3 の「表の上 3 行で決まれば解いて進み」の解釈）。公開した run の中の再試行（§2）と違い、run をまたぐと承認の取り消し・publish_at の変更があり得るので、承認の検査を通らずに出す経路を作らないため。runs の理由は `inflight_resolved_not_published`（設計に名前が無いので付けた）。
2. **止まり続けたときの通知は `fail` の状態で理由 `inflight_unresolved`**。3.3.0 の `held` の状態は「run は成功・承認済みが出られない」の意味で、`incident.notify` は `held` を success として進めて前の停止に「復旧」を送る作りのため、inflight の停止には使わなかった。停止のメールは停止が始まったときの 1 通で、同じ停止（同じ始まりの時刻・原稿）が続く間は送り直さない（従前どおり）。死活通知は毎 run `inflight_unresolved` で `/fail`。
3. **`thth inflight resolve` に二段確認（`--confirm <digest>`）を足した**。設計 §4 には書かれていない。「出ていない」を取り違えると次の run が 2 度出すので、`approve`・`retract` と同じ線にした。digest は inflight の始まりの時刻と原稿に結ぶので、別の inflight に流用できない。
4. **公開時刻の近似**: 自己解決と `--published` の `posted_at` は、一覧の行の時刻（あれば）か inflight の `started`（公開要求の約 30 秒前）。
5. **`thth send` の inflight（`(send)`）** は、解けたときに runs に post_id を残すだけで `sent/` は書かない（inflight に本文が無いため）。
6. **添付の inflight** は自己解決も `resolve` も対象外（journal が別の約束で動いている）。`show` は中身を出し、次の一手に `docs/原稿_添付_2.13.md` を案内する。
7. **3.3.1 より前の inflight**（`text_fingerprint` が無い）は、Threads なら container の status で決まるときだけ解ける。PUBLISHED の書き戻しと他媒体の一覧照合はできない（止まって人に任せる）。
8. 公開した run の中の status 確認は本文の経路だけ。添付の経路（`threads_media.publish`）は従前どおり（journal の `media_ambiguous`）。
