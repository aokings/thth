## 設計から外れた点・解釈した点

1. **「目的の変更」を見分ける元として、承認のときに `approved_goal:` を front-matter に書く**（`approval.approved_fields`・ローカルの二段確認とサーバの承認の両方）。目的が無ければ `none`。設計は「書き換えは runs と sent に残す」までで、承認の時点の目的をどこに控えるかは書いていない。指紋ではなく控えなので、`approved_goal` を書き換えても承認は古くならない。`approved_goal` を持たない原稿（3.6.0 より前の承認）は承認の時点が分からないので変更とは言わない。
2. **`--by goal`・observe・地図の層は公開の時点の記録だけから作る**（`goals.recorded_goals()`: sent と連投の実行記録）。いまの原稿は読まない——公開のあとに `goal:` を書き換えても過去の層は動かない。記録に目的の無い投稿（3.6.0 より前を含む）は `none`（設計「無ければ none」）。`unknown` の層は作っていない。
3. **承認のあとに `goal:` を 4 語以外に書き換えても公開は止めない**。記録には `unknown` と残す（目的は札なので公開の門にしない）。4 語の検査は lint と承認の入口だけ。束も同じ理由で `bundle.check()`（公開の経路も呼ぶ）には入れず、lint と `_prepare_bundle` に入れた。段ごとの `goal` は既存の `POST_KEYS` の検査が「知らない項目」で断る。
4. **MCP の `thth_report_timeline` はサーバ型だけ**（報告の口の他の道具と同じ。手元の stdio の `TOOLS` は変えていない——`tests/test_mcp.py` の集合も変わらない）。CLI `thth report timeline` はどこでも動く。
5. **サーバ型の送信（`server_writes`・`approval_jobs` の send）と MCP には `goal` の欄を足していない**（その経路の送信は `none` で残る）。設計は `thth send --goal` まで。
6. click の日次は `clicks` と、在れば `clicks_by_url`（Threads の account 日次がリンク先別に持つもの）を並べる。follow の日は JST の日付で `[開始日, 終了日)`。reply の「返信した人の異なり数」は 24 時間の窓が閉じたあとに取った記録がある投稿だけを数え、自分かどうか分からない返信が窓にあればその投稿は数えない（理由を `missing_reasons` に）。
7. **年表のリリースノートの行は、範囲の報告 id を含むか、範囲の project・account の名前を含む「実測から」の行があるものだけ**（語の一致）。`--since` は行の並びだけを絞り、集計は範囲の報告全部。先輩の年表は「最初の報告から 14 日未満か、まだ報告が無い」持ち主に出し、見る側の project も広場の open に参加しているときだけ（open と同じ線）。他の持ち主の project 名・題・id は出さない。
8. observe は投稿ごとの目的と主な物差しを先頭に出す形にした（目的ごとに段を分ける形は作っていない）。目的が無い投稿の行は従前の並びのまま。
9. inflight を解いて記録する経路（`inflight_resolve`）は sent に目的を書くが、runs の行には目的を足していない。
10. サーバ型の `analytics_report` の `by` の検査（`report_service`）は起点から `attachment_kind` を持っていない。`goal` だけを足し、`attachment_kind` は触っていない（範囲外・未確認のまま）。
