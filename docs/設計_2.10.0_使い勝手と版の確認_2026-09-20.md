## 1. 直し

### 1.1 `where` の引数
`parse_intermixed_args` で語とオプションの順序を自由にする（thth 全体でよい）。加えて `--word <語>`（複数可）を足し、語を明示できるようにする。既存の位置引数はそのまま。

### 1.2 Bluesky の投稿の指し方
`thread`・`send --reply-to`・`after`・`replies --post` が受ける Bluesky の post_id に **`https://bsky.app/profile/<handle|did>/post/<rkey>`** を足す。handle は `com.atproto.identity.resolveHandle`（公開・認証不要）で DID にし、内部では従来どおり `at://` に正規化して台帳に残す（台帳の形は変えない）。解決できなければ loud reject（`handle_unresolved`）。`where` の人向け出力には permalink の下に `post_id: at://…` を併記する。

### 1.3 `--json` の規律
「`--json` のとき stdout は JSON だけ・進捗と断りは stderr」を、`--json` を持つ全コマンドについて **1 つの表形式テスト**で固定する（既に守られているなら追加の直しは無い）。使い方文書に「手元のラッパは ssh なので、JSON だけ取るときは `2>/dev/null`」を 1 行。

### 1.4 ロック
- **dry-run の `send`（`--production` 無し）はロックを取らない**（読むだけ・台帳に書かない）。
- 書く口（`send --production`・`approve`・`replies --refresh`・`revoke`・`retract`）に **`--wait <秒>`**（既定 0＝今のまま即断り）。待って取れなければ今と同じ断り文＋「`--wait` で待てます」。
- 読む口（`where`・`thread`・`after`・`replies`・各 report）がロックを取らないことをテストで固定。

### 1.5 Mastodon の 403 と scope
- `mastodon.py` の HTTP エラーを `AdapterError` にするとき、**403 は `permission`** として `failure="permission"` 相当の理由コードを付け、検索なら「token に `read:search` が要る。アプリ設定で足して `thth token set <account> --by …` し直す」を案内。422／404 は今のまま。
- `account add --media mastodon` と `token set` のときに、**要る scope の一覧**（`read:accounts read:statuses read:search read:notifications write:statuses`）を stderr に出す。
- `doctor`（Mastodon）は読み取り probe を 2 つ足す: `/api/v2/search?type=statuses&q=thth&limit=1`（search）・`/api/v1/notifications?limit=1`（notifications）。結果は 2.9.0 の `doctor.json` に残り、`admin tokens` の `missing_scopes` に Mastodon も並ぶ（scope 名は probe の結果から**推定**と明記: `scopes_source: "probe"`）。

### 1.6 `who`
複数の handle を受ける（1 人ずつ順に・失敗は行ごと）。受けないなら断り文に「1 度に 1 人」。Codex が現行の引数を見て決める。

### 1.7 `approve` の絞り込み
`thth approve <dir> --account <name>` で、ディレクトリから拾う draft をその account のものに絞る。`--status` は作らない（draft 以外を承認する意味が無い）。使い方文書に「ディレクトリを渡せる・glob は手元で展開されるので使わない」を明記。

### 1.8 dry-run の字数
`send` と `approve` の一段目の末尾に **`文字数: 181/300（bluesky・grapheme）`** を出す。数え方と上限は `count_for`／`limit_for` の対（媒体名で分岐しない）。超過はいまどおり digest を出さずに止まる（そこは変えない・テストで固定）。

### 1.9 相対パスの解決
ファイルを受ける引数（`approve`・`preview`・`lint`・`revoke`）で、**相対パスが VM の cwd に無いときは各台帳の repo root からの相対として探す**。ちょうど 1 つの repo で見つかれば使い、どの repo を使ったかを stderr に 1 行。0 個なら「VM の repo に無い」、2 個以上なら「曖昧（候補列挙）」で断る。手元の絶対パス（`/Users/…`）は「手元のパスは写像できない」と今の案内。

## 2. 新しい口

### 2.1 `mentions` の Bluesky・Mastodon
- Bluesky: `app.bsky.notification.listNotifications`（reason ∈ mention／reply／quote）。読むだけ・台帳に書かない（Threads の `mentions` と同じ規律・相手は仮名 `author_key`・本文は表示だけ）。
- Mastodon: `GET /api/v1/notifications?types[]=mention`（`read:notifications` が要る・無ければ §1.5 の 403 案内）。
- 出力の形は Threads の `mentions` と同じ鍵（`kind`・`post_id`・`author_key`・`username`・`preview`・`timestamp`・`replied`）。`capabilities` に `mentions` を足す。`collect` の `inbox` 経路には**入れない**（台帳に書くかは別の裁定）。

### 2.2 `thth unanswered <account> [--since <期間>] [--json]`
自分の根投稿に付いた**他者の返信**のうち、自分の返信がどこにも無いものを一覧する。読むだけ。
- 源は既存の台帳だけ: `thth collect` が採った返信の台帳（`replies`）と、絡みの台帳（`reply_to`・`author_key`）・queue の front matter（`reply_to`）・自分の送信記録（`sent`）。訂正（Codex の照合 2026-09-20）: 現行の `sent` は `reply_to` を持たない——**2.10.0 から新たに書く sent に `reply_to`（無ければ `null`）を足す**。旧 sent の欠損は「根投稿」の証明にせず `unknown`。自分の返信が根に 1 本あるだけで他の相手の reply まで回答済みにしない（reply ごとに突き合わせる）。**枝を読みに行かない**（`--refresh` を付けたときだけ `replies --refresh` と同じ取り直しをしてから読む）。
- 行: `post_id`（根）・`reply_id`・`author_key`・`username`・`preview`・`age_hours`・`verified: "ledger_only"`（枝の実体は見ていない印）。
- `n_total`・`window`・`cannot_say`（採集が古い＝`collection_stale_hours`）を必ず添える。
- `handoff-report` の `cannot_say` にある `unresolved_replies_not_measured` は、この口が答えるので `unanswered: {n, oldest_age_hours}` を `handoff-report` にも載せる（同じ関数を呼ぶ・二重計算しない）。

### 2.3 `where` の絞り込みと材料
- `--since <期間|ISO>`（Bluesky は `searchPosts` の `since`・Mastodon は結果の `created_at` で絞る・絞った後の n を出す）。
- `--exclude-engaged`（絡みの台帳に `author_key` がある相手を落とす・落とした数を出す）。
- `--max-per-author <n>`（同じ `author_key` の行を n 件まで・落とした数を出す）。
- 各行に **`reply_count`**（Bluesky の `replyCount`・Mastodon の `replies_count`・取れなければ `null`）。自分の返信有無は既存の `replied` のまま。

### 2.4 `thth study add <施策JSON> <post_id|queue のパス> [--baseline]`
施策 JSON の `changed_post_ids`（`--baseline` なら `baseline_post_ids`）に post_id を足す。queue のパスを渡したら front matter の `post_id` を読む（無ければ断る）。**利用者の repo のファイルを書く口**なので、`--by` を要求し、commit はしない（今の `study-report` の規律と同じく、同期は利用者側）。

### 2.5 Bluesky／Mastodon の by_mark
`analytics_comparison.METRICS` に `reposts` を足す（Bluesky `repostCount`・Mastodon `reblogs_count`・Threads は insights の `reposts`——訂正 2026-09-20: 初版は「Threads は `null`」と書いたが、`threads.py` の POST_METRICS は reposts を採っている。3 媒体とも採れた値を出し、無いときだけ `null`）。views の無い媒体では by_mark の各刻みに likes／replies／reposts が並ぶ（採集がその値を記録していることを Codex が確かめる・無ければ `insights` の行に足す）。媒体をまたいで足さない約束はそのまま。

## 3. 版の確認を開始の流れに入れる（masaru の問い）

いま `thth board` で版は出るが、LLM は**前回の版を覚えていない**ので「変わったか」を判せない。2.6.0 の handoff cursor は「前回読んだ位置」を account ごとに持っているので、そこに版を足す。

- `handoff-report <account> --since-last-read` の出力に **`tool`** を足す:
  ```json
  "tool": {"version": "2.10.0", "previous_version": "2.9.0", "changed_since_last_read": true,
           "release_notes": ["docs/リリースノート_2.10.0_….md"], "notes_root": "/srv/thth/app", "notes_root_local_hint": "~/Developer/thth"}
  ```
  `release_notes` は `docs/リリースノート_<版>_<日付>.md` のうち `previous_version < 版 <= version` のもの（版の比較は数値の 3 組）。cursor が無ければ `previous_version: null`・`changed_since_last_read: null`・`release_notes` は最新 1 本。`--since-last-read` 無しでも `version` と最新 1 本は出す。
- cursor の snapshot に `tool_version` を足す。**旧 cursor（鍵が無い）は `tool_version: null` として読む**（`cursor_unreadable` にしない・`_validate` の `set(s)!=KEYS` を緩める）。`changes` にも `tool_version` の前後が出る。
- `skills/thth/SKILL.md` の冒頭に「開始時に `thth handoff-report <account> --since-last-read --json` を読む。`tool.changed_since_last_read` が真なら `release_notes` を読んでから作業する」。`thth-admin` の skill は `admin diff` が既に版の変化を出す。
- MCP の `operations_handoff` も同じ鍵を返す（同じ関数）。
