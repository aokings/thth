# 検収依頼 2.14.1: umask と lint の理由（9ffb708）

2026-09-23。初回の 3.0 通し運転（VM・Ubuntu・`umask 0002`）で出た 2 件の直し。
枝 `claude/2.14-x`（`main` = `d1a716e` = 配布済みの 2.14.0 から）。

**配っていません。** `thth/VERSION` は `2.14.0` のままです。版を上げるのも
`release` を進めるのも tag を打つのも masaru の一言を待ちます。

---

## 1. 何が起きていたか

`thth_draft_put` が 2 通りに詰まりました。**どちらも「断り方」の欠陥**です。

1. **P2**: `write_unavailable` とだけ返る。中では `managed_repo.initialize` →
   `git init` が作った `repos/_server/<account>/.git` が **0775**、`git fetch` が
   作った `.git/FETCH_HEAD` が **0664** で、その直後に thth 自身の隔離検査
   （`managed_repo.validate` → `server_files.directory` の `unsafe_server_directory`、
   `_storage_tree` → `server_files.regular` の `unsafe_server_file`）が同じ repo を
   断っていました。**thth が作らせたファイルを thth が拒む**という自家中毒で、
   運用者には理由が 1 文字も出ません。
2. **P3**: `invalid_draft: lint_failed` とだけ返る。実際の理由は台帳の
   `hashtags: false` が本文の `#語` を弾いたことでしたが、それが呼び手に届かず、
   同じ本文を送り直すしかありませんでした。

## 3. P2: Git を呼ぶのは thth なのだから umask も thth が決める

- **`managed_repo.run` が全ての git 子 process を `umask 0077` で起動します**
  （`private_umask()`）。managed repo へ git を出す口は
  `writeback._run_git` / `_run_git_bytes`（`managed_repo.account_for` が当たれば
  `managed_repo.run` へ合流）、`media_uploads`（`status` / `ls-files` / `checkout` と
  `writeback.commit_and_push`）、`managed_repo.initialize` の 5 commands、全部
  ここ 1 つに集まります。**直す場所は 1 箇所で足ります。**
- **`preexec_fn` は使いません。** fork と exec の間に Python を走らせる形なので、
  読み取りの締切タイマー（`report_http` の `threading.Timer`）が同じ process に
  いる以上は避けました。代わりに call の前後で process の umask を差し替えて
  必ず戻します。process 全体を一時的に**厳しく**するだけで、**緩める向きには
  決してならない**ので、同居する別 thread がファイルを作っても危険側に倒れません。
- **thth 自身が作るディレクトリは元から明示 0700** です
  （`server_files.directory(create=True)` の `os.mkdir(part, 0o700)`）。umask は
  bit を落とす方向にしか効かないので、そちらは触っていません。
- **断る理由をモードだと名指しします**（`managed_git_store_unsafe_mode`）。
  `_storage_tree` はディレクトリ・ファイルとも、群/他の書込 bit だけが理由の
  ときにこの静的な理由を上げます。`server_files.directory` も所有者違いを
  `unsafe_server_owner` に分けたので、`unsafe_server_directory` は**モードの話
  だけ**になりました（2.12.0 の `/srv/thth/state` 775 の事故と同じ層です）。
- **この理由は `write_unavailable` で潰しません。** `server_writes.REPO_REASONS` に
  入れて `SAFE_ERRORS` へ通します。運用者が `chmod` で直せる唯一の理由なので、
  HTTP なら `503 {"error":"managed_git_store_unsafe_mode"}`、MCP なら同じ 1 語が
  返ります。
- **`thth systemd --approval-worker` が `UMask=0077` を出します。**
  `docs/運用_サーバ書込_2.12.md` に、**MCP と `serve-reports` の起動口にも
  `umask 077` が要る**こと（systemd なら unit に `UMask=0077`、shell からなら
  起動前に `umask 077`）と、既に群書込可で作られてしまった場合は `chmod -R go-w`
  で直すことを書きました。

**既存の VM を直すとき**（配る前に masaru が判断すること）:

```sh
chmod -R go-w /srv/thth/repos/_server /srv/thth/state
```

所有者は変えません。これを先にやらないと、unit に `UMask=0077` を足しても
**既にあるファイル**は群書込可のままなので `managed_git_store_unsafe_mode` が
続きます。

## 4. P3: 断り文句は理由を持って帰る

- `lint.reason_code()` が `lint_file()` の 1 行を**固定の符丁 1 語**に畳みます。
  `hashtags_disabled_by_ledger`・`too_long`・`invalid_publish_at`・
  `control_char_in_body` など、いま 17 語です（`lint.REASONS`）。
- **lint の日本語 1 行と path はサーバの口から出しません。** 表に無い文面は
  `lint_failed` に落ちます。lint の文面が将来増えても、自由文が外へ漏れる経路は
  できません。
- `server_writes.DRAFT_REASONS` が `invalid_draft` に添えてよい理由の全てです
  （`lint.REASONS` ＋ `body_not_representable` ＋ `media_not_representable`）。
  **HTTP の `/write` も MCP の wrapper もこの表で濾します**——MCP 側は今まで
  `exc.reason` を素通ししていました。
- ついでに HTTP が `media_not_representable` も返すようになりました（今までは
  `body_` の方だけ通していて、文書（2.13.0 第 9 段）と食い違っていました）。

見え方:

| 本文 | 台帳 | 返り |
|---|---|---|
| `本文に #語 を入れる` | `hashtags: false` | `invalid_draft: hashtags_disabled_by_ledger` |
| 501 字（`char_limit: 500`） | — | `invalid_draft: too_long` |
| lint の知らない文面 | — | `invalid_draft: lint_failed`（今までどおり） |

## 7. 決めたこと・見ていないこと

1. **`unsafe_server_directory` の意味を狭めました**（所有者違いは
   `unsafe_server_owner` へ）。この 2 語はどちらも外へ出る口を持たない内部の
   理由で、試験も文書も参照していませんでした（2.12.0 のリリースノートの記述
   だけが該当し、そちらはモードの話なので今の意味と合っています）。
2. **利用者自身の repo の umask には触っていません。** `writeback._run_git` の
   非 managed 経路（`thth pull` が触る普通の project）は今までどおり運用者の
   umask で動きます。あちらのモードは thth が決めることではありません。
3. **`core.sharedRepository` は使いませんでした。** Git の側から permission を
   指定する道もありますが、`FETCH_HEAD` のような Git の内部ファイル全部に
   効く保証が読めず、`init` 経由で repo の config に鍵が増えると
   `managed_repo._config` の許す鍵の集合とぶつかります。umask なら**子 process が
   作る全て**に効きます。
4. **実機では確かめていません。** VM に降ろしてから、`chmod -R go-w` → unit 更新
   → `draft_put` の順で通してください。手元は macOS なので `umask 0002` は
   試験の中で作った状況です。
