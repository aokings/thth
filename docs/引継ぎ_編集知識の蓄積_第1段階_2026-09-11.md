## 3. 設計条件 3 つ（このセッションで決めた・理由込み）

Codex §4 の理由 ID 8 個（`unsupported_claim` ほか）を実装するにあたって、
**次の 3 つを満たすこと。**

### 条件 1: 理由の語彙は「コード」ではなく「データ」にする

`forms.py` の語彙はモジュール定数なので、入れ替えに commit と配布が要った。
**理由 ID はストアの中の版付きレコードにする。**
そうすれば差し替えが**記録 1 件**で済み、Codex §8 の
`proposed → shadow → accepted → retired` がそのまま乗る。

### 条件 2: `other` に自由文を必須にし、件数と内訳を出力に出す

**語彙が足りないことを、道具が自分で言えるようにする。**
`other` が増えたら語彙を疑う。これが「この語彙は分けているか」の自動化。

**`forms` は 3 セッションが 3 本書いて 3 本とも `問い→答え` に落ちた**ことで
初めて分かった。**そのときは道具が何も言わなかった。**同じ失敗を繰り返さない。

### 条件 3: 同じ指摘に、主体違いの判定を並べられる形にする

Codex §6.2 の**判定主体**をそのまま使う。
masaru と担当セッションが同じ指摘に違う ID を付けたとき、**上書きせず両方残る。**
これで一致率が測れる。**紙でやるより正確。**
