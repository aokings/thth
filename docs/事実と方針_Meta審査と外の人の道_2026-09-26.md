## (b) 審査員が試すのに何があれば足りるか

審査員は LLM を持たない前提で考える（Claude Code を用意して MCP をつなぐ審査員は想定できない・推測）。すると、審査員の手で 6 権限を試せる口は**ブラウザの画面**しかない。

| 案 | 審査員の手 | (a) との合い方 | masaru の方針との合い方 |
|---|---|---|---|
| A. 承認ページ（前のセッションの申請の文 §2.1） | 運営者が本文を置き、審査員は承認だけ | **合わない**: 本文を書くのが運営者で、"Create a new post … add text" を審査員がしていない | **合わない**: 承認を主役にする・審査員の口座だけ `--approval all` |
| B. 録画だけ・手で試す口なし | 招待と認可まで | 「試せない権限は落とす」に当たる恐れ | 合う |
| **C. 持ち主の画面で自分で書く・出す・消す** | `/activity` に入り、自分で書いて出す・返信・消す・自分の投稿と返信と数を見る | 合う | 合う: 承認ではなく持ち主の操作。LLM から頼むのと同じ道・同じ安全装置 |

前のセッションが最後に出した案（申し送りのぶれ 4）は C と同じ形。こちらは (a) の文言から同じところに行き着いた。

## (c) 3.12.0 に今あるもの・無いもの（L1）

ある:
- 招待リンク → Threads の認可 → 口座ができる → secret を 1 度だけ表示（`callback/src/invite.js`・`thth/invites.py`）。新しい招待の既定は `approval: none`。
- `/activity`: 出た・消した・予約・止めた理由を見る。止める・戻す・予約取り消し・設定・LLM の鍵の発行（`callback/src/activity.js`）。
- 安全装置（`thth/guard.py`）・承認なしの公開・削除（MCP の道具から）。

無い:
- **`/activity` で書いて出す・返信する・消す口。** 消すのは予約の取り消しだけ。
- **`/activity` で自分の投稿の一覧・返信・数を見る口。**「出た・消した」の記録はあるが、Threads から取った投稿・返信・数は出ない。→ `threads_read_replies`・`threads_manage_insights` は今のままでは審査員が試せない。
- `/activity` の操作は**毎回 secret を入れる**（`secretField` が各 form に入っている）。masaru の「何をするにもキーを入れる方式は使いたくない」に当たる。
- 外の人の LLM が THTH につなぐ道（MCP は stdio・起動口は VM の上）。
- 利用規約は今も "Approve each post yourself." と約束している（`callback/public/terms/`）。`llms.txt` の冒頭は "a human-approval gate"。

分からない（Dashboard で masaru が見るもの）: `threads_delete` の呼び出し数・App Purpose（Clients か）・09-22 の提出で「アプリの検証」欄に何を書いたか（repo に記録が無い）。

## (d) 進め方 1 本

1. **`/activity` を持ち主の小さな画面に広げる。** 入るのは 1 回（ユーザ名と secret・しばらく有効な cookie）で、中の操作ごとには secret を聞かない。足すのは、書いて出す（本文・画像 1 枚）・返信する・消す、自分の投稿の一覧・返信・数。中身は MCP の道具と同じ `server_writes` と読む道具を通し、安全装置も同じに効く。
2. **審査員の手順を書き直す。** 招待 → 認可 → secret を保存 → `/activity` に入る → 書いて出す → Threads のアプリで確かめる → 返信 → 数と返信を見る → 消す。運営者は何も用意しない。審査員の口座も `approval: none`。承認ページは出てこない。
3. **録画は 2 の手順をそのまま撮る。** 主な使い方（持ち主が自分の LLM に頼む）は前置きの文で説明し、映すのは審査員が真似できる画面だけ。昨夜の録画 0（承認の流れ）と `tools/appreview_rec0.sh` の `--approval all` は使わない。
4. **規約・privacy・`llms.txt` を 1 と同じ版で直す**（下書き `docs/下書き_利用規約とprivacyの3.12改訂_2026-09-26.md` を土台に「毎回承認」を外し、画面からの操作を足す）。
5. リモートの MCP は**審査の前提にしない**。外の人が自分の LLM を使うには要るので、審査とは別に masaru が決める。

規模の見立て（推測）: 1 は writer で 1〜2 日。そのあと録画と提出。

### 前提が変わったら

- **Meta が実際には録画しか見ていない**なら（09-22 の提出は CLI の録画だけで通った・L1。ただし読むだけの 4 権限で、試し方の記載は未確認）、1 は審査には要らなかったことになる。代償は 1〜2 日。逆に 1 を省いて試されたら、試せない権限だけ落ち、その分を出し直す（1 回の判定に 1 週間前後）。
- **審査員向けに A（承認ページ）で急ぐ**なら、今日にも出せる。ただし publish の要件（利用者が本文を書く）を満たさない恐れがあり、方針とも食い違う。
- **リモートの MCP を先に作る**と決めても、審査員が LLM を持たない限り、審査の口は 1 のままでよい。

## masaru に聞くこと（1 つ）

上の 1〜5 で進めてよいか。特に 1 の「入るのは 1 回・中の操作ごとには secret を聞かない」（止める・緩める・鍵の発行も同じ扱いにするか、そこだけ secret を聞き直すか）。推薦は、**緩める・止めたのを戻す・鍵の発行だけ secret を聞き直す**。書く・出す・消す・止めるは聞かない。
