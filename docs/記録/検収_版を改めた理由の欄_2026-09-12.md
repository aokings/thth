## P2: null補完が旧入力の再登録の同一性を壊す

`thth/topic_models.py` の `build_hypothesis()` 末尾で、新しい任意キーを `null` で補ってから内容IDを計算している。保存済み旧レコードにはキーが無いため、同じ入力・同じactorを再登録すると別レコードになる。

実プロセスCLIで、旧fb85182を用いて登録→同じ棚へ新318bc3bで同じJSONを登録した結果:

| 操作 | ID | stored |
|---|---|---|
| 旧版で登録 | `sha256:99ec8d562b1c93f5b1f1844918ea3268f0190c2a9f6a1d02c4cf6853aa023a87` | true |
| 新版で同一入力を登録 | `sha256:37ae9ee6d6e2cedbc1623f8e4d0390a5cdd490d97f5c263967d8e151ccbbb4ac` | true |
| 新版で明示nullを登録 | 上の新版IDと同じ | false |

一覧countは2。旧JSON自体は不変で、破損ではなく重複である。さらに旧IDを指す改訂を作っても、この複製は別IDなので後継として結び付かない。

**「旧ID互換性か、省略/nullの同一性か」の二択ではない。両方守れる。** 検査を終えた後、理由がNoneなら保存する辞書から `supersede_reason` を除き、文字列なら残して内容IDを計算すればよい。省略と明示nullを両方「キーなし」に正規化する。新しい辞書からnullキーを除いて再計算すると、実際に上表の旧IDへ一致した。保存済みJSONの書換え、全棚移行、別のID仕組みは不要。

## 依頼の3つの判断への回答

1. **supersedesがある新規改訂に理由を要求する方針に賛成。** 主張と改訂メモを分ける目的に直接対応する。新規の理由なし改訂は拒否してよい。一方、旧保存記録は読めるままとし、理由を推測で補わない。「任意キー」は旧改訂入力まで再受理する意味ではないことを明記する。理由は訂正だけでなく追加資料・対象範囲の変更でもよく、「以前の誤り」の告白を求める欄にしない。自由文の妥当性を機械が保証するとは扱わない。
2. **null補完の選択は変更する。** 上述のnull/省略をキーなしに揃える最小案を採る。旧IDを維持できるのに重複を受容する必要はない。
3. **REVIEW_OPTIONALとの全面統一は不要。** 今回は仮説だけで解決してよい。任意キー定数を他モデルで一斉に効かせる変更は、別の保存IDや受理範囲を変えるので含めない。HYPOTHESIS_OPTIONALを宣言として残すか局所処理にするかは実装裁量。
