## 1. 何が起きていたか

### 1-1. 画面に出ないものを根拠に「無し」と言っていた

運用の指摘: **`thth measured` が「欠けている指標: 無し」と出すのに、その判定は
人向け出力が 1 行も表示していないアカウント日次の台帳を使っていた。**

### 1-2. **取れる指標が層ごとに違った**（こちらが追いかけて見つけた）

| 層 | 取れる指標（`thth/adapters/threads.py`） |
|---|---|
| 投稿単位（`:237`） | views likes replies reposts quotes **shares** |
| アカウント日次（`:255`） | views likes replies reposts quotes **followers_count clicks** |

`shares` は投稿にしか無く、`clicks`・`followers_count` はアカウントにしか無い。
**なのに両方の台帳を 1 つの集合に混ぜ、1 つの期待一覧と突き合わせていました。**

> **片方の層でその指標が 1 度も採れていなくても、もう片方の層に出ていれば
> 「欠けていない」になる。**

運用が挙げた `clicks` は一例で、**逆向き（投稿の `views` が 1 件も採れていないのに、
日次に `views` があるので隠れる）のほうが重い**と考えています。

### 1-3. **翌日の行が前日の欠測を隠す**（運用が実測で確定させた）

`clicks` を採れるようにした修正が VM に着地したのが **00:08:24**。その日の日次採取は

```
asmon      00:03:12  … 5 分早い  → 2026-09-11 の clicks は**永久に欠測**
nigamilab  00:05:14  … 3 分早い  → 同上
kopicha    00:08:32  … **8 秒遅い** → 間に合った
```

日次は日付ごとに 1 度しか採りません（`thth/collect.py:332`）。**取り返せません。**
ところが翌日ぶんには `clicks` が入るので、**「1 度も現れていない」という全体判定
からは消えます。**

### 1-4. **同じ根が仮説の側にも出ていた**（運用が繋げた）

**帰属を正確に書きます。** 層が 2 つあると気づいたのはこちら（1-2）で、**その説明を
受けて「同じ根が仮説の側にも出ている」と繋げたのが運用セッション**です。運用自身の
訂正によります。

運用が仮説を 1 件登録し、**自分で穴を見つけて報告してきました。**

> 「views が最多の投稿の URL が、その日の `clicks_by_url` でも最多になる」。
> `views` は投稿単位、`clicks_by_url` はアカウント日次×URL。つまり私の予測は、
> **「その投稿が生んだクリック」という変数が台帳に存在しないまま書かれている。**

`LEDGER_METRICS` が**8 つの名前を並べただけの平らな一覧**だったので、両方「うちに
ある指標」として通っていました。

## 2. 直したこと

### 2-1. 欠測の判定（`thth/measured.py`・`thth/cli.py`・commit `6fa4b14`）

- 期待一覧を層ごとに分けた（`POST_METRIC_NAMES` / `ACCOUNT_DAILY_METRIC_NAMES`）
- **キー名も捨てた**（`missing_metrics` → 層ごとの 2 つ）。**名前を残すと古い
  読み手が黙って通る**ので、壊れて気づくようにしました（規約 5）
- **日次の台帳が 1 本も無ければ `None`。**「欠けている」と言わない——採っていない
  ので、欠けているかどうかも判らない。**空配列（台帳はあり欠けは無い）と混ぜない**
- **アカウント日次を人向け出力にも出す**
- **各行に `missing`**（その行に無い指標の名前）。1-3 の穴を残すため。
  `_row_missing()` の docstring に**3 つの時刻をそのまま書き込みました**

### 2-2. 仮説の指標（`thth/topic_models.py`・`thth/topic_cli.py`・commit `98aea8b`）

- `METRIC_UNITS`（指標 → **実際に取れる観測単位**）を唯一の定義にし、
  `LEDGER_METRICS` はそこから導く。**平らな一覧は無くしました**
- **そろう観測単位が 1 つも無い → 拒否**（`shares` と `clicks` など）
- **層が食い違う → 警告**（`unit_warnings`）。**拒否しません**——`proposed` は
  未検証の仮説を置く場所で、拒否すると置き場が無くなります（R4 の裁定に従いました）
- `METRIC_CAVEATS`: **その指標を使うと何が台帳に無いのか。** `clicks` は「どの投稿が
  生んだクリックかは台帳にありません」。**account ごとではなく指標ごとの但し書き**
  ——運用が「asmon だけ外せば検証できる」と誤ったのは、識別不能を account の問題だと
  見たためでした
- `unit_warnings` は**保存しません。** 読むたびに当てるので保存済みにも効きます
- **`declaration_notice` の言い切りも直しました。** 「観測単位は確認していません」の
  まま機能を足すと、**道具が自分について嘘をつきます**

## 3. **判定をお願いしたいこと**

1. **`missing_metrics` というキーを消したこと。** 互換を残さず壊す判断です。
   消費者は `thth/cli.py` 1 箇所だけでしたが、**外部に読み手がいる前提なら戻します。**
2. **日次の台帳が無いときの `None`。** 「欠けている」と「判らない」を分ける意図
   ですが、**`None` / `[]` / 非空の 3 状態を読み手に押し付けています。**
   別の表し方のほうがよければ指示ください。
3. **層の食い違いを「警告」に留めたこと。** R4 の「proposed は自由文でよい」に
   従った判断です。**拒否すべきなら変えます。**
4. **拒否と警告の線の引き方**（そろう単位が 0 なら拒否／食い違うだけなら警告）。
   これはこちらの設計判断で、外部の反例に基づいていません。

## 6. push していません

前回と同じです。`cmd_run()` 冒頭の `selfupdate.pull_and_reexec()` と 10 分周期の
timer により、**push は本番反映と同義**です。判定が返るまで push しません。

**なお前回の「必ず 10 分以内とは認定しない」という留保について、運用セッションが
実測を 1 つ出しました。** VM の reflog で `HEAD@{09-12 02:48:07} 77a09ae
pull --ff-only: Fast-forward`。**timer の次の発火（02:48:00）の 7 秒後**でした。
**実測 1 サンプル**です。「10 分以内」は依然として周期からの上限であって、
実測ではありません。
