## 2. 背景

Meta の管理画面に「ユーザートークン生成ツール」があり、Threads テスターの長期
アクセストークンをボタン 1 つで発行できることが分かった（2026-09-09 masaru 判断）。
`thth auth` の OAuth 往復（認可 URL → ブラウザ承認 → code 貼り付け → 短期/長期交換）
を経ずにトークンが手に入るので、masaru はこちらを使う。`thth auth` は tester 以外を
扱う日のために残した（削除していない）。

## 3. 実装した口

- `thth token set <account> [--force] [--stdin]`
  1. `accounts/<account>.json` の `token` パスに既に `.token` があれば、`--force`
     が無い限り exit 1（「既にあります。上書きするなら --force」）。有効なトークンを
     誤って潰さないための確認。
  2. トークンを読む（`thth/oauth.py::_read_pasted_token`）:
     - `--stdin` 指定時、または標準入力が端末でない（パイプ）とき: `sys.stdin.readline()`
       で黙って 1 行読む。
     - 標準入力が端末のとき: `getpass.getpass()` で画面に表示せず読む。
  3. `extract_token()`（`extract_code()` と同じ思想）で前後の空白・改行・引用符を
     落とし、`access_token=...` のような接頭辞が付いていれば剥がす。
  4. `GET {graph}/v1.0/me?fields=id,username` を叩いて実在確認する（`me` に触れる
     エンドポイントは `thth auth` の `fetch_me()` をそのまま再利用）。失敗（4xx/5xx・
     `id` が空）なら `.token` を作らず exit 1・「トークンが使えませんでした」（伏字を
     通した詳細つき）。
  5. 成功したら `~/.config/thth/<account>.token` に次の形で 600・原子的に書く（`thth auth`
     と同じ形）:
     ```json
     {
       "access_token": "...",
       "obtained_at": "<このコマンドを打った時刻・JST ISO>",
       "expires_in": 5184000,
       "user_id": "...",
       "username": "...",
       "scopes": null
     }
     ```
     - `obtained_at` は「管理画面で発行した時刻」ではなく「`thth token set` を打った
       時刻」になる（docstring に明記）。`thth refresh` は 50 日超で更新するだけなので、
       数日ずれても実害は無い。
     - `expires_in` は管理画面の発行では返らないので、長期トークンの既定 60 日
       （`oauth.py::DEFAULT_TOKEN_LIFETIME_SECONDS`）を使う。
     - `scopes` は管理画面発行では分からないので `null`（嘘の一覧は書かない）。
  6. 標準出力には `user_id`・`username` と確認文だけを出す。トークンは一切出さない
     （すべて `redact()` 経由の `_out()` を通る）。

- `thth/core.py::_default_adapter_factory`
  - `user_id` を `.token`（`thth auth` / `thth token set` が書く）優先・無ければ台帳
    `accounts/<account>.json` の `user_id` にフォールバックするよう変更した。
  - 台帳の `user_id` は元々必須項目ではなく（`accounts.REQUIRED_FIELDS` に無い）、
    既定値 `""` で動く。今回の変更で「空でも動く」ことをテストでも確認した
    （`tests/test_token_set.py::test_6_coreはtokenのuser_idを台帳より優先する`）。
  - `thth auth` が成功後に出していた「`accounts/<account>.json` の `user_id` を
    手で直してください」の案内文は削除した（統括の検収 T2a 指摘の解消。手順が
    要らなくなった）。

## 4. テスト（`tests/test_token_set.py`・8 本）

1. 正常系: 貼り付け → `me` → `.token` 600 で作られる。
2. `access_token=` 接頭辞つきの貼り付け。
3. 前後に空白と引用符が付いた貼り付け。
4. `me` が 4xx → exit 1・`.token` を作らない・仕込んだ偽トークン文字列が出力に出ない。
5. 既存 `.token` があるとき `--force` 無しで拒否（中身は変わらない）・`--force` で上書き。
6. `core._default_adapter_factory` が `.token` の `user_id` を台帳より優先する
   （台帳側 `user_id: ""` でも動く）。
7. `bin/thth token set <account> --stdin` を subprocess・実プロセスの標準入力パイプ
   経由で呼び、仕込んだ秘密文字列が stdout/stderr のどこにも出ないことを確認。
8. （日付入り）事故防止テスト: 仕込んだトークン文字列が `log` 経由でも `print`
   経由（既定）でも標準出力に一切出ないこと。

いずれも本物の Threads API には触れない（`tests/helpers/fake_oauth_server.py` の
`me` エンドポイントだけを使う）。

`python3 -m pytest tests/ -q` で全 94 件（既存 86 ＋今回 8）が通ることを確認した。

## 5. 気づいた食い違い・注意点

- 発注書に列挙されたテスト観点のうち「正常系」「`access_token=` 接頭辞」「空白・
  引用符」「`me` 4xx」「既存 `.token` の保護」「秘密が出ないこと」「`core` の優先順位」
  の 7 点は上記 1・2・3・4・5・6・8 に対応させた。「`--stdin` でパイプ経由も動く」は
  発注書の手順 1 に書かれていた検証観点なので、7 として追加した（発注書のテスト
  列挙には無いが、`--stdin` を実装した以上、実プロセスでの動作確認が要ると判断した）。
- `me` の応答に `id` はあるが空文字列のケース（`{"id": "", "username": "x"}` 等）も
  失敗扱いにした。発注書には明記が無いが、`user_id` が空のまま `.token` を書くと
  台帳フォールバックも使えなくなる（両方空）ので、安全側に倒した。
- `thth token set` は台帳の `redirect_uri`・`scopes`・app.env（`THREADS_APP_ID`/
  `THREADS_APP_SECRET`）を一切読まない（OAuth 往復を経ないので不要）。`thth auth`
  用の `app.env` が無い環境でも `thth token set` は動く。
