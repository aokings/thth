## 4. 実装の要点

### 4.1 A: 利用者 repo の同期（`thth/writeback.py::sync_repo()`）

`thth/core.py::_throw_locked()` が、repo ロック・account ロックの中・inflight
確認の後・queue を読む前に呼ぶ。`git fetch origin` → `git pull --ff-only`
（merge commit を作らない）。

- 失敗したら投稿しない: `ThrowResult(exit_code=2, action="none",
  error="repo_sync_failed")` を返し、runs に理由を残す。
- repo を持たないアカウント（`repos/_none` 相当・存在しないディレクトリ）・
  git repo でない・`origin` remote が無い場合は「同期の必要が無い」として
  何もせず成功扱い（壊れないことを優先）。
- `thth send`（同席の様態）は queue を読まないので `sync_repo()` を呼ばない
  （`send_once()` からは呼んでいない）。

### 4.2 B: rebase 後・push 前のもう一度の照合（`writeback.commit_and_push()` の `validate`）

既存の照合（書き戻し前・`_section_matches()`）は**ローカルのファイル**に
対してだけ行われ、その**あと**に `commit_and_push()` の `pull --rebase` が
remote の変更を取り込む。rebase の後にもう一度同じ照合を行わなければ、
「本文 B ＋ 本文 A の post_id」が push されうる（`独立検証が実際に踏んだ
経路）。

- `commit_and_push(..., validate=<callable>)`: `pull --rebase --autostash` が
  成功するたびに、push の直前に必ず呼ぶ（再試行のループでも毎回）。
- 不一致なら `PushValidationFailed` を送出。push はしない（commit はローカルに
  残る。手で直せる状態）。
- `thth/core.py::_throw_chosen()` はこれを捕まえて、inflight を残したまま
  `exit_code=1`（`action="inflight"`・`error="text_mismatch_after_rebase"`）
  で止める。次回実行も inflight チェックで止まる。

### 4.3 C: board に要確認を出す（`thth/report.py::board_summary()`）

`select.select_one()` が元々返している `needs_review`（パス一覧）と
`rejections`（パスと理由の対）を突き合わせ、`needs_review`（ファイル名＋
理由の一覧）・`approval_stale_count` を各アカウントの行に追加した。
`thth board`（`--json` 無し）はこれを人が読む形で出す。`thth throw` を手で
打って「出すものが無い」で終わるときも、`ThrowResult.rejections` 経由で
理由を出す。

## 7. まだ穴が残ると思う箇所（正直に記録）

- **`sync_repo()` は「同期できたか」だけを見ており、同期の結果 queue の
  中身が「意味的に整合しているか」までは見ていない。** 例えば、fetch/pull
  自体は成功しても、pull の瞬間と select を読む瞬間の間（同じ関数内、
  ロックは保持したまま）に理論上さらに remote へ push されることは
  git の仕組み上あり得ない（ロックは THTH 側の実行を直列化するだけで、
  remote への push 自体を止める仕組みではないため）。ただし
  「sync_repo() の `pull` が返ってきた直後から select が読むまで」の
  間隔はミリ秒オーダーで、B で塞いだ「公開中（アダプタの `publish()` が
  ブロックする数秒〜）」の窓に比べれば著しく狭い。理論上のゼロではない。
- **`sync_repo()` の失敗判定は `returncode != 0` だけを見ている。** git の
  出力メッセージの中身までは解釈していない（`_run_git()` の stderr を
  そのまま `redact_mod.redact()` して返すだけ）。「fast-forward できない」
  以外の失敗（例: ネットワーク切断・認証エラー）も同じ `repo_sync_failed`
  として扱われ、投稿を止める。安全側だが、原因の切り分けは人が
  `sync_err`（runs・ログ）を読む必要がある。
- **B の `validate` は本文（media の節）のハッシュだけを見ている。** front
  matter の他のフィールド（`topic`・`reply_to` 等）が rebase の間に remote
  側で書き換わった場合はここでは検知しない（`_section_matches()` は本文の
  hash のみを比較する設計・`approval.compute_body_hash()` の元々の役割
  どおり）。ただしこれは既存の `text_mismatch_before_writeback` と同じ
  範囲であり、B はその同じ範囲をもう一度・正しいタイミングで見ているだけ
  なので、新しく広げた穴ではない。
- **C の `board_summary()` は `select_one()` をアカウントごとにもう一度
  実行する。** `thth queue` の `_next_via_select_one()` と合わせて、同じ
  計算を 2 箇所（`queue_summary()`・`board_summary()`）で行っている
  （既存の `queue_summary()` も同様の構造だった）。ファイル数が少ない
  現状の運用規模では性能上の問題にはならないはずだが、将来 queue の
  ファイル数が大きく増えた場合は select をもう一度走らせるコストが
  重なる可能性がある。
- **`thth run`（timer が呼ぶ経路）は `core.throw_once()` を経由するので
  A・B の修正はそのまま効く**が、`thth run` 自身が token の有無だけを
  チェックしてから `throw_once()` を呼ぶ構造（`cli.py::cmd_run()`）は
  今回変更していない。timer からの実運用での確認（VM 上での実際の
  fetch/pull の権限・SSH 鍵の有無など）は本セッションの範囲外（ローカルの
  bare origin でのみ検証した）。
