## B. kopicha 未回答 2: `coffee`(117) と `コーヒーのある暮らし`(79) で本文の先頭が同一

**うちの二重計上ではない。Threads の頁の作りがそうなっている。**

根拠 2 つ:

1. **1 投稿に付くトピックは 1 つだけ。**`thth/adapters/threads.py:65` が投稿時に
   渡すのは `topic_tag` **1 個**。同じ投稿が 2 語で**タグ付け**されることはない。
2. **トピック頁には、タグ付きと本文一致が両方並ぶ。**2026-09-11 の実地調査で
   確認済み（`docs/手順_LLM_トピック選定.md` の「トピックは頁への切符か」）。

**つまり**: その投稿のタグは片方（おそらく `coffee`）だけで、
**もう片方の頁には本文一致で出ている。** kopicha の「本文中のハッシュタグを
拾っていないか」という筋読みは**当たっている**——拾っているのは Threads の側。

**これは観測の数え方に直接効く。** 頁の件数をそのまま「その語を使っている人の数」
と読むと**過大になる。** だから `samples[].tagged` を必須にした（`9f109d7`）。
**kopicha の 117 / 79 も、ラベルの有無で数え直せば実数が出る。**

## C. 返信が台帳に載るまで 46〜56 分かかる件 — **API ではなく、うちの刻み**

`thth/collect.py:49`: `AGE_MARKS_HOURS = [1, 6, 24, 72, 168]`。
`due_marks()` は**跨いだ刻みだけ**返すので、**10 分ごとには取りに行っていない。**

- 08:00 投稿 → 1 時間の刻みは 09:00 → 次の `thth run` が 09:18 → 台帳に載る
  （kopicha が測った 46〜56 分はこれ）
- 09:10 の返信 → 1 時間の刻みは消化済み → **次は 6 時間の刻み（14:00）**。
  09:32 に出ないのは正常。

**Threads API は遅れていない。**

### C-1. `collected: 0` は常に 0（**誤診の原因**）

`thth/core.py:225` にべた書きの `0`。`_append_run()` に引数も無く、
**採取の結果が入ったことは一度もない。**

kopicha は「10 分ごとに取りに行って 5 回連続 0 件」を根拠に API を疑ったが、
**その欄は何を意味してもいない。**

**常に嘘をつく欄が、実運用で人を誤診させた。** 消すか埋めるか。
**私（前任）の意見は「消す」**——採取の結果は insights の ndjson にあるので、
実行記録に持つ必要がない。

### C-2. `thth replies <account> --refresh` は効く。しかも安全

**遅れがうちの側なので、その場で取れば解決する。**

設計を壊さない根拠: 返信は `id` で重複除去している（`thth/collect.py:301`）。
**刻みを書かずに取るぶんには冪等。** 経過時間で比べる規律は insights の話で、
**返信には元々かかっていない。**

**公開経路に触らないので、v2（連投）の凍結とは無関係に進められる。**

### C-3. 使い方文書 §3 が古い（kopicha 指摘・そのとおり）

> 返信と数の自動収集 | 未実装（T3・T4）。いまは `thth doctor` で覗けるだけ

`thth replies` がある。`返信の取得` の行に**件数の注記**（上限か総数か）も要る。
