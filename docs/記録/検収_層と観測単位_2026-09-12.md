`shares` と `clicks` を持つ予測を `state=proposed` で記録すると、`schema_error`、終了コード2、保存0件になります。エラーは `sample_design='U'` にして残すよう案内しますが、同じ予測を保持したままUへ変えても同じエラー・保存0件になります。主担当も独立テストと別のmodel呼び出しで確認しました。同じ入力は変更前の `77a09ae` ではM/Uとも受理され、今回追加された拒否であることを確認しました。

指標の取得単位が違うことから判るのは、そのまま同じ粒度の量として扱えないことです。集計・対応づけ・相関を検討する**未検証の案そのものを保存できない**とまでは言えません。投稿sharesは取得時点の累計なので、単純に日次へ合計すれば検証できるとも認定していません。そこを未検証として保持するのがproposedの役割です。

**最小修正:** 今回追加した「共通単位0」の条件をproposed登録の拒否条件から外し、警告として返してください。`U` でも予測本文を削らず保持できるようにします。shadow/acceptedの登録禁止は維持してください。今回、集計器や新しい観測設計schema、実測による仮説検証を足す必要はありません。

## 合格した点と、依頼の4つの判断への回答

1. **`missing_metrics` の削除は、この対象では受容します。** repoの製品コード内の消費者を検索し、CLIが新しいキーへ追従していることを確認しました。存在を確認していない外部利用者を理由に旧キーを復活させる必要はありません。ただし、外部利用者が一切いないと認定したわけではなく、意味が変わったAPIキーの変更として扱ってください。
2. **`None / [] / 非空` の区別は妥当です。** 日次台帳がないときはNone、読める台帳があって全期待指標が存在すれば[]、存在しない指標があればその名前の配列になります。人向け表示も区別できています。新しい型の導入は要求しません。
3. **proposedへの警告は妥当です。** `views + clicks` の登録は警告と帰属の但し書きを返し、警告は保存されません。観測可能と検証済みだという扱いにはならず、noticeも実測参照・窓・欠測規則が未確認と明示します。shadowは引き続き拒否されました。
4. **拒否と警告の線はU1のとおり修正が必要です。** 共通単位0もproposedでは警告に揃えてください。未知の指標名など既存の検査まで全面的に外す要求ではありません。

欠測の具体観測は次のとおりです。

| 条件 | 結果 |
| --- | --- |
| 日次ファイルなし | `missing_account_daily_metrics=null` |
| 日次の全期待指標が0を含めて存在 | `[]`。0を欠測にしない |
| 日次にviewsだけ存在 | 他の期待指標が非空配列になる |
| 前日にclicksなし、翌日にclicks=0 | 前日行の `missing=['clicks']` が維持される |
| 日次viewsは存在、投稿viewsは欠測 | 投稿側の欠測が隠れない |
| 日次を人向け・JSONで読む | 日次行とその日の欠測が両方に出る |

主担当も添付の欠測再現スクリプトを実行して上記を確認しました。層ごとの期待一覧はアダプタの要求指標と一致しています。全期間の「1度も現れていない指標」と各行の欠測は別の意味であり、前者が空でも後者には欠測が残ります。

`None` はあくまで「該当日次ファイルがない」という現在の契約です。壊れたファイルは別の `broken` も併読する必要があり、この3状態だけで読み取り障害すべてを表すものではありません。
