## 裁定と対応

### 1〜3 は**本番の前に必ず直す**（P1）

**現状は安全**（プロジェクトの 3 アカウントは `production: false`、timer はリハーサル、承認済みの投稿ファイルは 0 本）。**この 3 件が入るまで、どのプロジェクトも `production: true` にしない。**

#### 1. 承認を「見た本文」に結び付ける

設計の中心は「masaru が見たものだけ出る」なのに、契約がそれを保証していなかった。`status: approved` にした後で本文・`account`・`reply_to`・`topic`・`publish_at` を書き換えても、承認済みのまま出る。

**対応**: 承認の対象を hash で固定する。

- **`thth approve <file>` に実体を持たせる**（CLI のみ・MCP には出さない・§3.7 の線は不変）。`status: approved` を書くと同時に、**本文＋`account`＋`reply_to`＋`topic`＋`publish_at` を正規化した `sha256` を `approved_sha` として front-matter に書く**。
- select は `approved_sha` が現在の内容と一致するときだけ通す。**不一致は「承認が古い」として落とし、board に出す**（黙って出さない・黙って通さない）。
- これで masaru の手数は増えない。いままで手で `approved` と打っていたところが 1 コマンドになるだけで、**むしろ楽になる**。
- **`approved_sha` は front-matter に足す**（§8-2 の共有 schema の変更）。**まだどの repo にも配っていないので、いま入れるのが最も安い。**

#### 1b. 同席の送信（`thth send`）も同じ線で守る

レビューの「プレビューした内容との一致を検査する」を採る。実装は:

- dry-run が本文の**短い digest** を表示する。
- `--production` は `--confirm <digest>` を要求し、一致しなければ送らない。
- 人への確認は増えない（dry-run の出力をそのまま次のコマンドに渡すだけ）が、**「見せたものと送るものが同じ」が機械で担保される**。

#### 2. clone 単位のロックを足す

設計は「1 repo に clone は 1 つ、アカウントは複数ぶら下がってよい」としているのに、ロックはアカウント単位。別ファイルへの投稿でも**同じ index・作業ツリー・rebase 状態**を同時に触る。timer の起点をずらしても、手打ちや遅延で重なる。

**対応**: `repo_dir` を正規化した単位のロック（`state/_repos/<正規化名>.lock`）を足し、**取得順を固定**する（repo → account の順。逆順を作らない＝デッドロックを作らない）。受け入れに「**同じ clone の別アカウントを同時に走らせる**」を足す。

いま共有している repo は無いが、§8-16（FB ページへの同時投稿）で必ず生じる。**安いうちに入れる。**

#### 3. 送った本文を動かせない記録として残す

本文 A を公開している最中に利用者が remote で本文を B に変えると、front-matter の更新と自動マージが成立し、**repo に「本文 B ＋ A の post_id」が残る**。push も inflight の削除も通るので、誰も気づかない。証跡として不正確。

**対応**:

- 公開の直前に、**送った本文そのものを変更不能な記録として保存する**（`data/sns/sent/<post_id>.txt` と、runs に本文の hash）。
- 書き戻しの直前に、**ファイルの現在の本文が「送った本文」と一致するか検査する**。不一致なら front-matter を書き換えず、**再公開もせず**、`needs_repair` として止めて board に出す（人が直す）。
- 1 の `approved_sha` と同じ hash の計算を使い回す。

### 4〜5 は**収集・保守の実装の前に**確定する（P2）

#### 4. 日次の取り方と、クリックの解釈

**(a) 取り方**: 「その日の最初の実行で当日 0〜24 時を取り、1 日 1 行で再取得しない」では、そのあとに起きた反応が記録に入らない。**前日の閉じた期間を取る**形に変え、API の反映遅れに対する**再取得の方針**（例: 直近 3 日ぶんを毎日上書きする）を決める。

**(b) クリックの解釈は統括の誤り**。§8-13 に「1 日 1 投稿なら、その日の日次 `clicks` は実質その投稿のクリック数」と書いたが、**成り立たない。過去の投稿も当日クリックされる。** 自信をもって推論した結果が単純に間違っていた。

- UTM を付けない判断自体は維持してよい（本文に見える URL を汚さない）。
- ただし **`clicks` はアカウント全体の日次指標**として扱い、**投稿別の成果に読み替えない**。§8-13 を書き直す。
- 投稿別のクリックが本当に要るなら、そのときに UTM か短い印を入れる（THTH が機械的に付ける）。**「要らない」の理由が消えたので、必要性の議論をやり直す。**

#### 5. トークンの保守を投稿から切り離す

`refresh` はどこにも配線されていない。加えて inflight が残っていると `run` は refresh より前で止まる。個人アカウント（timer 無効）と長期停止中のアカウントは、このままだと 60 日で黙って死ぬ。

**対応**: **投稿の可否と独立した保守の経路**を作る。`thth maintain`（全登録アカウントを走査してトークンの更新と残日数の監視、board への反映）を 1 日 1 回の timer に置く。**個人アカウントで投稿の timer を有効にする必要はない**（レビューの指摘どおり）。

## 文書の整理（レビューの最後の指摘）

現行仕様と変更履歴が同じ文書に同居していて、読み手が「いまどちらなのか」を判断できない。実例:

- 「返信は持たない」と「返信も THTH が出す」
- 「削除できる」と「削除権限は降りてこない」
- 「毎時」と「10 分刻み」
- 「07〜22 時」と「終日稼働」

**対応**: 設計書を **`docs/仕様_THTH.md`（いまどうなっているか・現在形だけ）** と **`docs/決定の記録_THTH.md`（いつ何をなぜ変えたか）** に割る。使う側は前者だけ読めばよく、経緯を知りたい人だけ後者を読む。`docs/使い方_...md` は既に現在形なのでそのまま。

## healthchecks の設定が実装とずれている

設計 §4.6 に「`period 1h`・`grace 30m`」とあるが、**timer は 10 分刻みの終日稼働**になった。夜間停止に戻すなら、正常な夜間の沈黙で通知が飛ぶ。**現行の終日稼働に合わせて設定を書き直す**（[Healthchecks の仕様](https://healthchecks.io/docs/configuring_checks/)）。まだ check を作っていないので、作るときに正しい値を入れる。
