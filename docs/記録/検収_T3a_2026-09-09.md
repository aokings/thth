### 2-2. `max_per_run`（台帳・既定 1）

- 何本出たかは `log()`（`"<account>: この実行で N 本投げました（mode=...・上限 max_per_run=...）"`）と `runs-YYYY-MM.ndjson`（同じ `run_id` で `action: post, status: ok` の行を数える）の両方から分かる。`ThrowResult` 自体には本数フィールドは足していない（返り値は最後の結果でよい、という発注どおり）。

**実装中に踏んだ問題点（2 つ・自分で直した）**:
1. 最初の実装は「select 候補から除く集合（`excluded_paths`）」を `last_post_at`/`recent_texts` の計算にも使う `files` に適用してしまい、直前に投げたファイルが間隔判定の入力からも消えて `min_interval_hours` が効かなくなった（3 本の queue に対し `min_interval_hours: 6, max_per_run: 3` でも 3 本とも出てしまった）。`last_post_at`/`recent_texts` は常に**全ファイル**から計算し、`excluded_paths` は select に渡す**候補プールだけ**から外すように直した。
2. `posted_at`（front-matter に書き戻す実際の投稿時刻）は `thth/adapters/threads.py` の `jst.iso()`（本物の壁時計）で作られ、`throw_once()` に渡す `now`（テストの時刻注入・本番は関数の先頭で 1 回だけ確定する値）とは別の時刻源になる。ループ 2 周目以降で disk から読み直した `posted_at` を使うと、投稿にかかった時間の分だけ `now` より後になり、`min_interval_hours: 0`（＝制限しない）のつもりでも `now - posted_at < 0` が真になって毎回落ちた（本番でも `wait_seconds` 分のずれで同じことが起きる）。**この run の中で自分が投げた分は disk を読み直さず、`now` を基準に `last_post_at` を上書きする**（`run_last_post_at`）ことで直した。他アカウントや前回の run 由来の間隔判定（disk 読み）はそのまま。

### 2-3. `min_interval_hours` と `quiet_hours` を「制限しない」に設定できるようにする

- `thth/select.py::in_quiet_hours()`: `quiet_hours` が `None`（null）または空配列なら常に `False`（＝静かな時間帯を設けない）を返すようにした。
- `min_interval_hours: 0` は元々の実装（`timedelta(hours=0)` との比較）で既に「制限しない」として動いていた（`masaru-threads` の台帳は最初から `0` だった）。今回は select 側のバグではなく、上記 2-2 の「`now` と `posted_at` の時刻源のずれ」が `max_per_run` ループと組み合わさったときにだけ症状が出ることが分かった（単発の `min_interval_hours: 0` は元々問題なし）。
- `accounts.load_account()` の必須項目チェックはキーの**有無**だけを見る（値の型は見ない）ので、`quiet_hours: null`・`min_interval_hours: 0` を弾かない。`tests/test_no_limits.py::test_台帳のquiet_hours_nullとmin_interval_0を形式検査は弾かない` で固定した。

### 2-4. systemd の unit を台帳から生成する `thth systemd <account>`

- 台帳 4 本すべてに `tick_minutes: 10`・`max_per_run: 1` を追加（`production` の値はどれも変えていない: `nigamilab-threads`/`asmon-kanto-threads`/`kopicha-threads` は `false` のまま、`masaru-threads` は `true` のまま）。

## いちばん価値のある発見: **時刻によって落ちるテストが 5 件あった**

実装セッションが自分の変更と無関係に気づき、`git stash` で素の main に戻して確かめたうえで報告してきた。**静かな時間帯（22:00〜07:00）に走らせると必ず落ちる**テストが 5 件あった（`test_roundtrip.py` 1・`test_fake_api.py` 4）。実際の壁時計を使って投稿の経路を通していたため、夜に走らせると `quiet_hours` が全部を落としていた。

**これは「たまに落ちるテスト」より悪い。** 昼は必ず緑、夜は必ず赤。日中に開発していれば一度も見えず、**夜に誰かが走らせたときだけ壊れているように見える**。しかも原因が自分の変更に見えるので、無実の変更が疑われる。今日 masaru と私が作業していたのが日中だったので、今まで一度も出ていなかった。

対処（account 生成に `quiet_hours=None` を足して安定させた）は**妥当だが、根の対処ではない**。根は「テストが本物の時計を読んでいる」こと。`core.throw_once()` は `now` を注入できるので、**時刻に依存する経路のテストは `now` を渡す形に寄せる**べき。T3b 以降で直す。急がないが、忘れないようここに残す。

## 実装セッションが自分で見つけて直した 2 件（良い仕事）

いずれも設計の不整合ではなく実装バグで、報告に経緯まで書かれていた。`max_per_run` のループを入れたときに (1) 除外集合を `last_post_at` の計算にまで適用して間隔判定が効かなくなり、(2) `posted_at`（本物の壁時計）と `now`（run 内で固定）の時刻源がずれて `min_interval_hours: 0` でも 2 本目が落ちていた。**どちらも「複数本出す」を実際に試さなければ出てこない**種類のもので、テストを先に書いた効果が出ている。
