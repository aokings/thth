## A. 文書と実装が食い違っている（ここが一番効きました）

### A-1. `thth approve` に `--confirm` が要ることが文書に無い

使い方文書 §4 は次のように書いています。

> ```
> ssh wt '... thth approve /path/to/docs/sns/queue/2026-09-10-example.md'
> ```

これをそのまま信じて 28 本を for ループで回したところ、**28 本すべて NG** になりました。
実際の `thth approve --help` には `--confirm CONFIRM  一段目が表示した digest。これが無いと承認しない`
とあり、`send` と同じ 2 段構えです。

`--confirm` の説明は文書には `thth send` の節にしかありません。approve にも同じ仕組みが
入ったときに、§4 の更新が漏れたのだと思います。

**提案**: §4 のコマンド例を 2 段に直す。設計としての 2 段構えは良いと思います（本文を見せてから
確定させる、という一線が機械で担保される）。文書だけの問題です。

## B. 一括の操作が想定されていない

### B-1. 28 本の承認に 56 回の呼び出しが要る

1 ファイルにつき「digest を出す」「digest を渡す」の 2 回。28 本で 56 回です。
実際にはこう書いて回しました。

```bash
for f in .../queue/*.md; do
  d=$(thth approve "$f" 2>&1 | grep -o "^digest: [0-9a-f]*" | awk '{print $2}')
  thth approve "$f" --confirm "$d"
done
```

digest を機械が取って機械が返しているので、**2 段構えの意味（人が本文を読む）が形骸化します**。
一括でやりたい人は必ずこう書くはずなので、正面から用意したほうが安全だと思います。

**提案**: ディレクトリまたは複数ファイルを受け取り、**全部の本文をまとめて表示してから、
束ねた digest 1 つで確認する**モード。人は 1 回読んで 1 回確認する。いまの一本ずつより、
むしろ「読んだ」の担保が強くなります。

### B-2. 承認が 1 本 1 commit

28 本で 28 commit が並びました。監査の跡としては正しいのですが、他の作業の履歴に混ざります。
一括モードを作るなら、まとめ commit も選べると読みやすいです。

## C. 誰が承認したかが残らない

`--by` を省略すると `approved_by: wt`（VM の unix ユーザー名）が入ります。

```
approved_by: wt
```

今回の判断は masaru のものですが、記録は `wt` です。承認は「留守中に出してよい」を決める行為で、
THTH が設計上いちばん重く扱っている一線のはずなので、ここが既定で `wt` になるのは弱いと思います。

**提案**: `--by` を必須にする。あるいは台帳に既定の承認者を持たせ、省略時はそれを使う。
少なくとも unix ユーザー名がそのまま入るのは避けたいです。

## E. 書式

### E-1. 人が書かない欄を人が書く

`approved_sha`・`approved_at`・`post_id`・`posted_at` は THTH が書く欄ですが、
テンプレートには空で置く必要があります。省略可にできれば、書く側のテンプレは半分になります。

### E-2. `publish_at` を 1 本ずつ計算する

「1 日 3 本・08:00 / 12:30 / 20:00」を 28 本ぶん展開するのは、結局スクリプトを書きました。

**提案**: 台帳に配信の型（1 日 N 本・この時刻）を持たせ、`publish_at` を省略したら
キューに積まれた順に自動で割り当てる。連載のように流すプロジェクトには効きます。
いまの `min_interval_hours` は「間隔が publish_at に勝つ」ので、目的が少し違います。

### E-3. approve に渡すパスが VM 側の絶対パス

手元で書いて push し、承認は `/srv/thth/repos/<project>/docs/sns/queue/...` を指します。
パスが 2 つあるので、手元のパスを渡して失敗する事故が起きやすいです。

**提案**: `thth approve <account> <ファイル名>` で解決できると安全です。

## F. 期待値の調整（実装ではなく文書）

トピックは**付けられるが探せない**（権限が降りていない）と §3 にあります。これは正しいのですが、
「では付ける意味はどこにあるのか」が書かれていないため、28 本ぶんのトピック設計に
どれだけ手をかけるべきか判断できませんでした。

**提案**: 「付けたトピックは、投稿を見た人がたどる導線としては働く。探される側にはまだ回れない」
のように、効き目の範囲を 1 行。トピックを凝るか広く取るかの判断がその 1 行で決まります。

## 良かったところ

- **`unverified_content` の考え方**が良いです。commit していないものは出さない、ファイルは消さない。
  「撤回したはずのものが復元されて出る」という事故の筋を、正面から塞いでいます
- **`approval_stale`** も同じで、承認は「そのときの中身」に結び付く、という割り切りが明快です。
  承認後に文面を直せる安心感がここから来ています
- **`thth lint`** が承認前に単体で走るのが助かりました。28 本を一度に検査して通ることを
  確かめてから承認に進めました
- **「THTH は何を書くかを決めない」**と最初に宣言してあるのが良いです。文体や頻度を
  こちらの責任として引き受けられるので、迷いがありませんでした
