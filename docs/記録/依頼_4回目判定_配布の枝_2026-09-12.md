## 1. F3 への対応

**指摘のとおりでした。** `except OSError: pass` で握り潰しており、**前回の
`ok: true` がそのまま有効に残っていました。**

- **書けないなら、せめて古いものを消す**（`os.remove`）。**古い成功を有効なまま
  残すのがいちばん悪い**ためです。
- **取りに行く前に「まだ結果が無い」を書く。** 結果の書き込みが失敗しても、
  残るのは古い成功ではなくこれです。

**「記録が書けないから投稿を止める」はしていません。** 投稿は続きます。

### 塞げていない範囲（隠さずに書きます）

**無効化の書き込み自体が失敗した場合、古い成功が残ります。** これは
**別プロセスの board には伝わりません。**

頂いた「**この制約を隠すために記録の記録を増やす必要はありません**」に従い、
**そこは塞いでいません。** 代わりに、`_begin_check` が失敗したときは
`_pull_locked` の戻り値に

    **配布の確認の記録を書けませんでした**（`<置き場>`。**board には前回の確認が
    残ったままになります**）

を前置きします。**その実行の中でだけ**言えることなので、**その範囲でだけ**言います。

## 2. 変異が、こちらのテストの嘘を 1 つ暴きました（報告）

**`_begin_check` を外しても、頂いた反例は通ります。**

    変異 P: `began = _begin_check(app_dir, ref)` → `began = True`
    → 反例 6 本すべて通過

**あの反例を満たしているのは `os.remove` のほうで、`_begin_check` は何にも
守られていませんでした。** 反例は `os.replace` に障害を注入するので、
`_write_check` の中で `os.remove` に落ちて記録が消え、`behind` が `None` になる
——**`_begin_check` を通らなくても成立します。**

`_begin_check` が効くのは**別の場面**です: **取得のあと、結果を書く前に実行が
死んだとき**（VM の再起動・timer の kill・`timeout`）。そこを
`test_結果を書く前に死んでも古い成功を残さない` に起こし、**変異 P をやり直して
今度は落ちることを確かめました。**

**最初の変異 P では「1 failed」と出ていたので、危うく「効いている」と読むところ
でした。** 落ちていたのは別のテスト（`test_無効化もできなかったらその実行では
言う`）で、**F3 の本体を守るテストは 1 本も落ちていませんでした。**

## 5. 配布運用について

**「masaru が手で push しない」方針は維持されています。**

**「403 だけで『masaru の代わりに Git 操作する経路が技術的に無い』とは言えない」**
——そのとおりです。こちらが言えるのは
**「GitHub の ruleset による権限分離は、この repo の現状では使えない」**までで、
**「代理実行の自動化」と「開発者が迂回できない権限分離」を混ぜて書いていました。**

- **代理実行の自動化**は可能です（`thth release <sha>` を作れば、masaru は
  「配ってよい」と言うだけで済みます）。
- **開発者が迂回できない分離**は、ruleset が使えないので**いまは取れていません。**

**`release` コマンドの追加を、この検収の条件にしていない**ことも了解しました。
**案の採用は masaru の判断待ちです。** GitHub の plan・権限をそちらが独立検証して
いないことも承知しています（こちらの 403 は `GET /repos/aokings/thth/rulesets` の
応答で、**plan そのものを読んだものではありません**）。
