# 案: THTH 4.0 の目玉（2026-10-15）

書いた人: THTH開発の委任（Fable 5.1・読むだけ・コードは変えていない）。依頼: 「フォロワーが 0 で、何を出しても反応が皆無な問題を破る」（masaru 10/13）に効く、4.0 の「グッとくる」機能を 5〜7 個。前提にしたのは masaru 10/15 の方針と決定:

- 「Meta の目を必要以上に恐れず、取れるものはとる、やれることはやれるように」
- **ダッシュボードと媒体をまたいだ連携は hub に譲る。THTH はヘッドレスの道具で、hub（と h2d）が読む材料と口を出す側に徹する**（10/9 の構想「ヘッドレス群とそのヘッド」と同じ線）

- 具体例「コーヒーの値段が凄い上がったり下がったりしたら、Threads に報告したりできますよね？」「流すべきか否かの判定を Jev にさせてもよいですよね？」

組み合わせ: **0 が軸**。H と Jev→THTH は 0 の「記事の種の入口」、A は 0 の「記事単位の反応」の分母を正しくする土台、F は hub が記事ごとの成績を描く材料、C は記事の告知が届いたかの確かめ、B は記事への反応の会話、D は記事の出し方の試し、E は告知の文の柵。理由は §5。

正直に言うと、**出発点（反応ゼロを破る）に直接効く「SNS の道具」としての機能は、もうほとんど THTH にある**。足りないのは (1) 人が手でやっていること（手の投稿・手の返信・ログアウトで検索して確かめる）が THTH の目に入っていないこと、(2) 「いつ出すか」が人の予定（timer の時刻）にしか結びついていないこと、(3) **「何のために出すか」＝記事が THTH の単位に無く、投稿が記事と切れていること**。A と C が (1)、H と F が (2)、0 が (3) を埋める。

## 1. 線引き: THTH が持つもの／hub が持つもの／h2d が持つもの

masaru 10/15 の決定と、10/9 の地図（門＝monban・時＝h2d・声＝THTH・場＝hub）に沿う。

| 種類 | THTH（声・ヘッドレス） | hub（場・ヘッド） | h2d（時と出来事） | 今の状態（L1） |
|---|---|---|---|---|
| SNS との読み書きと、その記録 | 持つ（出す・採る・会話・反応・絡み・言及） | 持たない | 持たない | THTH にある |
| **SNS の公開と予約** | **持つ**（承認の指紋に `publish_at`・guard・inflight と一体） | 持たない | 持たない。予約の遅れ・止まりを見張って起こす側 | 地図 §3 の例外のとおり。h2d の `thth-kanto-overdue`・`-inflight` 感知が既にある |
| 口座 1 つ・project 1 つの数と状態 | 持つ（`observe`・`after`・`analytics-report`・`measured`・`account status`・`where-log`） | 読む | 読む（`command_json` の probe） | hub は `observe --counts-only` を毎朝、h2d は 15 分ごとに読む |
| **出来事を外に流す** | **出す**（F: `events`・`h2d fires record`） | 受けて「行くべき所」に積む | 受けて感知の起点にする | THTH→hub は `thth run` の脈（`pulse.py`）だけ。THTH→h2d は h2d が読みに来る形だけ |

| 世の中の出来事を見張る（値段・発表・更新） | 持たない（`map` の世間の層は SNS の中の語の数） | 持たない | **持つ**（感知・条件・judge） | h2d にある |

| 人の判断の受け口（承認・止める・鍵） | 自分の分だけ（二段の承認・/activity） | 将来のヘッド（構想 §5） | `rules resolve` | 変えない。Meta への説明と一体 |
| 投稿の本文を決める | しない | しない | しない | 変えない（各レーンの LLM と人） |

| 外の AI（Jev）で判断する | しない | — | 持つ（`judge`・`config/judges.json`） | h2d にある。THTH のデータを渡す件は §2-H (1)・点検 §5 |

読み方: THTH は「口座ごと・媒体ごとに閉じた数と出来事」を版つきの JSON で出すところまで。足す・並べる・絵にする・人を動かす（hub）、世の中を見張る・起こす・判断を外に聞く（h2d）は相手。

## 2. THTH 4.0 の目玉の候補

書き方（依頼どおり）: (1) 売り文句 (2) 出発点にどう効くか (3) いまの THTH の何で作れるか (4) 媒体の原文で許されるか (5) 大きさと危険 (6) 他の道具との違い。

### 0. 記事を正本に、届け先ごとに出し分け、直したら巻き取る——コンテンツの流通部門（masaru 発案・筆頭）

(1) **「記事を 1 本書けば、ブログ・4 つの SNS・ブックマークへの出し方と、その後の反応まで THTH が持つ」**

masaru 10/15「各媒体の記事部門の更新反映なんかを THTH で巻き取るのが良いのかも。コンテンツマーケティングセクションとして機能する感じ。新世代のブログツールみたいな」。流れ:

```
正本 = 記事（レーンの repo の Markdown。music-research のエッセイ・nigamilab・asmon の数えた結果・kopicha の記事）
 → THTH が届け先ごとに出し分ける
     はてなブログ: 本文（AtomPub・予約・下書き・カテゴリ）
     Threads／X／Bluesky／Mastodon: 告知と連投（thth: 2・要点→根拠→リンク）
     はてなブックマーク: セルクマ（自分の記事を自分のアカウントで・1 記事 1 口座）
     （note は投稿 API が無いので外す）
 → 記事を直したら、出した先の更新を巻き取る（ブログは PUT・SNS は訂正の返信か追記の 1 本・ブックマークのコメントは更新）
 → 記事ごとに反応を束ねる（ブログの訪問・SNS の views/replies/clicks・ブックマークの数とコメント）→ 次の記事の種
 ← 外の出来事（h2d・Jev）は記事の種の入口（H）。見せる画面は hub（F）
```

**何が新しいか（既存の道具との違い・L3）**:

| 道具 | できること | 0 との違い |
|---|---|---|
| WordPress の自動共有（Jetpack Social）・はてなブログの「投稿と同時に X に流す」 | 記事を公開したら、題と URL を SNS に 1 本流す | 流すのは**題と URL の 1 本**で、告知の文は定型。訂正・追記は追わない。反応は SNS 側の画面で別々に見る。承認の二段は無い |
| Buffer・Hootsuite・Typefully | SNS への予約・連投・分析 | **記事という単位が無い**（投稿の束を人が手で記事に結ぶ）。ブログ本体には出さない。更新の追従は無い。本文は人か道具の AI が書き、承認の指紋は無い |
| 静的サイト生成（Astro 等）＋ CI | 記事を正本に、サイトを再生成 | サイトまでで、SNS・ブログ・ブックマークは外。反応は戻らない |
| Mixpost・Postiz（自前で置く投稿道具） | 複数 SNS への予約・簡単な分析 | Buffer と同じ。記事の単位・更新の追従・承認の指紋は無い |

0 の新しさは 4 つ: ①**記事が単位**（告知・連投・ブックマーク・ブログの本文が全部 1 つの記事 id に結ばれる）、②**正本は利用者の repo の Markdown**で、THTH は写しを持たず「どこに・どの版を出したか」だけを持つ（git の sha で追う・承認の指紋の流儀）、③**直したら巻き取る**（記事の sha が変われば、出した先ごとに「書き換える／訂正を足す／何もしない」を人が選んで二段で確定）、④**反応が記事に戻る**（`measured`・click の照合・ブックマークの数を記事ごとに束ね、`after --article` で読める）。LLM が CLI で最後まで回せる・人の承認の二段・分母つきの数、は THTH のまま。

(2) 出発点にどう効くか: フォロワー 0 の SNS の口座で、**いちばん届いていない層は「記事そのもの」**——SNS の告知は数件〜数十件の表示で終わる（L1 調査_X §0）が、記事は検索（SC）から人が来る（hub の数字・L1 media-hub CLAUDE.md §4）。記事と SNS を結ぶと、(a) 告知を「要点→根拠→リンク」の連投で出し、`goal: click` の照合（3.7.0 `unique_url_72h`）で**SNS からの流入を記事ごとに数えられる**、(b) はてなブックマーク（セルクマは公式に認められている・L1 調べ §3-2）とはてなブログは、**フォロワーに依らない新着の面**を持つ（新着エントリー・ブログのグループ・カテゴリ）——フォロワー 0 でも「見られる場所」が増える、(c) 記事を直したら告知も直る、で古い告知が嘘のまま残らない。masaru の「反応ゼロ」は SNS の数字の話だったが、0 は**記事の読者を分母にする**ことで、SNS の 0 を記事の訪問の中で見られるようにする。

(3) いまの THTH の何を使えるか（L1）:

| 要るもの | ある口 | 使い方 |
|---|---|---|
| 告知の原稿・連投 | queue の原稿（front-matter・`thth: 2` の束・`bundle.py`）・lint・preview | 記事 1 本から媒体ごとの告知の原稿を LLM が書き、束で出す。本文は THTH が作らない（SKILL の線） |
| 承認の二段・時刻 | `approve`（digest・`approved_sha`）・`publish_at`・guard・inflight | ブログの本文・SNS の告知・ブックマークのコメントも同じ二段。はてなも「見せた中身と違うものは通らない」 |
| リンクの照合 | `goal: click`・`analytics_clicks`（`unique_url_72h`）・`sent` の `has_link` | 記事 URL ごとの SNS からのクリック（Threads の `clicks_by_url`）。X は API に click が無い（L2） |
| 反応の採取 | `collect`（1h〜720h・返信・言及）・`measured`・`after`・`analytics-report --by goal/topic` | 記事 id の層を足せば記事単位で読める |
| 媒体の抽象 | `adapters/base.py`・`media_capabilities.py`（媒体ごとの「出せるもの」表） | はてなブログ・はてなブックマークを adapter として足す（`DELETE_PERMISSION` の流儀・`unsupported_on_platform`） |
| 口座の台帳・鍵 | `accounts/*.json`・`thth auth`・`token set --stdin`（Bluesky の App Password の流儀） | はてなは OAuth か WSSE（API キー）。API キーは Bluesky の App Password と同じ流儀で入る |
| 試し・学び | `study`・`plaza`・`goal`・`topic` | 「連投あり／無し」「ブックマークあり／無し」を記事単位で比べる |
| 外に出す数 | F の `events`・`summary`（schema つき） | hub が記事ごとの成績（SC・CF の訪問と並べて）を描く |

(4) **足りない口**:

- **記事という単位** `article_id`: 原稿の front-matter に `article: <記事の相対パス or URL>` と `article_sha`（repo の blob の sha）。`sent`・`measured`・`engagements` に写す。`thth article <project> <記事>` で「どこに・いつ・どの版を出したか」と反応の束を 1 枚に（口座をまたぐが**同じ記事の行を並べるだけ**で、合計・順位は作らない——自分の泉 §2.6 の線）。
- **届け先の対応表** `distribution`（project ごと・台帳の外の JSON か記事の front-matter）: 「この記事は はてなブログ本文＋Threads 連投＋Bluesky 1 本＋セルクマ、X は出さない」。THTH は表のとおり**原稿の雛形を置くまで**（本文は LLM が書く）。
- **更新の追従** `thth article diff <記事>`: 記事の sha が出したときと違えば、出した先ごとに「ブログ: PUT で書き換え／SNS: 訂正の返信を足す・何もしない／ブックマーク: コメントを更新」の候補を並べる（選ぶのは人・二段で確定）。SNS の投稿は書き換えない（API に編集が無い媒体が多い・X は有償）。
- **はてなブログの adapter**（AtomPub・POST/PUT/DELETE・下書き・予約・カテゴリ・画像はフォトライフ）と**はてなブックマークの adapter**（REST・追加/更新/削除・件数・コメント一覧）。詳細は `docs/調べ_はてなブログとはてなブックマーク_2026-10-15.md`（作成中・【読】【未】の印）に任せる。ここで引くのは 3 点だけ: セルクマは「自分の記事を自分のアカウントで・通常の範囲」なら公式に問題視されない（L1 調べ §3-2）／機械的な高頻度は対象になりうる（同 §3-1）→ guard をそのまま掛ける／レーンごとの複数アカウントは第 6 条 3 項 c に触れうるので**1 記事に対してブックマークするのは出したレーンの 1 口座だけ**（同 §3-2 の安全側の線）。
- **ブログの訪問を記事に戻す口**: THTH は持たない（SC・CF は hub）。THTH は `article_id` と URL を F の `events` に出し、hub が結ぶ。
- **note**: 投稿 API が無いので外す（masaru の整理）。将来は「note に手で貼る本文を `thth article render --for note` で出す」まで。

(5) **4.0 で何まで（段階）**:

| 段 | 中身 | 大きさ | 4.0 に入れるか |
|---|---|---|---|
| 0-1 | `article` の欄と記事単位の束ね（`thth article`・`after --article`・`events` に `article_id`） | 中 | **入れる**（既存の媒体だけで効く・はてなが無くても価値がある） |
| 0-2 | 届け先の対応表と、記事から告知の原稿の雛形を置く口（本文は LLM） | 小〜中 | **入れる** |
| 0-3 | はてなブックマークの adapter（セルクマ・件数・コメント）と、ブックマークの数の採取 | 中 | **入れる**（API が小さい・規約の線が読めている） |
| 0-4 | はてなブログの adapter（本文の公開・予約・PUT） | 中〜大 | 4.0 の後半か 4.1（画像のフォトライフ・OAuth の【未】がある） |
| 0-5 | 更新の追従（`article diff`・出した先ごとの候補・二段） | 中 | 4.1（0-1〜0-4 が出てから） |
| 0-6 | 記事の種の入口（H・Jev→THTH の `draft put` を記事の素案にも） | 小（H の上） | H と同時 |

危険: ①THTH が「ブログツール」に見えて、芯（SNS の道具・何を書くかを決めない）がぼやける——正本は利用者の repo・THTH は出し分けと記録だけ、を README の最初に書く。②はてなの複数アカウントの規約（調べ §3-2・【未】）——1 記事 1 口座の柵を道具で持つ。③記事の sha を追うので、repo の無い口座（招待・遠くの道）では 0-1 の `article` は URL だけになる（sha は無い）。④はてなブログの画像（フォトライフ）は差し替え不可・OAuth が通るか【未】。

(6) masaru が「グッとくる」か（正直に）: **ここは刺さると思う**。理由は、masaru の 6 つのメディア（kopicha・nigamilab・関東・染めと化学・キョンシーラボ・music-research）がどれも「記事を書いて、SNS で告知して、SC と CF で見る」を別々の道具と手でやっていて（L1 media-hub CLAUDE.md §3・§4）、「反応ゼロ」の悩みの実体が「記事が読まれない」だから。THTH が記事を単位に持てば、hub の朝の報告の SNS の行と SC の行が初めて同じ記事で結べる。危ういのは「新世代のブログツール」の言葉で、THTH が本文を持つ・画面を持つ方向に膨らむこと——**THTH は流通と記録、画面は hub、本文は repo** と最初に線を引けば、芯は守れる。もう 1 つ、はてなの口座をレーンごとに持つかの判断（規約・調べ §3-2 の 3）は masaru の決めで、ここが決まらないと 0-3・0-4 は進まない。

### H. 出来事から投稿を起こす——「値段が動いたら Threads に」（masaru 発案）

(1) **「世の中が動いた瞬間に、その口座だけが言える一言を出す」**

(2) フォロワー 0 の口座の根投稿は、他人のタイムラインにほぼ出ない（L2 調査_X §2.2）。例外は、**その瞬間にその話題を探している人がいる**とき——値段が急に動いた日に「コーヒー豆 値上がり」を検索する人、合格発表の日に学校名を検索する人。THTH は検索の層（`where`・`map`・`trends`・`counts`）で「人がいるか」を見てはいるが、**出すタイミングは timer の時刻（人の予定）にしか結びついていない**。出来事に結びつけると、「言えることがある瞬間」と「探している人がいる瞬間」が重なる。X の公開コードの重みで最も大きい「人に送りたくなる」（リンクのコピー 20.0・DM 5.0・L2）も、「今日値上がりした」という鮮度のある数字に出やすい。発見の種類（SKILL）の「変化」と「例外」はまさにこの型。

(3) 流れ（3 つの道具の役割を分ける）:

```
[h2d] 感知: 値段を見張る            → [h2d] 条件: 閾値・cooldown・（judge: Jev に「流す価値があるか」）
→ [h2d] 動作: レーンの LLM を起こす（wake・材料は出来事の JSON）
→ [レーン] LLM が THTH の SKILL で下書き（発見の種類「変化」・数字は材料からだけ）
→ [THTH] lint → 承認の一段目（本文と digest）→ 人の「出して」→ 二段目 → 出る
→ [THTH] collect が測る → after/study で「出来事起点の投稿」の層として読める
```

値段の出どころ（論点 (2)）: **一番確かなのは kopicha 自身の観測所**。`kopicha/collectors/` が国内ロースター・生豆卸・茶葉 EC の公開の価格・内容量を毎日機械収集し、`data/history/prices-2026-08〜10.ndjson` に履歴がある（L1・kopicha README「事実データ（銘柄・価格・内容量等）のみ収集」）。h2d の `command_json`（登録済みの読むだけのコマンド）か、kopicha が公開 JSON を 1 本出せば `http_json` の `threshold`／`changed` で見張れる。「同じ豆の店頭価格の中央値が 7 日で ±10%」「ある店が値上げ」は、**他人のデータの転載でなく自分の観測**なので、投稿の中身としても強い（調査_X §4.2「同じ豆が店で 1.4 倍違う」の線）。アラビカ先物（ICE）の値は、無料で規約上使える API があるかを今日確かめきれなかった（**未確認・L3**。報道の数字を引くなら出典を書く形になる）。先物より店頭の観測の方が kopicha の強みに合う。

他のレーン（論点 (3)）: asmon-kanto＝入試日程・倍率・出願数の発表（h2d の kanto 巡回が 389 URL を毎朝取っていて、`page`／`rss` 感知の `appears` で「倍率」の語が出た行を拾える・L1 h2d README）。music-research＝新譜・命日・配信開始（`rss`・時刻）。headlesson＝道具の新しい版（`github` 感知の `release`）。nigamilab＝苦味の論文・製品（`rss`）。**同じ型が効く**: 「出来事 → 材料つきで起こす → 下書き → 人が出す」はレーンに依らず、変わるのは感知と材料の形だけ。

THTH 側に要る口（論点 (4)）:
- **原稿の front-matter に `origin:`**（例 `origin: h2d:rule:kopicha-price-jump`・`origin_event: <出来事の id>`）。承認の指紋には入れない（`goal` と同じ扱い: 測り方の札）。`after`・`analytics-report`・`study` に `--origin` の層。これで「出来事起点の投稿は時刻起点より views が高いか」を数で言える。
- **遠くの道・MCP の下書きの置き場**（招待の口座・repo の無い口座）: `thth_draft_list` はあるが、置く口は `send --dry-run` の下書き 1 本だけ（L1 SKILL）。出来事から複数の下書きが来るので、`thth draft put <account> --text-file … --origin …` と一覧・捨てる口。
- **出来事の口（F）**: THTH 自身の出来事（反応の急増・新しい返信）も h2d の起点になる（§4.3）。
- **Jev → THTH の受け口**（`draft put`・`words put`・`study propose`・§4.3 の表）: 外のデータと Jev の判定・下書き・語の候補・比べる案を、承認の二段の手前に置く。Platform Data ではないので遠慮なく入れる（masaru 10/15）。
- **前承認の型**（下）: 作るなら THTH の口。

(4) 媒体の原文:
- 自分の口座に自分の文を出すこと自体は問題ない。**自動で出す**ことについて: X の Automation rules は「自分の投稿を自分で出す（情報・娯楽・新奇の目的なら自動でも可）」（L1 調査_X §1 I・II.D）。Threads の Developer Policies 1.7「利用者に代わって公開するなら事前の同意」（L2 調査_Threads §4）——利用者＝持ち主の同意があればよい。**縛るのは媒体より THTH 自身**: 9/23 承認済みの前置き「THTH never posts, replies or deletes on its own」（A2・点検 §6）と privacy の文、そして THTH の芯「人の承認なしの公開をしない」。
- **Jev に渡すもの**: 値段の例で Jev に渡るのは「外の API（kopicha の観測）の値」と「こちらの下書き（自分の文）」。どちらも Threads の Platform Data ではないので Meta の縛りに当たらない（masaru の答えのとおり・L2 点検 §2 Platform Terms 12.l の Platform Data は Meta から取ったものと派生物）。10/9 の地図 §5「THTH のデータは Jev に渡さない」は、点検 §5 で「Threads から取った他人の投稿は条件つき（3.c.ii.3 利用者の明示の同意・5.a 書面の合意）」と読み直されている。**自分の文と外のデータは、条件以前に対象外**。X の III.A(k) は学習の禁止で、推論は別。

(5) **大きさ**: 下書きまで＝中（THTH 側は `origin` の欄と遠くの下書きの口・h2d 側は感知とレシピ・レーン側は SKILL の 1 節）。前承認の型まで＝大。
**危険と論点 (1)——人の承認なしの公開との関係**:

| 形 | 何が起きるか | 利点 | 危険 |
|---|---|---|---|
| **a. 下書きまで自動・出すのは人の「出して」** | 起こされたレーンの LLM が下書き → `approve` の一段目で本文と digest が見える → masaru が二段目 | 今の芯・Meta への説明・privacy をそのまま守る。masaru は「はい／直して／やめる」だけ | 夜に値段が動いても朝まで出ない（鮮度を少し失う）。承認が溜まる |
| **b. 「Jev のはい」で人の「出して」を省く** | judge の p が `act_at` 以上なら、下書きがそのまま本番へ | 鮮度を失わない・masaru の手が要らない | **THTH の芯を破る**（人の承認なしの公開）。9/23 の前置き（A2）と privacy の「never posts on its own」を差し替えないと Meta Platform Terms 4.c・7.a（説明どおりに処理・説明の正確さ）に当たる。Jev が本文の誤りを見ない（数字の取り違え・固有名詞）。X の「人間か確認」中に自動で出すと確認を長引かせる恐れ（L1 返事_kopicha） |
| **c. 前承認の型**（masaru の問い） | 人が**型**（文の枕と結び・差し込みは数値だけ）を一度承認し、出来事が来たら THTH が差し込んで出す | a と b の間。本文の自由な生成を通さないので、Jev・LLM の文の誤りが入らない | A2 の差し替えは b と同じく要る。型の文が固定なので「同じ文の繰り返し」（X I.A・Meta スパム規定）に当たりやすい |

**c を作るなら何を固定すれば安全か**（THTH の口として）:
- 型の本文は人が承認し、差し込みは**数値と日付だけ**（型・範囲・小数の桁を宣言。文字列は差し込めない）。承認の指紋は「型の本文＋差し込みの宣言＋口座＋goal」で、出るときの指紋は「型の指紋＋差し込んだ値」を `sent` に残す。
- **上限**: 型ごとに 1 日 1 本・7 日 N 本・`until`（終わりの日・h2d の `until` と同じ考え）。guard（最短間隔・1 日 8 本・連投で停止）はそのまま掛かる。
- **止める口**: `/activity` の「止める」と `thth account stop` で型も止まる。型の取り消し（`template revoke`）は人だけ（MCP からはできない・`guard.resume` と同じ線）。
- **判断の記録**: Jev の p・model・時刻を `sent` に残す（本文は h2d 側の履歴にある）。
- **出さない条件**: `publish_hold`（x_not_permitted）・inflight・夜間（quiet hours）はそのまま断る。lint（文字数・ベイトの点検 E）は型の差し込み後にも掛ける。
- **文の繰り返しを避ける**: 型は 1 つでなく 3〜5 の言い回しを承認し、THTH が直近 N 本と同じ型を避ける（それでも「ほぼ同じ文」は残る。a が最も安全）。

**推し**: まず **a**（下書きまで自動）で 1 か月回し、下書きがどれだけ「そのまま出せた」かを `origin` の層で数える。「ほぼ全部そのまま出せた」が数で出てから **c** を設計する（b は推さない——Jev は「流す価値」の判断に向くが、本文の正しさの保証にはならない）。a の間も Jev の judge は h2d の条件として使える（「はい」なら起こす・「いいえ」なら起こさない——起こすかどうかの判断であって、出すかどうかではない）。

(6) IFTTT・Zapier に「RSS → 投稿」の型はある（L3）が、本文はテンプレートの差し込みで、人の承認も分母つきの測りも無い。Buffer 等には出来事起点は無い（L3）。THTH の違いは、出来事の材料から**その口座の LLM が自分のデータで書く**こと、承認の二段、そして出来事起点の投稿を時刻起点と**同じ物差しで測って**どちらが届くかを言えること。

### A. 手で出したものも THTH が測る・採る（外で出した投稿・返信の取り込み）

(1) **「手で出した投稿も、THTH が同じ物差しで測る」**

(2) 10/14〜15 の現実は、X の「人間か確認」を masaru がアプリで手で使って解き、人の手の返信を 1 本ずつ出す、という形。ところが THTH の採取（`collect`）は **THTH が出した投稿（queue・`sent/`）しか母集団にしない**（L1 `thth/collect.py` `owned_post_ids()`「母集団は queue の front_matter.account == name・束の段・sent/」）。`thth posts` は「手で出した分も含めて全部出し、THTH 経由かどうかを付ける」（L1 `cli.py cmd_posts`）ので一覧は見えるが、数（views・replies）も返信も採られず、`after`・`analytics-report`・`study`・`ask` の分母に入らない。**今いちばん効くと見ている手（手の返信・手の投稿）が、THTH の学びから外れている**。`clicks_before_post` の注記「THTH を通していない投稿か Threads の外のクリックが混ざっている可能性」（SKILL・L1）も同じ穴の裏返し。H で出来事起点の投稿を測るにも、この母集団の広げ方が土台になる。

(3) 作れる材料: Threads `recent_posts`（自分の投稿・`is_reply`・`replied_to`・`root_post`・3.21.0 で欄を足した）・X の Owned Reads（3.16.0・自分の投稿の数は 1 本 0.001 USD）・Bluesky `getAuthorFeed`・Mastodon `accounts/:id/statuses`（どちらも無料・L3 記憶）。`collect` の母集団に「媒体から取った自分の投稿のうち `sent/` に無いもの」を `via: manual` の札つきで足し、`measured`・`replies`・`engagements`（返信なら `found_by: manual`・相手は `author_key` だけ）に同じ形で書く。`after`・`study`・`analytics-report` に `--via thth|manual|all` の層。手の返信の「相手の返事」は 3.14.6 の `/replies` 採取がそのまま使える。

(4) 自分の投稿と、自分の投稿への返信の読み取りは、どの媒体も許可された用途の中（L2 点検 §2: `threads_basic`・`threads_read_replies`「owned by the app user」。X は自分の投稿の読み・Bluesky・Mastodon は縛り無し）。**他人の本文を保存しない決まりは変えない**（手の返信も `engagements` の形で相手は仮名だけ）。

(5) **中**。危険: 母集団が変わるので `ask`・`after` の中央値が動く（層で分ければ済む）。X は Owned Reads の費用が本数分増える（1 本 0.001 USD）。

(6) Buffer・Hootsuite は口座の全投稿を取り込んで分析するのが既定（L3）。THTH が「自分で出したものだけ測る」のは THTH 固有の偏り。違いは、THTH は手の返信を**絡みの台帳（相手は仮名・本文は無し）**として持ち、`who`・`--exclude-engaged` に効くこと。

### C. 見られる場所に出ているかの確かめ（visibility audit）

(1) **「0 なのは、届いていないのか、見られていないのか」**

(2) 10/14 の X: 読めるのに書けない、手で投稿したら「人間か確認」の画面、**確認が取れるまで検索とトレンドに出にくい**（L1 返事_kopicha 追記 18:46）。調査_X §8.6 は状態を A（URL が開けない）・B（開けるが検索に出ない）・C（検索に出るが表示が少ない）に分け、「人がログアウトで見るのが確か」として道具にしなかった。だが **THTH は自分の投稿が検索の結果に出るかを API で機械的に確かめられる**。「反応ゼロ」の原因が B か C かを、人がブラウザを開かずに切り分けられる。X の「人間か確認」が解けたかも、投稿を出さずに分かる（今は「1 本出して確かめる」・L1 申し送り 残り 1）。

(3) 作れる材料: Threads `keyword_search`（`author_username` に自分・`search_mode=TAG`・3.21.0 で `since`/`until`）／X recent search `from:<自分>`（有償・1 件 0.005 USD・`x_daily_reads` の中）／Bluesky `searchPosts`（無料）／Mastodon `/api/v2/search`（無料・全文検索はサーバの設定次第・L3）。形は `thth visible <account> [<post_id>]` → 投稿ごとに `search_from_me: seen|not_seen`・`search_by_tag: …`・`direct_fetch: ok|gone` と調べた時刻。**判定はしない**（「not_seen が続いた」と事実だけ。制限と断定しない——調査 §8.6 の線）。h2d の `command_json` の probe にすれば「not_seen が 3 回続いた」（`streak`）で起こせる（§4.3）。

(4) 自分の投稿を検索して見せることは Allowed Usage の中（L2 `threads_keyword_search`・`threads_basic`）。X は自分の投稿の読み。`observe` や timer から毎朝 X を検索するのは「timer と朝の一枚は X を検索しない」（L1 緩めない推し）に当たるので、**X は人が打つときだけ**。Threads・Bluesky・Mastodon は無料で timer に載せてよい。

(5) **小〜中**。危険: 「出ていない＝制限」と読まれること（表示の文で防ぐ）。X の費用（1 回 10 本で 0.05 USD）。

(6) 外部の「シャドウバン判定」サービスはログイン情報を渡す・誤判定が多い（L3・調査 §8.6 も「使わない」）。Buffer 等には無い（L3）。THTH は自分の鍵で自分の投稿を検索するだけなので、渡すものが無い。

### B. 会話の受信箱——会話が単位・4 媒体・反応した人の顔

(1) **「返していない会話が、4 媒体でひとつも漏れない」**

(2) Meta 公式は「返信は Threads の閲覧のほぼ半分」「会話を起こす投稿がおすすめに載りやすい」（L2 調査_Threads §2）。フォロワー 0 で最初に来る反応は、返信・言及・いいね・再投稿・フォローの数件で、**その数件に人が返すかどうか**が最初の会話になる。構想 §3.1「会話が単位になる」はこれ。10/7〜8 の不具合（刻みのすき間・絡みに行った先の返事の取りこぼし・外で出した投稿が見えない）も「会話を追い切れていない」ことから来ていた（L1 構想 §3）。

(3) いまあるもの: `unanswered`・`mentions`（3 媒体の言及を inbox に保存・3.22.0）・`replies`・`engagements`（絡みに行った先の返事・3.14.6）・`thread`・`who`。無いもの: ①これらを**会話（根→枝）ごとに束ねて、媒体をまたいで「返していない」順に並べる 1 つの口**（`thth inbox <project>`。合計や順位は作らず、会話ごとの行を時刻順に並べるだけで芯と両立）、②**反応した人**——Bluesky の `listNotifications` には like・repost・follow の actor が入り（L1 `adapters/bluesky.py:1044` は言及だけ読んでいる）、Mastodon の `/notifications` も favourite・reblog・follow を返す（L1 `adapters/mastodon.py:968` は言及だけ）。これを `author_key`（仮名）と種類だけで並べる。「最初の 100 人」の最初の顔が見える。Threads には like の一覧も通知の口も無い（L2 点検 A-1）。X の liking_users・followers は有償（User 読み 0.010 USD/件・L2）。「新しい返信が来た」は F の出来事として h2d に流れ、h2d が持ち主の LLM を起こして下書きを作らせる（§4.3・公開は人・自動返信はしない）。

(4) Bluesky・Mastodon の通知の読み取りに縛りは無い（L2 点検 §2）。Threads の返信・言及は許可済み。反応は **仮名と種類と時刻だけ**を保存すれば他人の情報を増やさない。X の Agreement IV.B は返信の台帳に既にかかっている話で新しい負担は無い。

(5) **中〜大**（束ねる口は中・反応の採取は小・X の有償の部分は別の段）。危険: `unanswered` と `mentions` の**言い換え**になる恐れ。言い換えでない部分は「会話ごとに束ねる」「反応した人」「4 媒体を 1 つの口で」の 3 つだけなので、**この 3 つが無ければ作らない**と決めておく。

(6) Hootsuite・Sprout の「統合受信箱」が同種（L3）。違いは、返信を機械が返さない・順位を付けない・他人の名前を保存しないこと、そして**絡みに行った先の返事**を同じ受信箱に入れること。

### D. 試しを道具が回す——宣言・出し分け・判定の日

(1) **「14 日の試しを、言い出しっぺの気力に頼らない」**

(2) 反応ゼロを破る方法は、調査 2 本とも「14 日で 1 つずつ変えて測る」。今の道具は `study add`・`study-report`・`plaza` で**測る**ことはできるが、**「いつ・どちらで出すか」の出し分けと「いつ判断するか」を人が覚えている**必要がある（L1 申し送り 残り 2「15 日目（10/27〜28）に §9.2」）。構想 §3.2「試すことが道具に入る」。H が入ると「出来事起点 vs 時刻起点」という新しい比較も生まれ、D の出番が増える。

(3) 作れる材料: `study`（施策 JSON・`changed_post_ids`・`baseline_post_ids`）・`goals`・`topic`・`origin`（H）・`analytics-report --by`・`observe` の「次の一手」（`confirm_due` のような期日の知らせの口が既にある）。足すのは、施策 JSON に `plan`（期間・交互に出す層・判断の日・物差し・min_n）、`approve` の一段目が「この原稿はどちらの群か」を言い `study add` を自動にする（原稿の欄は足さない——決定 4）、判断の日に `observe` が「判定の日。差は中央値で ×1.3（n=7/7）」と事実だけ出す、結果を `plaza` に置く口。判断の日の知らせは h2d の `promise`／時刻の起点でもよい（§4.3）。証拠の段（L1〜L5）を出力に付ける。

(4) 媒体に関わらない（自分の台帳だけ）。

(5) **中**。危険: 「出し分け」が道具の判断に見えること——道具は群の札を付けるだけで、本文も時刻も決めない。

(6) Buffer・Typefully に A/B の口は無い（L3）。THTH は分母・欠測・期間を道具が付けるのが違い。

### E. 出す前の「おすすめに載らない形」の点検（lint）

(1) **「ベイト・同じ書き出し・転載を、出す前に止める」**

(2) Meta の創作者向けの説明「クリックベイト・エンゲージメントベイト・景品・転載はおすすめに載らない」（L2 調査_Threads §2）、X の Automation rules「substantially similar」（L1 調査_X §1）。SKILL には書き方の決まりがあるが、lint は「直近 N 本と同じ書き出し」も「問いで終える頻度」も「@ の数」も見ていない（L1 `thth/lint.py`）。H の前承認の型（c）を作るなら、この点検が「同じ文の繰り返し」の柵になる。

(3) `lint`（`warning:` の口）・`sent/`（直近の自分の本文）。足すのは `similar_opening`・`too_many_mentions`・`ends_with_question_streak`・`same_url_streak`。**警告**にして断らない（文体の決めは台帳で）。

(4) 自分の本文だけ。

(5) **小**。危険: 書く側の自由を狭める——警告に留め、台帳で off にできるように。

(6) 媒体の「おすすめの線」に合わせた検査は見当たらない（L3）。

### F. 出来事の口と契約つきの JSON（4.0 の柱・hub と h2d の両方に効く）

(1) **「THTH の出来事と数を、版つきの 1 つの形で外へ」**

(2) 直接には効かない。だが hub がダッシュボードと「行くべき所」を持ち、h2d が出来事を起点に動く前提では、**THTH の出力が両方の目**になる。今は hub も h2d も `observe --json` を読んでいるが、h2d の感知は `sections[4].value.by_account…` と**並びの位置**で引いていて（L1 `h2d/config/sensors/thth-kanto-*.json` の note「位置に頼るので、THTH の出力の並びが変わると読めない」）、hub は節の名前で引く（L1 `hub/snsobs.py`）。schema の版は無い。地図 §4・構想 §6 の「先に約束事」。

(3) THTH 側に足すもの:
- **契約**: `observe --json` に `schema`（h2d の `h2d.status/1` と同じ流儀で `thth.observe/1`）と、節の名前の約束（`tool`・`unanswered`・`yesterday`・`world`・`today`・`next_steps`）。並びに頼らない読み方を文書と試験で縛る。他の `--json` の口（`summary`・`events`・`visible`・`after`）にも `schema` を付ける。
- **出来事の流れ** `thth events <project|account> --since <時刻> --json`（`thth.events/1`）: `sent`・runs・`publish_hold`・inflight・budget・`admin_log`・反応の採取・新しい返信と言及を**1 本の時刻順の流れ**に（本文は無し・id と種類と時刻と数）。種類は固定の語（`published`・`reply_received`・`mention_received`・`reaction_spike`・`publish_held`・`budget_exhausted`・`inflight_open`・`confirm_due`・`collection_stale`）。
- **押す口**: `collect`・`run` の終わりに、新しい出来事を `h2d fires record` で積む（`pulse.py` と同じ流儀: 実体が無ければ黙って何もしない・本文を含めない・失敗しても run の終了コードに影響しない）。hub には `hub status post --state blocked …` の形で「道具からの注意」（§4.2）。
- **数の要約** `thth summary <account> --since 7d --json`: views・replies・followers の日次の列（取れていない日は null）と、`unanswered`・`held`・`inflight`・`budget` の今。合計も順位も作らない。

(4) 自分の台帳だけ。X の有償読み取りは呼ばない。

(5) **中**。危険: 相手の都合で THTH の出力が増えて重くなる——`--counts-only` の線（本文無し・他人の情報無し）を守る。出来事を 2 経路（読みに来る・押す）で出すと二重に数えられる——`event_id` を付け、相手側が重複を除く。

(6) 他の道具の「API・webhook」に当たる。違いは、合計や絵や判断を THTH が作らないこと。

### G. 互換を崩す整理（4.0 でしかできない・目玉ではない）

3.18.0 のリリースノートに「4.0 で外す候補」として残っているもの（L1）: JSON の古い欄の名前（`id`・`message_id` → `post_id`）。構想 §3 の候補: 台帳の様態の分け方（「同席専用」と「予約あり」）・X の有償読み取りを媒体の例外でなく芯に（`x_daily_reads`・予算の口を全媒体の `reads` に）。古い docstring（`retract_cli.py:23`・`mcp/server.py:7-8`・点検 §9）。**小さいが、4.0 でないと後で面倒**。F の `schema` 付けと同時にやると 1 回で済む。

## 3. 候補にしなかったもの

- **既にある**: 検索に自分の履歴を重ねる（`where`）・枝の読み（`thread`）・相手の来歴（`who`）・出す前の問い（`ask`）・出したあと（`after`）・目的別の物差し（`goal`）・語の当たり率（`where-log`）・世間の層（`map`）・施策の広場（`plaza`）・返していない返信（`unanswered`）・言及の受信箱（3.22.0）・Threads の引用（`media_capabilities` の threads `quote: supported`・L1）・X の note_tweet・全文表示・遠くの道の `thread`/`where`/`who`（3.21.0）。
- **芯に反する**: 自動返信・人の承認なしの公開（H の b・c は論点として書いた）・大量の follow や like・「返信を求めている度」での順位付け（10/15 masaru「読む側の仕事」）・おすすめフィード（memory「保留」）。
- **THTH の外**: 「何を言うか」の素材と根拠の台帳（構想 §5.7・各 project のもの。kopicha の観測所はその実例）・ヘッド（構想 §5・持ち主は未決）・世の中の感知（h2d）。
- **hub・h2d へ**: §4。

## 4. hub・h2d に譲るもの——THTH 側の口と相手側の頼み

### 4.1 ダッシュボード生成（masaru 発案・hub へ）

**既にあるものとの違い（正直に）**: `board`＝運用の状態（版・配布・timer・held）、`observe`/`morning`＝前回の観測から今まで（1 枚・本文は題だけ）、`analytics-report`＝数の層（期間比較・goal・topic・時刻帯）、`where-log`＝語の当たり率、`/activity`＝招待の口座の行動の一覧と止める口、`map show`＝話題の点ごとの層。**数そのものは全部どこかにある。ダッシュボードで新しく生まれるのは「推移」（日ごとの views・replies・followers の列を投稿の日と重ねて見る）と「1 枚で見渡す」ことだけ**。推移の材料も `measured`（投稿ごとの刻み）と口座日次（Threads の `followers_count`・`clicks`）にある（L1 `measured.py:90`）。Bluesky・Mastodon・X の口座日次（followers）が採られているかは今日確かめきれなかった（L3。無ければ A か F の中で足す）。

**形の比較**:

| 形 | 向き・不向き | THTH の線との関係 |
|---|---|---|
| thth.me に置く（Worker が描く） | 招待の外の人も見られる。Worker の 48 KB・no-store の作法と、本文を Worker に上げない線がある。描く側（HTML・JS）を THTH が持つ | 「Web は見る」の中には収まるが、**媒体をまたいだ絵を THTH が持つ**ので 10/15 の決定に反する |
| 手元で開く静的 HTML（`thth dashboard --html`） | 速い・秘密が出ない。描く側を THTH が持つ | 口座 1 つ分なら THTH の線の中だが、project 横断は hub |
| **JSON を出すだけ（F の `events`・`summary`）** | 描くのは hub（朝の報告・hub の画面）か、利用者の LLM が作る Artifact。THTH は数と出来事を出すだけ | **10/15 の決定に合う。推し** |

**THTH 側の口**: F の `summary`（日次の列）と `events`（時刻順の流れ）、`observe` の schema の版。
**hub 側に頼むこと**: project ごと・口座ごとの 1 枚（投稿・推移・何が効いたか・世間の層・返していない返信）を hub が描く。世間の層は THTH の決まり（`--no-world`・溜めない）のまま、hub は THTH が `map` に残した数（5 未満は欠測）だけを使う。外の人（キョンシーラボ等）の口座の絵は hub の画面に出ない（hub は masaru の場）——外の人には利用者の LLM が `summary --json` から Artifact を作る、を SKILL に書く。

### 4.2 hub との連携強化（masaru 発案）

10/9 の地図 §4 の順（約束事 → 1 往復 → 門 → 記録と guard）に反しない形で。

| 例 | THTH 側の口 | hub 側の頼み | 地図との整合 |
|---|---|---|---|
| 返していない返信・止まった口座・予算切れ・inflight を「masaru が行くべき所」に積む | `summary`/`observe` の `attention` 節（F）。`thth run`・`collect` の終わりに `pulse` と同じ分岐で `hub status post --state blocked --project <p> --doing "x_not_permitted で止めています"`（L1 `hub/hub.py:8` の口） | `hub status` に「道具からの blocked」を受ける種（人のセッションと区別する印） | 地図 §4 の 2（THTH→hub の 1 往復）。報告の口→hub の伝言と同じ筋 |
| 各レーンの反応の数字を hub の朝の報告に | `summary --json`（口座ごと・日次の列）。`snsobs.py` を `summary` に差し替えるか両方読む | 朝の報告の SNS の段を「前日の数」から「7 日の推移」に | 合計は hub が作る |
| hub からレーンの LLM に「この返信に答えるとよい」を回す | B の受信箱の `--json`（会話 id・媒体・時刻・返していない時間。**本文は入れない**——本文は各レーンが `thth thread` で読む） | `hub msg` でレーンの窓口に会話 id を渡す。**答えるかはレーンの人と LLM** | 自動返信にならない線を hub 側にも書く。即時性が要るなら h2d の起こし（§4.3）の方が向く |
| 報告の口（`thth report file`）が開発に届く | `report` が置かれたら `pulse` と同じ口で hub に 1 行（地図 §4 の 2 の tracer） | 伝言を THTH 開発の窓口に配る | 地図で推薦済み |

hub 側は別の repo（media-hub・実装レーンだけが VM に反映・L1 media-hub CLAUDE.md §2）。THTH 側の口を先に出し、hub 側の頼みは `hub msg` で要点とパスだけ渡す（SKILL agent-mail）。

### 4.3 h2d との連携強化（masaru 発案）

前提（L1 地図 §3・h2d README）: 時刻の実行と世の中の感知は h2d、SNS の公開と予約は THTH、h2d は THTH の予約の遅れ・止まりを見張って起こす側。**2 つの筋**、どちらも F の契約つき JSON が前提。

| 筋 | THTH 側の口 | h2d 側の頼み | 今の状態・注意 |
|---|---|---|---|
| **1. THTH の読むだけの命令を `command_json` の probe にする**（h2d が読みに来る） | `observe`・`summary`・`events --since`・`visible`・`after` の `--json` に `schema` と名前つきの節（F）。probe に向く引数の形（`--counts-only`・`--no-world`・`--no-mark`）を文書に | `config/probes.json` の probe を名前の道（`sections[name=today]…` か `summary` の平らな鍵）に直す。`thth-kanto-*` の 3 感知を書き直す。`visible` の `not_seen` の `streak: 3` で起こす感知、`events` の `reaction_spike` で起こす感知 | h2d の probe は `thth-observe-asmon-kanto-threads` が既にある（L1）。並びの位置で読んでいるので、F を出すと同時に h2d 側を直さないと `sensor_error` になる——**THTH 側で古い並びを 1 版だけ残す**（4.0 で切る） |
| **2. THTH が出来事を `h2d fires record` で積む**（THTH が押す） | `collect`・`run` の終わりに新しい出来事（`reply_received`・`mention_received`・`reaction_spike`・`publish_held`・`budget_exhausted`・`inflight_open`・`confirm_due`）を `h2d fires record` で 1 件ずつ（`pulse.py` と同じ: 実体が無ければ黙る・本文を含めない・run の終了コードに影響しない・`event_id` で重複を除ける） | `fires record` が THTH の種類の語を受ける（project は `thth:<account>`）。レシピ例: `when.fire {project: "thth:kopicha-threads", kinds: ["reply_received"], if: {hours: "07:00-22:00", cooldown: "1h"}}` → `wake` でレーンの LLM を起こす（伝言に会話 id・媒体・時刻。本文は THTH の `thread` で読む）→ LLM が下書き → **出すのは人**（`approve` の二段）。自動返信はしない | 筋 1 より速い（15 分の probe を待たない）。同じ出来事を両方で数えないよう、感知は「状態」（inflight・overdue）、`fires record` は「起きたこと」（返信が来た）に分ける |
| **3. 世の中の出来事 → 投稿（H）** | `origin:` の欄・遠くの下書きの口・（4.1 以降）前承認の型 | 感知（kopicha の価格は `command_json` か `http_json` の `threshold`／`changed`、kanto は `page`／`rss` の `appears`）→ 条件（`cooldown`・`hours`・`judge`: Jev に「流す価値があるか」）→ `wake`（材料の JSON を伝言に） | H の (5)。Jev に渡るのは外のデータと自分の文（Platform Data でない） |
| 4. 判断の日・期限 | D の `plan` の判断の日を `observe` の次の一手に | `promise`／時刻の起点で「判定の日」にレーンを起こす | hub の約束（`hub promise`）経由でもよい |

**Jev の行の読み直し**（地図 §5「THTH のデータは Jev に渡さない」・masaru 10/15「THTH から出したものを Jev にかけるのは多少慎重に。Jev にかけたものを THTH に入れるのはガンガンやったら良い」）: 向きで分ける。

| 向き | 中身 | 縛り |
|---|---|---|
| **Jev → THTH**（持ち込む） | 判定（流す価値・どちらの群か）・下書き・外の数字の分析（価格の履歴・倍率）・検索語の候補・study の比べる案 | **Platform Data ではない**（外のデータと自分の文から Jev が作ったもの）。遠慮なく。公開は人の承認のまま |
| **THTH → Jev**（渡す） | THTH が取った他人の投稿（本文・username）・言及・返信の本文 | 点検 §5 の**条件つき**（Meta 3.c.ii.3 利用者の明示の同意・5.a 書面の合意＝TypeSafe の規約の確認・privacy の 1 文）。済むまで作らない。X は学習にだけ禁止 |
| THTH → Jev（数だけ） | 筋 2 の出来事（数・id・種類・本文無し）・`where --aggregate` の数 | 集計・非特定化の範囲。judge に渡しても他人の本文は出ない |

**Jev → THTH の口（THTH 側に要るもの・候補 H の一部として具体的に）**:
- `thth draft put <account> --text-file <f> --origin jev:<judge id> [--reply-to <post_id>] [--goal …] [--topic …]`: 外（h2d のレシピ・Jev・レーンの LLM）が作った下書きを、repo のある口座なら queue の原稿として（front-matter に `origin`・`origin_event`・`judge_p`・`judge_model`）、repo の無い口座（招待・遠くの道）なら VM の下書きの棚に置く。**置くだけで出ない**（`status: draft`・承認の二段はそのまま）。lint はその場で掛ける。
- `thth draft list|show|drop <account>`: 棚の一覧・1 件・捨てる（捨てた理由は符丁だけ・`verdict` は禁止鍵のまま）。
- `thth words put <project> --from <f>`: Jev が外の数字から出した検索語の候補を、`where --suggest` の「自分のデータ」の層と並べて出すための棚（`map` の点＝`thth admin map node` と同じ置き場。**語と出所だけ・本文は無し**）。
- `thth study propose <project> --from <f>`: Jev が出した「比べる案」（施策 JSON の素案）を study の下書きとして置く（`study add` は人が打つ）。
- 共通: `origin` の層で `after`・`analytics-report`・`study` が「Jev が作った下書きは、人が書いたものと届き方が違うか」を数で言える。Jev の p・model は `sent` に残す。
- **置かない**: Jev の判定で `approve` を押す口（b）。前承認の型（c）は H の論点のまま。

## 5. 推しと、その理由

**筆頭: 0（記事を正本に、届け先ごとに出し分け、直したら巻き取る）。** 理由: 「反応ゼロ」の悩みの実体は「記事が読まれない」で、THTH の中に記事という単位が無いことが、SNS の数字と記事の訪問（hub の SC・CF）を結べない根。0-1〜0-3（記事の欄・届け先の対応表・はてなブックマーク）は既存の媒体と小さな API で済み、はてなブログ（0-4）と更新の追従（0-5）は段で切れる。H・A・F・C・B・D・E は全部 0 の部品として読み直せる（§0 の「組み合わせ」）。芯（SNS の道具・本文は作らない・人の承認・画面は hub）は、正本を repo に置くことで守れる。

**推し 2: H（出来事から投稿を起こす・まず下書きまで）。** 理由: 出発点に対して、今の THTH に無い唯一の軸が「いつ出すか＝出来事」。フォロワー 0 の口座が届く数少ない瞬間（その話題を今探している人がいる瞬間）に、その口座だけが言える数字（kopicha の店頭価格の観測・関東の倍率）を出す。材料（kopicha の価格の履歴）・感知（h2d の http_json/command_json・judge）・出す道（THTH の承認の二段）・測る道（`after`・`study`）が**全部もうある**ので、足すのは `origin` の欄と遠くの下書きの口と h2d のレシピだけ。masaru の芯（人の承認なしの公開をしない）は a の形なら 1 ミリも動かない。前承認の型（c）は a を 1 か月回して「そのまま出せた率」が数で出てから。

**推し 3: A（手で出したものも THTH が測る・採る）。** 理由: 10/14〜15 の手の運用（X の「人間か確認」を手で解く・手の返信）が THTH の測りの外にある。これを中に入れないと、14 日の試しの分母に「本当に効いた手」が入らず、`after`・`ask`・`study` が「THTH を通したものだけの世界」を語り続ける。H の出来事起点の投稿を時刻起点・手の投稿と同じ物差しで測るにも、この母集団の広げ方が土台。Buffer が当然やっていることを THTH がやっていない、という意味でも 4.0 の基礎。

**masaru が「グッとくる」か（正直に）**: H は masaru 自身の発案で、「THTH は何を書くかを決めない・頼まれたときだけ動く」という芯を**出来事が頼む**形に広げる。ここは腹落ちしやすい一方、「出すのは人」のまま始めると「結局朝に承認するなら timer と何が違う」と見える危険がある——違いは**材料と鮮度**（出来事の JSON が下書きに付き、`origin` で測れる）で、前承認の型は次の段、と言い切った方がよい。A は「当然そうあるべきだった」の類で驚きはないが、10/14〜15 の手の運用が丸ごと記録に残るので腹落ちはする。C は小さいが 10/14 の経験に直接当たる。B はいちばん「製品らしい」が `unanswered`・`mentions` の言い換えに見える危険があり、「反応した人の顔」が入らなければ作らない。D は 15 日目の判定を一度人がやってから設計すると欄が実物に合う。E は守り。

**4.0 の柱として**: F（出来事の口と契約つき JSON）は目玉でないが、H・hub・h2d の 3 つがこれに乗る。ダッシュボードと連携を hub・h2d に譲る決定の裏側として 4.0 の最初に出す（地図 §4 の 1「約束事を先に」）。G は F と同時に。

**masaru が「グッとくる」か・0 について**: §2-0 (6) に書いた。刺さる見立てだが、「新世代のブログツール」の言葉で THTH が本文と画面を持つ方向に膨らむのが危うい。**THTH は流通と記録、画面は hub、本文は repo**。

**順**（推し）: F（契約・`events`・`fires record`・G を同時）→ 0-1（記事の欄と束ね）→ A → 0-2・0-3（対応表・はてなブックマーク。はてなの口座の決めが先）→ H の a（kopicha の価格で 1 本の tracer・Jev→THTH の `draft put`）→ C → E → 0-4（はてなブログ）→ B → D → 0-5（更新の追従）→ H の c（a の数を見てから）。
