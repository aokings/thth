# 設計 3.12.0: 承認を関所から「選ぶもの」へ・暴走は安全装置で止める（2026-09-26）

状態: **下書き（masaru の確認待ち）**。確認が取れたら段に割って作る。

## 0. 決定（masaru・2026-09-26 00:40〜01:00 JST）

- 「LLM とユーザの信頼性をこちらが疑うのは越権。私たちは道具の提供者に過ぎない」。
- 外の人も、masaru と同じく**自分の LLM から THTH を使う**。masaru は「ハナからそのつもり」だった。
- ただし「LLM が暴走して使い方を誤った場合はセーフティが効くようにする」。

経緯: 録画 0（審査員の流れ）を撮る途中で、masaru が「何をするにもキーを入れて承認する方式は使いたくない」と言った。3.10〜3.11 の招待の道は、外の人の LLM に「下書きと承認の依頼」までしか許さず、公開と削除は毎回 thth.me の承認ページで secret を入れさせていた。これは運営者が利用者とその LLM を疑う作りで、masaru の自分の口座（自分の LLM が queue に置けば出る）と食い違っていた。

## 1. 原則

1. **疑わない。** 利用者が自分の LLM に頼んだ時点で、本人の意思は示されている。運営者はそれを二重に確かめない。
2. **暴走は機械で止める。** 持ち主が決めた数値（上限・間隔・猶予）を道具が機械的に守る。守れないものは断り、止めて、知らせる。「こちらが信用するか」の判断は入れない。
3. **承認ページは選ぶもの。** 他人に下書きを任せる人、一件ずつ見たい人が口座ごとに選ぶ。既定は無し。
4. **守りは鍵で持つ。** LLM に渡す鍵（MCP の資格）の範囲・期限・取り消しで守る。鍵が漏れたときの被害は 2 の安全装置で上限を持つ。

## 2. 今の作り（3.11.1）

| 道 | 外の人の LLM（MCP・`scope` は口座に限った資格） | 誰が出すか |
|---|---|---|
| 下書き | `thth_draft_put` / `thth_draft_list` | — |
| 公開 | `thth_approval_request`（予約・承認で queue に刻む）・`thth_send_request`（承認の直後に出す） | 承認を受けた `approval-worker`（`thth/approval_jobs.py` の `_perform`） |
| 削除 | `thth_retract_request` | 同上 |
| 承認 | thth.me/approve/… か thth.me/pending（secret） | 本人 |

`server_writes.WRITE_OPERATIONS` のうち、公開と削除に至るのは `approval_request`・`send_request`・`retract_request` の 3 つで、どれも承認 job（`approval_jobs.create`）を作って本人の承認を待つ。

## 3. 変えること

### 3.1 口座の設定 `approval`

台帳に 1 項目足す。

| 値 | 意味 |
|---|---|
| `none`（既定） | 承認ページを使わない。LLM の依頼がそのまま公開・削除・予約になる（安全装置は効く） |
| `publish` | 公開（今すぐ・予約）だけ承認ページを通す。削除はそのまま |
| `all` | 公開も削除も承認ページを通す（3.11 と同じ動き） |

持ち主が変えられる（`thth account set <口座> approval <値>`・招待の口座は MCP の `thth_settings` からも）。既存の招待の口座（`inv-…`）は `all` のまま移す（勝手に緩めない）。

### 3.2 承認なしの道（`approval: none` / 削除だけ `publish`）

- `thth_send_request` → worker を待たず、その場で `core.send_once` と同じ点検（lint・digest）を通して出す。結果（post_id・permalink）を返す。
- `thth_approval_request` を予約として使っていた道 → `thth_schedule_request`（下書きを queue に「出してよい」として刻む。timer が `publish_at` 以降に拾う）に名前を分ける。旧名は `approval: none` の口座では同じ動きに流す。
- `thth_retract_request` → その場で削除する。
- どの道も、出したもの・消したものは口座の記録（`sent/`・`runs-*.ndjson`）に `via: mcp`・資格の id（`credential_digest` の先頭）つきで残す。

### 3.3 安全装置（口座ごと・持ち主が値を決める）

| 装置 | 既定 | 超えたとき |
|---|---|---|
| 最短間隔 `min_interval_hours` | 既存のまま（招待の口座は 6） | 断る（`too_soon`・次に出せる時刻を返す） |
| 1 日の公開の上限 `daily_max_posts` | 8 | 断る（`daily_limit`） |
| 1 日の削除の上限 `daily_max_retracts` | 5 | 断る |
| 急な連投 `burst` | 10 分に 3 件（公開と削除の合計） | **口座を止める**（`stopped: burst`）→ 持ち主に知らせる。止まった口座は持ち主が戻すまで公開・削除を断る |
| 夜間 `quiet_hours` | 既存のまま | 予約はずらす・今すぐは断る |
| 取り消しの猶予 `hold_minutes` | 0（無し） | 1 以上なら、今すぐの公開もその分待ってから出す。その間は持ち主が取り消せる |
| lint | 既存のまま | 断る（理由と次の一手つき） |

数え方は口座ごと・JST の日付で。上限の値は持ち主が変えられる（上げる方向も）。運営者が上限を押し付けることはしないが、既定値は置く。

### 3.4 持ち主が見る・止める

- **動きの一覧** `https://thth.me/activity`（今の `/pending` を広げる）: その口座で出たもの・消したもの・予約・猶予中のもの・止まった理由を新しい順に並べる。
- ここで secret（か 3.13 以降のパスキー）を使うのは**止める・取り消す・止めたのを戻す**ときだけ。毎回の公開には使わない。
- 止まったとき（burst・資格の失効など）は、MCP の次の呼び出しの答えに理由を載せ、`/activity` の先頭に出す。メールの通知は持ち主がメールを登録したときだけ（3.12 では入れ物だけ・送るのは後の版）。

### 3.5 鍵（MCP の資格）

- 今の資格（口座に限った `scope`・期限つき）をそのまま使う。承認なしの道はこの資格で開く。
- 持ち主が `/activity` から資格を取り消せる（今は運営者の `thth admin` だけ）。取り消すと、その資格での呼び出しは即座に断る。

## 4. 変えないこと

- 招待の流れ（招待リンク → Threads の認可 → 口座の用意）。secret の発行は残す（止める・取り消す用）。

## 9. 作りながら決めたこと（2026-09-26 夜間・主セッションの裁定。masaru の朝の確認待ち）

1. 最短間隔 `min_interval_hours` は**返信には掛けない**（会話なので）。返信も 1 日の上限と burst には数える。
2. `scheduled: false` の口座（今の招待の口座）では、予約（`thth_schedule_request`）と `hold_minutes>0` を `schedule_unavailable` で断る。刻んでも timer が無くて黙って出ない、を避ける。
3. **LLM に渡す鍵を本人が手に入れる道が無かった**（招待の完了で常駐が資格を足すが、bearer は hash だけで誰にも出さない）。`/activity` に「LLM の鍵を発行する」を置き、本人が secret で確かめて 1 度だけ受け取る（前の鍵は取り消し）。運営者は bearer を扱わない。
4. **LLM（`thth_settings`）から変えられるのは締める向きだけ**。承認は none→publish→all、数値は上限を下げる・間隔を延ばす。緩めるのは `/activity`（secret）か運営者の CLI から。暴走した LLM が自分で安全装置を外せないように。止まった口座の再開も LLM からはさせない。
5. 新しく招待で作る口座は `approval: none`。3.11 以前の招待の口座は `all` のまま（勝手に緩めない）。
6. 止めた印は既存の退出の止め（`leave_gate`・戻せない）と別に持つ（`state/<口座>/guard/stopped.json`）。
7. release のあと常駐を入れ替える道は、systemctl ではなく常駐が自分で終わる形（ディスクの版が動いたら 75 で終わり、`Restart=on-failure` が新しい版で起こす）。VM の利用者 wt は root 無しで restart できないため。
8. **外の人が MCP につなぐ道が無い**（段 3 で判明）。MCP は stdio で、起動口は VM の上（`ssh <server> thth-mcp-invitee`・設計 3.0 §2）。ssh を持たない外の人は鍵を発行してもつなげない。リモートの MCP（`https://thth.me/mcp` の Streamable HTTP を Worker で受け、VM へ relay する等）を置くかは masaru の判断。公開の口が増える（攻撃面）ので夜間には作らない。それまで新しい招待（`approval: none`）は作らない（利用規約の改訂待ちとも重なる）。
