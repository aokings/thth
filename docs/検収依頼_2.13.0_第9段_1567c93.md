## 2. 実装した契約

### 2.1 `thth_media_upload_url {account, kind, size, sha256, mime}`

1. 資格情報（`writes: true`・利用者 scope・managed repo）を再認証。
2. 申告を検査（kind・mime 許可表・size 上限・sha256 の形）。**外れたら Worker を一度も呼ばない。**
3. `state/<account>/media-uploads/<media_id>.json` を mode 600 で保存（`schema_version, media_id, actor, account, kind, mime, size, sha256, status=pending, created_at, expires_at(+600 s)`）。**Worker への問い合わせより前。**
4. Worker の `create`（`kind=source`・申告 size/sha/mime・100 MB 超は `part_size` 5 MiB）。
5. 返すのは `{media_id, upload_url, expires_at, part_size|null}`。`upload_url` は `<origin>/media-upload/<media_id>`、`media_id` は Worker の subject（43 文字 opaque）。URL は `redact.register_secret` に登録し、この応答以外には出しません。
6. もう一度呼べば別の session。古い方は Worker の時計で失効します（VM は消しに行きません）。

`create` が失敗したら控えは `unknown`（理由 `media_session_unavailable`）で残り、**自動で開き直しません**。

### 2.2 `thth_media_complete {account, media_id}`

1. 控えを読み、`(actor, account)` が一致しなければ `media_owner_mismatch`（**Worker 呼び出し 0 回**）。
2. `ready` なら同じ結果をそのまま返す（Worker 呼び出し 0 回）。`rejected` は `media_already_completed`、`unknown` は `media_upload_unknown`。
3. Worker `complete` → `status` → 署名付き `read` を private な temp file へ流し込み（既存 `_receive`）、申告 sha と長さを照合 → `ack` で R2 の source を退役。
4. 第 1 段の sanitize（`mediaformats.inspect` に account の媒体 policy）。拒否されたら静的理由で断り、控えを `rejected` にし、**repo には何も置きません**。
5. 通れば公開 sha を計算し、`docs/sns/media/<公開 sha>.<拡張子>` を書いて `git add`→commit→push（`draft_put` と同じ `commit_and_push` と `validate`）。書き掛けは残しません（temp→rename→fsync）。同じ公開 sha が既に commit 済みなら書き直しも commit もしません。
6. 控えを `ready`（`public_sha256, format, kind, width, height, duration, warnings, file`）にし、`{media_id, public_sha256, format, kind, width, height, duration, warnings}` を返します。

`complete` が 4xx なら確定失敗 `media_upload_failed`（控えは `rejected`）、5xx・transport 不明なら `unknown`（理由 `media_upload_unknown`）で、**二度目は Worker を呼びません**。

### 2.3 `thth_draft_put` の `media: [{media_id, alt}]`

`ready` で同じ actor・同じ account の控えだけを受けます（不一致 `media_owner_mismatch`、知らない id `media_unknown`、未確定 `media_not_ready`、alt 空 `invalid_draft: alt_required`）。front matter には

```yaml
media:
  - file: docs/sns/media/<公開 sha>.jpg
    alt: "湯呑み: 淡い緑。"
```

と書きます（alt は JSON 文字列で書くので往復が一致します。一致しなければ `invalid_draft: media_not_representable`）。以後は第 1 段そのまま（manifest・digest・lint・承認ページ）。draft の revision / expected_revision の意味は変えていません。`media` は毎回全量で、省略すれば添付の無い下書きになります（`topic`・`reply_to` と同じ扱い）。

### 2.4 後片付け

`thth admin media gc <account> --by <人>`：`docs/sns/media` の中で「追跡されている他のファイルの本文にその名前が出てこない」かつ mtime が 1 日以上前のものを、managed repo の 1 commit で消します。出力は `{account, removed_count, kept_count, intents_removed, reason}` の**件数だけ**（ファイル名は出しません）。参照の判定は文字列一致で、迷ったら残す側に倒します（消し過ぎより残し過ぎ）。同時に 1 日以上前の終了済み控えも片付けます。

## 4. 設計判断（見てほしいところ）

1. **source の「invalidate」は `ack`（退役）です。** Worker の `invalidate` は `kind=provider` の grant 専用で、`kind=source` の object には効きません（`media-object.js` の `publicResult`）。第 9 段では読み戻しの直後に `source_snapshot` が `ack` を打ち、**成功でも拒否でも退役は 1 回**です。sanitize の後にもう 1 回打つと Worker は 409 を返すだけなので、そうしていません。R2 の実消去は lifecycle 24h が backstop です（依頼 §4 の「ready の source を invalidate」は、この退役で既に済んでいます）。
2. **「GPS 付き JPEG → `location_metadata_present` で拒否」は実装と違います。** 第 1 段は top-level 画像の Exif GPS を**落とす**設計で（`mediaformats.jpeg` は Orientation 以外を捨てる。privacy 集合を集めるのは埋め込み cover のときだけ）、拒否になるのは動画の位置 box です。そこで試験は 2 本にしました——動画の位置 box は拒否、GPS 付き JPEG は「落として通る」ことを repo の bytes で確認。どちらも M2 が殺します。依頼文の方を直すか、画像も拒否に変えるかは masaru の裁定待ちです（現状は設計 §8-5「公開前に落とす（既定 on）」に従っています）。
3. **音声は「名指しで断る」** ようにしました。Worker の転送 mime 集合（`callback/src/media.js` の `MIME`）に音声がないため、`kind: audio` は表に行を持ったまま `media_mime_unsupported` で断ります。表から消す（＝理由なく落とす）ことはしていません。音声を通すには Worker の `MIME` に音声型を足す必要があり、第 9 段の範囲外としました。
4. **上限は 1 箇所** `thth/media_uploads.py` の `KINDS`（image 8,000,000 / video 1,000,000,000 / audio 100,000,000・暫定）。`FORMATS` は「検査した形式 → 転送 mime と拡張子」で、**申告 mime は信用しません**（実 bytes の検査結果と突き合わせます）。
5. **`media_id` は Worker の subject** です（依頼どおり）。したがって media_id を知る者は URL を組み立てられます。URL は本人にだけ返し、object は `pending` の間の 1 回だけ書けます。
6. **控えの単位はミリ秒**（`approval-jobs` と Worker に合わせました）。`expires_at` は VM の +600 秒と Worker の返す期限の小さい方です。
7. **静的理由だけ**が外へ出ます。sanitize の理由は先頭の code（`location_metadata_present` 等）だけを取り、未知の形なら `media_sanitize_refused` に丸めます。パス・値・URL・capability は理由にも記録にも入りません。
8. **gc の参照判定は文字列一致**（追跡ファイルの本文に `<64 hex>.<ext>` が出るか）。front matter の書き方に依らず、束（`thth: 2`）や注記から参照されていても残ります。過剰に残す方向の誤差です。
