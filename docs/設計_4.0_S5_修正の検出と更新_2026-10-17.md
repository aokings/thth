## 0. 一言で

**更新は今の 2 段の承認（`op: update` の原稿 → 1 段目に差分 → `--confirm` → timer が PUT の前に読み戻して比べる）をそのまま使い、足りない 4 つを足す。** (1) **検出**: `thth article diff <口座|project>` が、配信の台帳の `checked_rev`（出した版）と repo の HEAD にある記事の版（blob の sha）と画像の指紋を比べ、「直した」配信を並べて本文の差分と、そのまま保存できる更新の原稿の文面を出す（THTH は原稿を書かない・勝手に更新しない。保存して承認するのはレーンの LLM と人）。同じ比べを `thth deliveries` の 1 行・`thth morning`・`thth board`・`thth events`（`delivery_behind`・続いている状態）・MCP `thth_article_diff`・thth.me の読む口 `article_diff` に出す。(2) **承認の表示**: 台帳に `title`・`categories` を記録し、1 段目に「題: 旧 → 新」「カテゴリ: 足した・外した」「画像: 変わらず n・差し替え n・追加 n・外した n」「正本の版: 出した → 今回」を足す。本文も題もカテゴリも画像も変わっていない更新は `update_no_change` で断る（burst を使わない）。(3) **衝突を解く口 `thth conflict <口座>`**: 見る（`show`・はてなの今の本文との差分）・確かめる（`check`・GET で外での手直しを見つける。更新の原稿が無くても検出できる）・解く（`resolve --adopt`／`--gone`／`--no-follow`・2 段・控え・admin_log）。「THTH の側で上書きする」は別の道を作らず、**取り込む（`--adopt`・台帳の変更前の版をはてなの今の本文にする）→ 更新を承認し直す（1 段目の差分が「はてなの今の本文 → 記事」になる）** の 2 重の承認で行う。削除は衝突のままでも承認できる（`readback_changed`・`syntax_mismatch` のとき・1 段目に「手直しも消えます」）。(4) **結果不明の照合**: `thth inflight <口座>` のはてなの枝が一覧（題・公開時刻）を読んで候補を見せ、`resolve --published <entry_id>` の命令をそのまま出す（解くのは人・自動では解かない）。**burst は「同じ配信への操作は窓の中で 1 件」と数える**（公開 → 直して更新 → 消す、で口座が止まらない。別の記事の連投は今までどおり止まる。日の上限は変えない）。SNS の告知は記事を更新しても書き換えない（`thth article diff` が告知の一覧と「訂正の返信を出すなら」の案内を添えるだけ）。既存の承認の指紋（`thth-hatena-entry-1`・SNS の v1）は 1 バイトも変えない。

### 1.2 実機で分かった前提（記録・10/17）

- 更新は動く: 人が `op: update`・`delivery: dl_…` の原稿を書くと、1 段目に前の本文との差分が出て、PUT・読み戻しまで通った（S2 の 7）。外で手直しされていれば `conflict`（`readback_changed`）で止まった（8）。
- `conflict` の配信は更新も削除も承認できない（lint が `published` 以外を断る）。試しの記事 …/111823 はこの状態のまま（記録の 3）。
- 1 本の記事を短い間に「公開 → 更新 → 削除」すると口座の burst（10 分に 3）で口座が止まった（13・記録の 4）。
- 書き込みの時間切れで結果不明になった記事が、実際にははてなに届いていた。THTH は出し直さず止まり、人が一覧から `entry_id` を拾って `inflight resolve --published` で解けた。`thth inflight show` の文は SNS 向けのまま（記録の 10）。
- 題・カテゴリを更新したときの扱い・日付が動くか・はてなの空白の返し方は**まだ画面で見ていない**（S2 の 7 の残り）。

## 2. 言葉

- **出した版**（`checked_rev`）: 最後に公開・更新したときの記事ファイルの blob の sha。台帳にある。
- **今の版**（`current_rev`）: repo の **HEAD** にある記事ファイルの blob の sha（`hatena_entry.committed_rev`）。作業ツリーの未 commit の変更は見ない（S2 §7「記事は commit されてから」と同じ線）。
- **直した**（behind）: 出した版と今の版が違う、か、依存する画像の指紋（台帳の `images[].source_sha256`）が今の画像ファイルと違う。
- **外での手直し**: はてなの側の本文・題・カテゴリが、台帳の `readback_sha`・`title`・`categories` と違う。
- **取り込む**（adopt）: はてなの今の本文・題・カテゴリを「変更前の版」として台帳に書く。記事の正本（repo）には何も書かない。
- **追従をやめる**（`no_follow`）: この配信は記事の修正に追従しない。`article diff` は「直した」に数えない。削除はできる。

### 3.2 比べ方 `hatena_entry.source_status(record, account_cfg) -> dict`

```
{"checked_rev": "a1b2…", "current_rev": "c3d4…", "kind": "git"|"content"|None,
 "head_commit": "9f8e…", "behind": true|false|None, "reasons": ["body", "images"],
 "images": {"same": 2, "changed": 1, "missing": 0}, "error": None|"repo_unreadable"|"article_source_missing"}
```

- 対象は `state` が `published`・`conflict` の配信（`no_follow` は `behind: None`・理由 `no_follow`。`wanted`・`inflight`・`unknown`・`deleted` は見ない）。
- `current_rev` は `committed_rev(repo_file(repo_dir, article_source))`。repo の外（`article_rev_kind: content`）は作業ツリーの本文の sha256（S2 §7 と同じ扱い）。読めなければ `error` を入れて `behind: None`（「言えない」）。
- 画像: 台帳の `images[]` の各 `path` を repo の HEAD の blob（`git rev-parse HEAD:<path>` → `git cat-file`）で読んで sha256 を取り、`source_sha256` と比べる。無ければ `missing`。**作業ツリーの画像は読まない**（HEAD と作業ツリーが違う画像は `article_not_committed` の側）。
- `behind` は `current_rev != checked_rev` か画像に `changed`／`missing` があるとき。`checked_rev` が無い（S5 より前の台帳・`content` の台帳）なら `behind: None`・理由 `no_checked_rev`。

### 3.3 `thth article diff <口座|project> [--article …] [--delivery …] [--json] [--draft]`

読むだけ（台帳・repo の HEAD と作業ツリー・`sent/`）。媒体の API は呼ばない。

1. `deliveries_cli.build()` と同じ対象（口座か project・`--article` で絞る）。各配信に `source_status`。
2. `behind` の配信ごとに:
   - 本文の差分: 「前」は承認の控え `deliveries/<dl>.<指紋 12 桁>.body.md`（`_approved_body`・元の形）、「今回」は今の記事を `hatena_entry._render`（作業ツリー・`material()` と同じ）で変換した本文。控えが無ければ `sent/` の `text`（置き換えのあと）に倒して 1 行添える（S3 §5.3 と同じ）。作業ツリーが HEAD と違えば `article_not_committed` を添えて差分は出す（承認はどうせ断られる）。
   - 画像: `変わらず n・差し替え n（path）・追加 n（path）・外した n（path）`。
   - 告知: `deliveries_cli.announcements()` の行（§7）。
   - `--draft`: 更新の原稿の文面（§3.5）を標準出力に出す（ファイルは書かない）。
3. `--json`: `{"schema": "thth.article_diff/1", "deliveries": [{delivery, account, article, state, source, diff_lines[], images, announcements[], draft_text?}], "unreadable": [...], "cannot_say": [...]}`。`diff_lines` は `unified_diff` の行（本文は THTH の変換後なので秘密は入らない）。
4. 1 行の表示:

```
記事の修正  kopicha-hatenablog  直した 1 件・同じ 2 件・追従しない 0 件・言えない 0 件
  dl_3f9c2a7e1b4d  kopicha/2026-10-arabica  published  出した a1b2c3…（10/20 08:00）→ 今の版 c3d4e5…（commit 9f8e7d…）  画像: 変わらず 1
  ---- 本文の差分（出した版 → 今の版） ----
  …
  ---- ここまで ----
  告知: kopicha-threads 10/20 08:31（post_id）→ 書き換えません（訂正を出すなら返信の原稿で）
  更新するには: 更新の原稿を docs/sns/queue/ に書いて thth approve（thth article diff … --draft で文面が出ます）
```

### 3.5 更新の原稿は誰が書くか

| 案 | 形 | 利点 | 欠点 |
|---|---|---|---|
| A | レーンの LLM が今までどおり `op: update` の原稿を全部書く | 変更なし | 欄は台帳から写すだけなのに毎回書く。写し間違い（`delivery`・`article_source`）が起きる |
| B（推し） | **THTH が文面を出す（`thth article diff --draft`・標準出力）。保存・commit・承認はレーンの LLM と人** | 欄の写し間違いが無い。THTH はレーンの repo に新しいファイルを書かない（第二の正本を持たない・計画 §2） | LLM が保存する 1 手が残る |
| C | THTH が queue にファイルを書いて commit する | 1 手減る | THTH がレーンの repo に**新しい**ファイルを書く道が増える（今あるのは front matter の書き戻しだけ）。同時に作業しているレーンと衝突する |

**B にする。** 文面:

```markdown
---
thth: 1
account: kopicha-hatenablog
status: draft
publish_at: 2026-10-21T09:10:00+09:00
article: kopicha/2026-10-arabica
article_source: articles/2026-10-arabica.md
form: full
title: アラビカの値動き（2026 年 10 月）
categories: [コーヒー, 価格]
op: update
delivery: dl_3f9c2a7e1b4d
---

## hatenablog
```

- `publish_at` は今＋10 分（分まで・JST）。直すのは LLM。`title`・`categories` は台帳の記録（§4.2・無ければ空にして `title_required` が lint で出る）。`article`・`article_source`・`form`・`delivery` は台帳から。
- 保存先の案内は `docs/sns/queue/<日付>-<記事の名の末尾>-update.md`（文だけ・THTH は書かない）。
- **検出しても勝手に更新しない**: 原稿が無ければ何も出ない・原稿があっても承認が要る・承認のあとに記事が変われば `approval_stale`（S2 §8）。

## 4. 差分の承認（決めること 2）

### 4.1 今の 2 段との関係

変えない: 1 段目（`thth approve <原稿>`・遠くの道は `schedule_request` の `stage: 1`）が差分と digest を見せ、2 段目（`--confirm`）が書き戻す。timer は PUT の前に読み戻して `base_readback_sha` と比べ、違えば `conflict`。承認の指紋 `thth-hatena-entry-1` の 14 項目は **1 つも変えない**（題・カテゴリ・本文・画像・変更前の版は既に入っている）。

### 4.2 台帳に `title`・`categories` を記録する

- `deliveries.MUTABLE_FIELDS` に `title`・`categories` を足す。書くのは `assign_delivery`（`wanted`・create のとき）と `_record_outcome`（`published`・create と update）。`categories` は `material()` の並び（原稿の順）のまま。delete は書かない。
- これは「何を出したか」の記録で、指紋の材料ではない（指紋は `approved_sha`）。S5 より前の台帳には無い → 1 段目は「（台帳に記録なし）」と出し、比べない。

### 4.3 1 段目の表示（update）

`display_lines()` の update の枝を次の形にする（S1 §6.3 の形は保ち、行を足す）:

```
配信原稿  kopicha-hatenablog → kopicha.hatenablog.com（主体 hatena-kopicha・レーン kopicha）
操作: 更新   公開: 2026-10-21T09:10:00+09:00（timer が draft=no で送る）
記事: kopicha/2026-10-arabica（articles/2026-10-arabica.md・版 c3d4e5… git）・commit 9f8e7d…
正本の版: 出した a1b2c3…（10/20 08:00）→ 今回 c3d4e5…
題: アラビカの値動き（2026 年 10 月）                 ← 変わったときは「題: 旧 → 新」
カテゴリ: コーヒー・価格                              ← 変わったときは「カテゴリ: コーヒー・価格（足した: 相場／外した: 価格）」
画像: 変わらず 1・差し替え 1（images/chart.png・sha256 7e3f…→ 9a1c…）・追加 0・外した 0
変更前の版 readback_sha e5f6…（10/20 08:00 に確かめた・承認の控えと比べます）   ← 取り込んだあとは「（はてなの今の本文を 10/21 08:50 に取り込んだ・それと比べます）」
---- 本文の差分（前に出した本文 → 今回） ----
…
---- ここまで ----
digest: 3fa9c1e0b2d4
承認する: thth approve docs/sns/queue/… --confirm 3fa9c1e0b2d4 --by <名前>
```

- 「前」の本文の優先: (1) 台帳の `readback_sha` と同じ名の取り込みの控え `deliveries/<dl>.rb.<readback_sha 12 桁>.md`（§5.3・置き換えのあとの形なので画像の行の注記を添える）→ (2) 承認の控え `deliveries/<dl>.<指紋 12 桁>.body.md`（元の形）→ (3) `sent/` の `text`（注記つき）→ (4) 無ければ全文（今のまま）。
- 題・カテゴリ・画像の比べ先は台帳の `title`・`categories`・`images[]`（最後の `published` の値）。
- 遠くの道の `stage: 1` の `preview` も同じ行（`display_lines` を共有・今のまま）。

### 4.4 何も変わっていない更新は断る `update_no_change`

- `material()` の update で、承認の控え（(2)）が読めて `hatena_body_sha256(控え) == body_sha256(今回)`・`title` が台帳と同じ・`categories` が同じ集合・`images[]` の `(path, source_sha256)` が同じ、なら `EntryError("update_no_change")`。控えか台帳の記録が無ければ比べない（通す）。
- lint・1 段目・timer の 3 か所で同じ符丁（`LINT_CODES` と `S2_REFUSALS` に足す＝timer の照合で `approval_stale` に丸めない）。文: 「出した版と同じです（本文・題・カテゴリ・画像のどれも変わっていない）。更新は送りません」。
- 理由: 無駄な PUT は burst と日の上限を消費し、はてなの `updated` を動かす恐れがある（実機で未確認）。

### 4.5 lint の文を状態のとおりに（記録の 2）

`lint_errors` の 205〜207 行: `_ledger_for` が投げた `EntryError` の `code` が `delivery_state_<state>` ならその符丁で出す（文: 「delivery: の配信は <state> です。conflict は thth conflict <口座> で解いてから・deleted は消えています・wanted は create で」）。`delivery_unknown` は「台帳に無い」のときだけ。`LINT_CODES` に `delivery_state_conflict`・`delivery_state_deleted`・`delivery_state_wanted`・`delivery_state_inflight`・`delivery_state_unknown`・`delivery_state_no_follow` を足す（文は 1 つの表から）。

## 5. 衝突（`conflict`）を解く（決めること 3）

### 5.1 比べた案

| 案 | 形 | 利点 | 欠点 |
|---|---|---|---|
| A（推し） | **`thth conflict <口座>` に `show`・`check`・`resolve` を置く。解き方は `--adopt`（取り込む）・`--gone`（外で消えていた）・`--no-follow`（追従をやめる）の 3 つ。「THTH で上書き」は `--adopt` のあとに更新を承認し直す** | 上書きが必ず「はてなの今の本文 → 記事」の差分を見た承認を通る（2 重の承認）。PUT の前の比べ（`base_readback_sha`）の意味を変えない | 上書きに 2 回の 2 段が要る（4 回打つ） |
| B | 更新の原稿に `overwrite: yes` を書けば `conflict` でも PUT する | 1 回の承認 | 指紋に `overwrite` を足す（新しい項目・版を上げる話になる）。差分の「前」が承認の控えのままで、消される手直しが 1 段目に出ない |
| C | `conflict` の台帳を手で直す（`published` に書き換える） | 作らなくてよい | 記録が残らない・`seq` と `history` の検査で壊れる |

**A にする。** 上書きは B より手数が多いが、「何を消すか」を人が見る。

### 5.2 `thth conflict <口座> [<dl>] [show|check|resolve …]`

| 形 | 何をするか | 書くか | HTTP |
|---|---|---|---|
| `thth conflict <口座> [--json]` | `conflict` の配信の一覧（理由・いつから・`published_url`）と、`no_follow` の一覧 | 読むだけ | 無し |
| `thth conflict <口座> <dl> show` | 台帳の最後の行の理由・**はてなの今の本文を GET**（`read_entry`）して、最後に送った本文（`sent/` の `text`）との差分・題とカテゴリの違い・`content_type` | 読むだけ（台帳は書かない） | GET 1 回 |
| `thth conflict <口座> check [<dl>] [--limit 20]` | `published` の配信（か 1 つ）を GET して台帳と比べる。本文の sha・題・カテゴリが違う → **`conflict`（`readback_changed`・詳細 `body`／`title`／`categories`・`via: check`）**。404 → `conflict`（`entry_missing`）。同じ → 何も書かない（出力に「同じ（確かめた時刻）」）。`published_url`・`edit_uri`・`readback_sha` が無い `published`（人が `--published` で解いたもの・S1 監査 4）→ 埋める（`published` → `published` の行・`op: check`・`resolution: readback_filled`） | ロックの中で台帳 | GET 1 回/配信・1 件ごとに 2 秒空ける（S4 §7 の流儀） |
| `thth conflict <口座> <dl> resolve (--adopt \| --gone \| --no-follow) --by <名前> [--confirm <digest>]` | §5.3 | ロックの中で台帳・控え・admin_log | `--adopt` は GET 1 回 |

- ロックは `core._account_locks`（repo → principal → account・waitなし）。timer の run と同じ順。
- 対象の配信が無い・読めない → `delivery_missing`／`delivery_unreadable`（rc 2）。inflight が残っている口座では `resolve`・`check` を断る（`inflight_open`・先に `thth inflight` で解く）。
- `check` は timer に載せない（4.0 では手で打つ。毎 run の GET は要らない。入れるなら `maintain` の 1 日 1 回を後の版で）。

### 5.3 解き方の表

| 解き方 | 受ける理由 | 台帳 | 控え・記録 | そのあと |
|---|---|---|---|---|
| `--adopt`（はてなの側を正にする） | `readback_changed`・`syntax_mismatch`（人がはてなの画面で確かめた）・`no_follow` からの再追従・`published` から（外で手直ししたと知っていて先に取り込む） | `read_entry` → `readback_sha`＝今の本文の sha・`title`・`categories`＝今の値・`edit_uri`・`published_url`（無ければ）・`checked_at`。`state: published`。行 `{op: resolve, resolution: adopt_remote, resolved_by, previous_readback_sha, readback_sha, content_type}`。**`checked_rev` は触らない**（最後に送った記事の版はそのまま） | 今の本文を `deliveries/<dl>.rb.<readback_sha 12 桁>.md`（0600・1 段目の差分の「前」） | 承認済みの更新の原稿は `approval_stale`（`base_readback_sha` が変わる）→ 承認し直すと 1 段目の差分が「はてなの今の本文 → 記事」になる＝**上書きの承認**。手直しを repo に写すなら、`show` の差分を見て記事を直してから更新 |
| `--gone`（外で消えていた） | `entry_missing`・`published_elsewhere`（人が別のブログの画面で消した） | `state: deleted`・行 `{op: resolve, resolution: remote_deleted, resolved_by}` | `sent/` は触らない（THTH が消したのではない・削除の枠に数えない） | 承認済みの更新・削除の原稿は `delivery_state_deleted` → `thth revoke` で draft に戻す（案内を出す） |
| `--no-follow`（追従をやめる） | どの理由でも（`published` からも） | `state: no_follow`・行 `{op: resolve, resolution: no_follow, resolved_by}` | — | `article diff` は「追従しない」。更新は断る（`delivery_state_no_follow`）。削除はできる。戻すのは `--adopt` |

- 理由に合わない解き方は `resolution_not_applicable`（例: `entry_missing` に `--adopt`）。`--adopt` の GET が 404 なら `entry_missing` の衝突に書き換えて止める（`--gone` を案内）。GET が失敗（5xx・時間切れ）なら何も書かない（rc 1・次にもう一度）。
- **2 段**: `--confirm` が無ければ、解く内容（配信・理由・解き方・`--adopt` なら差分の要約と今の本文の sha）と digest を見せて何もしない（rc 1）。digest は `thth-delivery-resolve-1 | account | delivery | seq | resolution | （adopt なら今の本文の sha）` の sha256 の先頭 12 桁（`inflight_cli.digest` と同じ形・承認の指紋ではない・golden には載せず固定の試験だけ）。`seq` を入れるので、見せたあとに台帳が進めば digest が合わない。
- `admin_log.EVENTS` に **`delivery_resolved`**（subject は口座・presence-only: `delivery`・`resolution`・`by`・本文は入れない）。
- 出来事: `events_cli.KINDS` に **`delivery_resolved`**。`_delivery_kind` は `op: resolve` の行を状態に関わらず `delivery_resolved` にする（`published` に戻る行を `delivery_published` と読ませない・S1 監査 1 と同じ考え）。`op: check` の行は `conflict` なら `delivery_conflict`、`readback_filled` なら出さない。
- 遠くの道・MCP: `thth.me` に `conflict_status {account, delivery?, check?}`（`check: true` で `check` を 1 件）・`conflict_resolve {account, delivery, resolution, confirm?}`（2 段・`inflight_resolve` と同じ形）。MCP に `thth_conflict_status`・`thth_conflict_resolve`。理由: inflight の解きが遠くの道にある（S1 §1）のと同じ線で、衝突に気づくのはレーンの LLM。鍵の範囲は口座 → project。`principal resume` のような「暴走の戻し」ではないので MCP に出してよい。

### 5.4 削除は衝突のままできる（推し: できる）

| 案 | 利点 | 欠点 |
|---|---|---|
| A（推し） | **`op: delete` は `conflict`（理由 `readback_changed`・`syntax_mismatch`）の配信にも承認できる。** 1 段目に「この記事は外で手直しされています（10/21 08:50・本文）。消すと手直しも消えます」の 2 行 | 消す意思は衝突と独立（手直しを消したくなければ `--adopt` して記事に写してから）。手数が 1 回の 2 段で済む |
| B | 必ず `resolve` してから | 道が 1 つ | 消すために取り込みの GET と 2 段がもう 1 回要る |

- `_ledger_for(op="delete")` は `published` に加えて `conflict`（理由が上の 2 つ）と `no_follow` を受ける。`entry_missing`・`published_elsewhere` は受けない（`delivery_state_conflict` の文に「`thth conflict … resolve --gone`」）。
- **戻し先**: 今の `BEFORE["delete"] = "published"` を、**台帳の inflight の前の状態**にする（`deliveries.state_before_inflight(record)`: history を後ろから見て `inflight`・`unknown` でない最初の行の状態）。4xx で断られた削除・人の「出ていない」で `conflict` が `published` に化けない。`throw_chosen` の `BEFORE[op]` の 2 か所と `resolve` の 2 か所（627・654 行）をこれに替える（create・update は今と同じ値になる）。
- timer は delete の前に読み戻さない（今のまま）。

### 5.5 衝突の見せ方

- `thth deliveries` の 1 行: `conflict（readback_changed・本文/題・10/21 08:50）`／`conflict（entry_missing）`／`no_follow`（`_row` に `conflict_reason`・`conflict_detail`）。
- `delivery_held`（承認済みの原稿が `delivery_state_conflict` で止まっている）の `summary` に「`thth conflict <口座> <dl>` で解く」を添える。
- `thth morning`・`board`: 既存の held の行で出る（`delivery_state_*` は `invalid` の区分・変えない）。`conflict` の配信そのものの数 `deliveries_conflict_count` を板に足す（原稿が無い衝突＝`check` で見つけたものも見えるように）。
- 告知（S4）: `conflict` の配信を待つ告知は held（`target_conflict`）のまま。`--adopt` で `published` に戻れば出る。`--gone` なら `target_deleted`・`--no-follow` なら `target_no_follow`（S4 の形のまま・URL は変わらないので出してよいが、追従をやめた記事を告知するかは人が見る）。

### 5.6 外での手直しの検出を広げる（題・カテゴリ）

timer の update の 3（`throw_chosen`）は `get_entry`（本文だけ）を `read_entry`（dict）に替え、本文の sha に加えて **題とカテゴリ**を台帳の `title`・`categories` と比べる（台帳に無ければ比べない）。違えば `conflict`（`readback_changed`・行に `detail: ["title"]` など）。正規化は指紋と同じ（題: `.strip()`・連続する空白を 1 つに。カテゴリ: `.strip()`・空を除く・集合として比べる）。`base_readback_sha`（指紋の 6 番）は**本文だけのまま**（指紋を変えない）。

はてなが題やカテゴリを変えて返す（空白・並び）なら偽の衝突が出る。実機の 36（§14）で確かめ、出るなら正規化を足す（conflict にする線は変えない）。

## 6. burst の数え方（決めること 4）

### 6.1 比べた案

| 案 | 数え方 | 「公開 → 更新 → 削除」 | 「3 本の記事を続けて公開」 | 「1 本を 20 回更新」 |
|---|---|---|---|---|
| A（今） | 操作 1 回を 1 件 | 口座 3 件/10 分で **止まる**（記録の 13） | 止まる（4 本目） | 止まる |
| B（推し） | **同じ配信への操作は、窓の中で 1 件**（鍵は `delivery`）。別の配信は別々 | 1 件 → 止まらない | 止まる（4 本目・今と同じ） | burst では止まらないが、**日の上限（更新は `daily_max_posts` に入る・口座 3／主体 6）で止まる** |
| C | 更新と削除を burst に数えない | 止まらない | 止まる | 止まらない（日の上限だけ） |
| D | 上限の既定を上げる（口座 10/10 分） | 止まらない | 11 本目まで止まらない | — |

**B にする。** 理由: burst の目的は「急な連投で口座を止める」（`guard.py` の docstring）で、同じ記事を直す・消すのは連投ではない。安全側を崩さない根拠: (1) 窓の中で触れる**別々の配信**の数は今と同じ 3 まで。(2) 同じ配信を繰り返し更新する暴走は、更新が `daily_max_posts` に入っている（S1 §4.2・変えない）ので日に 3（口座）・6（主体）で止まる。(3) create → delete → create … で新しい配信を作り続ける暴走は、配信が別なので 4 本目で止まる。C は 1 本を何度も更新する暴走を burst で止められず、D は別の記事の連投を緩める。

### 6.2 実装

- `guard._classified()` の返りに **`key`** を足す: はてなの `entry_*` の行は `("delivery", <delivery>)`（`delivery` が無い古い行は `("post", post_id)`）、ブックマークの行は `("bm", post_id)`、SNS の行は `("post", post_id)` と `("retract", post_id)`（**SNS は今と同じ数**・公開と削除は別の件）。
- `summary()["recent"]`・`principal_summary()["recent"]` は窓の中の**鍵の種類の数**（`len({key …})`）。`burst_slot()`（返信の順番待ち・SNS だけ）は変えない。
- 日の数え（`posts_today`・`retracts_today`・`blog_today`・`bookmarks_today`）は今のまま（操作 1 回を 1 件）。
- docstring の「直近 `burst.minutes` 分の公開と削除の合計」に「同じ配信（はてな）は 1 件」を足す。
- 前提が変わる点: レーンが 1 日に 2 本以上出して、それぞれを直す運用になれば、`daily_max_posts` の既定（口座 3）を雛形で上げるか、更新を別の枠（`daily_max_updates`）に分ける。4.0 では分けない（`GUARD_DEFAULTS` の鍵は SNS の口座と共有していて、増やす影響が広い）。

## 7. SNS の告知との関係（決めること 5）

- **記事を更新しても告知は追従しない。** 計画 §3.5「SNS の告知は書き換えない。訂正か追記を人が選ぶ（候補は出す）」のとおり。告知は SNS の口座の公開物で、THTH の SNS の投稿は編集しない（媒体にも編集の口が無いものがある）。
- 「候補を出す」は `thth article diff` と更新の run のログの 1 行: `この記事の告知 2 件（kopicha-threads 10/20 08:31 …）は書き換えません。訂正や追記を出すなら、その投稿への返信の原稿（reply_to）を書いてください`。THTH は返信の原稿を作らない（文は LLM が書く・S4 §9 と同じ線）。
- 記事を**消した**（`deleted`・`--gone`）あとの告知は、`thth deliveries --article` と `article diff` の告知の行に `→ 記事は消えています` を添える。取り下げるかは人が選ぶ（`thth retract`）。
- `no_follow` の状態は**はてなの配信**（§5.3）のためのもの。約束 §3 の「SNS の告知など」は S4 で告知が台帳の外に出たので、告知には使わない（§13 の 2）。

## 8. 予約の取り消しと止め・結果不明の照合（決めること 6）

### 8.1 取り消しと止め（計画 §3.7）

S1 で入っている（`thth revoke`・/activity の `cancel_schedule`・主体の止め）。S5 で足すのは縛りだけ:

- 承認済みの `op: update`／`delete` の原稿を `thth revoke`（か /activity）で draft に戻すと、台帳は `published`（か `conflict`）のまま・timer は PUT／DELETE を打たない（T-S5-8a）。
- 主体を止めると、更新・削除・`conflict check`・`resolve --adopt` の GET は**打たない**（`check`・`resolve` も `guard.check(kind="entry_update")` の止めの段だけを通す。数は見ない——読む側なので）。

### 8.2 孤児の `wanted`（S1 監査 5）

`approve --confirm` が台帳を作ったあとに書き戻しが失敗すると、原稿の無い `wanted` が残る。これは既に「取り消した予約の配信」と同じ扱い（`delivery_unknown` の文「create で書けるのは取り消した予約の配信だけ」）で、**次の create の原稿に `delivery:` を書けば使える**。S5 は掃かない。`thth deliveries` の 1 行に `wanted（原稿なし・create で delivery: を書けば使える）` を出すだけ（`queue_file` の原稿が無い・あっても `delivery` が違う、で判定・読むだけ）。

### 8.3 結果不明の記事の照合（記録の 10・S1 §8.2 の「S5 の reconcile」）

実機で、書き込みの時間切れで `unknown` になった記事が実際にははてなに届いていた。THTH は出し直さず止まり（正しい）、人が一覧から `entry_id` を拾って解けたが、拾う作業が手だった。

| 案 | 形 | 利点 | 欠点 |
|---|---|---|---|
| A（推し） | **`thth inflight <口座>`（show）のはてなの枝が一覧（`_list`・1 頁 7 件）を読み、候補を見せる。解くのは人（`resolve --published <entry_id>` の命令をそのまま出す）** | 見つける手間が消える。解くのは今の 2 段のまま（`entry_id` を間違えると以後の更新・削除が別の記事に向く） | 自動では解けない |
| B | 次の run が一覧を読み、題・時刻・本文の sha が全部合えば自動で `published` に解く | 人が要らない | `readback_differs`（はてなが本文を変えて返す）があると本文の sha が合わず、題と時刻だけで決めることになる。`entry_id` の取り違えは取り返しがつきにくい |
| C | 何もしない | — | 記録の 10 がそのまま |

**A にする。** B は実機で「読み戻しは常に同じ」と分かってから（§14 の 38）。

- 候補の決め方: inflight に `delivery` がある口座で、一覧の各記事について (a) **題**が原稿の `title`（正規化は指紋と同じ）と同じ、(b) `published` が inflight の `started` の −2 分〜＋30 分、(c) 本文: `hatena_body_sha256(content)` が送った本文（`sent/` には無い——送る前に落ちているので、`material(fm, ledger=before)` と `_rebuild_body_sent` で組み立て直す・`resolve` と同じ）と同じか。(a)(b) が合えば候補、(c) も合えば「本文も同じ」。update の inflight は一覧でなく台帳の `entry_id` を `read_entry` して (c) と `edited` の時刻を見る。
- 表示: `候補 1 件: entry_id tag:…-9876543210（題「…」・公開 10/17 11:18・本文も同じ）→ thth inflight <口座> resolve --published tag:…-9876543210 --by <名前>`。0 件なら「一覧の 7 件に合う記事はありません（0 件なら --not-published・一覧より古ければ画面で確かめて --published）」。GET が失敗したら「照合できませんでした（<符丁>）」で今の表示に倒す。
- `inflight_cli._next_step` と `summary` の文: はてなの inflight（`delivery` あり）では「3.3.1 より前の inflight」などの SNS の文を出さず、「はてなの配信 dl_…（結果の行 seq n）。一覧の候補: …」の形にする。
- 遠くの道の `inflight_status` も同じ候補を返す（`candidates[]`）。GET 1 回。
- 自動の照合は run に入れない（`inflight_resolve` の SNS の自己解決は触らない）。

## 15. masaru に伺うこと

1. **burst の数え方を「同じ配信への操作は窓の中で 1 件」に変えてよいか。** 推し: **変える**（§6）。理由は、1 本の記事を「公開 → 直して更新 → 消す」する運用が口座を止めるのは安全装置の目的（連投を止める）から外れていて、別の記事の連投（4 本目）は今までどおり止まり、同じ記事を繰り返し更新する暴走は日の上限（口座 3・主体 6・更新も数える）で止まるため。代わりの形は「今のまま、口座ごとに `burst` を雛形で上げる（例 6/10 分）」——これだと別の記事の連投も 6 本まで通る。前提が変わる点: 更新を日の上限から外す（`daily_max_updates` を分ける）ことになったら、同じ記事の繰り返しを burst で見る必要が戻るので、鍵を「配信＋操作の種類」にする。
2. **削除を `conflict`（外で手直しされた・別の記法で出た）のまま承認できてよいか。** 推し: **できる**（§5.4・1 段目に「手直しも消えます」）。理由は、消す意思は衝突とは独立で、手直しを残したいなら先に `--adopt` して記事に写す道があるため。代わりの形は「必ず `resolve` してから」（GET と 2 段がもう 1 回）。前提が変わる点: レーンの LLM が衝突の記事を人に見せずに消す事故が起きたら、「必ず `resolve` してから」に戻す（`_ledger_for` の 1 行）。

ほかは推しで決めた（検出は読むだけで HEAD と比べる・更新の原稿は THTH が文面を出して LLM が保存する・台帳に `title`・`categories` を記録する・何も変わっていない更新は断る・上書きは「取り込む → 承認し直す」の 2 重の承認・題とカテゴリの外での変更も `conflict`・`check` は手で打つ・結果不明の照合は候補を見せるだけで自動で解かない・告知は追従しない・孤児の `wanted` は掃かない・MCP に 3 つの道具を足す）。
