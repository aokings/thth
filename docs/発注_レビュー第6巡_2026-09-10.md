## THTH は何か（前提）

4 つの Threads アカウント（nigamilab・asmon 関東・kopicha・運営者個人）に、
**予約投稿を出す基盤**。VM（Ubuntu）で systemd timer が 10 分刻みに回る。

**設計の中心はこれ 1 つ。**

> **masaru が見たものだけが出る。**

投稿の本文は利用者の git repo（プロジェクトごとに別 repo）の
`docs/sns/queue/*.md` に front-matter 付きで置かれる。THTH はその repo を
`pull --ff-only` で同期し、**同期を確認した commit の中身と 1 バイトも違わない
ファイルだけ**を候補にする。

## 過去 5 巡が見つけた穴の「形」

**5 巡すべて同じ形だった。「確かめたい事実」ではなく「その隣の事実」を確かめていた。**

| 巡 | 何を確かめていたか | 本当に必要だったこと |
|---|---|---|
| 2 | pull が成功した | **origin が存在する** |
| 3 | git コマンドが失敗しなかった | **同期の成功を積極的に確認する**（fail-closed に反転） |
| 4 | `HEAD == @{u}`（commit の一致） | **これから読むファイルの一致** |
| 5 | HEAD の中身と一致 | **同期を確認した OID の中身と一致**（HEAD は動く） |

**規約 12 として記録してある: 確かめたい事実そのものを確かめる。近い事実で代用しない。**
今回もこの形の穴が残っていないかを疑ってほしい。

## 今回の範囲で変わったこと

### A. 承認（`thth approve`）— **公開の経路に直接効く**

1. **二段確認になった。**`--confirm` 無しで呼ぶと**出す本文の全文と digest を表示して
   何も書き換えずに終わる**（exit 1）。`--confirm <digest>` で承認。
   digest は `approved_sha`（本文＋account＋reply_to＋topic＋publish_at の sha256）の先頭 12 桁。
2. **複数本をまとめて承認できる。**ファイルを並べても、**ディレクトリ**を渡してもよい
   （ディレクトリなら `status: draft` の `.md` だけが対象）。複数のときは
   **束の digest** を 1 つ出す＝各 `approved_sha` を**並べ替えて連結**した sha256 の先頭 12 桁。
3. **1 本でも lint に落ちる・`post_id` が付いていれば、1 本も承認しない。**
4. **承認が repo の同期を自分で行う。**clone ロックを取り、`sync_repo()` を通してから
   検査・書き込み・commit・push。
5. **`--by` が必須**（`THTH_ACTOR` でも可）。`approved_by` を front-matter と commit に残す。
6. 予定時刻を過ぎた原稿に警告を出す（`stale_days` 超なら「承認しても出ません」）。

**攻めてほしい筋:**

- **一段目で見せたものと、二段目で承認されるものが違う状態**を作れるか。
  本数が増えたとき・ディレクトリ渡しのとき・段の間に remote が動いたときを含めて。
- **束の digest を回避できるか。**部分集合・上位集合・並べ替え・重複を渡す、
  段の間にファイルを足す／消す、など。
- **同期（4）が段の間に何を持ち込むか。**一段目の pull と二段目の pull の間に
  remote が変わった場合の挙動。

### B. 取り消し（`thth revoke`）— 新規

`status` を `draft` に戻し、`approved_sha`/`approved_at`/`approved_by` を空にし、
`revoked_at`/`revoked_by`/`revoked_reason` を残す。**本文には触らない。**
clone ロックを取る。`post_id` 付きは断る。

**攻めてほしい筋:** 公開の最中に割り込めるか。取り消したものが出ないか。
取り消しの push が失敗したときに「止まったつもりで出る」ことがないか。

### C. 収集（`thth collect`）— 新規・**利用者 repo に書く**

投稿からの経過時間の刻み（1h・6h・24h・72h・7d）を跨いだら、数（insights）と返信を
1 回読んで 1 行足す。**追記のみ・冪等**（同じ刻みを二度書かない）。
`thth run` が投稿のあとに必ず呼ぶ。clone ロックを取り、`sync_repo()` を通してから書く。

置き場（利用者 repo）:
- `data/sns/insights/posts/<post_id>.ndjson`
- `data/sns/replies/<post_id>.ndjson`
- `data/sns/insights/account/<account>-YYYY-MM.ndjson`（前日の閉じた 1 日）

**統括が自分で疑っている筋（未検証・ここを優先してほしい）:**

> `collect` が commit に成功して **push に失敗**した場合、`HEAD != @{u}` になる。
> すると**次回以降の `sync_repo()` が落ちるので、投稿そのものが止まる。**
> しかも刻みは記録済みなので、その刻みは二度と採られない。
> **採取の失敗が投稿を止める**設計になっていないか。fail-closed ではあるが、
> 「採取は部分的な成功を許す」という意図と矛盾する。

### D. 自己更新（`thth/selfupdate.py`）

`thth run` が app 自身を `git pull --ff-only` し、進んでいたら 1 回だけ exec しなおす
（`THTH_SELF_UPDATED` で無限ループを防ぐ）。**2026-09-10 に実際に衝突したので
`state/_app.lock` を足した。**exec は lock を放してから行う。

**攻めてほしい筋:** 3 つの timer と手動実行が重なったときに、古いコードで走り続ける／
二重に更新する／lock を握ったまま exec する、が起きないか。

### E. 書き戻し（`writeback.commit_and_push`）

**複数パスを受けるようになった。**`git add -- <paths>` のあと
**`git commit --only -m <msg> -- <paths>`**。
（第 5 巡で「素の `git commit` が無関係な stage 済み変更を巻き込む」と指摘されたため）

**攻めてほしい筋:** `--only` が index の他のエントリを本当に残すか。
rebase 中・merge 中に呼ばれたときの挙動。
