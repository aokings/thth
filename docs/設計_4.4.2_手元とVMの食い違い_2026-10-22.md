# 設計の叩き台: 4.4.2 手元と VM の食い違い（2026-10-22・THTH開発 第8）

元: [計画_4.4_利用者の不満](計画_4.4_利用者の不満_2026-10-21.md) の 4.4.2 行（重なる不満 ①・5 窓口）。決めること: 範囲と、③（承認のほかの書き戻しを台帳に移すか）。

## 今の作り（読んで確かめた。行は 7ac32f8）

- **push 直後に断られる理由**: `thth approve` は先に `_expand_targets`（cli.py:672）でパスを探し、見つからなければその場で「VM の repo に無いパスです」と断る。取り込み（`sync_repo`、fetch と `merge --ff-only`）はそのあと（cli.py:704）。つまり取り込めば通るのに、取り込む前に断っている。`thth lint` は取り込みをしない。
- 取り込みは各 run の中（timer 10 分）と `thth pull` だけ。`queue`・`board` は取り込まず、遅れを `behind_remote` で見るだけ。
- 手元（Mac）の `thth` は 2 通り: ssh の薄い包み（引数をそのまま VM へ。**ファイルの中身は送らない**）と、4.0 の remote（thth.me 経由。`send --text-file` は手元で読んで本文を送る）。`lint`・`approve` は remote の対象外で、ssh の包みを通る。
- VM が利用者の repo に書くもの: 投稿の `status: posted`（core.py:1513）・スレッドの段・取り下げ・はてなの公開記録・incident・収集（返信・反応）・burst の順番待ち・サーバの下書きと画像。どれも今の枝の upstream へ rebase して push。

## 推し（4.4.2 に入れるもの）

1. **lint・approve は、パスが見つからなければその口座の repo を取り込んで 1 回だけ探し直す**（旗なし・自動）。取り込みは今の `sync_repo` のまま（ff だけ・失敗なら断る）。Mac のパスも、今ある読み替え（`_translate_local_path`）のあとで同じく取り込んで探し直す。
2. **断りに次の一歩を並べる**: 取り込んでも無いとき「VM は <sha>、remote は <sha>。push は済んでいますか」。`send --text-file` に Mac のパスが来たら「標準入力なら通る（`thth send … < ファイル`）」と、ssh の道。
3. **読むだけの命令（queue・board）**: remote より遅れていたら「取り込み待ち（VM <sha>／remote <sha>、次の取り込み HH:MM）」と出し、unverified_content を壊れたように見せない（こぴちゃ 8）。
4. **③ は移さない**（今のまま利用者の repo に書く）。理由: `status: posted` などは h2d・各窓口の posted.md・lint が repo から読んでいて、移すと 7 窓口の読み方が変わる。VM 側は push の前に rebase するので、食い違いの多くは 1・3 で消える。MMR 10（Mac の push が非早送り）は普通の git の pull で解けるので、断りの文で案内する。

前提が変わったら: 窓口から「VM の commit で Mac の push が何度も止まる」が続くなら、③ を移す（別の枝 `thth/records` か台帳）方へ倒す。その代償は、窓口の読み方の変更と知らせ直し。

## 入れないもの（4.4.3・4.5 へ）

- 手元のファイルを VM へ送って lint・approve する口（`lint`・`approve` を remote に載せる）: 承認の digest を VM で取るので中身の送り方の設計が要る。1 で push 済みの大半は通るので後回し。
