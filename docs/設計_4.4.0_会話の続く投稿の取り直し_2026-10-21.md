# 設計 4.4.0 会話の続く投稿の取り直し（2026-10-21）

依頼: kopicha 本線（こぴちゃ 第3）の `docs/sns/依頼_返信の起こしの遅れ_2026-10-21.md`（kopicha の repo）。

## 起きていたこと

THTH は自分の投稿の返信を、投稿からの経過時間の刻み（`REPLY_MARKS_HOURS` ＝ 1・6・24・72・168 時間・`thth/collect.py`）でしか採っていなかった。刻みの間に付いた返信は、次の刻みか手の `thth replies --refresh` まで台帳に入らない。h2d は台帳の「返していない返信の数」（`thth observe <口座> --json --no-mark --counts-only --no-world`）を 15 分ごとに読んで担当を起こすので、台帳に入らない返信は知りようがない。10/21 朝の kopicha-threads では、05:40 ごろの返信が台帳に入ったのは 08:10 の手の取り直しで、起こしは約 2 時間半遅れた。

## 決めたこと

`thth run`（10 分ごと）の採取（`collect_once()`）の中で、**会話が続いている投稿**だけ、刻みとは別に、前の取得からおおむね 20 分たったら会話を取り直す。中身は `thth/reply_follow.py`、取りに行く所は `collect._collect_follow()`。

- **会話が続いている**: 投稿から 48 時間以内、または直近 48 時間に返信が付いた投稿。返信は、台帳の返信の行の時刻（媒体の `timestamp`）と、自分が THTH から返した記録（`state/<口座>/sent/` の `reply_to` と `sent_at`）の両方を見る。自分の返信そのものも 1 本の投稿なので、48 時間以内なら自分の返信の枝も取り直す（Threads は `branch_replies`）。窓は `collect_days`（既定 14 日）の内だけ。
- **性質は `--refresh` と同じ**: 刻みを見ない・**刻みを進めない**・数（insights）を読まない。1h・6h・24h の数と刻みの記録は変わらない。新しく見つけた返信は台帳に入り、unanswered の数に効く。
- **新しい返信が無い取り直しは、利用者の repo に何も書かない。** 返信の台帳（利用者の repo の `data/sns/replies/…`）に書くのは、新しい返信が見つかった回だけ（返信の行と、`marks: []`・`trigger: "follow"` の取得の行）。書いたものは今の刻みと同じく採取の後段で「収集」の commit になる。新しい返信が無い回まで取得の行を書くと、会話の続く口座では 20 分おきに利用者の main に commit が積まれ、main の先頭がずれて承認の target が通らなくなる（10/21 に 4 回起きた不満と同じ形）。masaru 10/21「THTH の記録は VM の台帳に持ち、利用者の repo には積まない」に合わせた。
- **同じ回に 2 度読まない**: その回に刻みで返信を取る投稿は、取り直しの候補にしない。
- **前の取り直しの時刻は VM の state に持つ**: `$THTH_ROOT/state/<口座>/reply_follow.json`（`{"last": {post_id: 時刻}}`・取り直しが成功した時刻・`live_hours` の 2 倍より古い行は書くときに落とす）。20 分の判定は、これと返信の台帳の取得の行（`kind: fetch`・刻み・refresh・follow を問わない）の新しいほうから数える。state が壊れている・形が違う・読めないときは空として扱い log に 1 行（採取は止めない。空なら台帳の取得の行だけで数えるので、取りすぎは高々 1 回）。書けないときも log に 1 行で採取は続ける。取り直しに失敗した回は時刻を残さないので、次の回（10 分後）にまた取りに行く（刻みの失敗と同じ扱い）。
- **API の回数の柵**: 1 回の run で取り直すのは最大 10 本。並べ方は「いちばん新しい動き（返信の時刻・自分の返信の時刻・投稿の時刻のうち最も新しいもの）」の新しい順。古い順ではない。
- **失敗の扱い**: 取り直しの失敗は採取の `errors` に入れない（採取の終了コードも投稿の道も悪くしない）。理由は log に 1 行（「返信の取り直しができませんでした（次の回で取り直します）」）。

## 台帳の設定（口座ごと・任意）

```json
"reply_follow": {"enabled": true, "every_minutes": 20, "live_hours": 48, "max_posts": 10}
```

どの鍵も省略でき、省略すると既定（上の値）。`every_minutes` は 5〜1440、`live_hours` は 1〜720、`max_posts` は 0〜50（0 は切る）。形が違えば台帳の読み込みで断る（`invalid_reply_follow`）。

## 媒体

- Threads・Bluesky・Mastodon: 既定で対象。
- **X: 既定で外す。** X の枝の読み取りは他人の投稿の読み取りで、返ってきた投稿 1 本ごとに 0.005 USD の従量（`thth/adapters/x.py`）、回数の上限も厳しい。20 分おきに読むと 1 本の投稿の 48 時間で 144 回になる。設計 2026-10-08 は「timer・見張り・自動の返信には使わない」としている。台帳で `"reply_follow": {"enabled": true}` と明示したときだけ、THTH から出した自分の投稿（`sent/` に記録があり取り下げていないもの）に限って、1 回 10 本（`CONVERSATION_MIN`）で読む。読みの予算（`budget_x`）の外では読めず、その断りは取り直しの失敗として log に出るだけ。

## webhook の口の調べ（2026-10-21・公式資料）

- **Threads: ある。** [Threads Webhooks](https://developers.facebook.com/docs/threads/webhooks) の `replies`（自分の投稿への返信）・`mentions`・`publish`・`delete`。`replies` に要るのは `threads_basic` と `threads_read_replies`、アプリの App Review、権限の Advanced Access（無いと通知が届かない）、事業者の確認、受け口の URL（公開の https・Meta のサーバーからの確かめの token）、アプリでの購読の設定。非公開の口座には返信の通知が来ない。THTH で使うなら受け口は thth.me の Worker になり、Meta の審査が要る（申請の状況は masaru の領分）。
- **Mastodon: 利用者向けには無い。** [Webhooks](https://docs.joinmastodon.org/admin/webhooks/) は管理画面（Administration）で設定するサーバー管理者の口で、事件は `account.*`・`report.*`・`status.created`/`updated`。他所のサーバーの口座が受け取る返信の通知の口ではない。代わりは利用者の [streaming](https://docs.joinmastodon.org/methods/streaming/)（常時つなぐ WebSocket・timer の形と合わない）。
- **Bluesky: 無い。** 押し出しの口は [firehose／Jetstream](https://docs.bsky.app/docs/advanced-guides/firehose)（常時つなぐ WebSocket・網全体の流れを絞って読む）で、webhook ではない。

4.4.0 で作るのはポーリングだけ。Threads の webhook は、審査と受け口（Worker）の段取りが揃ったら別の版で考える。
