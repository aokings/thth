## 何が変わったか

### Worker（`callback/src/approval-object.js`・`callback/src/approval.js`）

- session `create` の body に **任意の `attachments`**（配列・最大 20）と **任意の `typed`**（文字列・16 KiB 以下）を受ける。既存 8 key は必須のまま、余分な key は `attachments`／`typed` 以外すべて 400 `invalid_request`。
- `attachments` の 1 行は閉じた key 集合 `{index, role, kind, format, public_sha256, public_size, width, height, duration, alt, preview}`。`index` は 1〜1000 の整数、`role` は `media|thumbnail|caption`、`kind` は `image|video|audio|caption`、`format` は `[a-z0-9]{2,16}`、`public_sha256` は 64 hex、`public_size` は非負整数、`width`／`height` は null か 0〜1,000,000 の整数、`duration` は null か 0〜86,400 の有限数、`alt` は 4096 文字以下、`preview` は null か 43 文字の capability（**`kind` が `image` のときだけ非 null を許す**）。
- 保存は本文・context と同じ session 行（同じ 600 秒の論理期限）。`view()` だけが返し、`clear()`（承認・失効・受領）は従来どおり receipt binding と期限しか残さないので、**`status`／`consume`／保存行には出ない**。
- ページは本文の `<pre>` の直後に一覧を出す。画像は `<figure><img src="/m/<capability>" alt="…"><figcaption>添付 N: JPEG 1200×800 · sha abababababab · alt: …</figcaption></figure>`、動画・音声は `<p>添付 3: 動画 01:12 · sha efefefefefef · alt: …</p>`、字幕は `<p>字幕 (ja) sha 343434343434</p>`、型付き添付と `post_options` は `<p>型付き添付／公開設定</p><pre>…</pre>`。すべて既存の `escape` を通す。script も inline event handler も無い。
- CSP は `img-src 'self'` を足すだけ（`default-src 'none'`・`style-src 'unsafe-inline'`・`form-action 'self'`・`frame-ancestors 'none'`・`base-uri 'none'`・`no-store`・`no-referrer` は従前）。`<img>` の見た目のために `figure`／`img`／`figcaption` の inline style を 1 行足した。
- `/m/<cap>`（`purpose=preview`）は第 4 段のまま。読んで確認した: `MediaObject.view()` は `kind` が `preview|provider`・`status==='ready'`・`now < expires_at` のときだけ `row.mime` の `Content-Type`（`no-store`・`nosniff`・`no-referrer`・`default-src 'none'; sandbox`）で本体を返し、期限後は 410 `media_expired`。レート制限は `MEDIA_PUBLIC_LIMIT`（送信元ごと毎分 120）で、1 ページ 20 枚は収まるので `wrangler.jsonc` は変えていない。

### VM（`thth/approval_jobs.py`・`thth/server_writes.py`）

- `server_writes.prepare()` に `media_out=` を足した（**表示専用**の受け皿。binding も digest も変わらないので、`_perform()` の `prepare(...) != binding` 比較はそのまま成立する）。`approval_request` の `media_approval_ui_unavailable` の拒否は削除（`retract_request` は無関係・`send_request` は本文だけなので元から添付を持たない）。
- `approval_jobs.create()` は job JSON を durable に書いた**後**、Worker への最初の request の**前**に添付を用意する（既存の「意図を先に残す」順序を守る）:
  1. `media.prepare(repo_dir, front_matter, medium)` を開き直し、`prepared_component` が承認時の manifest と 1 文字も違わないことを確かめる（違えば `approval_stale`）。
  2. 画像 1 枚ごとに `MediaRelay.upload_prepared(item)`（`kind=sanitized`）→ `MediaRelay.grant(item, source, purpose='preview')`。grant の `subject` が `/m/<cap>` の capability。
  3. upload の subject を job JSON の `media_subjects: {"<files の位置>": subject}` に残す。
  4. 動画・音声・字幕は upload も grant もしない（文字だけ）。
- **一件でも失敗したら session を登録しない。** job は `failed`／静的理由 `media_preview_unavailable` で残り、要求も同じ理由で止まる。途中まで取れた upload subject も記録してから止める。
- Worker へ送る 1 行には repo 内のパスも `source_sha256` も入れない（契約の閉じた key 集合だけ）。`typed` は manifest の `{attachments, post_options, captions}` の canonical JSON（`sort_keys`・区切り無し・`ensure_ascii=False`）で、どれも空なら送らない。
- `_public(job)` の白名単は変えていないので `media_subjects` は `request_status` に出ない。capability は job JSON にも入れていない。

### 設計判断（依頼書に明記が無く、こちらで決めたもの）

1. **静的理由は `media_preview_unavailable`。** 依頼書 §第 8 段の本文は `approval_registration_unknown` で止めると書いているが、それは「登録したかどうか分からない」を意味する既存の理由で、preview の失敗は「登録していないと分かっている」。指示（親からの task）に従い新しい静的理由を足した。`REASONS`・`SAFE_ERRORS` の両方に入れてある。**どちらの綴りで運用するかは masaru の一言待ち**（片方に寄せるのは 1 行）。
2. **承認時の upload は公開時の upload と共有しない。** `kind='approve'` の承認は原稿に `approved_sha` を書いて commit するだけで、実公開はその後の別実行（`run`／`send`）で起きる。R2 の sanitized は 600 秒しか生きないので、承認時の subject を公開時に使い回すことは原理的にできない。依頼書の許す「二重 upload にして follow-up」を選び、手掛かりとして `media_subjects` だけ残した。公開経路（`threads_media.py:246`）は従来どおり自分で upload する。
3. **preview の寿命は session よりわずかに短い。** Worker は preview の期限を `min(VM の希望, sanitized の期限)` に丸め、sanitized は upload 時刻 + 600 秒。upload は session 登録の直前なので、画像は session の失効より upload 所要時間（数秒）だけ早く 410 になる。「session より長く」することは、承認前に bytes を置く以上できない。文書に明記した（本文・digest・承認ボタンは 600 秒まで有効のまま、画像だけが先に消える）。
4. **`index` は manifest 行の index、`media_subjects` の key は `files` 配列の位置。** 同じ index が role 違いで並ぶ（media 1 と thumbnail 1）ため、subject の key だけは位置にした。
5. `attachments` が空配列でも（投票だけの原稿など）`typed` は出す。
