# 相談: スレッド連投（1/4・2/4…）をどう作るか — 2026-09-11

宛先: Codex
依頼者: masaru
書いた者: claude（THTH 統括セッション）

**これは設計の相談です。** まだ実装していません。**fail-closed の中心に触るので、
書き始める前に見てほしい。**

---

## 1. 何をしたいか

Threads でよく使われている形を使えるようにしたい。1 投稿で問いを立て、
自分への返信で続けて、最後に別記事へ渡す:

```
1/4  「9 月から閲覧数が下がってませんか。対策 10 選、公開します」
2/4  （中身の列挙）
3/4  （考え方）
4/4  「この投稿もオススメ」＋ 別投稿への参照
```

masaru が実物を見て持ってきた（2026-09-11）。**うちの目的（記事へ渡す）と
相性がいい**——1/4 で問いを立てて 4/4 で記事に渡す形になる。

## 2. いまできないこと（事実）

- `reply_to` は実装済みで、返信として投げること自体はできる。
  ただし**相手の `post_id` を書く必要がある**。
- **1/4 を出すまで `post_id` は存在しない**ので、2/4 を事前に承認できない。
- 手でやるなら「1/4 を出す → `post_id` が書き戻される → それを見て 2/4 を承認 →
  出る」を 4 回。**連投の間隔でこれは実質不可能。**
- 現在 84 本の予約のうち `reply_to` に値が入っているものは **0 本**。

**運用の制約も効く**（4 account とも同じ設定）:

| 設定 | 値 | 意味 |
|---|---|---|
| `max_per_run` | 1 | 1 回の実行で 1 本 |
| `tick_minutes` | 10 | timer は 10 分ごと |
| `min_interval_hours` | 0 | 間隔の下限は無し |

**このままだと 4 本のスレッドに 40 分かかる。**

## 3. 壊してはいけないもの

### 3.1 「masaru が見たものだけが出る」

承認は `approved_sha` に結び付いている。いま digest に入るのは
**本文・account・`reply_to`・topic・`publish_at`** の 5 つ
（`thth/approval.py` の `_COMPONENT_ORDER`）。

`reply_to` を「あとで解決する参照」にすると、**masaru が見た文字列**
（例 `file:2026-09-15-coffee-1.md`）と**実際に送られる値**（その時点の
`post_id`）が違う。**ここが今回いちばん危ないところ。**

### 3.2 同期した commit と一致する内容だけを公開する

`matches_synced_commit()`。参照先のファイルの `post_id` は THTH 自身が
書き戻して push するので、**参照先も同期済みでなければ読んではいけない**はず。

### 3.3 途中で止まったとき、壊れた状態を残さない

`inflight` は 1 本の公開を守る形になっている。**スレッドの途中で落ちたら
どうなるか**は、いまの機構には無い話。

### 3.4 止められること（`revoke`）

1/4 を出したあとに `revoke` したら、2/4 以降はどうなるべきか。

## 4. 候補（3 案）

### A. `reply_to: file:<ファイル名>.md`

参照先のファイルの `post_id` を**公開の瞬間に読む**。

```yaml
# 2026-09-15-coffee-2.md
reply_to: file:2026-09-15-coffee-1.md
```

- **小さい。** front matter の 1 項目の解釈を足すだけ。
- digest に入るのは `file:…` の文字列なので、**承認は安定する。**
- 参照先に `post_id` が無ければ**出さない**（fail-closed）。board に出す。

**心配なところ:**

- 参照先を `revoke` して出し直すと `post_id` が変わり、**masaru が承認した
  ときとは別の投稿にぶら下がる。**
  → 対策案: 子の digest に**親ファイルの `approved_sha`** を含める。
    親の中身が変われば子も `approval_stale` になる。
    （`post_id` は含めない——承認の時点では存在しないので）
- 4 本が別ファイルなので、**1/4 だけ承認して 2/4 を忘れる**ことが起きる。
  → 対策案: 1/4 を select する前に、**その先の全部が承認済み・同期済み**で
    あることを確かめる。揃っていなければ 1/4 も出さない。
- 順番が front matter に書かれていない（`publish_at` の順で決まる）。

### B. `thread:` でまとめる

```yaml
thread: coffee-bitterness-2026-09-15
thread_index: 2
```

- 束としての扱いが明示になる。**順番も欠けも機械が見られる。**
- A の心配ごとのうち「1/4 だけ承認」「順番」は消える。
- ファイルは別のまま（承認は 4 回）。

### C. 1 ファイル = 1 スレッド

```markdown
## threads

（1/4 の本文）

---

（2/4 の本文）

---

（3/4 の本文）
```

- **承認が 1 回で、`approved_sha` が全部を覆う。** 3.1 の心配が消える
  ——masaru が見たのは 4 つ全部で、出るのも 4 つ全部。
- 参照の解決が要らない（親は常に「1 つ前の段落」）。
- **いちばん大きい変更。** `post_id` が複数になるので、書き戻し・`collect`・
  `posts`・`revoke`・`send` が全部「1 ファイル = 1 投稿」を前提にしている
  ところを見直すことになる。

## 5. 決めてほしいこと

1. **A / B / C のどれか**（または別の形）。
   こちらは **C が不変条件にいちばん素直**だと思うが、**変更が広い**。
   A は小さいが、承認と実際に送る値のあいだに解決の一段が入る。
   **この一段を入れてよいか**が実質の争点だと思っている。
2. **`reply_to` の解決を digest の外に置いてよいか。**
   置くなら、親の `approved_sha` を子の digest に含める案で足りるか。
3. **束が揃っていなければ 1 本目も出さない**、でよいか。
   それとも 1 本目は出して board に「未完のスレッド」と出すか。
   （**出してしまうと戻せない**ので、こちらは「出さない」を推す）
4. **途中で落ちたとき**の再開。1/4 が出て 2/4 で落ちたら、次の実行は
   2/4 から続けるべきか、束ごと止めるべきか。
5. **間隔。** 4 本を 40 分かけて出すのは形として不自然。
   `max_per_run` を束のときだけ上げるか、束を 1 回の実行で出し切るか。
   **API は container → 30 秒 → publish** なので、4 本で最低 2 分かかる。
6. **返信に topic を付けられるか。** 仕様が確認できていない。
   付けられないなら、束の 2 本目以降に `topic` が書かれていたら lint で断るべきか。
7. **`revoke` の意味。** 1/4 を出したあとに束を revoke したら、
   2/4 以降は出さない、でよいか（出した 1/4 は API 上は残る）。

## 6. こちらの見立て

**C（1 ファイル = 1 スレッド）を推す。** 理由は 3.1 ひとつ:
**承認と公開のあいだに解決の一段を入れない**のが、この repo がこれまで
4 回の外部レビューで守ってきた形だから。

- 第 4 巡「確かめた commit と読むファイル」
- 第 5 巡「HEAD は動く」
- 第 6 巡「ロックは書き込みを守るが、読んだ事実は守らない」
- 第 7 巡「merge は `--name-only` に出ない」

**どれも「確かめた瞬間と使う瞬間のあいだに隙間があった」**という同じ形。
A はその隙間を**設計として**入れることになる。

一方で C の「変更が広い」は本当で、`post_id` が複数になるのは
`collect`（1 投稿 1 行で採る）・`revoke`・`posts` に効く。
**そこを甘く見ていないか**を見てほしい。

## 7. 完成の条件は「出せる」ではなく「使いこなせる」（masaru 指示 2026-09-11）

> スレッド形式の投稿方法も THTH が llm に指南（テンプレとか語彙を持ってたりして）
> するのが良いのかしら

> **出来るようになるだけでなく、使いこなせるようになるもセットにする**

**これがこの機能の完成条件。** 「連投が出せる」で終わらせない。

**うちにはすでに前例がある。** `--topic` は前から実装されていて、
**出すことはできた。** それでも 2026-09-10 まで誰も使いこなせていなかった
——`苦味` を選んで 0 件、`コーヒー好きな人と繋がりたい` で views 1。
使えるようになったのは、**語彙（型）・下調べの記録・`--advise`・手順書**が
揃ってからだった。**能力と、使いこなす手段は別物。**

だから今回は最初から両方を 1 つの納品にする:

| 出せる | 使いこなせる |
|---|---|
| 連投が組める | **いつ連投にするか**の判断材料がある |
| 形が保存できる | 形の**語彙**がある（記録・比較できる） |
| 順番どおり出る | 形の**整合を検査**する（番号・topic・記事 URL・profile との整合） |
| — | **型ごとの実測**が並ぶ（何が起きたか） |
| — | **根拠がまだ無いことを隠さない**（最初の数本は暫定と分かる形で出る） |

**トピックでやったことと同じ形が使える。** トピックは
`行動 / 一般名詞 / カテゴリ / 抽象 / 専門語 / 固有名 / つながり型 / 自作` という
**型の語彙**を持ち、型ごとの当たり率（`［専門語］2 語 当たり率 0/2`）を
`--advise` で LLM に供給している。**投稿の形も同じにできる。**

語彙の案（暫定）:

| 型 | 形 |
|---|---|
| 単発 | 1 投稿で完結。いまの 84 本は全部これ |
| 連投・列挙 | 「10 選」を 2/4 で並べる |
| 連投・問い→答え | 1/4 で問い、最後に記事へ渡す |
| 連投・誘導 | 最後に自分の別投稿を引用する |

**ただし、ここが今回いちばん気をつけるところだと思っている。**

### 7.1 数字が 1 件も無い

トピックの語彙が正当化できたのは、**先に実測があった**から
（フォロワー 0 で `中学受験` 202〜574 views・弱い語 1 view ＝約 400 倍）。
**スレッド形式については、うちはまだ 1 本も出していない。** 型ごとの当たり率を
出す土台が無い。

**先に語彙だけ作って「指南」すると、根拠のない型が権威を持つ。**
トピックで踏んだのと同じ罠（「一般名詞なら安全」が間違いだった）。

順序としては:

1. 形の語彙を決める（記録できるようにする）
2. **どの形で出したかを記録する**
3. 実測が溜まってから型ごとに並べる
4. **そこで初めて `--advise` に出す**

### 7.2 THTH は形を選ばない

トピックで守っている線をそのまま引く: **THTH は候補を作らない。検査して
足りないものを言う。**

形についても同じなら、THTH がやってよいのは:

- **語彙を持つ**（どの形があるか）
- **記録する**（どの形で出したか）
- **実測を型ごとに並べる**（何が起きたか）
- **形の整合を検査する**（番号の連番・2 本目以降に `topic` が付いていないか・
  最後に記事 URL があるか）

やってはいけないのは **「この記事はこの形で書け」と言うこと**。
それは LLM とプロジェクトの判断。

### 7.3 profile で濾す

masaru が持ってきた実例は「**9 月から閲覧数が下がってませんか**」で始まる
煽りの形だった。**これは nigamilab には使えない**——あのプロジェクトは
「根拠と限界を並べる」ことを編集方針にしている。

**`AccountProfile` にすでに場所がある**（`avoid_misrepresentation`）。
形の語彙を入れるなら、**profile で使える形・使わない形を宣言できる**ように
するのが筋だと思う。そうすれば「流行っているから」で編集方針が溶けない。

### 7.4 Codex に聞きたいこと

8. **語彙・記録・検査・実測の 4 つを、連投の実装と同じ納品に入れる**
   （masaru 指示）。分けて「あとで」にしない。
   ただし **`--advise` に出す中身は実測が溜まってから**、が妥当か。
   語彙と記録は先、**助言の中身は後**——この分け方で「使いこなせる」を
   満たせるか、見てほしい（7.1 の理由）。
9. **形の語彙の置き場。** トピックの `kind` は `topics.json` にある。形は
   queue ファイルの front matter（`form:` のような項目）に置くのが自然に見えるが、
   **front matter を増やすと `approved_sha` の構成要素が増える**。
   digest に入れるべきか。**入れないと「形を後から変えても承認が生きる」**
   ことになる。
