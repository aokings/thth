# 添付を含む原稿の準備（2.13 第1段）

この段階では `lint`・`preview`・`approve` の一段目と `send` の乾式試験で、添付と本文を一緒に確認できます。媒体への upload／公開とブラウザーの添付承認画面は後段です。実送信は `media_provider_unavailable`、サーバーの承認要求は `media_approval_ui_unavailable` で止まり、本文だけに落として公開しません。

## ファイルと承認

`file` は台帳の `repo_dir` を起点にした相対パスです。絶対パス、親への遡り、symlink、hardlink、FIFO は受け付けません。各ファイルに空でない `alt` が必要です。ファイルは自分の原稿 repo に置き、他の実行環境でも使う原稿では画像等も Git へ登録・同期してください。THTH は原稿の承認時に元ファイルを書き換えません。

```yaml
media:
  - file: docs/photos/tea.jpg
    alt: 白いカップに注いだ緑茶
```

`thth: 1` は top-level、`thth: 2` は各 `posts` 項目の `index` の下にこの欄を書きます。添付を持つ段だけ本文を空にできます。添付なしの既存原稿と承認 hash は変わりません。

```yaml
posts:
  - index: 1
    media:
      - file: docs/photos/tea.jpg
        alt: 白いカップに注いだ緑茶
  - index: 2
    media: []
```

`thth send <account> --media docs/photos/tea.jpg --alt '白いカップに注いだ緑茶'` で添付だけの乾式試験ができます。複数指定は同数の `--media` と `--alt` を順番に対応させます。本文を付ける場合は従来の `--text-file` を使います。

承認には本文・既存公開設定に加え、ファイル順、元 SHA256、公開 SHA256、元／公開 byte 数、alt、寸法、秒数、Orientation、型付き設定と字幕 SHA を含めます。元ファイルの metadata だけを変え、公開 bytes が同じになっても再承認が必要です。準備中の bytes は匿名の private snapshot に固定し、元ファイルの差替えも別に検出します。公開用 stream は mutable な原稿ファイルから読みません。

## 形式と metadata

| 形式 | 処理・限界 |
|---|---|
| JPEG | segment/scan 境界を確認。Exif は Orientation の最小 IFD へ再構成。ICC、最小 JFIF の色・pixel aspect、Adobe ColorTransform、圧縮画像構造を保持。XMP/IPTC/comment/thumbnail は削除。未知 APP、ICC なしで解釈を保てない Exif ColorSpace 等は理由付き拒否。 |
| PNG/APNG | chunk 長・CRC・順序と圧縮データ長を検査。Orientation の最小 Exif、ICC、色／透過／animation 構造を保持。text/time を削除。未知 critical／安全性不明の ancillary は拒否。 |
| WebP | RIFF 長・pad・feature flags・再構成 chunk の順序を検査。Orientation の最小 Exif、ICC、alpha／animation を保持。XMP を削除。未知 chunk は拒否。 |
| GIF | 構造だけ検査し bytes は不変。Comment/Application Extension 内の私的情報が除去される保証はありません。 |
| MP4/MOV | bytes 不変。box 境界・寸法・movie duration を読み、位置 key があれば `location_metadata_present`。解析できない metadata track／vendor metadata は `location_metadata_unverifiable`。fragment/edit-list 等で秒数を確認できない構造は `duration_unverifiable`。 |
| その他 | 自動変換しません。`unsupported_attachment: <medium>/<format>` 等の理由で拒否します。 |

この検査は汎用 codec の完全な復号検証ではありません。画像・動画の実 decoder 互換、実媒体の codec／寸法／容量／処理状態と実表示は後段・配布担当の確認対象です。媒体の上限を一律4点等に縮小していません。対応済みの準備処理と媒体での送信可否を分けます。

## ファイル以外の型付き入力

追加欄は厳密な2-space字下げ、または明示 JSON を使います。JSON の重複 key、null による型置換、未知 key は拒否します。投票選択肢や styles の入れ子は JSON 値で書きます。

```yaml
attachments:
  - type: poll
    options: ["温かい", "冷たい"]
    expires_in: 300
    multiple: false
post_options:
  visibility: public
```

- `quote`: `uri`、Bluesky は `cid` も必要。
- `link`: HTTPS `url`、任意の `title`／`description`。Bluesky は両方必須。画像を付ける場合は `thumbnail_file` と `thumbnail_alt` の両方が必要です。内部で説明を確認しても、媒体に alt 欄がない thumb へ alt が送られるとは表示しません。
- `poll`: `options`、Mastodon は `expires_in` 必須。任意の `multiple`／`hide_totals`。Mastodon の media と投票、Threads の投票と link/text は排他です。
- Threads `text`: `text`、任意の HTTPS `link`、`styles`（`offset`／`length`／`styling_info`）。style の媒体上の単位・対応値を推測して変換しません。
- Threads `gif`: `provider` と `id`。任意 URL の代理取得はしません。provider の受理値は後段で確認します。

`post_options` は Mastodon の `visibility/language/sensitive/spoiler_text/quote_approval_policy/focus`、Bluesky の `languages/labels/presentation/gallery/facets`、Threads の `text_spoiler/media_spoiler/ghost/reply_control/reply_approvals` を型検査します。これら全値を承認に含めます。既存の `location_id/reply_to/topic/share_to_instagram` をここへ重複記入することはできません。媒体別の上限・機能可否は後段の provider 検査で確かめます。

Bluesky 字幕は `captions: [{"media_index":1,"file":"docs/ja.vtt","lang":"ja"}]` のように、1から始まるファイルの番号へ結び付けます。UTF-8 WebVTT の境界を検査し、bytes は変えず SHA を承認へ含めます。
