# 添付を含む原稿（2.13 第1〜6段）

`lint`・`preview`・`approve` の一段目と `send` の乾式試験で、添付と本文を一緒に確認できます。第2段では Mastodon の対応する画像・MP4/MOV を upload し、処理完了を確認してから公開します。第3段は Bluesky 画像、第4段は Threads 画像に対応します。第5段は Threads 動画、第6段は Bluesky 動画です。ブラウザーの添付承認画面は後段です。未対応の実送信は `media_provider_unavailable` 等、サーバーの承認要求は `media_approval_ui_unavailable` で止まり、本文だけに落として公開しません。

## ファイルと承認

`file` は台帳の `repo_dir` を起点にした相対パスです。絶対パス、親への遡り、symlink、hardlink、FIFO は受け付けません。台帳の repo_dir の祖先 symlink も realpath へ自動解決せず `media: repo_dir_symlink` として拒否します。各ファイルに空でない `alt` が必要です。ファイルは自分の原稿 repo に置き、他の実行環境でも使う原稿では画像等も Git へ登録・同期してください。THTH は原稿の承認時に元ファイルを書き換えません。

```yaml
media:
  - file: docs/photos/tea.jpg
    alt: 白いカップに注いだ緑茶
```

`thth: 1` は top-level、`thth: 2` は各 `posts` 項目の `index` の下にこの欄を書きます。添付を持つ段だけ本文を空にできます。添付なしの既存原稿と承認 hash は変わりません。

```yaml
posts:
  - index: 1
    media:
      - file: docs/photos/tea.jpg
        alt: 白いカップに注いだ緑茶
  - index: 2
    media: []
```

`thth send <account> --media docs/photos/tea.jpg --alt '白いカップに注いだ緑茶'` で添付だけの乾式試験ができます。複数指定は同数の `--media` と `--alt` を順番に対応させます。本文を付ける場合は従来の `--text-file` を使います。

承認には本文・既存公開設定に加え、ファイル順、元 SHA256、公開 SHA256、元／公開 byte 数、alt、寸法、秒数、Orientation、型付き設定と字幕 SHA を含めます。元ファイルの metadata だけを変え、公開 bytes が同じになっても再承認が必要です。準備中の bytes は匿名の private snapshot に固定し、元ファイルの差替えも別に検出します。公開用 stream は mutable な原稿ファイルから読みません。

## 形式と metadata

| 形式 | 処理・限界 |
|---|---|
| JPEG | segment/scan 境界を確認。Exif は Orientation の最小 IFD へ再構成。ICC、最小 JFIF の色・pixel aspect、Adobe ColorTransform、圧縮画像構造を保持。XMP/IPTC/comment/thumbnail は削除。未知 APP、ICC なしで解釈を保てない Exif ColorSpace 等は理由付き拒否。 |
| PNG/APNG | chunk 長・CRC・順序と圧縮データ長を検査。Orientation の最小 Exif、ICC、色／透過／animation 構造を保持。text/time を削除。未知 critical／安全性不明の ancillary は拒否。 |
| WebP | RIFF 長・pad・feature flags・再構成 chunk の順序を検査。Orientation の最小 Exif、ICC、alpha／animation を保持。XMP を削除。未知 chunk は拒否。 |
| GIF | 構造だけ検査し bytes は不変。Comment/Application Extension 内の私的情報が除去される保証はありません。 |
| MP4/MOV | bytes 不変。box 境界・寸法・movie duration を読み、位置 key があれば `location_metadata_present`。解析できない metadata track／vendor metadata は `location_metadata_unverifiable`。fragment 等で秒数を確認できない構造は `duration_unverifiable`。Threads だけは構造検証済み edit-list を警告として扱い、movie header の秒数を使います。top-level／moov 以下の未知 box と全 uuid を拒否。free/skip は payload 全0のみ許可し、mdat は走査しません。 |
| その他 | 自動変換しません。`unsupported_attachment: <medium>/<format>` 等の理由で拒否します。 |

この検査は汎用 codec の完全な復号検証ではありません。画像・動画の実 decoder 互換、実媒体の codec／寸法／容量／処理状態と実表示は後段・配布担当の確認対象です。媒体の上限を一律4点等に縮小していません。対応済みの準備処理と媒体での送信可否を分けます。

## ファイル以外の型付き入力

追加欄は厳密な2-space字下げ、または明示 JSON を使います。JSON の重複 key、null による型置換、未知 key は拒否します。投票選択肢や styles の入れ子は JSON 値で書きます。

```yaml
attachments:
  - type: poll
    options: ["温かい", "冷たい"]
    expires_in: 300
    multiple: false
post_options:
  visibility: public
```

- `quote`: `uri`、Bluesky は `cid` も必要。
- `link`: HTTPS `url`、任意の `title`／`description`。Bluesky は両方必須。画像を付ける場合は `thumbnail_file` と `thumbnail_alt` の両方が必要です。内部で説明を確認しても、媒体に alt 欄がない thumb へ alt が送られるとは表示しません。
- `poll`: `options`、Mastodon は `expires_in` 必須。任意の `multiple`／`hide_totals`。Mastodon の media と投票、Threads の投票と link/text は排他です。
- Threads `text`: `text`、任意の HTTPS `link`、`styles`（`offset`／`length`／`styling_info`）。style の媒体上の単位・対応値を推測して変換しません。
- Threads `gif`: `provider` と `id`。任意 URL の代理取得はしません。provider の受理値は後段で確認します。

`post_options` は Mastodon の `visibility/language/sensitive/spoiler_text/quote_approval_policy/focus`、Bluesky の `languages/labels/presentation/gallery/facets`、Threads の `text_spoiler/media_spoiler/ghost/reply_control/reply_approvals` を型検査します。これら全値を承認に含めます。既存の `location_id/reply_to/topic/share_to_instagram` をここへ重複記入することはできません。媒体別の上限・機能可否は後段の provider 検査で確かめます。

Bluesky 字幕は `captions: [{"media_index":1,"file":"docs/ja.vtt","lang":"ja"}]` のように、1から始まるファイルの番号へ結び付けます。UTF-8 WebVTT の境界を検査し、bytes は変えず SHA を承認へ含めます。

## Mastodon への画像・動画送信（第2段）

添付 API には `write:media` が必要です。`thth auth <account> --by <名前>` で追加scopeを含む再認可を行います。必要scope集合ごとの新clientを別ファイルに保存し、旧client/tokenを登録・交換の失敗で置き換えません。旧tokenの本文投稿は継続できます。旧pending認可は `auth_restart_required` としてやり直しが必要です。granted scopeに不足が記録されていればupload前に拒否します。未記録なら実応答で判定し、403は `provider_forbidden`（権限の確認か再認可）でありscope不足と断定しません。

既存の原稿承認→`run`、連投の段別実行、または `send --media ... --alt ...` の乾式表示→`--production --confirm <表示されたdigest>` で利用します。台帳の `production` 許可と通常の二段確認は維持します。添付だけなら本文を省けます。元ファイル・alt・順序・公開設定が変われば再承認してください。

送信前に対象 instance の `/api/v2/instance` を読み、点数、magic 由来 MIME、公開 byte 数、画素数、alt の文字数を照合します。画像で使わない動画上限の欠測は拒否理由にしません。必要な観測値が欠けた場合は `media_capability_unavailable` で upload 前に停止します。`description_limit` を返さない古い instance で既定値を推測することもありません。点数を独自に4等へ狭めません。

能力観測は account の private `media_capabilities.json` に instance・version・観測時刻とともに保存します。Mastodon の添付を持つ `lint` は公開 instance 情報を有界 GET で取得し、上限超過・必要値の欠測・取得失敗をエラーにします。この GET に credential は読み込みません。`preview` は同じ instance の cache の出所・時刻、または `capability_unobserved` を表示します。cache があるだけで本番を許可せず、本番でも最新 GET を行います。添付なし lint の挙動は変わりません。

MP4/MOV は最初の video track の sample table と timescale から平均 frame rate を読みます。VFR の瞬間最大ではなく平均の floor を、instance の `video_frame_rate_limit` と比較します。解析できない timing／codec、矛盾する sample table は `video_rate_unverifiable`／`video_dimensions_unverifiable` 等で停止します。ffprobe の codec 由来 fallback 値を推測せず、ファイル変換もしません。これは任意 codec の復号検証・実媒体による受理を保証するものではありません。

Mastodon の file `media` に加え、`post_options` の `public/unlisted` visibility、language、sensitive、spoiler_text、添付順の focus を送ります。従来の private/direct 投稿非対応は変わりません。typed poll/quote/link、quote_approval_policy、音声、字幕などこの段で未実装の intent は理由付きで拒否し、無視した成功にはしません。残る API 機能の網羅は後段です。

upload は同じ公開用 snapshot の bytes と alt を multipart で一度だけ送り、200 ready または202の既知 ID を記録します。202は206を処理中として GET で待ち、200 ready を全件確認してから順番どおりの ID で投稿します。最大120秒の待機はローカル処理待ちの方針で、動画の尺の上限ではありません。待機後も source／原稿・撤回・連投期限を再照合します。

各 upload と公開 POST より先に private inflight を fsync します。添付作成後の422/404・待機期限・承認変更は `media_held` として公開せず停止します。upload／公開の応答断・不明応答、公開後の記録失敗は `media_ambiguous` として保持します。再起動でも inflight がある間は再 upload／再投稿しません。状態を確認せず inflight を消して再試行しないでください。未使用の添付が媒体側に残る場合があり、自動削除は行いません。

添付付き Idempotency-Key は順序、公開 SHA、alt、本文、返信先、公開設定を含みます。媒体側の約1時間の重複抑制を、恒久的な一回性の保証として扱いません。成功時の sent／連投記録には公開 SHA・種類・alt の有無・媒体の添付 ID を残します。blob と credential、生 HTTP エラー本文は記録しません。準備中の alt 等の全 intent は private inflight に置きます。

ここまでの送信検証は合成ファイルと隔離したローカル HTTP/Git fixture です。実 instance、実 decoder、実 token での公開・処理時間・実表示は未測定です。

認可client名は `mastodon.<origin SHA256>.<scope集合SHA256先頭8>.env`。scope集合は重複を除いた昇順配列のASCII JSON（空白なし）で固定します。旧無印clientは削除・上書きしません。rehearseは新世代があればそれを読み、無ければ有効な旧5scopeを表示します。新世代が壊れていれば `auth_client_invalid` として停止し、旧世代へ黙って切り替えません。rehearseでproviderのHTTP/登録は行いません（既存の空relay待機は継続）。

## Bluesky への画像送信（第3段）

同じ原稿承認→`run`、連投の段別実行、`send --media ... --alt ...` の二段確認で画像を送れます。JPEG/PNG/WebP/GIF を準備済み公開 snapshot から送り、元ファイルを送り直しません。通常 `images` は1〜4枚、明示 `post_options: {"gallery":true}` は gallery schema の20枚までです。公式が authoring UI に示す10枚の soft limit は、CLI の API 上限と区別します。各ファイルは公開bytesで2,000,000 bytes以下です。縮小・圧縮して制限へ合わせることはありません。

画像の `lint` はこの固定 Lexicon の点数・公開サイズを local で検査します。alt と順序をそのまま embed に渡し、公開寸法とOrientationから表示上の aspectRatio を作ります。GIF は構造検査・bytes不変の既定です。PDSが返す blob のCID・size・MIMEが承認した公開bytesと一致しない場合は投稿しません。CIDは公式のCIDv1/raw/SHA-256/base32に従って公開SHAから比較します。

upload後に承認・元ファイル・退出状態が変わればcreateRecordへ進みません。既知blobがある公開前停止は `media_held`、POSTの応答断や不正成功応答は `media_ambiguous` として private inflightを保持し、再起動で自動upload／再投稿は行いません。投稿成功後の記録失敗でも同じです。PDS側の未参照blobの回収時刻・物理削除は保証せず、ththから自動削除しません。

この画像段の投稿オプションはgalleryだけです。languages/labels/facetsとtyped quote/cardは後段です。字幕・presentation・動画は第6段の動画専用口で扱い、画像と一緒に指定された未対応intentを無視せずupload前に拒否します。既存本文からのURL/タグfacetsと返信先root/parentは維持します。画像の実表示、PDS側の再encode、gallery対応クライアントの表示は実機未測定です。本文だけの既存経路・sent形式は変わりません。


### 処理待ちと多枚数の運用上限

Mastodon の処理待ち上限120秒は添付1件ごとです。4件なら最大8分 account lock を保持します。Bluesky gallery は20枚で公開 bytes が最大40 MBメモリに載り、投稿まで最大21本の要求を直列に送ります。

媒体の接続先は HTTPS のみです。隔離したローカル試験に限り `THTH_TEST_ALLOW_HTTP=1` で localhost・127.0.0.1・::1 の HTTP を許可します。環境 proxy、file、FTP、data URL は利用しません。


## Threads 画像と R2（第4段）

JPEG/PNG を1枚、または2〜20枚のカルーセルとして送信します。alt は各画像へ送り、本文・返信先・topic・location・Instagram共有の承認済み値を保持します。動画・GIFや型付き添付、追加post_optionsは後段であり、無言に落として公開しません。CLI/既存原稿の二段承認を使い、招待サーバーの添付承認画面はまだ開放しません。

画像は sanitize 後の公開 bytes を **暫定8,000,000 bytes以下**に制限します。公式の「8 MB」は整数単位が未定義です。8,000,001〜8,388,608 bytesは、媒体が受け付ける可能性があっても現在のththは断る帯です。配布担当が8,100,000 bytes前後のJPEGで実測し、受理を確認できれば上限を更新します。この暫定値を一次確認済みAPIの整数上限とは扱いません。縦横いずれかの比率が10:1を超えるものは拒否します。幅320未満／1440超は媒体による拡大／縮小の注記のみで、ththは拒否しません。ICCを保持し、色空間を検査・変換しません。媒体はsRGBへ変換します。

運営者の既存relay署名鍵を使い、VMからWorkerへ署名付き管理要求を送り、R2の資格情報はVMへ置きません。内部CLI/timerの所有者は運営者とaccountへ結びつけ、原稿の任意値からactorを選びません。各upload/公開grantは別の乱数IDとR2 objectを持ち、同SHAでも別account／別grantのcleanupは共有しません。公開URLや認可値はjournal/sentへ保存しません。

upload capabilityは600秒・complete一度。100,000,000 bytes超の汎用uploadはmultipart（最終以外同サイズ、最低5MiB）ですが、Threads画像自体は上記8MB制限です。VMはR2から署名付きで読み返した実bytesのSHAとサイズを照合してから公開grantを作ります。未加工ファイルの署名読取もSHA一致後にackし、ack後は論理読取不可になります。previewは600秒、provider画像URLは発行から600秒。公開成功の最初のackだけがack起点3600秒に設定し、再送で延長しません。明示失敗では即時失効を試み、不明な結果ではURLの再発行・延長・再POSTをしません。

containerごとに最大120秒を有界に待ち、同時に各provider URLの期限を確認します。FINISHEDと最終承認を確認してから公開します。期限後の成功応答では公開しません。公開済みの結果が確定していてURLのackだけ失敗した場合は再投稿せず、journalにack未確認を残し、暫定期限を延長しません。upload/container/publicationの不明状態ではinflightを保持して自動再送を止めます。

公開URLの期限後はGET/HEAD/Rangeすべて410。正しい形の未知／削除済みcapabilityも410で、永久markerを保存しません（不正な形は404）。R2物理削除は24時間backstopとalarmの再試行で扱い、実サービスの即時削除は保証しません。すでに配信したbytesの回収はできません。

配布担当の確認が必要なのは、R2 binding/bucket lifecycle・custom domain/route・Worker planのbody/CPU/memory上限・実Threadsの画像URL取得と処理時間・8MBの整数境界・実表示です。ここでの試験はローカルMiniflare/SQLite/R2と偽Graphです。実R2作成・認可・投稿・公開配布は実施していません。

R2 cleanup は障害時に object/upload ID を Worker 内に保持し、1 分後の alarm を明示再設定します。初回を含め最大10回で自動再試行を止め、cleanup_failed と試行数を残します。multipart の abort 成功と既知の complete 成功を区別し、閉じた upload を繰り返し abort しません。object delete が成功するまで管理行は残し、URL は論理失効したままです。alarm 設定自体の永続化障害やサービス停止中は、24 時間での物理削除を保証しません。配布側が bucket lifecycle と cleanup の稼働を確認します。

createMultipartUpload の応答が失われ upload ID を受け取れなかった場合、part は受け付けません。空の multipart 管理状態をこちらから指定して abort できない限界があり、Cloudflare の未完 upload の既定 7 日失効等に依存します。これは parts を受け取った後の abort 障害と別です。実 R2 の障害・lifecycle は今回未測定です。


## Threads 動画と混在カルーセル（第5段）

MP4/MOV の動画を1本、またはJPEG/PNG画像と混ぜた2〜20点のカルーセルとして送ります。各動画のaltと公開bytesを保持し、先頭からのchildren順は原稿順です。動画はVIDEO/video_urlでcontainerを作り、全件FINISHEDと最終承認を確認してからpublishします。sentのkindはvideoとし、動画を画像として記録しません。字幕・追加post_options・型付き添付の残りは後段です。

拒否する規格値は尺0秒以下／300秒超、暫定SI1,000,000,000 bytes超、幅1920超、幅:高さが0.01:1未満または10:1超です。1,000,000,001〜1,073,741,824 bytesは、媒体が受け付ける可能性があっても暫定的に断る帯です。このSI上限はAPI実測済みの整数値ではありません。媒体へ合わせる再encode／圧縮／切詰めは行いません。

C12裁定により、動画の規格による拒否はcontainer・duration・bytes・幅・比率だけです。平均frame rate、codec label、audio channels／sample rate、progressive fieldは観測できても警告に留めます。audioとvideoのbtrtはencoderの宣言max/avgを別々に表示し、非zeroのどちらかがaudio 128,000 bps／video 100,000,000 bpsを超える場合も警告だけです。0・欠測やGOP・chroma・VBR・AACの実bitstreamは未認証であり、媒体側が拒否する場合があります。宣言値を実測bitrateや媒体の受理保証とは扱いません。

Threadsに限り、構造検査を通るedit-listとmoovがmdatより後の配置はlintの警告です。構造不正、位置key、uuid、未知metadata、nonzero paddingは警告へ格下げせず従来どおり拒否します。mdat本文は走査せず、元動画bytesは変えません。任意decoderでの復号・表示は未確認です。

provider URLは動画の発行から1800秒、画像は600秒、公開成功の最初のACKから3600秒です。動画の処理待ちは1800秒以内、画像は120秒以内に加え、すでに発行した全grantの最短期限を守ります。複数点を直列処理すると先のURLの期限が先に来てheldとなる場合があります。期限を伸ばすためのURL再発行や自動再POSTは行いません。1800秒はC10裁定の待機枠であり、Metaの処理完了時間保証ではありません。公式処理時間目安と実Threadsの長い動画／混在fetchは未測定です。


## Bluesky 動画（第6段）

MP4動画1本を、承認済み公開snapshotのままBluesky動画サービスへ送ります。上限は固定Lexiconの300,000,000 bytes、公式アプリの600秒です。画像の2MB上限は動画へ適用しません。元動画をththで圧縮・変換しません。MOV、画像との混在、複数動画、型付き添付の同時指定はこの口では理由付き拒否です。構造／位置metadataの拒否は従来のBluesky向け規則を維持します。

`captions` は動画index 1に結び付けたUTF-8 WebVTTを20件まで、各20,000 bytes以下で送ります。言語・順序・字幕bytesのSHAも承認と送信で一致させます。動画alt、寸法から得るaspectRatio、`post_options.presentation`をそのままembedへ渡します。presentationの既知例はdefault/gifですが、将来のhintも文字列として保持し、実クライアントの表示対応を保証しません。languages/labels/facets等の追加設定やtyped quote/cardの残りは後段で、黙って省略しません。

lintは容量・尺・寸法・字幕の静的境界を検査します。日次残量やemail確認等の投稿権限は未観測と表示し、本番送信の直前にgetUploadLimitsを取得します。canUploadが不明／falseならuploadしません。残り件数／bytesが応答にある場合だけ必要量と比較し、欠測を0とは扱いません。

認証済みsessionのDID文書から最初の該当PDS serviceを選び、HTTPSのhostnameからupload用audienceを作ります。設定先がentrywayである場合に、そのhostnameをPDSと推定しません。DID文書が欠ける場合は `video_pds_unavailable` として停止します。limits用とupload用のservice tokenはaudience／権限を分け、短命tokenをRAM以外へ保存しません。処理状態GETにはtokenを送りません。

uploadは1回、処理待ちは最大1800秒か取得tokenの期限までです。この有界待機はththの方針であり、Blueskyの処理完了時間保証ではありません。jobの本人DIDとIDを照合し、未知のstateは処理中として待ちます。already_existsというエラー名だけでは公開せず、本人jobと有効なblobがそろった場合のみ再利用します。期限・停止・承認変更の後は既知jobをheldとして保持し、createRecordへ進みません。POST応答喪失・保存失敗はunknownのinflightを保持し、自動再upload／再投稿をしません。

動画サービスはupstreamで最適化したblobを返します。入力の公開SHAは承認とuploadの同一bytes、返却CIDはサービス処理後のblobとして別に扱います。画像のように入力SHAとの一致を要求しません。返却CIDの形式、MP4 MIME、容量と本人jobを検証し、そのblobで投稿します。字幕blobは元の公開SHAと照合します。

検証は隔離した偽PDS／動画サービスのHTTP応答と合成MP4です。実PDSのservice-auth許可／email確認、300MB direct uploadの受付、サービスの最適化品質・処理時間・実クライアント表示は未測定です。実サービスのupload残物の物理回収は保証しません。

規格の出所は [固定動画Lexicon](https://github.com/bluesky-social/atproto/blob/7870a59c0b0aa5955ba3b663f9e095350f50e194/lexicons/app/bsky/embed/video.json)、[公式アプリの容量／尺定数](https://github.com/bluesky-social/social-app/blob/547b6155779714f126f8be82c785d1ca50014bfa/src/lib/constants.ts)、[Bluesky公式動画ガイド](https://bsky.network/docs/about-bluesky-content/video/)です。参照した仕様と実サービスでの受付確認は区別します。

Worker の media 制限（C17・暫定運用値）: 公開 GET/HEAD/Range は送信元 IP ごとに 120 回/60 秒、署名 control は IP ごとに 600 回/60 秒、upload は subject ごとに 240 回/60 秒です。既存承認系とは別枠で、binding 未設定や超過は後続の署名・DO・R2 処理へ進めません。Cloudflare location 単位の緩やかな制限であり、厳密な課金上限ではありません。同じ IP を共有する利用者が影響を受ける場合があります。429 を理由とした公開要求の自動再送はしません。

Worker の `sanitized` は画像 8,000,000 bytes、動画 1,000,000,000 bytes が上限です。EXIF 除去前の `source` は公開画像上限を流用せず、共通 transport 暫定上限 1,000,000,000 bytes とします。これは媒体の仕様上限ではなく、Web 入口の段で再照合する資源制限です。


掃除の義務は R2 割当の前に account DO に登録します。期限前の予定は異常件数に含めず、期限後に成功を確認できない義務は `cleanup_unconfirmed`、10 回失敗は `cleanup_failed` として、署名付き account status から doctor へ件数と静的理由だけ返します。集約の取得・応答検証に失敗した場合は件数を null、`cleanup_observation_unavailable` とし、0 件正常にはしません。subject、URL、object key は Worker 内に閉じます。削除と集約除去の成功確認後に管理行を消します。24 時間以内の物理削除は保証しません。

管理者は `thth admin media cleanup-retry <account> --by <名前> --json` で期限済みの削除だけを再開できます。承認・投稿・公開 URL の再発行は行いません。退出後にも回復可能です。1 回に最大64件を schedule し、remaining_count が残るときは追加の管理実行が必要です。コマンドは by の妥当性と既存 operator 署名を要求し、結果に件数以外の秘密を出しません。通常の投稿や cleanup alarm が再投稿することはありません。

R2 の書込み中は同じ世代の I/O ticket を永続保持し、alarm は object の不在だけで掃除義務を消しません。遅れて完了した書込みの補償削除に失敗した場合も義務を保持し、書込み完了確認後の cleanup-retry で削除を再開できます。R2 書込み応答の喪失・拒否や isolate 再起動などで I/O の結果自体が不明になった ticket は自動で完了と見なしません。10 回で自動試行を止めて未確認／失敗を表示し、通常の cleanup-retry だけで完全回復できたとは扱いません。この残留状態を公開・再投稿で解消することはありません。

既知 ETag の同一 part 再送は可能ですが、R2 応答を失って結果不明になった part は後続書込みを止めます。通常の再試行で未知 ticket を強制解除しません。


| 管理口 | 作用 | 回復の限界 |
| --- | --- | --- |
| `admin media cleanup-retry` | 期限済みの物理削除を再試行 | 結果不明の書込みを強制解除しないため、本口だけでは回復できない場合があります。再投稿はしません。 |

配布担当は R2 bucket に `media/` prefix・作成から24時間で削除する lifecycle rule を backstop として設定します。Worker の掃除とは独立した運用であり、物理削除時刻の保証ではありません。この実装検証では Cloudflare 側の設定を行っていません。
