# 添付を含む原稿（2.13 第1〜6段・第7段の投票・引用・リンク）

`lint`・`preview`・`approve` の一段目と `send` の乾式試験で、添付と本文を一緒に確認できます。第2段では Mastodon の対応する画像・MP4/MOV を upload し、処理完了を確認してから公開します。第3段は Bluesky 画像、第4段は Threads 画像に対応します。第5段は Threads 動画、第6段は Bluesky 動画です。第8段でブラウザーの承認ページが添付を表示します。未対応の実送信は `media_provider_unavailable` 等で止まり、本文だけに落として公開しません。

## ファイルと承認

`file` は台帳の `repo_dir` を起点にした相対パスです。絶対パス、親への遡り、symlink、hardlink、FIFO は受け付けません。台帳の repo_dir の祖先 symlink も realpath へ自動解決せず `media: repo_dir_symlink` として拒否します。各ファイルに空でない `alt` が必要です。ファイルは自分の原稿 repo に置き、他の実行環境でも使う原稿では画像等も Git へ登録・同期してください。THTH は原稿の承認時に元ファイルを書き換えません。

```yaml
media:
  - file: docs/photos/tea.jpg
    alt: 白いカップに注いだ緑茶
```

`thth: 1` は top-level、`thth: 2` は各 `posts` 項目の `index` の下にこの欄を書きます。添付を持つ段だけ本文を空にできます。添付なしの既存原稿と承認 hash は変わりません。

```yaml
posts:
  - index: 1
    media:
      - file: docs/photos/tea.jpg
        alt: 白いカップに注いだ緑茶
  - index: 2
    media: []
```

`thth send <account> --media docs/photos/tea.jpg --alt '白いカップに注いだ緑茶'` で添付だけの乾式試験ができます。複数指定は同数の `--media` と `--alt` を順番に対応させます。本文を付ける場合は従来の `--text-file` を使います。

承認には本文・既存公開設定に加え、ファイル順、元 SHA256、公開 SHA256、元／公開 byte 数、alt、寸法、秒数、Orientation、型付き設定と字幕 SHA を含めます。元ファイルの metadata だけを変え、公開 bytes が同じになっても再承認が必要です。準備中の bytes は匿名の private snapshot に固定し、元ファイルの差替えも別に検出します。公開用 stream は mutable な原稿ファイルから読みません。

## 形式と metadata

| 形式 | 処理・限界 |
|---|---|
| JPEG | segment/scan 境界を確認。Exif は Orientation の最小 IFD へ再構成。ICC、最小 JFIF の色・pixel aspect、Adobe ColorTransform、圧縮画像構造を保持。XMP/IPTC/comment/thumbnail は削除。未知 APP、ICC なしで解釈を保てない Exif ColorSpace 等は理由付き拒否。 |
| PNG/APNG | chunk 長・CRC・順序と圧縮データ長を検査。Orientation の最小 Exif、ICC、色／透過／animation 構造を保持。text/time を削除。未知 critical／安全性不明の ancillary は拒否。 |
| WebP | RIFF 長・pad・feature flags・再構成 chunk の順序を検査。Orientation の最小 Exif、ICC、alpha／animation を保持。XMP を削除。未知 chunk は拒否。 |
| GIF | 構造だけ検査し bytes は不変。Comment/Application Extension 内の私的情報が除去される保証はありません。 |
| MP4/MOV | bytes 不変。box 境界・寸法・movie duration を読み、位置 key があれば `location_metadata_present`。解析できない metadata track／vendor metadata は `location_metadata_unverifiable`。fragment 等で秒数を確認できない構造は `duration_unverifiable`。Threads だけは構造検証済み edit-list を警告として扱い、movie header の秒数を使います。top-level／moov 以下の未知 box と全 uuid を拒否。free/skip は payload 全0のみ許可し、mdat は走査しません。 |
| AAC/ADTS | syncword 0xFFF・layer ビット 00 を MP3 の判定より先に名前で見分け、構造解析の前に `unsupported_attachment: <medium>/aac_adts` で断ります。裸の ADTS は privacy 検査の境界（`privacy_inspection_boundary_unverified`）が未確認なためで、壊れた MP3 としては報告しません。次の一歩は「m4a に入れ直す」です。 |
| ASF/WMV/WMA | 先頭の header object GUID（30 26 B2 75 …）で名前を確定し、`unsupported_attachment: <medium>/asf` で断ります。静的理由は `deferred_by_ruling_c14`——C14 の裁定で、半端に検査せず先送りしています。 |
| その他 | 自動変換しません。`unsupported_attachment: <medium>/<format>` 等の理由で拒否します。 |

この検査は汎用 codec の完全な復号検証ではありません。画像・動画の実 decoder 互換、実媒体の codec／寸法／容量／処理状態と実表示は後段・配布担当の確認対象です。媒体の上限を一律4点等に縮小していません。対応済みの準備処理と媒体での送信可否を分けます。

## ファイル以外の型付き入力

追加欄は厳密な2-space字下げ、または明示 JSON を使います。JSON の重複 key、null による型置換、未知 key は拒否します。投票選択肢や styles の入れ子は JSON 値で書きます。

```yaml
attachments:
  - type: poll
    options: ["温かい", "冷たい"]
    expires_in: 300
    multiple: false
post_options:
  visibility: public
```

- `quote`: `uri`、Bluesky は `cid` も必要。
- `link`: HTTPS `url`、任意の `title`／`description`。Bluesky は両方必須。画像を付ける場合は `thumbnail_file` と `thumbnail_alt` の両方が必要です。内部で説明を確認しても、媒体に alt 欄がない thumb へ alt が送られるとは表示しません。
- `poll`: `options`、Mastodon は `expires_in` 必須。任意の `multiple`／`hide_totals`。Mastodon の media と投票、Threads の投票と link/text は排他です。
- Threads `text`: `text`、任意の HTTPS `link`、`styles`（`offset`／`length`／`styling_info`）。style の媒体上の単位・対応値を推測して変換しません。原稿では `bold`／`italic`／`highlight`／`underline`／`strikethrough` の小文字で書き、送信時だけ Meta の文書が並べている綴り（`Bold`・`Italic`・`Highlight`・`Underline`・`Strikethrough`）へ直します。**この大文字小文字は文書の記載であって実 API の応答で確かめた値ではありません**（C15）。実機で受理・表示を確認するのは配布担当の実測項目です。
- Threads `gif`: `provider` と `id`。任意 URL の代理取得はしません。provider の受理値は後段で確認します。

`post_options` は Mastodon の `visibility/language/sensitive/spoiler_text/quote_approval_policy/focus`、Bluesky の `languages/labels/presentation/gallery/facets`、Threads の `text_spoiler/media_spoiler/ghost/reply_control/reply_approvals` を型検査します。これら全値を承認に含めます。既存の `location_id/reply_to/topic/share_to_instagram` をここへ重複記入することはできません。媒体別の上限・機能可否は後段の provider 検査で確かめます。

Bluesky 字幕は `captions: [{"media_index":1,"file":"docs/ja.vtt","lang":"ja"}]` のように、1から始まるファイルの番号へ結び付けます。UTF-8 WebVTT の境界を検査し、bytes は変えず SHA を承認へ含めます。

## Mastodon への画像・動画送信（第2段）

添付 API には `write:media` が必要です。`thth auth <account> --by <名前>` で追加scopeを含む再認可を行います。必要scope集合ごとの新clientを別ファイルに保存し、旧client/tokenを登録・交換の失敗で置き換えません。旧tokenの本文投稿は継続できます。旧pending認可は `auth_restart_required` としてやり直しが必要です。granted scopeに不足が記録されていればupload前に拒否します。未記録なら実応答で判定し、403は `provider_forbidden`（権限の確認か再認可）でありscope不足と断定しません。

既存の原稿承認→`run`、連投の段別実行、または `send --media ... --alt ...` の乾式表示→`--production --confirm <表示されたdigest>` で利用します。台帳の `production` 許可と通常の二段確認は維持します。添付だけなら本文を省けます。元ファイル・alt・順序・公開設定が変われば再承認してください。

送信前に対象 instance の `/api/v2/instance` を読み、点数、magic 由来 MIME、公開 byte 数、画素数、alt の文字数を照合します。画像で使わない動画上限の欠測は拒否理由にしません。必要な観測値が欠けた場合は `media_capability_unavailable` で upload 前に停止します。`description_limit` を返さない古い instance で既定値を推測することもありません。点数を独自に4等へ狭めません。

能力観測は account の private `media_capabilities.json` に instance・version・観測時刻とともに保存します。Mastodon の添付を持つ `lint` は公開 instance 情報を有界 GET で取得し、上限超過・必要値の欠測・取得失敗をエラーにします。この GET に credential は読み込みません。`preview` は同じ instance の cache の出所・時刻、または `capability_unobserved` を表示します。cache があるだけで本番を許可せず、本番でも最新 GET を行います。添付なし lint の挙動は変わりません。

MP4/MOV は最初の video track の sample table と timescale から平均 frame rate を読みます。VFR の瞬間最大ではなく平均の floor を、instance の `video_frame_rate_limit` と比較します。解析できない timing／codec、矛盾する sample table は `video_rate_unverifiable`／`video_dimensions_unverifiable` 等で停止します。ffprobe の codec 由来 fallback 値を推測せず、ファイル変換もしません。これは任意 codec の復号検証・実媒体による受理を保証するものではありません。

Mastodon の file `media` に加え、`post_options` の `public/unlisted` visibility、language、sensitive、spoiler_text、添付順の focus を送ります。従来の private/direct 投稿非対応は変わりません。typed poll/quote/link、quote_approval_policy、音声、字幕などこの段で未実装の intent は理由付きで拒否し、無視した成功にはしません。残る API 機能の網羅は後段です。

upload は同じ公開用 snapshot の bytes と alt を multipart で一度だけ送り、200 ready または202の既知 ID を記録します。202は206を処理中として GET で待ち、200 ready を全件確認してから順番どおりの ID で投稿します。最大120秒の待機はローカル処理待ちの方針で、動画の尺の上限ではありません。待機後も source／原稿・撤回・連投期限を再照合します。

各 upload と公開 POST より先に private inflight を fsync します。添付作成後の422/404・待機期限・承認変更は `media_held` として公開せず停止します。upload／公開の応答断・不明応答、公開後の記録失敗は `media_ambiguous` として保持します。再起動でも inflight がある間は再 upload／再投稿しません。状態を確認せず inflight を消して再試行しないでください。未使用の添付が媒体側に残る場合があり、自動削除は行いません。

添付付き Idempotency-Key は順序、公開 SHA、alt、本文、返信先、公開設定を含みます。媒体側の約1時間の重複抑制を、恒久的な一回性の保証として扱いません。成功時の sent／連投記録には公開 SHA・種類・alt の有無・媒体の添付 ID を残します。blob と credential、生 HTTP エラー本文は記録しません。準備中の alt 等の全 intent は private inflight に置きます。

ここまでの送信検証は合成ファイルと隔離したローカル HTTP/Git fixture です。実 instance、実 decoder、実 token での公開・処理時間・実表示は未測定です。

認可client名は `mastodon.<origin SHA256>.<scope集合SHA256先頭8>.env`。scope集合は重複を除いた昇順配列のASCII JSON（空白なし）で固定します。旧無印clientは削除・上書きしません。rehearseは新世代があればそれを読み、無ければ有効な旧5scopeを表示します。新世代が壊れていれば `auth_client_invalid` として停止し、旧世代へ黙って切り替えません。rehearseでproviderのHTTP/登録は行いません（既存の空relay待機は継続）。

## Bluesky への画像送信（第3段）

同じ原稿承認→`run`、連投の段別実行、`send --media ... --alt ...` の二段確認で画像を送れます。JPEG/PNG/WebP/GIF を準備済み公開 snapshot から送り、元ファイルを送り直しません。通常 `images` は1〜4枚、明示 `post_options: {"gallery":true}` は gallery schema の20枚までです。公式が authoring UI に示す10枚の soft limit は、CLI の API 上限と区別します。各ファイルは公開bytesで2,000,000 bytes以下です。縮小・圧縮して制限へ合わせることはありません。

画像の `lint` はこの固定 Lexicon の点数・公開サイズを local で検査します。alt と順序をそのまま embed に渡し、公開寸法とOrientationから表示上の aspectRatio を作ります。GIF は構造検査・bytes不変の既定です。PDSが返す blob のCID・size・MIMEが承認した公開bytesと一致しない場合は投稿しません。CIDは公式のCIDv1/raw/SHA-256/base32に従って公開SHAから比較します。

upload後に承認・元ファイル・退出状態が変わればcreateRecordへ進みません。既知blobがある公開前停止は `media_held`、POSTの応答断や不正成功応答は `media_ambiguous` として private inflightを保持し、再起動で自動upload／再投稿は行いません。投稿成功後の記録失敗でも同じです。PDS側の未参照blobの回収時刻・物理削除は保証せず、ththから自動削除しません。

この画像段の投稿オプションはgalleryだけです。languages/labels/facetsは後段です。typed quote/cardは第7段の節を参照してください。字幕・presentation・動画は第6段の動画専用口で扱い、画像と一緒に指定された未対応intentを無視せずupload前に拒否します。既存本文からのURL/タグfacetsと返信先root/parentは維持します。画像の実表示、PDS側の再encode、gallery対応クライアントの表示は実機未測定です。本文だけの既存経路・sent形式は変わりません。


### 処理待ちと多枚数の運用上限

Mastodon の処理待ち上限120秒は添付1件ごとです。4件なら最大8分 account lock を保持します。Bluesky gallery は20枚で公開 bytes が最大40 MBメモリに載り、投稿まで最大21本の要求を直列に送ります。

媒体の接続先は HTTPS のみです。隔離したローカル試験に限り `THTH_TEST_ALLOW_HTTP=1` で localhost・127.0.0.1・::1 の HTTP を許可します。環境 proxy、file、FTP、data URL は利用しません。


## Threads 画像と R2（第4段）

JPEG/PNG を1枚、または2〜20枚のカルーセルとして送信します。alt は各画像へ送り、本文・返信先・topic・location・Instagram共有の承認済み値を保持します。動画・GIFや型付き添付、追加post_optionsは後段であり、無言に落として公開しません。CLI/既存原稿の二段承認を使い、招待サーバーの添付承認画面はまだ開放しません。

画像は sanitize 後の公開 bytes を **暫定8,000,000 bytes以下**に制限します。公式の「8 MB」は整数単位が未定義です。8,000,001〜8,388,608 bytesは、媒体が受け付ける可能性があっても現在のththは断る帯です。配布担当が8,100,000 bytes前後のJPEGで実測し、受理を確認できれば上限を更新します。この暫定値を一次確認済みAPIの整数上限とは扱いません。縦横いずれかの比率が10:1を超えるものは拒否します。幅320未満／1440超は媒体による拡大／縮小の注記のみで、ththは拒否しません。ICCを保持し、色空間を検査・変換しません。媒体はsRGBへ変換します。

運営者の既存relay署名鍵を使い、VMからWorkerへ署名付き管理要求を送り、R2の資格情報はVMへ置きません。内部CLI/timerの所有者は運営者とaccountへ結びつけ、原稿の任意値からactorを選びません。各upload/公開grantは別の乱数IDとR2 objectを持ち、同SHAでも別account／別grantのcleanupは共有しません。公開URLや認可値はjournal/sentへ保存しません。

upload capabilityは600秒・complete一度。100,000,000 bytes超の汎用uploadはmultipart（最終以外同サイズ、最低5MiB）ですが、Threads画像自体は上記8MB制限です。VMはR2から署名付きで読み返した実bytesのSHAとサイズを照合してから公開grantを作ります。未加工ファイルの署名読取もSHA一致後にackし、ack後は論理読取不可になります。previewは600秒、provider画像URLは発行から600秒。公開成功の最初のackだけがack起点3600秒に設定し、再送で延長しません。明示失敗では即時失効を試み、不明な結果ではURLの再発行・延長・再POSTをしません。

containerごとに最大120秒を有界に待ち、同時に各provider URLの期限を確認します。FINISHEDと最終承認を確認してから公開します。期限後の成功応答では公開しません。公開済みの結果が確定していてURLのackだけ失敗した場合は再投稿せず、journalにack未確認を残し、暫定期限を延長しません。upload/container/publicationの不明状態ではinflightを保持して自動再送を止めます。

公開URLの期限後はGET/HEAD/Rangeすべて410。正しい形の未知／削除済みcapabilityも410で、永久markerを保存しません（不正な形は404）。R2物理削除は24時間backstopとalarmの再試行で扱い、実サービスの即時削除は保証しません。すでに配信したbytesの回収はできません。

配布担当の確認が必要なのは、R2 binding/bucket lifecycle・custom domain/route・Worker planのbody/CPU/memory上限・実Threadsの画像URL取得と処理時間・8MBの整数境界・実表示です。ここでの試験はローカルMiniflare/SQLite/R2と偽Graphです。実R2作成・認可・投稿・公開配布は実施していません。

R2 cleanup は障害時に object/upload ID を Worker 内に保持し、1 分後の alarm を明示再設定します。初回を含め最大10回で自動再試行を止め、cleanup_failed と試行数を残します。multipart の abort 成功と既知の complete 成功を区別し、閉じた upload を繰り返し abort しません。object delete が成功するまで管理行は残し、URL は論理失効したままです。alarm 設定自体の永続化障害やサービス停止中は、24 時間での物理削除を保証しません。配布側が bucket lifecycle と cleanup の稼働を確認します。

createMultipartUpload の応答が失われ upload ID を受け取れなかった場合、part は受け付けません。空の multipart 管理状態をこちらから指定して abort できない限界があり、Cloudflare の未完 upload の既定 7 日失効等に依存します。これは parts を受け取った後の abort 障害と別です。実 R2 の障害・lifecycle は今回未測定です。


## Threads 動画と混在カルーセル（第5段）

MP4/MOV の動画を1本、またはJPEG/PNG画像と混ぜた2〜20点のカルーセルとして送ります。各動画のaltと公開bytesを保持し、先頭からのchildren順は原稿順です。動画はVIDEO/video_urlでcontainerを作り、全件FINISHEDと最終承認を確認してからpublishします。sentのkindはvideoとし、動画を画像として記録しません。字幕・追加post_options・型付き添付の残りは後段です。

拒否する規格値は尺0秒以下／300秒超、暫定SI1,000,000,000 bytes超、幅1920超、幅:高さが0.01:1未満または10:1超です。1,000,000,001〜1,073,741,824 bytesは、媒体が受け付ける可能性があっても暫定的に断る帯です。このSI上限はAPI実測済みの整数値ではありません。媒体へ合わせる再encode／圧縮／切詰めは行いません。

C12裁定により、動画の規格による拒否はcontainer・duration・bytes・幅・比率だけです。平均frame rate、codec label、audio channels／sample rate、progressive fieldは観測できても警告に留めます。audioとvideoのbtrtはencoderの宣言max/avgを別々に表示し、非zeroのどちらかがaudio 128,000 bps／video 100,000,000 bpsを超える場合も警告だけです。0・欠測やGOP・chroma・VBR・AACの実bitstreamは未認証であり、媒体側が拒否する場合があります。宣言値を実測bitrateや媒体の受理保証とは扱いません。

Threadsに限り、構造検査を通るedit-listとmoovがmdatより後の配置はlintの警告です。構造不正、位置key、uuid、未知metadata、nonzero paddingは警告へ格下げせず従来どおり拒否します。mdat本文は走査せず、元動画bytesは変えません。任意decoderでの復号・表示は未確認です。

provider URLは動画の発行から1800秒、画像は600秒、公開成功の最初のACKから3600秒です。動画の処理待ちは1800秒以内、画像は120秒以内に加え、すでに発行した全grantの最短期限を守ります。複数点を直列処理すると先のURLの期限が先に来てheldとなる場合があります。期限を伸ばすためのURL再発行や自動再POSTは行いません。1800秒はC10裁定の待機枠であり、Metaの処理完了時間保証ではありません。公式処理時間目安と実Threadsの長い動画／混在fetchは未測定です。


## Bluesky 動画（第6段）

MP4動画1本を、承認済み公開snapshotのままBluesky動画サービスへ送ります。上限は固定Lexiconの300,000,000 bytes、公式アプリの600秒です。画像の2MB上限は動画へ適用しません。元動画をththで圧縮・変換しません。MOV、画像との混在、複数動画、型付き添付の同時指定はこの口では理由付き拒否です。構造／位置metadataの拒否は従来のBluesky向け規則を維持します。

`captions` は動画index 1に結び付けたUTF-8 WebVTTを20件まで、各20,000 bytes以下で送ります。言語・順序・字幕bytesのSHAも承認と送信で一致させます。動画alt、寸法から得るaspectRatio、`post_options.presentation`をそのままembedへ渡します。presentationの既知例はdefault/gifですが、将来のhintも文字列として保持し、実クライアントの表示対応を保証しません。languages/labels/facets等の追加設定は後段で、黙って省略しません。引用との組合せは第7段の節を参照してください。

lintは容量・尺・寸法・字幕の静的境界を検査します。日次残量やemail確認等の投稿権限は未観測と表示し、本番送信の直前にgetUploadLimitsを取得します。canUploadが不明／falseならuploadしません。残り件数／bytesが応答にある場合だけ必要量と比較し、欠測を0とは扱いません。

認証済みsessionのDID文書から最初の該当PDS serviceを選び、HTTPSのhostnameからupload用audienceを作ります。設定先がentrywayである場合に、そのhostnameをPDSと推定しません。DID文書が欠ける場合は `video_pds_unavailable` として停止します。limits用とupload用のservice tokenはaudience／権限を分け、短命tokenをRAM以外へ保存しません。処理状態GETにはtokenを送りません。

uploadは1回、処理待ちは最大1800秒か取得tokenの期限までです。この有界待機はththの方針であり、Blueskyの処理完了時間保証ではありません。jobの本人DIDとIDを照合し、未知のstateは処理中として待ちます。already_existsというエラー名だけでは公開せず、本人jobと有効なblobがそろった場合のみ再利用します。期限・停止・承認変更の後は既知jobをheldとして保持し、createRecordへ進みません。POST応答喪失・保存失敗はunknownのinflightを保持し、自動再upload／再投稿をしません。

動画サービスはupstreamで最適化したblobを返します。入力の公開SHAは承認とuploadの同一bytes、返却CIDはサービス処理後のblobとして別に扱います。画像のように入力SHAとの一致を要求しません。返却CIDの形式、MP4 MIME、容量と本人jobを検証し、そのblobで投稿します。字幕blobは元の公開SHAと照合します。

検証は隔離した偽PDS／動画サービスのHTTP応答と合成MP4です。実PDSのservice-auth許可／email確認、300MB direct uploadの受付、サービスの最適化品質・処理時間・実クライアント表示は未測定です。実サービスのupload残物の物理回収は保証しません。

規格の出所は [固定動画Lexicon](https://github.com/bluesky-social/atproto/blob/7870a59c0b0aa5955ba3b663f9e095350f50e194/lexicons/app/bsky/embed/video.json)、[公式アプリの容量／尺定数](https://github.com/bluesky-social/social-app/blob/547b6155779714f126f8be82c785d1ca50014bfa/src/lib/constants.ts)、[Bluesky公式動画ガイド](https://bsky.network/docs/about-bluesky-content/video/)です。参照した仕様と実サービスでの受付確認は区別します。

### Mastodon の投票

`attachments` に `{"type":"poll","options":["一つ目","二つ目"],"expires_in":3600,"multiple":false,"hide_totals":false}` を指定する。本文は必要。画像・動画などの `media` とは同時指定できない。選択肢数・文字数・期限は最新instance設定で lint と送信直前に確認し、未取得時は推測しない。文字数は固定Unicode 17.0.0のextended grapheme clusterで数える（instance側のUnicode版差は未確認）。投票だけなら `write:media` は要求せず、投稿の権限で送る。

選択肢・順序・期限・複数選択・集計非表示の変更は再承認が必要。投稿結果不明は再送しない。CLIでの下書き・承認・送信がこの段の対象で、招待者用承認画面・upload入口の完成を示すものではない。

### Mastodon の引用と引用許可

`attachments: [{"type":"quote","uri":"引用先のローカル数値status ID"}]` と指定します。外部URLを自動検索・取得してIDへ変えません。Bluesky用の `cid` はMastodonでは拒否します。最新instanceの `api_versions.mastodon >= 7` が必要で、版文字列から推測しません。引用先のIDと公開範囲を読み直し、private/direct・欠測・不可視を拒否してから添付uploadやstatus POSTへ進みます。既存のpublic/unlisted制限は維持します。公開前の取得とprovider側処理の間の変更を原子的に防ぐ保証はなく、返却公開範囲が非公開/不明なら不明結果として再送しません。

`post_options: {"quote_approval_policy":"public"}` は public/followers/nobody を指定できます。省略時のprovider既定設定はそのままです。設定だけの本文投稿、引用＋画像/動画、引用＋投票にも対応します。mediaが無い場合は本文が必要で、引用だけの空本文へ勝手に文字を足しません。引用IDと許可設定の変更は再承認が必要です。引用元の許可・ブロック・承認状態の最終判断や実表示はproviderに属し、ローカルfixture通過をその実測結果とはしません。

### Mastodon のリンクと本文の公開設定

`attachments: [{"type":"link","url":"https://example.org/article"}]` は、承認する本文にも同じURLを完全な空白区切りのtokenまたは独立行として書きます。前後の文字と連結して曖昧な場合は `link_text_mismatch` で止まり、ththが勝手に本文へ追加しません。これはローカル入力の明示方法で、Mastodonの全URL検出規則を再現するものではありません。Mastodonの通常の本文URL由来previewに渡す指定であり、title/description/thumbnailを自由に送るcreate APIは無いので、その欄を指定すると拒否します。ththからURLをfetchせず、実際のカード生成・表示はprovider側に委ねます。

ファイル無しの `post_options` でも language/sensitive/spoiler_text/visibility を送れます。本文は必要で、falseや空のspoiler_textも省略しません。public/unlisted制限、既存の承認対象と最終確認、不明結果の再送禁止は共通です。linkは投票/引用/ファイルと合わせられますが、それぞれの既存の排他条件と必要能力を満たす必要があります。parentが無いfocus指定を黙って捨てることはしません。

Worker の media 制限（C17・暫定運用値）: 公開 GET/HEAD/Range は送信元 IP ごとに 120 回/60 秒、署名 control は IP ごとに 600 回/60 秒、upload は subject ごとに 240 回/60 秒です。既存承認系とは別枠で、binding 未設定や超過は後続の署名・DO・R2 処理へ進めません。Cloudflare location 単位の緩やかな制限であり、厳密な課金上限ではありません。同じ IP を共有する利用者が影響を受ける場合があります。429 を理由とした公開要求の自動再送はしません。

Worker の `sanitized` は画像 8,000,000 bytes、動画 1,000,000,000 bytes が上限です。EXIF 除去前の `source` は公開画像上限を流用せず、共通 transport 暫定上限 1,000,000,000 bytes とします。これは媒体の仕様上限ではなく、Web 入口の段で再照合する資源制限です。


掃除の義務は R2 割当の前に account DO に登録します。期限前の予定は異常件数に含めず、期限後に成功を確認できない義務は `cleanup_unconfirmed`、10 回失敗は `cleanup_failed` として、署名付き account status から doctor へ件数と静的理由だけ返します。集約の取得・応答検証に失敗した場合は件数を null、`cleanup_observation_unavailable` とし、0 件正常にはしません。subject、URL、object key は Worker 内に閉じます。削除と集約除去の成功確認後に管理行を消します。24 時間以内の物理削除は保証しません。

管理者は `thth admin media cleanup-retry <account> --by <名前> --json` で期限済みの削除だけを再開できます。承認・投稿・公開 URL の再発行は行いません。退出後にも回復可能です。1 回に最大64件を schedule し、remaining_count が残るときは追加の管理実行が必要です。コマンドは by の妥当性と既存 operator 署名を要求し、結果に件数以外の秘密を出しません。通常の投稿や cleanup alarm が再投稿することはありません。

R2 の書込み中は同じ世代の I/O ticket を永続保持し、alarm は object の不在だけで掃除義務を消しません。遅れて完了した書込みの補償削除に失敗した場合も義務を保持し、書込み完了確認後の cleanup-retry で削除を再開できます。R2 書込み応答の喪失・拒否や isolate 再起動などで I/O の結果自体が不明になった ticket は自動で完了と見なしません。10 回で自動試行を止めて未確認／失敗を表示し、通常の cleanup-retry だけで完全回復できたとは扱いません。この残留状態を公開・再投稿で解消することはありません。

既知 ETag の同一 part 再送は可能ですが、R2 応答を失って結果不明になった part は後続書込みを止めます。通常の再試行で未知 ticket を強制解除しません。


| 管理口 | 作用 | 回復の限界 |
| --- | --- | --- |
| `admin media cleanup-retry` | 期限済みの物理削除を再試行 | 結果不明の書込みを強制解除しないため、本口だけでは回復できない場合があります。再投稿はしません。 |

配布担当は R2 bucket に `media/` prefix・作成から24時間で削除する lifecycle rule を backstop として設定します。Worker の掃除とは独立した運用であり、物理削除時刻の保証ではありません。この実装検証では Cloudflare 側の設定を行っていません。

cleanup-retry の1回64件の選択位置は account ごとに永続保持し、失敗した先頭件だけに固定せず次の対象へ巡回します。未期限の対象は選びません。並行実行でも選択位置を RPC 前に更新し、削除済みの位置からは次の対象へ進みます。


### Mastodon の GIF

GIF は元の構造を検査し、bytes を変えず `image/gif` と alt を送ります。Comment/Application Extension の私的情報まで除去したとは保証しません。送信元GIFは最新instanceの画像MIME・容量・画素数上限で検査し、BMFF動画のframe rateを捏造しません。Mastodon側がimageまたはgifvを返す場合に対応し、202/206の処理中は既知IDで有界に待ちます。複数GIFや静止画との組合せはinstance点数とprovider受理が必要です。providerによる動画化・混在の受理・最終表示は実サービス未測定です。

## Bluesky の外部カード（第7段）

`attachments: [{"type":"link","url":"https://example.org/article","title":"表題","description":"説明"}]` で明示します。title/descriptionは空文字も保持し、本文は空でもカードを付けられます。ththはカード先URLを取得せず、表題や画像の自動抽出もしません。URL・表題・説明・関連参照・画像・説明文の変更は再承認が必要です。

任意の `thumbnail_file` と `thumbnail_alt` を同じlink宣言に指定できます。画像は共通の検査・metadata処理後の公開bytesを送り、上限は通常画像の2MBとは別の **1,000,000 bytes** です。Blueskyのexternal Lexiconにはthumbnail用alt欄がないため、`thumbnail_alt` は承認表示とdigestに保持するローカルの確認文で、APIへalt欄を追加しません。lintにもこの違いを警告します。

`associated_refs: [{"uri":"at://…/collection/key","cid":"b…"}]` は規格に合うstrong referenceを順序どおりexternal.associatedRefsへ渡します。参照先を取得・解決して存在を確かめる機能ではありません。カードと通常mediaの同時指定と未対応の追加post_optionsは理由付きで拒否します。引用との組合せは次節のrecordWithMediaを使います。ファイルが無いカードも公開直前の承認確認とdurableな送信記録を通し、送信結果不明時に自動再POSTしません。実サービスでのカード表示は未測定です。

## Bluesky の引用と添付の組合せ（第7段）

`attachments: [{"type":"quote","uri":"at://…/collection/key","cid":"b…"}]` はURIとrecord CIDを明示します。参照先を取得してCIDを補完する機能ではありません。入力構文を検証してから、そのまま `app.bsky.embed.record` へ渡します。引用だけなら本文は空でも進められます。URI/CIDのどちらを変えても再承認が必要です。

通常画像、明示gallery、動画、外部カードのいずれかと引用を合わせると `app.bsky.embed.recordWithMedia` を使います。画像alt・順序・aspectRatio、動画の処理後blob・字幕・presentation、カードの明示欄は内側のembedへ保持します。引用先の存在・閲覧権限・実クライアントの表示はprovider側の判定で、ローカル試験による保証ではありません。カードと通常画像を同時に詰めるなど、recordWithMediaのmedia欄で表現できない組合せは拒否します。

### Threads のリンクプレビュー

`attachments: [{"type":"link","url":"https://example.com/article"}]` は TEXT 投稿の `link_attachment` へ渡します。本文中の HTTP(S) リンクと指定リンクは重複を除いて最大5つです。画像・動画との併用や、カードの title／description／thumbnail を指定する形はこの口では拒否します。リンク先のページは thth が取得しません。実際のプレビュー内容は媒体側が生成します。

ファイルなしでも URL は承認対象です。公開直前に変更されていれば停止し、作成・公開結果が不明なら自動再送しません。リンクだけの投稿では R2 へのアップロードや公開 URL の発行は行いません。

### Threads の引用

`attachments: [{"type":"quote","uri":"123456789"}]` は TEXT 投稿の `quote_post_id` になります。`uri` には Threads の数字の投稿 ID を指定します。Web ページの URL を入力して ID を検索する口ではありません。リンクプレビューと指定する場合も、両方の値を承認して送信します。引用先へのアクセス可否や引用許可は媒体の応答で確認され、thth が事前に内容を取得したとは扱いません。

引用は TEXT／画像／動画／carousel に付けられます。単体は最終 container、carousel は親だけに quote_post_id を付け、子には付けません。公式例は IMAGE で、CAROUSEL＋引用は配布担当の実媒体確認待ちです。link は TEXT 専用という制限を維持します。Bluesky 用 CID の併記は拒否します。引用先を承認後に変えれば公開を止め、結果不明の公開を自動でやり直しません。

### Bluesky の投稿 metadata

`post_options` の `languages` は `langs`（最大3）、`labels` は selfLabels（最大10・各128 UTF-8 bytes）、`tags` は本文外のタグ（最大8・各640 UTF-8 bytesかつ64 graphemes）として送ります。labels は既知の名前だけに限定しません。languages は言語タグの構文検査で、登録簿へ問い合わせません。空配列も指定した状態として保持します。

`facets` は effective 本文の UTF-8 byteStart／byteEnd と features 配列です。link の表示範囲は URL 文字列そのものでなくても構いません。1範囲に複数 feature を宣言でき、完全同一の feature／facet は重複を除きます。同じ範囲に異なる内容や順序を宣言した場合と、異なる範囲が重なる場合は、それぞれ理由を表示して拒否します。隣接範囲は許可します。URI・DID・ラベル先へ追加問い合わせはしません。

`hashtags: false` では非空 `tags` と明示 tag facet も `hashtags_disabled_by_ledger` で拒否し、黙って取り除きません。空 tags、languages、labels、link／mention facet は使えます。`max_hashtags` は従来どおり本文内の #語だけが対象で、本文外 tags に独自の3件制限は加えません。新しい明示タグの64 graphemesだけ固定 Unicode17 分割を使い、既存本文・topic・自動タグの数え方は維持します。metadata だけでは空本文を投稿できません。

### Threads のプロバイダー GIF

`attachments: [{"type":"gif","provider":"GIPHY","id":"プロバイダーのID"}]` を TEXT 投稿の `gif_attachment` として送ります。現在確認済みの provider は `GIPHY` のみです。ID は承認対象ですが、thth はリモート GIF を取得・検査・R2 保存しません。ID の先にある内容の不変性は保証しません。これはローカル GIF ファイル添付とは別の入口です。ローカル画像・動画との併用は拒否します。

### Threads の投票

`attachments: [{"type":"poll","options":["一つ目","二つ目"]}]` を TEXT 投稿へ付けられます。選択肢は2〜4個、各1〜25 Unicode code pointsで暫定計数します。日本語・絵文字・結合文字もこの単位で数え、実媒体の文字単位は未測定です。画像・動画・link attachment・長文添付・GIFとの併用は拒否します。`expires_in`・`multiple`・`hide_totals` は作成APIで確認されていないため、false等を含め指定自体を `threads/poll_option` で拒否し、黙って落としません。既存の本文計数は変更しません。

### Threads の長文添付

`attachments: [{"type":"text","text":"長い本文"}]` を `plaintext` として TEXT 投稿へ付けます。最大10,000 Unicode code pointsの暫定計数で、日本語・絵文字・結合文字もこの単位です。画像・動画・投票との併用はできません。任意の `link` は `link_attachment_url` に対応し、投稿側 link attachment との二重指定は拒否します。本文・長文内・明示リンクを合わせて同一URLを一つと数え最大5個です。URLは自動取得しません。

任意の `styles` は `offset`・`length`・`styling_info` の配列で、style名は `bold`・`italic`・`highlight`・`underline`・`strikethrough`。範囲の重なりや範囲外は拒否します。offset単位は実媒体未確認のため、stylesを指定する長文はASCII限定です。非ASCIIなら `threads_offset_unit_unverified` で拒否し、推測変換しません。装飾なしの日本語長文は使用できます。本文の従来の文字計数は変更しません。

### Threads の返信管理

`post_options.reply_control` は `everyone`・`accounts_you_follow`・`mentioned_only`・`parent_post_author_only`・`followers_only` を受け付けます。`reply_approvals` は true/false を明示でき、`enable_reply_approvals` として送ります。TEXT・画像・動画の最終container、carouselは親だけが対象です。返信管理だけでは空本文を投稿できません。承認後の値変更は stale として止めます。ghostとの併用規則はghostの実装で別途確認します。

### Threads の画像・動画 spoiler

`post_options.media_spoiler: true` は画像・動画・carouselの最終containerに `is_spoiler_media` を設定します。carousel全体が対象で、子containerへは送りません。falseも明示値として送ります。ファイルを持たない投稿への指定は拒否します。値は承認対象に含まれます。

### Threads の本文 spoiler

`post_options.text_spoiler: true` は本文全体を覆い、falseはspoiler無しを明示します。部分指定には `text_spoiler: [{"offset":0,"length":3}]` を使えます。範囲は最大10個、非負offset・正のlengthで本文内に収めます。配列の順序・重複・重なりは保持して送ります（装飾の重なり禁止とは別）。trueまたは非空配列で範囲を送る場合はC16の暫定ASCII限定が適用され、非ASCII本文は `threads_offset_unit_unverified`。falseと空配列はoffsetを送らないため、この制限はありません。本文が空のtrueは拒否します。本文・範囲の変更は承認の変更です。

Threads `post_options.ghost: true` は本文のみの投稿で、媒体側で24時間後に自動archiveされます。返信・添付・topic/location/Instagram共有・他のpost optionは併用できません（本文spoilerのみ可）。明示falseは通常投稿の設定として送信します。本文が空のghostは拒否します。

Mastodon の MP4/M4A・MOV 音声は、変換せず承認時と同じ bytes を送ります。実instanceが返す音声MIME（MP4系は audio/mp4・audio/m4a・audio/x-m4a、MOVは video/quicktime）と video_size_limit を確認します。音声に画像の寸法・fps制約を当てず、寸法は適用外、秒数が取得できなければ未取得と表示します。

音声の曲名・artist・comment・coverなど非位置metadataは警告して保持します。embedded JPEG/PNG coverも構造検査し、GPSや検査できないXMP/IPTC・maker note・nested thumbnail等があれば静的理由で拒否します。coverを書き換えないので、該当時は元ファイルからcoverを外して再承認してください。位置情報のない個人metadataまで消去したという保証ではありません。音声sample内の文字列はmetadataとして走査しません。別形式の音声・custom thumbnailは各対応表の実装状況を確認してください。

WAV は RIFF/WAVE の PCM・IEEE float と対応する拡張ヘッダを構造検査し、元 bytes のまま送ります。秒数は sample frame 数から算出、幅・高さ・fps は適用外です。曲名・artist・comment は警告して保持します。位置欄や検査できない ID3/iXML/BWF・未知の chunk、RF64/RIFX などはそのファイルだけ理由付きで拒否します。全 WAV codec/拡張の対応を意味しません。受理 MIME とサイズは最新 instance の観測を用います。

BMFF の typed metadata も検査対象です。入れ子の QuickTime metadata・BMP cover・型が未指定の binary 値・未知型は、位置情報がないと確認できないため拒否します。既知の文字・数値型は構造を検査して警告付きで保持します。独自の metadata 拡張を持つ音声・動画は、理由を確認して該当 metadata/cover を外してください。

Mastodon の native FLAC 音声は、最新 instance が `audio/flac` または `audio/x-flac` を受理する場合に送ります。元 bytes を変換せず、幅・高さ・fps は適用外、STREAMINFO の総sample数0は秒数未取得のままです。metadata の型・長さ・文字 encoding と frame header/subframe 境界・CRC を検査します。PCM を復号して MD5 と照合したことや、聴感上の正しさは保証しません。

FLAC の曲名等の UTF-8 comment と検査済み JPEG/PNG PICTURE は警告して保持します。位置キーや埋込画像の位置metadataは拒否します。外部 cover URI は取得せず、application・cuesheet・未知metadata、comment内に別符号化された未検査cover/XMLは `location_metadata_unverifiable` とします。PICTUREの表示寸法宣言だけで画像検査を省略しません。Ogg封入FLACは別形式の対応対象です。音声容量は instance の larger-media 上限で判定し、独自の画像寸法・fps上限は適用しません。

Mastodon の MP3 は MPEG-1/2/2.5 Layer III の frame/header・side information・bit reservoir の範囲・保護 CRC を検査し、元 bytes のまま送ります。秒数は符号化 frame 数に基づく長さで、encoder delay/padding を差し引いた再生時間や PCM 復号の保証ではありません。最新 instance の `audio/mpeg` / `audio/mp3` と容量を確認し、音声の寸法・fps は適用外です。

ID3v2.3/v2.4 の通常の曲名・artist・comment・URL、ID3v1、検査済み JPEG/PNG cover は警告して保持します。位置欄や cover の位置情報は拒否し、cover を外して再準備してください。未検査の unsynchronisation・拡張header・暗号化/圧縮・PRIV/GEOB/未知frame・ID3v2.2・APE等は `location_metadata_unverifiable`、free bitrate/別MPEG layerは `unsupported_attachment_structure` です。正当な HLS の PRIV timestamp も現時点では未対応であり、壊れた音声という意味ではありません。URLを取得せず、sample内を位置文字列として走査しません。

Mastodon の Ogg Opus は page CRC・serial/sequence/continuation と Opus packet の framing・channel mapping を検査し、元 bytes のまま送ります。pre-skip・初期 granule offset・末尾 trim を分け、chain は秒数を合計します。同時に多重化された複数 stream の共通時間軸は推測せず秒数未取得、寸法・fps は適用外です。PCM 復号や聴感の保証ではありません。最新 instance の `audio/ogg` / `audio/opus` と容量を確認します。

OpusTags の通常 UTF-8 comment と検査済み JPEG/PNG の `METADATA_BLOCK_PICTURE` は警告して保持します。位置キー・cover の位置情報・外部 cover・未検査 XML/旧 cover・非zero binary extension/padding は静的理由で拒否します。仕様上は許される未検査拡張も含むため、すべてを壊れた音声とは呼びません。Opus 以外の Ogg codec は別対応であり、封入名だけで受理しません。

Ogg Vorbis も元 bytes のまま、最新 instance が `audio/ogg` を受理する場合に送れます。Vorbis I の識別・comment・setup header、codebook/floor/residue/mapping/mode の構造と参照を検査します。`audio/opus` への読み替えはしません。通常 comment と検査済み JPEG/PNG cover は警告して保持し、位置情報・未検査の拡張は拒否します。

Vorbis の秒数は block の重なりと granule を照合して算出します。初回EOSだけで初期offsetと末尾trimを区別できない場合や同時多重化の共通時間軸は未取得とします。適用外の寸法/fpsを0に補完しません。floor/residueのPCM合成や再生成功を検証したものではありません。仕様上許されるaudio packetの途中切れを、metadataのないことと音質の保証に取り違えないでください。

Mastodon の WebM 音声は Opus / Vorbis track の構造・codec header・packet framing、EBML の型/長さ/CRC と block lacing を検査し、最新 instance が `audio/webm` を受理する場合に元 bytes を送ります。ファイル拡張子だけでは判定しません。秒数は container の Duration 宣言を観測した値で、欠測は未取得、寸法/fpsは適用外です。PCM 復号や実際の再生時間を保証するものではありません。

WebM の通常の曲名・track名・文字tagと検査済み JPEG/PNG cover は警告付きで保持します。位置tag/cover位置情報、未知の binary tag・暗号化/圧縮・未検査拡張は静的理由で拒否します。zeroのVoidと長さ不明Segmentは扱いますが、長さ不明Cluster、他のcodec・動画trackはこの音声項目では未対応です。正当な未対応構造まで壊れた媒体とは呼びません。外部ファイル参照は取得せず、coded sampleの文字列をmetadataとみなして走査しません。

### Mastodonの音声・動画に付けるthumbnail

音声・動画の `media` 項目に `thumbnail_file` と `thumbnail_alt` を両方指定できます。画像を親にはできません。v1とv2の各投稿で同じ形式です。

```yaml
media:
  - file: audio.flac
    alt: 音声の説明
    thumbnail_file: cover.png
    thumbnail_alt: 承認画面で確認する表紙の説明
```

thumbnailは親と同じuploadの `thumbnail` partに入り、投稿の添付件数やmedia IDは増えません。`thumbnail_alt` は承認表示・digestだけに保持します。Mastodonの対応するalt送信欄がないため、親のdescriptionへ混ぜず警告を表示します。外部カードのthumbnailとは別の指定です。

元と公開画像のSHA、alt、親との対応を承認に含めます。JPEG/PNG/WebP等は既存の画像検査・metadata除去を通し、親・thumbnailの差し替えはいずれも再承認が必要です。親と同様にrepo内の安全な通常ファイルだけを読み、公開用snapshotの同じbytesを送ります。

thumbnailのサイズは最新instanceの `image_size_limit`（上流の共通IMAGE_LIMIT）未満であることを確認し、MIMEは報告された対応型で検査します。上流thumbnail検査で確認できたのはMIMEとサイズのため、通常画像の `image_matrix_limit` を独自に追加適用しません。構造検査・sanitizeの限界は従来どおりです。実instanceでの受理・表示は未検証です。

Mastodonの通常の画像・動画・音声も、観測した各サイズ上限の「未満」を必要とします。上流モデルの `less_than` に合わせ、上限ちょうどはupload前に拒否します。音声には動画側のsize上限を使い、画素数・fpsを音声へ適用しません。実instance固有の受理境界は未測定です。


### Mastodon の WebM 動画

WebM の VP8 / VP9 と、併用される Opus / Vorbis 音声を扱います。EBMLの既知の容器構造、型・CRC・block/lacing境界、VP9の既知CodecPrivate項目と位置metadataを検査し、元bytesを変換せず最新instanceの `video/webm`・動画容量・画素数・fps上限で判定します。VP8の不明なCodecPrivate、未知codec/拡張、長さ不明Clusterは理由付き未対応です。位置tag/埋込cover位置情報は拒否し、検査済みの非位置metadataは警告付きで保持します。

寸法は最初のvideo trackのencoded PixelWidth/Height、秒数はcontainer Durationの宣言です。fpsはDefaultDurationがあればその逆数を有界有理数へ丸めて使い、無ければ検査できた全blockの時刻・frame数と最終BlockDurationによる平均です。最終区間が分からなければ `video_rate_unverifiable`、Duration欠測は秒数未取得です。VFRの瞬間最大を独自上限にはしません。providerのFFmpegの有限probe・標準fps推定、codec解析と常に同じ結果になる保証はありません。

符号化した映像の画素復号・再生可能性・映像内の情報やsample payload中の任意データまで検査したとはしません。保持する表示用のcolour/crop/display宣言を変換せず、親thumbnailは既存の音声・動画向け契約に従います。実instanceの変換結果・画面表示は未測定です。

## 承認ページの添付表示（第8段）

サーバー経由の `approval_request` は、承認ページに本文と添付の一覧を一緒に出します。人が見ていない添付を承認させないための段です。

画像は承認ページの中に表示します。VM は承認 session を登録する前に、公開用に sanitize 済みの bytes を Worker へ `kind=sanitized` で upload し、`purpose=preview` の一回限りの capability を発行します。ページの `<img src="/m/…">` はその capability です。capability は承認ページの HTML にだけ現れ、`request_status`、受領、管理ログ、journal のどれにも出しません。ページの CSP は `default-src 'none'` のまま `img-src 'self'` を足すだけで、script も外部読み込みもありません。alt・型付き添付・本文は同じ escape を通します。

動画と音声は文字だけです（「添付 3: 動画 01:12 · sha efefefefefef · alt: …」）。先頭フレームは作りません——元 bytes を変換しない規律をここでも守ります。字幕は「字幕 (ja) sha 343434343434」、型付き添付（投票・引用・リンク・text・GIF）と `post_options` は「型付き添付／公開設定」と題した canonical JSON の `<pre>` です。sha は公開 SHA256 の先頭 12 桁、寸法は公開 bytes の寸法です。

upload か preview の発行に一件でも失敗したら、**session を登録しません**。要求は `media_preview_unavailable` で止まり、job は `failed` で残ります。画像の欠けた承認ページは出しません。

digest は第1段のままです。添付の sha・alt・順序・型付き添付は既に digest に入っており、ページの「digest:」の行も表示も変えません。添付一覧は表示専用で、受領（receipt）には一切入りません。


## 招待者の添付（第9段）

VM も git repo も持たない招待者が、MCP の書く口だけで添付を付けられるようにする段です。**MCP でバイナリは送りません。**サーバが一回限りのアップロード URL を発行し、招待者は curl かブラウザーでその URL に置きます。置いた bytes はサーバが読み戻し、第1段と同じ sanitize を通してから managed repo に入ります。

### 三つの口

1. `thth_media_upload_url {account, kind, size, sha256, mime}` — 種類・大きさ・sha256 を**先に申告**します。サーバは申告を検査し、`state/<account>/media-uploads/<media_id>.json`（mode 600）に控えを書いてから Worker の upload session を開き、`{media_id, upload_url, expires_at, part_size}` を返します。`upload_url` は `https://thth.me/media-upload/<media_id>` で、**この応答にだけ**出ます（`request_status`・管理ログ・journal・標準出力には出ません）。10 分で失効し、もう一度呼ぶと別の URL になります（古い方は放っておけば失効します）。
2. `thth_media_complete {account, media_id}` — 置き終えたことを伝えます。サーバは Worker の `complete` を呼び、署名付きの読み出しで **bytes を取り寄せて sha256 を照合**し、R2 の source を退役（`ack`）させてから sanitize を行い、公開 bytes を `docs/sns/media/<公開 sha256>.<拡張子>` に置いて commit します。応答は `{media_id, public_sha256, format, kind, width, height, duration, warnings}` です。
3. `thth_draft_put` の `media: [{media_id, alt}]` — 確定した添付を下書きに付けます。front matter には `media: [{file: docs/sns/media/…, alt: …}]` として書かれ、**以後は第1段・第2段と全く同じ**（manifest・digest・lint・承認ページ）です。alt は必須です。

### 申告の上限と種類

| kind | 上限（暫定） | 受け付ける mime → 拡張子 |
|---|---|---|
| image | 8,000,000 bytes | image/jpeg → jpg、image/png → png、image/webp → webp、image/gif → gif |
| video | 1,000,000,000 bytes | video/mp4 → mp4、video/quicktime → mov |
| audio | 100,000,000 bytes | （2.13.0 では無し。Worker の転送 mime 集合に音声が無いため `media_mime_unsupported` で断ります） |

上限は `thth/media_uploads.py` の `KINDS` 一箇所にあります。100 MB を超える申告は multipart（5 MiB part）になり、`part_size` を返します。申告が上限・種類・mime のどれかに外れたら、**Worker を一度も呼ばずに**断ります。申告した mime は信用しません——`complete` で実際の bytes を検査し、検査した形式と申告が食い違えば `media_kind_mismatch` / `media_mime_mismatch` で断り、repo には何も置きません。

### 断る理由（静的）

`media_kind_unsupported`・`media_mime_unsupported`・`media_size_exceeded`・`media_unknown`・`media_not_ready`・`media_owner_mismatch`・`media_already_completed`・`media_upload_failed`・`media_upload_unknown`・`media_session_unavailable`・`media_commit_unconfirmed`・`media_kind_mismatch`・`media_mime_mismatch`、および sanitize の理由（`location_metadata_present`・`location_metadata_unverifiable`・`sanitize_unverifiable`・`unsupported_attachment` ほか）。理由にパス・値・URL は入りません。

sanitize で断られた添付は控えが `rejected` になり、二度目の `complete` も `media_already_completed` で断ります。動画の位置 box は拒否します。画像の Exif GPS は第1段のとおり**落とします**（拒否ではありません）——repo に入るのは位置情報の無い公開 bytes です。

### 持ち主

`media_id` は「その account の、その actor が開いた session」です。別の actor・別の account からの `complete` と `draft_put` は `media_owner_mismatch` で、**Worker を一度も呼びません**。Worker 側も `create` で持ち主を結び付けているので、二重に断ります。

### 寿命と後片付け

- upload session（R2 の source）: 600 秒。`complete` の読み出し直後に退役します。R2 の lifecycle 24 時間が backstop です。
- 控え（`state/<account>/media-uploads/<media_id>.json`）: `pending` → `ready` / `rejected` / `unknown`。結果不明は**自動で再試行しません**。もう一度置きたければ新しい URL を取り直します。
- 公開ファイル（`docs/sns/media/…`）: 下書きから参照されている間は残ります。参照されなくなって 1 日たったものは `thth admin media gc <account> --by <人>` が managed repo の commit で消し、件数だけを報告します（名前は出しません）。参照の判定は「追跡されている他のファイルの本文にその名前が出てくるか」で、迷ったら残す側に倒します。
