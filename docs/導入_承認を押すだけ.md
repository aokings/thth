# 導入: 承認を押すだけ

2.11.0 の認可手順。利用者は、masaru から届く認可 URL を開き、自分の SNS アカウントを確認して承認します。利用者自身が VM、THTH の account 台帳、Meta アプリを用意する手順ではありません。招待制の運用で、アプリとサーバは masaru が管理します。

この版で実装するのはサーバ側の CLI と認可の預かり所です。利用者向けの「接続」ページはまだありません。以下の管理コマンドは masaru 側で実行します。ソースがあることと、本番への配布・実認可の成功は別です。インストール済みの版は `thth --version`、稼働 revision は `thth board` で確かめます。

## 1. 利用者: URL を開いて承認する

Threads・対応する Mastodon・X は、masaru が開始した認可 URL をスマホなどのブラウザで開きます。表示されたアカウントと権限を確認し、承認してください。URL には一時的な state が含まれるので、公開場所や LLM の会話へ貼りません。トークンをコピーする必要はありません。本人と台帳が一致したときだけサーバが保存します。

サーバは 2 秒間隔で最大 600 秒待ちます。承認後の code は預かり所で最大 300 秒だけ保持し、一度だけ渡します。X の code は受信時刻から 30 秒未満で交換します。600 秒以内に届かなければ `auth_timeout` で終了し、masaru が新しい認可を開始します。使い終わった URL を再利用しないでください。

預かり所に到達できない場合は、サーバが貼付の代替手順を案内します。戻り URL や code を公開・ログ・LLM へ渡さず、masaru が秘密を表示しない入力で扱います。この最後の手段では、人が code を扱います。X の貼付 code は発行時刻が分からないため直ちに交換し、媒体に拒否されたら認可をやり直します。

**Bluesky は別の入口です。** この版では OAuth を名乗りません。App Password を秘密管理ツールに安全に登録し、masaru が §5 の stdin 経路で渡します。ログインパスワードは使いません。App Password をチャットや原稿に書かないでください。atproto OAuth/DPoP は製品には未実装です。

## 2. masaru: アプリと預かり所の準備

Threads と X は運営者が開発者側でアプリを登録し、callback を **`https://thth.me/callback/`** に設定します。Threads の利用者追加・公開範囲・必要権限は Meta のアプリ設定と審査状態に依存します。管理画面の表示だけで権限の実力を判断せず、認可後に §7 で確かめます。

Mastodon は instance の OAuth metadata から `authorization_code`、S256、正しい同一 origin の endpoint と必要な 5 scope を確認し、instance ごとに自動登録します。不明・非対応なら認可を始めず拒否します。全 instance で使えるという保証ではありません。

預かり所は app secret や token を持たず、一時的な code と read key の hash を扱います。SQLite Durable Object が一度だけの引渡しを調整し、state は 600 秒で失効します。正しい read key の GET は総数 400 回まで。不正な key は受け付けません。期限後の cleanup は payload と hash を削除するため、永久の使用済み名簿は作りません。サーバは毎回新しい乱数 state を作ります。

本番 Worker の配布は別作業です。2.11 のソース検証だけを理由に「配布済み」「実認可済み」とは扱いません。Bluesky OAuth metadata の配信も、この版では行いません。

## 3. masaru: client 準備（Threads は app.env）

`app set` は `--by` を必須とし、標準入力で JSON を受け取ります。値は表示せず、プロジェクト外へ mode 600 で保存します。JSON は秘密管理ツールから渡してください。実値をコマンド引数、シェル履歴、文書、LLM の文脈へ書きません。

| 媒体 | 標準入力 JSON の鍵 | 保存先 |
|---|---|---|
| Threads | `client_id`, `client_secret` | `~/.config/thth/app.env`（既存の `THREADS_APP_ID` / `THREADS_APP_SECRET` 形式） |
| X | `client_id`, `client_secret`, `client_type`, `redirect_uri` | `~/.config/thth/apps/x.env` |
| Mastodon | 手入力しない。`auth` が instance ごとに登録 | `~/.config/thth/apps/mastodon.<origin の hash>.env` |

X の `client_type` は `confidential`、`redirect_uri` は `https://thth.me/callback/` です。public client はこの版では受け付けません。

1Password CLI が別途使える場合の例です。`op` は THTH には同梱していません。参照先は秘密管理側の JSON フィールドです。

```sh
op read "op://THTH/threads-client/json" | thth app set threads --by masaru --stdin
op read "op://THTH/x-client/json" | thth app set x --by masaru --stdin
thth app show --json
```

`app show` は既存の Threads app.env の有無・鍵の有無・mode だけを表示します。X の値を表示するコマンドではありません。Threads の旧 flags `thth app set --app-id <ID> --secret-stdin --by masaru` も互換で残りますが、新しい JSON stdin 経路を優先します。

手動保存と Mastodon の自動登録は `app_set` として管理変更ログへ記録します。client ID も secret も値は記録せず、項目の有無・媒体・実行者だけを残します。app の subject は account ではなく、このイベントで account の通知待ちを作りません。

## 4. masaru: アカウント台帳

招待した利用者の台帳は masaru がサーバ側で作ります。正本は `$THTH_ROOT/accounts/<account>.json`。秘密は台帳にも Git にも置きません。

```sh
thth account add invited-threads --media threads --project invited --handle <handle> --redirect-uri https://thth.me/callback/ --by masaru
thth account add invited-mastodon --media mastodon --project invited --handle <acct> --instance https://<instance> --by masaru
thth account add invited-bluesky --media bluesky --project invited --handle <handle.bsky.social> --by masaru
thth account add invited-x --media x --project invited --handle <username> --by masaru
```

`<…>` は台帳に登録する本人の値へ置き換えます。雛形のダミーが残っていると認可を拒否します。作成時は `production: false`・`scheduled: false` です。認可の成功だけでは本番投稿を有効にしません。既存の来歴と二段階承認・digest・production の条件を維持します。

## 5. masaru: 認可とトークン

通常はサーバ側で次のコマンドを実行し、人向けに 1 行だけ出る URL を利用者へ届けます。認可 URL は運用ログに保存しません。

```sh
thth auth invited-threads --by masaru
thth auth invited-mastodon --by masaru
thth auth invited-x --by masaru
```

認可待ち・stdin 待ち・token 交換 HTTP の間は管理全体のロックを保持しません。最後の保存時に台帳・client・flow・既存 token の世代を再確認します。待機中に新しい認可や token の差替えがあった場合は、古い完了結果で上書きしません。`--paste` は初めから貼付、`--code` は保存済み state の再開で、期限や state を省略して通す口ではありません。

`--rehearse` は保存済み client を読み、RAM の未登録 state で空の預かり所を待ちます。token、state、doctor、管理ログを書きません。実認可を試すコマンドではありません。Mastodon など未登録 client は、この経路では自動登録せず明示的に断ります。

秘密管理ツールから渡す逃げ道は次の形です。

```sh
op read "op://THTH/invited-bluesky/app-password" | thth token set invited-bluesky --stdin --by masaru
op read "op://THTH/invited-threads/access-token" | thth token set invited-threads --stdin --by masaru
op read "op://THTH/invited-mastodon/access-token" | thth token set invited-mastodon --stdin --by masaru
```

Bluesky は台帳の identifier を使って `createSession` で DID/handle を照合し、App Password を mode 600 で保存します。返された JWT は保存しません。Threads/Mastodon の同じ flag は access token 入力です。既存 token があるときは意図を確かめて `--force` を付けます。X の token stdin 入力はありません。X は `auth` を使います。旧 Bluesky `auth` の対話入力も同じ本人検証を通します。

## 6. masaru: 維持と timer

Threads は従来の長期 token 更新規則、Mastodon は expiry/refresh なし、Bluesky は App Password の方式を維持します。既存の VM timer はこの版では変更しません。

X は auth-only です。投稿・採集 adapter はなく、認可や `tweet.write` の取得で投稿を有効化しません。期限は応答の `expires_in` だけから計算し、欠測を 2 時間や Threads の 60 日で補いません。`maintain` は残り 5 分以内を更新対象とする実装です。X が短い寿命を返す場合、従来の 1 日 1 回 timer では維持できません。masaru が期限と運用間隔を別途確認してください。

X の refresh は confidential client の Basic 認証を使います。応答に新しい refresh token がない形は保守的に拒否しますが、媒体が常に新 token を返すという公式保証を主張するものではありません。交換後の応答検査や本人確認に失敗した場合、ローカルの旧ファイルを保持しても、媒体側で旧 refresh token が再利用できる保証はありません。`thth auth <account> --by masaru` で再認可してください。

## 7. masaru: 確認と失敗の読み方

```sh
thth doctor invited-threads --json
thth admin tokens --json
thth admin log --json
thth board
```

`auth_via` は `relay` / `paste` / `token_set`、`auth_observed_at` は認可経路の記録時刻です。`probed_at` は明示的な doctor/管理者 probe の時刻で、認可しただけでは更新しません。古い probe は履歴として残しますが、credential が変わった場合は現在の権限推定に使いません。内部の世代 hash は公開レポートに出しません。

scope は応答の記録を優先します。Mastodon の応答 scope がない場合だけ、現在 credential の probe を根拠とした推定を別表示します。通信失敗は scope 不足と決めつけません。Bluesky の OAuth scope は不適用なので不明のままです。X の doctor は auth-only の未対応を説明し、probe 0 件を「異常なし」にはしません。HTTP/MCP はこの時刻付き記録を読むだけで、認可や probe を起動しません。

保存と管理ログは短い transaction で扱います。追記前の失敗は元の token/client を復元します。部分追記は `outcome_uncertain`、全行追記後の fsync 失敗は `durability_unconfirmed` と表示し、変更を保持します。再実行する前に状態とログを確認してください。token とログの確定後に doctor 観測だけ保存できなかった場合、認可は成功のまま `auth_observation_not_recorded` を表示します。観測失敗を probe 成功に読み替えません。

このガイドはソースの実装契約です。ローカル fake HTTP・障害注入の検証、Claude の read-only rehearse、本番認可、配布、全版検収はそれぞれ別の証拠です。実 SNS への認可・X の実 refresh rotation・利用者の通し導入はこの文書だけでは確認済みとしません。書く口の HTTPS/MCP 公開と退出は後版で、この版には追加しません。
