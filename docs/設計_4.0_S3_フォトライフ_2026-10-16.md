# 設計: 4.0 S3 — はてなフォトライフ: 画像を上げる・依存する画像の指紋・画像だけ成功の扱い（2026-10-16）

書いた人: THTH開発 第3 のサブエージェント（Claude Fable 5.1）。[計画_4.0](計画_4.0_2026-10-15.md) §4.1 の S3 を、[設計_4.0_S1](設計_4.0_S1_主体とブログとレーン_2026-10-16.md) と [設計_4.0_S2](設計_4.0_S2_はてなブログ_2026-10-16.md) が main に入ったあとの形（3.25.0・`b2bfa91`）の上に、実装者（Opus の書き手）がそのまま作れる粒度で決める文書。**コードは 1 行も変えていない。**

S2 は画像つきの記事を `images_unsupported_until_s3`（`hatena_convert.REFUSE_LOCAL_IMAGES`・`RULES` の `images`）で断っている。S3 はこれを外し、記事の中の手元の画像をフォトライフに上げ、本文の画像をその参照に置き換えて出せるようにする。はてなの口座はまだ無い（masaru が登録中）ので、S2 と同じく「実機なしで作れて fake で試験できる範囲」（§2〜§14）と「実機でしか確かめられないこと」（§15）を分ける。

## 0. 一言で

**画像は、承認のあと・公開の直前に、timer が同じロックの中で 1 枚ずつフォトライフへ上げる（記事の POST の前）。上がった画像は「中身の sha256 → フォトライフの id」の台帳を主体ごとに持ち（`principal_state/<p>/fotolife/<sha256>.json`）、同じ中身は 2 度上げない（使い回す前に GET で在ることを確かめる）。承認の指紋は S1 の `thth-hatena-entry-1` のまま 1 バイトも変えない——本文は `![alt](<path>)` の元の形で指紋に入り、画像の中身は `images`（path＝sha256）で固定される。フォトライフの id は承認の時点には無いので指紋には入れず、送る直前に本文へ埋める。画像だけ上がって記事が出なかった・分からなかったときは、画像の台帳が残るので次の試みで使い回す（記事の側の倒し方は S2 のまま: 4xx＝出ていない・5xx と時間切れ＝分からない）。画像の上げ自体が分からないときは、再び上げる前にフォトライフの一覧（`/atom/feed`）を題で照合する。容量と形式は公式に数が無いので THTH の側の上限で断る。**

### 1.2 公式の頁（10/16 に開いて確かめた・JST）

- **フォトライフ AtomPub**（https://developer.hatena.ne.jp/ja/documents/fotolife/apis/atom ・10/16 22:30 ごろ WebFetch）:
  - 「参照元の AtomAPI 仕様はドラフト段階のため、今後この API の実装や文書が変更される可能性があります」と冒頭にある。
  - 認証は OAuth か WSSE。**OAuth は GET に `read_private`、POST／PUT／DELETE に `write_private`**（明記）。変更履歴「2013 年 10 月 3 日: OAuth に対応」。
  - PostURI `/atom/post`（POST だけ・成功 201・`Location` に EditURI）。送る XML: `title`・`content mode="base64" type="<画像の Content-Type>"`（例 `image/jpeg`）・`dc:subject`（**上げる先のフォルダ名。無ければ自動で作られる**）・`generator`（上げる道具の名。設定画面で道具ごとにフォルダを振り分けられる）。名前空間は **`http://purl.org/atom/ns#`（Atom 0.3）**・`xmlns:dc="http://purl.org/dc/elements/1.1/"`。
  - 返る XML: `id`（`tag:hatena.ne.jp,2005:fotolife-<user>-<ID>`）・`link rel="alternate" type="text/html"`（写真のページ `http://f.hatena.ne.jp/<user>/<ID>`）・**`link rel="service.edit"`**（EditURI `http://f.hatena.ne.jp/atom/edit/<ID>`）・`hatena:imageurl`（`http://f.hatena.ne.jp/images/fotolife/<頭文字>/<user>/<日付>/<ID>.jpg`）・`hatena:imageurlsmall`（`…_m.gif`）・**`hatena:syntax`（`f:id:<user>:<ID>:image`）**。名前空間 `xmlns:hatena="http://www.hatena.ne.jp/info/xmlns#"`。`hatena:imageurlmedium` は記載なし。原文の `dc:subject` の閉じタグは `dc:subjetct` と綴りが誤っている（応答を読むときに名前で決め打ちしない理由）。
  - EditURI `/atom/edit/<ID>`: GET 200（entry）・PUT 200（**題だけ変えられる。画像の差し替えは不可**・消して上げ直す）・DELETE 200。FeedURI `/atom/feed`（GET だけ・件数は利用者のフォトライフの設定に依る）。
  - **記載なし**: 画像の形式の一覧・1 枚の容量・月の容量・回数の上限・エラーの状態番号の一覧（「正常時と異なるステータスコードとエラーメッセージをヘッダで返す」とだけ）・`https` の URL（例はすべて `http://`）。
- **OAuth の scope**（https://developer.hatena.ne.jp/ja/documents/auth/apis/oauth/scopes ・10/16）: `read_public`・`write_public`・`read_private`・`write_private` の 4 つ。「write_private を許可したからといって read_public が必要な操作も可能になるとは限らない」。サービスごとの対応は書かれていない。
- **OAuth 対応 API 一覧**（https://developer.hatena.ne.jp/ja/documents/auth/apis/oauth/apis ・10/16）: はてなブログ AtomPub・ブックマーク REST API などが載り、**フォトライフは載っていない**（調べ §19 の食い違いのまま）。フォトライフの API の文書の側は OAuth 対応と明記しているので、**OAuth で通ると見て作り、実機の最初に確かめる**（§15 の 14。通らなければ §11 の代わりの形）。
- **`https://f.hatena.ne.jp/atom/post`・`/atom/feed`・`/atom`**（10/16 22:39 JST・`curl` で認証なしの GET）: いずれも **401**。`http://f.hatena.ne.jp/atom/post` は **302 → `https://f.hatena.ne.jp:443/atom/post`**。つまり https の入口は在り、平文は https に飛ばされる。`httpsafe` は平文を断るので、THTH は最初から `https://f.hatena.ne.jp` に送る（公式の例の `http://` は使わない）。
- **フォトライフのヘルプ**（https://f.hatena.ne.jp/help → https://hatena.zendesk.com/hc/ja/sections/18070073813785 に 302・10/16）: 飛び先が 403 で読めなかった。容量・形式の現行の数は**確かめられていない**（検索で出るのは 2005〜2012 年の記事: 当時は月 30 MB、有料で 3 GB。古いので使わない）。

## 2. 言葉

- **画像**: 記事（`article_source`）が `![alt](path)` で参照する、レーンの repo の中のファイル。他所の画像（`https://…`）は依存に数えない（S1・S2 のまま）。
- **中身の指紋**: 画像ファイルの sha256（`source_sha256`）。承認の指紋の材料であり、フォトライフの台帳の鍵。
- **フォトライフの id**: EditURI の末尾（`/atom/edit/<ID>` の `<ID>`）。`hatena:syntax` の `f:id:<user>:<ID'>:image` の `<ID'>` は `<ID>` に形式の字（例 `j`）が付いた形と**推測**している（公式の例は両方 `XXXXXXXXXXXXXX` で区別がつかない）。台帳には両方をそのまま持つ。
- **配置**（placement）: 本文の 1 つの画像の参照を、どのフォトライフの id に置き換えるか。`{path → fotolife}` の対応。
- **送る本文**（`body_sent`）: 承認した本文（`m["body"]`・画像は元の形）に配置を埋めたもの。`sent/` の `text`・読み戻しの比べ・次の更新の `base_readback_sha` はこちら。承認の指紋と 1 段目の表示は元の形（§5）。

## 3. 上げる時機

### 3.1 比べた案

| 案 | いつ | 利点 | 欠点 |
|---|---|---|---|
| (a) 承認の 1 段目（見せるとき） | 人が見る前 | 1 段目に本物の URL を出せる | 承認していないものが外（フォトライフのアルバム）に出る。見るだけで書き込みが起きる |
| (b) 承認の 2 段目（刻むとき） | 承認の直後 | 公開の時刻に上げる作業が減る | 予約が 3 日先でも画像だけ先に出る。遠くの道（thth.me）の `schedule_request` の中で HTTP の書き込みが起きる（今は repo と台帳しか書かない） |
| (c)（推し） **timer が公開の直前に、同じロックの中で、記事の POST の前に** | `throw_chosen` の 3b と 4 の間 | 承認済みのものしか出ない。画像が外に出るのは記事が出る数秒前。失敗の扱いが記事の 1 run に閉じる。thth.me の道に書き込みを足さない | 公開の 1 run が長くなる（画像 1 枚ごとに POST 1 回） |
| (d) 別の段（timer が先に上げておく run） | 公開の前の run | 公開の run が短い | 段が 1 つ増え、上げた画像と承認の対応を別に持つことになる |

**(c) にする。** 「承認したものだけが外に出る」が THTH の芯（計画 §1）で、(a)(b) はそれを画像で破る。(d) は (c) で遅いと分かってから分ければよい（§3.2 の順を 1 つの関数にしておけば、別の段に移せる）。

### 3.2 `throw_chosen` の順（差し込む位置）

S2 の順（§1.1）の **3b（記法）と 4（inflight）の間**に「3c 画像」を入れる。create と update だけ。delete は画像を触らない。

```
3c. 画像（hatena_fotolife.ensure_uploaded(principal_cfg, account_cfg, m, adapter_f, log) -> placements）
    - m["images"] の各 {path, source_sha256, bytes} について、主体の画像の台帳（§4）を引く
      - 台帳にあり state=uploaded → GET /atom/edit/<id> で在ることを確かめる（§4.3）
          200 → 使い回す／404 → 台帳の行を消して上げ直す／ほかの失敗 → `fotolife_check_failed`（出ない側・次の run）
      - 台帳にあり state=unknown → 先に /atom/feed で題を照合（§7.2）。見つかれば uploaded に直して使い回す。無ければ上げる
      - 台帳に無い → 上げる（§6）。201 なら台帳に書いてから次の画像へ
    - 1 枚でも「出ていない」（4xx）なら、その場で止める（`fotolife_rejected`・ロールバックしない・上がった分は台帳に残る）
    - 1 枚でも「分からない」なら、台帳に unknown を書いて止める（`fotolife_ambiguous`・次の run が照合する）
    - 全部そろえば placements を返し、m["body_sent"] = hatena_convert.embed_images(m["body"], placements)
4.  inflight …（以降 S2 のまま。adapter に渡す body は m["body_sent"]・images は渡さない）
```

- ロックは repo → principal → account（S1 §4.3）の中。画像の台帳は主体の物なので、**主体のロックの中でしか書かない**（2 レーンが同じ主体で同時に走ることは無い。同じレーンの 2 process は account で待つ）。
- 画像の段で止まったときは **inflight も配信の台帳の行も書かない**（記事はまだ何も送っていない。台帳は `wanted`／`published` のまま）。run のログに 1 行と `run("post", "error", <符丁>)`。終了コードは「次の run で解けるもの」（`fotolife_ambiguous`・`fotolife_check_failed`・`fotolife_daily_limit`）は 1、「人が直すもの」（`fotolife_rejected*`・`image_*`）は 2（`action="refused"`）。
- dry-run（`rehearsal`）は上げない。「画像 n 件を上げるはず（うち m 件は上がっている）」をログに出す。

## 4. 画像の台帳（同じ画像を 2 度上げない）

### 4.1 比べた案

| 案 | 置き場 | 利点 | 欠点 |
|---|---|---|---|
| A | 配信の台帳の `images[]` だけ（S1 の予約） | 新しい置き場が要らない | 同じ画像を別の配信（別の記事・同じ記事の update）で使うと、また上げる。台帳をまたいだ検索が要る |
| B（推し） | **主体ごとに 1 画像 1 ファイル `principal_state/<p>/fotolife/<sha256>.json`**。配信の台帳の `images[]` には上がった結果を写す | 鍵が中身の指紋なので、どの記事・どの配信からでも同じ画像は 1 度。主体＝はてな ID＝フォトライフの口座と単位が一致する | 置き場が 1 つ増える。配信の台帳との二重持ち（ただし正本は主体の側、`images[]` は見せるための写し） |
| C | 主体に 1 本の `fotolife/index.json` | ファイルが 1 つ | 画像が増えるほど読み書きが重い。`replace_at` の衝突の範囲が広い |

**B にする。** 「同じ画像を 2 度上げない」を配信をまたいで満たせるのは B だけ。写しを持つ懸念（CLAUDE.md §4「写しを作らない」）は、配信の台帳の `images[]` を「その配信で何を使ったかの記録」（履歴）と位置づけ、使い回す判断には使わない（判断は主体の台帳だけ）ことで分ける。

### 4.2 形 `principal_state/<p>/fotolife/<sha256>.json`

```json
{
  "schema": "thth.fotolife-image/1",
  "sha256": "7e3f…（64 桁）",
  "bytes": 312004,
  "content_type": "image/jpeg",
  "state": "uploaded",
  "fotolife_id": "20261020075901",
  "syntax": "f:id:kopicha-aoki:20261020075901j:image",
  "edit_uri": "https://f.hatena.ne.jp/atom/edit/20261020075901",
  "image_url": "https://cdn-ak.f.st-hatena.com/images/fotolife/k/kopicha-aoki/20261020/20261020075901.jpg",
  "title": "arabica.jpg thth:7e3f0a1b2c3d",
  "folder": "thth",
  "uploaded_at": "2026-10-20T08:00:12+09:00",
  "first_seen": {"account": "kopicha-hatenablog", "delivery": "dl_3f9c2a7e1b4d", "path": "images/arabica.jpg"},
  "checked_at": "2026-10-20T08:00:13+09:00"
}
```

| 欄 | 決め |
|---|---|
| ファイル名 | 中身の sha256（64 桁の小文字）。`name_is_safe` の代わりに `^[0-9a-f]{64}$` で検査 |
| `state` | `uploaded`（201 が読めた）・`unknown`（送ったが結果が分からない・§7.2）。消したときはファイルを消す（`deleted` の状態は持たない。4.0 では消す口を作らない・§8） |
| `fotolife_id` | EditURI の末尾。`^[0-9]{1,20}$` |
| `syntax` | 応答の `hatena:syntax` をそのまま。`f:id:<hatena_id>:` で始まらなければ **`fotolife_user_mismatch`**（別の ID の口座に上がった＝token が別人。台帳には書かず `unknown` にもしない＝「出ていない」扱いで止める。人が `thth principal auth --force`） |
| `image_url` | 応答の `hatena:imageurl` をそのまま（スキームも直さない。本文には埋めない・§5.2） |
| `title` | 送った題。`<basename> thth:<sha256 の先頭 12 桁>`（§7.2 の照合の鍵・§10） |
| `first_seen` | 最初に上げたときの口座・配信・パス。見せるためだけ |
| `checked_at` | 最後に GET で在ることを確かめた時刻 |

- 書き方は `server_files.replace_at(expected=…)`・0600・置き場は `server_files.directory(create=True)` で 0700（`deliveries._write` と同じ形）。読めないファイルは「無い」とみなさず **`fotolife_ledger_unreadable` で止める**（壊れた台帳を無視して上げ直すと二重になる）。
- `images[]`（配信の台帳）には、出たあと（`_record_outcome` の `fields`）に `fotolife_id`・`syntax`・`image_url`・`uploaded_at` を写す。`MUTABLE_FIELDS` に `images` は既にある。

### 4.3 使い回す前の確かめ

- 台帳に `uploaded` があっても、**毎回 `GET /atom/edit/<id>`（read_private）で在ることを確かめてから**使う。人がフォトライフの画面で消していれば 404 → 台帳のファイルを消して上げ直す。200 でも応答の `id` の末尾が `fotolife_id` と違えば `fotolife_check_failed`（出ない側）。
- 確かめの GET は 1 枚 1 回（公開 1 run あたり画像の数だけ増える。`READ_TIMEOUT` 30 秒）。`checked_at` を更新する。
- 確かめが失敗（5xx・時間切れ）→ その run は出ない（`fotolife_check_failed`・exit 1）。上げ直しはしない（在るかもしれない）。

## 5. 承認の指紋との整合

### 5.1 指紋は変えない

- `thth-hatena-entry-1` の 14 項目はそのまま。`body_sha256` は**画像が `![alt](<path>)` の元の形**の本文、`images` は `path=sha256`。S1 §6.2 の決め（「承認の時点では fotolife_id が無いので、指紋では元の形のまま置き、`images` で中身を固定する」）をそのまま実装する。`FINGERPRINT_VERSION`・`fingerprint_golden.GOLDEN` は触らない（T-S3-5b）。
- 画像の中身を 1 バイト変えれば `images` が変わり、指紋が変わる → 承認済みの原稿は `approval_stale`（画像だけ差し替えても修正として検出される・計画 §3.3）。alt を変えれば `body_sha256` が変わる。
- フォトライフの id は承認の対象にしない。理由: 承認の時点に無い・同じ中身なら id が違っても見え方は同じ・id を入れると「上げてから承認」（§3 の (a)(b)）になる。

### 5.2 送る直前の置き換え `hatena_convert.embed_images(body, placements) -> str`

- `RULES` の外に置く（`render()` の出力＝承認の指紋の材料は変えない。**`VERSION` は `s2-rules-1` のまま**）。`hatena_publish` が `m["body"]` と配置から `m["body_sent"]` を作る 1 か所だけが呼ぶ。決定的。
- 置き換えの形（比べた案）:

| 案 | 形 | 利点 | 欠点 |
|---|---|---|---|
| (i)（推し） **フォトライフ記法** `[f:id:<hatena_id>:<ID'>:plain]` | はてなの編集画面の「写真を投稿」が入れるのと同じ形。URL の形（`f.hatena.ne.jp` か CDN か・http か https か）に依らず、はてなが正しい URL で描く | **Markdown モードでフォトライフ記法が効くことは公式の頁で確かめていない**（推測: 効く。はてなブログの写真の挿入は Markdown モードでもこの記法を入れる）。alt が落ちる（`:alt=` の付け方は未確認） |
| (ii) Markdown `![alt](<hatena:imageurl>)` | 純粋な Markdown。alt が残る | `hatena:imageurl` が https の CDN で返るかが未確認（公式の例は `http://f.hatena.ne.jp/images/…`）。http のままでは混在コンテンツ。はてなが URL を付け替えたら壊れる |
| (iii) HTML `<img src=… alt=…>` | alt が残る | (ii) と同じ URL の問題 |

  **(i) にする**。ただし実機の 16（§15）で (i) が描かれなければ (ii) に切り替えられるよう、`embed_images` は `form`（`fotolife_plain`／`markdown_url`）を引数に取り、既定を module の定数 `IMAGE_FORM = "fotolife_plain"` に置く。両方を fake で試験する（T-S3-3c）。alt は (i) では `[f:id:…:plain:alt=<alt>]` を**試さない**（未確認の記法を本番の本文に入れない）。alt を残したいときは実機で `:alt=` が効くと分かってから足す（§15 の 16）。
- `<ID'>` は台帳の `syntax` の 3 番目の欄（`f:id:<user>:<ID'>:image` の `<ID'>`）をそのまま使う（推測の形式の字を THTH が付けない）。
- 置き換える範囲は `image_paths()` が数えた参照と**同じ**: コードの囲み（```・~~~）とコードの span の中は数えず・置き換えない（`_absolute_links` と同じ区切り方を `_images` にも使う。S2 の `_images` は囲みの中も拾っていたので、**囲みの中に画像の参照がある記事では `images` が変わり承認が古くなる**——本番にはてなの原稿は無いので困るものは無い。T-S3-3d）。
- `![alt](path "title")`・`![alt](<path>)` も同じ 1 つの参照として置き換える（`_IMAGE_RE` が受ける形の全部）。他所の画像（`https://…`）は触らない。

### 5.3 読み戻し・`sent/`・次の更新

- `_record_outcome`: `readback_differs` は **`m["body_sent"]`** と比べる（今は `m["body"]`）。`sent.write(text=m["body_sent"])`。台帳の `readback_sha` は応答の `content` の指紋（送る本文の形＝置き換えたあと）。
- 次の `update` の `base_readback_sha` は台帳の `readback_sha`（置き換えたあとの形）。PUT の前の GET も置き換えたあとの形が返るので、比べはそのまま合う（S2 §6 を変えない）。
- 承認の 1 段目の **update の差分**（`display_lines` の `_previous_text`）: 今は `sent/` の `text`（置き換えたあと）と今回の `m["body"]`（元の形）を比べるので、画像の行が毎回「変わった」と出る。**前の本文は承認の控え `deliveries/<delivery>.<指紋 12 桁>.body.md`（元の形）から読む**（指紋は台帳の最後の `published` の行の `approved_sha`）。控えが無ければ `sent/` の `text` に倒し、「画像の行は置き換えのため差が出ます」と 1 行添える。

## 6. adapter `thth/adapters/fotolife.py`

### 6.1 置き場と口

- `thth/adapters/fotolife.py`（新）。`base.Adapter` は継がない・`REGISTRY` に載せない（hatenablog と同じ理由）。`hatenablog.HatenaBlogAdapter` とは**別のクラス**（入口のホストが違う・XML の名前空間が違う）。認証の材料（token・consumer・`redact.register_secret`・`_user_agent`・`_request` の形）は `hatenablog` から**関数として切り出して共有**する（`thth/adapters/hatena_common.py`（新）に `request_signed(method, url, *, headers, body, timeout, consumer, token)` と `load_credentials(account_cfg, principal_cfg)` を置き、`hatenablog.factory` もそれを使う。既存の試験が緑のまま動くこと）。
- `factory(account_cfg, principal_cfg) -> FotolifeAdapter`。作れなければ `hatena_publish.AdapterUnavailable(code)`（`token_missing` 等・hatenablog と同じ符丁）。差し込み口は `hatena_fotolife.ADAPTER_FACTORY`（None なら本物）。試験は `throw_once(fotolife_factory=…)`… ではなく、**`hatena_publish.throw_chosen` の `adapter_factory` と同じ引数の形で `fotolife_factory` を 1 つ足す**（`core.throw_once` の引数に 1 つ足す・既定 None）。
- 口:

```
upload(*, data: bytes, content_type: str, title: str, folder: str) -> UploadResult
get_image(*, fotolife_id: str) -> dict            # 200 なら {id, fotolife_id, syntax, image_url, edit_uri, title}
recent(*, pages: int = 1) -> list[dict]           # /atom/feed（§7.2 の照合）。件数は設定次第
UploadResult(ok, ambiguous, fotolife_id, syntax, image_url, edit_uri, error, status)
```

- URL は **`https://f.hatena.ne.jp`** 固定（`BASE`）。`/atom/post`・`/atom/edit/<id>`・`/atom/feed`。`<id>` は `^[0-9]{1,20}$` でなければ `fotolife_id_invalid`（台帳の `edit_uri` は組んだ URL と比べるだけ・違えば `edit_uri_mismatch`。hatenablog §3.1 と同じ線）。
- 画像の削除（DELETE）・題の変更（PUT）は **4.0 では作らない**（口を増やさない。消すのは人がフォトライフの画面で）。

### 6.2 送る XML

```xml
<?xml version="1.0" encoding="utf-8"?>
<entry xmlns="http://purl.org/atom/ns#" xmlns:dc="http://purl.org/dc/elements/1.1/">
  <title>arabica.jpg thth:7e3f0a1b2c3d</title>
  <content mode="base64" type="image/jpeg">…base64…</content>
  <dc:subject>thth</dc:subject>
  <generator>thth</generator>
</entry>
```

- 名前空間は**公式の例のまま Atom 0.3**（`http://purl.org/atom/ns#`）。`ET.register_namespace("dc", …)` は process 全体に効く（S2 監査 低-9 と同じ懸念）ので、`hatenablog` と同じく module の先頭で 1 度だけ登録し、Atom 0.3 は既定の名前空間（接頭辞なし）にせず**文字列で組む**（`xml.sax.saxutils.escape` で題・フォルダをエスケープ）。ET の既定の名前空間の登録が 2 つ（Atom 1.0 と 0.3）でぶつかるのを避けるため。
- `Content-Type: application/atom+xml; charset=utf-8`（**推測**。公式に記載なし。401 以外の 4xx（400・415）が返れば §15 の 14 で `application/xml` を試す）。
- base64 は `base64.b64encode(data).decode("ascii")`（改行を入れない）。
- 題・フォルダに制御文字・`\x1e`・`\x1f` があれば `fotolife_title_invalid`（送る前）。

### 6.3 応答の読み `parse_photo(bytes) -> dict`

- 名前空間を**決め打ちしない**: `{*}entry`・`{*}id`・`{*}link`・`{*}imageurl`・`{*}syntax` のように local name で探す（公式の例の綴りの誤り `dc:subjetct` と、Atom 0.3／1.0 のどちらで返るか分からないことへの備え）。
- 欄: `fotolife_id`（`link rel="service.edit"` の `href` の末尾の数字。無ければ `Location` ヘッダの末尾。どちらも無ければ `response_invalid`）・`syntax`（`hatena:syntax`。無ければ `response_invalid`）・`image_url`（`hatena:imageurl`。無くても通す）・`edit_uri`・`title`・`id`。
- `DOCTYPE`・`ENTITY` があれば `response_invalid`（hatenablog と同じ）。応答の上限 4 MiB。

### 6.4 断りと結果不明の分け方（`UploadResult` への写し）

S2 §3.5 の線（4xx＝出ていない・5xx と時間切れと読めない応答＝分からない）に揃える。

| 起きたこと | `ok` | `ambiguous` | `error` | 画像の台帳 | 公開の run |
|---|---|---|---|---|---|
| 201・読めた・`syntax` の user が `hatena_id` | 真 | — | — | `uploaded` を書く | 次の画像へ |
| 201・`syntax` の user が違う | 偽 | 偽 | `fotolife_user_mismatch` | 書かない | 止める（exit 2・`principal auth --force` を案内） |
| 2xx だが XML が読めない・`syntax` が無い・201 以外の 2xx | 偽 | **真** | `response_invalid`／`fotolife_http_<code>` | `unknown` | 止める（exit 1・次の run が §7.2 で照合） |
| 400・415 | 偽 | 偽 | `fotolife_rejected_<code>` | 書かない | 止める（exit 2） |
| 401・403 | 偽 | 偽 | `hatena_auth_rejected` | 書かない | 止める（exit 2・案内は S2 と同じ。**フォトライフだけ 401 なら OAuth が通っていない可能性**＝§11） |
| 413 | 偽 | 偽 | `fotolife_too_large` | 書かない | 止める（exit 2・「画像を小さくするか fotolife.max_image_bytes を下げる」） |
| 429 | 偽 | 偽 | `provider_rate_limited` | 書かない | 止める（exit 1・次の run。再試行しない） |
| その他の 4xx | 偽 | 偽 | `fotolife_http_<code>` | 書かない | 止める（exit 2） |
| 5xx | 偽 | 真 | `fotolife_http_<code>` | `unknown` | 止める（exit 1） |
| 時間切れ・`URLError`・`OSError`・接続断 | 偽 | 真 | `fotolife_transport_failed` | `unknown` | 止める（exit 1） |
| `RedirectBlocked`（書き込みのあとの別ホストへの 3xx） | 偽 | 真 | `redirect_blocked` | `unknown` | 止める（exit 1） |
| `EndpointRejected`（接続の前） | 偽 | 偽 | `endpoint_rejected` | 書かない | 止める（exit 2） |
| 応答が大きすぎる | 偽 | 真 | `response_too_large` | `unknown` | 止める（exit 1） |

- 「止める」は §3.2 のとおり **inflight も配信の台帳も書かない**。上がった画像（この run で `uploaded` を書けた分）は台帳に残り、次の試みで使い回す。これが「画像だけ成功」の形の 1 つ目（2 つ目は §7.1）。
- 時間切れ: 上げは **120 秒**（`min(口座の timeout, 120)`。8 MiB の base64 は 11 MB 弱になるので 60 秒では短い）。GET は 30 秒。
- 再試行しない・sleep しない（S2 と同じ）。

## 7. 画像だけ上がって記事が出なかった／分からないとき

### 7.1 記事の側が失敗したとき（画像は全部上がった）

| 記事の側 | 配信の台帳（S2 のまま） | 画像の台帳 | 次の試み |
|---|---|---|---|
| 4xx（出ていない） | `BEFORE[op]` に戻す・inflight 消す | そのまま（`uploaded`） | 次の run が同じ原稿を拾い、§4.3 の GET で在ることを確かめて使い回す。上げ直さない |
| 404（update・delete の外で消された記事） | `conflict`（`entry_missing`） | そのまま | 人が見る。画像は残る |
| 5xx・時間切れ（分からない） | `unknown`・inflight 残す | そのまま | 人が `thth inflight <口座> resolve` で解く。`--not-published` なら次の run が使い回す。`--published` なら `_record_outcome` が `images[]` に写す（配置は台帳から組み立て直せる・§7.3） |
| 出たが `conflict`（`published_elsewhere`・`syntax_mismatch`） | `conflict` | そのまま | 人が見る |

- 上がった画像を**消さない**（消すのは書き込みで、記事が本当に出ていないかを画像の側は知らない。残しても害は「アルバムに記事の無い画像が 1 枚ある」だけ）。
- `thth deliveries <口座>` の 1 行表示に `画像 3 件（上がっている 3）`／`画像 3 件（上がっている 1・結果不明 1）` を出す（主体の台帳を sha256 で引いて数える）。

### 7.2 画像の上げ自体が分からないとき（`unknown`）

- 台帳に `state: unknown`・`title`・`sent_at` を書いて止める（§6.4）。
- 次の run（同じ原稿を拾う）の 3c で、`unknown` の画像は**上げ直す前に `GET /atom/feed` を読み、`title` が一致する写真を探す**（1 頁。`pages` は主体の `fotolife.feed_pages`・既定 1）。見つかれば `uploaded` に直して（`fotolife_id`・`syntax`・`image_url` を埋め）使い回す。見つからなければ上げる（**二重の可能性を受け入れる**: 一覧の件数は利用者の設定に依り、古い写真は一覧から落ちる。その代わり `title` に指紋を入れてあるので、人がフォトライフの画面で `thth:<12 桁>` を検索すれば二重を見つけられる）。
- 一覧の GET が失敗したら `fotolife_check_failed`（出ない側・次の run）。上げ直さない。
- 人が解く口は作らない（`thth inflight` は記事の inflight の口。画像は次の run が自分で照合する）。見る口は `thth fotolife <主体>`（§12.4）。

### 7.3 `resolve --published` のとき

`hatena_publish.resolve` は `material(fm, …, ledger=before)` で材料を組み立て直す。S3 は続けて `hatena_fotolife.placements_from_ledger(principal, m["images"])`（**HTTP を打たない**。主体の台帳の `uploaded` の行だけから配置を作る）で `m["body_sent"]` を作り、`_record_outcome` に渡す。台帳に無い画像があれば配置は作れない → `body_sent` は None とし、`readback_differs` の比べは飛ばして（印を付けない）`images[]` には `fotolife_id` 無しで写す（`NO_READBACK_NOTE` と同じ調子で 1 行）。送ったときには全部そろっていたはずなので、無いのは人が台帳を消したときだけ。

## 8. 記事の更新で画像が変わったとき

- `material()` は今の記事から `images` を数え直す。中身が変われば sha256 が変わり、承認の指紋が変わる（§5.1）→ 承認し直す（`thth approve`）。
- 新しい sha256 は台帳に無いので上げる。同じパスでも中身が違えば別の画像（フォトライフでは差し替えができないので、これが正しい）。
- 参照されなくなった古い画像（差し替えた元・記事から外した画像・`delete` した記事の画像）は **4.0 では消さない**（§17 の 1）。台帳にも残る（別の記事で同じ画像を使えば使い回せる）。
- 画像の数が多い記事の `update` は、変わっていない画像ごとに §4.3 の GET が 1 回ずつ走る（上げはしない）。

## 9. 容量・形式・枚数の上限（THTH の側で断る）

公式に数が無い（§1.2）ので、THTH の側の上限を置き、実機で分かったら直す。断るのは **lint・承認の 1 段目・timer の 3 か所**（S2 の断りと同じ場所・同じ符丁。`hatena_entry.LINT_CODES`・`S2_REFUSALS` に足す＝timer の照合で `approval_stale` に丸めない）。

| 何 | 既定 | 符丁 | 置き場（主体の台帳 `fotolife` の欄・任意） |
|---|---|---|---|
| 1 枚の容量 | **8 MiB** | `image_too_large` | `fotolife.max_image_bytes`（1 MiB〜64 MiB） |
| 形式 | **JPEG・PNG・GIF**（先頭のバイト列で判定: `FFD8FF`・`89504E470D0A1A0A`・`GIF87a`／`GIF89a`。拡張子は見ない） | `image_type_unsupported` | 増やすのはコードの定数（WebP・HEIC・SVG は入れない。SVG はスクリプトを含みうるので実機で通っても入れない） |
| 1 記事の枚数 | **20** | `too_many_images` | `fotolife.max_images_per_entry`（1〜100） |
| 1 記事の合計 | **64 MiB** | `images_too_large` | `fotolife.max_total_bytes` |
| 主体の 1 日の上げ | **30 枚**（画像の台帳の `uploaded_at` が今日のもの＋`unknown` の `sent_at` が今日のもの） | `fotolife_daily_limit`（`next_at` は翌日の 0 時・`WAITING_REFUSALS` に足す＝timer の失敗にしない） | `fotolife.daily_max_uploads`（1〜500） |
| 空のファイル | — | `image_missing`（既存の符丁のまま） | — |

- 形式の判定で `content_type` を決める（`image/jpeg`・`image/png`・`image/gif`）。送る XML の `type` はこれ。
- 主体の 1 日の上げは `guard` に入れず（`sent/` に書かない・公開物ではない）、`hatena_fotolife.ensure_uploaded` が主体のロックの中で台帳を数える。主体の burst には数えない（画像の上げは記事の公開に付随し、記事の burst で抑えられている）。
- 1 枚の容量の既定 8 MiB は推測（はてなの画面からの上げの上限が分からない）。実機の 15（§15）で大きい画像を 1 枚上げて、返る状態番号（413 か 400 か 201）を見てから既定を直す。

## 10. フォルダ・題・generator

- **フォルダ**（`dc:subject`）: 既定 **`thth`**。主体の台帳 `blogs[].fotolife_folder` で**ブログごとに**変えられる（1〜64 字・制御文字なし・`/` なし・前後の空白なし）。比べた案: (a) 指定しない（フォトライフの既定のフォルダに混ざる）・(b) ブログ id をフォルダ名に・(c) 固定 `thth`。(c) を既定にするのは、どの道具が上げたかがアルバムで分かり、はてなの編集画面が使う「Hatena Blog」のフォルダと混ざらないため。主体＝レーンなので、レーンごとの分離は口座（サブアカウント）の側で済んでいる。
- フォルダが無ければはてなが作る（公式）。**作られたフォルダの公開範囲は THTH が決められない**（API に欄が無い・推測: 既定は公開）。記事に埋める画像は公開でなければ描けないので、公開で困らない。アルバムの頁（`f.hatena.ne.jp/<user>/`）に画像が並ぶことは受け入れる（§17）。
- **題**: `<basename> thth:<sha256 の先頭 12 桁>`（例 `arabica.jpg thth:7e3f0a1b2c3d`）。basename は 1〜80 字に切る。§7.2 の照合の鍵。
- **generator**: 固定 `thth`。

## 11. OAuth の scope と主体との関係

- scope は **S2 の 4 つ固定のまま**（`principal_cli.SCOPES`）。フォトライフは `read_private`（GET）・`write_private`（POST）と公式にあり、どちらも入っている。token のファイルは**同じ 1 本**（主体に 1 つ・S1 §4.4）。`thth principal auth` は変えない。
- **主体＝はてな ID＝フォトライフの口座**。レーンごとのサブアカウント（S1 §17）で、各レーンの画像はそのレーンのサブアカウントのフォトライフに上がる。画像の台帳は `principal_state/<p>/fotolife/`。月の容量（あれば）もレーンごとに分かれる。
- 止め: 主体が止まっていれば（`principal_stopped`）記事の guard で止まるので、画像の段には来ない（3c は guard のあと）。

## 17. masaru に伺うこと

1. **参照されなくなった画像をフォトライフに残してよいか。** 推し: **4.0 では消さない**（§8）。記事を差し替えた・消したあとも、画像はフォトライフのアルバム（`f.hatena.ne.jp/<サブアカウント>/`・フォルダ `thth`）に残る。理由は、消すのは取り消せない書き込みで、同じ画像を別の記事で使い回せる利点を捨てることになり、残しても害は「アルバムに記事の無い画像がある」だけだから。前提が変わる点: アルバムを人に見せる場として使いたい（記事に無い画像を置きたくない）なら、S5 の `reconcile` に「どの配信からも参照されていない画像」を並べ、人が承認して消す口（DELETE・2 段）を足す。

ほかは推しで決めた（上げる時機は公開の直前・台帳は主体ごとに sha256 で・指紋は変えない・置き換えはフォトライフ記法・フォルダは `thth`・上限の数値は §9・結果不明は一覧の題で照合・OAuth が通らなければ WSSE の枝を足す）。画像が記事の数秒前にアルバムに出ること（§3）と、月の容量の上限（§15 の 22 で見る）は、伺わずに進める。
