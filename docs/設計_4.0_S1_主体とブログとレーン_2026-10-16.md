# 設計: 4.0 S1 — 主体とブログとレーンの境界（2026-10-16）

書いた人: THTH開発 第3 のサブエージェント（Claude Fable 5.1）。[計画_4.0](計画_4.0_2026-10-15.md) §4.1 の S1（記事と配信の台帳・出来事の復元・はてなの主体／ブログ／レーンの境界）を、実装者（Opus の書き手）がそのまま作れる粒度で決める文書。**コードはまだ 1 行も変えていない。** 欄の意味は [約束_記事と配信の記録](約束_記事と配信の記録_2026-10-16.md) に合わせ、食い違いは末尾 §13 に並べた（直していない）。

対象の道具の版: 3.24.0（`thth/VERSION`）。

## 0. 一言で

**はてな ID 1 つ（主体）を `principals/` の台帳 1 本で持ち、レーンごとの口座（例 `kopicha-hatenablog`）は「主体 ＋ ブログ 1 つ」を指すだけにする。** 口座ごとの道具（observe・queue・repo_dir・timer・thth.me の鍵）は今のまま動く。止め・burst・ブックマークの上限・ロック・token は主体に 1 つ。ブログの id は原稿に書かせず台帳から引き、承認の指紋と送信の直前の両方で「この口座に許したブログか」を確かめる。はてなの配信は新しい種類の承認（`thth-hatena-entry-1`）で、SNS の指紋は 1 バイトも変えない。出来事の id は配信の台帳の「配信 id ＋ 通し番号」から決まるので、記録の前に落ちても同じ id で復元できる。

## 2. 言葉

- **主体**（principal）: 認証の主体。はてな ID 1 つと、その token。masaru 個人の 1 アカウント（計画 §5 の決定）。
- **ブログ**: 主体が持つはてなブログ 1 つ。`blog_id` はブログのドメイン（例 `kopicha.hatenablog.com`・独自ドメインならそれ）。AtomPub の入口は `https://blog.hatena.ne.jp/<hatena_id>/<blog_id>/atom`。
- **レーン**: THTH の `project`（kopicha・asmon-kanto …）。自分の repo を持ち、口座が複数ぶら下がる。
- **口座**: 今までどおり `accounts/<name>.json` 1 本。はてなの口座は「レーン × ブログ」に 1 本（`kopicha-hatenablog`）。
- **配信**（delivery）: 記事 × 届け先 × 公開物の 1 件（約束 §2）。
- **配信原稿**: 承認の対象。変換したあとの本文・依存する画像の指紋・blog_id・操作・題・カテゴリ・公開時刻を固定したもの。

## 3. 台帳の形

### 3.1 比べた案

| 案 | 形 | 利点 | 欠点 |
|---|---|---|---|
| A（推し） | 主体の台帳を `principals/<name>.json` に 1 本。レーンの口座は `media: hatenablog`・`principal: <name>`・`blog_id` を持ち、`token` は主体と同じパスを書く | 口座ごとの道具が無傷。止め・上限・ロック・token を主体に 1 つ置ける。鍵（thth.me）の範囲は口座 → project のまま | 台帳の種類が 1 つ増える（loader・doctor・account add に手が入る） |
| B | 主体を作らず、レーンごとの口座に同じ token のパスを書くだけ | 変更が最小 | 止め・上限・burst が口座ごとに割れ、同じはてな ID で 2 レーン合計の連投が止まらない（レビュー 2 の 2 が却下した形そのもの） |
| C | 主体を 1 口座（`masaru-hatena`）にして、ブログとレーンをその中の表で持つ | 止め・上限が自然に 1 つ | observe・queue・repo_dir・timer・鍵が口座に付くので、レーンごとの repo と鍵の範囲に合わない。レーンの LLM が他レーンのブログを見られる |

**A にする。** B は計画が既に退けた。C は「口座ごとの道具を壊さない」に反する。

### 3.2 主体の台帳 `principals/<name>.json`

置き場は口座の台帳と同じ基準（`accounts.accounts_dir_info()` の親、つまり `$THTH_ROOT/principals/`。`THTH_PRINCIPALS_DIR` で差し替え可・app repo の中には置かない）。名前の検査は `accounts.name_is_safe` を使い回す。0600。

```json
{
  "principal": "hatena-masaru",
  "kind": "hatena",
  "hatena_id": "masaru-aoki",
  "token": "~/.config/thth/hatena-masaru.token",
  "consumer": "~/.config/thth/hatena-masaru.consumer",
  "auth": "oauth",
  "blogs": [
    {"blog_id": "kopicha.hatenablog.com", "lanes": ["kopicha"], "syntax": "markdown",
     "daily_max_posts": 3, "daily_max_retracts": 2},
    {"blog_id": "asmon-kanto.hatenablog.com", "lanes": ["asmon-kanto"], "syntax": "markdown"}
  ],
  "bookmark": {"lanes": ["kopicha", "asmon-kanto"]},
  "daily_max_posts": 6,
  "daily_max_retracts": 3,
  "daily_max_bookmarks": 3,
  "burst": {"count": 3, "minutes": 30},
  "user_agent_contact": "https://thth.me/"
}
```

| 欄 | 意味 | 検査 |
|---|---|---|
| `principal` | 主体の名。ファイル名と一致 | `name_is_safe`・ファイル名と違えば `principal_name_mismatch` |
| `kind` | 4.0 は `hatena` だけ | 知らなければ断る |
| `hatena_id` | はてな ID。AtomPub の URL と WSSE のユーザ名 | 英数と `-`・`_`、1〜32 字 |
| `token` | OAuth の token（か WSSE の API キー）のファイル。**主体にだけ置く** | 口座の `token` と同じパスでなければ `principal_token_mismatch`（§3.3） |
| `consumer` | OAuth の consumer key／secret のファイル（計画 §5 の 1）。WSSE なら不要 | 値は台帳に書かない |
| `auth` | `oauth` か `wsse`。S2 で決める（既定 `oauth`） | 2 値 |
| `blogs[]` | 主体が持つブログの一覧。`lanes` は**そのブログを使ってよい project**。`syntax` は配信先に設定した記法（S2 が公開前に API で確かめる） | `blog_id` は小文字のホスト名・重複なし。`lanes` は空でない。ブログごとの上限は任意（無ければ主体の値の範囲内で口座の値） |
| `bookmark.lanes` | ブックマークを打ってよい project | 空なら誰も打てない |
| `daily_max_posts` 等 | 主体の上限（§4.2） | `accounts.valid_guard_value` と同じ検査（鍵名を共有） |
| `user_agent_contact` | はてなが求める User-Agent の連絡先（調べ §2） | URL |

主体の状態は `$THTH_ROOT/state/_principals/<name>/`（口座の `state/<account>/` と同じ 0700・`server_files.directory` の規律）。中身: `guard/stopped.json`（止めの印）・`lock`（ロック）・`token.lock`（token 更新のロック）。**公開の記録（sent）は主体には置かない**——数は口座の `sent/` を横断して数える（§4.2）。写しを作らない。

### 3.3 レーンの口座 `accounts/kopicha-hatenablog.json`

既存の必須項目を全部そろえる（loader を分岐させない）。足すのは 3 つ。

```json
{
  "account": "kopicha-hatenablog",
  "project": "kopicha",
  "media": "hatenablog",
  "principal": "hatena-masaru",
  "blog_id": "kopicha.hatenablog.com",
  "handle": "masaru-aoki",
  "repo_dir": "$THTH_ROOT/repos/kopicha",
  "queue_dir": "docs/sns/queue",
  "replies_dir": "data/sns/replies",
  "quiet_hours": ["23:00", "06:00"],
  "min_interval_hours": 0,
  "collect_days": 14,
  "hashtags": false,
  "stale_days": 7,
  "env": "~/.config/thth/kopicha-hatenablog.env",
  "token": "~/.config/thth/hatena-masaru.token",
  "ping": "wrapper",
  "timeout": 300,
  "dry_run_env": "THTH_DRY_RUN",
  "production": false,
  "scheduled": true,
  "daily_max_posts": 3,
  "daily_max_retracts": 2
}
```

- `media: hatenablog`。ブックマークは**この口座の操作の 1 種**（§6）で、別の口座にしない。理由: 鍵の範囲（口座 → project）がそのまま効く・口座が増えない・「1 記事に付けるのは主体の 1 口座だけ」（計画 §3.4）が構造で満たされる。
- `principal` と `blog_id` は必須（`media` が `hatenablog` のとき）。`load_account` の末尾で主体の台帳を読み、次を確かめる。1 つでも外れれば `AccountError`（符丁は括弧の中）:
  1. 主体がある・`kind: hatena`（`principal_missing`）
  2. `blog_id` が主体の `blogs[]` にある（`blog_unknown`）
  3. 口座の `project` がそのブログの `lanes` にある（`blog_not_allowed_for_lane`）
  4. 口座の `token` が主体の `token` と同じパス（`principal_token_mismatch`）
  5. `handle` が主体の `hatena_id` と同じ（`principal_handle_mismatch`・見せるときの名乗りを 1 つに）
- **`token` を口座にも書く理由**: `load_token`・`token_exists`・`thth doctor`・`maintain` が `cfg["token"]` を読む経路を全部そのままにするため。正本は主体。口座の側は「同じパスを指す」ことを loader が強制する。書き換えるのは主体の口だけ（§4.4）。
- `thth account add <name> --media hatenablog --principal <p> --blog <blog_id>` が雛形（`accounts.example/hatenablog.json`）から写す。`thth principal add <name> --hatena-id <id>` が主体の雛形から写す。どちらも dummy の検査（`dummy_fields`）に `blog_id: demo.hatenablog.com` を足す。
- 1 ブログに口座は 1 本が普通。同じ `blog_id` を 2 レーンが使うのは、主体の `lanes` に両方を書いたときだけ許す（数え方は §4.2）。

### 3.4 配信の台帳 `state/<account>/deliveries/<delivery>.json`

約束 §2・§3 の欄をここに置く。**口座の `state/` の中**に置くのは、`sent/`・`inflight.json` と同じ規律（0600・原子的な置き換え・`server_files`）で扱うため。レーンの repo には書かない（repo に書くのは queue の front matter だけ）。

```json
{
  "schema": "thth.delivery/1",
  "delivery": "dl_3f9c2a7e1b4d",
  "account": "kopicha-hatenablog",
  "principal": "hatena-masaru",
  "blog_id": "kopicha.hatenablog.com",
  "article": "kopicha/2026-10-arabica",
  "article_source": "articles/2026-10-arabica.md",
  "form": "full",
  "queue_file": "docs/sns/queue/2026-10-20-arabica-hatena.md",
  "state": "published",
  "seq": 2,
  "entry_id": "tag:blog.hatena.ne.jp,2013:blog-masaru-aoki-1234567890-9876543210",
  "edit_uri": "https://blog.hatena.ne.jp/masaru-aoki/kopicha.hatenablog.com/atom/entry/9876543210",
  "published_url": "https://kopicha.hatenablog.com/entry/2026/10/20/080000",
  "wanted_rev": "a1b2c3…",
  "checked_rev": "a1b2c3…",
  "checked_at": "2026-10-20T08:00:41+09:00",
  "readback_sha": "e5f6…",
  "images": [
    {"path": "images/arabica.jpg", "source_sha256": "…", "fotolife_id": "f:id:masaru-aoki:20261020075901j:image", "url": "https://cdn-ak.f.st-hatena.com/…"}
  ],
  "history": [
    {"seq": 1, "state": "inflight", "at": "2026-10-20T08:00:12+09:00", "op": "create", "approved_sha": "…", "origin": {"via": "timer"}},
    {"seq": 2, "state": "published", "at": "2026-10-20T08:00:41+09:00", "op": "create", "entry_id": "tag:…", "published_url": "https://…", "checked_rev": "a1b2c3…", "approved_sha": "…"}
  ]
}
```

| 欄 | 決め |
|---|---|
| `delivery` | `dl_` ＋ 12 桁の 16 進の乱数（`secrets.token_hex(6)`）。承認の 2 段目で THTH が振り、queue の front matter にも `delivery:` として書き戻す（人は書かない。書いてあれば lint が断る） |
| `state` | 約束 §3 の 6 つ（`wanted`・`inflight`・`unknown`・`published`・`conflict`・`no_follow`）に `deleted` を足す。`unknown` は結果不明——**失敗とみなして出し直さない** |
| `seq` | 状態が変わるたびに 1 増える整数。`history[]` の最後の `seq` と同じ。**出来事の id の材料**（§8） |
| `wanted_rev`／`checked_rev` | 約束 §2 の `article_rev`。repo があれば**その記事ファイルの blob の sha**（`git hash-object`）、無ければ本文の sha256。`article_rev_kind` は `git`／`content`。HEAD の commit にしないのは、無関係な commit で「直した」と見えないため（§13 の 3） |
| `readback_sha` | 公開のあと GET で読み戻した本文の指紋（§5.3 の正規化）。次の更新のとき「変更前の版」として承認に入り、PUT の前にもう一度 GET して比べる |
| `images[]` | 依存する画像。`source_sha256` は正本の画像ファイルの sha256。`fotolife_id`・`url` は上がったあとに入る（S3。画像だけ成功したときに次の試みで使い回す置き場をここに用意しておく） |
| `history[]` | 追記だけ。1 行が「状態の変わり目」。`approved_sha` を毎回書くのは、何を承認して出したかを後から言うため |

書き方は `server_files.replace_at(expected=古い中身)`——読んでから書くまでに他の process が変えていれば `server_file_changed` で断る（主体のロックの中でしか書かないので、普通は起きない）。

配信の一覧（`thth deliveries <account|project> [--article …]`）は S1 で読む口だけ作る（JSON と 1 行表示）。

### 3.5 配信原稿（queue のファイル）

レーンの LLM が自分の repo の `docs/sns/queue/` に書く。形は今の queue と同じ `thth: 1` の front matter で、はてなの口座のときだけ次の欄が効く。

```markdown
---
thth: 1
account: kopicha-hatenablog
status: draft
publish_at: 2026-10-20T08:00:00+09:00
article: kopicha/2026-10-arabica
article_source: articles/2026-10-arabica.md
form: full
title: アラビカの値動き（2026 年 10 月）
categories: [コーヒー, 価格]
op: create
---

## hatenablog

（この節は使わない。本文は article_source から変換する）
```

- `op` は `create`（既定）・`update`・`delete`。`update`／`delete` は `delivery:` が要る（承認のときに台帳から `entry_id`・`readback_sha` を引く）。
- `blog_id` は**原稿に書かせない**。書いてあれば lint が `blog_id_in_manuscript` で断る（§5）。
- `## hatenablog` の節は空でよい（`extract_section(allow_empty=True)`）。本文の出所は `article_source` だけ。
- `article_source` は repo の中の相対パスだけ（`..`・絶対パス・`.` 始まりは `invalid_article_source`）。
- lint（`thth/lint.py`）に足す理由の符丁: `article_required`・`article_source_missing`・`invalid_article_source`・`title_required`・`invalid_op`・`delivery_required`・`blog_id_in_manuscript`・`categories_invalid`（10 個まで・1 つ 40 字まで）。

変換したあとの本文（`body.md`）と画像の一覧は、承認の 1 段目で `state/<account>/approve_pending/<delivery>/` に固定して置き、2 段目で `deliveries/<delivery>.json` の `wanted_rev`・`images[]` に写して pending を消す。timer は公開の直前にもう一度 `article_source` から変換し直して指紋を計算する（§5.2）。固定した写しは「何を承認したか」を後から見せるための控えで、送る本文はその時点の変換結果——両方の指紋が一致しなければ `approval_stale`。

## 4. 止め・上限・ロック・token

### 4.1 止めの単位

| 印 | 置き場 | 誰が置く | 効く範囲 | 戻す口 |
|---|---|---|---|---|
| 主体の止め | `state/_principals/<p>/guard/stopped.json` | burst（機械）・`owner`（持ち主） | **その主体のすべてのブログの公開・更新・削除と、ブックマークの追加・削除** | `thth principal resume <p> --by <名前>`（運営者の CLI）。4.0 では /activity には出さない（Worker の deploy が要るので後の版） |
| 口座の止め | `state/<account>/guard/stopped.json`（今のまま） | burst・owner | その口座だけ | `thth account resume`（今のまま） |
| 媒体の断りで止める印 | `state/<account>/publish_hold/held.json` | 媒体の断り | その口座 | 同上 |

- 見る順: **主体の止め → 口座の止め → 媒体の断りの印**。主体が止まっていれば `GuardRefused("principal_stopped", reason=…)`。符丁 `principal_stopped` を `server_writes.SAFE_ERRORS` と `guard.REFUSALS` に足す。
- 読めない印は止まっている側に倒す（`guard.stopped` と同じ）。
- 止めるとき `admin_log.append("principal_stopped", …)`。`admin_log.EVENTS` に `principal_stopped`・`principal_resumed` を足す。
- `thth events` は `principal_stopped`（`ongoing: true`・`account` はその主体を使う口座ごとに 1 件ずつ）を出す。種類の名前を増やすだけで既存の名前は変えない。

### 4.2 上限と数え方

数える材料は今までどおり**口座の `sent/`**。はてなの口座の `sent/<post_id>.json` に `kind`（`entry_create`・`entry_update`・`entry_delete`・`bookmark_add`・`bookmark_delete`）と `blog_id`・`delivery` を足す（`sent.write` の引数を増やす。無い行は SNS の公開として今までどおり数える）。`post_id` は entry なら `entry_id`、ブックマークなら `bm:` ＋ URL の sha256 の先頭 24 桁（`postid.to_filename` が通る形）。

| 単位 | 何を数える | 既定 | 材料 |
|---|---|---|---|
| 口座（＝普通はブログ） | `entry_create`＋`entry_update` を `daily_max_posts`、`entry_delete` を `daily_max_retracts`。`min_interval_hours`・`quiet_hours` も今のまま効く | posts 3・retracts 2（雛形に書く。`GUARD_DEFAULTS` は変えない） | その口座の `sent/` |
| ブログ | 同じ `blog_id` を持つ口座の合計 | 主体の `blogs[].daily_max_posts` 等（無ければ数えない＝口座の上限に任せる） | 主体を使う口座を `list_account_names` で歩いて `blog_id` が同じ `sent/` を足す |
| 主体 | 全ブログの `entry_*` の合計を `daily_max_posts`／`daily_max_retracts`。`bookmark_add`＋`bookmark_delete` を `daily_max_bookmarks`。**burst は entry と bookmark の合計** | posts 6・retracts 3・bookmarks 3・burst 3 件/30 分 | 主体を使う全口座の `sent/` |
| 記事 1 つ | ブックマークは 1 URL に 1 回だけ（削除したあとも 2 回目は断る・`bookmark_once`） | — | 配信の台帳 `bookmark` の欄（§6） |

- 数は `guard.check` に `principal` の段を足して見る。`kind` に `entry_update`・`bookmark`・`bookmark_delete` を足す（`KINDS`）。`schedule` のときは `publish_at` の日で、主体の `sent/` の日の合計に「その日に刻んである approved の数」（`server_writes.schedule` の `same_day` と同じ数え方を、主体を使う全口座の queue に広げる）を足して見る。
- 断りの符丁: `principal_daily_limit`・`principal_retract_limit`・`bookmark_limit`・`blog_daily_limit`・`blog_retract_limit`・`bookmark_once`・`principal_stopped`（詳細 `burst`／`owner`）。どれも `next_at` を添える。
- **はてなの回数の上限は公式に数が無い**（調べ §1・§2）。ここの既定は THTH の側の安全装置で、持ち主が台帳で上げ下げする。上限の設定の口は `thth principal set <p> daily_max_posts 10 --by <名前>`（`account_settings` と同じ検査・`valid_guard_value` を使い回す）。
- 読む側（件数・コメントの取得）は上限に数えない。間隔（数秒）は S4 の adapter が守る。

### 4.3 ロックの順

今の順 **repo → account** に主体を挟む: **repo → principal → account**。

- 取るのは `core._account_locks` と `server_files.account_locks` の 2 か所だけ（入口が 2 つあるのは今と同じ）。`cfg.get("principal")` があるときだけ principal のロック（`state/_principals/<p>/lock`）を repo のあとに取る。SNS の口座は今までどおり 2 段。
- デッドロックしない理由: 順が全順序（repo < principal < account）で、逆順に取る経路が無い。別レーンの 2 process は repo が違うので repo では待たず、principal で 1 つが待つ。principal を持ったまま repo を待つ経路は無い。SNS の process は principal を取らないので、はてなの process と交わるのは repo だけ。
- 待ち: timer の run は repo と同じく principal も 60 秒待つ（`wait` を共有）。遠くの道は待たない（`server_resource_busy` → `account_busy`）。
- principal のロックを持つ区間は、安全装置の数え直し → 公開 → `sent/` と配信の台帳の書き込みまで。主体の数え直しをロックの外でしないこと（2 レーンの同時の公開で burst をすり抜ける）。

### 4.4 token の更新の取り合い

- token のファイルは主体に 1 本。**書くのは `thth principal auth <p>`（認可のやり直し）と、期限つきなら `maintain` の更新だけ**。どちらも `state/_principals/<p>/token.lock` を `fcntl.flock` で取って `os.replace` で原子的に置く。レーンの口座の道（run・send・遠くの道）は読むだけで、書かない。
- はてなの OAuth 1.0a の access token に期限があるかは**未確認**（推測: 無い。S2 の最初に確かめる）。期限が無ければ更新の口は要らず、`token.lock` は `principal auth` の二重起動を防ぐだけ。
- 読む側は 1 回で全部読む（`json.load` 1 回）。`os.replace` で置くので、読みかけの壊れたファイルは見ない。
- X の `_refresh_x_if_due` の形（読む前に更新）は、はてなでは使わない。更新が要るなら `maintain` の 1 日 1 回に限る（複数レーンの run が同時に更新しに行く形を作らない）。

### 6.5 timer が出すとき

`select_one` のはてなの枝: `approved_kind == hatena_entry` の原稿だけ `compute_hatena_entry_sha` で照合（SNS の原稿に `approved_kind` があれば `approval_stale`）。照合に通ったら `core._throw_chosen` の中で:

1. 主体のロックの中で主体の台帳を読み直し、§5.2 の 6 を確かめる
2. `guard.check(kind=entry_create|entry_update|entry_delete)` を口座・ブログ・主体の 3 段で
3. `update` なら GET で読み戻し、`readback_sha` が `base_readback_sha` と違えば配信の台帳を `conflict` にして止める（上書きしない）
4. `inflight.write`（`delivery`・`seq`・`approved_fingerprint` を入れる）→ 配信の台帳に `inflight` の行
5. POST／PUT／DELETE を 1 回
6. `sent.write`（`kind`・`blog_id`・`delivery`）→ 配信の台帳に `published`／`deleted` の行（`entry_id`・`published_url`・`checked_rev`・`readback_sha`）→ queue の書き戻し（`post_id`・`url`・`delivery`）→ `inflight.clear`
7. 応答が無い・読めない → inflight を残して `unknown` の行（出し直さない）

## 7. ブックマーク

### 7.1 4.0 の範囲

- **自分の記事だけ**: 対象の URL は、その口座の配信の台帳に `state: published` で `published_url` があるものに限る（`bookmark_target_not_own`）。他人の記事（ネタ元）のブックマークは 4.0 に入れない（承認の形は同じにできるので、入れるときは `lanes` と上限だけ足す）。
- **公開のあとにだけ承認する**: URL が決まってから。「記事の承認と一緒に、公開後に打つ」形（調べ §5-2 の推し）は 4.0 では作らない（§12 の問い 1）。
- 1 URL に 1 回だけ（`bookmark_once`）。コメントは必須（運営者であることが分かる文を LLM が書く。THTH は中身を決めない）。`private` は 4.0 では `false` 固定。
- 削除（`thth bookmark retract`）は同じ 2 段・主体の `daily_max_retracts` には数えず `daily_max_bookmarks` に数える。

### 7.2 承認の対象 `thth-hatena-bookmark-1`

| # | 欄 | 正規化 |
|---|---|---|
| 1 | `version` | 固定 |
| 2 | `account` | `.strip()` |
| 3 | `principal` | 主体の名 |
| 4 | `op` | `add`／`delete` |
| 5 | `url` | `.strip()`。配信の台帳の `published_url` と**文字どおり**一致 |
| 6 | `delivery` | 対象の配信 id |
| 7 | `comment` | `.strip()`・改行を空白に・100 字まで（はてなの上限は未記載。超えたら lint が断る） |
| 8 | `tags` | 各 `.strip()`・空を除く・並べ替え・`\x1e`・10 個まで |

### 7.3 道

- 手元: `thth bookmark add <口座> --delivery <id> --comment "…" [--tags a,b]` が 1 段目（表示: URL・題・コメント・タグ・主体・今日の主体の残り枠）と digest。`--confirm <digest> --by <名前> --production` で打つ。予約はしない（queue に載せない。打つのは今）。
- 遠くの道: `bookmark_request {account, delivery, comment, tags, confirm?}`（`WRITE_OPERATIONS` に足す・2 段）。鍵は口座の範囲。
- MCP: `thth_bookmark_request`（CLI の subprocess）。
- 記録: `sent/bm:<sha>.json`（`kind: bookmark_add`・`url`・`delivery`）と、配信の台帳の `bookmark: {state, at, comment_sha256, tags}` と `history` の行（`bookmarked`／`bookmark_deleted`）。
- 安全装置: 主体の止め → 口座の止め → `daily_max_bookmarks`（主体）→ burst（主体・entry と合算）→ `bookmark_once`。quiet_hours は掛けない（タイムラインに出る公開ではない）。

## 8. 出来事の id を配信の台帳から決める

### 8.1 決め

- 配信の台帳から出る出来事の `event_id` は **`"ev_" + sha256("thth.delivery/1|" + delivery + "|" + seq)[:24]`**。`kind`・時刻は入れない（時刻は記録のたびに揺れうる。`delivery` と `seq` は書いた瞬間に決まり、二度と変わらない）。
- 出来事の種類（`events_cli.KINDS` に足す。名前は増やすだけ）: `delivery_published`・`delivery_updated`・`delivery_deleted`・`delivery_unknown`・`delivery_conflict`・`bookmarked`・`bookmark_deleted`・`principal_stopped`。`ref` は `delivery`、`summary` は題と blog_id、`at` は `history[].at`。
- `inflight` の行は出来事にしない（今の `inflight_open` が「今も続いている状態」として出す。`ref` に `delivery` を入れる）。
- `_sent_events` の `published`／`retracted` は、はてなの `sent/` の行（`kind` が `entry_*`／`bookmark_*`）を**飛ばす**（同じ出来事を 2 つの名前で出さない）。SNS の行は今までどおり。

### 8.2 記録の前の中断の回収（計画 §3.8）

`thth events` は書かない道具なので、「出来事を書く前に落ちる」は起きない。起きうるのは「媒体には出たが、配信の台帳の行を書く前に落ちた」。その形は inflight が残るので:

1. 次の run は inflight を見て止まる（今と同じ）。
2. `thth inflight <口座> resolve --published <entry_id>`（人が画面で確かめて解く）か、`thth deliveries <口座> reconcile`（S5。AtomPub の一覧を読んで `text_fingerprint` で突き合わせ、人に候補を見せる）で解く。
3. 解くとき、配信の台帳に**同じ `seq`**（inflight に書いてある `seq`）で `published` の行を書く。だから `event_id` は、落ちずに書けていたときと**同じ値**になる。受け手は `event_id` で重複を除くので、どちらの経路でも 1 度だけ扱う。
4. `inflight.write` に `delivery` と `seq` を入れるのは、このため。seq を inflight に書く前に台帳の `seq` を 1 進めておく（`inflight` の行が `seq: n` で台帳に入っているので、`published` は `seq: n+1`。inflight に書くのは `n+1`）。

押す口（hub・h2d に送る）は S1 では作らない。作るときは `event_id` をそのまま使う。
