## 2. 小品 1: 人が押す口（human approval as a service）

### 2.1 約束
「LLM が案を出す。人がスマホで見て、secret を入れて押す。押した記録（receipt）だけを機械に返す。押されなかったものは何も起きない。」

### 2.2 いまの仕様（THTH 2.12.x の現物・そのまま切り出せる）
- **登録**（管理者・署名付き）: `POST /approval/person/<name>/set|revoke|unlock|status`。人ごとに DO `ApprovalPerson`（名前の sha256 で `getByName`）。secret は VM 側で生成（`secrets.token_urlsafe(32)`＝43 文字）し **tty に一度だけ表示**、Worker には `salt`（32 byte）＋ PBKDF2-SHA256 の verifier（**100,000 回**・workerd の上限）＋ `iterations` だけを送る。世代（generation）を持ち、`set` し直すと旧ページは無効。連続失敗 5 回で本人ロック、`unlock` で解除。
- **セッション**（job・署名付き）: `POST /approval/session/<token>/create` に `{person, job_id, digest, account, kind∈approve|send|retract, text, context{media,reply_to,publish_at,target,reason,topic,options}, read_key_hash}`。token は VM が 43 文字の乱数で選ぶ（URL＝`/approve/<token>`）。**10 分で失効**（600 s の論理期限・PITR の物理消去は約束しない）。
- **人の画面**: `GET /approve/<token>` が本文・account・digest・context・csrf を HTML で出す（`no-store`・`no-referrer`・CSP `form-action 'self'`）。`POST`（同 origin・`application/x-www-form-urlencoded`・`csrf,secret` の 2 key だけ）。誤り 403・成功 200「サーバが内容を再確認します」。失効 410。
- **受領**（job・署名付き）: `status`（`read_key` で読む）→ `approved` なら `consume` が **一度だけ** 200 で receipt `{job_id, digest, account, kind, approver, generation, approved_at, expires_at}`。二度目 404。DO `ApprovalAccount` が account 単位の grant を持ち、Person の consume が一回限りの世代門。
- **VM 側**: `state/<account>/approval-jobs/<job_id>.json`（durable・0600）に intent を先に書く。`thth approval-worker --credentials <file>` が 2 秒ごとに poll → consume → 実行の直前に **本文・台帳・資格情報・secret 世代を再確認**（変わっていれば実行しない）。結果不明は `unknown` で止まり自動再送しない。
- **署名**: RSA-3072 PSS（salt 32・SHA-256）。canonical＝`'thth-approval-v1'\n<method>\n<path>\n<role>\n<subject>\n<operation>\n<timestamp ms>\n<nonce>\n<sha256(body)>`。headers `X-Thth-Time`・`X-Thth-Nonce`・`X-Thth-Signature`（unpadded base64url）。時刻 ±60 s・同 nonce 再送拒否。公開鍵は Worker secret `APPROVAL_PUBLIC_KEY`、秘密鍵は VM `~/.config/thth/apps/relay-signer.key`（`thth admin relay-key init|show`）。redirect は追わない。
- **rate limit**: 公開ページ 120/IP/60 s、署名入口 600/IP/60 s、job 180/subject/60 s。429 と retry-after。
- **削除受付**（同居）: `DeletionInbox` DO・`/data-deletion-status?code=`。Meta のデータ削除 callback を opaque receipt で受け、VM が署名で読み・照合・完了を書く。

### 2.3 切り出すときの境界
- **そのまま**: 署名・DO・失効・一回限り・rate limit・privacy ページ・CSP。
- **差し替え可能に**: digest の計算（利用側が「何を承認するか」を canonical にして sha256 を渡す。Worker は digest を **不透明な 64 hex** としてしか扱わない——いまもそう）。context の表示欄（labels）は利用側が渡す `{label: value}` の配列に一般化。
- **利用側の最小 API**（案）: `register_person(name) -> secret (tty)`, `request_approval(person, kind, text, digest, context) -> url`, `wait(token, read_key) -> receipt | expired`, `consume(token)`. Python の `approval_relay.py` がそのまま client library になる。
- **運営**: Cloudflare Workers（Free でも DO SQLite・rate limit は使える。PBKDF2 は 100,000 回まで）。1 Worker・1 zone。

### 2.4 磨くべき箇所（3.0 で招待者に使ってもらってから）
承認ページの文面・失効の見せ方・通知（承認待ちが放置されている）・添付の表示（2.13 第 7 段以降）・複数 job の一覧。

## 3. 小品 2: 秘密を持たない認可の預かり所（同居）

### 3.1 約束
「OAuth の code を 5 分だけ 1 回預かる。秘密（client secret・token）は預からない。人は URL を開いて承認を押すだけ。」

### 3.2 いまの仕様（THTH 2.11.x）
- VM の `thth auth <account> --by <名前>` が `state`（32 byte 乱数）＋ PKCE `code_verifier` を作り `state/<account>/auth_state.json`（600・10 分）に保存。認可 URL を 1 行だけ出す（scope は adapter が決め、人は選ばない）。
- 預かり所 `https://thth.me/callback`（redirect_uri）→ DO `AuthRelay`（state ごと）に code を **5 分・1 回**。VM は `register`（POST）で state を先に登録し、`GET /relay/<state>`（Bearer read key）を 2 秒おきに最長 10 分。pending→ready→consumed。GET 400 回で打ち切り。
- `User-Agent: thth/<ver> (+https://thth.me)` 必須（Cloudflare が `Python-urllib` を 403 にする）。
- 媒体差は `AuthProfile`（`adapters/auth_mastodon.py` 等）: authorize URL・token endpoint・scope・本人照合（`verify_credentials`／`me`）。Mastodon は instance ごとに **アプリを自動登録**（client ファイルは `mastodon.<origin sha>.<必要 scope 集合の sha 先頭 8>.env`・scope 集合が変わると世代が変わり旧ファイルは触らない・旧 pending は `auth_restart_required`）。X は PKCE＋Basic・code 30 s。Bluesky はアプリパスワードを `token set --stdin`。
- 預かり所が使えないときの後方互換: 戻り URL 全体を貼る（`--paste`）。`--rehearse` は RAM だけで 600 s 待つ（保存・認可・交換しない）。
- token は媒体から VM へ直接届き、`token set` 相当で 600 に保存。granted scope を台帳に記録（不足は upload 前に静的理由で止める）。

### 3.3 切り出すときの境界
- Worker 側（`relay.js`・`relay-object.js`）は THTH 固有を含まない。そのまま。
- `authflow.py`（骨）と `AuthProfile`（媒体差）を分け、profile を利用側が書く。
- 利用側の最小 API: `begin(profile) -> (url, session)`, `poll(session) -> code`, `exchange(profile, code) -> token (stdin/600 に保存する callback)`。

## 4. 小品 3: 一回限りの公開 URL（capability URL・同居）

### 4.1 約束
「1 ファイルを、宛先と用途と期限を決めた能力で、1 回だけ外に渡す。」

### 4.2 いまの仕様（THTH 2.13 第 4 段）
- **upload session**（署名付き control `POST /media/<subject>/create`）: 1 ファイル・600 s・`complete` は一度・part は再試行可・100 MB 超は multipart（最後以外 5 MiB 以上・等サイズ）。`PUT /media-upload/<subject>[/<n>]`（bearer は 43 文字の path・未署名）。VM が `complete` 後に署名付き `read` で **取り出して sha を照合**（Worker 側で hash しない）。
- **capability**（`provider`／`preview`・署名付き）: `/m/<cap>`（43 文字 opaque・`(公開 sha, account, purpose, generation)` に束縛・sha は URL に出ない）。provider は発行から **画像 600 s／動画 1800 s**、署名付き `ack`（`published`）で **ack+3600 s に一度だけ**延長・二度目は延長しない。明示失敗は即時失効（`invalidate`）。結果不明は延長も再発行もしない。失効・未知（well-formed）・掃除済は **410**（GET/HEAD/Range）、malformed 404。未知の lookup で DO row も alarm も作らない。
- **掃除**: R2 object は cleanup alarm で物理削除（60 s 間隔・最大 10 回・成功確認だけを削除済みに・上限後は `cleanup_failed` を row に保持して alarm 停止）。書込み開始を durable な I/O ticket に登録し、未解決 I/O がある間は削除完了に進めない（遅い put と掃除の競合の直し・C17-A10）。remote の結果自体が不明な ticket は時間で確定せず保持（C18）。account 単位 DO が未解決 subject 集合を冪等に持ち、doctor には件数と静的理由だけ。管理者の署名付き `cleanup-retry` は削除の再開だけ。bucket の lifecycle rule（`media/`・24h）は独立の backstop（保証とは書かない）。
- **rate limit**: `/m/*` 120/IP/60 s（HEAD・Range 含む）、`/media/*` 600/IP/60 s（署名検証より前）、`/media-upload/*` 240/subject/60 s。
- **size 上限（Worker）**: `kind=sanitized` 画像 8,000,000／動画 1,000,000,000。`kind=source` は transport 上限 1,000,000,000（暫定資源上限）。
- **署名**: canonical `'thth-media-v1'\n<method>\n<path>\nmedia\n<subject>\n<operation>\n<ts>\n<nonce>\n<sha256(body)>`（approval と同じ鍵）。
- **秘密**: capability・subject・URL は `redact.register_secret`。Worker は log を出さない（`observability.enabled=false`）。

### 4.3 切り出すときの境界
- 用途（purpose）の集合と TTL を利用側の設定に。ack の意味（「外部が取り込んだ」）は利用側が決める。
- 利用側の最小 API: `upload(bytes|stream, sha256, size, mime) -> subject`, `grant(subject, purpose) -> url`, `ack(subject)`, `invalidate(subject)`.

## 5. 小品 4〜6: Python の小さな package

### 5.1 版とリリースノートを道具が伝える口
- `handoff-report --since-last-read` の `tool` block: `{version, previous, changed, release_notes, notes_root_local_hint, notes_reason}`。cursor（栞）は `handoff_cursor.py`（`read/write/changes/snapshot`）で account ごと・`--mark-read` で進める。**絶対パスは HTTP/MCP に出さない**（2.10.0 の P2 の教訓）。
- skill の開始手順: 「`tool.changed` が true ならリリースノートを読んでから作業」。
- 一般化: `tool_block(version_file, notes_dir, cursor) -> dict`。

### 5.2 追記のみの変更ログと来歴
- `state/_admin/accounts.ndjson`（append-only・flock・`transaction()`）。行は `{event, subject, by, via, at, diff, run_id}`。**diff は presence-only**（`{'private_key': ['absent','present']}` のように値を書かない）。`--by` 必須の guard（`admin_log.actor(by)`）。読む口 `thth admin log|diff --since-last-read`。
- 一般化: `AppendLog(path).append(event, subject, by, diff)`・`guarded(fn)`。

### 5.3 秘密の扱いの土台
- `secrets_fs`: 600 の原子的な書き込み（temp→fsync→rename・`O_NOFOLLOW`・nlink 1・owner 一致）。`server_files.directory(private=True)` の走査（`0o077` 拒否）。
- `redact.register_secret(value)`: 出力・例外文からの伏字。
- プロジェクト外の置き場（`~/.config/<project>/`・`chmod 700`）と `rotate-client-secret.sh`（値を echo しない・クリップボード）。
- `httpsafe`: https 限定（loopback は `THTH_TEST_ALLOW_HTTP=1` でのみ）・明示 handler の opener（file/ftp/data/proxy 無し）・同一 origin 以外の redirect 拒否・応答 1 MiB 上限・timeout 必須。
- 一般化: そのまま package に。

## 7. ヘッドレス道具の作法（`AI協業の作法.md` と並べる 1 枚・骨子）

1. LLM が操作するが、取り返しのつかない一手は人の画面で押す。承認を LLM の経路から切り離す。
2. 秘密は LLM の文脈を通らない（預かり所・パスワードマネージャから直接・tty に一度だけ）。
3. 読む口と書く口を分け、書く口はすべて記録する（`--by`・append-only・presence-only）。
4. 道具が自分の版と変更を LLM に伝える（栞・`tool`）。
5. 数字には分母、無いものは null＋理由（`cannot_say`）。推測で埋めさせない。
6. 断るときは静的な理由コード（入力値を反射しない）と次の一手。
7. 結果不明は不明のまま保持し、時間で確定しない・自動で再送しない（durable intent・held/unknown）。
8. ローカルで通っても本番で落ちる制限（workerd の PBKDF2 100,000・CPU・body・R2 multipart・既存ディレクトリの mode）は「配布担当の本番実測」欄に毎回書く。
9. 検収は LLM に使わせて使い勝手レポートを書かせる。

## 8. 監査の工程（手順書として切り出す・このセッションの型）

1. 候補は `.git` 付きの別 clone（`/private/tmp` 配下・leak probe が `/Users|/private|/Volumes|/srv` を探すため）で・clean・実 import を確認。
2. 全 suite（Python と **Node の両方**——2026-09-21 に Node を回さず main が赤のまま merge した反省）。
3. 2.7.0 の回帰 probe（`~/thth-exchange/in/2026-09-18_v3監査の直し_probe/`・semantics＋http/isolation/unix script＋leak）。
4. 自前 probe（観点: 指紋の束縛・秘密走査・null＋理由・境界の両側・再実行で要求 0・秘密が理由/journal/stdout に出ない）。
5. 変異は 1 箇所置換＋逆置換＋`git diff --quiet`。候補の試験だけで殺せない変異は試験追加の P3。
6. 機械部分は Opus 5 のエージェント、判断と回答は Fable（コスト）。
7. 受け入れは main へ merge（release は触らない）。配布は masaru の一言。
8. Codex との往復: `~/thth-exchange/in/`（Claude→Codex）・`out/`（Codex→Claude）・20 分 heartbeat・固定 SHA・照合（C 番号）・部分検収。
