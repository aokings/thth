# 構想: 台帳ベースの総合サイト運営（THTH に寄せる）

2026-11-12 昼、masaru と THTH開発 第15 のブレストの記録。同じ日の午後に THTH開発 第16 が §6 の「合わせる働きと `thth sync`」を、夕方に Fable の見立て（§3 の行の 2 種類・§6 の順序）と masaru の「有料版」の考え（§6）を足した。**叩き台**。決めたのは §1 の 2 つだけで、ほかは案。

## 1. 決めたこと（masaru 2026-11-12）

- THTH の姿は「**台帳ベースの総合サイト運営ツール**」。
- 器は **THTH に寄せる**（別の名前の道具にしない）。masaru「名前も可愛いし」。

これは 9/26 の「THTH は SNS を調べ・投稿し・予約する CLI ツール」を広げる決めになる。CLI が先で、MCP と skill はその写し、という作り方は変えない（§6）。

## 2. 一言で

台帳を正本にして、そこから**つくり・だし・測り**、測った結果を台帳に戻して行を育てる。

## 3. 台帳とは

運営で扱う「もの」を 1 行ずつ持ち、その今の状態と、なぜそうなったかを残しておく正本。頁も投稿も報告も、そこから作る写し。英語の言い方は **register** が近い（ledger は会計とブロックチェーンの印象が強い。registry は MCP registry とぶつかる）。

台帳の 5 つの性質:

1. 1 行 = 1 つのもの（学校・店・商品・図鑑の項目・催し・指標）。番号はずっと同じものを指す
2. 状態を持つ（試し → 本採用 → 退役、など）
3. 由来を持つ（数字の出所と取得日・足した理由・誰の決めか）
4. 変えた跡が残る（git の commit）
5. ほかのものはここから作る。直すときは台帳を直す

行は 2 種類ある（Fable の見立て 11/12）。合わせる向きが逆になる:

- **自前の行**: 正本は台帳（頁・これから出す投稿など）。外を台帳に合わせる。上の 5 がそのまま当てはまる
- **取り込みの行**: 正本は外（店の商品の値段・在庫など。THTH は店に書かない）。台帳は写し・由来・メモを持ち、台帳を外に合わせる。最初の実例は `thth shop` の店の写し（[設計_ショップとWordPressの口_2026-11-12.md](設計_ショップとWordPressの口_2026-11-12.md)）

似たものとの違い: データベースは理由を持たない。ログは「今どうなっているか」を持たない。表計算は由来と跡が残りにくい。

## 4. 体にたとえると

| | 役 | 担い手 |
|---|---|---|
| 大脳（記憶と判断の跡） | 台帳 | 持ち主の手元（§5） |
| 考える働き | 台帳を読み、次の手を考え、決めたことを書き戻す | 持ち主の LLM（セッションは入れ替わってよい） |
| 手足と感覚器 | だす・測る、外へ出すときの手すり | THTH |
| 顔と体 | 外から見えるもの | サイト・SNS・広告 |

考える働きが入れ替わっても、台帳が残れば同じサイトとして続く（セッションの申し送りと同じ形）。

育て方は media-hub の repo の設計の書（設計_スコアボード_育つ指標_2026-10-04） と同じ。指標だけでなく、頁・投稿・広告も「試し → 本採用 → 退役」で育てる。広告でいえば、boost は試し、効いたら extend（本採用）、効かなければ stop（退役）。

## 5. 外の人の台帳の持ち方（案）

- **正本は持ち主の側に置く。** THTH の運営者が預かるのは、出したもの（頁・投稿・広告）とその数の写しだけ。今のアカウントごとの記録と範囲はほぼ同じ
- **台帳の形を公開の決まりにする**: 平文の .md を 1 行 1 枚で置く。頭の項目（frontmatter）に「番号・状態・由来・見直し日」を必ず持たせる。git の repo にする。点検の命令（仮に `thth register check`）を柵にする
- **置き場は持ち主が選ぶ**:
  - 手元のフォルダ
  - Obsidian の保管庫（Sync は有料で Obsidian が預かる。運営者は何も預からずに済む）
  - `thth sync`（§6 の案。monban が暗号のまま運び、運営者は中身を読めない）
  - 自分の GitLab や GitHub の非公開 repo（変更の申し出と承認で決める流れ・CI の点検・Pages で頁の公開まで 1 か所でつながる）
- **THTH が書くのは頭の項目の数の欄だけ。** 本文には触らない（同期のぶつかりを避ける）
- **お客さんの個人の情報は台帳に入れない。** やりとりは各 SNS の側に置き、台帳には件数だけを持つ
- **運営者が自前の専用の場所（自前の GitLab・Forgejo）を立てるのは、まだしない。** 外の利用者が増えて、承認の流れをそろえたくなった段で考える。立てると、運営者が大脳を預かる重さ（privacy・削除・持ち出し・運用）が戻ってくる

前提が変わると結論も変わる。最初の外の利用者が機械の苦手な店なら、預かり（Obsidian Sync か運営者の場所）が最初から要る。

## 6. 今ある部品と無いもの

- **THTH にある**: だす・測る（SNS と広告）・手すり（二段確認・上限・前向きな断り）・Meta の審査を通した口・PyPI と registry と thth.me（外の人の入口）。届けるシナリオの構想（`docs/構想_5.0_届けるシナリオ_2026-10-23.md`）は、台帳の行を届ける順と拍子として読み直せる
- **media-hub と各メディアにある（自前用）**: 台帳から頁を作る（学校台帳など）・検索と訪問の数（計測台帳）・指標を育てる（スコアボード）
- **無い**:
  - 外の人に渡せる台帳の決まりと点検
  - 行から頁を作る公開の仕組み（サイトの頁も広告の受け皿の 1 枚頁も同じ仕組みで作る）
  - 頁の数（来た人の数・どの投稿や広告から来たか。ピクセルや cookie を使わず数だけ）を行へ返す口
  - 台帳と外の実際を合わせる働き・台帳を置き場どうしで運ぶ `thth sync`（下の案）

### 合わせる働きと `thth sync`（案・masaru と第16 の 11/12 午後の話）

2 つを分ける。前の世代の案は「台帳と外を合わせる命令を `thth sync` と呼ぶ・台帳の置き場どうしは git と Obsidian に任せる」だったが、masaru の指摘で向きを替えた。

1. **合わせる働きは基礎で、名前を付けない**（masaru「名前付ける機能ではなくて基礎機能」）。台帳＝ありたい姿、外（SNS・広告・サイト）＝実際。THTH はどの命令でも、まず外の今を読んで台帳と比べ、差を見せてから動く。差を埋める確認の重さは、今の `thth ads` の手すりと同じ並びを全体の規則にする:
   - 外の今を読んで台帳の隣に写す（測る）: 確認なし
   - 止める・下げる: 確認なし（すぐ）
   - 出す・始める・上げる・消す: 二段確認
2. **`thth sync` は台帳そのものを置き場どうし（自分の PC・VM・仲間の手元）で同じにする命令**（masaru「Obsidian sync の thth 版」）。運ぶ器は **monban を進化させて**担う（masaru「monban を進化させて対応させる」）:

| 置く所 | 中身 |
|---|---|
| monban | 暗号にした台帳の版を預かる・運ぶ・履歴を持つ。中身は読まない（「ハウスの中には入らない」の延長）。端末の確かめと失効は今の owner と device の口 |
| THTH | `thth sync` の命令（monban の client を使う）・台帳の決まりと点検・合わせる働き |

**売り方（masaru 11/12 夕方・考え）**: **データを預かる契約が土台**で、預かったデータから店や頁を作って公開できる（「かなり細やかな事が出来ちゃう」）。形は「**門の中に金庫と庭を造る**」（masaru）:

| 場所 | 中身 | 読める者 |
|---|---|---|
| 門（monban） | 鍵で人を確かめる・記録を付ける。ハウスの中には入らない | — |
| 金庫 | 台帳の私の部分（メモ・由来・下書き・非公開の商品など） | 持ち主だけ（端から端までの暗号・運営者は読めない） |
| 庭 | 持ち主が「見せる」と決めた部分（商品名・値段・写真・頁の本文） | 誰でも（店や頁として公開する） |

- 庭に置く物は公開する物なので、もともと秘密ではない。運営者が庭の中身から店や頁を作って出せる。利用者は Cloudflare のアカウントを作らなくてよい（前の `thth pages` の案の重さが消える）
- 店の商品を読むのは手元の thth のまま（BASE の PAT は手元だけ・設計の書 §1）。読んだ商品のうち、庭に置くと決めた部分だけを預ける
- `thth sync`（金庫を運ぶ）・庭・その上の店と頁のフル機能が有料の契約。どこまでを無料に残すか（例: BASE の 1 店を読んで 1 商品ずつ下書き、の今の版）は §8
- 増える重さ: 庭の公開の中身への責任（terms に載せてよい物・止める手順・通報の受け口）、金庫と庭の線引きの説明（何が庭に出るかを持ち主が選び、出る前に見せる）
- 分け方（monban の設計案 §14・c80d0f1）: monban は「出来上がった頁の束を平文で預かり・版で入れ替え・配り・止める」まで。行から頁を作るのは THTH の手元（`thth publish`（仮））。金庫から庭への道は monban の中に作らない。庭に出す前に「新しく出る・変わる・消える物」の一覧と見本を見せて二段確認。段 1 の庭は静的な頁だけ（script と form を止める・買うは外の決済の頁へのリンク）。配るのは monban.me ではなく別のドメインか持ち主のドメイン
- **LP の最適化**（masaru 11/12 夕方「有料版 pages に契約すれば、LP 最適化なんかも出来ちゃう」・考え）: 1 つの LP に案を 2〜3 個並べて比べ、試し → 本採用 → 退役で育てる。広告ごとに受け皿の LP を作る。案は利用者の LLM が書き、承認のあとに庭に出す。決めること: privacy の「頁を見た人を記録しない」との折り合い（案ごと・日ごとの数だけを、cookie もピクセルも使わずに数える形。数えるのは配る側＝門の記録が素直。静的な頁で script を止める段 1 とも合う）・cookie なしの振り分け・成果は「店の商品頁へ進んだ数」までしか見えない（注文は読まない）・来る人が少ない店では差が出るまで長い・検索との関係（canonical と一時の転送・要確認）

**順序（Fable の見立て 11/12）**: 合わせる働きは「利用者に名前を見せない」の意味に留め、中では種類ごとに名前を付けた決まりを持つ（字のとおり全部の命令で外を読むと、呼び出しの数と待ちが全部に乗る）。sync・金庫・頁は、家族の店で「読む → 下書き → 承認 → 出す → 測って行へ返す」が 1 周してから作る（運ぶ中身＝台帳の決まりが、その実物から起こせるため）。新しい口は 1 つずつ足す。2 つめの取り込む元は Shopify より Meta のカタログを先に。

暗号は端から端まで（運ぶ側は鍵を持たない）を叩き台にする。そうすれば §5 の「運営者が大脳を預かる重さ」のうち、中身を読める重さは戻らない。残るのは、暗号の箱の置き場の費用・消す求めへの応じ方・持ち出しの口。monban への依頼の本文は `docs/依頼_monban_台帳の版の預かり_2026-11-12.md`。

## 7. media-hub との関係（案）

統合はしない。自前のメディアは THTH の最初の利用者になる。media-hub にある頁づくりと数の部品は、外の人に渡せる形へ育て直しながら、少しずつ THTH の側へ寄せる。hub は指揮と管理（どのメディアが、いつ、何を回すか・朝の一枚）に残る。

10/23 の線引き（THTH は外へ届ける側・hub は自前のもの同士の連携と管理）は、「台帳と、つくる・だす・測るの道具は THTH。自前のどのメディアに使うかの指揮は hub」に読み替える。**media-hub の担当と相談してから決める**。

## 8. まだ決めていないこと

- 最初の外の利用者は誰か（自分の Claude Code を使える人か、機械の苦手な店か）
- 「もの」の台帳と「手（施策）」の台帳を分けるか、1 つにするか
- 昇格と退役を誰が決めるか（外の人なら、LLM が候補を出し、本人が決める）
- 頁の置き場（まず thth.me の下か、持ち主の独自ドメインか、Obsidian Publish や GitLab Pages に任せるか）
- 9/26 の「Web は見る・止める・鍵だけ」との折り合い（頁を配るのは「投稿を出す」の延長と見る案）
- Meta の審査の説明（SNS の道具として出している）とずれないか。束の提出はこの構想と切り離して今のまま進める
- 合わせる働き（§6）: 二段確認の要る差が多いとき 1 件ずつか、まとめて 1 回か。台帳から行を消したら外も消すか、「外に残っている」と見せるだけか（消すと戻せないので、見せるだけが叩き台）。timer で自動に回すのは「測る」と「止める・下げる」までに絞るか
- 無料と有料の線（§6 の売り方）: 無料に何を残すか・有料の値段と支払いの口（お金が動くので masaru の承認）・terms
- 庭（§6）: 置き場（thth.me の下か、持ち主のドメインか）・庭の頁の作り（台帳の行から）・庭と金庫の線を持ち主がどう選ぶか・載せてよい物と止める手順
- `thth sync`（§6）: 同時に書いたときのぶつかりの解き方・履歴をどこまで残すか・置き場の費用を誰が持つか（無料の招待制の間と、外に開くとき）・privacy と terms の書き方
