## 4. 設計と食い違った点・実装で埋めた空白（直さずに記録する）

1. **文字数カウントに含める「末尾改行 1 個」**: `queuefile.extract_section()` は
   §4.1 の指示どおり節の本文を「前後に何も足さない・末尾改行1個」に正規化する。
   この末尾の改行 1 文字を 500 字の文字数カウントに含めている（含めないという解釈も
   ありうる）。501 字フィクスチャは「通常文字 500 字＋末尾改行 1 個＝501」で作った。
   実際に Threads API に投げる text はこの正規化後の文字列そのものなので、投げる文字数と
   検査する文字数を一致させる目的でこの解釈を採ったが、設計書はここまで明記していない。

2. **絵文字の判定基準**: §2.2 は「絵文字は UTF-8 バイト数」とだけ書いており、
   「何を絵文字とみなすか」の基準が無い。`unicodedata.category(ch) == "So"`
   （Symbol, Other）＋地域指示記号（国旗）を絵文字とみなす実装にした。異体字セレクタ
   （U+FE0F、カテゴリ Mn）は絵文字扱いにしていない（例: ☕️ は 4 字＝☕のUTF-8 3バイト＋
   異体字セレクタ 1 字）。本物の Threads のカウント方式とは検証していない（L3）。

3. **select 条件 8 のエラー名**: §3.3 は「媒体の節が無い／文字数超過 → 落として
   `error="too_long(NNN)"`」と 1 文で書いているが、節が無い場合に `NNN` に何を
   入れるかは定義できない。実装は節が無い場合を `error="no_section"`、文字数超過の
   場合だけ `error="too_long(NNN)"` に分けた。

4. **`--now` の意味**: 発注書に `thth throw [--now]` とだけあり、意味の定義が
   無かった。実装は「静かな時間帯・最短間隔（select 条件 6・7）だけを無視して
   今すぐ試す」とした（承認 gate・post_id・型外・文字数等の他の条件は無視しない）。
   受け入れテストの対象外なので動作確認のみ。

5. **`thth queue` の「次に出るもの」**: `select_one()`（いま出せるかどうか）とは
   別に、`report.queue_summary()` の「次に出るもの・いつ」は quiet_hours・
   min_interval・文字数・重複チェックを見ない「予定」の案内にした（post_id 無し・
   approved・publish_at が形式的に正しいものの中で最早）。設計は「次に出るのは
   何か・いつか」としか書いておらず、この粒度は実装が決めた。

6. **`git pull --rebase` に `--autostash` を追加**: §4.3 は `git pull --rebase`
   としか書いていないが、test_20260901（中断が残した未ステージ変更）を通すために
   `--autostash` を付けた。中断者の変更を保持したまま rebase が通ることを
   `tests/test_writeback_rebase.py` で確認している。

7. **ロックの「待つ」か「弾く」か**: 発注書 §5-9 は「待つか『既に実行中』で弾かれる」と
   両論併記だったので、watchtower `wt-run` の flock（`LOCK_NB`）と同じ「即座に弾く」を
   採った（ブロッキング待機は実装していない）。

8. **`accounts.APP_DIR` の隔離**: テストが実物の `accounts/nigamilab-threads.json`
   を汚さずに動くよう、`THTH_APP_DIR` 環境変数（未設定時は `accounts.APP_DIR` を
   使う）を追加した。これは設計に無い実装用の拡張だが、環境変数を設定しない限り
   本番の挙動（`accounts/` は常に app repo 直下）は変わらない。

9. **`thth throw` と `thth run` で production 判定の入力が違う**: `thth throw` は
   CLI の `--production` フラグが立っていないと常に dry-run（台帳が production: true

   実際に本番になるかどうかは台帳の `production` 1 つだけで決まる。§3.7 の表
   （`thth throw` は「早く走らせるだけ」、`thth run` が timer の本来の実行経路）と
   整合させる意図でこう分けたが、設計書に明記された分岐ではない。

10. **T3 以降の項目**: `thth run` は T1 では throw のみを行い、collect・refresh は

## 判定: **条件付き合格**。下の 1 件を直したら T1 完了とする。

### 差し戻し 1 件（`thth/core.py`）— 曖昧な公開失敗で inflight を消している

`_throw_locked()` が公開の失敗を一様に扱い、`publish_result.error` があれば必ず `inflight_mod.clear()` している。コメントには「コンテナ作成・公開の失敗は『実際には出ていない』ので inflight を残す理由が無い」とあるが、**公開の呼び出しについてはこれが成り立たない**。

`thth/adapters/threads.py` は公開の失敗を `HTTPError`（サーバが応答を返した）と `URLError`／`TimeoutError`／`OSError`（応答が返らなかった）に分けて捕まえているのに、`core.py` はその区別を捨てている。timeout や接続断は「Threads 側では成立して応答だけ失われた」場合を含む。

**再現の筋**: 08:07 の実行で公開が timeout → 実際には投稿されている → inflight が消える → md は post_id も `posted` も持たないまま → 09:07 の実行が同じファイルを選び直して**二重投稿**。`duplicate_text`（条件 11）は `status: posted` の md としか突き合わせないので掛からない。inflight はまさにこの窓のために作った仕掛けなので、ここで消すと仕掛けが目的を果たさない。

**直し方**（設計 §3.5 に表を足したので、それに合わせる）:

| どこで | 何が | inflight |
|---|---|---|
| コンテナ作成の失敗（全部） | 出ていない | 消す |
| 公開が HTTP 4xx | 出ていない | 消す |
| 公開が timeout・接続断・5xx・200 だが id 無し | **分からない** | **消さない**・exit 1 |
| 公開は成功・書き戻し／push が失敗 | 出た | 消さない（実装済み） |

そのために `PublishResult` に**失敗の種類**（例: `failure="none"|"container"|"publish_definite"|"publish_ambiguous"`）を持たせ、`core.py` はそれだけを見て分岐する。**HTTP の状態番号を core が解釈しない**（媒体ごとの知識はアダプタに閉じる・§3.4）。テストは受け入れ 10 の 6 種に **2 つ足す**: 「公開が timeout → inflight が残り exit 1」「公開が 4xx → inflight が消えて exit 1」。

## 差し戻し対応（2026-09-09）

事実だけを書く。

### 直したこと 1: 曖昧な公開失敗で inflight を消していた点

- `thth/adapters/base.py`: `PublishResult` に `failure: str = "none"` を追加。値は `"none"`／`"container"`／`"publish_definite"`／`"publish_ambiguous"` の 4 種。
- `thth/adapters/threads.py`: `publish()` の例外処理を分岐し直した。
  - コンテナ作成の失敗（`HTTPError`／`URLError`・`TimeoutError`・`OSError`／id 無し）は全部 `failure="container"`。
  - 公開の `HTTPError` は `e.code` が 400〜499 なら `failure="publish_definite"`、それ以外（5xx 等）は `failure="publish_ambiguous"`。
  - 公開の `URLError`・`TimeoutError`・`OSError`、および 200 だが id 無しは `failure="publish_ambiguous"`。
- `thth/core.py`: `_throw_locked()` は `publish_result.failure` だけを見て分岐する（HTTP の状態番号は core で見ない）。`failure == "publish_ambiguous"` のときは `inflight_mod.clear()` を呼ばずに `exit_code=1`・`action="inflight"` で返す（board には `inflight.json` がそのまま残るので既存の表示経路に乗る）。それ以外（`"container"`・`"publish_definite"`）は従来どおり inflight を消して `exit_code=1`・`action="post"`。
- テストを 2 本追加（`tests/test_fake_api.py` の `test_7_公開がtimeoutならinflightが残り次回も止まる`・`test_8_公開が4xxならinflightが消えて次回は普通に選び直せる`）。`python3 -m pytest tests/ -q` で確認。

### 直したこと 2: `thth queue` の「次に出るもの」を `select_one()` に一本化

- `thth/report.py`: 独立ロジックだった `_peek_next()` を削除し、`_next_via_select_one()` を新設。`core.list_queue_files`・`core.last_post_at`・`select_mod.recent_posted_texts`・`select_mod.select_one` を core の `throw_once()` と同じ呼び方で呼ぶ。`queue_summary()` の戻り値に `next_rejections`（選ばれなかった候補とその理由。他アカウント由来の `account_mismatch` は除く）を追加。`queue_summary(account_name, now=None)` に `now` 引数を追加（テスト用の時刻注入。既定は `jst.now_jst()`）。
- `thth/cli.py`: `cmd_queue` のテキスト出力に `いま出ない: <file> — <reason>` の行を追加。
- `tests/test_queue.py` を全面的に書き直し、`select_one()` の判定（`future`・`min_interval`・`quiet_hours`・`post_id_present`）が `next_rejections` に出ることを確認するテストにした。

### 併せて反映した裁定 2 件

- **文字数に末尾改行を含めない**: `thth/queuefile.py` の `extract_section()` を「前後の空行を落として末尾改行 1 個を足す」実装から「前後の空白を `str.strip()` で落とした文字列をそのまま返す」実装に変更。`tests/test_preview.py`・`tests/test_select.py`・`tests/test_lint.py` の 501 字フィクスチャ（旧実装は「500 通常文字＋末尾改行 1 個」で 501 字を作っていた）を「501 通常文字」に直した。
