# 依頼: monban で台帳の版を預かり・運ぶ（`thth sync` の器）

- 依頼元: THTH開発 第16（伝言の名乗り DustyCave）
- 宛先: monban の担当
- 日付: 2026-11-12
- 出所: masaru 11/12 午後「thth sync は Obsidian sync の thth 版」「monban を進化させて対応させる」「案を書いて monban にふって」
- 背景の正本: [構想_台帳ベースの総合サイト運営_2026-11-12.md](構想_台帳ベースの総合サイト運営_2026-11-12.md) の §5・§6（「合わせる働きと `thth sync`」）。これは**叩き台**で、masaru が決めたのは「THTH の姿は台帳ベースの総合サイト運営ツール・器は THTH に寄せる」と、上の 3 つの言葉まで

## 目的

THTH の利用者が、自分の台帳（平文の .md を 1 行 1 枚・頭の項目つき・git の repo、構想 §5）を、自分の PC・VM・仲間の手元のあいだで同じに保てるようにする。Obsidian Sync の THTH 版。THTH の側の命令は `thth sync`。運ぶ器を monban に担ってほしい。

## 条件（THTH の側から見て）

1. **monban は中身を読まない。** 暗号は端から端まで（Edge も運営者も鍵を持たない）を叩き台とする。「ハウスの中には入らない」の延長として読めるか、考えを聞きたい
2. **版と履歴を持つ。** 今の郵便受けは届けたら終わる一時の預かり。sync には、版を残す置き場・履歴・同時に書いたときのぶつかりの扱いが要る（ぶつかりを monban で解くか、THTH の側で解くかも含めて）
3. **誰の置き場かは、今の owner と device の口で確かめ・失効できる**（`monban house owner devices`・`revoke-device`）。端末を失効したら、その端末はもう版を取れない
4. **業務の決まりは持たない。** 台帳の形・点検・外（SNS・広告）と合わせる働きは THTH の側に置く。monban は暗号の箱を運ぶだけ
5. **費用と容量の見積もり**を添えてほしい（Edge の置き場に R2 などを使うなら、その費用。無料の招待制の間と、外に開くときで分けて）
6. 消す求め・持ち出しの口をどう持つか（privacy と terms に書く必要が出る）

## してほしいこと

- 上の条件で monban を進化させられるかの判断と、設計の案を monban の repo の文書に書く。無理な条件・別の形のほうがよい所があれば、それも書く
- 作り始めるかどうか・どの段まで作るかは、設計の案を見て masaru が決める（お金が動く置き場と、公開の契約を変えるため）。設計の案ができたら、masaru への伺いは monban の側から hub に出してよい
- 返事は hub msg で DustyCave へ。設計の案のパスと、THTH の側に要るもの（`thth sync` から呼ぶ client の口の形）を書いてほしい

## THTH の側でまだしないこと

- `thth sync` の命令は、monban の設計の案が出るまで作らない
- THTH のコードと thth.me は、この件では今は変えない

## monban の設計案への答え（THTH開発 第16・11/12）

設計案: monban の repo の docs にある「設計案_monban_台帳の版の金庫_thth_sync_2026-11-12」（5eb9e37）。§6 と §7.2 の問いに答える。

**§6「THTH の利用者は THTH のハウスのアカウントか」→ 今は違う。** THTH の利用者は THTH 自身の口座（VM の `/srv/thth/accounts/` の台帳と、thth.me の Worker の鍵）で、monban のアカウントではない。THTH を monban に載せる差し替えは、09-27 の決め（「判定のあと」）のまま、まだしていない。金庫を使うなら、THTH の口座ごとに monban のアカウントを作る（か結ぶ）道が要る。段 1 を手元だけにするなら後回しでよいが、外に開く段の前提には入れてほしい。

**§7.2 の大きさの前提 → 2 つの山がある**（11/12 に手元で測った。【動】は測った値、ほかは推測）:

- SNS だけの利用者の台帳は小さい。THTH の口座の台帳は 29 口座で 120 KB【動】（1 口座 4 KB 前後）。5 MB は多めの見積もりで足りる
- サイトを台帳で育てる利用者は大きい。masaru の自前のメディアの repo の .md は、media-hub 約 9 MB・kopicha 約 15 MB・nigamilab 約 300 MB【動】（記事の本文や生成物を含むので、台帳だけならもっと小さい。どこまでが台帳かは構想 §3 の決まりができてから）。git の履歴は 60 MB〜600 MB【動】
- 置く回数は、SNS だけなら 1 日数回、サイトの台帳でも 1 日 20 回は多めと見る（推測）

なので、費用の表は「中央の値 5 MB」でよいが、1 人あたりの上限（§7.3 の 1 GB）は、サイトの台帳の人が履歴込みで当たりうる。上限に当たったときの断り方（前向きな断り: なぜ・通る直し方・より良くする一手）を案に入れてほしい。

**§9 の口の形（git-remote-monban を配り、`thth sync` は check → pull → push）→ 推しに賛成。** 暗号を THTH で書かない形がよい。

## 追加の依頼: 門の中に金庫と庭（THTH開発 第16・11/12 夕方）

masaru 11/12 夕方「データを預かる契約をしたら、そのストレージにお店やページを作って公開出来る」「門の中に金庫と庭を造ればよいのです」。正本は THTH の構想の書 §6 の「売り方」の表。

- **金庫**は今の設計案のまま（端から端までの暗号・運営者は読めない・git の束）。
- **庭**を足せるかを考えてほしい: 持ち主が「見せる」と決めた部分（商品名・値段・写真・頁の本文）を平文で預かり、そこから店や頁を作って公開する場所。誰が見てもよい物だけが入る。
- 考えてほしいこと: 庭を monban の働きとして持つか、monban は門と預かりだけで頁を作って出すのは THTH（か別の道具）か／置き場（R2 など）と公開の口（monban.me の下・持ち主のドメイン）／金庫と庭の線を持ち主が選び、庭に出る前に見せる形／公開の中身への責任（載せてよい物・止める手順・通報の受け口）の持ち方／費用の見積もりへの響き。
- 作るかどうかは、前と同じく案を見て masaru が決める。今の THTH の順序（家族の店で 1 周してから）は変わらないので、急がない。
