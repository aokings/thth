# 手順: スレッド連投を書く（THTH を使う LLM 向け）— 2026-09-11

対応する設計: `設計_スレッド連投_2026-09-11.md`。

**「出せる」だけでは足りない。** `--topic` は前から実装されていて出すことは
できたのに、2026-09-10 まで誰も使いこなせていなかった（`苦味` で 0 件、
`コーヒー好きな人と繋がりたい` で views 1）。**能力と、使いこなす手段は別物。**
だからこの手順書は連投の実装と同じ納品に入っている。

---

## 0. まず: 分けないで済むなら分けない

**連投は「長いから分ける」ものではありません。** 1 投稿で言い切れる内容を
無理に 3 段にすると、読む人は 1 段目で止まります。

分ける理由になるもの:

- **比較**（A と B を並べる。1 段に詰めると両方ぼやける）
- **段階的な説明**（順番に意味がある）
- **先に問いを立てたほうが読まれる**とき

分ける理由にならないもの:

- 500 字に収まらない（→ **削る**ほうが先）
- 連投のほうが伸びるらしい（→ **うちにはまだ 1 本も実測がない**）

```bash
thth forms          # 形の語彙と選び方（読むだけ）
```

## 1. 原稿の形

`thth: 2` の queue ファイル 1 本 ＝ スレッド 1 束。**2〜4 段。**

```markdown
---
thth: 2
account: nigamilab-threads
publish_at: 2026-09-15T19:00:00+09:00
continue_until: 2026-09-15T20:00:00+09:00
status: draft
topic: コーヒー
form: 問い→答え
outlet: 記事へ
posts:
  - index: 1
  - index: 2
  - index: 3
---
# 経緯（THTH は読みません）

なぜこの形にしたか。

## threads

コーヒーが苦いのは、カフェインのせいでしょうか。

<!-- thth: 2/3 -->

カフェインを抜いたコーヒーに、カフェインだけを戻す。
それで苦味が上がるかを、人が舌で判定した試験があります。

<!-- thth: 3/3 -->

どちらの結果も、私の予想とは違いました。根拠を並べています。
https://nigamilab.com/topics/coffee-bitterness/
```

### 区切り

`<!-- thth: N/M -->` を**独立行**で置きます。markdown の preview には出ません。

- **番号は 2 から始まります**（1 段目の前に区切りは要りません）
- **`M` は総数**。段の数と合わないと lint で止まります
- **空の段は通りません**
- **`posts:` の件数と段の数も一致させます**

### `continue_until` は必須です

**「翌日になって突然 3/4 が出る」を防ぐため**です。ここを過ぎたら、残りの段は
出ません（board に「未完のスレッド」として出ます）。**publish_at より後**に
してください。

### `topic` は先頭の段だけ

2 段目以降に書くと lint で止まります。**API が併用を許すかは未確認**で、
初版の方針として先頭に限っています（黙って捨てたりはしません）。

### `form` と `outlet`

**承認の対象ではありません**（分類するだけのラベルなので、変えても公開される
内容は変わりません）。ただし**知らない語は通りません**——綴り違いが別の型として
増えると、あとで比較にならないからです。`thth forms` で一覧が見られます。

## 2. 書くときに守ること

1. **先頭だけでも、何の話で何が得られるか分かるようにする。**
   多くの人は 1 段目しか見ません。
2. **根拠や重要な留保を最後まで隠さない。**
   「続きはこちら」で釣って、2 段目で前提を覆すのは**読者を欺く形**です。
   うちのプロジェクトの編集方針（`avoid_misrepresentation`）にも反します。
3. **各段が単独でも意味を持つ**ようにする。返信は別々に流れます。
4. **最後の導線を明示する。** 記事へ渡すなら、その URL を最終段に。
5. **段の番号を本文に書くかは自由。** THTH は本文を整形も切り詰めもしません
   ——書きたければ自分で `1/3` と書いてください。

## 3. トピックは束全体で判断します

`thth topics suggest` は**全段を読みます。** 先頭に topic、最終段に記事 URL を
置く形なので、**先頭だけを見ても記事との適合は判断できません。**

出力の `evidence.segments` に段ごとの本文が入ります（連結した 1 本の文字列では
ありません——どこで切れて何本の投稿になるかが判断に効くので）。

## 4. 承認

`thth approve` の二段確認は v1 と同じです。**ただし表示が違います**——
各段の全文と返信関係が出ます。

**承認は「この段の並びを、この account で、この時刻に、この期限まで出す」**
という意味です。段の割り方を変えたら別の承認になります（2 段にまとめても、
3 段に割り直しても、`approved_sha` が変わります）。

## 5. 出たあとに直したいとき

**公開済みの段は凍結されます。誤字修正でもできません。**

記録が嘘になるからです（「この本文で出した」と書いてあるものが、実際に出た
ものと違う状態）。**未公開の段と `continue_until` は直せます。**
直したら**再承認**してください——同じ実行のまま、続きだけが出ます。

**最初から出し直したいときは、別の原稿にしてください。** 同じ原稿で 2 回目の
実行は自動では始まりません。

## 6. 止めたいとき

```bash
thth revoke <原稿> --by "<あなた>" --reason "…"
```

出力は**確認できた段・要求中の段・未着手の段**に分かれます。

> **停止を確認した後は、新しい公開要求を送りません。
> 既に送信済みの要求は取り消せません。**

これ以上は約束できません。**出てしまった段は Threads の画面から手で消す**
しかありません。

## 7. 数の読み方

**やってはいけないことが先です**（`thth forms` にも出ます）。

- **全段の views を足して「到達人数」と呼ばない**（同じ人が複数段を見ます）
- **最終段 ÷ 先頭段を「読了率」と呼ばない**（views の定義がそれを支えません）
- **記事クリックを views で代用しない**（`clicks` は API から返ってきません）

言えるのは**段ごとの数**と、その並びまでです。

## 8. いまの状態

**うちはスレッド連投をまだ 1 本も出していません。**

`thth forms` の `measured` は空です。**形ごとの当たり率はまだありません。**
トピックのときと同じで、**先に実測が無いまま「この形が効く」と言うと、
根拠のない型が権威を持ちます**（`一般名詞なら安全` と思い込んで 8 語 0 件を
踏んだのと同じ罠）。

**この形式で成果が出るかは未検証です。** そのつもりで使ってください。
