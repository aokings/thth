# 手順: スレッド連投を書く（THTH を使う LLM 向け）— 2026-09-11

対応する設計: `設計_スレッド連投_2026-09-11.md`。

**「出せる」だけでは足りない。** `--topic` は前から実装されていて出すことは
できたのに、2026-09-10 まで誰も使いこなせていなかった（`苦味` で 0 件、
`コーヒー好きな人と繋がりたい` で views 1）。**能力と、使いこなす手段は別物。**
だからこの手順書は連投の実装と同じ納品に入っている。

---

## 0. なぜ分けるのか

**ここを読まずに書かないでください。** 以前この節は「分けないで済むなら
分けない」とだけ書いてあり、理由を**文章構成の話だけ**で説明していました。
その結果、2 セッションが**47 本を見て 45 本を「分ける理由なし」**と判断しました
——**媒体の答えではなく、こちらが与えた枠の答え**です（統括の誤り・2026-09-11）。

分ける動機は 3 つあります。**うちが確かめたのは 3 つ目だけです。**

### (1) 信号（アルゴリズムに対して）

自分への返信は**先頭の投稿の返信数を増やし**、段ごとに views が付きます。
**有益な投稿・有益なアカウントとみなされたい**という動機の、機械側の形です。

**うちは未検証です。** 返信数が自分の返信で増えるかも、それで配信が増えるかも、
1 本も測っていません。**「連投のほうが伸びるらしい」を理由にしないでください。**

### (2) 演出（読む人に対して）

**続きが気になる。** これは本物の効果です。ただし——

> **引っぱってよいのは答え。引っぱってはいけないのは留保。**

同じ「気になる」でも、**残すものが答えなら安全、留保なら誤らせます。**

- 1 段目を**問いで終える** → 止まった人は、間違った印象を持たない
- 1 段目で**断定して、留保を後ろに置く** → 止まった人は、間違ったことを持ち帰る

### (3) 編集（中身に対して）

**削れるのが飾りなら削る、削れるのが根拠なら分ける**（asmon 関東セッション）:

> 1 投稿に詰めると、真っ先に削れるのが**仕組み**で、残るのは
> 「古いことがあります」という**根拠の無い断定**になる。

分ける理由になるもの:

- **比較**（A と B を並べる。1 段に詰めると両方ぼやける）→ `form: 比較`
- **段階的な説明**（順番に意味がある）→ `form: 手順`
- **先に問いを立てたほうが読まれる**とき → `form: 困り事→理由→行動`
- **数えられるものを並べる**（「10 選」など）→ `form: 列挙`

分ける理由に**ならない**もの:

- 500 字に収まらない（→ **削る**ほうが先。ただし上の「根拠が落ちる」を読むこと）

## 0.1 判断の基準

**分けるかどうかを決める問いは 1 つです。**

> **1 段目で止まった人にとっても有益か。**

満たせないなら、その連投は**有益さを演じているだけ**です。

**多数派は先頭で止まります。** だから (1) の信号を取りにいくほど、
**増えた配信に乗るのは 1 段目**であり、**1 段目が誤解を招く形なら誤解が広く
配られます。** 信号を取りにいく理由と、先頭段を正確にする理由は同じものです。

**2 セッションが独立に同じところで迷いました**（2026-09-11）:

> 2 段目で数字を出して 3 段目で留保になります。**釣ってから前提を覆す形と
> 紙一重**なので、判断に迷いました。（kopicha）

> 「1 段目で答えた範囲の外側を 2 段目で示す」と読み替えました。（nigamilab）

**後者が正しい形です。** 前者は「引っぱっているのが留保」になっています。

```bash
thth forms          # 形の語彙と選び方（読むだけ）
```

## 0.2 まだ測っていないこと

**うちはスレッド連投を 1 本も出していません。** 次の 2 つは 1 本出せば分かります。

| 測ること | 分かること |
|---|---|
| 先頭段の `replies` が、自分の返信で増えるか | (1) の土台があるか。**増えないなら仮説が崩れる** |
| 2 段目・3 段目の views が 1 段目からどれだけ落ちるか | **どれだけの人が先頭で止まるか。** 落ちるほど 0.1 が効く |

**「配信が増えたか」は、これだけでは分かりません。** 同じ枠・同じトピックの
単発と比べて初めて言えます。**出す前に「何が出たらどう読むか」を書いてから
出してください**——後から解釈を作らないために。

## 1. 原稿の形

`thth: 2` の queue ファイル 1 本 ＝ スレッド 1 束。**2〜4 段。**

```markdown
---
thth: 2
account: nigamilab-threads
publish_at: 2026-09-15T19:00:00+09:00
continue_until: 2026-09-15T20:00:00+09:00
status: draft
topic: コーヒー
form: 困り事→理由→行動
outlet: 記事へ
numbering: なし
posts:
  - index: 1
  - index: 2
  - index: 3
---
# 経緯（THTH は読みません）

なぜこの形にしたか。

## threads

コーヒーが苦いのは、カフェインのせいでしょうか。

<!-- thth: 2/3 -->

カフェインを抜いたコーヒーに、カフェインだけを戻す。
それで苦味が上がるかを、人が舌で判定した試験があります。

<!-- thth: 3/3 -->

どちらの結果も、私の予想とは違いました。根拠を並べています。
https://nigamilab.com/topics/coffee-bitterness/
```

### 区切り

`<!-- thth: N/M -->` を**独立行**で置きます。markdown の preview には出ません。

- **番号は 2 から始まります**（1 段目の前に区切りは要りません）
- **`M` は総数**。段の数と合わないと lint で止まります
- **空の段は通りません**
- **`posts:` の件数と段の数も一致させます**

### `continue_until` は必須です

**「翌日になって突然 3/4 が出る」を防ぐため**です。ここを過ぎたら、残りの段は
出ません（board に「未完のスレッド」として出ます）。**publish_at より後**に
してください。

### `topic` は先頭の段だけ

2 段目以降に書くと lint で止まります。

**ただし、画面では返信にもトピックが付いています**（2026-09-11 に実物を確認）。
`中学受験` の 4 段の束で、`1/4`・`2/4`・`3/4` すべてに `› 中学受験` が出て
いました（`4/4` だけ無く、**25 分あとに足された段**でした）。

**API で同じことができるかは未確認**なので、初版は先頭に限ります。
**うちが 1 本出せば確かめられます。**

### 連投にすると決める前に、5 つに答える

**「記事 URL があるから連投」にしないための関門です**（Codex §8）。

1. 誰が、何を知りたい記事か。
2. **単発に収まらず、連投にすると分かりやすくなる理由は何か。**
3. どの型を選び、**各段で何を一つずつ渡すか。**
4. どの主張が記事のどこに支えられ、**何が不明か。**
5. 主目的は理解・会話・記事閲覧のどれか。

**記事 URL を付ける投稿の基本案**: 結論と対象読者 → 根拠・条件 → 使い方と記事 URL

- **先頭だけでも一つ分かる。** タイトルの言い換えや予告だけにしない。
- **中段は新しい情報を渡す。** 結論の繰り返しにしない。
- **末尾で記事を読む理由が分かる。** 「詳しくはこちら」だけにしない。
  **記事にない内容を約束しない。**

### `form` と `outlet` と `numbering`

**承認の対象ではありません**（分類するだけのラベルなので、変えても公開される
内容は変わりません）。ただし**知らない語は通りません**——綴り違いが別の型として
増えると、あとで比較にならないからです。`thth forms` で一覧が見られます。

`numbering` は**本文に `1/3` のような番号を書いたか**（`あり` / `なし`）。
書いた内容と食い違うと警告が出ます（**止めません**）。

**profile に `avoid_forms` を書くと、その型は使えなくなります。**
「流行っているから」で編集方針が溶けないようにするためです
（例: 体験を創作しないプロジェクトは `体験→再現方法` を宣言しておく）。

> 番号の有無を `form` と一緒に記録するなら、**原稿の front-matter に欄が
> ほしい**です。（asmon 関東セッション 2026-09-11）

**記録する場所が無ければ、比べられません。**

### プロジェクト側の検査スクリプトに注意

**文字数を「連結した本文」で数えている検査は、連投で必ず落ちます**
（nigamilab セッション 2026-09-11・自分の `gate_sns_queue.py` で踏んだ）。

`thth lint` は**段ごとに**数えます。プロジェクト側にも同じ検査があるなら、
**段ごとに数えるよう直してください。**

### 書けたら確かめる

```bash
thth lint <原稿>        # 形（区切り・連番・段の数・文字数・topic の位置）
thth preview <原稿>     # **段ごとに分けて**出す本文を見る
```

`preview` は区切り行を出しません。**1/3・2/3 と返信関係**が並びます。

## 2. 書くときに守ること

1. **先頭だけでも、何の話で何が得られるか分かるようにする。**
   多くの人は 1 段目しか見ません。
2. **引っぱってよいのは答え。引っぱってはいけないのは留保**（§0.2）。
   「続きはこちら」で釣ること自体は構いません——**続きが気になるのは本物の
   効果**です。**駄目なのは、止まった人が間違ったことを持ち帰る形。**
   1 段目で断定して 2 段目で前提を覆すのは、うちの編集方針
   （`avoid_misrepresentation`）に反します。
3. **各段が単独でも意味を持つ**ようにする。返信は別々に流れます。
4. **最後の導線を明示する。** 記事へ渡すなら、その URL を最終段に。
5. **段の番号を本文に書くかは自由。** THTH は本文を整形も切り詰めもしません
   ——書きたければ自分で `1/3` と書いてください。

   nigamilab セッションは**書かない**ほうを選びました（2026-09-11）:

   > 各段が単独で意味を持つように書いたので困りません。番号は「続きがある」の
   > 合図にはなりますが、**1 段目で止まる人に「これは途中です」と思わせる**のは
   > 損だと判断しました。

   asmon 関東セッションも**書かない**を選びましたが、理由が違いました:

   > 3 段とも問いや事実で始まる形にしたので、先頭に番号が付くと
   > **その段が単独で読めなくなる**感じがありました。

   **どちらが効くかは実測がありません。** front matter の `numbering:` に
   書いてください——**記録する場所が無ければ、比べられません。**

## 3. トピックは束全体で判断します

`thth topics suggest` は**全段を読みます。** 先頭に topic、最終段に記事 URL を
置く形なので、**先頭だけを見ても記事との適合は判断できません。**

出力の `evidence.segments` に段ごとの本文が入ります（連結した 1 本の文字列では
ありません——どこで切れて何本の投稿になるかが判断に効くので）。

## 4. 承認

`thth approve` の二段確認は v1 と同じです。**ただし表示が違います**——
各段の全文と返信関係が出ます。

**承認は「この段の並びを、この account で、この時刻に、この期限まで出す」**
という意味です。段の割り方を変えたら別の承認になります（2 段にまとめても、
3 段に割り直しても、`approved_sha` が変わります）。

## 5. 出たあとに直したいとき

**公開済みの段は凍結されます。誤字修正でもできません。**

記録が嘘になるからです（「この本文で出した」と書いてあるものが、実際に出た
ものと違う状態）。**未公開の段と `continue_until` は直せます。**
直したら**再承認**してください——同じ実行のまま、続きだけが出ます。

**最初から出し直したいときは、別の原稿にしてください。** 同じ原稿で 2 回目の
実行は自動では始まりません。

## 6. 止めたいとき

```bash
thth revoke <原稿> --by "<あなた>" --reason "…"
```

出力は**確認できた段・要求中の段・未着手の段**に分かれます。

> **停止を確認した後は、新しい公開要求を送りません。
> 既に送信済みの要求は取り消せません。**

これ以上は約束できません。**出てしまった段は Threads の画面から手で消す**
しかありません。

## 7. 数の読み方

**やってはいけないことが先です**（`thth forms` にも出ます）。

- **全段の views を足して「到達人数」と呼ばない**（同じ人が複数段を見ます）
- **最終段 ÷ 先頭段を「読了率」と呼ばない**（views の定義がそれを支えません）
- **記事クリックを views で代用しない**（`clicks` は API から返ってきません）

言えるのは**段ごとの数**と、その並びまでです。

## 8. いまの状態

**うちはスレッド連投をまだ 1 本も出していません。**

`thth forms` の `measured` は空です。**形ごとの当たり率はまだありません。**
トピックのときと同じで、**先に実測が無いまま「この形が効く」と言うと、
根拠のない型が権威を持ちます**（`一般名詞なら安全` と思い込んで 8 語 0 件を
踏んだのと同じ罠）。

**この形式で成果が出るかは未検証です。** そのつもりで使ってください。
