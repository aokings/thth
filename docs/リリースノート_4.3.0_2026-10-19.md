# リリースノート 4.3.0（返信はまとめて出す）

2026-10-19。masaru「返信対応が即時じゃなくて、スケジュールになっちゃうのがちょっとモヤります」「返信が 10 分おきに出る、みたいなオペレーションになるからです」への直し。設計は [上限と連投の柵の「返信の扱い（4.3）」](設計_上限と連投の柵_2026-10-17.md)。

## 起きていたこと

レーン（kopicha など）は人への返信を queue の原稿（`reply_to:`／`reply_to_file:` と `publish_at`）で書き、何本もまとめて承認しています。timer（`thth run`・10 分ごと）は 1 回に `max_per_run`（既定 1）本しか出さないので、まとめて承認した返信が 10 分おきに 1 本ずつ出ていました。投稿の間隔（`min_interval_hours`・kopicha-mastodon と kopicha-bluesky は 6 時間）も返信に掛かっていました。

## 変わったこと

- **timer は時刻の来た返信を 1 回でまとめて出します。** `max_per_run` は投稿（返信でないもの）にだけ掛かります。返信は返信の窓・返信の日の上限・1 回の時間（どれも下）に入るだけその回で出し、入らなかった分は queue に残って次の回（日の上限なら翌日 0 時以降の回）が出します。口座は止めません。`publish_at` は書き換えないので承認の指紋は変わりません。返信どうしの間は 3 秒置きます。
- **1 回の実行で返信に使う時間は 150 秒まで**です。時間は実行の入口から数えます（ロックを待った分・投稿に使った分を含む）。1 本を始める前に「経過 + 1 本の見込み（Threads 40 秒・ほかは 5 秒）」が 150 秒を超えるなら、その返信から次の回に回します。Threads では 1 回でおよそ 3 本です。
- **返信には投稿の間隔（`min_interval_hours`）を掛けません**（timer でも）。**返信を出しても次の投稿は押されません**（間隔は投稿の時刻だけから数えます）。静かな時間帯（`quiet_hours`）は返信にも掛かります。
- **承認したその場で送ります。** `thth approve --confirm` と `--confirm-file`（2 段目）で確定し push まで通った原稿のうち、返信で `publish_at` が今か過去のものは、同じ命令の中で timer と同じ道（ロック・同期・承認の照合・返信の窓・日の上限・時間）で出します。出力は「<口座>: 承認して N 本送りました」に、残した分があれば理由と次の時刻を日本語で添えます（`--json` は `sent_now` を常に出します・送らなければ空）。送らないのは、本番でない口座・`scheduled: false`・はてな・媒体の断りで止めた口座・**安全装置か持ち主が止めた口座**・timer が動いている最中（ロックを待たず、timer に任せます）。投稿と未来の時刻の返信は今どおり timer が時刻に出します。
- **返信の窓は返信だけを数えます。** 柵の行 `reply.burst` は返信だけを数え、既定は Threads・Bluesky・Mastodon が 10 分に 10 件、**X は 10 分に 3 件**です（媒体の特性の台帳に根拠つきで置きました。10 は媒体の文書には無い THTH の線で、どの媒体の API の上限よりも内側。X は自動化の規則と 10/14 の「人間か確認」の観測から締めた推測です）。投稿の窓 `post.burst`（10 分に 3 で口座を止める）は返信を数えなくなりました。返信を何本出しても口座は止まりません。
- **返信の日の上限を投稿と分けました。** 新しい行 `reply.daily`（返信だけ・既定 50・数は THTH の推測）。投稿の日の上限 `post.daily`（`daily_max_posts`）は投稿だけを数えます。超えた返信は `daily_limit`（詳細 `reply_daily`・翌日 0 時を添える）で断るか、timer なら翌日に回します。口座は止めません。数は `thth account set <口座> reply.daily <数> --by <名前>` で変えられます。timer・承認の場の送り・`thth send --reply-to`・thth.me の `send_request`・返信の順番待ち・thth.me の予約（猶予を含む）のどれでも同じ行で数えます。予約では、刻む原稿が返信なら「その日の返信 + その日に刻んだ返信の原稿」、投稿なら「その日の投稿 + その日に刻んだ投稿の原稿」を数えます。

## 変わらないもの

承認の指紋・投稿の振る舞い（1 回 `max_per_run` 本・投稿の窓で止める）・はてなのブログとブックマーク・スレッド連投・断りの符丁（足したのは `daily_limit` の詳細 `reply_daily` だけ）。thth.me の `send_request` は今もその場で出し、`schedule_request` は予約のまま timer が出します。MCP には承認の道具がありません。

## thth.me（Worker）

**Worker の deploy は要りません。** 変わったのは VM の Python だけです（Worker は断りの符丁をそのまま中継し、詳細の語を検めていません）。出すのは release の枝を進めることと tag だけです。`/activity` の「今日の公開」は 4.3.0 から投稿だけの数になります（返信を含まない・`daily_max_posts` と同じ数え方）。

## 確かめた範囲

試験（偽物の媒体と本物の git の一時 repo）と、柵を 10 か所 1 つずつ壊して赤を見たこと（設計の節に表）。本番の媒体ではまだ確かめていません。`reply.daily` の 50 と X の 10 分に 3 は推測の数で、媒体の文書にはありません。

## レーンへの使い方の案内

**返信は `publish_at` を今か過去にして、まとめて承認すれば、その場で出ます。** 1 段目 `thth approve <原稿…>` で本文を見せ、2 段目 `thth approve <原稿…> --confirm <束の digest> --by <名前>`（または `--confirm-file`）。返信の窓（X は 10 分に 3 件・ほかは 10 件）を超えた分と、1 回の時間（Threads はおよそ 3 本）に収まらなかった分は、次の timer（10 分以内）で出ます。1 日に 50 本を超える返信は翌日に回ります。急がない返信は今までどおり未来の `publish_at` で予約できます。
