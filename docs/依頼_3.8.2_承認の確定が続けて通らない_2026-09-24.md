## 1. 同期で FETCH_HEAD に依らない（P1）

**実測**: masaru が確定の命令 10 行（`thth approve <VM のパス> --confirm <digest> --by masaru`）を `set -e` で続けて実行 → 1 本目だけ承認、2 本目で「repo を同期できないので承認しません: git pull --ff-only に失敗しました: fatal: Cannot fast-forward to multiple branches.」。clone の設定に異常は無く、FETCH_HEAD に for-merge の行が 2 つ読まれた競合（1 本目の commit・push と前後して別の fetch が FETCH_HEAD を書いた）と見られる。

**直し**（`thth/writeback.py`）:
- `_confirm_synced`: `fetch origin` のあと `pull --ff-only` をやめ、`merge --ff-only @{u}`（upstream の ref を直接使う・FETCH_HEAD を読まない）。
- push の再試行（`pull --rebase --autostash`）も、`fetch origin` のあと `rebase --autostash @{u}` にする（index の控えと戻しは従前どおり）。
- 他に `pull` を使っている所（`thth pull`・selfupdate 等）を grep し、FETCH_HEAD に依る形があれば同じく直す（直した所を検収依頼に列挙）。
- どこかで repo の lock を取らずに fetch している読み手があれば、それも検収依頼に書く（直すかは判断が要れば報告）。

**試験**: 本物の git で、FETCH_HEAD に for-merge を 2 行書いた状態（別の枝も for-merge にした fetch の直後）でも `_confirm_synced` が通る／`merge --ff-only @{u}` で追いつく／upstream が進んでいて ff できないときは従前どおり断る。確定を 3 本続けて打つ試験（同じ repo・間に別の fetch を挟む）で 3 本とも承認される。単変異: `pull --ff-only` に戻す 1 本。

## 2. 複数の確定を 1 回で（要望）

- `thth approve --confirm-file <file> --by <名前>`: 1 行に `<原稿のパス> <digest>` の組。1 回の同期と 1 回の lock の中で順に確定し、1 本でも digest が合わなければその 1 本だけ断って他は進める（断った本と理由を最後に並べる）。commit は 1 本ずつ（従前どおりの単位）でも、まとめて 1 本でもよい（検収依頼に書く）。push は最後に 1 回。
- 途中で止まったとき（同期・push の失敗）は、どこまで通ったかと、残りの命令をそのまま打てる形で出す。
- 1 段目の出力（digest を出す所）に、複数あるとき `--confirm-file` の中身の形を 1 行添える。

**試験**: 3 本の組で全部通る／1 本だけ digest 違いでその 1 本だけ断る／push 失敗で残りの命令が出る。単変異: 1 本の digest 違いで全部を止める形 1 本。
