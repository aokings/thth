## 4. 実装の要点

### 4.1 P1・1: 5 項目の指紋（`thth/core.py`）

旧実装の `_section_matches()` は本文（media の節）の hash（
`approval.compute_body_hash()`）しか見ていなかった。公開中に別 clone から
`account`・`topic`・`reply_to`・`publish_at` だけを書き換えて push しても、
本文の hash は変わらないためすり抜けていた。

- `_throw_chosen()` の冒頭（select_one() が approved_sha の一致を検査済みの
  直後・公開の前）で、`approval.compute_approved_sha()` と同じ 5 項目
  （本文・account・reply_to・topic・publish_at）の指紋 `expected_fingerprint`
  を固定する。`status` は THTH 自身が `posted` に変えるので指紋には含めない
  （`compute_approved_sha()` の 5 項目のまま・変更していない）。
- この指紋を `inflight.write()`・`sent.write()` の新しい引数
  `approved_fingerprint` として記録する（`body_hash` は既存のテスト・記録との
  後方互換のため残すが、実際の照合には使わない）。
- `_current_fingerprint(path, media)`: **いまファイルに書かれている** 5 項目
  から指紋を計算し直す（型外・publish_at が壊れている場合は None＝不一致
  扱い・fail-closed）。
- `_fingerprint_matches(path, media, expected_fingerprint)`: 上の現在値を
  固定した指紋と比較する。**現在の `approved_sha` の値そのものとは比較しない**
  ——remote が別内容で再承認されている可能性があるため、「実際に公開した
  投稿」の指紋という不動点とだけ比較する。
- 書き戻し前（rebase 前・ローカルのファイル）の照合と、
  `writeback.commit_and_push()` の `validate` コールバック（rebase 後・push
  直前）の両方をこの関数に切り替えた。不一致なら従来どおり: push しない・
  書き戻さない・再公開しない・inflight を残す・exit 1
  （`text_mismatch_before_writeback` / `text_mismatch_after_rebase`）。

### 4.2 P1・2: git repo なのに origin が無いのは同期失敗（`thth/writeback.py::sync_repo()`）

旧実装は「`origin` という remote が無い」を「`repo_dir` が存在しない」
「git repo でない」と同じ枝で成功扱い（素通り）にしていた。有効な承認済み
queue を残したまま `origin` を外すと、同期元を確認できないまま select →
公開に進み、書き戻しの push で初めて失敗していた。

- `repo_dir` が存在しない・git repo でない（`.git` が無い）→ そこに queue は
  無いので引き続き素通り（成功扱い）。
- `repo_dir` が git repo なのに `origin` が無い、または `git remote`
  コマンド自体が失敗する → 同期失敗として扱う（`(False, "origin という
  remote が見つかりません（同期元を確認できないため投稿しません）")` 等）。
  呼び出し側 `core.py::_throw_locked()` は既存の `repo_sync_failed` 経路
  （`exit_code=2`）でそのまま受ける（`core.py` 自体は変更していない）。
- `fetch` できない・`--ff-only` に失敗する、は元々正しく同期失敗として
  扱っていたので変えていない。

### 4.3 P2: board の妥当性検査を時刻から切り離す（`thth/select.py::select_one()`）

旧実装は条件 6（静かな時間帯）・7（最短間隔）を条件 8 以降（内容・承認の
妥当性検査）より**先に**見ており、全滅すればそこで即 return していた。その
ため `approval_stale` 等の内容診断が静かな時間帯にはまったく走らず、
board の実行時刻（06:20 JST）がちょうど静かな時間帯（22:00〜07:00）の中に
あるため、同じ承認後変更ファイルが 10:00 には要確認 1 件・06:20 には 0 件、
という食い違いが起きていた。

- 条件 8 以降（media の節・approval_stale・文字数超過・hashtag・topic・
  stale・重複本文）を**全候補について先に**評価し、`needs_review`・
  `rejections`（内容起因の理由）を確定させる。
- 妥当性検査を通った候補（survivors）に対してのみ、そのあとで条件 6・7
  （静かな時間帯・最短間隔）を適用し、「いま出すかどうか」だけを決める。
- 静かな時間帯には出さない、という既存の挙動（`chosen` が None になる）
  そのものは変えていない。`thth/report.py`（board・queue いずれも
  `select_one()` を呼ぶだけ）は無変更。

**挙動の変化点（意図した副作用）**: 内容が不正（例: 文字数超過）で、かつ
静かな時間帯でもあるファイルについて、報告される理由が変わる。旧実装は
（静かな時間帯の判定が先に走るため）`quiet_hours` とだけ報告していたが、
新実装は本来の理由（例: `too_long(600)`）をまず報告する。これは指摘の
「content/approval diagnostics must be independent of publication eligibility」
の要求どおりで、既存の `tests/test_quiet_hours.py`・`tests/test_select.py`
（いずれも内容が正常なファイルで静かな時間帯・最短間隔を検査している）は
無修正のまま緑。

## 7. まだ穴が残ると思う箇所（正直に記録）

- **P1・1 は書き戻し・再公開・inflight を止めるが、公開そのものは取り消せない。**
  `adapter.publish()` は指紋の照合より前に呼ばれる（実際に Threads へ送る
  API 呼び出しは、元々選ばれた account のトークンで行われる）。今回の修正が
  防ぐのは「変更後の属性に元の投稿の post_id を付けて push し、記録上の
  account/topic が実投稿と食い違ったまま残ること」であって、公開そのものの
  取り消しではない（REVIEW.md の P1・1 の注記どおり: "not evidence that a
  post was sent to the changed account... the API payload used the originally
  selected account"）。
- **`_current_fingerprint()` は型外・publish_at 不正を「不一致（None）」として
  fail-closed で扱う。** これは意図した挙動（安全側）だが、`account` フィール
  ドがまるごと消えた等の壊れ方をした場合、原因（メタデータ改変か単純な
  ファイル破損か）の切り分けは人が repo を見る必要がある（`error` コードは
  `text_mismatch_before_writeback` / `text_mismatch_after_rebase` のみで、
  どの項目が食い違ったかまでは出さない）。
- **P1・2 は `git remote` の returncode のみで判定する。** stderr の中身
  までは解釈していない（`redact_mod.redact()` してそのまま返すだけ）。
  「origin が無い」以外の `git remote` 失敗（壊れた repo 等）も同じ
  `repo_sync_failed` になる。安全側だが原因の切り分けは人が読む必要がある
  （前回の検収文書 §7 で同種の指摘が `sync_repo()` の fetch/pull 側にも
  ある。今回はそこを広げていない）。
- **P2 の分離により、静かな時間帯中に報告される rejection 理由が変わる
  ケースがある**（§4.3 の「挙動の変化点」）。`thth/cli.py`・
  `thth/report.py::queue_summary()`（`next_rejections`）はこの理由文字列を
  そのまま表示に使っているため、静かな時間帯に「なぜ出ないか」の一次的な
  表示が `quiet_hours` から本来の理由（`too_long` 等）に変わる場合がある。
  指摘の要求どおりの変更だが、運用側の表示文言に影響がある点は明記しておく。
- **`board_summary()` は今回も `select_one()` をアカウントごとにもう一度
  実行する構造のまま**（前回の検収文書 §7 で指摘済みの重複。今回は
  select_one() 内部の順序を直しただけで、呼び出し構造自体は変えていない）。
