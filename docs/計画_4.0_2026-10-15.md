## 0. 一言で

**4.0 は「記事を書いたら各媒体へ届け、直したら反映できる」版にする**（masaru 10/15 の目玉・10/16「入れる」）。

**完成の条件は次の一連が通ること**（masaru 10/16）:

1. 画像つきの記事を承認して、はてなブログへ公開できる（今すぐ・予約）
2. SNS の告知と、選んだ記事のはてなブックマークを、その記事に結べる
3. 正本（利用者の repo の記事）の修正を検出できる
4. 差分を承認して、出した先を更新できる
5. 反応を記事へ戻せる

この一連の検収に、別のブログへの誤送信・外での手直し・通信の切断・画像だけ成功・予約の取り消しと止めを含める（§3.7）。

**「読者が増えた」はリリースの条件にしない。** 配信と更新が正しく動くことが 4.0 の成立で、反応ゼロに効いたかは運用のあとに別に測る（§6）。

### 名前の読み替え（masaru 10/15）

THTH はもともと「ThreadsThrower（Threads への投げ手）」（設計 9/8）。名前は変えず、**広い意味の thread（糸・話の流れ）を投げる道具＝Thread Thrower** と読み替える（masaru「広義の Thread を取ればよいのでは」）: 1 本の記事からブログ・SNS・ブックマークへ伸びる糸を張り、その糸を伝って反応を記事に戻す。コマンド名・PyPI・MCP registry・thth.me は変わらない。

## 1. いまの THTH と、4.0 で変えたいこと

THTH は SNS（Threads・X・Bluesky・Mastodon）の「調べる・出す・測る」の CLI。利用者は自分の LLM から使う。公開は承認の二段か `--production` を通す・自動返信はしない・上限で暴走を止める、が芯。

出発点（masaru 10/13）は「フォロワーが 0 で、何を出しても反応が皆無な問題を破る」。SNS の道具としての機能はもうほとんどある。足りないのは:

1. **記事が THTH の単位に無い**。投稿が記事と切れていて、SNS の数と記事の読まれ方を結べない。
2. **ブログとブックマークへの道が無い**。記事を読まれる場所に置く道と、はてなの中で見つけてもらう道。
3. **直したものを出した先へ反映する道が無い**。

## 2. 線引き（masaru 10/15 の決定と、レビューを受けた言い直し）

| | THTH（声・ヘッドレス） | hub（場・見せる頭） | h2d（時と出来事） |
|---|---|---|---|
| SNS・ブログ・ブックマークへの読み書きと記録 | 持つ | — | — |
| 公開と予約（承認・上限・止め）。**予約の台帳は THTH の 1 か所だけ** | 持つ | — | 遅れ・止まりを見張って起こす |
| 記事の正本 | **持たない**（利用者の repo）。配信に要る確定した配信原稿・承認の対象・送信の記録は持つ | — | — |
| ダッシュボード・媒体をまたいだ合計や順位 | **持たない**（材料を出すだけ） | **持つ** | — |
| 世の中の出来事を見張る・判定（Jev） | 持たない | — | **持つ** |
| 出来事を外に流す | **出す** | 受けて「行くべき所」に積む | 受けて起点にする |

- masaru「ダッシュボードやメディア間連携なんかは、ハブに譲っちゃう」（10/15）。
- **「写しを持たない」の言い直し**（レビュー 1 の 3）: THTH は記事の**編集できる第二の正本**を持たない。承認した配信原稿（変換したあとの本文・依存する画像・配信先）は固定して持つ。持たないと「何を承認したか」が言えない。
- **予約の台帳は 1 か所**（masaru 10/16「予約台帳が点在するのは避けるべき」）: はてなブログの予約は、はてな側の予約（`hatenablog:scheduled`）を使わず、THTH の timer が時刻に「今すぐ公開」を送る（§3.3）。
- **Jev の線はデータの由来で決める**（masaru 10/15 は向きで分けた。レビュー 1 の 10 を受けて言い直す）: 自前の観測・利用者が書いた原稿・媒体 API 由来・その派生や混合・由来不明を区別し、送り先と目的ごとに許す。値段の観測（自前）の経路は、Meta や TypeSafe の未確認と切り離して進められる。媒体 API 由来のものを Jev に渡すのは、TypeSafe の規約の確認（masaru）のあと。

## 3. 4.0 の中身

### 3.1 記事と配信の台帳

[約束_記事と配信の記録](約束_記事と配信の記録_2026-10-16.md) を実装する。

- 欄: `article`（変わらない記事の名）・`article_source`（正本の所在）・`article_rev`（正本の版。repo があれば commit、無ければ本文の sha256・`article_rev_kind` で区別）・`delivery`（配信 1 件の id）・`destination`・`form`（`full`／`summary`／`entry`）・`published_id`・`published_url`。
- 既存の `article_id`（topics の記事の証拠の指紋）とは名前を分ける。意味は変えない。
- 配信先ごとの状態: 望む版・最後に確かめた版・操作中・結果不明・競合・追従不要。**外で手直しされたものを勝手に上書きしない。結果不明を失敗とみなして出し直さない**（いまの inflight の決まりを広げる）。
- `article` の無い原稿（短い観測・会話）は今のまま出せる。毎回記事を作らせない。
- `form: full` で同じ本文を 2 か所以上に出すなら、代表 URL（検索で正とする所）を配信先の表で 1 つ決める。決まっていなければ 2 か所目は断る。

### 3.2 はてなの口座と安全装置の境界（レビュー 1 の 5・レビュー 2 の 2）

- **形**: 運営者の 1 アカウントで複数のブログ（無料 3・Pro 10）を持ち、ブックマークも運営者として行う。THTH では「レーン → 配信先のブログ → 認証の主体（はてな ID）」を別の段として持ち、レーンごとに操作できるブログ id を限る。
- **今のコードとの差**: 上限は THTH の口座ごと（`thth/guard.py` の `_events` が口座の `sent/` を数える）、ロックは repo と口座ごと（`thth/server_files.py` の `account_locks`）。同じはてなの認証をレーン別の口座に入れると、止めと上限が分かれてしまう。
- **決めること（実装の前に設計の文書で）**: 止めは認証の主体の単位（1 つ止まれば、その主体のすべてのブログとブックマークが止まる）。上限はブログごとと主体ごとの両方。ロックは主体の単位。ブックマークの上限と止めは主体に 1 つ。
- **承認の対象**: ブログの配信原稿の指紋に、変換したあとの本文・依存する画像の指紋・`blog_id`・新規か更新か・対象の `entry_id`・変更前の版・題・カテゴリを入れる。**SNS の今の承認の指紋は変えない**（再承認を起こさない）。はてなの配信は新しい種類の承認として足す。

### 3.3 はてなブログ: 本文と画像の変換・公開・予約（0-4・レビュー 2 の 3）

- **本文の変換**: AtomPub は本文を「ブログに登録された記法」として解釈する（公式・10/16 確認）。配信先のブログは Markdown の記法に設定することを前提にし、THTH は公開の前にブログの記法を確かめて違えば断る。相対リンクは正本の所在から絶対 URL に、画像はフォトライフの URL に置き換える。脚注・表・埋め込みの扱いは実機で確かめて、変換の表に書く。
- **変換したあとの確かめ**: 承認の画面（`approve` の一段目）に、変換したあとの本文を見せる。公開のあと GET で読み戻し、送った本文と比べて記録する。
- **画像**: フォトライフ API（OAuth・`write_private`、公式に明記）で上げる。依存する画像の指紋を配信原稿に入れるので、画像だけ差し替えても修正として検出できる。画像だけ上がって本文が失敗したときは、上がった画像を記録して次の試みで使い回す（二重に上げない）。
- **公開と予約**: 承認した配信原稿を、THTH の queue に載せる。時刻が来たら timer が AtomPub で `draft=no` の公開を 1 回送る。**はてな側の予約（`scheduled=yes`）と、未承認の公開・下書きの送信は使わない。** 予約の変更・取り消しは THTH の予約の取り消し（`revoke`・持ち主の /activity）と止めで行い、はてなの文書に書かれていない予約の扱いに頼らない。代わりに引き受けること: 出る時刻は timer の間隔の分だけずれる。VM が止まっている間は出ない（SNS の予約と同じ条件）。
- **削除**: AtomPub の DELETE。今の `retract` と同じ二段と上限。

### 3.4 告知とブックマークを記事に結ぶ（0-2・0-3）

- SNS の告知の原稿に `article` と `form` を書けば、配信の台帳に結ばれる。告知の本文は LLM が書く（THTH は雛形を置く口だけ）。
- 記事をはてなブログに出したあとに告知を出す順は、同じ記事の公開が `published` になってから timer が出す（公開した URL を告知に差し込む）。
- **はてなブックマーク**: 追加・削除・件数・コメントの一覧。**全記事に機械で付けない。記事を選んで承認したときだけ**付ける（自分のサイトを自分のアカウントでブックマークすること自体は問題にしない、が公式の「なお」書き。機械的な高頻度は対象・10/16 確認）。1 記事に付けるのは主体の 1 口座だけ。

### 3.5 修正の検出と、差分の承認と更新（0-5・レビュー 1 の 4）

- `thth article diff <article>`: 正本の今の版と、配信先ごとの「最後に確かめた版」を比べ、本文と依存する画像の差を出す。
- 更新は差分を見せる二段の承認で、AtomPub の PUT を送る。PUT の前に GET で今の本文を読み、最後に確かめた版と違えば「外で手直しされた」として**止めて人に見せる**（上書きしない）。
- SNS の告知は書き換えない。訂正か追記を人が選ぶ（候補は出す）。

### 3.6 反応を記事へ戻す（レビュー 1 の 2・6）

- 記事ごとに束ねる: SNS の数（公開物ごと）・ブックマークの件数とコメント・クリック（`analytics_clicks`）・サイトの訪問（hub から来るものがあれば）。
- 出所（`sns`／`site`／`hatena`）・帰属の強さ（直接／条件つきの推定／不明）・集計の範囲と欠測の理由（取れなかった／0 件／まだ時点前）を分けて持つ。帰属できない流入を記事の総訪問から推して埋めない。合計や順位は hub。
- 自分のブックマークは反応に数えない。登録の成立・自分の分・第三者の分・訪問を分ける。

### 3.7 検収（完成の条件の一連に付ける）

| 場面 | 通る条件 |
|---|---|
| 別のブログへの誤送信 | レーンに許していないブログ id は承認の段でも送信の段でも断る |
| 外での手直し | PUT の前の読み戻しで気づき、止めて見せる。上書きしない |
| 通信の切断（送ったが応答が無い） | 結果不明として記録し、出し直さない。読み戻しで確かめる手順を出す |
| 画像だけ成功 | 上がった画像を記録し、次の試みで二重に上げない |
| 予約の取り消し・止め | 取り消した・止めた予約は出ない（timer が拾わない）。止めは主体の全ブログとブックマークに効く |
| 記録の前の中断 | 公開は成功し、出来事を書く前に落ちても、配信の台帳から同じ `event_id` で出来事を復元できる（§3.8） |

実機の検収は、はてなの試しのブログで行い、通ってから本番のレーンのブログに広げる。

### 3.8 出来事の記録と復元（レビュー 1 の 13・レビュー 2 の 5）

- `thth events`（3.23.0）は、出来事ごとに `event_id`・発生時刻・記録時刻・版を持ち、カーソルで読み直せる。押す通知（h2d・hub）は即時の知らせ、記録は取りこぼしの回収。
- **足すこと**: 配信の台帳を出来事の元にし、`event_id` を「配信 id と状態の変わり目」から決まる値にする。出来事を書く前に落ちても、次の run が台帳と出来事の記録を突き合わせて、足りない出来事を同じ `event_id` で書き足す。受け手は `event_id` で重複を除く。

### 3.9 約束つきの JSON と、互換を崩す整理（レビュー 1 の 11・12）

- `observe --json` は 3.23.0 で版（`schema_version`）と、既存の節の識別子（`section`）を使った `sections_by_name` を持った。hub と h2d は名前で読むよう移り済み（#2520・#2522）。
- 古い形（並び順の `sections` など）を外すのは、「新しい形を出す版の配布 → 利用者ごとの移行の確認 → 互換の試験 → 予告した撤去日」が揃ってから。非推奨の項目・代わり・撤去の予定を `observe` などに機械で読める形で出す。
- 答えの欄の名前をそろえる前に、意味・型・単位・時刻の基準・母集団・欠測の扱いを移行表に書く。過去の台帳や承認の指紋の意味は変えない。承認の指紋を変えるなら、再承認が要る原稿を先に並べ、移行で新しい指紋を自動で書いて「再承認した」ことにしない。
- **4.0 の一連（§3.1〜3.8）を先にする**。欄の名前の整理は、条件が揃ったものだけ 4.0 に入れ、揃わないものは非推奨のまま次の大きな版へ送る。

### 3.10 4.0 のあとに送るもの

- **出来事から投稿を起こす**（値段の急変を kopicha の Threads へ）: (a) 下書きまで自動・出すのは人、から始める。自動で起きるレーンには**下書きの作成・更新だけの権限**を渡す（公開・予約の確定・削除は別の権限・レビュー 1 の 8）。前承認の型（c）へ進む条件は、そのまま出せた率に加え、誤検知・取りこぼし・却下の理由・承認までの時間・鮮度切れの記録と、正常と異常の試験（レビュー 1 の 9）。`origin` は測る札で、実行の許可の根拠に使わない。
- **A. 手で出したものも測る**・**C. 届いているかの確かめ**（「見つからない＝制限」とは判定しない）・**E. 出す前の点検**・**B. 会話の受信箱**・**D. 試しを道具が回す**。
- 既存の thth.me の `send`／`schedule` が、認証された依頼をそのまま実行する 3.12.0 の設計（利用者とその LLM を疑わない・masaru 09-26）は変えない。3.21.1・3.24.0 で、CLI では `--production` が無ければ出さない・予約しない、に揃えた。新しい自動の経路には「頼めば出る」を持ち込まない。

## 5. 決めること・頼むこと（masaru）

1. **はてなの口座と OAuth の登録**: 運営者のアカウント・試しのブログ 1 つ・OAuth のアプリの登録（consumer key は `~/.config/thth/` に置く）。

## 6. 反応ゼロへの効き目の測り方（4.0 の成立とは別）

- 評価は「公開の成立 → 発見・表示 → 反応 → 記事への訪問」の 4 段に分ける。
- 仮説（masaru）: はてなブログのオーナーははてブの利用者でもあるので、はてなブログに出せばブックマークをもらいやすい。はてなブログに出した記事と、SNS の告知だけの記事とで付き方を比べる。
- **普通に配信した記事の反応を測るのと、「何件で新着・人気に載るか」を逆算する実験は分ける**。後者はしない（ガイドライン「作為的行動」は、表示アルゴリズムを検証して結果や推測を公開する行為をしないよう求める・10/16 確認）。露出を増やすために読者登録やスターを機械でばらまくこともしない。
- 「他に無い」を採る理由にしない。THTH の価値は、利用者の repo・承認・配信の記録・記事の反応を 1 つにつなげられること。
