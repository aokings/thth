## 0. 原則と、この書の結論

> 「アカウントホルダーであれば当然できる依頼を出来ないのはおかしい。依頼を受けていないのに代理者である LLM が勝手に実行出来てしまうのが問題」（masaru 2026-11-23）

柵を置く場所を「THTH を通した投稿か」から「持ち主が頼んだか」に移す。

**推し（1 つ）**: 自分の口座の投稿なら、THTH の記録が有っても無くても、どの道からでも消せるようにする。そのうえで、次の 4 つをどの道でも同じにする。

1. **自分の投稿かは、id 1 件を読んで確かめる**（直近 25 件の一覧を探すのをやめる）。媒体の DELETE が他人の物を断るのは二重目の守りにする。
2. **記録の無い投稿は必ず二段**。一段目で媒体から読んだ本文・日時・URL を見せ、確認の番号（digest）に本文の指紋を入れる。番号は一段目を通らないと作れなくなるので、MCP が中で番号を作って一回で消す今の作りは、記録の無い投稿では成り立たなくなる。
3. **頼んだ印は道ごとに 1 つ**: 手元は二段確認、thth.me と MCP は持ち主が `/activity` で発行した鍵（＝前もって任せた）＋二段。承認の頁は戻さない（3.13.0 の決定のまま）。
4. **頼まれていない削除は、数で止め・残し・見せる**: 1 日の削除の上限と急な連投の止めに数え、`retracted_outside/` に誰が・どの鍵で・なぜを残し、`/activity` に並べる。

正直に書くと、**LLM が頼まれたかどうかを機械で見分ける方法は、持ち主だけが押せる場所（`/activity`）を挟む以外に無い**。推しはそれを挟まない。理由は §2 に書き、割れる所は §9 で masaru に問う。

## 2. 「持ち主が頼んだ」を何で確かめるか（道ごと）

まず、機械にできることとできないことを分ける。

- **できる**: 消す前に対象を見せる／見せた物と消す物が同じだと番号で縛る／鍵が持ち主の発行した物かを確かめる／数で止める／残す／持ち主に見せる。
- **できない**: 手元の端末で命令を打ったのが人か LLM かを見分けること。番号は口座・id・理由から計算できる値で、秘密ではない（`thth/approval.py:363-379`）。LLM は一段目を打てば二段目も打てる。

だから「頼まれずに消す道が残らないか」への答えは、**道そのものは残る。残るのは持ち主が LLM に鍵か端末を渡した範囲の中だけで、その中での行き過ぎは数と記録と見える化で抑える**、になる。これは THTH が出した投稿の削除で 9/26 から取っている線と同じ（「疑わない、暴走は機械で止める」`thth/guard.py:1-4`）。記録の無い投稿に広げることで増える害は、「THTH が本文と原稿を持っていない、出し直せない投稿まで届く」こと。そこで記録の無い投稿にだけ、二段をサーバの側でも必ず通す。

| 道 | 頼んだ印 | 頼まれずに消す道は残るか | 抑えるもの |
|---|---|---|---|
| 手元の CLI | 二段確認（今のまま）。一段目で本文・日時・URL を出す | 残る（LLM が端末を持てば両段を打てる）。持ち主の端末で動く LLM の許可は、その LLM の側の決まりの持ち場 | 1 日の上限・連投の止め・`--by` と `--reason` の記録 |
| 遠くの道の CLI | 持ち主が `/activity` で発行した鍵＋二段。**記録の無い投稿は、サーバが番号を照らす**（今は手元で照らすだけ） | 残る（同上） | 同上＋鍵の id が記録に残る・持ち主は `/activity` で鍵を取り消せる |
| MCP（サーバ型・遠くの道） | 同じ鍵＋二段。記録の無い投稿は、`confirm` 無しで呼ぶと一段目（本文・日時・URL・番号）が返るだけで消えない | 残る。ただし一回の呼び出しでは消えなくなる | 同上。道具の説明に「持ち主が消すと言った投稿だけ。一段目の中身を持ち主に見せてから」と書く |
| 手元の MCP（鍵なし） | 出さない（今のまま） | 残らない | 柵 `test_MCPには直接取り下げの口が無い` |
| timer・自動の道 | 削除は無い | 残らない | `.delete_post(` が 1 か所の柵 |

**承認の頁を戻さない理由**: masaru は 9/26 に「不要なところに置かれた金庫なんて邪魔なだけ」と決め、選べる設定としても残さなかった（`docs/設計_3.13.0_…md` §0）。持ち主だけが押せる場所を削除に挟むと、その金庫を 1 つ戻すことになる。数（1 日 5 件）で害の大きさは今の THTH の投稿の削除と同じに収まる。ここは結果が割れるので §9 の問い 1 にした。

**記録のある投稿の MCP の一回削除は、今回は変えない**。10/15 に「MCP は今までどおり一回」と決めた線で（`thth/remote.py:927`）、THTH が出した投稿は本文が手元に残り出し直せる。そろえるかは §9 の問い 2。

## 3. 「自分の口座の投稿か」の確かめ方（媒体ごと）

直近 25 件の一覧を探すのをやめ、**id 1 件を読む口**を adapter に 1 つ足す（仮の名 `own_post(post_id)`）。返すのは本文・日時・URL・種類（投稿／ストーリーズ／再投稿）。自分の物でなければ決まった例外、読めなければ別の例外。今ある `fetch_post` は「枝の根を引く口」で、媒体ごとに持ち主の見方がばらばら（下の表）なので、流用せず、中で同じ要求を使う別の口にする。

| 媒体 | 1 件の読み | 持ち主の見方 | 媒体の DELETE | 気をつける点 |
|---|---|---|---|---|
| Threads | `GET /{id}`（`threads.py:1896`）。今は `username` を返すだけで持ち主を比べていない | 応答の `owner`（無ければ `username`）を口座の `user_id`・handle と比べる | 公式の文は「認証した利用者が作った投稿を消す」・1 日 100 件（`threads.py:736-739` の注記） | 再投稿の id に DELETE すると再投稿の取り消しになる（`threads.py:801-806`）。一段目に種類を出す。`owner` の欄が返るかは実地で確かめる |
| X | `GET /2/tweets/:id`（`x.py:977`） | `author_id` を自分の `user_id` と比べる | `DELETE /2/tweets/:id`（`x.py:487`）。X は他人の投稿を断る | 読みは有償。自分の投稿の読みは別の台帳で 1 本 0.001 USD・1 日の本数の上限には数えない（`thth/budget_x.py:333-340`）。この台帳に載せる。月の上限に当たったら消さずに断る（直し方: 月の上限を上げる・X の画面から手で） |
| Mastodon | `GET /api/v1/statuses/:id`（`mastodon.py:759`） | `account.id` を `.token` の `user_id`（`mastodon.py:275-277`）と比べる | 他人の投稿は 404（`mastodon.py:518` の注記） | 今の `fetch_post` は公開・未収載でない投稿を断る（`mastodon.py:771`）。**自分の投稿だと確かめた後なら**、フォロワー限定の投稿も本人に見せて消せるようにする（持ち主を先に見る） |
| Bluesky | `com.atproto.repo.getRecord`（`delete_post` の中で既に読んでいる・`bluesky.py:782-`） | id の形が `at://<自分の DID>/app.bsky.feed.post/<rkey>` であること（`bluesky.py:800`）。形で決まる | 自分の repo の記録だけ | 足すのは本文を一段目に出すことだけ |
| Facebook | `GET /{post_id}`（`facebook.py:1139`） | `from.id` をページの id と比べている（`facebook.py:1148`）。そのまま使う | ページの鍵は**ページに書かれた他人の投稿も消せる**ことがある | だから Facebook は媒体の断りに任せられない。読みの照らしが本線。「このアプリで作った投稿しか消せない」かは未確認 |
| Instagram | `GET /{media}`（`instagram.py:500`） | `owner.id` を口座の id と比べている（`instagram.py:509`）。そのまま使う | `DELETE /{ig-media-id}`（口の形は L3・`instagram.py:354` の注記） | ストーリーズの id で `GET /{id}` の `owner` が返るかは未確認。返らなければ、ストーリーズだけ今の `recent_stories`（24 時間の物は全部入る）で探す |

決まり:

- **読めなければ消さない**（今と同じ・`tests/test_retract_own_outside_post.py` の 3 本目）。他人の物を断る媒体でも、本文を見せられない削除はしない。X の「読みを省いて媒体の断りに任せる」は取らない。対象を取り違えたときに気づけないため。
- 25 件の定数（`OWN_POST_LOOKUP`）と、断りの文の「古い投稿には触りません」を消す。古いかどうかは理由にならない。
- 記録のある投稿（THTH が出した物）は読まない。今のまま記録の本文を見せる。

## 4. 記録・安全装置・監査

**記録の置き場**は `retracted_outside/` のままでよい。`sent/` に入れると「THTH が出したもの」（`post_ids`・board・採取）に数えられてしまう（`thth/sent.py:368-370`）。足すのは次の 3 つ。

- 遠くの道から消したときの出所（道の名と鍵の id）。`write_outside_retraction` は `origin` を受ける作りになっている（`sent.py:382-389`）ので、`direct_retract` から渡すだけ。
- 種類（投稿／ストーリーズ／再投稿）と、媒体の日時。
- `/activity` への並び。今の要約は `sent/` の記録しか見ていない（`thth/activity.py:158-166`）。`retracted_outside/` の行を「消した」の行として足す。行の形は変えない（Worker の側の検査を変えずに済ませる）。

口座を退出するときに `state/<口座>/` ごと消える中に入っているかは、直す段で `thth/leave.py` を読んで確かめる（今回は未確認）。

**安全装置の数え方**は今のまま 1 本にする。記録の無い投稿の削除も `daily_max_retracts`（既定 5）と連投の窓に 1 件として数える（`guard.py:283-287`）。別の上限は作らない。持ち主が覚える数を増やさないため。遠くの道でも同じ関数（`_guarded(…,'retract',…)`・`server_writes.py:354`）を通るので、足す作りは無い。数えるのは消した後の記録からなので、「消したのに記録を書けなかった」ときは数え漏れる。これは `sent/` の道と同じ弱さで、今回は広げない。

**監査**: この直しは `server_writes`・`mcp`・`remote`（と、たぶん `guard`）に触るので、今の表でも監査の書が要る（`tools/release_gate.py:40-80`）。ただし **DELETE の 1 か所がある `thth/retract_cli.py` が表に無い**。今日の `e96d8d7` も、`guard.py` に 5 行触ったから監査に掛かるだけで、`retract_cli.py` だけの直しなら素通りしていた。表に 1 行足す:

```
"retract": ("thth/retract_cli.py", "thth/edit_cli.py", "thth/reaction_cli.py"),
```

（`edit_cli.py` は直す・隠す・消すの口、`reaction_cli.py` は反応の取り消しで Threads の DELETE に届く。adapter の `delete_post` は大きなファイルの中なので、Facebook の `_write` と同じ理由で入れず、呼ぶ側で縛る。）

## 5. ほかの「THTH を通していない物に触らない」断り

| 断り | 場所 | 判断 | 理由 |
|---|---|---|---|
| 反応の取り消し `not_found`（X・Mastodon・Instagram） | `thth/reaction_cli.py:222-225` | **直す** | この 3 つの取り消しは「自分の、その投稿への反応を外す」口で、元の投稿の id だけで打てる（`x.py:557-573`・`mastodon.py:611-623`・`instagram.py:751-`）。他人の物には届かない。記録が無くても 1 回頼み、`reactions/` に「THTH の外で付けた反応を外した」と残す。X は 1 回 0.010 USD の目安を今と同じに出す |
| 同（Bluesky） | 同上 | **直す**（後の段） | 反応そのものの記録の uri が要る。投稿を読むと自分の反応の uri が付いてくるので、それを使う。自分の repo の中だけ |

## 6. 直す範囲と順番

版は 1 回にまとめる（11/13「release はまとめて」）。中の順番:

1. **adapter に `own_post`**（6 媒体）と、偽サーバの試験。ここだけなら本番の動きは変わらない。
2. **手元の `thth retract`**: `_find_own_post` を `own_post` の 1 件読みに替える。番号に本文の指紋を入れる（記録の無い投稿だけ・版の語を別にする）。25 件と「古い投稿」の文を消す。`:26`・`:307` の古い文を直す。
3. **サーバの口**: `direct_retract` が記録の無いとき `own_post` で確かめ、`confirm` を照らす。`retract_request` に `confirm` の欄を足す（記録のある投稿では省ける）。新しい符丁を `SAFE_ERRORS` に。
4. **遠くの道の CLI と MCP**: 一段目をサーバに訊く形にする（本文はサーバが媒体から読む）。MCP の `thth_retract_request` に `confirm`・説明の文を直す。
5. **`/activity` に並べる**・`retracted_outside/` に出所と種類。
6. **反応の取り消し**（X・Mastodon・Instagram）と、Threads・投稿の直しの断りの文。
7. **`DANGER_AREAS` に 1 行**・柵の試験・監査（Fable・1 段 2 回まで）・リリースノート。
8. Bluesky の反応の取り消しは、間に合わなければ次の版に回す。

Worker（`callback/`）は変えない見込み。変わるなら Worker が先・VM があと。

| 記録の無い投稿は一回では消えない（サーバ・MCP） | `confirm` 無し → 一段目が返り DELETE 0 回。違う番号 → 0 回。合う番号 → 1 回 | サーバの番号の照らしを外す → 赤 |
| 番号は一段目を通らないと作れない | 口座・id・理由だけから計算した番号では通らない | 番号の材料から本文の指紋を抜く → 赤 |
| 見せた後に本文が変わったら消さない | 一段目と二段目の間に偽サーバの本文を変える → 0 回 | 同上 |
| 遠くの道でも数える | 記録の無い投稿を上限まで消す → 次は `retract_limit`。連投で口座が止まる | `guard._action_rows` の `retracted_outside` の行を外す → 赤（今日の試験の 1 本目を遠くの道にも） |
| 出所が残る・`/activity` に並ぶ | 記録に道の名と鍵の id・要約に「消した」の行 | `origin` を渡さない → 赤 |
| DELETE は 1 か所のまま | 今の source の柵（`.delete_post(` が 1 回）を変えない。`own_post(` を呼ぶのも `retract_cli` の 1 か所 | `server_writes` から直接 adapter を呼ぶ → 赤 |
| 手元の MCP に口が無い | 今の柵のまま | — |
| 断りの 3 つ | 新しい符丁に なぜ・直し方・より良く | 1 つ空にする → 赤（今ある目録の柵） |
| 反応の取り消し | 記録なしで X・Mastodon・Instagram は媒体に 1 回・Threads は断りに直し方 | — |

試験は書き手を並べず、`python -m pytest -q -n 4` の終了コードを見てから進む。

## 8. 危ない点と、残る不確かさ

- **LLM が頼まれずに消す道は、鍵か端末を渡した範囲では残る**（§2）。抑えは 1 日 5 件・連投の止め・記録・`/activity`。5 件は出し直せない投稿でも 5 件で、0 にはならない。
- **Meta の DELETE を実地で確かめていない**。Instagram の投稿とストーリーズの DELETE（口の形が L3）、Facebook の「アプリが作った投稿しか消せない」かどうか、Threads の `owner` の欄、ストーリーズ 1 件の `owner`。今日の `e96d8d7` も偽サーバの試験だけで、本物の口座で消した記録は申し送り 第23 に無い。出す前に、こぴちゃの口座で「THTH の外で出した投稿 1 本」と「Threads から共有したストーリーズ 1 本」を実際に消して確かめる（masaru の一言が要る・消える物なので）。
- **Threads の再投稿の id** に DELETE すると再投稿が外れる。一段目の種類の表示で防ぐが、`media_type` が読めない応答だと「投稿」と出る。
- **X の読みは有償**（0.001 USD／本・月の上限だけ）。月の上限に当たると消せない。持ち主には X の画面という逃げ道がある。
- **Mastodon のフォロワー限定の投稿**を一段目に出す。本人の投稿を本人に見せるだけだが、`--json` の出力や LLM の文脈に乗る。採取や記録の本文に流れないこと（`retracted_outside/` には残る）を監査で見る。
- **一段目と二段目の間**に媒体の側で消えた・直された場合は、番号が合わないか `post_missing` で止まる。消えた物を「消した」とは記録しない（今と同じ）。
- **遠くの道の一段目**が今の「手元で `posts` を 50 件引いて探す」（`remote.py:963-973`）からサーバの 1 件読みに替わる。古い CLI と新しいサーバの組み合わせでは、記録の無い投稿は `confirm_required` で止まるだけで、消えはしない（安全な側）。
- `retracted_outside/` に本文を残す。退出で消えるかは未確認（§4）。

## 9. masaru への問い

**問い 1**: thth.me と MCP の道でも、記録の無い自分の投稿を「鍵を発行したこと＝前もって任せた」として、その場で（二段で）消せるようにしてよいですか。

- 推し: **よい**。承認の頁は戻さない。害は 1 日 5 件までで、`/activity` に並び、鍵は取り消せる。
- 代わりの案: 記録の無い投稿だけは、`/activity` で持ち主が押すまで消さない。「頼まれていない削除」は確実に無くなるが、3.13.0 で消した金庫を 1 つ戻すことになり、Worker の直しと監査が増える。
- 前提が変わると: 外の利用者が増え、古い投稿を LLM に消された事故が 1 件でも出たら、代わりの案に寄せる。そのときは手元の道にも同じ押す場所が要るかを一緒に決める。

**問い 2**: THTH が出した投稿（記録のある投稿）の MCP の削除は、今の「一回の呼び出しで消える」のままでよいですか。

- 推し: **今回は変えない**。10/15 の決定の線で、本文が手元に残り出し直せる。
- 代わりの案: 記録のある投稿も二段にそろえる（一段目を返してから消す）。道ごとの差は無くなるが、今 MCP で消している LLM の手数が 1 回増える。
