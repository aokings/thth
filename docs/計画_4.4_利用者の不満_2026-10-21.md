## 決めたこと

- **⑤ の記録の置き場**（masaru 10/21「推しでよし」・本線 第5 経由 #3732）: **VM の台帳に持ち、利用者の repo には積まない**。repo から見えなくなる分は、必要なら THTH から書き出す口で補う。出したら各窓口に「確定が main に積まれなくなった」と知らせる。伺ったときの書き方: 推しは「承認の記録を VM の台帳（state）に持ち、利用者の repo には積まない」。代わりの案は「別の枝（`thth/records`）に積む」。前者は repo に記録が残らない（今は repo の commit が承認の証拠の 1 つ）、後者は枝が 1 本増え、利用者の repo の設定（保護・push 先）に触る。契約（利用者の repo に何を書くか）が変わるので、作る前に伺う。
- **承認のほかに repo に積むもの**（masaru 10/21 夜「推しでおk」・THTH開発 第7 の会話）: 投稿の書き戻し（status: posted）・はてなの公開・incident・新しい返信の収集は、**4.4.1 では今のまま利用者の repo に書く**。台帳（VM）に移すかは **4.4.2（手元と VM の食い違い）でまとめて決める**。4.4.1 は 10/21 21:59 に出した。

## 4.4.3 の伺い（THTH開発 第9・2026-10-23・本線へ要返事）

2 つ決めたい。番号は版を 4.5.x で数える（本番が 4.5.1 のため）。

1. **`--approval A…` で hub の verify と close まで THTH がするか。** 推し: **THTH は hub を呼ばない。** VM に hub は無く（10/23 `ssh wt 'command -v hub'` で無し）、THTH は PyPI で外の人も使う道具なので、masaru の hub に依存させない（THTH と hub の線引き 10/15）。代わりに THTH は材料を出す: `thth approve --digest-only`／`--json` で hub の `--target` に渡す digest を出し、複数のファイルを 1 つの digest にまとめる。verify と close を一続きにするのは hub の側（hub が `thth approve` を包む）に頼む。
   - 前提が変わったら: VM に hub が入る、または hub が HTTP の口を持つなら、THTH から呼ぶ案は安くなる。代償は THTH の外の利用者に無意味な引数が 1 つ増えること。
2. **はてなブックマークにも gate の番号を求めるか。** 推し: **CLI の `--production` だけ、口座の台帳の `require_gate: true` に従わせる**（X などと同じ決まりにそろえる）。thth.me の `bookmark_request`・`bookmark_batch_request` は Web の口なので求めない。求めるかどうかは口座ごとに窓口が決める（既定は求めない）。

この 2 つと、`revoke` の複数と `--account` を 1 つの版にする。

## 版の出し方

各版とも、書き手（Opus・worktree）→ 手元の全件 → 柵を壊して赤 → main → CI → `hub approve ask` → 承認で release と tag。
