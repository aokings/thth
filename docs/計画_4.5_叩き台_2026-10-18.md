## 0. 一言で

**4.5 は「4.0 で張った糸（記事 → ブログ・告知・ブックマーク → 反応）を、レーンが毎日回しても手が増えない版」にする。** 新しい媒体も新しい画面も足さない。足すのは、(1) 媒体の断りや観測が台帳に戻る周回、(2) 調査メモの型を 1 日分まとめて回す口の仕上げ、(3) 評価の報告を THTH の口だけで書ける材料、(4) 4.0〜4.2 で積んだ残りの始末。

**完成の条件の案**（masaru が決める）:

1. 両レーンの「調査メモ」の 1 日分（候補 → 札 → まとめて承認 → 時刻を散らして付く → 後からタグやコメントを直す）が、THTH の口だけで回り、masaru の手は 1 日分に「はい」1 回。
2. 媒体の観測（断り・切られたタグ・人間か確認・反応の無さ）が、人の手を介さず `thth media observations` に集まり、開発のセッションが台帳を直した周回が**本物で 1 回以上**回っている（観測 → 台帳の項目の `evidence`／`confidence` の修正 → 断りの文に根拠が出る）。
3. 10/27〜28 の評価と、その後の週の評価が、`thth article reactions`・`thth observe --json`・`thth media observations` の出力だけで書ける（合計と順位は hub）。
4. 上限の台帳の旧名が「非推奨」の段まで進み（`doctor` が警告・`migrate-limits` がある）、4.1.x／4.2.x に回した指摘と全体の監査の低 3 つが閉じている。
5. はてなの実機の「残り」のうち、運用で自然に出るものが記録に埋まっている（本物の SNS への告知・結果不明のブックマーク・第三者のブックマーク・24h の自分の分）。

4.0 と同じく、「読者が増えた」はリリースの条件にしない。

## 3. 4.5 の柱

### 3.1 柱 1: 見立てに学び返し（観測 → 台帳を人が直す周回）

**何が困っているか**

- 設計 §9 は B（観測は機械が集め、台帳は人が直す）を選び、段 4 で `observations.ndjson` と `thth media observations`／`observe` が入った。しかし**周回はまだ 1 度も回っていない**。集めるのは命令を打ったときだけで、timer が集めない。`no_reaction` は人が足す種類で、S6 の反応の採取（1h・6h・24h の刻み）から機械では出ない。
- 観測が台帳に戻らなかった実例: X の 403 `x_not_permitted`（10/14）は返事の文書に残っただけ（設計 §9.1 の C の難）。フォトライフの初回 403（見つけたこと 16・10/17）は記録に残っただけで台帳に無い。タグの長さ（kopicha 10/18）は台帳に「観測・確かさ low」で入ったが、**公式のヘルプには「約全角 10 文字（32 バイト）まで」と書いてある**（https://b.hatena.ne.jp/help/entry/tag ・10/18 に開いて確かめた）。観測（31 は通る・34 は切れる）と矛盾しない（文字の境で 32 バイト以下に切る）。つまり「観測 → 公式の文書で裏が取れた → `official_doc`・high に直す」という周回の最初の 1 件が、もう目の前にある。
- 評価（§2 E2）は「媒体に断られた回数」を見たいが、今は打たないと集まらないので、評価の日に初めて打つと、10/18〜27 の runs から拾い直すことになる（拾える作りではある。runs の行を鍵にするので取りこぼしはない・段 4 の監査 低-1）。

**選択肢と推し**

| 案 | 形 | 利 | 難 |
|---|---|---|---|
| A | 今のまま（打ったときだけ集める・`no_reaction` は人） | 変更なし | 周回が回らない。評価の日にまとめて拾う |
| B（推し） | **`thth run` の末尾で軽く集める**（その口座の runs の新しい行だけ・HTTP は打たない）＋ **`no_reaction` を S6 の採取から機械で出す**（公開から 7 日の刻みで others 0・スター 0・告知の表示が 10 未満、を 1 行）＋ **台帳を直す候補を文書の形で出す** `thth media traits propose <媒体>`（観測から「この項目の `confidence` を上げる／`notes` に足す／台帳に無い符丁」の差分を Markdown で出す。commit は人） | 周回が回る。数は動かさない（§9.3 のまま） | run が少し重くなる（読むだけ・新しい行だけなので小さい）。`no_reaction` の線（7 日・表示 10）は推測 |
| C | 自動で数を動かす | 手が要らない | §9.3 のとおり採らない |

**入れないもの**: 自動で数字を動かすこと・確率と学習（§5.4）・媒体のスパム判定を THTH が推し量って本文を採点すること・観測を hub に押すこと（hub は `observe --json` で読める形に 1 行足すだけ）。

**見積もり**: 段 3 つ（run の末尾の集め／`no_reaction` の機械化／`propose`）。書き手の日 1〜2。最初の周回（タグの長さを `official_doc` に直す・`TAG_MAX_BYTES` を 32 にするか）は段の前に手で 1 回やって、周回の形を文書に残す。

**何を測れば効いたと言えるか**: (a) 台帳の項目のうち `evidence` が観測から公式へ、または `confidence` が動いた項目の数（4.5 の間に 1 以上）。(b) 断りの文が「台帳に無い符丁」を出す回数（30 日で 0 に近づく）。(c) 評価の日に、媒体の断りの表を**打たずに**読めた（E2）。

### 3.2 柱 2: 記事ごとの手応えを一枚に（材料と口だけ）

**何が困っているか**

- S6 で `thth article reactions <口座|project> --article <記事>` と morning の「昨日」の記事ごとの数は入った。しかし**記事を 1 本ずつ名指しする口しか無い**。評価は「両レーンの全記事」を並べて見るので、記事ごとに打って貼る作業になる（推測。E1 で確かめる）。
- 告知の行は本物の SNS に出てから（rehearsal は `sent/` に書かない）。10/27 の kopicha の告知が最初。
- 「訪問」（サイトへの流入）は hub の側で、THTH は持たない（計画 4.0 §2）。評価の 4 段の最後は hub が足す。
- 調査メモの型では、**単位が記事でなくケース（タグ）**になりつつある（「タグで寄せれば記事になる」・記事より先に札がたまる）。THTH の反応の単位は配信（記事）とブックマーク 1 件で、ケースのタグで束ねる口が無い。

**選択肢と推し**

| 案 | 形 | 利 | 難 |
|---|---|---|---|
| A（推し） | **読む口を 2 つ足すだけ**: `thth article reactions <口座|project> --all [--since 14d] --json`（記事の一覧・出所と窓つき・足さない）と、`thth bookmark list <口座> --tag <タグ> [--json]`（そのタグの札の数・付いた日・結果・第三者のブクマ数）。`observe --json` の `yesterday.articles` の形はそのまま。hub には「この 2 つを読む」と頼む | 線引きを守る（合計と順位は hub）。評価の材料が 2 命令で揃う | 「一枚」には見えない（hub の画面が一枚） |
| B | THTH に記事・ケースの一枚の表（morning に節を足す） | THTH だけで読める | morning が重くなる。hub と二重 |
| C | 何も足さず hub が `data/hatena/reactions/` を直接読む | 変更なし | レーンの repo の台帳を hub が読む線が増える・形の約束が無い |

**入れないもの**: ダッシュボード・媒体をまたいだ合計や順位・サイトの訪問の推定・「反応から次の記事の種」（S6 §7.2・後の版）。

**見積もり**: 段 1〜2。書き手の日 0.5〜1。E1 で足りなかった欄があれば、その欄を加える分だけ増える。

**何を測れば効いたと言えるか**: 次の週の評価が `--all --json` と `--tag` の出力から書けた（手で台帳を読んだ欄が 0）。hub が読み始めた（snsobs に鍵が増えた）。

### 3.3 柱 3: 調査メモの型を道具に（候補 → 札 → まとめて承認 → 直し）

**何が困っているか**

- kopicha は候補の一覧（2,578 行）と 1 日分の切り出し（50 件・同じホスト 5・ケースのタグ付きを先に）を**自前の Node のスクリプト**で持ち、THTH には札の JSON Lines だけを渡す。関東はこれから一覧を作る（母集団 1,610 本・載せる／載せないの決め・優先度 4 段）。型の「そろえる部分」は hub の文書、タグの語はレーンごと。**THTH が持つべき所と、レーンが持つべき所の線がまだ引かれていない**。
- 10/18 にタグの旧名 3 件を `bookmark edit` で直した。ケースの名を変える（事件 → ケース、捜査 → 調査）と、その名を持つ札を全部直すことになる。はてなのヘルプ（https://b.hatena.ne.jp/help/entry/tag ・10/18 確認）では、タグの一括の置換と削除は **PC のブラウザの画面だけ**（タグ編集・一度に 1 つ）で、REST API にはタグの名前を変える口が無い（https://developer.hatena.ne.jp/ja/documents/bookmark/apis/rest ・10/18 確認: タグ API は `GET /rest/1/my/tags` だけ）。THTH でやるなら札 1 件ずつの POST（既にあれば更新）になる。
- 札の中身の約束（タグ 5 種がそろっているか・「台帳」などの内部の語・コメントの字数・署名）は、今は kopicha のスクリプトが見張る。関東は別に作ることになる。
- 日の上限に当たると、後ろの**直しの札**（日の枠を使わない）も翌日に回る（S4 §23 低-3・4.2.x に回した）。

**選択肢と推し**

| 何 | THTH が持つ（推し） | レーンが持つ | 理由 |
|---|---|---|---|
| 候補の一覧（台帳の原典の抜き出し・載せる／載せない） | 持たない | 持つ | 台帳の形がレーンごとに違う（kopicha は claims.csv・関東は disclosure JSON）。THTH は原典の意味を知らない |
| 1 日分の切り出し（上限の中で・同じホスト・優先の順） | **`thth bookmark batch --plan`**: 札のファイル（何百行でもよい）を渡すと、口座と主体の今の枠・同じホスト・`bookmark_once`・タグの長さを当てて「今日出せる N 件・残り・断る理由」を**書かずに**出し、`--take` で今日の分の札のファイルを書き出す | 優先の順（ケース → それ以外）は札の並びで表す | 枠の計算は THTH にしか無い（段 1〜4 の表）。今は 1 段目の `_forecast` が内側で同じ計算をしているので、外に出すだけ |
| 札の中身の約束 | **口座の `bookmark.tag_vocab`**（任意・レーンの repo のファイルを指す: 許すタグの語・必須の組・禁じる語）。lint と 1 段目で**予告**（断らない）。無ければ今のまま | 語の表そのもの | 型は hub のもの。THTH は「持ち主が置いた表に照らす」だけ。断らないのは、利用者を疑わない線 |
| タグの一括の直し | **`thth bookmark retag <口座> --from <旧> --to <新>`**: `sent/bm:` から旧のタグを持つ自分の札を集め、1 段目に件数と一覧、2 段目で `op: edit` の札としてまとめの順番待ちに置く（連投の窓の中で散らす）。件数が多い（例 30 超・推測）ときは 1 段目で「はてなの画面のタグ編集なら 1 回」と案内する | 画面で直すか THTH で直すかの選び | API に置換が無い。THTH で直すと 1 件ずつの POST で、はてなの「機械的な高頻度」の線の中（更新は `bookmark.burst` に数え、日の枠には数えない・4.2 の決め） |
