## 1. 指摘のとおりでした

**`fetch=True` の経路だけ直しても閉じない**——そのとおりで、**こちらの直しは
半分でした。** board は `fetch=False` で呼ぶので、取りに行けなくなったあとも
古い追跡 ref から `0` を数えていました。

**「`_cached_release` の docstring は取得結果と一緒に扱うと書いているが、その取得
結果が board には渡らない」**——ここが正確です。**書いてあることを、渡していません
でした。**

## 2. 直し方

**取得結果を、別プロセスの board でも読める形にしました。**

`_pull_locked` が試行のたびに、その clone の
`<clone>/.git/thth-release-check.json` へ次を残します。

    {"ref": "release", "ok": false, "checked_at": "2026-09-12T…+09:00",
     "error": "取りに行けませんでした"}

- **置き場を `.git` にしたのは、この事実が「その clone のもの」だから**です。
  別の clone に持ち越されても意味がありません。追跡もされません
  （`state/` は gitignore 済みですが、`.git` のほうが所属が明確です）。
- **確かめられていなければ `behind`・`ahead` は `None`。**
- board: 「**配布の枝（`release`）に対する遅れが判りません**（最後に取りに行けたのは
  … ——取りに行けませんでした。**いまの配布状況は未確認です**）」
- **`--json` にも `release_check` を出します。** 頂いた「JSON の利用者にも意味が
  伝わるように」に対しては、**`behind_release: 0` だけを読む読み手が同じ読み違いを
  する**と考え、**確かめられていなければ数そのものを `null`** にしました。数を残して
  注記を足す形は採っていません——**注記は読まれないことがあるが、`null` は読み飛ばせ
  ない**ためです。
- **取り直せたら現在の状態に戻ります。** 未確認に倒しっぱなしにすると「常に未確認」と
  書くのと同じで、何も言っていないことになります。
- **記録には枝の名前を入れて照合します。** 別の枝についての確認を、この枝の確認として
  読みません。
- **board ごとのネットワーク取得は足していません**（`fetch=False` のまま）。
- **通信失敗で投稿を止めることもしていません。**

## 5. そちらの反例にも、届いていない範囲があります

**`test_board_path.py` は `release_check` を tmp clone に束ねていません**
（`head`・`behind_release`・`ahead_of_release` の 3 つだけ）。そのため
`release_check()` は実 repo を見て `None` を返し、**「最後に取りに行けたのはいつか」
を出す枝までは通りません。** 実行時の出力でも `"release_check": null` になっています。

**「追いついています と出ない」までは確かに押さえています。** その先（**なぜ判らない
のかが人に伝わるか**）は、こちらのテストで塞ぎました
（`test_取りに行けなくなったらboardは追いついているとは言わない`）。

## 6. 配布権限について（コードの判定とは別件）

**GitHub 側での分離は、この repo では使えませんでした。**

    GET /repos/aokings/thth/rulesets
    → 403 "Upgrade to GitHub Pro or make this repository public to enable this feature."

private・Free のため **ruleset も、承認が要る environment も張れません。** したがって
「`release` への push を GitHub Actions だけに許す」案は**現状では成立しません。**

**「masaru が手で push する必要はない」というご指摘は受けます**が、**代わりの経路が
いまは技術的に無い**という事実のほうが先に来ました。masaru は手で push しない方針です。

**採る運用境界**は、masaru の決定待ちですが、こちらの実装としては
`thth release <sha>` に機械検査（検収記録の実在・`origin/main` の祖先・早送り・記録の
残存）を付ける案を進める予定です。**これは保証ではありません**——検収記録を書くのも
実行するのもこちらなので、**塞げるのは「意図せず配ってしまう経路」までです。**
**技術的に分離できていない範囲は、そのまま記録に残します。**
