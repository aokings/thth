2. 【読】**(b) は、正常な repo を誤って止める道は見つからなかった。**
   - 空の repo（HEAD が無い）・unborn HEAD: `_confirm_synced` の手前の `rev-parse HEAD`／`@{u}` の確かめで先に断られ、`history_damage` まで来ない。
   - 浅い clone（`--depth`）: `rev-list --count HEAD` は graft／shallow を尊重して数えるので通る【読】。
   - 部分 clone（blob:none）: `--count` は commit しか見ないので、欠けた blob で止まることはない。blob や木の欠けは捕まえない（投稿に要るのは commit の履歴だけなので範囲として狭いが妥当）。部分 clone の promisor remote から欠けた commit が取り直される可能性は、本物では見ていない【未】。

   - stderr への `print` は `file=sys.stderr` で、stdout の JSON は壊さない【読】。

3. 【読】**性能。** `history_damage` は同期の最後に毎回 1 度 `rev-list --count HEAD` を打つ。commit-graph があれば commit 数に対してほぼ一定、無ければ全 commit を開く。記事と台帳の repo なら小さいが、この線に載る repo が大きく育つと、1 回の投稿あたりの費用が増える。毎回でなく間隔を空ける作りにはなっていない。直すほどではない。

4. 【読】**断りの文の秘密・パス。** 断りの末尾の git の stderr は `redact_mod.redact` を通している。`redact` は秘密の形（`access_token=`・`Authorization:`・登録された値）だけを伏せ、パスは伏せない。git の欠けのエラーは通常 `bad object <sha>`・`unable to read <sha>`・`exists in commit-graph but not in the object database` のような sha 入りの文で、絶対パスは出にくい。ただし `.git` 配下のファイルの権限のエラーなどではパスが出うる。stderr の注意の行（graph が古いとき）は `os.path.abspath(repo_dir)` を出す。ユーザーの端末・ログに出るもので、外へ出る JSON ではない。
