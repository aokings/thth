## 2. 項目ごと（実装・試験・変異）

### F1 — 決着した承認 session が preview を失効させる（`dee098b`）

**実装。** `ApprovalSession.clear()`（承認・期限切れ・受領の 3 経路）が、attachments を落とす直前に `attachments[].preview` を控えます（`collect()`）。実際の失効は storage transaction の外で `settle()` が行い、capability id から `/m/` と同じ導出（`getByName(sha256(id))`）で media object の `invalidate` を呼びます。404/410 も RPC の例外も握り潰します——preview は表示だけのもので、承認の結末を変えてはいけません。session の alarm も、行を消す前に同じ控えを取ります。

併せて `create` が各 preview の寿命を session の `expires_at` まで引き下げます（`MediaObject.boundExpiry`。**縮めるだけで延ばせない**。`cleanup_at` も同じ値に下げるので R2 の bytes の削除も早まります）。isolate が消えて `invalidate` が届かなくても、grant 自身の期限が session を越えません（durable な後詰め）。

**試験**（`callback/test/approval.test.mjs`。実 media object・実 R2・実 preview grant で）:

1. `consuming an approval revokes every preview the page showed` — 受領後に `/m/<preview>` が即 410。
2. `an expired approval page revokes its previews before its own clock kills them` — **session の時計だけ**を進める（grant は自分の時計ではまだ生きている）→ 410 は失効の RPC 以外から来ない。
3. `approval still completes when one preview object is already gone` — preview の 1 本が既に消えていても承認は 200 で通り、残りの 1 本は失効する。
4. `a preview never outlives the approval session that shows it` — session の期限が grant より早い場合に grant の `expires_at` / `cleanup_at` が session の値まで下がる。

**変異。** (a) `clear()` の `collect(row)` を削る → 1・2・3 の 3 本が落ちる。(b) `create` の `boundExpiry` の輪を削る → 4 が落ちる。どちらも 29 本中の該当分だけが落ちました。

### F2 — 承認ページの正直さ（`2d34dec`）

**実装。** (a) ページの GET が画像 preview を 1 本ずつ media object に尋ねます（`MediaObject.live()` ＝ `view` と同じ関門から bytes を除いたもの）。1 本でも生きていなければ**承認フォームを出さず**、`<p>添付を表示できないため、この承認ページは使えません。サーバから新しく承認を求めてください。</p>` だけを出します（状態は **200**・本文と digest は読める）。binding が無い・RPC が投げた、も「出せない」に数えます。図の説明には `画像が表示されない場合は承認しないでください` を添えます。

(b) `<img>` に `loading="lazy"` を足しました。`/m/…` は公開ページと同じ送信元ごと毎分 120 の枠なので、**20 枚のページを 1 分に 7 回以上読み直すと 429**（120 ÷ 20 ＝ 6 回まで）。`docs/運用_承認relay_2.12.md` に書きました。**preview 専用の枠は作っていません**——`/m/…` の制限は DO を呼ぶ前に効かせており（試験 `media rate rejection precedes signing, body, DO and R2`）、purpose は DO の中にしか無いので、区別しようとすると制限の目的そのものが崩れます。

**試験**（同）: `a preview that stopped serving removes the approve form and says so`（生きている → `<form` あり／失効 → `<form` 無し・`name="secret"` 無し・文言あり・digest は残る・状態 200）、`an image whose preview never existed cannot be approved from the page`（存在しない capability でも同じ・画像 preview が 1 本も無いページは不変）。既存の `approval page renders images…` と `attachment alt and typed JSON are escaped like the body` に `loading="lazy"` と図説の文言を入れました。

**変異。** (a) `d.live===true` を `true` に固定 → 2 本が落ちる。(b) `loading="lazy"` と図説の文言を消す → 既存の 2 本が落ちる。

### F3 — 送る前に断る（`ccf664f`）

**実装。** alt の上限を 1 本にしました（`thth/media.py` の `MAX_ALT_BYTES = 2000`。原稿の `validate` と招待者の口 `media_uploads.draft_rows` が同じ定数を見る）。超えたら静的な `media: alt_too_long`。Worker は 1 行 4096 文字まで受けますが、20 行ぶんは承認 `create` の body に入りません。

`approval_jobs._attachments` が**upload も grant も始める前に**組み上がる `create` の body を測ります。行数 > 20 なら `approval_attachments_too_many`、body > 90 KiB（Worker の 96 KiB から余白）なら `approval_request_too_large`。どちらも job は definite な `failed`（`unknown` ではない）。capability は 43 文字なので、placeholder で測った byte 数は実際に送る byte 数と一致します。代表画像と字幕も 1 行として数えます（F10）。

session `create` が Worker の **4xx** で断られたときは `failed` ／ `approval_registration_rejected`。5xx・通信断・応答の型違いは従来どおり `unknown` ／ `approval_registration_unknown`。

**試験**（`tests/test_v213_stage810_audit.py`）: alt 2000/2001 byte・多 byte・代表画像の alt／21 行で upload 0 回・20 行は通る／body 90 KiB 超で upload 0 回・`remote.rows == {}`・手前の body は送られて byte 数が下見と一致／400・409・429・500・通信断の 5 通り。

**変異。** alt の検査を削る → alt の 1 本が落ちる。行数の検査を削る → 21 行の 1 本。body の検査を削る → 90 KiB の 1 本。`rejected` を `False` に固定 → 4xx の 3 param が落ちる。

**限界。** `approval_attachments_too_many` は、Threads の原稿経路では **lint がもっと手前で 21 枚を断る**ので通常は届きません（`threads_media.intent_error`）。転送の backstop なので `_attachments` 自身に対する試験にしてあります（`prepare` を差し替え、relay が呼ばれたら落ちる）。

### F4 — `admin media gc` を 1 つの取引にする（`f25238d`）

**実装。** `git add -- <path>` は**追跡されていないパスが 1 本混じると呼び出し全体を断ります**。これまでの gc は先に全部 unlink してから commit を頼んでいたので、書きかけの残骸が 1 つあるだけで「追跡ファイルは working tree から消えたのに commit は無い」状態になりました。

`git ls-files -z -- <paths>` で追跡・未追跡を先に分け、**追跡ぶんだけを 1 つの commit にし、未追跡の残骸はその commit の後で unlink** します。commit ができなかったら `git checkout -- <paths>` で working tree を戻し、`media_gc_unconfirmed` を**件数つきで返します**（例外にして件数を全部 None にしません）。

**試験**（`tests/test_v213_media_upload.py`）: `test_gc_commits_tracked_files_and_unlinks_an_untracked_leftover`（未追跡 1 ＋ 追跡 2 → 3 つとも消え、commit は 1 つ、`git status` clean）、`test_a_failed_gc_commit_restores_every_tracked_file`（commit 失敗 → 2 つとも戻り `restored_count` が 2・working tree は clean）。

**変異。** `thth/media_uploads.py` を直す前に戻す → 2 本とも落ちる（1 本目は実際に `ValueError: media_gc_unconfirmed` を出し、追跡 2 本が消えたままになることを示します）。

### F5 — 4 MiB を超える原稿も読む（`455ed74`）

`_referenced` が大きさで飛ばすのをやめ、1 MiB ずつの有界ループ＋末尾 128 byte の継ぎで走査します（読み境界を跨いだ名前も拾う）。走査は bytes のままなので decode できないファイルからも ASCII の名前を拾います。試験: 5 MiB の原稿が添付の名前を 1 MiB 境界を跨ぐ位置に持つ → gc はその添付を残す（直す前は消す）。

### F6 — 読み戻しの大きさは VM の控えが正本（`f2940be`）

`source_snapshot(subject, sha256, size)` に VM の控え（`record['size']`）を渡し、Worker の `status` がそれと違ったら**1 byte も読まずに** `media_source_mismatch`。署名付きの read も出さず、temp file も作らず、`ack` もしない（source は retire されない）。試験: 偽の Worker が size±1 を宣言 → `control` は `status` の 1 回だけ・`TemporaryFile` は 1 つも作られない（spy）。

### F7 — 置き去りの lock と壊れた控え（`2178257`）

`media-uploads/` の `*.lock` を gc が片付けます。**先に自分で flock を取り**（動いている session のものは触らない）、24 時間の backstop より古いものだけを unlink します（session の寿命は 10 分）。mode が 600 でない lock は触らず飛ばします。読めない・形が壊れた intent は**数えて報告し（`corrupt_count`）、消しません**。`admin media gc` の出力に `locks=` と `corrupt=`、JSON に `locks_removed` / `corrupt_count` / `restored_count` を足しました。

### 試験の揺れ — upload IP 枠（`97ca1dd`）

`real upload IP quota rejects request121 …` は実 Miniflare の枠に 121 回 dispatch していました。枠は**実時刻に固定された窓**なので、CPU が混むと 121 回が 60 秒境界を跨ぎ、121 回目が通ります（試験したい振る舞いとは無関係な理由で落ちる）。設定値（120/60）を runtime の options から読み直し、**試験が持つ時計**の固定窓で数える偽の limiter に対して数えます。「次の窓は空から始まる」まで確かめられるようになりました。実 binding が刺さっていることは、窓に依らない 1 回の実 dispatch で見ます。

## 4. 決めたこと

1. **`live()` は `view` の関門から bytes を除いたもの**にしました（別の判定基準を作らない）。R2 の `get` はしないので、ページの GET が preview の本数ぶん R2 を読むことはありません。
2. **binding が無いときは「出せない」に数えます。** 画像 preview を持つ session を、`MEDIA_OBJECT` の無い Worker が出すことはできません（承認ページの `approve/` は媒体の binding が無くても 503 にしない既存の作りを保ったうえで、画像がある session だけをフォーム無しにします）。
3. **preview 専用のレート枠は作りませんでした**（§F2(b) の理由）。`loading="lazy"` ＋ 文書化が今の答えです。
4. **`invalidate` は preview にしか効きません。** provider の grant は `published` / `invalidate` の署名付き手順を持っており、承認 session が触ってよいものではありません。
5. **壊れた intent は消さない。** 数えて人に見せます（消すと証拠ごと消える）。
6. gc の失敗は例外でなく**件数つきの `reason`** にしました。`admin media gc` の exit code（`reason` があれば 2）は変わりません。

## 5. 限界（この worktree では確かめていないこと）

1. 実 Worker・実 R2 での `live()` の往復時間。20 枚のページは preview の本数ぶん RPC が直列に走ります（Miniflare では 1 本あたり 1 ms 未満ですが、本番の DO は別の isolate です）。**配布担当の実測対象**です。
2. 20 枚のページの実 CDN 下での `loading="lazy"` の効き（どの画像が実際に取得されるかは閲覧環境次第）。
3. 429 に当たったときの実際の体験（1 分待って読み直す）の実機確認。
4. `git checkout -- <paths>` による復元は、**commit までは進んで push で失敗した**場合には効きません（その場合は commit がローカルに残り、`media_gc_unconfirmed` ＋ `restored_count: 0` が返ります）。これは直す前と同じ振る舞いで、手で直す前提です。
5. F6 の `media_source_mismatch` は**偽の Worker**でしか通していません（実 Worker は正しい size を返すため）。
