# 設計 4.5.0 X の全期間の検索（2026-10-21）

## 0. 目的と使う人

X の他人の公開投稿を、全期間（2006 年 3 月から）から読む口を足す。

使う人は MMR（音楽の頁のサイト）。アーティスト本人の公式アカウントの過去の投稿を曲名で絞って読み、頁の出典（本人の言葉）にする。**読むだけ**で、投稿・いいね・返信はしない。規模は 1 曲 20 本 × 約 350 曲＝7,000 本ほど。

## 1. 一次資料（2026-10-21 に読んだもの）

- 検索の案内 <https://docs.x.com/x-api/posts/search/introduction>: 全期間の検索は従量の契約と Enterprise で使える。1 回 500 本まで・語は 1,024 字まで（Enterprise は 4,096）・2006 年 3 月から。
- `GET /2/tweets/search/all` <https://docs.x.com/x-api/posts/search-all-posts>: `max_results` は 10〜500（既定 10）。`start_time`／`end_time`（`since_id`／`until_id` とはどちらか一方）。`next_token`（`pagination_token` とはどちらか一方）。`sort_order` は recency／relevancy。応答の `meta` は `result_count`・`next_token`・`newest_id`・`oldest_id`。
- `GET /2/tweets/counts/all` <https://docs.x.com/x-api/posts/get-count-of-all-posts>: `granularity` は minute／hour／day（既定 hour）。応答は `data[].start`・`end`・`post_count` と `meta.total_post_count`・`next_token`。
- 件数の案内 <https://docs.x.com/x-api/posts/counts/introduction>: **31 日ごとに 1 ページ**（day でも hour でも 31 日分）。
- 料金表 <https://docs.x.com/x-api/getting-started/pricing>: Posts: Read は**返った 1 本** 0.005 USD。Counts: All は **1 回** 0.010 USD。同じ UTC の日の同じ投稿は 2 回目に課金しない、ただし「soft guarantee」。

資料に書かれていないこと（実機で未確認）: `start_time` を渡さないときの窓（古い資料では直近 30 日）・件数の口のページの並び（新しい順か古い順か）・rate limit の数（古い資料では 1 秒に 1 回）。THTH は `start_time` を必ず渡し（既定 2006-03-21T00:00:01Z）、ページの間を 1.1 秒空ける。

## 2. 口の形

```
thth archive <口座> --from <handle> --title <曲名> [--max-total 20] [--per-call 10] [--max-pages 5]
             [--since YYYY-MM-DD] [--until YYYY-MM-DD] [--sort recency|relevancy] [--include-retweets] [--json]
thth archive <口座> --query '<語>' …
thth archive <口座> --from <handle> --title <曲名> --count-only [--max-pages 1] [--granularity day|hour] …
```

- `--from` と `--title` から `from:<handle> "<曲名>" -is:retweet` を組み立てる（`thth/x_archive.py` の `build_query`）。handle は `@` を外して英数と `_` の 15 字まで。曲名の中の引用符（`"`・`“`・`”`・`＂` など）は空白にする——X の検索には引用符の中で引用符を逃がす書き方が無く、残すと句が切れて別の語になるため。制御文字は断る。引用符だけの曲名は空になるので断る。
- 返す行（`--json` の `posts`）: `post_id`・`url`（`https://x.com/<handle>/status/<id>`）・`created_at`・`text`（長文は `note_tweet` の全文）・`author_username`・`conversation_id`。MMR は `url` を出典に使う。
- **返すだけで保存しない**。runs には件数だけ（語も本文も書かない）。

## 3. 規律（今の検索と同じ）

- **予約は要求の前、確定は応答の後。** 1 ページごとに `budget_x.archive_read(口座, 本数)` で押さえ、発射し、応答に入っていた本数で確定する。
- **課金は返った本数。** 10 本を頼んで 7 本返れば 7 本（0.035 USD）。0 本なら 0。
- **結果が不明なら投げ直さない。** 応答が読めなければ押さえた本数のまま `uncertain`（多めに数える側）。2 ページ目より後で断られた・不明になったときは、それまでの行を返して止まる（`stopped`）。1 ページ目なら断りをそのまま返す。
- **同じ日の 2 回目は無料、には頼らない。** 料金表は「soft guarantee」と書くので、THTH は返った本数を毎回数える。
- **1 回の本数**は 10〜100（既定 10）。一次資料は 500 まで頼めるが、台帳の 1 回の上限（100）に合わせて小さくした。
- **総本数**は 10〜500（既定 20＝曲 1 つ分）。ページは `min(1 回の本数, 残り)` 本ずつ頼み、**残りが 10 本未満になったら辿らない**（X は 10 本未満を頼めないので、頼めば上限を超えて課金されうる）。だから課金は総本数を超えない。
- **ページ**は 1〜50（既定 5）。空のページに `next_token` が付いて続くことがあるため（空のページは課金 0 だが要求は数える）。
- 範囲外の指定は**要求も予約もせずに** rc=2 `x_archive_limit`。CLI と adapter の両方で見る。
- X が `max_results` より多く返したときは、台帳が実費より少なく数えうる（仕様違反の時だけ・1 ページ最大 2 USD）。辿るのは実数で止まる。
- 予算の断り（`budget_exhausted`・`x_archive_daily_read_cap`）も要求の前。

## 4. 件数の口（`--count-only`）

- `GET /2/tweets/counts/all`・1 回 0.010 USD（`budget_x.request_read(COUNTS_ALL)`・別の台帳 `budget_x_counts_all.json`）。月の上限は他の台帳と分け合い、1 日の本数には数えない（trends・counts と同じ）。
- **31 日ごとに 1 ページ**なので、窓を数えきるのに要るページ数は要求の前に分かる。`--max-pages`（1〜300・既定 1）より多く要る窓は、**要求の前に**断り、要るページ数と推定 USD を言う。
- 叩くのは `min(--max-pages, 要るページ数)` 回まで（CLI の見積もりを adapter に渡す）。X が窓の外まで `next_token` を返し続けても、見積もりより多くは叩かない。
- **注意（使い方）**: 2006 年からの全期間を数えると約 245 ページ＝約 2.45 USD／曲。曲ごとに「0 件なら読まない」を件数の口でやると、350 曲で約 860 USD になり、読むより高い。**全期間を見るなら、`--max-total 10` の検索を 1 回打つほうが安い**（当たりが 0 本なら 0 USD、当たっても 10 本＝0.05 USD まで）。件数の口は、年や月に窓を絞って「どの時期に多いか」を見るときに使う（1 年なら 12 ページ＝0.12 USD）。

## 5. 予算（1 日の本数を別に持つ）

今の決まり: 他人の投稿の読み取り（`where`・`thread`・`list show`）は口座ごとに JST の 1 日 `x_daily_reads` 本（既定 60・最大 10,000）。7,000 本はこれを超える。`x_daily_reads` を上げると、人に返す出向きの検索の柵まで緩む。

そこで**材料集めの枠を別に持つ**:

- 全期間の検索は別の台帳 `state/_admin/budget_x_archive_reads.json`（形は他人の投稿の台帳と同じ・単価 0.005 USD・版 `2026-10-21-posts-read-archive`）に数える。
- 1 日の本数は口座の台帳の **`x_archive_daily_reads`**（X の口座だけ・**既定 0＝読まない**・最大 10,000）。`thth account set` の項目に足した（MCP からは締める向きだけ）。
- 全期間の読みは `x_daily_reads` に数えず、`x_daily_reads` は緩めない。
- 月の上限（`thth admin budget x --monthly`）は、本人確認・他人の投稿・自分の投稿の数字・リスト・コミュニティ・トレンド・件数と分け合う。`thth admin budget x --json` に `archive_read`（本数・推定 USD・口座ごとの今日の本数）と `counts_all_read` が出る。

### 7,000 本を読むために親が打つ命令（この版では打っていない）

7,000 本 × 0.005 USD＝35 USD。今月の使用に足して余裕を見る。例（VM・口座名は MMR が使う X の口座に置き換える）:

```
env THTH_ROOT=/srv/thth /srv/thth/app/bin/thth admin budget x --json        # 今月の使用と上限を見る
env THTH_ROOT=/srv/thth /srv/thth/app/bin/thth admin budget x --monthly <今の上限＋40> --by masaru
env THTH_ROOT=/srv/thth /srv/thth/app/bin/thth account set <口座> x_archive_daily_reads 7000 --by masaru
```

1 日で読みきらないなら、`x_archive_daily_reads` を小さく（例 1,000＝5 USD／日）して数日に分けるほうが、間違えたときの損が小さい。

上限は UTC の月ごとに戻る。月をまたいで読むときは、月の初めに上限を元に戻すか、残りの額に合わせて置き直す。7,000 本は 1 日 1,000 本に分けるのが推し。

## 6. 人の居ない道からは叩かない

- `cli._main` は、先頭の語が `run`・`collect`・`maintain`・`morning`・`observe`・`worker`・`map`・`hatena` の命令の間、`x_archive.unattended()` の印を立てる（process 全体の数・thread をまたいでも効く）。`collect.collect_once` も中身の前に印を立てる（worker などが Python から呼ぶ道）。
- 印が立っている間、`XAdapter.archive_search`・`archive_counts` と `thth archive` は**要求も予約もせずに** `x_archive_unattended` で断る。
- 2 つの口は `CAPABILITIES` に載せない。`where`・`map`・`morning` は capability で口を拾うので、そもそも呼ばない。
- 柵の試験: `tests/test_v450_x_full_archive.py`（§8）。

## 7. MCP には出さない

4.5.0 では MCP の道具にしない。理由: 全期間の検索はページを辿るので 1 回の命令の費用が大きく（最大 500 本＝2.5 USD）、LLM の繰り返しの呼び出しで積み上がりやすい。MMR の使い方は CLI（`ssh wt` で `thth archive … --json`）で足りる。出すときは同じ規律（予算・上限・人の居ない道）を CLI に任せる形（`run_cli`）で足す。

## 9. 確かめていないこと

本物の X では叩いていない（従量の契約で全期間の検索が通るか・利用者のトークンで通るか・件数のページの並び・rate limit）。初めの 1 回は `--max-total 10` で打って、返った行と `x_read_cost` を見るのがよい。
