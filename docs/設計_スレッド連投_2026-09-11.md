### 区切り

**裸の `---` は使わない**（本文の区切りと衝突する・Codex 指摘）。
`<!-- thth: N/M -->` は**独立行の予約構文**とする。番号・総数が不正なもの、
空の段は**拒否する**（Codex 最終条件 5）。**段の数と `posts:` の件数が
食い違うのも不正**（第 2 稿の例がまさにそれだった——3 段なのに `posts` が 2 件）。



- markdown の preview に出ない（masaru が読むとき邪魔にならない）
- **番号を自分で持つ**ので、連番と総数を機械が検査できる
- 本文に自然には現れない

**番号は自動で振らない。** 本文に `1/3` と書きたければ書き手が書く。
THTH は本文を**整形も切り詰めもしない**という既存の約束を崩さないため。
書かれている番号と区切りの番号が食い違えば lint で断る。

## 2. 親子の対応記録（Codex 指示の 1 点目）

### 2.1 何に固定するか

**「ファイル」ではなく「この束の、この版の、この実行の、この段」。**

公開のたびに、その段の記録を front matter に書き戻す:

```yaml
posts:
  - index: 1
    post_id: "18016228439944497"
    posted_at: 2026-09-15T19:00:12+09:00
    reply_to:
    run_id: run-20260915T190000-7f3a      # 公開要求より前に発行
    bundle_sha: 4525e124…                 # 公開した時点の承認版
  - index: 2
    post_id:
    posted_at:
    reply_to:
```

**同じ内容が `state/threads/<run_id>.json` にも永続化される。**
原稿だけを書き換えても、そちらと一致しなければ親にならない（§2.1.1）。

**`run_id` は最初の公開要求より前に発行して永続化する**（Codex 最終条件 1）。

第 2 稿では「1 段目の `post_id` を実行 ID にする」と書いたが**採らない**——
**1 段目の公開結果が不明になった場合、ID がまだ無く、`inflight` や進行状態を
作れない。** 結果不明はいちばん守りたい場面なので、そこで使えない識別子は
使えない。

| 名前 | いつ決まるか |
|---|---|
| `run_id` | **公開要求より前**に発行して state に永続化 |
| `root_post_id` | 1 段目の**公開成功後**に記録 |

各段の公開記録に残すもの:
**`run_id` / `index` / `account` / 承認版 / 本文の指紋 / 実際の返信先 / `post_id`**

### 2.1.1 git と公開記録は別物

> **Git で同期済みであることと、THTH が実際に公開した記録であることは別です。**

親 ID は、**同期した原稿と、永続化した公開記録の両方を照合して**決める。
記録が欠ける・食い違う場合は**止める。**

**原稿に整合した ID 一式を書くだけでは、親を差し替えられない。**
（原稿は利用者 repo にあり、人が書き換えられる。公開記録は THTH が
自分で書いた事実。**両方が揃って初めて親が決まる。**）

### 2.2 2 段目の親をどう決めるか

承認が意味しているのは:

> **この承認済みの束の 1 段目として公開された投稿に返信する**

公開時に照合するもの（**全部一致しなければ出さない**）:

1. **過去の公開内容が、新しい承認版の固定済み部分と一致する**
   （Codex 最終条件 2。第 2 稿の「過去の `bundle_sha` が現在の `approved_sha` と
   全部一致」から変更——続きを直すと `approved_sha` は変わるが、
   **公開済み部分は凍結されているので一致する**）
2. これから出す段より前の全段に、**永続化した公開記録**があり `post_id` を持つ
3. その記録がすべて**同じ `run_id`** → 別の実行で出した投稿を拾わない
4. **原稿の記録と永続化した公開記録が一致する**（§2.1.1）
5. 原稿側の記録が**同期済みの commit に入っている**（`matches_synced_commit`）
6. `account` が一致

**解決した `post_id` を、送信の前に `reply_to` として書き戻す。**
「何に返信したか」が記録に残る（あとから照合できる）。

### 2.3 同じ内容を再投稿した場合

撤回して**最初から別スレッドとして**出し直すと `approved_sha` は同じになりうる。
**それでも `run_id` が違う**ので、前の実行の記録は条件 3 で弾かれる。
古い記録は**消さずに履歴として残す**（何が起きたかを消さない）。

## 3. 途中停止と再開（Codex 指示の 2 点目）

### 3.1 判断は「どこまで出たか」ではなく「何が確定しているか」

| 停止時点 | 次の動作 |
|---|---|
| N 段目が公開・記録・同期済み、N+1 は未着手 | **承認・撤回・同期・`continue_until` を再検査して続行できる** |
| N 段目の公開結果が不明（timeout・応答不明） | **自動で再送しない。後続も止める。** 人が Threads を見て判断する |
| N 段目は公開成功、書き戻しか push が失敗 | **公開済みとして保持し、後続を止める。再公開しない** |
| 束の内容変更・撤回・同期失敗 | 続行しない |

**3 行目が既存の `inflight` と同じ形。** いまは 1 投稿ぶんしか守っていないので、
`(account, run_id, index)` まで持つ形に広げる。

### 3.2 継続期限

`continue_until` を front matter に置き、**`approved_sha` に含める**。

**「翌日になって突然 3/4 が出る」を防ぐ。** 期限を過ぎたら残りは出さず、
board に「未完のスレッド（期限切れ）」として出す。**出し直すなら
再承認**（続きだけを承認する形は §5）。

### 3.3 段ごとにロックを取り直す

**束の 4 本を 1 つのロックの中で出さない。** Codex の指摘どおり、
それだと「1 本目のあとで止める」が働かない（`revoke` は同じ clone ロックを取る）。

```
段ごとに:
  ロックを取る → 同期 → 撤回と承認を再検査 → 公開 → 書き戻し → push → ロックを放す
```

**その隙間に `revoke` が入れる。** これが狙い。

**state に「進行中」と書くだけでは排他にならない**（Codex 最終条件 3）。

- **実行の取得・再開・段の進行は、すべてロックの中で判定して永続状態を更新する。**
- 次の段では**必ず同期し**、同じ束の状態・承認・撤回を読み直す。
- **30 秒待機中に期限を越えることがあるので、実際の公開要求の直前にも
  現在時刻で期限を検査する。**
- **未解決の公開結果がある間は、同じ account の別投稿へ進まない。**
- **初版は、同じ account の公開主体を 1 台に限定する。** 別 clone からの
  編集・撤回は許すが、**複数ホストでの同時公開は保証範囲に入れない。**

## 4. 撤回の効力が発生する時点（Codex 指示の 3 点目）

### 4.1 約束の文面

> **停止を確認した後は、新しい公開要求を送らない。
> 既に送信済みの要求は取り消せない。**

これ以上は約束できない。**別 clone への撤回 push だけで、実行中の要求まで
即座に止まるとは保証できない。**

### 4.2 2 つの状態を分ける

| 状態 | 意味 | どこに記録するか |
|---|---|---|
| **停止要求済み** | `revoke` が front matter に `revoked_at` を書いて push した | 原稿（利用者 repo） |
| **実行側が停止確認済み** | 公開側が次の段の前にそれを読み、止めることを決めた | `state/threads/<run_id>.json` と `runs` |

**`revoke` が返すのは前者まで。** 「止まりました」と言わない——
**第 6 巡 P1-2「止められなかった投稿を、止められたと利用者に伝える」**と
同じ誤りになる。

`revoke` の出力案:

```
停止を要求しました。
  公開を確認できた段: 1, 2
  要求中（結果が未確定）の段: 3
  未着手の段: 4
実行側がこれを読んだ時点で、新しい公開要求を送らなくなります。
**すでに送信済みの要求は取り消せません。** 出てしまったものは
Threads の画面から手で消してください。
```

**「次の確認点は約 10 分後」とは書かない**（Codex 最終条件 3）——束は同じ起動の
中で進むので固定ではない。**「3 段目以降は未公開」とも断定しない**——
確認できた段・要求中の段・未着手の段を**分けて**出す。

### 4.3 出た段は残す

API 上、公開済みの投稿は THTH から取り消せない。
**記録も消さない**（`posts[].post_id` はそのまま）。
未公開の続きへの承認だけを取り消す。

## 5. 内容を直したいとき（確定・Codex 最終条件 2）

**続きの修正は「同じ実行の、新しい承認版」。**

第 2 稿の「続きを直して出し直すなら新しい `run_id`」は**撤回する**——
**続きなのに新しい実行にすると、既に公開した親との対応が崩れる。**

| | 扱い |
|---|---|
| 公開済み部分の本文・順序・返信関係 | **凍結。** 警告ではなく、**承認時と公開時の両方で拒否する** |
| 未公開部分・`continue_until` | 変更してよい。**ただし再承認する** |
| 再承認の対象 | **固定した公開済み部分の記録と、変更後の残りをまとめて** |
| 過去の公開記録の `bundle_sha` | **書き換えない。** 各記録は**当時の承認版**に結び付く |
| 新しい `run_id` にするとき | **最初から別スレッドとして再投稿するときだけ** |

**凍結は強制する**（Codex 最終条件 4）。誤字修正でも公開履歴を書き換えない。

## 6. 間隔と上限

**1 回の起動で束を順次処理する。** ただし `max_per_run` を 4 にはしない。
Codex の指示どおり **2 つを分ける**:

| 設定 | 意味 |
|---|---|
| `max_bundles_per_run` | 1 回の起動で**開始できる束の数**。既定 **1** |
| `max_posts_per_run` | 1 回の起動で**実際に API へ送る投稿数**の上限。既定 **4** |

**初版の束は 2〜4 段。再開分も投稿数に数える**（Codex 最終条件 4）。

各投稿の間に §3.3 の確認点を置く。**確認点を飛ばして速く出さない。**

30 秒待機は今回**変えない**（公開失敗の分類に効く・Codex 指摘）。

## 8. 形の語彙（「使いこなせる」を初版から入れる）

Codex の指摘を受けて**第 1 稿の方針を撤回する。**

> 「使いこなせる」は、実測待ちにすると満たせません。
> テンプレートは**書くための補助**であり、成果の保証ではありません。

第 1 稿では「語彙と記録は先、助言の中身は実測が溜まってから」と書いたが、
**それでは使いこなせるようにならない。** 実測が要るのは
**「形式ごとの成果に基づく推薦」だけ**で、判断材料は初版から渡せる。

### 8.1 軸を 2 つに分ける

第 1 稿の語彙は軸が混ざっていた（「列挙」「問い→答え」は**構成**、
「誘導」は**目的**・Codex 指摘）。

| `form`（構成） | `outlet`（最後の導線） |
|---|---|
| 単発 | 記事へ |
| 列挙 | 別投稿へ |
| 問い→答え | 無し |
| 手順 | |

**別々に記録すると比較できる**（「問い→答え × 記事へ」と
「列挙 × 記事へ」を並べられる）。

### 8.2 初版から LLM へ渡す判断材料

**実測ゼロでも渡せるもの。**

- **単発で十分な内容を、無理に分割しない。**
- 比較や段階的な説明には、連投を候補にする。
- **先頭だけでも、何の話で何が得られるか分かるようにする。**
- **続きを読ませるために、根拠や重要な留保を最後まで隠さない。**
- 各段の役割と、最後の導線を説明する。
- **「この形式で成果が出るかは未検証」と明示する。**

手順書（`docs/手順_LLM_トピック選定.md` に並ぶ形）に置く。

### 8.3 `form` は承認対象か

Codex の区別をそのまま採る:

| 種類 | 承認対象か |
|---|---|
| 分割・順序・番号・**送信本文を変える**指定 | **承認対象**（`approved_sha` に入る） |
| 既にある本文を**分類するだけ**のラベル | 公開承認とは**別**。ただし**実測に使った版を記録する** |

`form` / `outlet` は後者。**ラベルを変えても公開される内容は変わらない。**
**`--advise` への影響だけでは承認対象にしない**（Codex 最終条件 4）。

**ラベルの履歴は、時刻だけでなく当時の値と分類の版を保存する**（同）:

```json
{"at": "2026-09-15T18:00:00+09:00", "form": "問い→答え",
 "outlet": "記事へ", "vocabulary_version": "2026-09-11.1"}
```

## 9. 計測（やってはいけないことを先に書く）

- **投稿単位のまま保持し、束へ紐付ける。**
- **全段の views を足して「到達人数」と呼ばない**（同じ人が複数段を見る）。
- **最終段 ÷ 先頭段を「読了率」と呼ばない**（views の定義がそれを支えない）。

  Threads API から返ってこない）。

## 10. トピック提案も束全体を読む（Codex 指摘）

**見落としていた。**

> 先頭に topic、最終段に記事 URL を置くなら、**先頭だけを検査しても
> 記事との適合は判断できません。**

いまの `topic_advice.build_context()` は `queuefile.extract_section()` で
**1 つの節**を取っている。`thth: 2` では:

- **承認指紋もトピック提案の入力も、単なる本文連結ではなく
  「段の境界と順序を保持した配列」**（Codex 最終条件 5）
- URL の抽出（`extract_urls`）は全段から
- `evidence.post_text` は段ごとに分かれた形

**承認画面には、各段の全文と返信関係を明示する**（同）。

**`thth: 2` の原稿を単発として扱わない検査**を、公開側だけでなく
**トピック提案側にも置く。**

7. 手順書と語彙（§8）
8. 計測の紐付け（§9）

**完成範囲は 1〜8 すべて**（Codex 最終条件 6）。
**手順書・語彙・計測の紐付けも初版の納品に含める。**
成果データがゼロでも構わないが、**指南を後回しにしない。**

## 12. 検収で再現すること（Codex 指定）

- **1 段目の公開結果不明**・各段の**公開成功直後の中断**・**push 失敗**で
  再公開しない
- **同じ内容の別実行の記録**や、**差し替えた親 ID** を使えない
- **別 clone からの撤回・本文変更・期限変更**が、次の公開判断に反映される
- **同時起動でも同じ段を二重公開しない**
- **続きの再承認**で公開済み部分が変わらず、未公開部分だけ続行する
- **既存 v1 の承認・公開が維持**され、**旧コードは v2 を拒否する**
- **LLM がテンプレートから束を作り**、全段を使ったトピック判断・承認・
  偽 API での公開・計測表示まで通せる

**本番導入前に、実装を独立レビューする。**
