# サーバ側の停止と退出（管理者）

masaru が `thth account leave <account> --by masaru` を実行します。HTTPS/MCP に退出操作はありません。進行中の対象通信が終わるまで待ち、ローカルの停止を永続化してから、承認 Worker と媒体側の権限を失効させます。同じ本人の別 account は停止しません。

Mastodon と X は運営者が保存した client と対象 account の専用 token で失効を要求します。失効が確認できなければ、停止状態と再試行用 token を残し、同じコマンドの再実行を求めます。通信失敗時に、遠隔側で何も起きなかったとは判断しません。

Threads の接続解除と Bluesky の App Password 削除は本人の設定で確認してください。表示は **local 完了／remote 未確認** を分けます。他 account と共有している接続の場合は、先に運用者が解除対象を切り分けます。共有の App Password や接続をそのまま解除すると、別 account に影響することがあります。

削除対象は、対象 account の専用 token・env・台帳・state と、`repos/_server/<account>` の管理原稿です。共有ファイル、全体の app client・署名鍵、外部の利用者 repo、変更ログは残します。所有関係やファイルの実体を確認できない場合は停止状態のまま拒否します。同じ account 名を再利用して停止記録を回避することはできません。

token/env の自動削除を許す配置は、対象の `state/<account>/` 内、`$THTH_ROOT/secrets/<account>[.<suffix>]` の直下ファイル、または従来の `~/.config/thth/<account>.token`・`<account>.env` です。`A2`・`A-other` は `A` の専用名ではなく、`A.foo` という別 account がある場合もその名前を含むファイルは `A` の所有物とみなしません。これ以外の配置は停止済み・leave 未完了として拒否します。自動で移設せず、管理者が所有関係を切り分けてください。全体の app/env・apps・署名鍵が対象の state や管理 repo に入っている場合も、その木は削除しません。

削除は中断しても同じ停止 journal から再開します。削除後に変更ログや journal の永続化が失敗した場合は、成功扱いせず再実行してください。`thth admin account <account>` と `thth admin log --account <account>` で停止状態・削除カテゴリと件数を確認できます。通常利用者からは停止 account を除外し、同じ資格情報の別 account は利用できます。

## 媒体からの削除要求

`/data-deletion` は signed request を短期の受付番号として保存します。この時点は **受付（未照合）** で、account の特定や削除の完了を意味しません。

管理者が `thth admin deletion sync --by masaru` を実行すると、VM 内の app secret で署名を検証し、Threads の保存済み本人 ID と一意に一致した要求だけを `deletion_requested` として記録します。本文・署名・app secret は表示やログに出しません。鍵を読めない、本人不明、複数 account に一致する要求は未照合のまま保持します。読取済みの app secret で HMAC 不一致を確認した偽署名だけは、署名付き管理口で blob を回収し、受付枠を解放します。この回収は account と結び付けず、退出や削除完了にはしません。公開 status は見つからない応答となり、元の期限まで再試行照合用の SHA と期限だけを保持します。sync の件数は照合済み・未照合・HMAC 不一致の回収を分け、本文や署名を記録しません。

その後、管理者が対象の `account leave` を実行します。永続化された退出記録ができてから Worker に完了を伝えます。`/data-deletion-status?code=<受付番号>` は未照合／照合済み／完了を区別し、完了時刻には VM の退出記録時刻を返します。Worker への完了通知だけが失敗した場合も、同じ leave を再実行します。

受付の論理期限は 30 日です。照合後に signed blob を稼働中の DO から除去し、期限切れの受付は読めません。Cloudflare SQLite DO の PITR による復元可能期間までの物理消去は保証しません。実媒体の削除 callback と失効応答の確認は、ローカルの fake 通信試験とは別に必要です。

受付の同時保持上限は 1000 件です。定期的に sync して偽署名を回収する必要があり、sync が動かない場合や到着量が処理量を超える場合の受付枠枯渇を解決したものではありません。入力形式の検査だけを署名の検証とは扱いません。

通常の認可・token set・refresh は媒体検証から保存まで、account add/force/migrate と app client 保存は保存区間で、認証情報の共有ロックを取り、媒体失効は同じ場所の排他ロック内で共有関係を読み直します。別 account の更新が先に確定して共有 grant になった場合は失効を拒否し、失効が先の場合は別 account の保存が応答まで待ちます。人の入力待ちをこの共有ロックに入れず、媒体通信中に全体の管理ログ flock は保持しません。同一 OS ユーザーが直接ファイルを書き換える競合まで防ぐ保証ではありません。

2.10 の「dry-run／読む口はロックを取らない」は、追加裁定で account/repo の実行ロックを取らない意味に限定しました。既存の account/repo の実行ロックは引き続き取りませんが、停止と競合しないため、対象通信の応答を読み終えるまで、および最小 runs 記録の間は専用の停止調整 lease を取ります。`state/_leave/<account>.lock` は本文や SNS 台帳を持たない空の mode 600 ファイルです。停止処理が先に進んだ場合は、後から古い処理が state を再作成することを防ぎます。これは承認・投稿・SNS 台帳更新を dry-run に追加するものではありません。

読む側の停止調整は `LOCK_SH | LOCK_NB` です。通信・最小 runs だけでなく、account を対象とするローカル CLI／HTTP／MCP の report 計算も共有 lease の中で行います。退出の排他 lease が先に取られていれば待たずに `account_leaving` で断り、CLI は rc 2（JSON は `cannot_say: ["account_leaving"]`）、HTTP は 503、MCP は同じ理由のエラーを返します。退出側だけが既存の読取を drain するまで待ちます。完了済み退出を恒久的に「退出中」とはせず、user scope からの除外と管理者の履歴読取は従来どおりです。資格が元から許可したが停止で除外された account の区別は内部診断にだけ使い、権限や公開応答へ追加しません。

## 停止理由と権限の点検

`run` は正規の停止を `account_stopped`、停止記録を安全に読めない場合を `account_stop_state_unreadable` と区別します。追記が安全でない場合は runs を作らず、1 行 JSON の `runs_recorded: false` と `record_unavailable` に静的理由を出して exit 2 で終わります。投稿・運用通知・死活成功通知は行いません。board は既存の記録と現在の停止理由を表示し、未保存の run 履歴は推測しません。

`thth doctor <account> --json` は state／repos／accounts の mode を読み取りだけで調べ、書込可能な共有権限を `unsafe_directory_mode` と表示します。775 なら管理者が対象ディレクトリを確認して `chmod 755 <対象ディレクトリ>` で直します（自動変更しません）。
