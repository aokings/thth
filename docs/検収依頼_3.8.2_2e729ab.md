## 件 1 `58c50d1` 同期で FETCH_HEAD に依らない（P1）

- 直し（`thth/writeback.py`）:
  - `_confirm_synced()`: `fetch origin` → **`merge --ff-only @{u}`**（従前は `pull --ff-only`）。ff できないとき（枝分かれ・作業ツリーの衝突）は従前どおり断る。断りの文は「git merge --ff-only @{u} に失敗しました（upstream に早送りで追いつけません）: …」。その後の `HEAD == @{u}` の確かめは従前どおり。
  - `commit_and_push()` の再試行: `fetch origin` → **`rebase --autostash @{u}`**（従前は `pull --rebase --autostash`）。index の控えと戻し（`save_index`・`restore_index`）は従前どおり。
- 本物の git での再現: 一時の bare と clone。「別のプロセスの fetch」は git の前に挟んだ包み（`GIT_EXEC_PATH` と `PATH` の先頭に置いた `git`）で作った——**どの fetch の直後にも、別の fetch が `--append` で FETCH_HEAD に for-merge の行を足す**。`git pull` が中で呼ぶ fetch もこの包みを通るので、従前の形は実測と同じ「fatal: Cannot fast-forward to multiple branches.」で断られ（単変異で確認）、直した形は通る。足す行は 2 通り（別の枝を名指し・同じ upstream がもう一度＝並んで走った `fetch origin` 2 本が書き込みを重ねた形）で、どちらでも従前の形は断られた。

## 判断が要る点

1. **ロック無しで fetch する読み手（`behind_remote()`）をどうするか。** 件 1 で FETCH_HEAD の競合は同期に効かなくなったが、ロックの中の同期と同時に走ると ref の書き込みがぶつかり、同期側の fetch が失敗して承認が「git fetch に失敗しました」で断られる形は残る（起きたことは未確認）。案: (a) このまま、(b) `behind_remote()` も repo のロックを待たずに取りに行き、取れなければ fetch せず「いま確かめられない」と言う、(c) 読み手の fetch に `--no-write-fetch-head` だけ足す（ref の衝突は残る）。
2. **push に失敗したときの次の一手。** 手元に push していない承認の commit があると、次の `thth approve` は同期（`HEAD == @{u}` の確かめ）で断るので、thth の命令だけでは先へ進めない。いまは `git -C <repo> push` をそのまま打てる形で出している（従前の 1 本ずつの承認も「手で push」と言うだけ）。VM で生の git を打たせずに済ませるなら、承認の commit だけを push し直す口が別に要る。
