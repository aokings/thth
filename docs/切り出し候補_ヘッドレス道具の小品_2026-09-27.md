## 2. 小品 1: 鍵つきの郵便受け（pull-based request relay）＋ ブラウザ式の login

### 2.1 約束
「外から入る口の無いサーバに、鍵で認証した依頼を届ける。サーバが取りに来て行い、結果を返す。郵便受けは中身を読まず、記録もしない。」

これは THTH に限らない。家の中の機械・会社の中の VM・ラズパイ——**inbound を開けたくないが、外の CLI や LLM から使いたい**ものすべてに要る。healthchecks.io が「ping が来ないことを知らせる」1 行で立っているように、これは「口を開けずに依頼を届ける」1 行で立つ。

### 2.2 いまの仕様（3.14.0〜3.14.3 の現物）
- **依頼**: `POST https://<host>/api/v1/<operation>`（`Authorization: Bearer <鍵>`・JSON body `{"account", ...}`・48 KB）。Worker は鍵の sha256 を `Person` DO の表で照らし（口座と期限）、鍵ごと 60 回/分・IP 120 回/分で制限し、`Account` DO に `request:<id>` を置き（120 秒・口座ごと 8 件）、**応答を最長 20 秒保留**（0.5 秒ごとに見る）。結果が入れば 200 でそのまま返す。超えたら 202 `{status: pending, request_id}` → `GET /api/v1/result/<id>`（10 分で消える）。
- **取りに来る側**: サーバの常駐が署名つき sync（`/relay/v/activity/<person>/sync`・RSA-PSS・canonical は第 1 版 §2.2）で依頼を受け取り、その鍵の資格で実行し、結果を次の sync で押し上げる。待ちがあれば 2 秒・無ければ 10 秒。冪等（`request_id`・`state/<口座>/requests/<id>.json`）。**権威はサーバ**（鍵をもう一度確かめる）。
- **鍵**: 発行はサーバ側の資格（sha256・scope・期限 365 日・actor）。Worker は表（hash・口座・期限）だけを sync で受け取る。発行し直しで前の鍵は無効。取り消しは持ち主の画面から。
- **ブラウザ式の login**（`/login/<code>`）: CLI が code（8 字）と poll_token（43 字）を作り `POST /api/v1/login/start`。ブラウザで持ち主が口座名と secret を入れて「この機械に鍵を渡す」→ Worker が鍵を発行（rotate と同じ・hash をサーバへ）→ `Login` DO に 1 度だけ置く → CLI が `GET /api/v1/login/poll/<code>`（poll_token）で受け取り 0600 に保存。鍵は画面に出ない。10 分で消える。口座の様子が届くまでページが自分で待つ（3.14.3）。
- **CLI 側**（`thth/remote.py`）: 25 秒・202 なら 1 秒おきに最長 90 秒・401 は `invalid_key`/`key_expired`・429 は `Retry-After` で 1 回・網の失敗は `remote_unavailable`。鍵は読んだ直後に伏せ字に登録。**手元の道と遠くの道で命令・引数・`--json` を同じにし、判定は 1 か所**（`remote.route`）。

### 2.3 切り出すときの境界
- Worker（`api.js`・`login.js`・`person-object.js` の `Person`/`Account`/`Login`・`relay.js`）は operation の名前を見ない。**利用側は operation 名の集合と body の上限を設定で渡す**だけ。
- サーバ側の常駐（`thth/api_requests.py`・`activity.py` の sync）は「依頼を受け取り・関数を呼び・結果を返す」骨だけを library に。関数の表（operation → callable）は利用側。
- CLI 側（`remote.py`）は `call(operation, **args)`・`login()`・`logout()` の 3 つ。
- **利用側の最小 API**: Worker を deploy → サーバで `relay-key init`（署名鍵）→ 常駐に `handlers={...}` を渡す → CLI で `login`。

### 2.4 磨くべき箇所（今日までに見えたもの）
- 依頼の中身の暗号化（今は Worker が平文で最長 120 秒持つ・記録はしない）。E2E にするなら鍵の交換が要る。
- 複数の機械（口座に鍵 1 つ → 2 台目で login すると 1 台目が切れる）。
- `via` の区別（CLI か MCP か）。

## 5. 小品 4: 安全装置と停止スイッチ（承認ページの代わりに残った守り）

### 5.1 約束
「持ち主が決めた数値を機械が守る。超えたら断り、急なら止め、止まったら知らせる。戻すのは持ち主だけ。」

### 5.2 いまの仕様（3.12.0〜）
- 数値（口座ごと・持ち主が決める）: 最短間隔（返信には掛けない）・1 日の公開の上限・1 日の削除の上限・急な連投（10 分に N 件で**口座を止める**）・夜間・取り消しの猶予。数え方は口座の記録から（`guard.summary`）。止めた印は `state/<口座>/guard/stopped.json`（理由・時刻）。
- **LLM から変えられるのは締める向きだけ**（`thth_settings`）。緩める・止めたのを戻す・鍵の発行し直しは持ち主の画面（`/activity`・口座の secret）。
- 持ち主の画面 `/activity`: サーバが 10 秒ごとに押し上げる要約（出た・消した・予約・止まった理由・今日の数・鍵の期限）を 1 時間だけ持つ。操作（止める・戻す・予約の取り消し・設定・鍵）は secret で確かめ、サーバが取りに来て行う。閲覧は記録しない。
- 断りは符丁＋次の一手（`too_soon`＋`next_at`・`daily_limit`・`retract_limit`・`account_stopped`＋理由）。

### 5.3 切り出すときの境界
- `guard.py` は「記録から数える関数」と「数値の表」だけを受け取る library に（記録の形は利用側が `events()` で渡す）。
- `/activity` は小品 1 の Worker に同居（`Person` DO）。要約の形（`validSummary`）と操作の集合（`ACTION_KINDS`）を利用側の設定に。

## 6. 小品 5〜7: Python の小さな package

第 1 版 §5 のまま（版の口・append-only の変更ログ・秘密の土台）。足す:
- **符丁を丸めない**（3.14.3 の教訓）: 内側の断り（`inflight`・`repo_broken`・`unsafe_owned_directory`）を外側が `invalid_draft`・`request_failed`・`leave_incomplete` に丸めると、使う側は何も分からない。「安全な符丁の集合」は**足す**方向で管理し、理由（`reason`）と次の一手を通す。
- **umask は入口で**（運営者の CLI が ssh から打たれると 0002 で来る）。

## 7. 小品 8: LLM エージェントのための healthchecks → **media-hub の「脈」に合流**

第 1 版 §6 で「将来」としていたものは、media-hub 側が **`hub pulse`** として先に作った（media-hub の `/Volumes/NexDev/Developer/media-hub/docs/設計_hubの脈_healthchecks卒業_2026-09-27.md`・9/27）。形: 見張られる仕事が終わるたびに VM の hub へ脈を 1 行置く（`hub pulse <名前> [--fail] [--note]`）→ `media.yaml` の `pulses:` に持ち主が「何時間おきに来るはずか」を書く（hub は推定しない）→ 毎朝「失敗を言ってきた 🔴／止まっている 🔴／遅れている 🟡／期待に無い脈 ⚪」を朝の 5 行に出す。**HTTP の受け口を VM に開けない**（VM の中は直に打つ・外は ssh）。Healthchecks.io からの卒業。

## 8. ヘッドレス道具の作法（第 2 版・`AI協業の作法.md` と並べる 1 枚）

1. **厚い CLI・薄い MCP・skills が包む。** 新しい機能は「CLI の命令として何か」を先に決める。MCP の道具はその写し、skill はその案内。Web の画面は「見る・止める・鍵」に留める。
2. **金庫を置かない。** 取り返しのつかない一手は、承認の関所ではなく、持ち主が決めた数値の安全装置と停止スイッチで守る。LLM から変えられるのは締める向きだけ。
3. **秘密は LLM の文脈を通らない。** 鍵は `login` で手元に置き、命令だけが使う。画面に出すのは 1 度だけ。残すのは hash と verifier だけ。
4. **外から入る口を開けない。** 依頼は郵便受けに置き、サーバが取りに来る。権威はサーバ。
5. **読む口と書く口を分け、書く口はすべて記録する**（`--by`・`via`・鍵の id・append-only・presence-only）。
6. **道具が自分の版と変更を LLM に伝える**（栞・`tool`）。
7. **数字には分母、無いものは null＋理由。** 推測で埋めさせない。
8. **断るときは静的な符丁＋次の一手。内側の理由を外側で丸めない。**
9. **結果不明は不明のまま保持し、時間で確定しない・自動で再送しない。** ただし**解く道を遠くからも**用意する（`inflight resolve`）。
10. **置き場は作る時に全部作る。** あとから作る設計は「途中の状態」を生む。
11. **ログインは 1 台 1 回。** 貼らせない（ブラウザで許可）。
12. **本番でしか出ない制限**（workerd の PBKDF2・CPU・body・R2 の multipart・umask・既存の mode）は配布担当の実測欄に毎回書く。
13. **検収は LLM に使わせて使い勝手レポートを書かせる。** 外の審査員（Meta）に試させるのも同じ検収。
14. **決まりでなく得で集める**（hub §11）。「必須」と通達して守らせるのでなく、道具を通すと楽になる形にする。通達の「必須」は、得の形に置き換えられたら消す。
15. **中心は壊れない所に**（hub §11）。台帳・名札・見張り・鍵の表は VM と道具の側。LLM のセッションは画面で、いつ差し替わってもよい。
16. **今ある手作業を 1 つ置き換えるときだけ足す**（hub の道具 §4）。部品は既製品でよく、作るのは名札と台帳（つなぎ）だけ。
17. **待つときは起こさない**（Agent Mail の教訓 09-26）。新着が来たときだけ 1 回起きる pull にする。定期に起きて文脈を読み直す見張りは、枠を食う「バケツの穴」。

## 8.5 メディアハブ側の知見（09-27 追記・masaru「メディアハブ側の知見もあるかもしれません」）

media-hub の hub（`設計_プロジェクトハブ_2026-09-25.md`・`設計_hubの道具_2026-09-24.md`・`設計_約束の台帳`・`設計_名簿と当番`・`設計_hubの脈`・SKILL `agent-mail`）は、THTH と同じ VM（wt）で、同じ原則（ヘッドレス・薄い MCP・厚い CLI・厚い SKILLS・メールも画面も作らない）で育っている。masaru の目指す姿は **LLM のヘッドレスなグループウェア**（hub §9）。THTH の小品と hub の小品は、その両半分にあたる:

| 半分 | 何をつなぐか | 小品 |
|---|---|---|
| THTH 側（外向き） | 外の人と、その機械・LLM を、口を開けないサーバにつなぐ | 郵便受け・login と鍵・口座をつなぐ・capability URL・安全装置と停止スイッチ |
| hub 側（内向き） | 内側の LLM たち（各プロジェクトのセッション・Codex）と masaru をつなぐ | 状況の掲示板と受信箱（`hub status post`・`waiting_on_masaru`）・名簿と当番（誰が本線か・1 つの名前は同時に 1 つのセッション）・約束の台帳（期日のある約束を 1 件 1 行・朝に「過ぎた・今日・近い」）・伝言箱（Agent Mail・push でなく pull）・脈（§7） |

hub から借りるもの・揃えるもの:

1. **秘密の置き方は hub の方が進んでいる**: VM の `/etc/credstore.encrypted/`（`systemd-creds`・ホスト鍵で暗号化・平文はサービスが動く数分だけ `$CREDENTIALS_DIRECTORY` に出る・入れるのは Mac から `pbpaste | ssh …`・チャットにも echo にも出さない）。THTH の「所有者だけの 600 のファイル」より一段上。小品 7（秘密の土台）はこの形を正にする。**残る穴も書いてある**（同じ OS ユーザーならサービスの数分間だけ読める・ディスクごとの持ち出し）——穴を書く作法も借りる。
2. **「得で集める」**: THTH の安全装置も、`/activity` も、login も、「通すと楽」の形になっているかで見直す（例: `hub status post` を送っていれば止まっても借宿が続きを拾える、と同じ得を、外の人に対しても作る）。
3. **状態は VM と道具に、セッションは画面に**: hub のセッションが容量制限で落ちても別の借宿で続けられたのは、状態が VM とファイルにあったから。THTH も同じ（このセッションが落ちても、口座・鍵の表・依頼の記録は VM にある）。**申し送り書と hub の 1 行**がその「画面の差し替え」を支える。
4. **伝言は pull・待つときは起こさない**: Agent Mail の `wait_inbox.sh`（新着で 1 回起きて終わる）。THTH の郵便受けも同じ思想（Worker が預かり、VM が取りに来る）。同じ VM に Agent Mail を移すなら、localhost だけで待ち受けて Mac からは ssh のトンネル（hub §10）。
5. **hub が作るのは名札と台帳だけ、部品は既製品**（伝言は Agent Mail・見張りは systemd・SNS は THTH）。THTH の小品を切り出すときも、hub から見て「既製品」になる粒（郵便受け・脈・口座をつなぐ）に切る。
6. **VM に置かないもの**（hub §10）: セッションの操作・各セッションの記録の中身。THTH でも同じ線（依頼の中身は記録するが、LLM の会話は預からない）。
7. **控え**: VM 1 台に集まるものは毎日別の場所へ写す（hub §10 ④）。THTH の `state/` と口座の記録も同じ（今は VM の中の git だけ）。小品にするなら「控えの作法」も 1 行で言えるようにする。

つまり、切り出しの「最初の 1 本」（§9）は THTH 側の Worker だが、**VM の側の骨（署名つき relay・取りに来る常駐・脈・台帳）は hub と THTH で共有できる**。hub の道具の設計 §2-5「三層」と、この文書の §8 の 1 は同じ文で、同じ VM に同居している。名前を付けるなら、その共有の骨に付けるのがよい。

## 9. 着手の時期・順・名前（未決・masaru の一言待ち）

- **時期**: Meta の判定が出るまでは凍結（09-27〜）。判定のあと、3.14.x の後始末（`RELAY_PUBLIC_KEY`・旧 path・添付の遠くの道・`via`）を済ませてから。
- **最初の 1 本**: 小品 1（郵便受け＋login＋鍵）＋2（口座をつなぐ）＋3（capability URL）＋4 の画面（`/activity`）を同居させた **1 つの Worker** と、その Python の library（常駐の骨・`remote.py`・`guard.py`）。THTH をそれに依存させる。第 1 版と同じ形だが、中心が「承認」から「郵便受け」に変わった。
- **名前の候補**（masaru が付ける・無ければこの 3 つから）: `postbox`（郵便受け・依頼を預けてサーバが取りに来る）／`gatehouse`（門番小屋・口を開けずに人と鍵を確かめる）／`relayer`。§8.5 のとおり、名前は THTH の Worker でなく **hub と THTH が共有する VM 側の骨**（署名つき relay・取りに来る常駐・脈・台帳）に付ける方が長持ちする。
- **料金・運用**: Cloudflare 1 アカウント・1 Worker・DO SQLite・R2 1 bucket・rate limit（第 1 版と同じ）。
- **検収**: 別プロジェクトの LLM セッションに使わせて使い勝手レポート。Meta の審査員の試験結果も検収の 1 つ。
