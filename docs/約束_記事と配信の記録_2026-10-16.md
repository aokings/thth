# 約束: 記事と配信の記録（叩き台・2026-10-16）

書いた人: THTH開発 第3（Claude Opus 5.5）。[計画_4.0](計画_4.0_2026-10-15.md) §7 の 2・3（外部レビュー指摘 2〜4）を、実装の前に欄と意味として固める文書。**決まった約束ではなく叩き台**。コードはまだ何も変えていない。4.0 の段（§7 の 10）で「記事との対応付け・配信先の表」を作るときの元にする。

## 0. 一言で

THTH は**記事の編集できる第二の正本を持たない**。持つのは、配信に要る確定した原稿・承認の対象・送信の記録と、それらが**どの記事のどの版から出たか**の結び付けだけ。

## 1. 名前の衝突（先に決めること）

`article_id` という名前は既に使っている。`thth/topic_models.py` の `build_article` が、取得した記事の証拠（本文・取得時刻・範囲）から**中身の指紋で**作る id で、判断コンテキスト（`CONTEXT_KEYS`）にも `article_id`・`article_content_sha256` として入る。本文が 1 字変われば変わる。

ここで要るのは逆に、**本文を直しても変わらない記事の同一性**。同じ名前で意味を変えると、過去の台帳と判断コンテキストの意味が変わる（計画 §7 の 8「過去の台帳や承認の指紋の意味は変えない」に反する）。

**推し: 新しい欄は別の名前にする。** 既存の `article_id` は「記事の証拠の指紋」のまま残し、4.0 の移行表で `article_evidence_id` への改名を候補に載せる（足して残す → 非推奨 → 撤去の順）。

## 2. 欄

| 欄 | 意味 | 誰が決めるか | 変わるか |
|---|---|---|---|
| `article` | 記事の同一性。利用者が決める短い名（例 `kopicha/2026-10-arabica`）。英小文字・数字・`-`・`/` | 利用者（とその LLM） | 変わらない。改名は「別の記事」として扱い、旧名からの付け替えは記録を残す操作で |
| `article_source` | 正本の所在。repo 内の相対パスか URL | 利用者 | 動かしてよい（同一性は `article`） |
| `article_rev` | 正本の版。repo があれば**記事ファイルの blob の sha**（`git hash-object`・無関係な commit で変わらないように・10/16 設計 S1）、無ければ本文の sha256 | THTH が計算 | 本文を直すと変わる |
| `article_rev_kind` | `git` か `content`（repo の無い利用者には「版の前後が分からない」ことを示す） | THTH | — |
| `delivery` | 配信 1 件の id（記事 × 届け先 × 公開物）。安定した乱数 | THTH | 変わらない |
| `destination` | 届け先（媒体・口座・はてなならブログ id） | 利用者が表で決める | — |
| `form` | 届け先での形: `full`（全文）・`summary`（独立した要約）・`entry`（元記事への入口） | 利用者 | 配信ごとに固定 |
| `published_id`・`published_url` | 媒体が返した公開物の id と URL | 媒体 | — |
| `approved_sha` | 承認した中身の指紋（今の承認の指紋そのまま） | THTH | 意味は変えない |

- 原稿の front matter に足すのは `article` と `form` だけ（任意）。`article_rev` は承認の時点で THTH が計算して承認の記録に書く。**承認の指紋（`approved_sha`）には入れない**: 入れると既存の原稿の指紋が全部変わり、再承認が要る（計画 §7 の 8）。版の食い違いは指紋ではなく「承認した版」と「今の版」の比べで見せる。
- `article` の無い原稿（短い観測・会話）は今のまま出せる。毎回記事を作らせない（計画 §7 の 1）。

## 3. 配信先ごとの状態（4.0 で台帳と動きの両方・10/16 の計画の書き直しで 4.0 に入った）

| 状態 | 意味 |
|---|---|
| `wanted` | 出したい版（`article_rev`）がある |
| `inflight` | 操作中（今の `inflight.json` を広げる） |
| `unknown` | 結果不明。**失敗とみなして出し直さない**（今の inflight と同じ決まり） |
| `published` | 公開を確かめた版がある（`checked_rev`・`checked_at`） |
| `conflict` | 媒体の側で手直しされた形跡がある。**勝手に上書きしない** |
| `no_follow` | 追従しない（SNS の告知など。直すかは人が選ぶ） |

更新の追従（`thth article diff`・差分の承認と更新）も 4.0（計画 §3.5）。状態に `deleted` を足し、状態の変わり目ごとに通し番号 `seq` を振る（[設計_4.0_S1](設計_4.0_S1_主体とブログとレーン_2026-10-16.md) §3.4）。

## 4. 数字の出所と帰属

記事ごとの数は、出所と帰属の強さを分けて持つ。合計は THTH では作らない（ダッシュボードと媒体をまたいだ合計は hub・計画 §2）。

| 欄 | 値 |
|---|---|
| `source` | `sns`（媒体の API）・`site`（サイトの訪問・hub から）・`hatena`（ブックマーク件数） |
| `attribution` | `direct`（公開物そのものの数）・`inferred`（条件つきの推定。条件を `attribution_basis` に）・`unknown` |
| `window` | 集計の期間・重複の除き方・欠測の理由（`not_fetched`／`zero`／`not_yet`） |

- 帰属できない流入を、記事の総訪問から推して埋めない。
- はてなの自分のブックマークは反応に数えない（登録の成立・自分の分・第三者の分・新着への掲載・訪問を分ける・計画 §7 の 4）。

## 5. 全文の転載と代表 URL

`form: full` で同じ本文を 2 か所以上に出すときは、どれを代表 URL（検索で正とする所）にするかを配信先の表で 1 つ決める。決まっていなければ `full` の 2 か所目は断る。はてなブログへの本文の配信も 4.0 に入った（計画 §3.3）。

## 6. 決めること

- **masaru に伺う**: なし（推しで進める）。`article` の書式と `form` の 3 つの名前は、各レーンの LLM が書くので、出す前に 1 レーン（kopicha の価格の記事）で試して直す。
- 4.0 の移行表に載せる: 既存の `article_id` → `article_evidence_id`。

## 7. 確かめた深さ

コードを読んで確かめたもの: 既存の `article_id` の作り（`thth/topic_models.py:87-105`・`CONTEXT_KEYS`）、承認の指紋の欄（`thth/approval.py` の `approved_fields`）、原稿の状態（`thth/queuefile.py` の `KNOWN_STATUSES`）。ほかは設計の文で、動かしていない。
