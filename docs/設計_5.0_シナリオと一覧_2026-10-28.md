## 0. 一言と完成の条件

**5.0 は「どの話がどの段で止まっていて、次に何が要り、何を忘れているかを、THTH が 1 枚で言える版」にする。** 原稿を書くのも、段を進めるのも、今までどおり窓口の LLM と承認。THTH は宣言を読み、台帳（`sent/`・配信の台帳・`bm:`・返信）と突き合わせて、現在地と「次の一手」と止まりを出す。

masaru の困りごとは 3 つで、それぞれに THTH が出す答えを決める。

| 困りごと | 意味 | THTH が出すもの |
|---|---|---|
| **抜け** | 糸のどこかの段に何も無い（日記を書かずに告知した・告知の無い記事） | 糸ごとの段の表に「0 本」が見える。`next` に「この段に 1 本要る」 |
| **漏れ** | 出したものがどの話にも結ばれていない（原稿に札が無い・型の枠が空いた） | 結ばれていない原稿の数（`untied`）。型ごとの枠の空き（`empty_slots`） |
| **忘れ** | 動いていた話が止まったまま（調べたきり日記が無い・記事は出たが告知していない） | 糸ごとの `stalled`（最後に動いてからの日数）と `events` の `scenario_stalled` |

**完成の条件の案**（masaru が決める）:

1. kopicha と関東のそれぞれで、糸 1 本と型 1 つを宣言し、`thth scenario <project>` の 1 枚だけで「いま 3 段目・次は X への告知・5 日止まっている」が読める。窓口の LLM がその 1 枚から次の原稿を書き始められる（原稿の正本や日誌を読み直さなくてよい）。
2. 止まり（`scenario_stalled`）と型の在庫切れ（`series_low`）が `thth events` に出て、hub の朝の一枚に載る。人が気づく前に鳴った例が本物で 1 件以上ある。
3. thth.me のアクティビティの頁に、持ち主の糸と型の一覧（段・止まり・次の一手）が並ぶ。masaru がスマホで開いて 10 秒で「どれが止まっているか」が分かる。
4. シナリオを 1 つも宣言していない口座（masaru-*・headlesson 等・外の利用者）は、出力も振る舞いも 4.5.6 と同じ。承認済みの原稿の指紋は 1 バイトも変わらない。

4.0・4.5 と同じく、「読者が増えた」は条件にしない。

## 1. 線引き（守ること）

- **THTH は書かない・決めない。** 原稿は窓口、出すかは承認。THTH は材料・次の一手・止まりを出すだけ。`next` に本文を入れない（`body` という鍵はこの口に出てこない・`observe` の規律 (e) と同じ）。
- **指紋を壊さない。** 糸と型の札（`thread:`・`series:`）は、出す本文も出し方も変えない札なので、承認の指紋に**入れない**（`goal:` と同じ扱い）。`not_after` は出し方を変えるので指紋に入れた（4.5.6）が、これは違う。
- **masaru の台帳の形に依存しない。** 知識の台帳（claims.csv・行事の JSON）は読まない。THTH が読むのは、自分の台帳と、窓口が書いた宣言のファイルだけ。
- **知識の側の出来事は受け取る**（構想 §8）。「調べた・仮説を立てた・記事が出た」は、窓口が糸のファイルに 1 行書く（§3.4）。
- **Web は見る・止める・鍵だけ。** 一覧の画面は読むだけ。押せるのは今あるもの（止める・予約の取り消し）のまま（§5）。
- **hub は読む側。** `thth scenario --json` と `events` を読んで朝の一枚に載せる。THTH は hub を呼ばない。

## 2. 2 つの単位: 糸と型

構想 §4.5 のまま。THTH が数える物差しが違うので、宣言も別の形にする。

| | 糸（thread） | 型（series） |
|---|---|---|
| 何 | 1 つのテーマが 調べる → 日記 → 記事 → 告知 → 温める と進んで終わる | 決まった枠（曜日・時刻）で出し続ける。終わりが無い |
| 進み方 | 段（stage）を順に満たす | 枠（slot）を埋め続ける |
| 困りごと | 抜け・忘れ（止まり） | 漏れ（枠の空き・在庫切れ） |
| THTH が出す | 現在の段・各段の本数・次の一手・止まり | 枠ごとの在庫・次の空き・期限切れ間近 |
| 例 | kopicha「数字で淹れる No.4 煎茶」・関東「文化祭 2026」 | kopicha「数字で淹れる」（火・金 7 時）・関東「21 時の悩み」・関東「週末の行事」（期日つき） |

型の 1 回は糸の 1 本でもある（`series:` と `thread:` を両方書ける）。

## 3. 宣言の形

### 3.1 置き場（未決 2 への推し）

**推し: 窓口の repo、原稿の隣（`docs/sns/scenarios/<id>.md`）。THTH は VM の managed repo から原稿と同じ道で読む。**

理由:
- 宣言は「計画」で、窓口の LLM が書き・読み・直すもの。原稿と同じ場所にあれば、窓口は原稿を書くときに隣を見る。git に履歴が残る。
- VM に新しい台帳を作らなくてよい（段 1 が小さくなる）。現在地は宣言と既存の台帳から**毎回計算する**（状態を持たない）。だから壊れた・消えた・移した、で THTH の台帳と食い違うことが無い。
- 4.4.1 が承認の記録を台帳へ移したのは「サイトの repo に承認の commit が積もる」のを避けるため。宣言は窓口が自分で書くものなので、その理由が当たらない。

前提が変わったら: 遠くの道（`/api/v1`・repo を持たない利用者）がシナリオを先に使うなら、宣言を VM の台帳に置き `thth scenario declare <file>`（API も同じ）で送る形が要る。段 3 に置いた（§6）。その場合も repo の利用者は repo のファイルが正本のまま（`declare` が写す）。

### 3.2 糸のファイル

`thth_scenario: 1` を持つ Markdown。front-matter は原稿と同じ 1 行 1 項目の形（窓口が書き慣れている・`queuefile` の読み方を使い回す）。段の並びだけ本文に書く。

```
---
thth_scenario: 1
kind: thread
id: num-04-sencha
title: 数字で淹れる No.4 煎茶
project: kopicha
stale_after_days: 7
---
# 段（上から順に満たす）

- collect: hatena_bookmark tag=num-04 need=5
- diary: hatenablog need=1
- article: site signal=article_published
- announce: threads,x need=2
- warm: threads,x replies_within_hours=6

# 出来事（窓口が書く・THTH は読むだけ）

- 2026-10-25 researched 全国茶生産団体連合会の目安を 5 本はてブ
- 2026-10-27 article_published https://kopicha.example/recipes/sencha
```

- `id`: `[a-z0-9][a-z0-9_-]{0,63}`。project の中で一意。原稿の `thread:` に書く値。
- 段の 1 行: `<段の名>: <媒体> <条件…>`。媒体は `hatena_bookmark`・`hatenablog`・`site`・`threads`・`x`・`bluesky`・`mastodon`（SNS は `,` で並べられる）。条件は `need=<本数>`（既定 1）・`tag=<タグ>`（はてブだけ・既定は id）・`signal=<出来事の名>`（`site` だけ）・`replies_within_hours=<時間>`（warm だけ）。
- `stale_after_days`: これだけ動きが無ければ「止まり」。既定 7。
- 出来事の行: `- <日付> <名> <自由な文>`。名は `researched`・`hypothesis`・`article_published`・`article_updated`・`closed`（糸を終える）。THTH は日付と名だけ読む。文は表示にそのまま出す（60 字まで）。

**知識の出来事は数の条件の代わりになる**（構想 §0）。`collect` に `need=5` と書いてあっても、出来事の行に `researched` があればその段は満たしたとみなす（どちらか早い方）。数の条件は、出来事が書かれないときの代わり。

### 3.3 型のファイル

```
---
thth_scenario: 1
kind: series
id: num
title: 数字で淹れる
project: kopicha
accounts: kopicha-threads, kopicha-x
slots: tue 07:00, fri 07:00
stock_floor: 2
material_remaining: 4
---
```

- `slots`: 曜日と時刻の組。THTH はこれで「次の枠がいつで、そこに承認済みの原稿があるか」を数える。関東の時間帯の型（`08:00`・`10:30`・`19:00`・`21:00`）は曜日を省いて毎日。
- `stock_floor`: 承認済みで未来の本数がこれを切ったら `series_low`。
- `material_remaining`（任意・**窓口が書く数**・未決 5 への推し）: 材料があと何回分か。THTH は台帳を読まず、この数が `stock_floor` 相当（既定 2）を切ったら `next` に「調べる（collect）を起こす」と書く。窓口が更新を忘れれば古くなる——それでよい（THTH は推測しない・古い日付を添えて出す）。
- 期日の型（関東の行事）は `slots` の代わりに `deadline: true` を書く。原稿ごとの `not_after`（4.5.6）が期日で、THTH は「期限が 48 時間以内の承認済みでない原稿」と「期限が過ぎて出なかった原稿」を型ごとに並べる。期日から逆算した拍子（2 週間前・3 日前・前日）は段 3（§6）。

### 3.4 原稿の札

原稿（SNS・はてなブログ）の front-matter に 1 行:

```
thread: num-04-sencha
series: num
```

- 任意。無ければ今までどおり。
- lint は id の形と「宣言のファイルがあるか」を**予告**する（`thread_not_declared`・断らない。利用者を疑わない線）。
- **指紋に入れない。** `approved_sha` の材料（`compute_approved_components`）に足さない。承認のあとに札を付けても直しても再承認は要らない。
- はてなブックマークの札（`bookmark batch` の `ITEM_KEYS`）は**変えない**。糸との結びはタグで取る（`collect` の `tag=`）。kopicha の調査メモがケースをタグで束ねている今の型にそのまま乗る。

### 3.5 現在地の計算（THTH が読む台帳）

| 段の媒体 | どこを読むか | 数え方 |
|---|---|---|
| `hatena_bookmark` | project のはてなの口座の `sent/bm:`（`result: confirmed`） | タグに `tag=` を含む行の数。第三者の分は数えない |
| `hatenablog` | 配信の台帳 ＋ その `queue_file` の front-matter | `thread:` が一致する配信。`published` を「済み」、`wanted`／`inflight`／`unknown` を「途中」、`conflict` を「止まり」 |
| `site` | 糸のファイルの出来事の行 | `signal=` の名の行があれば済み |
| SNS | 口座の queue と `sent/` | `thread:` が一致する原稿。`posted` を済み、`approved` で未来を「予定」、`draft` を「下書き」。`announces:` があれば告知として印 |
| `warm` | 返信の台帳（`reply_received`）・`unanswered` | 糸の SNS の投稿への返信の数と、未返信のうち `replies_within_hours` を越えたもの |

現在の段 = 上から見て最初の満たしていない段。`closed` の出来事があれば「終わり」。
最後の動き = 上のどれかの最新の時刻。`now - 最後の動き > stale_after_days` で `stalled`。
`next` = 現在の段で足りないものを**名詞で**書く（「hatenablog に 1 本（日記）」「x に告知 1 本（threads は済み）」「未返信 2 件・6 時間を越えた 1 件」）。本文は書かない。

読めない台帳は段ごとに `cannot_say` に符丁を出し、0 と混ぜない（`events` と同じ規律）。

## 4. CLI の口と `--json` の契約

### 4.1 命令

```
thth scenario <project|account> [--json]            糸と型の一覧（既定）
thth scenario show <project> <id> [--json]          1 本の詳細（段ごとの原稿・出来事）
thth scenario lint <project> [--json]               宣言の誤り・結ばれていない原稿・無い id を指す札
thth events <project> … に 2 種類を足す             scenario_stalled・series_low
```

書かない・媒体の API を呼ばない（`events` と同じ）。`run`・timer は触らない。

端末の出力の例（形は仮）:

### 4.3 `events` に足す 2 種類

- `scenario_stalled`（続いている状態・`ongoing: true`）: 糸が `stale_after_days` を越えて動いていない。`ref` は糸の id、`stage`・`days`・`next` が付く。id は `"ev_" + sha256("thth.scenario/1|<project>|<id>|<stage>")[:24]`——同じ段で止まっているあいだは同じ id、段が進めば別の id（受け手が 1 度だけ扱える）。
- `series_low`（続いている状態）: 型の承認済みの在庫が `stock_floor` を切った。`ref` は型の id、`approved_future`・`floor`・`next_slot` が付く。`schedule_thin`（口座全体の 1 日の本数）と別の名前にし、混ぜない（未決 3 への推し・§8）。

hub は `events --json` の `kind` でこの 2 つを拾うだけで、朝の一枚に載せられる（`event_id` で重複を除くのは今までどおり）。

## 5. 一覧の画面

### 5.1 どこに（第10 の推しに賛成・理由を足す）

**アクティビティの頁（thth.me/activity）に「シナリオ」の節を足す。** 新しい頁・新しい入口・script は作らない。

理由:
- 入り方・閉じ方・守り（PBKDF2・5 回で 15 分・10 分で閉じる・CSP・no-store）がそのまま使える。新しく守るものを増やさない。
- 「持ち主が自分の口座のものを見る」という頁の意味と同じ。外の利用者も自分の糸と型が見える。
- hub の朝の一枚は masaru の自前のもの同士をまたいで並べる所で、THTH の画面はその下の「1 人の持ち主の 1 枚」。重ならない。

より良い形は無いか: 鍵なしで開ける読むだけの頁（`/scenarios/<person>`）は、スマホで開くのが 1 手軽いが、題と次の一手（何を調べているか）が外に見える。糸の題は公開前の記事の題そのもので、見せたくない。採らない。

### 5.2 何が並ぶか・押せること

口座の節の**上**に、持ち主ごとに 1 つの節「シナリオ」:

```
シナリオ                                     最終更新 11:20
糸  数字で淹れる No.4 煎茶   3/5 article   止まり 5 日   次: article_published を糸のファイルに 1 行
糸  狭山の霜                 2/5 diary     予定あり       次: 11/12 12:00 に出る
型  数字で淹れる  在庫 1 本（floor 2）  次の空き 金 07:00   ← 足りません
型  週末の行事    期限 48 時間以内 2 本（承認済み 1・未承認 1）
結ばれていない原稿: 3
```

押せること: **増やさない**。止める・予約の取り消し・設定・鍵は今の節のまま。糸を進める操作は無い（進めるのは原稿と承認）。「この糸の原稿の予約を取り消す」も今の行から押せる（`draft_id` のある行）ので、新しい道は要らない。

### 5.3 VM が押し上げる要約の形

`activity.sync` の body に `scenarios` を足す（`accounts` と並ぶ鍵。3.14.0 で `keys`・`results` を足したのと同じ作法）。

```json
"scenarios": [
  {"kind": "thread", "id": "num-04-sencha", "title": "数字で淹れる No.4 煎茶",
   "stage": "3/5 article", "state": "stalled", "stalled_days": 5, "next": "article_published を糸のファイルに 1 行"},
  {"kind": "series", "id": "num", "title": "数字で淹れる",
   "stage": "在庫 1/2", "state": "low", "stalled_days": null, "next": "金 07:00 の枠が空き"}
]
```

- 上限: 1 人 16 行・`title`／`next` は 60 字・`id` は 64 字・`stage` は 24 字・`state` は `active|stalled|closed|ok|low|expiring` の語だけ。制御文字なし。`validSummary` と同じ厳しさで `validScenario` を書く。
- 1 時間で忘れる（`ACTIVITY_TTL`）・10 秒ごとに押し直す、は今のまま。VM 側の計算は `scenario` の `--json` と同じ関数を呼び、そこから 6 つの欄に畳むだけ（二重に計算しない）。
- 出す順: Worker が先・VM があと（`approval` 鍵の前例）。古い Worker は `scenarios` を知らないので、**Worker を出すまで VM は `scenarios` を載せない**（`_legacy` と同じく、断られたら落として押し直す）。
- `SETTING_WORDS` は触らない（段 5 の撤去の版の仕事・計画 4.5 §6）。

## 6. 作る順と大きさ

4.5 の実績（段の数と書き手の日で見る）にそろえる。段ごとに 書き手 Opus → 全件の試験 → 柵を壊して赤 → 監査 → main。

| 段 | 中身 | 効く困りごと | 書き手の日 | Worker |
|---|---|---|---|---|
| **1** | 宣言のファイル（糸・型）を読む / 原稿の `thread:`・`series:`（lint は予告・指紋に入れない）/ `thth scenario`・`show`・`lint` と `--json` / `events` の `scenario_stalled`・`series_low` | 抜け（段の 0 本）・忘れ（止まり）・漏れ（`untied`・在庫） | **1〜1.5** | 不要 |
| 2 | アクティビティの頁の「シナリオ」の節（VM の `scenarios`・Worker の `validScenario` と描画・Worker を先に出す） | 一目で分かる（スマホ） | 1 | **要る** |
| 3 | 期日の型: 行事ごとの逆算の拍子を `next` に出す（型のファイルに `events:` の行・`lead_days: 14, 3, 1`）/ 遠くの道の `thth scenario declare`（API で宣言を送る） | 関東の行事の漏れ・外の利用者 | 1.5〜2 | 不要（API の操作名が増えるだけ・`SAFE_ERRORS` に符丁） |
| 4 | 戻りの輪: `thth scenario seeds <project>`（返信の多かった問い・クリックの多かった告知を、次の糸の候補として並べる。選ぶのは窓口）/ 糸の `mix`（告知・こぼれ話・問いの内訳） | 次の糸の種 | 1 | 不要 |

計: 段 4 つ・書き手の日 **4.5〜5.5**・監査込みで暦 1〜2 週。**段 1 だけで masaru の 3 つの困りごとに答えが出る**ので、段 1 を 4.6.0（か 5.0.0 の最初）として先に出し、kopicha と関東に糸 1 本・型 1 つを書いてもらって 1 週間回す。段 2 以降の順は、その 1 週間の「画面が無くて困ったか」「行事の漏れが出たか」で決める。

**段 1 の大きさの見積もりの根拠**: 新しい台帳を作らない・書かない・媒体を呼ばない。読むのは全部 `events_cli` が既に読んでいる所（`sent/`・配信の台帳・`bm:`・返信の台帳・queue）。新しいのは宣言のファイルの読み（`queuefile` の front-matter の読み方を使い回す・200 行くらい）と、段の計算（300 行くらい）、出力（100 行）、試験。

**段 1 で確かめること**（出す前）: (a) kopicha の `num` の型と、関東の `21:00 悩み` の型を本物の宣言で書いて `series_low` が 10/21 の関東の状況（朝・夜の枠が尽きた）で鳴ること。(b) `thread:` を付けた承認済みの原稿の `approved_sha` が変わらないこと（golden の試験）。(c) 宣言の無い口座で `thth scenario` が空の表を返し、`events` の出力が 4.5.6 と同じこと。

## 7. 実地の確かめ（読んで分かったこと）

- kopicha の queue（`docs/sns/queue/`）: Threads・X・Bluesky・Mastodon・はてなブログの原稿が 1 つの置き場に並ぶ（名前で `th-`・`x-`・`bs-`・`md-`・`hb-` と分かる）。はてなブログは `hb-sousa-NNN`（調査メモ）で 11/12 の予約まで承認済みがある。front-matter に `goal:`（follow 248・click 137・reply 27・reach 14・両 repo 合計）はあるが、`announces:`・`series:`・`thread:` は 1 本も無い。シリーズ「数字で淹れる」は文書 `docs/sns/シリーズ_数字で淹れる.md` に表で持っていて、THTH からは見えない。
- 関東の queue（asmon `docs/sns/queue/`）: 名前が `<日付>-<時刻>-<型>` で、`0800`（朝の数えた事実）・`1030`（文化祭など）・`1900`（要項）・`2100`（悩み）の 4 枠。11/4 まで予約がある。型は名前にしか無い。`not_after` を書いた原稿は見ていない（第9 が勧めた段・未確認）。
- 承認の指紋: `thread`・`series` を足しても `compute_approved_components` を触らなければ指紋は変わらない（`goal` が同じ作り）。
- VM: `state/` に 19 口座（kopicha 5・関東 3・masaru 3・ほか）。4.5.6。シナリオを使うのは当面 kopicha と関東だけで、残りには何も変わらない。

## 8. 未決 1〜5 への推し（構想 §6）

| # | 未決 | 推し | 前提が変わったら |
|---|---|---|---|
| 1 | 本体（サイト）との受け渡し | **出来事を受け取るだけ**（窓口が糸のファイルに `article_published` を 1 行）。本体の記事を配信の台帳に載せない | hub が本体の出来事（サイトの build・sitemap）を持つなら、hub → THTH は `events` の契約で渡す（§9 の問 2）。THTH が本体の URL を見に行く案は、外の HTTP と本体の形への依存が増えるので採らない |
| 2 | 宣言の置き場 | **repo（原稿の隣）**。現在地は毎回計算 | 遠くの道の利用者が先なら VM の台帳＋`declare`（段 3）。その場合も repo の利用者は repo が正本 |
| 3 | 拍子との関係 | **物差しは分ける**。`schedule_thin` は口座全体の 1 日の本数、`series_low` は型の承認済みの本数。糸の `over_days`・`mix` は段 4 で糸の中だけで数える。混ぜると、どちらが鳴ったのか分からなくなる | 型が口座の投稿の全部を覆うようになれば（関東の 4 枠で全部）、`schedule_thin` は要らなくなるかもしれない。そのときは `schedule_thin` を残したまま `series_low` を主にする |
| 4 | 外の利用者 | **同じ形で使える**。宣言は project と口座に結ぶだけで、masaru の台帳の形を知らない。段 1 は repo の利用者、段 3 で API | 外の利用者が来なければ段 3 の `declare` は作らない |
| 5 | 材料の数え方 | **窓口が `material_remaining` を書く**。THTH は台帳を読まない。書いた日を添えて出す | 窓口の台帳の形が hub でそろえば、hub が数えて宣言に書く（THTH は変えない） |

## 9. masaru に伺う問い（2 問・推しつき）

1. **一覧の画面は、アクティビティの頁（持ち主が入って見る・10 分で閉じる・1 時間で忘れる・題は 60 字）に節を足す形でよいか。** 推し: **よい**。理由: 守りを増やさない・外の利用者にも効く・hub の朝の一枚と重ならない。割れる点: 鍵なしで開ける専用の頁なら手軽だが、公開前の記事の題が外に見える。また、画面を作るのは段 2 で、段 1（CLI と `events`）を 1 週間回してからにしたい。画面を先に見たいなら段 2 を段 1 と並べて書き手を 2 体にする（書き手の日は変わらず暦が縮む）。
2. **本体（サイト）の「記事が出た」は、窓口が糸のファイルに 1 行書く形でよいか。** 推し: **よい**。理由: THTH は本体の形を知らない・外の HTTP を叩かない・構想 §8 の「出来事を受け取る」と同じ。割れる点: 窓口が書き忘れると糸が `article` で止まったままに見える（止まりとして鳴るので、忘れは見つかる）。代わりに hub が本体の build から出来事を出すなら、THTH 側は `events` の契約（`kind: article_published`・`ref` は URL）を段 3 で受ける口を足す（書き手の日 +0.5）。

推しで決めたこと（伺っていない・違えば直す）: 札は指紋に入れない。はてブの札は変えずタグで結ぶ。`stale_after_days` の既定 7。`scenarios` の行の上限 16・60 字。`series_low` と `schedule_thin` は別の名前。lint は予告だけで断らない。

## 10. 入れないもの（理由つき）

| 入れないもの | 理由 |
|---|---|
| THTH が原稿を書く・段を自動で進める・次の原稿の予約を自動で置く | 書かない・決めない（構想 §1）。`next` は名詞の列挙まで |
| 知識の台帳（claims.csv・行事の JSON）を THTH が読む | 形が窓口ごとに違う・外の利用者に無関係（構想 §8）。数は窓口が書く |
| 本体のサイトマップ・URL を THTH が見に行く | 外の HTTP と本体の形への依存。出来事を受け取る（§9 問 2） |
| はてブの札の形（`ITEM_KEYS`）を変える | 指紋と `batch` の約束を動かす。タグで足りる |
| 札（`thread:`・`series:`）を指紋に入れる | 本文も出し方も変えないので要らない。入れると承認済みの原稿に札を付けるたびに再承認になる |
| 新しい頁・script・鍵なしの頁・押せる操作の追加 | Web は見る・止める・鍵だけ。題が外に見える |
| 媒体をまたいだ合計・順位・masaru の全 project を並べる 1 枚 | hub の領分（10/23 の線）。THTH は 1 人の持ち主の 1 枚と `--json` |
| 糸の進み具合を VM の台帳に保存する | 毎回計算すれば食い違いが起きない。重くなったら（糸 100 本超・推測）そのとき考える |
| 型の受け取られ方（型ごとの views・返信・フォロー）の表 | `after`・`measured` の材料で hub が並べられる。4.5 の柱 2 と同じ線。段 4 の後 |
| `SETTING_WORDS`・上限の台帳の旧名 | 段 5 の撤去の版（計画 4.5 §6） |
