## 0. 一言と完成の条件

**5.0 は「どの話がどの段で止まっていて、次に何が要り、何を忘れているかを、THTH が 1 枚で言える版」にする。** 原稿を書くのも、段を進めるのも、今までどおり窓口の LLM と承認。THTH は宣言を読み、台帳（`sent/`・配信の台帳・`bm:`・返信）と突き合わせて、現在地と「次の一手」と止まりを出す。

masaru の困りごとは 3 つで、それぞれに THTH が出す答えを決める。

| 困りごと | 意味 | THTH が出すもの |
|---|---|---|
| **抜け** | 糸のどこかの段に何も無い（日記を書かずに告知した・告知の無い記事） | 糸ごとの段の表に「0 本」が見える。`next` に「この段に 1 本要る」 |
| **漏れ** | 出したものがどの話にも結ばれていない（原稿に札が無い・型の枠が空いた） | 結ばれていない原稿の数（`untied`）。型ごとの枠の空き（`empty_slots`） |
| **忘れ** | 動いていた話が止まったまま（調べたきり日記が無い・記事は出たが告知していない） | 糸ごとの `stalled`（最後に動いてからの日数）と `events` の `scenario_stalled` |

**完成の条件の案**（masaru が決める）:

1. kopicha と関東のそれぞれで、糸 1 本と型 1 つを宣言し、`thth scenario <project>` の 1 枚だけで「いま 3 段目・次は X への告知・5 日止まっている」が読める。窓口の LLM がその 1 枚から次の原稿を書き始められる（原稿の正本や日誌を読み直さなくてよい）。
2. 止まり（`scenario_stalled`）と型の在庫切れ（`series_low`）が `thth events` に出て、hub の朝の一枚に載る。人が気づく前に鳴った例が本物で 1 件以上ある。
3. 会話の中で「ダッシュボード見せて」と言うと、全メディア → メディア → キャンペーン／シリーズの 3 階層の画面が出て、押したところから LLM がそのまま動ける。masaru が実際に使う（10/28「これなら僕でも使うかもしれない」・§5）。
4. シナリオを 1 つも宣言していない口座（masaru-*・headlesson 等・外の利用者）は、出力も振る舞いも 4.5.6 と同じ。承認済みの原稿の指紋は 1 バイトも変わらない。

4.0・4.5 と同じく、「読者が増えた」は条件にしない。

## 1. 線引き（守ること）

- **THTH は書かない・決めない。** 原稿は窓口、出すかは承認。THTH は材料・次の一手・止まりを出すだけ。`next` に本文を入れない（`body` という鍵はこの口に出てこない・`observe` の規律 (e) と同じ）。
- **指紋を壊さない。** 糸と型の札（`thread:`・`series:`）は、出す本文も出し方も変えない札なので、承認の指紋に**入れない**（`goal:` と同じ扱い）。`not_after` は出し方を変えるので指紋に入れた（4.5.6）が、これは違う。
- **masaru の台帳の形に依存しない。** 知識の台帳（claims.csv・行事の JSON）は読まない。THTH が読むのは、自分の台帳と、窓口が書いた宣言のファイルだけ。
- **知識の側の出来事は受け取る**（構想 §8）。「調べた・仮説を立てた・記事が出た」は、窓口が糸のファイルに 1 行書く（§3.4）。
- **Web は見る・止める・鍵だけ。** 一覧の画面は thth.me に作らず、会話の中に利用者の LLM が描く。押せるものは全部 LLM への指示（§5）。
- **hub は読む側。** `thth scenario --json` と `events` を読んで朝の一枚に載せる。THTH は hub を呼ばない。

## 2. 2 つの単位: 糸と型

構想 §4.5 のまま。THTH が数える物差しが違うので、宣言も別の形にする。

| | 糸（thread） | 型（series） |
|---|---|---|
| 何 | 1 つのテーマが 調べる → 日記 → 記事 → 告知 → 温める と進んで終わる | 決まった枠（曜日・時刻）で出し続ける。終わりが無い |
| 進み方 | 段（stage）を順に満たす | 枠（slot）を埋め続ける |
| 困りごと | 抜け・忘れ（止まり） | 漏れ（枠の空き・在庫切れ） |
| THTH が出す | 現在の段・各段の本数・次の一手・止まり | 枠ごとの在庫・次の空き・期限切れ間近 |
| 例 | kopicha「数字で淹れる No.4 煎茶」・関東「文化祭 2026」 | kopicha「数字で淹れる」（火・金 7 時）・関東「21 時の悩み」・関東「週末の行事」（期日つき） |

型の 1 回は糸の 1 本でもある（`series:` と `thread:` を両方書ける）。

## 3. 宣言の形

### 3.1 置き場（未決 2 への推し）

**推し: 窓口の repo、原稿の隣（`docs/sns/scenarios/<id>.md`）。THTH は VM の managed repo から原稿と同じ道で読む。**

理由:
- 宣言は「計画」で、窓口の LLM が書き・読み・直すもの。原稿と同じ場所にあれば、窓口は原稿を書くときに隣を見る。git に履歴が残る。
- VM に新しい台帳を作らなくてよい（段 1 が小さくなる）。現在地は宣言と既存の台帳から**毎回計算する**（状態を持たない）。だから壊れた・消えた・移した、で THTH の台帳と食い違うことが無い。
- 4.4.1 が承認の記録を台帳へ移したのは「サイトの repo に承認の commit が積もる」のを避けるため。宣言は窓口が自分で書くものなので、その理由が当たらない。

前提が変わったら: 遠くの道（`/api/v1`・repo を持たない利用者）がシナリオを先に使うなら、宣言を VM の台帳に置き `thth scenario declare <file>`（API も同じ）で送る形が要る。段 3 に置いた（§6）。その場合も repo の利用者は repo のファイルが正本のまま（`declare` が写す）。

### 3.2 糸のファイル

`thth_scenario: 1` を持つ Markdown。front-matter は原稿と同じ 1 行 1 項目の形（窓口が書き慣れている・`queuefile` の読み方を使い回す）。段の並びだけ本文に書く。

```
---
thth_scenario: 1
kind: thread
id: num-04-sencha
title: 数字で淹れる No.4 煎茶
project: kopicha
stale_after_days: 7
---
# 段（上から順に満たす）

- collect: hatena_bookmark tag=num-04 need=5
- diary: hatenablog need=1
- article: site signal=article_published
- announce: threads,x need=2
- warm: threads,x replies_within_hours=6

# 出来事（窓口が書く・THTH は読むだけ）

- 2026-10-25 researched 全国茶生産団体連合会の目安を 5 本はてブ
- 2026-10-27 article_published https://kopicha.example/recipes/sencha
```

- `id`: `[a-z0-9][a-z0-9_-]{0,63}`。project の中で一意。原稿の `thread:` に書く値。
- 段の 1 行: `<段の名>: <媒体> <条件…>`。媒体は `hatena_bookmark`・`hatenablog`・`site`・`threads`・`x`・`bluesky`・`mastodon`（SNS は `,` で並べられる）。条件は `need=<本数>`（既定 1）・`tag=<タグ>`（はてブだけ・既定は id）・`signal=<出来事の名>`（`site` だけ）・`replies_within_hours=<時間>`（warm だけ）。
- `stale_after_days`: これだけ動きが無ければ「止まり」。既定 7。
- 出来事の行: `- <日付> <名> <自由な文>`。名は `researched`・`hypothesis`・`article_published`・`article_updated`・`closed`（糸を終える）。THTH は日付と名だけ読む。文は表示にそのまま出す（60 字まで）。

**知識の出来事は数の条件の代わりになる**（構想 §0）。`collect` に `need=5` と書いてあっても、出来事の行に `researched` があればその段は満たしたとみなす（どちらか早い方）。数の条件は、出来事が書かれないときの代わり。

### 3.3 型のファイル

```
---
thth_scenario: 1
kind: series
id: num
title: 数字で淹れる
project: kopicha
accounts: kopicha-threads, kopicha-x
slots: tue 07:00, fri 07:00
stock_floor: 2
material_remaining: 4
---
```

- `slots`: 曜日と時刻の組。THTH はこれで「次の枠がいつで、そこに承認済みの原稿があるか」を数える。関東の時間帯の型（`08:00`・`10:30`・`19:00`・`21:00`）は曜日を省いて毎日。
- `stock_floor`: 承認済みで未来の本数がこれを切ったら `series_low`。
- `material_remaining`（任意・**窓口が書く数**・未決 5 への推し）: 材料があと何回分か。THTH は台帳を読まず、この数が `stock_floor` 相当（既定 2）を切ったら `next` に「調べる（collect）を起こす」と書く。窓口が更新を忘れれば古くなる——それでよい（THTH は推測しない・古い日付を添えて出す）。
- 期日の型（関東の行事）は `slots` の代わりに `deadline: true` を書く。原稿ごとの `not_after`（4.5.6）が期日で、THTH は「期限が 48 時間以内の承認済みでない原稿」と「期限が過ぎて出なかった原稿」を型ごとに並べる。期日から逆算した拍子（2 週間前・3 日前・前日）は段 3（§6）。

### 3.4 原稿の札

原稿（SNS・はてなブログ）の front-matter に 1 行:

```
thread: num-04-sencha
series: num
```

- 任意。無ければ今までどおり。
- lint は id の形と「宣言のファイルがあるか」を**予告**する（`thread_not_declared`・断らない。利用者を疑わない線）。
- **指紋に入れない。** `approved_sha` の材料（`compute_approved_components`）に足さない。承認のあとに札を付けても直しても再承認は要らない。
- はてなブックマークの札（`bookmark batch` の `ITEM_KEYS`）は**変えない**。糸との結びはタグで取る（`collect` の `tag=`）。kopicha の調査メモがケースをタグで束ねている今の型にそのまま乗る。

### 3.5 現在地の計算（THTH が読む台帳）

| 段の媒体 | どこを読むか | 数え方 |
|---|---|---|
| `hatena_bookmark` | project のはてなの口座の `sent/bm:`（`result: confirmed`） | タグに `tag=` を含む行の数。第三者の分は数えない |
| `hatenablog` | 配信の台帳 ＋ その `queue_file` の front-matter | `thread:` が一致する配信。`published` を「済み」、`wanted`／`inflight`／`unknown` を「途中」、`conflict` を「止まり」 |
| `site` | 糸のファイルの出来事の行 | `signal=` の名の行があれば済み |
| SNS | 口座の queue と `sent/` | `thread:` が一致する原稿。`posted` を済み、`approved` で未来を「予定」、`draft` を「下書き」。`announces:` があれば告知として印 |
| `warm` | 返信の台帳（`reply_received`）・`unanswered` | 糸の SNS の投稿への返信の数と、未返信のうち `replies_within_hours` を越えたもの |

現在の段 = 上から見て最初の満たしていない段。`closed` の出来事があれば「終わり」。
最後の動き = 上のどれかの最新の時刻。`now - 最後の動き > stale_after_days` で `stalled`。
`next` = 現在の段で足りないものを**名詞で**書く（「hatenablog に 1 本（日記）」「x に告知 1 本（threads は済み）」「未返信 2 件・6 時間を越えた 1 件」）。本文は書かない。

読めない台帳は段ごとに `cannot_say` に符丁を出し、0 と混ぜない（`events` と同じ規律）。

## 4. CLI の口と `--json` の契約

### 4.1 命令

```
thth scenario <project|account> [--json]            糸と型の一覧（既定）
thth scenario show <project> <id> [--json]          1 本の詳細（段ごとの原稿・出来事）
thth scenario lint <project> [--json]               宣言の誤り・結ばれていない原稿・無い id を指す札
thth events <project> … に 2 種類を足す             scenario_stalled・series_low
```

書かない・媒体の API を呼ばない（`events` と同じ）。`run`・timer は触らない。

端末の出力の例（形は仮）:

### 4.3 `events` に足す 2 種類

- `scenario_stalled`（続いている状態・`ongoing: true`）: 糸が `stale_after_days` を越えて動いていない。`ref` は糸の id、`stage`・`days`・`next` が付く。id は `"ev_" + sha256("thth.scenario/1|<project>|<id>|<stage>")[:24]`——同じ段で止まっているあいだは同じ id、段が進めば別の id（受け手が 1 度だけ扱える）。
- `series_low`（続いている状態）: 型の承認済みの在庫が `stock_floor` を切った。`ref` は型の id、`approved_future`・`floor`・`next_slot` が付く。`schedule_thin`（口座全体の 1 日の本数）と別の名前にし、混ぜない（未決 3 への推し・§8）。

hub は `events --json` の `kind` でこの 2 つを拾うだけで、朝の一枚に載せられる（`event_id` で重複を除くのは今までどおり）。

## 5. 一覧の画面 — 会話の中の 3 階層のダッシュボード（10/28 masaru の決定で書き直し）

### 5.1 決まったこと（masaru 10/28）

経緯: 第10 が Pencil で描いた thth.me の節（`design/scenario-overview.pen` の A案・B案）は「Claude Code が作る画面ぽい・人間には分かりにくい」。PC版（同じファイルの「PC版 ダッシュボード」・`design/exports/desktop-dashboard.png`）と業界の標準の用語に直したところ、masaru「このままダッシュボードを作ると、ダッシュボード見ながらあなたと話したくなりますよね」「ダッシュボードの操作もしたくなりそう」「PC版として書いてくれた画面くらいの情報量があるととても良い」「もうひと階層上の各メディアを並べたダッシュボードも欲しい」「さらにひと階層下の、キャンペーンや、シリーズに入った画面も欲しい」「使いながら洗練させられますよね？」→「進めましょう。これなら僕でも使うかもしれない」。

決めたこと:

1. **ダッシュボードは thth.me に作らない。会話の中に、利用者の LLM が描く。** THTH は `--json` で中身を全部出し、skill と画面の型（ひな形）を配る。LLM は型に数字を流し込んで会話の横に出す。
2. **押せるものは全部「LLM への指示」。** ボタン・枠・予定を押すと、その指示が会話に入り、LLM が THTH の CLI を動かす。公開の承認は今までどおり THTH の承認の頁で本人が押す。取り消し・止めるなど戻せないものは LLM が 1 度確かめてから。→ 「Web は見る・止める・鍵だけ」「THTH は CLI」は崩れない。
3. **3 階層**: 全メディア → メディア（project）→ キャンペーン／シリーズ。
4. **業界の標準の用語で出す**（下の表）。設計の中の言葉（糸・型・段）は画面に出さない。
5. **見た目は使いながら直す。** 並び・色・言葉は型と skill を直して commit するだけ（release 不要）。新しい数字は `--json` を足す（release が要る）。

thth.me のアクティビティの頁は今のまま（出先のスマホで止まりを見る・止める）。`activity.sync` に `scenarios` を足す案（旧 §5.3）は**取りやめ**。Worker の deploy は 5.0 では要らない。

### 5.2 用語（画面と `--json` の説明に使う）

| 設計の言葉 | 画面の言葉 | `--json` の鍵（変えない） |
|---|---|---|
| project | メディア | `project` |
| 糸 | キャンペーン | `threads[]`（`kind: thread`） |
| 型 | シリーズ（定期投稿） | `series[]` |
| 段 | ステップ（リサーチ → 仮説 → 本記事 → SNS 告知 → エンゲージ） | `stages[]` |
| collect / diary / article / announce / warm | リサーチ（はてなブックマーク）/ 仮説（はてなブログ）/ 本記事（オウンドメディア記事）/ SNS 告知 / エンゲージ | 段の名はそのまま |
| 止まり | 停滞 | `state: stalled` |
| 在庫・下限 | 承認済みストック・目安 | `stock.approved_future`・`stock.floor` |
| 枠の空き | 空き枠（未割り当て） | `next_slot.filled: false`・`empty_slots_14d` |
| 結ばれていない原稿 | 未分類の下書き | `untied.drafts` |
| 次の一手 | 次のアクション | `next[]` |
| 表示・反応 | インプレッション・エンゲージメント率 | `summary` の既存の鍵 |

キャンペーンの「目的」は糸のファイルの front-matter に `goal_text:`（任意・60 字）を 1 行。指紋とは無関係（宣言のファイルで原稿ではない）。

### 5.4 `thth dashboard` の口

```
thth dashboard [--json]                         階層 1（持ち主の全 project）
thth dashboard <project> [--json]               階層 2
thth dashboard <project> campaign <id> [--json] 階層 3a（= scenario show の中身＋成果）
thth dashboard <project> series <id> [--json]   階層 3b
```

- `schema: "thth.dashboard/1"`・`level: "all"|"project"|"campaign"|"series"`。中身は**既存の計算を呼んで束ねるだけ**: `thth.scenario/1`（段 1）・`summary`・`schedule`・`events`（要対応）・`measured`／`after`（成果）。二重に計算しない。
- 書かない・媒体を呼ばない（`events` と同じ）。本文は入れない（題と `head` は 60 字まで）。数には分母、取れないものは `null` と `cannot_say`。
- 階層 1 の「持ち主の全 project」は、その鍵（口座）で見える project の全部。外の利用者も同じ（自分の project だけ）。hub の朝の一枚とは分ける: 朝の一枚は THTH 以外の仕事も含む masaru の全体、こちらは THTH の中身だけ。朝の一枚には要対応の数と「ダッシュボードを見せて」の入口だけ載せればよい（hub の仕事・THTH は呼ばない）。
- 遠くの道（thth.me 経由）でも同じ答えが出ること（`remote_unsupported` にしない）。

### 5.5 skill と画面の型

- 置き場: `skills/thth/dashboard/`（`SKILL.md` に足す節は短く・詳しくは隣の文書）。型は階層ごとに 1 つの HTML の断片（`all.html`・`project.html`・`campaign.html`・`series.html`）。LLM は `--json` を読み、型の差し込み口に数字を入れて出す。毎回ゼロから描かない（ばらつかないため）。
- 型の決まり: 会話の欄（横 680px 前後）で読める。色は会話の側の変数（明るい・暗いの両方）。押せるところは全部 `sendPrompt` 相当の「LLM への指示」で、指示文は「ダッシュボードから: …」で始める（LLM が出どころを分かるため）。
- skill に書くこと: 「ダッシュボード見せて」「〇〇を開いて」で何を叩くか／押された指示の受け方（承認は本人・戻せない操作は 1 度確かめる）／取れない数字の出し方／型の直し方（直したら commit）。
- 洗練の回し方: 見た目の直しは型と skill の commit だけ（release 不要）。新しい数字は `--json` に鍵を足す（約束: 足すだけ・名前を変えない・消さない）。

### 5.6 入れないもの

- thth.me の新しい頁・script・操作の口。チャットの窓を THTH に作ること（会話は利用者の LLM の側）。
- ダッシュボードから直接 THTH を動かす道（押したら必ず LLM を通る）。
- 媒体の順位づけ・おすすめ。THTH は数と状態まで。

## 10. 入れないもの（理由つき）

| 入れないもの | 理由 |
|---|---|
| THTH が原稿を書く・段を自動で進める・次の原稿の予約を自動で置く | 書かない・決めない（構想 §1）。`next` は名詞の列挙まで |
