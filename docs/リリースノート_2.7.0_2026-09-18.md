# THTH 2.7.0 リリースノート（プロジェクトのセッション向け）

2026-09-18。VM の `thth` は 2.7.0 になっています（`thth --version` で確認できます）。2.5.0 から 2.7.0 までの変更を、使う側の言葉でまとめます。設計や検収の記録は次にあります。

- `docs/設計_v3.1_分析の磨きと採集_2026-09-18.md`
- `docs/検証_v31_A実装_2026-09-18.md`
- `docs/検証_v31_C実装_2026-09-18.md`

## 一言で

**自分の投稿がどう読まれたかを、数字の出所と時間条件つきで読める**ようになりました。3 つの読み取り専用コマンドがあり、どれも台帳・原稿・承認を書き換えません。

```bash
thth handoff-report <account> --json          # セッションの最初に: いま何が起きているか
thth analytics-report <account> --json         # 直近 7 日の活動: 刻みごとの views・散らばり・絡んだ枝の帰結
thth analytics-report <account> --compare-previous --by hour_band --json   # 前の 7 日との差を層別で
thth study-report <repo 内の施策 JSON> --json  # 「この変更を試した」と宣言した投稿群の観測
```

MCP からは `operations_handoff`・`analytics_report`・`study_report`。

## 新しく読めるもの

**刻みごとの値（`by_mark`）** — 投稿から 1h・6h・24h・72h・168h・720h（30 日）の時点の views・likes・replies。「同じ 24h の views でも、1h で半分来る投稿と 20h かけて来る投稿は違う」が見えます。各刻みは帯（例: 24h は 24 時間以上 30 時間未満）に入った最初の観測だけを使い、帯に入らなければ `null` と理由。720h の値は**採集が 30 日後に走ってから**なので、いま出る投稿はまだありません。

**散らばり（`iqr`・`min`・`max`）** — 中央値の隣に必ず付きます。差が 5 でも IQR が 40 なら雑音です。標本が 4 未満のときは `iqr` は `null`（`spread_reason` に理由）。

**絡んだ枝の帰結（`engagements.by_thread`）** — 自分が返信しに行った枝ごとに、その返信の 24h の反応、相手が返してきたか（`author_replied_back`: true / false / 分からないなら null）、最初の反応までの時間。`topic`・`form`・`hour_band` の層別も。相手の本文・username は出ません（仮名 `author_key` だけ）。

**層別の比較（`--by kind|hour_band|topic`）** — 前の期間との比較を、型・時間帯・トピックで分けて。層の合計が全体と一致することを `reconciliation` で確かめられます。小さな層は `min_n` 未満で `null`。

**採集の鮮度（`collection`）** — `last_success_at`・`last_attempt_at`・`last_attempt_ok`。`generated_at`（レポートを作った時刻）と混ぜないでください。台帳がいつ更新されたかは、こちらです。

**枝の形の推移（`shape_at`）** — 自分の根投稿について、24h・72h・168h 時点までに採れた返信だけで枝の数・深さ・参加者を計算。

**前回からの差分（`handoff-report --since-last-read`）** — 前回「読んだ」と印を付けた時点からの変化（承認待ちの増減・inflight の出現/解消・通知の新しい event・最後の投稿）だけを先に出します。印を付けるのは **`--mark-read --by <名前>` を付けたときだけ**（付けなければ何も書きません）。MCP と HTTP からは印を付けられません。

**`cannot_say_details`** — 従来の `cannot_say`（日本語の文）の隣に、機械で読めるコード（`median_sample_insufficient`・`post_mark_uncollected`・`collection_records_unavailable` …）。分岐に使ってください。従来の文はそのまま残っています。

**施策の「いつ判断できるか」（`eligibility_forecast`）** — `study-report` で、まだ 24h に達していない投稿がいつ揃うかの時刻。採集が走る保証はしません。

## 採集で変わったこと

- 投稿 1 本につき、30 日後に指標を 1 回多く採ります（720h）。返信の採集は今までどおり 14 日・5 回。
- 新しい観測行に、その時点で最新（48 時間以内）のフォロワー数が `context` として付きます（`followers_count`・`followers_count_at`・`staleness_hours`）。**率は出しません。** views の差を「投稿が良かった」のか「読者が増えた」のかを分けて読むための分母です。過去の行には付きません。

## 読むときの約束（変わっていません）

- `null` は「取れていない」であって 0 ではありません。0 は 0 です。
- 中央値は `min_n`（既定 5）以上の標本があるときだけ。
- 差は観測の差です。因果・施策の効果・推奨には読み替えないでください。
- 媒体や account をまたいで足さない・順位を付けない。並べるだけ。
- 母集団は「所有を確認できた自分の根投稿」と「自分が絡みに行った返信」。SNS 上の全投稿ではありません。
- `generated_at` が新しいことは、台帳が新しい証拠ではありません。`collection` を見てください。

## まだできないこと

- 世間の投稿の検索・他人のプロフィール・場所の検索は、Meta の App Review（審査中）が通るまで、自分の投稿とテスターの範囲に限られます。
- 絡んだ枝のその後の追跡と、語の定期観測は、規約の照合の結果を踏まえて据え置きです。
- Bluesky・Mastodon は同じ形で読めますが、views の無い媒体は `null` のまま並びます。

困ったら、レポートの `cannot_say_details` のコードと、次の文書を見てください。

- `docs/分析レポート_v1.md`
- `docs/運用引継ぎレポート_v1.md`
- `docs/施策レポート_v1.md`
