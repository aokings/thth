# 調べ: 記事の投稿・更新を API でできるブログサービス（はてなブログ以外）

調べた日: 2026-11-12。調べた者: Claude（Sonnet 5.5）。

## 印の意味

- 【公式】 そのサービスの公式の頁を開いて読んだ（URL を付ける）。
- 【記事】 公式でない記事・報道・ライブラリの説明。または検索結果の要約でしか見ていない。
- 【推測】 上のどちらにも根拠がない、こちらの推測。
- 「分からない」 調べたが確かめられなかった。

注意: 頁の読み取りは要約を返す道具を通したので、細かい条件の読み落としがありうる。実装の前に原文を開き直すこと。note の公式ヘルプと note の規約は、直接は開けなかった（403）。

## サービスごとの根拠

### WordPress（自分で置く型）

- 【公式】作る `POST /wp/v2/posts`、直す `POST /wp/v2/posts/<id>`、消す `DELETE /wp/v2/posts/<id>`（`force` でごみ箱を飛ばす）。状態は publish・future・draft・pending・private。日付での予約の書き方は、この頁には明記がない。 https://developer.wordpress.org/rest-api/reference/posts/ （2026-11-12）
- 【公式】鍵は「アプリのパスワード」。wp-admin の利用者の編集画面で作り、Basic 認証で送る。「5.6 から標準で入っている」。cookie 認証は WordPress の中だけ。OAuth や JWT は外付けの部品が要る。 https://developer.wordpress.org/rest-api/using-the-rest-api/authentication/ （2026-11-12）
- 【推測】読む側（一覧・閲覧数）は REST で記事の一覧は取れる。閲覧数は標準では取れず、部品（Jetpack など）次第。
- 【推測】規約は、各サイトの運営者の決めごと。AI・アフィリエイトの禁止は WordPress 本体にはない。自分で置く型なので、外の書き手のサイトごとに鍵をもらう形になる。

### WordPress.com

- 【公式】`status` は publish（既定）・draft・future。future は「公開の別名で、未来の日付を併せて付ける」。`date` は ISO 8601。認証は Bearer。 https://developer.wordpress.com/docs/api/1.1/post/sites/%24site/posts/new/ （2026-11-12）
- 【公式】アプリは Applications Manager で自分で登録し、Client ID・Client Secret・Redirect URI を得る。審査の記載はない。範囲（scope）に posts・stats・sites など。認証コード方式が本番向き。パスワード方式は開発専用。 https://developer.wordpress.com/docs/api/oauth2/ （2026-11-12）
- 【公式】読める範囲に stats がある（閲覧数など）。ただし各項目の中身までは読んでいない。
- 【公式】責任ある使い方の指針: 公開は WordPress.com の規約の範囲で。過度な呼び出しは不可。スパム・詐欺は不可。「Automattic」「WordPress」の名前やロゴは同意なしに使えない。AI とアフィリエイトの明記はない。 https://developer.wordpress.com/docs/api/guidelines-for-responsible-use-of-automattics-apis/ （2026-11-12）
- 分からない: 更新・削除の細部、API の終了予定。

### Blogger

- 【公式】作る（POST）・直す（PUT・PATCH）・消す（DELETE）・読む（一覧・検索）。書き込みは OAuth 2.0 必須（範囲 `https://www.googleapis.com/auth/blogger`）。公開ブログを読むだけなら API キーでよい。 https://developers.google.com/blogger/docs/3.0/using （2026-11-12）
- 【公式】作るときは `isDraft` で下書きにできる。 https://developers.google.com/blogger/docs/3.0/reference/posts/insert （2026-11-12）
- 【公式】publish に `publishDate`（「公開を予約する日時」）がある。 https://developers.google.com/blogger/docs/3.0/reference/posts/publish （2026-11-12）
- 分からない: 規約・割り当て（クォータ）・終了予定・審査の有無（Google の OAuth の確認が要るかもしれない【推測】）。

### Qiita

- 【公式】`POST /api/v2/items`（title・body・tags が必須）、`PATCH /api/v2/items/:id`、`DELETE /api/v2/items/:id`。書き込みは access token が要り、設定の「アプリケーション」で個人用を発行するか OAuth。範囲は `write_qiita`。認証つきで 1 時間 1000 回。予約公開の記載はない。 https://qiita.com/api/v2/docs （2026-11-12）
- 【公式】規約第 11 条: 広告・宣伝・販売が主目的の記事、SEO やアフィリエイトを目的とする投稿は禁止。自動投稿や AI の記事を名指しした条文は、この頁にはない。 https://qiita.com/terms （2026-11-12）
- 分からない: 外の書き手の鍵をもらって代行することへの規約上の扱い（個人の鍵なので使えるはず【推測】）。API の終了予定。

### Zenn

- 【公式】投稿専用の API はなく、GitHub と連携したリポジトリに md を push すると同期（deploy）される。`published: true` で公開、`published_at` に未来の日付で予約（日本時間）。ファイルを消しても記事は消えない（削除は管理画面）。 https://zenn.dev/zenn/articles/zenn-cli-guide （2026-11-12）
- 【記事】読む用の非公式寄りの API はあるが、トピックは取れないという記述がある。 https://zenn.dev/ （検索結果の要約）
- 分からない: 規約（AI の記事など）。
- 【推測】THTH からは、書き手の GitHub のリポジトリに push する形になる。API とは別の形。

### note

- 【記事】2026-10-08 に note が「note API」の提供を始めた（報道・検索結果）。対象は法人向けの note pro の利用企業で、「ソリューションパートナー」の契約をした事業者が使える。第一弾は StoryHub 社のサービス。できるのは下書き保存まで。公開・見出し画像・有料設定・埋め込みは非対応。対応サービス以外の道具は直接つなげない。 https://www.oricon.co.jp/pressrelease/3027859/ 、公式ヘルプ https://www.help-note.com/hc/ja/articles/63304278903321-%E5%A4%96%E9%83%A8%E3%82%B5%E3%83%BC%E3%83%93%E3%82%B9%E3%81%A8%E9%80%A3%E6%90%BA%E3%81%97%E3%81%A6-note%E3%81%AE%E8%A8%98%E4%BA%8B%E3%82%92%E4%BD%9C%E6%88%90%E3%81%99%E3%82%8B-note-API （ヘルプは直接開けず、検索の要約で見た。2026-11-12）
- 【記事】非公式の API で投稿する試みが開発者の記事にある（cookie 認証・CSRF のエラー）。規約上の危うさと仕様変更の恐れがある。 https://zenn.dev/centervil/articles/2025-04-23_054_dev-diary
- 分からない: 規約の自動投稿・AI・アフィリエイトの条文（規約の頁は 403 で読めなかった）。個人向けの公式 API の予定。
- 【推測】個人の書き手の note に THTH が公式に出す道は、いまは無い。

### Seesaa ブログ

- 【公式】blogger・metaWeblog・MT 互換の XML-RPC に対応。入口は `https://blog.seesaa.jp/rpc`。認証はアカウント登録のメールとパスワード（API 専用の鍵はない）。アカウントやブログの新規作成は API ではできない。予約投稿の記載はない。 https://faq.seesaa.net/article/376863567.html （2026-11-12）
- 分からない: 規約・予約・閲覧数の取得・終了予定。
- 【推測】パスワードを第三者の道具に預ける形なので、外の書き手に頼みにくい。

### livedoor Blog

- 【記事】2004 年に「livedoor Blog AtomAPI」が公開された（報道）。非公式の Ruby の部品（2016 年）が WSSE 認証とユーザー名・API キーで、投稿・下書き・画像の送信をする。 https://internet.watch.impress.co.jp/cda/news/2004/06/25/3651.html 、https://www.rubydoc.info/gems/livedoor_blog_atom_pub/0.1.1 （2026-11-12）
- 公式の頁は見つけられなかった。公式の開発者向けの頁（ブログパークのヘルプ）は第三者のアプリの規則の話で、API の記載はない。 https://help.blogpark.jp/archives/52585355.html （2026-11-12）
- 分からない: いま動くか・API キーの取り方・規約・予約。

### FC2 ブログ

- 【記事】metaWeblog 形式で `blog.fc2.com/xmlrpc.php` に送る例が個人の記録にある（2011 年ごろ）。ID・メール・パスワードを使う。 https://gist.github.com/fetus-hina/1199879 （検索結果）
- 公式の頁は見つけられなかった（help.fc2.com でも該当なし）。
- 分からない: いま動くか・規約・予約。

### Ameba ブログ（アメブロ）

### Medium

- 【公式】「Medium API はもう支援されない」「新しい連携は受け付けない」。リポジトリは 2023-03-02 に保管（読み取り専用）。投稿の口（`POST /v1/users/{id}/posts` など）の記述は残る。 https://github.com/Medium/medium-api-docs （2026-11-12）
- 【公式】API 利用規約: 自動で作った投稿・フォロー等は禁止。API の利用で収益を得ることも禁止。大量の呼び出しは制限・遮断されうる。 https://github.com/Medium/medium-policy/blob/master/api-terms-of-use.md （2026-11-12）

### Ghost

- 【公式】Admin API の posts は、閲覧・読み・直す・作る・複製・消すが連携に使える。鍵は連携の admin API キー（`id:secret`）で短い JWT に署名する。スタッフ用トークンもある。自分で置く型も Ghost(Pro)（`*.ghost.io`）も同じ入口の形。 https://docs.ghost.org/admin-api/ （2026-11-12）
- 予約の頁（`status: scheduled`・`published_at`）は、開いた頁では確かめられなかった。【推測】あるはず。
- 分からない: 規約。

### Substack

- 【記事】公式の投稿 API はない。2026-04 に出た公式の開発者 API は、LinkedIn のハンドルから公開プロフィールを引く狭いもので、申し込み・利用規約の手続きがある。投稿は非公式の逆引きの部品（python-substack など）で、メールとパスワードか cookie を使う。 https://dev.to/equinoxaifinancergb/does-substack-have-an-api-2026-and-what-you-can-actually-get-29il 、https://pypi.org/project/python-substack/ （検索結果）

### Tumblr

- 【公式】作る・直す（NPF の `/posts`・`/posts/{id}`、旧 `/post`・`/post/edit`）、消す（`POST /v2/blog/{blog}/post/delete`）。`state` は published・queue・draft・private。`publish_on`（ISO 8601）は `state=queue` のときだけ効く。アプリは tumblr.com/oauth/apps で登録し、OAuth2（範囲 basic・write・offline_access）。審査の記載は見ていない。投稿数の上限（キュー・1 日）のエラーあり。 https://www.tumblr.com/docs/en/api/v2 （2026-11-12）
- 分からない: 規約・終了予定。

### dev.to（Forem）

- 【公式】`POST /api/articles`（`published` の既定は false で下書き）、`PUT /api/articles/{id}`（著者の鍵のみ）。消す API は書かれておらず、非公開化は管理者・モデレーターの権限が要る。予約の請求の項目は書かれていない。鍵は `api-key` ヘッダー。 https://developers.forem.com/api/v1 （2026-11-12）
- 【公式】AI の記事は、誠実に出し、AI の関与を明示すれば可。宣伝・SEO の被リンク・金銭の勧誘が目的の記事は停止の対象。 https://dev.to/guidelines-for-ai-assisted-articles-on-dev （2026-11-12）
- 分からない: 鍵の取り方（設定画面と思うが頁には無い【推測】）・規約の自動投稿の条文。

### Hashnode

- 公式の頁は開けなかった（開発者向けの頁の名前が引けず、GraphQL の入口 gql-beta.hashnode.com は説明のない画面だった）。
- 【記事】GraphQL（`gql.hashnode.com`）に個人のアクセストークンで publishPost を呼ぶ。removePost があるとする記事がある。予約の仕組みはスキーマにないとする記事がある。2026-02 に publishPost が極端に遅いという報告。 https://hashnode.com/posts/hashnode-api-issue-publishpost-performance/6991237848080d46778f78e1 （検索結果）

### Micro.blog

- 【公式】Micropub。作る（`h=entry`・`content`）・直す（`action=update`・`replace`）・消す（`action=delete`・`url`）。token は IndieAuth かアカウントのアプリ用 token。下書き（`post-status=draft`）から後で公開に更新できる。予約公開は書かれていない。 https://book.micro.blog/micropub （2026-11-12）
- 分からない: 規約・利用の大きさ。

## THTH が次に足すなら（推し）

はてなブログと同じく「書き手が自分の鍵を渡す」形になるものを選ぶ。

1. **WordPress（自分で置く型）と WordPress.com** を 1 つの口にまとめて足す。
   - 理由: 公式で作る・直す・消す・予約がそろい、鍵は審査なしで書き手が自分で作れる（アプリのパスワード、または OAuth アプリの自己登録）。サイトの数が多く、日本の個人・事業者のブログにも多い【推測】。
   - 前提: 書き手が自分のサイトで REST を有効にしていること（既定で有効）。サイトごとの運営者の規則や、予約の日付の細部は実機で確かめる必要がある。
2. **Blogger**。
   - 理由: 公式で作る・直す・消す・予約（`publishDate`）がそろう。
   - 前提: Google の OAuth の確認（審査）が要るかもしれない【推測】。THTH が OAuth の窓口を持てること。日本の利用は多くない【推測】。
3. **Qiita**（技術系の書き手が相手なら）。
   - 理由: 個人の access token を書き手が発行でき、作る・直す・消すが公式にある。1 時間 1000 回で十分。
   - 前提: 予約公開は API に無い（THTH 側の予約で出す形になる）。規約でアフィリエイト・SEO 目的の投稿が禁止なので、THTH の使い道が宣伝寄りなら合わない。技術以外の書き手には向かない。

足さないほうがよいもの: Medium（新規連携を受けない）・goo ブログ（終了）・Substack（公式の道なし）・note（個人向けは無く、法人向けは下書きのみで契約が要る。ただし需要は大きいので、note の動きは追う価値がある）。livedoor・FC2・Ameba は公式の根拠が取れていないので、足す前に実機の確認が要る。
