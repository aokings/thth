## 1. 退出しても systemd の timer が残る（P2・報告の口 r20260923-653324b9）

**実測**: kopicha-server-mastodon の `thth account leave` 完了後（3.1.2・09-23 12:48）も `thth@kopicha-server-mastodon.timer` が active のまま 10 分ごとに空回りし（`account_stopped`）、`thth admin timers` の記録（`state/_admin/timers.json`）にも残った。手で `sudo systemctl disable --now` した。

**直し**:
- `thth/leave.py` の削除の段のあとに、その account の unit（`thth@<name>.timer`・`thth-collect@<name>.timer`・`thth-collect@<name>.service` があれば）を止める。VM では `wt` に passwordless sudo があり、運用者はこれまで `sudo -n systemctl disable --now <unit>` で止めている。道具は **`sudo -n` で 1 回だけ試み**、失敗（sudo が無い・パスワードが要る・unit が無い）でも退出は完了のまま、結果を `row['timers']`＝`{disabled: [...], pending: [...], reason}` に記録して、`command()` が「残った unit を止める命令」をそのまま打てる形で 1 行出す（例: `timer_cleanup_pending: sudo systemctl disable --now thth@<name>.timer`）。unit が存在しないときは何もしない（`systemctl list-unit-files` で確かめる）。
- `thth admin timers` は、台帳の無い account の unit と timers.json の記録を `orphan_unit` として静的に出し、止める命令を添える。timers.json から台帳の無い account の記録を消す（次の `admin timers` の更新で）。
- systemctl も sudo も呼べない試験環境で動くこと（`shutil.which` と subprocess を注入）。

**試験**: fake の subprocess で (a) 成功 → disabled に 2 unit・pending 空、(b) sudo 失敗 → 退出は completed・pending に unit・打てる命令の行、(c) unit が無い → 何も呼ばない、(d) `admin timers` が orphan を出す。単変異: sudo 失敗で退出を失敗にする形 1 本。

## 2. `thth who` が同じ repo の他 account の返信を数える（P3）

**原因**: `thth/who_cli.py` が `replies_mod.load(account_name)` を `owned_only` なしで呼ぶ。返信の台帳は同じ repo の 3 口座で共有なので、他の媒体の返信行も読まれ、`author_key(media, username)` を**この account の media で**計算するため、同じ username の人が他の媒体で返信していると「相手→自分」に混ざる。

**直し**: `replies_mod.load(account_name, owned_only=True)`（3.1.1 の母集団）。`who` の分母に `other_account_files` を出す。`unanswered`・`morning`・`observe` など、他に `owned_only` なしで返信を数えている読み手が無いかを grep し、あれば同じく直す（持ち主の判定を自前でしている所は触らない・直した所は検収依頼に列挙）。

**試験**: 同じ repo の threads と bluesky の台帳で、同じ username の返信を threads の投稿にだけ置く → `who kopicha-bluesky @名前` の「相手→自分」が 0。単変異: owned_only を外す 1 本。

## 3. 広場の公開（open）の二段確認の穴（P2・3.4.0 検収で残した穴）

**穴**: 二段確認が掛かるのは project → open の切り替えだけ。(a) 既に open の書き込みの更新（判定の理由・観測の取り直し・本文の追記）で、他の持ち主に見える写しが二段確認なしで作り直される。(b) 他の持ち主が open の書き込みに付ける返信も二段確認なしで見える。

**直し**: (a) open の書き込みの update は、写しが変わるなら 1 回目で「他の持ち主に見える新しい姿」と digest を出すだけにし、`--confirm <digest>` で反映（project 範囲だけの変更・判定のコードだけの変更で写しが変わらないなら一段）。(b) open の書き込みへの返信は、返信する側の持ち主の CLI で二段（1 回目で他の持ち主に見える姿と digest・2 回目で反映）。MCP からの open への返信は受けない（`open_requires_cli`）。project 範囲の返信は従前どおり一段。

**試験**: (a) 写しが変わる update は 1 回目で変わらない・2 回目で変わる・digest 違いで断る、写しが変わらない update は一段、(b) open への返信の二段と MCP の断り。単変異: (a)(b) それぞれ 1 回目で反映する形 各 1 本。
