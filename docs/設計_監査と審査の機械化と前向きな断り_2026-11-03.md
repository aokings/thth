## 0. 前提を疑った所

1. **「厳格な skill」は skill の文を厚くすることではない。** skill 4 本で 103 KB（thth 69,079・thth-flow 17,436・thth-ads 12,704・thth-admin 3,987 バイト）【動】。厳しさは「道具の出力の先頭 1 行」と「lint」に寄せ、skill は地図に薄くする。型は既にある（`thth/flow_skill.py` `skill_line()`・`thth/ads/guide.py:39 skill_ref()`）。
2. **LLM の監査を CI の中で走らせるのは、関門として弱い**（結果が揺れる・費用・鍵）。LLM の監査は CI の外のまま、**監査の書の有無と「危ない 0」を機械が読む**。
3. **3 つ（why・fix・better）を全符丁に文で必須にすると雑音になる。** 置き場が読めない系に「もっと良く」は書けない。`no_better`（理由つき）を明示して通し、その数に上限を置いて絞る。
4. **「審査」に THTH が自分に課す柵が抜けていた。** privacy の頁の約束とコードの置き場の一致（監査 5.7.0 K-1 の型）・符丁と `--json` の欄を消さない互換。これは試験で縛れる。

### 代表例（今 → 前向きな形）

## 2. 監査・審査と呼ぶもの（masaru の読み (1)〜(4) の直しと足し）

- (1) 開発の監査: 監査で見つけた型を**毎回「柵」に落とす段**が無い（K-1 → privacy と置き場の照合試験のように）。
- (2) 媒体の審査: `thth doctor`・`auth_log` で半分ある。足すもの: 使わない権限の失効の見張り（28・90 日・広告の段 30 日）・年次の Data Use Checkup とデータ削除の受け口の生きている確認・審査員が手で押す画面（`/activity`・招待）と CLI の呼び出しの対応表を道具が出す。
- (3) 入会と量の審査: 口座ごとの柵はある。足すもの: **共有アプリ全体の数**（全テナントの合計が上限にどれだけ近いか）・新テナントの慣らし期間。内容は判断せず、量と振る舞い（断りの繰り返し・急な連投）だけ。
- (4) skill: 厳しくする先は lint と出力。操作の記録（`refusals.record`・`runs`・`admin log`）から違反を見つける。今の控えは直近 5 件で率が出ない。
- 足すもの: ①**代理店→客の承認**（客を承認者にする席が無い）、②**媒体の規約の種類の事前確認**（はてなの商用・X の重複）、③**お金の承認**（予算を変える操作）、④**互換**、⑤**privacy とコードの一致**。

## 3. 断りの形の契約

- **目録を 1 か所に**: `thth/refusal_catalog.py`。1 符丁 1 項目で `kind`（refusal／cannot_say）・`why`・`fix`（`text`・`command`）・`better`・`no_better`（`internal`／`terminal`）・`doors`（cli・mcp・remote）・`since`・`lang`。穴埋めは静的な型に**検査済みの値だけ**（台帳にある口座名・時刻・台帳の数値）。自由文・本文・パスは埋めない。
- **3 つの口で同じもの**: CLI は 1 行目 `符丁: なぜ` を保ち（`refusals.reason_code` が読む）、`通すには:`・`もっと良く:`・`report_channel:` を続ける。`--json` は既存の鍵を消さず `why`・`fix`・`better`・`next_at` を足す。MCP は text の 1 行目は符丁のまま、行を足す。Worker（`callback/src`・符丁 33）は目録を JSON に書き出して読む。ダッシュボードの `THTH_REASON` は目録から生成。
- **試験で縛る**（`tests/test_refusal_catalog.py`）: ①AST で集めた符丁が目録に無ければ赤 ②`why`・`fix.text` が空なら赤・`better` が空なら `no_better` の理由が要る・`no_better` の数に上限（版ごとに下げる） ③`retired` の無い符丁が消えたら赤（互換） ④`THTH_REASON` 4 本が生成物と一致 ⑤`too_soon` の fix を空にして赤を一度見る。
- **既存を壊さず移す**: 既存の 16 の dict を目録に吸い、元の名前は目録の見方に置き換える（呼び出し側は無改修）。`guard_refusal_message` と `lint._REASON_TABLE` は残し、一致を試験で縛る。次の段で 25 種類の `_fail` 系の口を `refusal.emit(args, code, **values)` に 1 本ずつ寄せる。

## 4. 使い勝手を保ち伸ばす

- **通るときは黙る**: 関門は rc 0 で 1 行も足さない。
- **同じ確かめを 2 度させない**: `fix.command` は値を埋めてそのまま打てる形（`--by` だけ穴）。送信の道と `--dry-run` が同じ目録・同じ 3 行。2 段確認の 1 段目は断りに数えない（既存）。
- **覚えることを増やさない**: 断りの 3 行が次に打つ命令そのものになるので、skill から「断られたら」の段落を減らせる。
- **`--fix`** は front-matter の形だけ（`publish_at`・`not_after`・`thth:` の印）。本文は提案に留める。
- **先回り**: `before_you_post` に今日の残り枠（daily・burst・quiet_hours）を数で。
- **手数の釣り合いを測る**: 断りの率（口座ごと・7 日・100 命令あたり）と同じ符丁の 10 分内の繰り返しを dashboard に（0 なら出さない）。段ごとに上がっていないことを完成の条件に。
- **どこで減らすか**: fix があるときの `report_channel` は短縮形・skill thth を地図にして −30%【推】・observe の節を 3 行の文体に。

## 5. skill の厳格化

- 試作【動】: skill の `thth a b` の命令は argparse の 209 経路に全部実在。MCP の道具名の「無い」は動的生成（`mcp/server.py:892`）の誤検知。**skill lint は regex でなく `cli.build_parser()` と MCP の道具一覧を import して突き合わせる。**
- `tests/test_skills_lint.py`: ①命令が実在 ②MCP の道具名が実在 ③符丁が目録にある ④古い版の「新しく」を警告 ⑤skill ごとの大きさの上限（ラチェット・thth は 70,000 から） ⑥既存の skill の試験はそのまま。
- 操作の記録から違反を見つける（3 型・読むだけ）: 同じ符丁を 10 分に 3 回／open に `--preview` なしで post／send の前に lint・`--dry-run` が無い。observe の第 1 段に 1 行（0 なら出さない）。

## 6. 開発の監査の機械化

- **二層**: (A) 決まる柵（CI・毎 push）＝全件試験＋目録の柵・skill lint・privacy とコードの一致・互換の柵・秘密の形の走査。(B) LLM の監査（CI の外）＝今の形を保ち、監査の書の頭を機械が読める形に（commit の範囲・危ない の数・直した commit・監査した者）。
- **関門** `tools/release_gate.py`（手元と CI）: ①CI 緑 ②その版のリリースノート ③危ない領域（`server_writes`・`server_reads`・`guard`・`plaza_redact`・`leave`・`callback/`・privacy／terms・承認の口）に触る diff なら、範囲を覆う監査の書があり「危ない」が 0（か却下の理由） ④互換の柵が緑。欠ければ `release_blocked: <符丁>` と 3 行（関門も前向きな断りに従う）。
- **費用と速さ**【推】: Fable の監査 1 回 30〜60 分・数十ドル。危ない領域に触る版だけ必須。監査の書の末尾に「柵にしたもの」の欄を必須に。
- **masaru の「出して」の前に揃うもの**: `release_gate` が緑＋リリースノート＋VM で確かめる 1 行。hub の `approve verify` にこの関門を結べる。

## 8. masaru に聞く問い

1. **決まった（masaru 2026-11-03「推しでOK」）: better は利用者向けの断りだけ必須。内部の故障系は `no_better: internal` を明示し、その数に上限を置いて版ごとに下げる。**
