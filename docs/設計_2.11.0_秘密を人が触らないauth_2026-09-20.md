# 設計 2.11.0: 秘密を人が触らない auth——X を見据えた共通の骨

2026-09-20。masaru の言葉: 「シークレットを LLM に見えないように仕込む作業が毎回煩雑。注意のいる作業のわりに原始的」「X を生やすのも 3.0 の要件。その辺も見据えた作りに」。

本書は契約。実装は Codex（2.10.0 の後）。裁定は §8。

## 0. 現在地（8a1deef・L1）

- Threads: `thth auth <account> --by` が認可 URL を出し、人がブラウザで承認し、**戻り URL を貼る**（`state` 照合 → code → 短期 → 長期 token → `me` で handle 照合）。thth.me の callback は戻り URL を見せるだけ。`maintain` が長期 token を refresh。
- Bluesky: `thth auth` はアプリパスワードを対話で貼る（`create_session`）。
- Mastodon: 人がブラウザでアプリを作り scope を選び、トークンを目で運んで `thth token set` に貼る。今日の `read:search` 不足はこの手順で起きた。
- 共通: 秘密が人の目とクリップボードを通る。手順は媒体ごとに違う。scope は人が選ぶ。

## 1. 目指すもの（3.0 の条件）

**導入は「`thth auth <account> --by 名前` が出す URL をスマホで開いて承認を押す」だけ。** トークンは媒体から VM へ直接届き、人も LLM も値を見ない。scope は道具が要求する。媒体が増えても手順は同じ 1 つ。

**裁定（masaru・2026-09-20 昼）: 3.0 は「クローズドのサーバ型」。** 招待制（`account add --by masaru` の延長・利用者自身は account を作らない）・masaru のアプリ・masaru のサーバ。利用者は VM も Meta アプリも持たず、`thth auth` はサーバ側で（masaru か「接続」ページから）始める。本書の預かり所と VM の分離はそのまま使う。書く口（`approve`／`send`）を利用者 scope の HTTPS／MCP に開く設計と退出（失効・削除・記録）は 2.12.0 として別に起こす。道具型（各自が自分のアプリと VM を持つ）の導入文書は書かない。

## 2. 共通の骨（`thth/authflow.py`・新設）

OAuth 2.0 の認可コード方式＋PKCE を 1 本の流れにし、媒体差は adapter の `AuthProfile` に閉じ込める。

1. **クライアントの用意**: 媒体ごとの client_id／client_secret は VM の `~/.config/thth/apps/<medium>[.<instance>].env`（600・プロジェクト外・2.9.0 の `app.env` と同じ流儀）。Mastodon は instance ごとに **`POST /api/v1/apps` で自動登録**し（人はアプリを作らない）、その結果をここに書く。Threads・X は運営者が開発者ポータルで作った値を 1 度だけ置く（`thth app set <medium>`・既存の `thth app` の延長・`--stdin` で秘密管理ツールから流せる）。
2. **開始**: `thth auth <account> --by 名前` が `state`（32 byte 乱数）と PKCE の `code_verifier` を作り、`state/<account>/auth_state.json`（600・10 分で失効）に保存。認可 URL を 1 行だけ出す（scope は adapter が決める・人は選ばない）。
3. **承認**: 人がスマホで開いて承認。媒体が `https://thth.me/callback/?code=…&state=…` に戻す。
4. **code の受け渡し（2 経路・どちらも可）**:
   - **預かり所（既定）**: thth.me が `code` を `state` に紐づけて **5 分だけ** 預かる（§3）。VM の `thth auth` は開始後に預かり所を 2 秒おきに最長 10 分取りに行き、届いたら人は何もしない。
   - **貼る（後方互換）**: 預かり所が使えないとき、いまと同じく戻り URL を貼る。
5. **交換**: VM が `code`＋`code_verifier`＋client_secret でトークンを取る。**`code_verifier` は VM から出ない**ので、`code` だけを知っても（預かり所や browser 履歴から）トークンにできない。
6. **確認**: 本人確認の API（`me`／`verify_credentials`／`users/me`）で handle を照合（既存 `handle_matches`）。応答の `scope` を `.token` に記録（`scopes_source: "response"`）。
7. **保存**: `.token`（600）に access／refresh／`obtained_at`／`expires_at`／`scopes`。変更ログに `token_set`（2.9.0 のまま）。`maintain` が期限の近いものを refresh（Threads の長期 token と同じ口・adapter の `refresh()` に委ねる）。

## 3. thth.me の預かり所（Cloudflare Worker＋Durable Object・長期の秘密を持たない）

**訂正（Codex の実装前照合 2026-09-20）: 初版は KV と書いたが、KV は eventual consistency で「1 回だけ渡す」を保証できない。Durable Object（SQLite storage・強整合 transaction）に置き、状態遷移を持つ。**

- 状態: VM が開始時に `state` と **read key の hash** を登録（`pending`）→ callback が code と受付時刻 `received_at` を 1 度だけ置く（`ready`・重複 callback は上書きしない）→ VM が `Authorization: Bearer <read key>` で 1 度だけ取得（`consumed`・tombstone は state 期限まで）。未登録・二重登録・期限切れの state は拒否。code の寿命は初回 callback から 300 秒以内かつ state 開始から 600 秒以内。consume 後の通信断は再認可（確実な 1 度受領は保証しない）。read key は認可 URL・ログ・出力に出ない。 未登録 state の GET は 404 で永続状態も alarm も作らない。登録済み state で read key 欠落／不一致は 401（空待ち成功ではない）。期限後・consumed 後の callback は格納しない。失効時に payload と read key hash は削除し、VM は state を毎回新規生成して再利用しない。cleanup 後の同じ値の再登録を永久に拒否する保証はしない（永久保存は持たない）。
- 制限: Rate Limiting binding（拠点単位・近似）で per-IP 120 回/分、DO 内で per-state の総 GET 上限 400 回（正しい read key を提示した試行だけを数える・誤 read key の 401 は数えない・超過は `expired`。訂正 2026-09-20: 初版の 40 回は 2 秒 poll × 600 秒 = 300 回と整合しなかった）。429 は待つ・全体 600 秒は延ばさない。入力長の上限・`Cache-Control: no-store`・`Referrer-Policy: no-referrer`・観測ログ off。
- 費用: 「1 認可 = 1 key なので無料枠を超えない」は撤回。未測定。deploy 後に利用量を読む。

- `GET /callback/?code&state`: 登録済みの `state` なら DO に `code`＋`received_at` を置き、「承認できました。ターミナル（VM）が受け取ります。貼り付けは要りません」と表示。未登録・期限切れ・DO に置けないときは今の画面（戻り URL を見せる）に落ちる。
- `POST /relay/<state>`（登録・read key の hash を body に）と `GET /relay/<state>`（read key の Bearer 必須）: 1 回だけ `{"code": …, "received_at": …}` を返して `consumed` に。無ければ 404。
- `code` はログに出さない（Worker のログを切る・URL に載る `code` を `console.log` しない）。
- **預かり所に長期 token・client_secret・`code_verifier` を置かない**（code は短命だが credential として扱い、DO の外・ログに出さない）。`code_verifier` と client_secret は、その媒体の正しい token endpoint に HTTPS でだけ送る（relay・ブラウザ・ログ・stdout／stderr・runs・変更ログには出さない）。Threads は PKCE 無し（Meta 非対応）なので「全媒体を PKCE で守る」とは言わない。X の code 交換期限は 30 秒なので、VM は取得後ただちに交換し、stale は再認可。
- 同じ Worker が `/oauth/client-metadata.json`（§4 Bluesky 用）を配る。

## 5. 逃げ道（残す・正式化する）

`thth token set <account> --by 名前 --stdin` は残す。**秘密管理ツールから流すのを正式な形**として文書に書く（値は画面に出ない・LLM の文脈に入らない）:

```bash
op read "op://THTH/<account>/credential" | thth token set <account> --by masaru --stdin
```

対話で貼る形（tty）も残すが、文書では「最後の手段」にする。Bluesky の `token set --stdin` は入力をアプリパスワードとして扱う（媒体別の意味を `--help` と導入文書に明記）。

`app set <medium> --stdin` は `--by` 必須で、変更ログに `app_set`（presence-only: `client_id`／`client_secret` の有無だけ）を残す。既存の Threads の `app set --app-id … --secret-stdin` も同じ契約に揃える（`--by` 必須・`app_set` を記録・旧 flag は残す）。`EVENTS` に `app_set` を足す。

## 6. 観測（2.9.0・2.10.0 との接続）

## 7. 順番と検収

1. §3 預かり所（Worker＋Durable Object）——`callback/` の変更・`wrangler` の DO binding・deploy は masaru の一言で Claude。否定ケース: 未登録 state の callback は預からない・read key 無し／不一致は 401・2 回目の取得は 404（consumed）・期限後は 404・重複 callback は上書きしない・code と read key はログに出ない・per-state 400 回超で expired・Bluesky の client metadata は 2.11 では配信しない（404）。
2. §2 共通の骨＋Threads を預かり所に載せる（既存の貼る経路は残す）。`admin_log.guarded` は認可待ちの間 lock を持たない（待機／交換と最終保存の transaction を分ける）。`--rehearse` は RAM だけの session で、VM の state／token／app／doctor／runs／変更ログ／lock を作らず変えず消さず、relay に登録しない専用乱数 state で空を待つ GET のみ・予期せず code が来ても交換しない・600 秒 timeout は fake clock で先に検証。VM 実測はこの無登録 GET だけ。
3. Mastodon（自動登録＋PKCE＋verify_credentials）。実機: kopicha-mastodon を `thth auth` で入れ直し、`read:search` が付くこと・`where` の 403 が消えることを masaru の承認で確かめる。
4. X の `AuthProfile`（開発者ポータルの App が要る・masaru が用意できたときに実機）。
5. Bluesky atproto OAuth の試み（収まらなければ §4 の判断で次版へ）。
6. §5・§6・文書（導入の手順を 1 枚に書き直す: `docs/導入_自分のMetaアプリで動かす.md` を「導入_承認を押すだけ」に）。
- 秘密の走査: 全経路で stdout／stderr／runs／変更ログ／預かり所のログに token・code_verifier・client_secret が出ないことを、偽の値で固定。
