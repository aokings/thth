本書は契約。実装は Codex。裁定は §8。§0 の要件は masaru の追記待ち（枚数・動画の長さ・頻度）——**空欄のまま着手してよい**。

## 0. 要件（masaru・2026-09-20 夜）

**「投稿できるものは全て thth が投稿できないと変」**（masaru）。要件は「画像と動画」ではなく、**各媒体の公式 API が 1 投稿に付けられるものすべて**。

- 対象媒体: thth が adapter を持つ全部（Threads・Bluesky・Mastodon。X は 2.14.0 の adapter と同時にこの規律を適用）。
- 対象の種類: 媒体ごとに Codex の実装前照合で**一次資料から網羅表を作る**（画像・複数画像・動画・GIF・音声・alt・リンクカード・引用・投票・場所など、API が受け付けるもの全部）。表の各行は「2.13.0 で出す」か「出さない理由（API に無い・承認ページで見せられない・費用）」のどちらかを持つ。**理由なく落とす行を作らない。**
- 枚数・長さ・大きさの上限は媒体の上限をそのまま使う（thth が独自に狭めない）。超えるときは lint で断り、**自動で縮めない**（§1 の「原稿は人が見たまま出る」規律）。
- 1 日の本数の上限は設けない（既存の予算・承認の規律で足りる）。

## 0.1 網羅の規律（この版で足す）

- `thth doctor`／`handoff-report` の `tool` に **媒体ごとの「出せるもの」表**を載せる（LLM が「この媒体に動画は出せるか」を推測でなく道具に聞ける）。
- 出せない種類を原稿に書いたら lint が **その媒体名と種類と理由** で断る（`unsupported_attachment: threads/audio` のような静的な理由コード）。
- 検収依頼には媒体ごとの網羅表と、各行の実測（実 API か record／replay）を付ける。

## 1. 原則（変えない）

1. **添付も承認の対象。** 一段目は本文と添付の一覧（ファイル名・種類・サイズ・寸法／秒数・alt・sha256 の先頭 12 桁）を見せ、**digest にファイルの sha256 と alt を含める**。承認後に差し替えた添付は出ない（`approval_stale`）。
2. **承認ページは添付を見せる。** 画像はそのまま、動画は長さと先頭フレーム（作れなければ「動画 mm:ss」と sha256）。人が見ていないものを承認させない。
3. **alt は必須。** 無ければ lint で loud reject（`alt_required`）。
4. **元ファイルを台帳に残さない。** 残すのは sha256・種類・寸法／秒数・alt・媒体側の ID／URL。
5. 秘密・分母・null＋理由・記録の規律はそのまま。

## 2. 原稿の書き方（自分の repo を持つ project）

front matter に `media:` を足す（1 投稿 4 点まで・画像と動画は混ぜない・媒体の上限に従う）:

```yaml
media:
  - file: docs/sns/media/2026-09-21-tea.jpg
    alt: 湯呑みに注いだ玉露。淡い緑。
  - file: docs/sns/media/2026-09-21-tea-2.jpg
    alt: 茶葉の拡大。
```

- `file` は repo 内の相対パス（`..` 不可・symlink 不可・sha256 を lint が計算して `approved_sha` の材料に）。
- `thth lint`／`preview`／`approve` の一段目に添付の一覧が出る。`thth send --media <path> --alt <文>`（複数可）も同じ扱い。
- 連投（`thth: 2`）は各段に `media:` を持てる。

## 3. 招待者（サーバ型）の入口

- MCP でバイナリは送らない。`thth_media_upload_url`（利用者 scope・書く資格情報）が **一回限りのアップロード URL**（thth.me の Worker→R2・10 分・種類とサイズの上限付き）を返し、利用者が curl かブラウザでファイルを置く。Worker は sha256・種類・サイズ・寸法を記録し、`media_id`（= sha256）を返す。
- `thth_draft_put` の `media: [{media_id, alt}]` で下書きに付ける。サーバは R2 から取り寄せて repo の `docs/sns/media/<sha256>.<ext>` に置き（managed repo）、front matter を書く。以後は §2 と同じ。
- アップロードした人と使える account を紐づける（他人の account には付けられない）。承認されなかった添付は 10 分で R2 から消える。

## 4. 媒体ごとの出し方（一次資料は Codex の実装前照合で固定）

| 媒体 | 方式 | 制約 |
|---|---|---|
| Threads | 公開 URL（`media_type: IMAGE|VIDEO|CAROUSEL`・`image_url`／`video_url`）。container を作り、動画は `status` を poll してから publish。GIF・リンク添付・引用・場所など API が受けるものは網羅表で扱う | 画像 8MB・動画は処理待ち・CAROUSEL は API の上限のまま（§0・thth で狭めない） |
| Bluesky | `com.atproto.repo.uploadBlob` → `app.bsky.embed.images`（alt 必須）・動画は `app.bsky.embed.video`（上限と処理待ちは照合で固定）・リンクカードや引用など embed の他の型も網羅表に | 画像 1 枚 1MB 以下（超えるときは lint で断る・**自動縮小はしない**）。**動画もこの版**（§0） |
| Mastodon | `POST /api/v2/media`（`description`=alt）→ `media_ids`。画像・動画・GIF・音声のほか投票（`poll`）など status API が受けるものは網羅表で扱う | instance の上限を `instance` API で読む |

公開 URL は thth.me の R2（`/m/<sha256>.<ext>`・**承認から公開までの間だけ**有効・公開後 24 時間で削除・Threads 側にコピーされる前提）。`Cache-Control: no-store`・列挙不可・sha256 を知る者だけが読める。

## 5. 記録と観測

- sent／insights の行に `media: [{sha256, kind, alt_present, remote_id}]`。本文と同じく元ファイルは残さない。
- `analytics-report --by kind` の `kind` に `image`／`video`／`carousel` を足す（媒体をまたいで足さない）。
- 承認ページの表示は 10 分の論理保存（2.12 と同じ）。R2 の物理消去は約束しない。

## 6. 秘密と隔離

- R2 の資格情報は Worker の binding だけ。VM は署名付き request（2.12 の骨）で一回限り URL を発行する。
- アップロード URL は本人にだけ返す（承認 URL と同じ例外）。ファイルの中身を stdout／ログに出さない。
- 種類は magic bytes で判定（拡張子を信じない）。SVG・HTML など実行可能な形式は拒否。EXIF の位置情報は**落とす**（公開前に strip・裁定 §8）。

## 7. 順番と検収

1. 原稿の `media:`・lint・digest（§1・§2）——自分の repo の project で。VM は read-only。
2. Mastodon → Bluesky（画像）→ Threads（画像・R2）→ Threads（動画）→ Bluesky（動画）→ 網羅表の残り（GIF・音声・投票・リンクカード・引用など、媒体ごと）。順番は段取りであり、**範囲は §0 の全部**。
3. 承認ページの表示（§1-2）。
4. 招待者の入口（§3）。
5. 記録と観測（§5）。
- 実機: masaru の承認で kopicha か masaru の account に、媒体ごとに網羅表の各行 1 本ずつ（画像・動画は必須。他は API が record／replay で確かめられるなら実機は 1 本に絞ってよい）。
