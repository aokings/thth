## 1. 目的

実店舗の持ち主が、店の事実（営業の時間・臨時の休み・催し・店頭の品）と思いを台帳に 1 回書けば、そこから

1. SNS に出す下書きが、間違った事実を載せずに作られ、
2. 店の情報が載っている外の場所（Google マップ・食べログなど）に貼る文もそろい、
3. 足りない事実と思いは、聞かれて答えるだけで台帳に貯まる

ようにする。レジの口は、この流れの一部（新しい品・再入荷）を自動で埋める助けで、主役ではない。ここは叩き台の見立て（持ち主が書く行が主・口から取り込む行が従）と同じ。

## 2. できあがりの条件（何ができたら「実店舗に使える」と言えるか）

次の 6 つが、本物の店 1 つで、証拠つきで言えたとき。レジの口と Google への出し先は条件に入れない（あれば楽になる物で、無くても使える形を先に作る）。

| 番号 | 条件 | 証拠 |
|---|---|---|
| 1 | レジの口の無い店が、台帳だけで 4 週間回った | 台帳の repo の commit の並び・その間に出た投稿の一覧 |
| 2 | 営業の時間・臨時の休み・催し・品の 4 種類が、どれも「本人が認めた」の行として 1 件以上入り、3 種類以上のきっかけから 下書き → 承認 → 投稿 まで通った | 下書きの頭の出所（台帳の行の番号と commit）と、出た投稿の URL |
| 3 | 間違った事実が出ない柵が、わざと壊して赤になった（推測の行・見直し日を過ぎた行・承認の時に変わっていた行・終わった催し・出さない印の欄） | 試験の名前と、壊したときの赤い出力 |
| 4 | 臨時の休み 1 件で、SNS の下書きと、外の場所ごとの貼る文がそろい、持ち主が「貼った」と記録できた | 台帳の「外の場所」の行の合わせた日 |
| 5 | 持ち主に聞いた問いの数と、答えが返った数が記録にあり、持ち主が「多すぎる」と言っていない | 問いの記録・持ち主の一言 |
| 6 | privacy の文・店主向けの 1 枚・コードが一致している。`thth leave` で実店舗の分が消える | `tests/test_privacy_matches_code.py` と leave の試験 |

「誰が回す道具か」も書いておく。最初の版は BASE のときと同じで、**店主が自分で使う道具ではなく、masaru が身近な店を代わりに回す道具**になる見込み。店主が自分の LLM で回す形は、この 6 つが言えてから考える。

## 4. 最初の使い手（見立て）

2 つに分けて考えるのがよい。

**台帳の機械の土台（段 1）は、自前のメディアで回す。** 構想 §9 の 5（masaru「今我々が運営しているメディアでも十分有効な仕組みにしてね」「最初に回すのは自前のメディアで、店はその次」）のとおり。候補は kopicha。repo の文書から読める範囲では、kopicha は SNS の口座（Threads と X）と材料の台帳（claims.csv）を持つメディアで、事実の層が既にあり、思いの層（編集の考え・扱わないこと）を足す形が素直に試せる【読んで確かめた範囲: `docs/構想_5.0_届けるシナリオ_2026-10-23.md`】。kopicha の repo は kopicha の本線の持ち場なので、THTH開発は書かない。「台帳の形を 1 つ置いて点検を回してほしい」と hub msg で頼む形になる。

**実店舗の形（段 2 から）は、本物の店が要る。** 営業の時間・臨時の休み・催しは、メディアには無い。机の上で作ると、聞く問いと柵の線が実物とずれる（構想 §6「実物から起こす」）。

ここで分からないことが 1 つある。**kopicha や masaru の家族の店に、実店舗（か、店頭に立つ機会）があるかを、私は repo から確かめられなかった。** 設計の書にあるのは「家族の BASE の店」までで、店頭があるとは書かれていない。見立てを 3 つの場合に分ける。

| 場合 | 最初の実店舗の使い手 | 理由と代償 |
|---|---|---|
| 身近に常設の実店舗がある（家族・知人） | その店。masaru が代わりに回す | いちばんよい。段 0 でレジと外の場所を聞く。店主の了承の 1 枚が要る |
| 常設の店は無いが、家族の BASE の店が催事やマルシェに出ることがある | 家族の店。「催し」と「その日だけの営業の時間」の形だけを先に回す | 今の `thth shop`（BASE）の利用者のまま、実店舗の形の半分（催し・臨時）を実物で試せる。営業の時間・定休日・外の場所は試せないので、§2 の条件はそろわない |
| どちらも無い | 段 1 で止める | 作れるが作らない。実物の無いまま段 2 を作ると、柵の線が机の上の物になる。代償は実店舗が遅れること |

推しは、**段 1 を kopicha で回し始めるのと並べて、段 0 で実店舗の候補を masaru に聞く**こと。これは判断というより事実の問いなので、§7 の割れる判断の 1 にまとめた。

## 5. 段ごとの計画

### 段 0: 最初の店を決めて、実情を聞く（コードなし）

- **入る物**: 最初の実店舗を 1 つ決める。店に聞く 5 つ（どのレジか・店の情報がどこに載っているか（Google マップ・食べログ・ホットペッパー・Instagram など）とそれぞれの管理画面を誰が持つか・いま発信でいちばん困っていること・営業の時間と休みを今どこに書いているか・店と家が同じ場所か）。店主向けの 1 枚の下書き（読む物・読まない物・聞かれる数・住所と電話の扱い・誰が代わりに回すか）
- **入らない物**: コード・アカウント・鍵・申請
- **柵**: 無い（文書だけ）
- **privacy と規約に足す文**: まだ足さない（無い機能を公開の約束に書かない・原則 庭 §2 の 1 と同じ考え）
- **確かめ方**: 聞いた 5 つの答えが `docs/` の 1 枚にある。店主向けの 1 枚を店主が読んだ
- **次へ進む条件**: 店が決まるのを待たずに、段 1〜4 を見本の店（架空の飲食店 1 つと物販 1 つ・試験の材料と例の台帳に置く）で作る（masaru 2026-11-13「実店舗決まるの待ってたら出来るわけないじゃん」）。段 0 は本物の店が見つかったときに行い、店が 1 つ決まって店主が「代わりに回してよい」と言ったら、§2 の条件の確かめ（本物の店で 下書き → 承認 → 投稿）に入る

### 段 1: 台帳の機械の土台（自前のメディアで回す）

叩き台は手の台帳を `thth shop` の種類 `manual` として入れる案だった。ここは変える。台帳の点検と印の柵は実店舗だけの物ではなく、構想 §5 と §9 の 4 の「台帳の機械」そのものなので、**店にもメディアにも共通の土台として作り、実店舗は段 2 でその上に「形」を足す**（違いと理由は §8 の 2）。

- **入る物**:
  - 台帳の形の点検（構想 §5 の `thth register check`（仮））: 1 行 1 枚の .md・頭の項目の番号・状態・由来・見直し日・出してよいかの印
  - 3 つの印（推測・本人が認めた・本人が違うと言った）と、印を付け替える**認める操作**。印は手で書き換えても通ってしまうので、認めた記録（どの行の・どの中身を・いつ）を機械が別に持ち、行の中身が変わったら「認めた」が外れる形にする（中身の指紋を持つ・今の承認の指紋と同じ考え）
  - 柵の関数 1 つ: 「この行は中身の材料に使えるか」（推測でない・違うと言われていない・見直し日を過ぎていない・出してよい印がある・認めたあと中身が変わっていない）。使えないときは前向きな断り（なぜ・通る直し方・より良くする一手）
- **入らない物**: 実店舗の形・きっかけ・下書き・聞く流れ・`thth sync`・庭・網に出る物すべて
- **柵**: 形の点検の試験。印の柵の試験（推測の行は使えない・中身を変えたら認めたが外れる）。断りの符丁に 3 つの欄がそろう試験（今の `tests/test_refusal_catalog.py` に乗る）。新しいファイルが網の部品を import しない試験（今の `tests/test_store_base_audit.py` と同じ形）。作ったら一度わざと壊して赤を見る
- **privacy と規約に足す文**: 「台帳は持ち主の手元にあり、THTH の運営者は預からない。THTH が台帳に書くのは頭の項目の決まった欄だけ」。網に出ないので、足すのは外の人に配る版から
- **確かめ方**: kopicha（か別の自前のメディア）の台帳の行 10 枚ほどで点検が通り、推測の行を材料に引くと断られるのを、その repo の担当が動かして確かめる
- **次へ進む条件**: 自前のメディア 1 つで点検が 1 週間回り、形の直しの求めが止まった。段 0 の店が決まっている

### 段 2: 実店舗の形と、きっかけから下書き（レジの口なし）

- **入る物**:
  - 実店舗の行の種類（叩き台 §4.1 の形を元に）: 店・営業の時間・臨時・催し・品・思い。営業の時間の本文の形の点検（時刻の形・曜日の抜け・日をまたぐ書き方）
  - 暦と台帳から出るきっかけ（叩き台 §6.1）: 臨時の休みが近い・催しが近い・営業の時間が変わる・店頭の新しい品（持ち主が `品/` に 1 枚足した）・季節の品の始まり
  - きっかけから下書き 1 本ずつ（今の `draft.py` と同じく、承認されていない queue の下書き・1 回に 1 本か上限 3 本）
  - 下書きの頭に、台帳の行の出所（番号と commit）と**出さない期限**（臨時は休みの日の終わり・催しは終わりの時刻）。期限を過ぎた下書きは承認でも予約でも断る
  - 承認の確定の段で台帳を読み直す（今の `recheck.py` の延長）: 行が変わった・認めたが外れた・退役した、なら断る
  - 営業の時間と臨時の休みの行だけは、認める操作を二段確認にする（間違えたときの害が大きい・叩き台 §4.3 の案のまま）
- **入らない物**: レジ・Google・外の場所の頁を読むこと・口コミ・お客さんの写った写真を選ぶこと・臨時の休みの理由を本文に書くこと（既定で書かない）・「今日やっています」のような毎日の自動の投稿（事実の変化が無い日に出す物は作らない）
- **柵**: §2 の条件 3 の 5 つの試験。住所・電話は既定で出さない試験。終わった催しの下書きが通らない試験。危ない領域の表（`tools/release_gate.py` の `DANGER_AREAS`）に新しいファイルを足す（下書きを作る口なので監査が要る）
- **privacy と規約に足す文**: 「店の事実（営業の時間・休み・催し・品）は持ち主が台帳に書いた物だけを使う。THTH は店の頁やレジを読まない（この版）。住所と電話は既定で外に出さない。写真は持ち主が選んだ物だけ」。店主向けの 1 枚に「臨時の休みの理由は既定で書かない（店と家が同じ場所だと、家が空く知らせになる）」
- **確かめ方**: 本物の店の台帳で、臨時の休み 1 件・催し 1 件・品 1 件を 下書き → 承認 → 投稿 まで通す。出た投稿の URL と、下書きの頭の出所を突き合わせる。画面の写しを取る
- **次へ進む条件**: 3 種類のきっかけで投稿が出た。間違った事実の投稿が 0。店主が「この形で続けてよい」と言った

### 段 3: 聞いて埋める

- **入る物**: 穴の一覧（営業の時間が無い・見直し日が過ぎた・12 月に入って年末年始の 1 枚が無い・品に思いの 1 枚が無い）。問いの記録（どの穴に・いつ・何を聞き・どう答えたか）。同じ穴を続けて聞かない間（機械が数える）。季節の問い（年末年始・お盆・大型連休）。推す・聞く言葉は持ち主の LLM が書く（構想 §9 の 4 の分け方）
- **入らない物**: THTH が持ち主に直接知らせを送ること（LINE・メールなど。聞くのは持ち主の LLM との会話の中だけ）・答えから自動で「認めた」にすること（営業の時間と臨時は認める操作を通す）
- **柵**: 上限を超えた問いは出ない試験。「違う」と言われた推測を二度聞かない試験。会話の一言だけでは営業の時間と臨時が「認めた」にならない試験
- **privacy と規約に足す文**: 「聞いた問いと答えは持ち主の台帳に残る。運営者は預からない」
- **確かめ方**: 2 週間回して、問いの数・答えの数・答えから増えた行の数を数える。店主に「多いか」を聞く
- **次へ進む条件**: 聞いた答えから作った行で投稿が 1 本出た。上限の数を実績で決め直した（叩き台の「1 日 3 問・7 日空ける・3 週間前」は、忙しい店主には 1 日ごとより週 1 回にまとめるほうが合うかもしれない。数は決め打ちにせず、ここで測って決める）

### 段 4: 外の場所に手で貼る束

叩き台は Google ビジネス プロフィールを「出し先」として後の段に置き、ほかの外の場所は扱っていなかった。ここは足す。実店舗の持ち主の手間は「同じ休みの知らせを、あちこちに直しに行くこと」にあり、**API を 1 本も使わずに、その手間を半分にできる**から。

- **入る物**:
  - 台帳に「外の場所」の行: 店の情報が載っている場所ごとに 1 枚（場所の名前・店の頁の URL・管理画面を誰が持つか・最後に台帳と合わせた日）
  - 営業の時間・臨時・催しが変わったとき、場所ごとの**貼る文**（その場所の欄の形と字数に合わせた文）と、**貼ったかの点検表**を出す。持ち主が自分の管理画面で貼り、「貼った」と記録する
  - 見直し日を過ぎた場所は「合っているか見てください」と穴の一覧に出す。持ち主が外の場所の今の文を自分で写して貼れば、台帳と比べてずれを見せる（叩き台 §10.1 の A'）。ずれたとき、どちらが正しいかは機械が決めず、持ち主に聞く
  - まだ貼っていない場所は、毎朝の 1 枚に 1 行残す（叩き台 §10.2）
- **入らない物**: THTH が外の場所の頁を読むこと・ホットペッパーグルメの公開の API で読んで比べること（叩き台 §10.1 の A。理由は下）・管理画面に入ること・店主の ID とパスワードを預かること・口コミを読むことと返すこと・予約や空席の連動。THTH が「合っている」と言うこと（確かめるのは持ち主の目）
- **柵**: 外の場所の行の URL へ THTH が網で出ない試験（この段のコードが網の部品を import しない）。推測の行から貼る文が出ない試験。貼る文に出さない印の欄が入らない試験
- **privacy と規約に足す文**: 「THTH は食べログ・ホットペッパー・Google マップなどの頁を読まず、管理画面にも入らない。貼る文を作るだけで、貼るのは持ち主」
- **確かめ方**: 臨時の休み 1 件で、2 つ以上の場所の貼る文が出て、持ち主が貼って記録するまでを 1 回通す
- **次へ進む条件**: §2 の 6 つがそろった。ここで「実店舗に使える」と言える。段 5・6 は、ここまでで「手で書くのが手間」「Google に貼るのが手間」と実際に言われた物だけを作る

手で貼る形にする理由（原文・§9）: 食べログの店舗会員規約はアカウントを第三者に譲渡・貸与・開示してはならないとしている。食べログの利用規約は営利を目的としたアクセスと、情報の複製や保管を、同意なしではできないとしている。Retty も無断の複製・転載と、競合するサービスのための情報収集を禁じている。どれも「自動で取る」という語は無いが、THTH が読みに行く形も管理画面に入る形も、線の外に出るおそれが高い。貼る文を作って持ち主が貼る形なら、どの規約にも触れない。

ホットペッパーグルメの API で読んで比べる形（叩き台 §10.1 の A）を入れない理由: API の決まりの頁に「飲食店から金銭等の対価を得るビジネスに関わるサイトでの利用を禁止」とあり、THTH に有料の版ができると当たりうる。叩き台が挙げた利用規約の「加工をしない・24 時間で更新か削除」の読みも割れる。読めるのは 1 つの場所の営業の時間と定休日だけで、臨時の休みは読めない。得る物が小さく、確かめる物が多い。持ち主が自分で写して貼る形（A'）で同じことができるので、そちらで足りるかを先に実物で見る。
