公式の頁（10/16 に開いた）:

- **AtomPub**（https://developer.hatena.ne.jp/ja/documents/blog/apis/atom）: OAuth は `read_private`・`write_private`。入口は `https://blog.hatena.ne.jp/<はてなID>/<ブログID>/atom`、記事は `…/atom/entry`（POST → 201・`Location` に member URI）、個別は `…/atom/entry/<entry_id>`（GET 200・PUT 200・DELETE 200）。名前空間は Atom・`app`（`http://www.w3.org/2007/app`）・`hatenablog`（`http://www.hatena.ne.jp/info/xmlns#hatenablog`）。送る XML は `title`・`author/name`・`content type="text/plain"`（**本文はブログに設定した記法として解釈される**）・`updated`（任意）・`category term`（複数可）・`app:control/app:draft`（yes/no）・`app:preview`・`hatenablog:scheduled`・`hatenablog:custom-url`。返る XML は `id`（`tag:blog.hatena.ne.jp,2013:blog-<はてなID>-…`）・`link rel="edit"`・`link rel="alternate" type="text/html"`（公開 URL）・`published`・`app:edited`・**`content` の `type` がブログの記法を映す**（`text/html` 見たまま・`text/x-hatena-syntax` はてな記法・`text/x-markdown` Markdown）・`hatena:formatted-content type="text/html"`（整形済み）・`app:control`。一覧（`GET …/atom/entry`）は 7 件ずつ・`link rel="next"`。カテゴリは `GET …/atom/category`。エラーは 400（XML の不備）・401・404・405・500。**回数の上限の記述は無い。** PUT は元の記法を保つ。`scheduled` は POST だけに書かれている。
- **OAuth**（https://developer.hatena.ne.jp/ja/documents/auth/apis/oauth/consumer）: request token は `POST https://www.hatena.com/oauth/initiate`（**hatena.com**）に `scope` を form の body で（`read_public%2Cread_private` のように `,` 区切り）。認可は `https://www.hatena.ne.jp/oauth/authorize?oauth_token=…`（スマホは `/touch/oauth/authorize`）。access token は `POST https://www.hatena.com/oauth/token` に `oauth_token`・`oauth_verifier`。`oauth_callback` に `oob` を渡すと**画面に `oauth_verifier` が出て、人がアプリに打つ**。署名は `HMAC-SHA1`（例にあるのはこれだけ）。access token の応答は `oauth_token`・`oauth_token_secret`・`url_name`・`display_name`。**期限の記述は無い。** API は `Authorization: OAuth realm="", oauth_consumer_key, oauth_nonce, oauth_signature, oauth_signature_method, oauth_timestamp, oauth_token, oauth_version="1.0"`（RFC 5849）。

## 2. 認証

### 2.1 方式: OAuth 1.0a にする（WSSE は作らない）

| | OAuth 1.0a | WSSE |
|---|---|---|
| 公式の推し | 新規のアプリは OAuth（手順 §参考） | 使えるが古い |
| 秘密の種類 | consumer key／secret＋token／secret | はてな ID＋API キー |
| S3（フォトライフ）・S4（ブックマーク） | **同じ token で通る**（ブックマークは OAuth だけ） | ブックマークは通らない。秘密が 2 種類になる |
| 手間 | 署名を自前で書く（60 行ほど・§2.2） | ヘッダ 1 本 |

**OAuth にする。** 理由は、S4 のブックマークが OAuth しか無いので、どのみち要る。秘密を 2 種類持つ理由が無い。主体の台帳の `auth` は `oauth`／`wsse` を受ける形（S1）のまま残すが、S2 の adapter は `wsse` を `auth_unsupported` で断る（作らない。要るときに別の設計で足す）。

### 2.2 署名 `thth/oauth1.py`（新・標準ライブラリだけ）

`pyproject` の `dependencies = []` を守る（requests_oauthlib を足さない）。要るのは `hmac`・`hashlib`・`secrets`・`time`・`urllib.parse`・`base64` だけ。

```
percent_encode(s) -> str                       # RFC 5849 §3.6（英数と -._~ 以外を %XX・大文字）
base_string(method, url, params) -> str        # §3.4.1（query・body・oauth_* を全部集めて鍵と値を encode → 並べ替え → & 連結）
sign_hmac_sha1(base, consumer_secret, token_secret) -> str   # §3.4.2（鍵は `encode(cs)&encode(ts)`・base64）
authorization_header(*, consumer_key, consumer_secret, token=None, token_secret=None,
                     method, url, body_params=None, extra_oauth=None,
                     nonce=None, timestamp=None) -> str      # `OAuth realm="", …`（§3.5.1）
```

- `url` は scheme・host を小文字に・既定のポートを落とし・query を外した形を base に使う（§3.4.1.2）。query と `application/x-www-form-urlencoded` の body の鍵と値は base に入れる（§3.4.1.3）。XML の body は入れない。
- `nonce` は `secrets.token_hex(16)`、`timestamp` は `int(time.time())`。試験は固定の値を差し込む。
- **固定の答え**: RFC 5849 §3.4.1.1 の例（`POST http://example.com/request?b5=…`）の base string と署名を golden にする（実装者が RFC の原文から写す。推測で書かない）。`percent_encode` は `~` を encode しない・空白は `%20`・`*` は `%2A` を 1 つずつ縛る。
- 時計がずれると署名が断られる（401）。VM は NTP なので S2 では見ない。401 が出たら §12 の 2 で時計を疑う行を残す。

### 2.3 秘密のファイル（主体に 1 本ずつ・0600・`~/.config/thth/`）

| ファイル | 中身 | 書く口 |
|---|---|---|
| `consumer`（`~/.config/thth/hatena-masaru.consumer`） | `{"schema": "thth.hatena-consumer/1", "consumer_key": "…", "consumer_secret": "…"}` | `thth principal auth`（1 段目） |
| `token`（`~/.config/thth/hatena-masaru.token`） | `{"schema": "thth.hatena-oauth/1", "hatena_id": "masaru-aoki", "oauth_token": "…", "oauth_token_secret": "…", "scopes": ["read_public", "write_public", "read_private", "write_private"], "obtained_at": "2026-10-…T…+09:00"}` | `thth principal auth`（3 段目・`principals.write_token`＝`token.lock` の中） |

- 読むのは `accounts.load_token(account_cfg)`（口座の `token` は主体と同じパスを loader が強制している・S1 §3.3）と `principals.load_principal(name)["consumer"]` のパス。**期限が無いので更新の道は作らない**（`maintain` は触らない。`_refresh_x_if_due` の形は使わない）。はてなが token を失効させれば 401 で出ない側に倒れ、`thth principal auth --force` でやり直す。

## 3. adapter `thth/adapters/hatenablog.py`

### 3.1 置き場と口

- 置き場は `thth/adapters/hatenablog.py`（他の媒体と同じ場所）。ただし `base.Adapter` は**継がない**——口が違う（`publish(Post)` ではなく `create_entry(title, body, …)`）し、core は `media == "hatenablog"` で `hatena_publish` に分岐している（`core.py` 556 行）。`adapters/__init__.py` の `REGISTRY` にも**載せない**（`observe`・`collect`・`doctor` の probe が `make_adapter` で作ろうとして `UnknownMedium` になる経路は、S1 のまま「はてなの口座では読む口が無い」で正しい。`doctor` の probe は §3.7）。
- 差し込みは `hatena_publish.ADAPTER_FACTORY = hatenablog.factory`（`thth/hatena_publish.py` の import 時ではなく、`thth/adapters/hatenablog.py` の末尾でもなく、**`core` が `hatena_publish` を呼ぶ直前**で `hatena_publish.ADAPTER_FACTORY or hatenablog.factory` と解決する。試験が `adapter_factory=` で差し替える経路はそのまま）。
- `factory(account_cfg, principal_cfg) -> HatenaBlogAdapter`。中で `accounts.load_token(account_cfg)`（None → `token_missing`）・`principal_cfg["consumer"]` を読む（無い → `consumer_missing`・`schema` が違う → `token_invalid`／`consumer_invalid`）・`principal_cfg.get("auth", "oauth") != "oauth"` → `auth_unsupported`。どれも `hatena_publish.AdapterUnavailable(code)` で上げ、`throw_chosen` は `Unsupported` と同じ場所で受けて**何も書かずに** exit 2・`action="refused"`・`error=<code>`（S2 で `throw_chosen` に足す 1 か所）。
- 口（S1 の docstring のまま・引数の名前も変えない）:

```
get_entry(*, entry_id, edit_uri) -> str                      # 今の本文（content の文字列）
create_entry(*, title, body, categories, images) -> EntryResult
update_entry(*, entry_id, edit_uri, title, body, categories, images) -> EntryResult
delete_entry(*, entry_id, edit_uri) -> EntryResult
blog_syntax() -> str | None                                   # 最新の記事の content の type（記事が無ければ None）・§5
probe() -> dict                                               # doctor と principal auth の段 7 が使う（entries・syntax・status）
```

- URL は **`hatena_id`（主体）と `blog_id`（口座）だけ**から組む（S1 §5.2 の 7）: `https://blog.hatena.ne.jp/<hatena_id>/<blog_id>/atom/entry`。`edit_uri` は台帳にあっても**使わない**——`entry_id` の末尾の数字（`tag:…-<数字>` の最後の `-` のあと）から `…/atom/entry/<数字>` を組む。台帳の `edit_uri` と組んだ URL が違えば `edit_uri_mismatch` で出ない側（台帳を信じて別のブログへ PUT しない）。`images` は S2 では空しか来ない（§4.3）。空でなければ `images_unsupported`（断り・出ていない）。

### 3.2 HTTP の作法

- `urllib.request.Request(url, data=body, method=…, headers=…)` → `httpsafe.urlopen(req, timeout=…)`（同一 origin のリダイレクトだけ・平文不可・proxy 不可・leave_gate の lease）。x.py の `request` と同じ形で、`_request(method, path, *, body=None, content_type=None) -> (status, headers, bytes)` を 1 つ持つ。
- ヘッダ: `Authorization`（§2.2）・`Accept: application/atom+xml`・`Content-Type: application/atom+xml; charset=utf-8`（POST・PUT）・`User-Agent: thth/<版> (+<user_agent_contact>)`（主体の台帳の `user_agent_contact`・既定 `https://thth.me/`。はてなは User-Agent の無いアクセスを制限しうる・調べ §2）。
- 時間切れ: GET 30 秒・POST／PUT／DELETE 60 秒（`min(口座の timeout, これ)`）。
- 応答の上限 4 MiB（`hatena:formatted-content` が本文の倍になるので 1 MiB では足りない可能性）。超えたら `response_too_large`（分からない側）。
- **再試行はしない**（書き込みは 1 回。timer の次の run が次の原稿を見る）。adapter の中で sleep しない。読む側の間隔（数秒）は S4・S5 の呼び手が守る。
- 例外の文は `redact.redact` を通してから `EntryResult.error` に入れる（Authorization の値が文に混ざる経路を作らない）。

### 3.3 送る XML の作り（`xml.etree.ElementTree`）

```xml
<?xml version="1.0" encoding="utf-8"?>
<entry xmlns="http://www.w3.org/2005/Atom" xmlns:app="http://www.w3.org/2007/app">
  <title>アラビカの値動き（2026 年 10 月）</title>
  <author><name>masaru-aoki</name></author>
  <content type="text/plain">…変換したあとの本文…</content>
  <category term="コーヒー" />
  <category term="価格" />
  <app:control><app:draft>no</app:draft></app:control>
</entry>
```

- `content` の `type` は **`text/plain`**（公式の例のまま。本文はブログの記法として解釈される）。`text/x-markdown` を送る試みは実機の確かめに回す（§12 の 5）。
- `updated` は**書かない**（create は今の時刻＝timer が出した時刻。update で書くと日付が動く恐れ。実機で確かめる・§12 の 7）。
- `app:draft` は常に `no`（S1 の指紋の 14 番）。`app:preview`・`hatenablog:scheduled`・`hatenablog:custom-url` は**書かない**（要素そのものを作らない。将来の `custom_url:` は別の承認）。
- 文字列は ET がエスケープする。制御文字は `queuefile.find_control_char` が材料の段で断っている（S1）。`ET.tostring(root, encoding="unicode")` の前に `ET.register_namespace("app", …)`。
- PUT も同じ XML（`entry_id` は URL で指す。`id` 要素は書かない）。DELETE は body 無し。

### 3.4 応答の読み（正規化）

`parse_entry(bytes) -> dict` を 1 つ。名前空間は Atom・`app`・`hatena`（`http://www.hatena.ne.jp/info/xmlns#`）・`hatenablog`。

| 欄 | 元 | 無いとき |
|---|---|---|
| `entry_id` | `atom:id` の文字列（`tag:blog.hatena.ne.jp,2013:blog-…` の形。`postid.is_usable` が通るか） | `response_invalid` |
| `edit_uri` | `atom:link[@rel="edit"]/@href` | `response_invalid` |
| `published_url` | `atom:link[@rel="alternate"][@type="text/html"]/@href`（無ければ `rel="alternate"` の最初） | None（create なら `response_invalid`） |
| `content` | `atom:content` の文字列（`type` も `content_type` に） | `""`・`content_type` None |
| `draft` | `app:control/app:draft` の文字列（`yes`／`no`） | None |
| `title`・`categories`・`edited`・`published` | それぞれ | None・`[]` |

- XML が読めない（`ET.ParseError`）・根が `atom:entry` でない → `response_invalid`。
- expat の entity 展開の守りは Python 3.10 以上の expat（2.4.1 以上）に任せ、応答の上限 4 MiB で押さえる（`defusedxml` は足さない）。`DOCTYPE` があれば `response_invalid`（AtomPub の応答に DTD は来ない）。

### 3.5 断りと結果不明の分け方（`EntryResult` への写し）

| 起きたこと | `ok` | `ambiguous` | `error` | 台帳（`hatena_publish` の扱い） |
|---|---|---|---|---|
| POST 201・読めた・`entry_id` あり・`draft=no` | 真 | — | — | `published` |
| POST 201・読めた・`draft=yes`（下書きになった） | 偽 | **真** | `hatena_draft_unexpected` | `unknown`（出たかもしれない。人が見る） |
| PUT 200・読めた | 真 | — | — | `published` |
| DELETE 200 | 真 | — | — | `deleted` |
| 2xx だが XML が読めない・`entry_id` が無い・期待と違う状態番号（200 の POST 等） | 偽 | 真 | `response_invalid`／`hatena_http_<code>` | `unknown` |
| 400 | 偽 | 偽 | `hatena_http_400`（XML の不備） | 元の状態に戻す |
| 401・403 | 偽 | 偽 | `hatena_auth_rejected` | 元の状態。run のログに `thth principal auth <p> --force` を案内 |
| 404（update・delete・get） | 偽 | 偽 | `hatena_entry_missing` | **`conflict`（理由 `entry_missing`）**——外で消された記事に PUT／DELETE を打ち直さない。S1 の `BEFORE`（`published` に戻す）はここだけ変える（§15 の 5） |
| 405 | 偽 | 偽 | `hatena_http_405` | 元の状態 |
| 429・その他の 4xx | 偽 | 偽 | `provider_rate_limited`／`hatena_http_<code>` | 元の状態 |
| 5xx | 偽 | 真 | `hatena_http_<code>` | `unknown` |
| 時間切れ・`URLError`・`OSError`・接続断 | 偽 | 真 | `hatena_transport_failed` | `unknown` |
| `EndpointRejected`（接続の前に止めた） | 偽 | 偽 | `endpoint_rejected` | 元の状態 |
| 書き込みの `RedirectBlocked`（別ホスト・格下げの 3xx を追わずに止めた。要求は届いている） | 偽 | **真** | `redirect_blocked` | `unknown`（10/16 監査 中-1 で直した） |
| 応答が大きすぎる | 偽 | 真 | `response_too_large` | `unknown` |
| 公開 URL のホストが `blog_id` と違う | 真 | — | — | S1 のまま `conflict`（`published_elsewhere`） |

- 「4xx は出ていない」は X・Mastodon と同じ線。**POST の 201 が読めなかったときは出ている可能性があるので `unknown`**（inflight が残り、人が `thth inflight <口座> resolve` で解く。S5 の reconcile が一覧を読んで候補を出す）。
- `get_entry` は `hatena_publish` が `except Exception` で `readback_failed` にしている（S1）。S2 は `get_entry` が 404 のとき `EntryMissing` を上げ、`throw_chosen` はそれだけ `conflict`（`entry_missing`）に写す。ほかの例外は今までどおり `readback_failed`（次の run でもう一度）。
- `readback_body` は 201／200 の応答の `content`（別に GET しない・§6）。

### 3.6 回数と間隔

- はてなの公式に回数の上限は無い（§1）。THTH の側の上限は S1 の 3 段（口座 3／日・主体 6／日・burst 3 件/30 分）のまま。adapter は数えない。
- 1 回の公開で送る HTTP は、create で **GET 1（記法の確かめ・§5）＋POST 1**、update で **GET 1（読み戻し）＋GET 1（記法）＋PUT 1**、delete で **DELETE 1**。記法の GET は 1 件の一覧（`?page=` 無し・7 件）で足りる。
- 429 が来たら断りとして記録し、再試行しない（調べ §5-3 の線）。主体の止めは掛けない（暴走ではない。連投の守りは burst が担う）。

### 3.7 `thth doctor` と probe

`doctor.py` 488 行のはてなの枝に、`factory` が作れるか（token・consumer の有無・schema）と `probe()`（`GET …/atom/entry`・200 か・記事の数・最新の記事の記法）を足す。probe が 401 なら「`thth principal auth <p> --force` をやり直す」、404 なら「blog_id か hatena_id を確かめる」。rc の意味は今のまま（診断はできたが×があるなら 1）。

## 4. 変換 `hatena_convert.render()`

### 4.1 形: 規則の表

```python
VERSION = "s2-rules-1"
RULES = (
    # (名前, 本文に効く関数, 実機で確かめたか)
    ("strip_front_matter",  _strip_front_matter,  "n/a"),        # 記事の先頭の --- … --- を落とす
    ("strip_leading_h1",    _strip_leading_h1,    "n/a"),        # 先頭の `# 題` が title と同じなら落とす（題が二重に出ない）
    ("absolute_links",      _absolute_links,      "n/a"),        # [text](相対) → link_base で絶対に（§4.2）
    ("images",              _images,              "s3"),         # 手元の画像は S2 では断る（§4.3）
    ("footnotes",           _passthrough,         "unverified"), # [^1] をそのまま通す
    ("tables",              _passthrough,         "unverified"), # GFM の表をそのまま通す
    ("headings",            _passthrough,         "unverified"), # ## 以下をそのまま
    ("code_fences",         _passthrough,         "unverified"), # ``` をそのまま
    ("embeds",              _passthrough,         "unverified"), # URL だけの行をそのまま（[URL:embed] には変えない）
    ("normalize",           approval.normalize_hatena_body, "n/a"),  # S1 §6.2（最後）
)
```

- `render(source_text, *, article_source, image_sha=None, base_url=None, title=None)` は `RULES` を上から順に通す**決定的な**関数のまま。`base_url` は口座の `link_base`（§4.2）、`title` は `strip_leading_h1` のため（`hatena_entry.material` が渡す。S1 の呼び手に引数を 1 つ足すだけ）。
- 3 列目は文書のための印で、**コードの動きを変えない**。実機で確かめた規則は `"ok"`／直した規則は関数を差し替え、`VERSION` を上げる。**`VERSION` を上げると承認済みの原稿は `approval_stale` になる**（本文の sha が変わるため・S1 の決め）。今は本番にはてなの原稿が無いので S2 の投入で困るものは無い。以後は、規則を変える版のリリースノートに「はてなの承認済みの原稿は再承認」と 1 行書く。
- `passthrough` を規則として並べるのは、「通した」と「見ていない」を分けて後から表を読めるようにするため。

### 4.2 相対リンク

- 口座の台帳（`accounts/<lane>-hatenablog.json`）に任意の欄 **`link_base`**（例 `https://kopicha.example/`・https だけ・`httpsafe.validated_url(base=True)` で検査）を足す。雛形 `accounts.example/hatenablog.json` にはダミー（`https://example.invalid/`）を置き、`dummy_fields` に入れる。
- `[text](rel)` の形の相対リンク（`://`・`mailto:`・`#` 始まり・`/` 始まりを除く）は、`urljoin(link_base + dirname(article_source) + "/", rel)` で絶対にする。`/` 始まりは `urljoin(link_base, rel)`。`#` だけは**そのまま**（同じ記事の中のアンカー）。
- **インライン HTML の `<a href="相対">` と自動リンク `<相対>` は、`link_base` があっても変えずに `relative_link_unresolvable` で断る**（監査の低-6 の直し `85d4cab`。`/` も `.` も無い山括弧は注記とみなして通す）。
- **`link_base` が無いのに相対リンクがある → `relative_link_unresolvable` で断る**（lint・1 段目・timer の全部。推測で貼らない）。
- `.md` で終わるリンクの拡張子は**変えない**（レーンのサイトの URL の形は THTH が知らない）。
- 画像の相対パスはこの規則では触らない（§4.3）。

### 4.3 画像（S2 ではフォトライフが無い）

選択肢: (a) `![alt](images/x.jpg)` のまま出す（壊れた画像で公開される）、(b) 画像の段だけ S3 まで止めて本文は出す（画像の行を落として出す）、(c) **画像つきの記事は S2 では断る**。

**(c) にする。** (a) は「承認した本文と違う見え方で出る」、(b) は「承認の指紋に画像が入っているのに本文から消す」で、どちらも承認した中身と出るものがずれる。断るのは lint・1 段目（`material`）・timer の 3 か所で同じ符丁 `images_unsupported_until_s3`（`hatena_entry.LINT_CODES` に足す・文は「画像つきの記事は 4.0 の S3（フォトライフ）で出せるようになります」）。他所の画像（`https://…`）は依存に数えない（S1 のまま）ので通る。S3 が入ったらこの断りを外す（`RULES` の `images` の関数を差し替えるだけ）。

## 5. ブログの記法の確かめ（計画 §3.3「Markdown でなければ断る」）

AtomPub にブログの設定を読む口は無い。分かるのは**記事の `content` の `type`**（`text/x-markdown`・`text/x-hatena-syntax`・`text/html`）だけ。しかも編集モードは記事ごとに作った時点で固まり、ブログの設定はあとで変えられる（手順 §2）。だから「最新の記事の型」が、いちばん近い代わり。

1. **主体の台帳の `blogs[].syntax`**: S2 は `markdown` だけ通す（`hatena`・`html` は `load_account` の段で `blog_syntax_unsupported`。`principals.SYNTAXES` は残すが受けるのは 1 つ）。人が「Markdown モードに設定した」と宣言する欄。
2. **送る直前**（`throw_chosen` の guard のあと・inflight の前）: `adapter.blog_syntax()`（一覧の GET・最新の 1 件の `content@type`）。`text/x-markdown` でなければ **`blog_syntax_mismatch` で断る**（出ない側・台帳は書かない・run のログに「ブログの編集モードを Markdown にしてから」）。記事が 0 件なら None＝確かめられない → 台帳の宣言を信じて進む。GET 自体が失敗したら `syntax_check_failed`（出ない側・次の run）。
3. **出たあと**: 201／200 の応答の `content@type` が `text/x-markdown` でなければ、台帳を **`conflict`（理由 `syntax_mismatch`）** にして止め、ログに「記事は出たが別の記法で解釈された。はてなの画面で確かめる」。出し直さない・消さない（人が見る）。次の公開は 2 で止まる（最新の記事がその型になるため）。
4. `thth doctor`（§3.7）と `principal auth` の段 7 で、記法を人に見せる。

これで「宣言（1）・直前の近い証拠（2）・事後の確かな証拠（3）」の 3 段になり、どれか 1 つが抜けても壊れた記事が増え続けない。

## 6. 読み戻しの正規化と「同じ」

- `readback_sha = approval.hatena_body_sha256(応答の content)`（S1 のまま: CRLF→LF・各行の末尾の空白・末尾の空白行を落とす）。**S2 では正規化を増やさない**——はてなが本文をどう返すか（空白や Unicode を触るか）は実機で見るまで分からないので、先に緩めない（§12 の 8）。
- 読み戻しの元は、create／update は **201／200 の応答の `content`**（計画 §3.3 は「公開のあと GET で読み戻し」と書くが、応答に同じ `content` が返るので GET を 1 回省く。§15 の 6）。update の**前**の比べは `get_entry`（GET）。
- 出たあと `readback_sha != body_sha256`（送った本文と返った本文が違う）なら、台帳の `published` の行に **`readback_differs: true`** を足す（欄を 1 つ足す・`MUTABLE_FIELDS` には入れない・履歴の行だけ）。`conflict` にはしない（はてなが空白を直して返すだけかもしれない）。`thth deliveries` の 1 行表示に `読み戻し差あり` を出す。実機で「常に同じ」と分かれば、後の版で `conflict` に格上げできる。
- PUT の前の「同じ」: `hatena_body_sha256(今の content) == base_readback_sha`（S1 のまま・文字どおり）。題やカテゴリの外での変更は**見ない**（S2 の範囲は本文。題を比べるのは S5 の差分の設計で）。

## 7. 記事ファイルが同期した commit と一致するかの確かめ（S1 の申し送り）

- `article_rev` は blob の sha（S1）。これに「その blob が HEAD にあるか」を足す: `git -C <repo> rev-parse HEAD:<article_source>` の値と、作業ツリーの記事の blob の sha を比べる（`hatena_entry.committed_rev(repo_dir, rel) -> str | None`・`writeback._run_git` を使う）。違う（未 commit の変更がある）・HEAD に無い（untracked）→ **`article_not_committed`**。
- 効く場所: lint（警告でなく断り）・承認の 1 段目・timer の照合（`select_problem`）。理由: 承認も公開も「どの commit の記事か」を後から言えること（計画 §0-3「正本の修正を検出できる」の土台）。timer の run は queue の repo を取り込んでから select する（`writeback` の fetch・rebase の既存の経路・読んで確かめただけ）ので、VM の作業ツリーが HEAD と違うのは誰かが VM で直接いじったときだけ。
- 台帳に `wanted_commit`（承認したときの HEAD）・`checked_commit`（出したときの HEAD）を足す（`MUTABLE_FIELDS` に 2 つ）。承認の表示に `版 a1b2c3… git（commit 9f8e7d…）` と出す。指紋には入れない（約束 §2 の決め・S1 §6.1）。
- repo でない置き場（`article_rev_kind == content`）はこの確かめをしない（`None` → 通す）。

## 8. 承認のあとに記事を直すと止まることをレーンに知らせる（S1 §14）

今: `select_problem` が `approval_stale` を返し、`held`（候補 `reapprove`）として observe・morning・board に出る（`held_category`）。run のログにも 1 行出る。`thth events` には出ない。S2 で足すのは 2 つ。

1. **`thth events` に `delivery_held`**（`events_cli.KINDS` に足す・名前を増やすだけ）: はてなの口座ごとに `select_one` を読むだけで走らせ、`held_items` の各行を `ongoing: true` の出来事にする。`ref` は `delivery`（front matter）、`summary` は「承認が古い（記事を直した）: <原稿名>・再承認は thth approve <原稿>」、`event_id = "ev_" + sha256("thth.held/1|" + account + "|" + delivery + "|" + reason + "|" + approved_sha)[:24]`（同じ止まり方のあいだは同じ id・再承認して指紋が変われば別の id）。`delivery_state_*`（conflict・unknown・inflight）も同じ型で `reason` を変える。
2. **run のログの文に次の一手**: `承認が古いので出しません: a.md（approval_stale）。記事か原稿を直した場合は thth approve docs/sns/queue/a.md --by <名前> で承認し直してください`（`throw_chosen` の 1 行を直す）。

`hub` や `h2d` へ押す口は S1 と同じく作らない（`thth events` を読む側が拾う）。

## 9. S1 監査 §15 の 3・7 の縛り

- **3（inflight を先に書き、台帳の行があと）**: `throw_chosen` の docstring の順 4 を「inflight を書く → 台帳に `inflight` の行」と**実際の順どおり**に直し、試験 T-S2-9a「inflight だけ書けて台帳に行が無い（台帳 `seq + 2 == inflight.seq`・状態 `wanted`）から `resolve not_published` → 台帳は触らず inflight だけ片づく。`resolve --published` は `seq_mismatch`」を足す（`resolve` の `never_sent` の枝をわざと消すと赤）。
- **7（試験の穴）**: T-S2-9b 手元の `thth send`／`retract`／`reply` をはてなの口座に打つと `unsupported_operation`（`cli` の各入口に `hatena_entry.is_hatena(cfg)` の断りが無ければ足す）。T-S2-9c `sent/` を書いたあと `deliveries.advance` が落ちた（monkeypatch で `server_file_changed`）→ inflight が残る → `resolve --published <entry_id>` で `_record_sent` が二重に書かず・台帳に同じ `seq` で `published` が入る。T-S2-9d 読めない台帳（JSON を壊す）を指す approved の原稿は `select_problem` が `approval_stale` に倒れ、timer は何も書かない。

## 14. masaru に伺うこと

1. **相対リンクの基準の URL（`link_base`）。** 推し: **レーンの口座の台帳に `link_base`（レーンの記事が公開されているサイトの URL）を書き、無ければ相対リンクのある記事は断る**（§4.2）。代わりの形は「`https://<blog_id>/` を基準にする」。推しの理由は、記事の中の相対リンクはレーンの自分のサイトを指していて、はてなブログの中には無い（推測で貼ると壊れたリンクで公開される）。伺う理由は、**レーンの記事が公開されているサイトがあるのか**（kopicha・関東の記事は repo の中だけで、公開の場所がはてなブログだけなら、相対リンクは「同じブログの別の記事」を指すことになり、代わりの形が正しい）を私が知らないため。前提が変わる点: 公開の場所がはてなブログだけなら、`link_base` を省いて `https://<blog_id>/` を既定にする（`RULES` の `absolute_links` の既定を変えるだけ）。

ほかは推しで決めた（OAuth で WSSE は作らない・画像つきの記事は S2 では断る・記法は最新の記事の型で見る・読み戻しは応答の `content`・commit されていない記事は断る）。
