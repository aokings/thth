## 2. 記録（`sent` / `insights`）

### 2.1 `media` は既に全経路にあった

第 2〜6 段の確認結果（`grep alt_present`）: Mastodon（画像・動画・音声・thumbnail 親）、Bluesky（画像・動画）、Threads（画像・動画・カルーセル）の**すべての送信経路**が `media: [{sha256, kind, alt_present, remote_id}]` を作っていました。欠けはありません。投票・引用・リンク・GIF・長文は**ファイルではない**ので `media` には出ません（依頼の「only files」のとおり）。

直したのは 1 点だけです。`alt_present` が 4 か所とも `True` の決め打ちでした。`thth/adapters/base.py` に `alt_present(row)` を置き、manifest の `alt` から導きます。lint が `alt_required` で断るので実運用の値は変わりませんが、**決め打ちは将来 alt の無い経路ができたときに記録が黙って嘘をつきます**。`alt` の文字そのものは残しません（真偽 1 つ）。

### 2.2 `attachment_kinds`

`thth/media.py` の `attachment_kinds(manifest)` が作り、`thth/sent.py` の `write()` が検査して書きます。

- ファイルの種類（`role == 'media'` の `kind`: `image` / `video` / `audio`）
- 型付きの種類（`poll` / `quote` / `link` / `gif` / `text`。`media.TYPED_KINDS`）
- ファイルが 2 点以上なら `carousel`（Threads の CAROUSEL・Bluesky の gallery/images・Mastodon の複数 `media_ids` を**媒体名を混ぜずに**1 語で言う。これが無いと依頼にある `carousel` の層が永久に空になる）
- 何も無ければ `["none"]`。**空 list にしません**——「無かった」と「判らない」を同じ形にすると母数が読めません。

`thumbnail` / `caption` の役割のファイルは数えません（`media` 受領にも出ません）。語彙は `sent.ATTACHMENT_KINDS` に固定し、未知語・重複・空・`none` との併記を `invalid_attachment_kinds` で断ります。`thth/core.py` の 2 か所（不在の様態・同席の様態）から同じ 1 本を通します。

## 5. 第 9 段の直し 3 件

### (a) Worker の転送 mime に音声

`callback/src/media.js` の `MIME` に `audio/mpeg` / `audio/flac` / `audio/ogg` / `audio/wav` / `audio/x-wav` / `audio/webm` / `audio/mp4`。`thth/media_uploads.py` の `KINDS['audio']` を同じ集合で開き、上限は 100,000,000 bytes（multipart 閾値と同じなので音声は必ず 1 回の PUT）。

`FORMATS` を **`(kind, format) -> (受け付ける mime の組, 公開拡張子)`** に組み替えました。container の名前 1 つが 2 つのことを指すためです——検査した `mp4` は track によって `video/mp4` にも `audio/mp4`（`.m4a`）にもなり、`wav` は `audio/wav` と `audio/x-wav` の両方を受け、`ogg` と `ogg_vorbis` は同じ `audio/ogg` です。`complete` の mime 照合は**検査した (kind, format) の組に対する所属**になりました（申告は相変わらず信用しません）。

### (b) `media_id` ≠ upload subject

第 9 段は `media_id` をそのまま subject（＝ PUT の URL の最後の一節）にしていました。**`media_id` を知る者は一回限りの URL を組み立てられた**わけです。いまは

```
subject  = secrets.token_urlsafe(32)          # 控えの中だけ・URL の中だけ
media_id = 'm' + base64url(sha256(subject))[:42]   # 43 文字・外に出るのはこちら
```

控え（`state/<account>/media-uploads/<media_id>.json`・mode 600）は `subject` も持ち、`_valid()` が `derive_media_id(subject) == media_id` を毎回突き合わせます。Worker の control（`create` / `complete` / `status` / `read` / `ack`）と URL は subject、`thth_media_complete` と `thth_draft_put` は `media_id`。**subject を `media_id` の位置に渡すと `media_unknown`** です（試験あり）。

### (c) multipart PUT の手順

`docs/運用_サーバ書込_2.12.md` に「置き方（招待者の手順）」を追加。`part_size` の有無・`<upload_url>/<番号>` に 1 から連番で順番に・最後の part だけ短くてよい・合計が申告 `size` と一致・最後に `complete`。curl の実例 2 本付き。あわせて mime 表（音声を含む）と `media_id` の但し書きも更新しました。

## 7. 決めたこと（裁定が要るかもしれない箇所）

1. **`carousel` を `attachment_kinds` に入れた。** 依頼の列挙（ファイルの種類＋型付きの種類）には無い語ですが、依頼が数えよと言う層の一覧には `carousel` があります。ファイル 2 点以上を媒体に依らず `carousel` と呼ぶことで層が埋まります。呼ばない方がよければ 1 行で外せます。
2. **`attached` の層を足した。** 依頼の層一覧には無いが、`none` と `unknown` だけでは母数が分割されず `reconciliation` が書けません。`_tag_strata` の `tagged` と同じ役です。
3. **表に形式名（`jpeg`…`vtt`）と `bmff brand` / `unknown format` を入れた。** adapter が `unsupported_attachment: <媒体>/<形式>` を投げるので、部分集合の条件を満たすには表側に同じ名前が要ります。結果として「この媒体はこの形式を受けるか」が読める表になりました。
4. **組合せの理由 key は `REFUSALS` に分け、外に出さない。** `poll_combination` のような「形が違う」理由は能力の表ではないので、LLM が読む `tool.capabilities` からは外しました。部分集合の試験は和集合で見ます。
5. **`mastodon.carousel_quote` / `threads.carousel_quote` は `unverified`、`bluesky.carousel_quote` は `supported`。** Bluesky は第 7 段で引用＋添付の組合せを実装し replay 試験があるため。Mastodon は引用＋複数 media を通す実装はあるが確かめていないため `unverified`。
6. **`bluesky.reply_control` は `unsupported: threadgate_not_implemented`。** provider には threadgate があるが thth が実装していない、という区別を理由の語で言っています（`provider_has_no_*` とは別の語）。
7. **音声の公開拡張子**: `audio/mp4` は `.m4a`、`audio/webm` は `.webm`、`ogg_vorbis` も `.ogg`。gc の参照判定（`[0-9a-f]{64}\.[a-z0-9]{2,4}`）の範囲内です。

## 8. 限界（実測していないこと）

- **表の値は静的な宣言**で、provider を叩いた結果ではありません。`basis: static_table_not_a_provider_probe` と docs に明記しました。`supported` は「thth が API に渡せて、fake / record-replay の試験が通っている」の意味です。

- multipart PUT の手順は文書だけで、**実 R2 に対する分割 PUT は未実施**です（part の順序・最終 part の扱いは Worker 側の既存試験のみ）。
