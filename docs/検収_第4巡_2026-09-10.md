## 直した形（個別の条件でなく、形を変えた）

### 1. 「確かめた commit」と「読むファイル」を結び付ける

`sync_repo()` が確かめていたのは **commit の一致**（`HEAD == @{u}`）だった。
必要だったのは **これから読むファイルの一致**。近い事実で代用していた。

`thth/writeback.py::matches_synced_commit()` を足し、**ファイル 1 本ごとに
HEAD の blob とバイト列を直接比べる**。`git status` の解釈（staged／unstaged／
untracked／`.gitignore`）には頼らない——解釈の隙間がそのまま素通りの経路になるので、
**未 commit・staged・追跡外・無視・symlink・HEAD に無い、をすべて同じ 1 つの理由に
倒す**（`select` の `unverified_content`）。ここに載っていない新しい壊れ方が今後
見つかっても、この関数を触らずに安全側へ倒れる。

- **何も消さない・戻さない。** 作業中の変更はそのまま残し、その 1 本を候補から
  外して board に出すだけ。
- **ファイルは 1 回だけ読み、検査もその同じバイト列で行う**（`queuefile.parse_text()`）。
  読み直すと、検査したバイト列と select が見るバイト列が別物になりうる。
- board（`report.py`）も同じ `core.list_queue_files()` を通るので、**公開の判断と
  board の診断が同じ事実を見る**。

### 2. `thth approve` が承認を commit して push する

1 の裏返し。承認がファイルの中だけにある状態は「永久に出ない」を意味するので、
承認と同時に commit・push する。commit 先は台帳の `repo_dir` ではなく
**そのファイルが入っている repo**（masaru が自分の clone で承認することもある）。
push できなければ非ゼロで終わり、その旨を述べる（黙って「承認しました」と言わない）。

副産物として、**承認した瞬間が利用者 repo の履歴に残る**。「いつ何を承認したか」が
後から動かせない形になった。

### 3. 承認済みなのに出ないものは、理由が何であれ要確認に出す

`duplicate_text`・`no_section`・`too_long`・`hashtag`・`topic_*` も `needs_review` に
積む。**条件の並び順が board の見え方を変えてしまう形そのもの**を潰した。時間が
経てば解決する理由（`future`・`quiet_hours`・`min_interval`）だけが積まれない
（それらは 2 段目・`_apply_timing_gate()` にある）。

## fixture が本番と違っていた（規約 11 の再演・今回も出た）

`write_queue_file()` は queue ファイルを**ディスクに置くだけ**だった。本番の queue
ファイルは利用者 repo の commit として届くので、この形の fixture は本番では
一度も起きない状態を作っていた。commit・push まで行うように直したところ、
**33 件が落ちて 22 件に減り、最後まで詰めて 0 になった**。第 3 巡で
「fixture が本番と違う形をしていないかを疑う」を規約に足した直後に、**別の場所で
同じ罠が出た**。一度直せば済む種類のものではない。

select の単体テスト（1 条件 1 テスト）だけは、毎回 clone を作るのが筋悪なので
`parse_verified()` という**名前と docstring で前提を明示する helper** を通す。
前提そのものは `test_atlas_fourth_review.py` が本物の clone と実プロセスで確かめる。
