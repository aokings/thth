## 設計から外れた点・判断した点

1. **lint の符丁を 1 語足した**: `reply_to_file_unreadable`（指した原稿は在るが `thth: 1` として読めない）。設計の 6 語だと「無い」と言うことになり、直す場所を取り違えるため。
2. **`reply_to: file:…` を断る**（`reply_to_file_invalid`・lint と select）。指紋の reply_to 欄を共有するので、許すと `reply_to_file: a.md` と同じ指紋になる。
3. **併用の指紋**: `reply_to` と `reply_to_file` が両方あるとき、指紋の欄はどちらか一方だけの値と一致しない値（`file:<名前>` と `reply_to` を `\x1e` でつないだもの）。lint も select も併用を断るので、ここは二重の守り。
4. **同期を確かめていない指した原稿は「待ち」扱い**（select）。手元で `post_id:` を書き足しただけの原稿に返信先を向けさせないため。副作用として、同じ実行で問いを出した直後の答えは次の実行（最大 10 分後）で出る（試験で固定）。
5. **待ちの候補は publish_at が未来でも要確認に出る**（設計 §2「要確認に静的理由で出す」をそのまま。妥当性の段は時刻を見ない規律のため）。朝に「明日の答えが返信待ち」と出るのは正常の表示。
6. **待ち以外の未解決（取り下げ・読めない・消えた・account 違い 等）** は runs に実エラーとして残す（`_is_error_reason`）。待ちは残さない。morning の `waiting_items` には待ち以外の未解決も理由付きで並べた（時刻超過から外した原稿がどこにも出ない形を避けるため）。`next_steps` には足していない。
7. **指した原稿が `status: withdrawn`（未公開のまま取り下げ）** は post_id が無いので「待ち」のまま出続ける。設計の 5 状態に無いので足していない——判断が要る点。
8. **`handoff-report` の栞（`handoff_cursor.QUEUE_KEYS`）には `waiting_reply` を足していない**。足すと既存の栞が `cursor_unreadable` になる（鍵の集合を完全一致で見ている）。`changes_since` には `waiting_reply` の変化は出ない。
9. **`thth report add` は CLI でも `--by` を必須にした**（`report file` と同じ）。CLI の範囲は `report show` と同じく絞らない（手元の CLI は VM の持ち主の口）。project の絞りは MCP（サーバ型の credential）で効く。
10. **似た報告の範囲**: project を持たない account は同じ account の中だけ（`Scope` の既存の規律）。`_` も記号として切る（`reply_to_file` は `reply`・`to`・`file`）。2 字の英語（`to` 等）も語に数えるので、英字の題では重なりが出やすい——設計どおりにした。
11. **preview の返信先の行は照合しない見込み**（同期を確かめない）。実際に出すときは select が同期を確かめた原稿だけで解決し直す。
12. MCP のサーバ型の下書き（`thth_draft_put`）は `reply_to_file` を受けない（裁定 5）。受ける口は作っていない。
