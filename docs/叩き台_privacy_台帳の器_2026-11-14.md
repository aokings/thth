### 2-1. 1 段落め（直す）

変える前:

> `thth register` reads a register: a folder of plain text files, one file per thing, that the owner keeps on their own computer, so that drafts use only facts the owner has confirmed. The register stays with the owner; THTH's operator does not hold it, and THTH does not send it anywhere (this part of THTH has no network access). In the register, THTH writes only the fixed head fields `confirmed`, `confirmed_at`, `synced_on` and `synced_row` and adds lines to the question log (`問いの記録.jsonl`), and it does not change any other line. On the computer where it runs, THTH keeps the register's name, project, folder path and kind, and a record of which rows the owner confirmed (the row's ID, a fingerprint of its contents, when and by whom); with it THTH notices that a row changed after it was confirmed. It also keeps a list of the drafts it wrote (each draft's path and the origin lines written in its head: the row, the fingerprint, the register's commit, the trigger and the deadline), so that it reads the row again at approval even if those lines are removed from the draft. THTH refuses to use a row that is a guess, that the owner said is wrong, that is past its review date, that is retired or that is not marked as public, and refuses a row that looks like it contains a key or a password. `thth register remove` deletes THTH's files for the register on the computer where it runs; when the project's last account leaves, `thth leave` deletes them there. Neither deletes the register folder.

変えた後:

> `thth register` reads a register: a folder of plain text files, one file per thing, that the owner keeps on their own computer, so that drafts and other material use only records that have reached a decision under the register's own rules, such as rows the owner confirmed. The register stays with the owner; THTH's operator does not hold it, and THTH does not send it anywhere (this part of THTH has no network access). In its everyday work (confirming rows, drafting, asking and recording a paste), THTH writes in the register only the fixed head fields `confirmed`, `confirmed_at`, `synced_on` and `synced_row` and adds lines to the question log (`問いの記録.jsonl`), and it does not change any other line; it writes anything else in the register only when the owner runs a command for it, as described below. On the computer where it runs, THTH keeps the register's name, project, folder path and kind, and a record of which rows the owner confirmed (the row's ID, a fingerprint of its contents, when and by whom); with it THTH notices that a row changed after it was confirmed. It also keeps a list of the drafts it wrote (each draft's path and the origin lines written in its head: the row, the fingerprint, the register's commit, the trigger and the deadline), so that it reads the row again at approval even if those lines are removed from the draft. ### 2-2. 2 段落め（足す）

> A register can also hold decisions about its records and rules for where they may be used (a page, a site or another tool). A decision records which version of which record it is about, the question it answers, the answer, who made it and when, the type of reason and its explanation, and until when it holds. THTH adds decisions to the register's judgment log (`.thth/judgments.jsonl`) only when the owner records or accepts them, and adds lines without rewriting earlier ones, except for an erase request (below). A decision that stops a record takes effect at once. A decision that allows more takes effect only after the owner accepts it and THTH seals it with a key that belongs to the owner. The private key is kept on the owner's computer in an owner-only file (by default `~/.config/thth/register_seal.pem`, mode 600), never inside a register or a repository that contains one, and THTH does not show it; the owner gives the matching public key to the build that publishes the material. THTH writes the material to a folder outside the register and keeps each seal in the register (`.thth/seals/`). A copy of the seal is published with the material, so that the next build can check it. The seal and its copy hold the outlet's name and who it is for, a generation number, the time, the THTH version, a fingerprint of the rules, the size and fingerprint of the judgment log, the IDs of the records used (with fingerprints of their versions) and of any the build left out, fingerprints of each item and of each table row and file written, and a fingerprint of each line of the judgment log (made from the question, the record, the answer and the dates, without who decided or the line's ID). They do not hold the records' values or the explanations of decisions. Fields the owner marks as private for an outlet are left out of the material for readers; the fingerprint of a record's version is still made from the whole record. When the owner records it, THTH also keeps a list of the addresses published for an outlet (`.thth/published/`: each address, when it was first published, and whether it is live, redirected or gone). Records from the owner's shared register, which holds things used across projects such as the operator's details, enter an outlet's material only when the outlet names their kind and the owner has taken that version.

### 2-3. 3 段落め（足す）

> When the owner has THTH change register files (change or add a table row, bring in files from another folder, which THTH only reads, bring in a checked set of files, or replace several files at once), THTH first keeps the earlier contents and a list of the register's files (`.thth/kept/`) and writes the plan of the replacement (`.thth/batch/`), so that a stopped replacement can be finished or undone. The list also records who collected and who checked a set of files. THTH does not remove kept versions on its own: with them the owner can see what changed and when, and restore an earlier state. When the owner sets up the shared register, THTH copies the declarations of its built-in kinds into it (`.thth/kinds/`). If the owner wants something gone from the register and its history, such as an address written by mistake, the owner files an erase request (`.thth/erase/`). The request records who asked, when, which record and field, and the type of reason, not the content to be removed. After the owner confirms the scope in two steps, THTH removes it from the register's current text, the kept earlier versions and plans, the judgment log (rewriting the affected lines into a marker, keeping the number and order of lines) and the seals, then reads every file in the register folder, outside git's own folder, to check that the content is gone. THTH does not change or check git history, material already written or published, other copies or the shared register; the result lists them as not checked until the owner marks each one. Past results that used the erased version can no longer be reproduced; the result says which outlets and generations are affected, without the erased content or its fingerprint.

### 2-4. 4 段落め（足す）

> No THTH command deletes a register folder or what THTH wrote inside it. `thth register remove` deletes THTH's files for one register on the computer where it runs (its name, project, folder path and kind, the record of confirmed rows and the list of drafts). Removing an account keeps those files and the register's decisions, even for the project's last account. Removing a media project deletes its accounts and THTH's files for its registers, and keeps the shared register and other projects. Removing an owner deletes all of the owner's accounts, THTH's files for every register (the shared one too), the owner's principals with the keys THTH holds for them, and the seal's private key. Removing an account, a project or an owner stops without deleting anything if a register folder lies where it would delete. Removing a project or an owner first shows what will be deleted and what will remain, deletes only after the owner confirms, and keeps a record on that computer (the accounts, registers and folders involved, who ran it, the stage reached, and the kinds and counts deleted), so that the same command can continue after a stop.

## 4. 持ち主に決めてほしい所

1. **配る封に記録の番号が載る**（`items`・`inputs`・`dropped`。共通の台帳の記録は `common:<番号>`）。公開の場所に出るので、読者の目に番号が見える。推し: **載せてよい**。番号は材料の頁の中身を見ればたいてい分かり、外すと CI の確かめ（前の世代の続きか・外して配ったか）が組めない。番号に人の名前などを入れない決まりを台帳の側（種類の宣言の番号の形）で持つほうが効く。
2. **行ごとの骨の指紋が公開の場所に出る**（`deployed.lines`。問い・記録・単位・語・結論・日時・いつまでの sha256 の頭 32 字）。誰がと番号は入らないが、問いと語の組が少ないので、記録の番号が分かれば中身（だめ・止めるなど）を当てられうる。推し: **このまま出す**。消す求めのあと CI が行ごとに比べるのに要る。文には「指紋」と書き、当てられうることは書かない（約束を増やさない）。気になるなら、骨に台帳ごとの塩を混ぜる直しを開発に頼む。
3. **記録の版の指紋は、出さない欄も含む記録の全体から作る**（公開の封に載る）。出さない欄の値は入らないが、ほかの欄が分かる人は、短い値（電話番号など）を当てられうる。推し: **文で正直に書いたまま出し、直しは開発に回す**（出さない欄を除いた版の指紋を別に持つ）。
4. **保存の期間の節に台帳の行を足すか**。今の節は運営者のサーバーの物だけで、台帳の行が無い。推し: **足さない**。台帳と THTH の控えは持ち主の手元にあり、期間は「持ち主が消すまで」で、台帳の節の 4 段落めに書いた。
5. **置き場の名前（`.thth/...`）を privacy に書くか**。原則 3 は「細部（ファイルの場所）は貼り紙と文書に置く」。推し: **今回は書く**（頼まれた形・既存の節も `confirmed` などの名前を書いている）。次に節を大きく直すときに外すかを決める。
6. 施行日 `PRIVACY_EFFECTIVE`（今 2026-11-13）は書き手は変えていない。出す日に主セッションが入れる。
