# 設計 v2.0.1: 同席送信（`thth send`）で出した投稿を `thth collect` が採る

正本: `docs/設計_v2_泉と門_2026-09-13.md`（§3.2.2 数値は出所を連れて歩く・§4.2 採集と実測の
媒体差）。本書はその差分だけを書く。masaru 裁定 2026-09-14「1（すぐ着手）」。

## 0. 何が壊れていたか

`thth/collect.py` の `collect_once()` は `core.list_queue_files()`（queue の原稿）だけを
対象にしていた。**`thth send`（同席の様態）は queue を通らない**——出した記録は
`state/<account>/sent/<post_id>.json`（`thth/sent.py`）だけにある。したがって
同席専用の台帳（`repo_dir: $THTH_ROOT/repos/_none`・`scheduled: false`）では、
**実測も返信も 1 件も採れなかった。**

`thth board` と `thth posts` は 2026-09-13 に `sent/` を読むよう直っている
（`thth/report.py`・`thth/account_report.py`）。**collect だけが直っていなかった。**

## 1. 置き場の解決を 1 か所に（`accounts.data_dirs()`）

規則は 2 行:

1. `repo_dir` が**実在する git repo** なら、従来どおり `repo_dir/data/sns/…`（既存の
   経路は 1 バイトも変えない。`replies_dir` の指定もそのまま効く）。
2. そうでなければ（`_none`・存在しない・`.git` が無い）**`$THTH_ROOT/state/<account>/data/sns/…`**
   （`accounts.state_dir_for()` の下）。この側では `replies_dir` は効かない——repo の
   レイアウトに合わせる相手がいないので、置き場は道具が決める。

`data_dirs(account_cfg, account_name)` が `{"insights_posts", "insights_account",
"replies", "inbox"}` を返し、**書き手も読み手も全部これを通る**。直書きしていた
読み手は `thth/account_report.py`・`thth/measured.py`・`thth/replies.py`・`thth/collect.py`。

**git の書き戻しは repo があるときだけ。** state 側は書いて終わり（同席専用に原稿 repo は
無く、state は VM のローカルで、`thth board` が読む場所）。`run_collect()` は repo が
無ければロックも同期も commit も push もしない。

## 2. collect の対象に `sent/` を足す

`sent.records(state_dir)` の各行を、`_with_bundle_posts()` が束の段に対してやっているのと
同じ**疑似 queue ファイル**にして、既存の採集ループへ流す。

- `post_id` ← 記録の `post_id`、`posted_at` ← `sent_at`、本文 ← `text`、`account` ←
  その account、`media` ← 台帳の `media`。`topic`・`kind`・`reply_to` は**無い**
  （同席の送信は front-matter を持たない。無いものを推定で埋めない）。
- **queue 由来と `post_id` が重なれば queue を正**（同じ投稿を 2 回数えない）。
  **重なりは生の `post_id` の文字列一致で見る**——だから **queue の front-matter に
  書き戻す `post_id` は生の形**（`at://did:plc:…/…`）で、`postid.to_filename()` の
  percent-encoding を通した形では書かない（監査 2 回目・P3-12）。encode 済みの形が
  片方にだけ入ると、**同じ投稿が別の `post_id` として 2 回数えられる**。encode は
  **パスを作るときだけ**（ファイル名 1 つぶん）で、台帳の値には現れない。
- `collect_days` の窓は queue と同じ。
- `_refresh_targets()`（`thth replies --refresh`）も同じ母集団を見る。

**queue の経路の振る舞いは変えない**——既存のテストは無改変で通る。

**母集団が増えたぶん、`share` の outbox にも同席送信の形が入る**（監査 2 回目・
P2-6・2026-09-14）。`share.enqueue_*` の白名簿は 1 行も変えていないので、出るのは
これまでと同じ形（`text_length`・`has_link`・刻み・仮名化した観測者）だけ——
**本文・handle・生の `post_id` は入らない**。増えたのは「どの投稿を数えたか」であって
「何を出すか」ではない。`share` が off なら何も変わらない。

## 3. 数値は出所を連れて歩く（設計 v1 §3.2.2）

実測の行と返信の `kind: fetch` の行に `source` を書く。`"queue"`（書き戻された
front-matter）か `"sent"`（同席の送信）。**無印は旧行**で、読み手は `queue` として扱う。
`thth measured`・`thth threads`・`thth replies`・`thth posts` は `--json` に鍵を、
人向けには 1 語（`出所=同席の送信`）を出す。

**本文は `sent/` にだけ置く。** 実測・返信の行に入るのは `text_length` と `has_link`
（queue 由来と同じ導出値）だけで、本文そのものは repo にも outbox にも写さない。

## 4. 止まる条件

- 採集が `sent/` の**本文**を repo や outbox に写す形になったら止まる。
- `share.enqueue_*` の白名簿は変えない。
- `thth/VERSION` は触らない（tag は開発セッション）。
