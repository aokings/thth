# 設計 2.9.0: 管理者の視点——inventory・来歴・変更ログ・読み口

2026-09-19。きっかけ: kopicha のセッションが 09-18 夜に Bluesky・Mastodon の account を自分で足し、翌日には本番投稿していたが、管理側には何も届かず、台帳にも「誰が・いつ」が残っていなかった。masaru の言葉: 「管理者権限用の mcp＋cli＋skills を認証付きで作った方が良くない？」「必要な情報が仔細に取れるように網羅的な仕様に」。

本書は契約。実装は Codex。裁定は §7。

## 0. 原則

1. **読むだけ。** 管理者にも承認・投稿・台帳の書き換え・token の入れ替えは開けない。管理者が書けるのは cursor（`--mark-read`）だけ（2.6.0 の handoff と同じ流儀）。
2. **認証は新しく作らない。** VM の CLI は ssh のユーザ（`wt`）が境界。HTTP は `serve-reports` の service credential に **`scope: admin`** を足す。MCP は admin scope の資格情報を渡したセッションだけが全体を読める。
3. **秘密の値は絶対に出さない。** token・app secret・通知先メールは、存在・置き場・権限・メタ（期限・scope・user_id）だけ。
4. **推測で埋めない。** 記録が無いものは `null`＋理由コード。過去（ログ開始前）の来歴は `null` のまま。
5. **既存の鍵を変えない。** `board`・`doctor`・`handoff-report` の出力はそのまま。`admin` はそれらを**横断して束ねる**読み口で、計算を二重に持たない（同じ関数を呼ぶ）。

## 1. 来歴を台帳に持たせる（書く側の変更・唯一）

`thth account add` に **`--by <名前>` を必須**にし、台帳に次を書く（既存台帳には無く、`null` で読む）:

```json
"provenance": {"created_at": "...", "created_by": "masaru", "created_via": "cli|mcp", "created_host": "<hostname>"}
```

`thth account` の編集系も同じ `--by` を取り、§2 のログに残す。`--by` が無ければ **loud reject**（黙って `unknown` にしない）。訂正（Codex の実装前照合 2026-09-19）: 現行の `account add --force` は移行ガードの迂回だけで上書き機能は無い——**上書きは `--force --by` を明示したときだけ**行い、既存の `provenance.created_*` は保つ（更新は §2 のログに `account_updated`）。既存の top-level `thth revoke` は**投稿承認の取り消し**なので触らず、token の失効は **`thth token revoke <account> --by`** として別に足す。削除コマンドは作らない（`account_removed` は event 型としてだけ定義し、手で消したときにログへ書く口は無い＝`null` の来歴になる）。

## 2. 変更ログ（追記のみ）

`$THTH_ROOT/state/_admin/accounts.ndjson`（600・追記のみ・1 行 1 event）:

```json
{"at": "...", "by": "masaru", "via": "cli", "host": "...", "event": "account_added|account_updated|account_removed|token_set|token_refreshed|token_revoked|production_enabled|production_disabled",
 "account": "kopicha-bluesky", "medium": "bluesky", "diff": {"hashtags": [false, true]}, "run_id": null}
```

- `diff` は台帳の**値の前後**。秘密に当たる鍵（`token`・`env`・通知先）は**パスの変化の有無だけ**（`"token": ["absent", "present"]`）。
- 書くのは `account_cli`・`oauth`（`auth`／`token set`／`refresh`）・`maintain` だけ。`admin` は読むだけ。
- 壊れた行は読む側で `broken` に数え、使わない（`measured._read_ndjson` と同じ）。

## 3. 読み口 `thth admin …`（全部 `--json` と Markdown・読むだけ）

### 3.1 `thth admin inventory`

全 account を 1 行ずつ。**項目 × 出所 × 取れないときの値**を固定する（これが「網羅的」の担保）:

| 項目 | 出所 | 取れないとき |
|---|---|---|
| `account`・`project`・`medium`・`handle`・`instance` | 台帳 | 台帳が読めない account は `ledger: "unreadable"` の行として残す（消さない） |
| `production`・`hashtags`・`max_hashtags`・`min_interval_hours`・`quiet_hours`・`collect_days`・`stale_days`・`scheduled` | 台帳 | 鍵が無ければ `null`（既定値を書かない。既定は `defaults` に別出し） |
| `repo`: `state`（ok/none/broken）・`dir`・`origin`（有無）・`ahead`/`behind`/`dirty`（`data/sns` 配下） | `accounts.repo_state`・`git` | git が無い／読めない → `null`＋`repo_reason` |
| `provenance`（§1） | 台帳 | 無ければ全部 `null`＋`provenance_reason: "recorded_before_2.9.0"` |
| `token`: `present`・`mode_ok`（600）・`obtained_at`・`expires_at`・`remaining_days`・`no_expiry`・`user_id`・`username`・`scopes`・`scopes_source`・`handle_matches` | `.token` のメタ（`oauth.token_age_and_remaining`） | 無ければ `present: false`、他は `null` |
| `permissions`: 口ごとの ○/×/― と HTTP 番号 | `doctor` の probe（**読み取りだけ**・`--probe` を付けたときだけ叩く。既定は前回の `doctor` の記録があればそれ、無ければ `null`） | `probed_at: null` |
| `queue`: 承認待ち・超過・型外・未帰属型外・下書き | `handoff-report` の `queue.counts` | repo 無しは `null` |
| `inflight`・`last_post`・`sent_count` | `handoff-report` | 同左 |
| `collection`: `last_success_at`・`last_attempt_at`・`last_attempt_ok`・最後に到達した刻み | `collection_status`・insights | 記録なし → `null`＋`collection_records_unavailable` |
| `notifications`: outbox の `last`・未処理・配達状態・通知先の**有無** | incident outbox・healthcheck status | 同左（メールアドレスは出さない） |
| `timer`: unit 名・`active`・`last_trigger`・`next_trigger`・最後の `ExecMainStatus` | `systemctl show`（VM 上でだけ。HTTP 経由は前回の記録） | systemd が無い／読めない → `null`＋`timer_reason` |
| `last_change`: §2 の最新 event | 変更ログ | ログ無し → `null` |

`summary` に全体の件数（account 数・媒体別・production 数・token 期限 7 日以内・inflight あり・型外あり・timer 停止）。**媒体や account をまたいだ数値の合計は件数だけ**（views 等は足さない）。

### 3.2 `thth admin account <name>`

3.1 の 1 行を仔細に: 台帳の全項目（秘密はパスと権限だけ）、token メタ、`doctor` の全 probe（`--probe` 時）、queue の内訳（型外はファイル名を出さず件数）、直近 N 件の runs（成否・collected・error の伏字済み文）、通知の event 履歴、変更ログのこの account の全行、repo の git 状態、`analytics-report` の `collection`。

### 3.3 `thth admin log [--since <時刻>] [--account <name>] [--event <種類>]`

§2 の変更ログをそのまま。`broken` の件数を添える。

### 3.4 `thth admin tokens`

全 account の token を**期限順**に: `remaining_days`・`scopes` と `DEFAULT_SCOPES` の差・`handle_matches`・最後の `refresh` の成否（`maintain` の記録）。

### 3.5 `thth admin timers`

VM 上で `systemctl list-timers`／`show` を読み、account ごとに `thth-run@`・`thth-collect@`・`maintain` の状態。HTTP からは「最後に記録した値」と `observed_at`。

### 3.6 `thth admin release`

`thth board` の 1 行目と同じ源（`selfupdate`）: 版・revision・`release` との差・署名の確認状態・最後の自己更新の試行と結果・`app.env` の存在と鍵名（値なし）。

### 3.7 `thth admin diff --since-last-read [--mark-read --by <名前>]`

3.1 の inventory 全体を snapshot として `state/_admin/admin_cursor.json` に持ち、前回との差（account の増減・production の変化・token の入替／期限の接近・inflight の出現／解消・型外の増減・timer の停止／復帰・版の変化）を先出し。`handoff_cursor` と同じ実装を共有する（書くのは `--mark-read --by` のときだけ・HTTP からは書けない）。

### 3.8 共通

- `schema_version: 1`・`report_type: "admin_inventory"|"admin_account"|…`・`generated_at`・`observed_from: {"host": …, "via": "cli|http"}`。
- `cannot_say` と `cannot_say_details`（2.6.0 の形）。
- 秘密の走査テスト: 出力に token 値・app secret・メールアドレス・`~/.config/thth/` の**中身**が出ないことを、偽の秘密を置いて固定する。

## 4. HTTP・MCP・skill

- `serve-reports` の資格情報に **`"scope": "admin"`** を足す（既定は今の account 列挙＝`user`）。admin は全 account を対象に `analytics_report`・`operations_handoff`・**`admin_inventory`・`admin_account`・`admin_log`・`admin_tokens`・`admin_release`・`admin_diff`** を呼べる。`admin_timers` は HTTP では「最後の記録」だけ。`mark_read` は HTTP から受け付けない（既存どおり）。
- 起動時の preflight（`report_isolation`）は admin scope でも同じ（root の全 account を対象に検査）。
- MCP: `thth_admin_*` の 6 道具。**MCP を起動した環境が admin の資格情報を持つときだけ tools/list に出す**（無ければ出さない・呼ばれても `unauthorized`）。
- `skills/thth-admin/SKILL.md`: 「開始時に `admin diff --since-last-read` → 変化があった account を `admin account <name>` → 週 1 で `admin tokens`」。**読んだ結果から承認・投稿・設定変更をしない**（人に渡す）。

## 5. 通知

§2 の event のうち `account_added`・`production_enabled`・`token_set`・`token_revoked` を、既存の停止通知（incident）と同じ経路で**管理者宛**に 1 通（本文は event の 1 行・秘密なし）。宛先は既存の管理者アドレス設定。既定は on・台帳の `notify_admin_on_change: false` で止められる。

## 6. 順番と検収

1. §1・§2（来歴と変更ログ）——書く側は小さい。`--by` 必須の loud reject・追記のみ・秘密は有無だけ、をテストと変異で。
2. §3.1〜3.3（inventory・account・log）——項目 × 出所 × `null` 理由の表をそのままテストの表にする（1 項目 1 ケース）。既存関数を呼び、計算を二重に持たないことを差分で確認。
3. §3.4〜3.7。
4. §4（HTTP admin scope・MCP・skill）——2.5.0 の HTTP probe に admin の否定ケース（user scope で `admin_*` → `unsupported_operation`、admin でも `mark_read` → `invalid_request`）を足す。
5. §5。
- 実台帳: VM の 8 account で `admin inventory` を読み、`board`・`doctor`・`handoff-report` と**値が一致**すること（同じ関数なので一致するはず。しなければ二重計算の印）。
- 秘密の走査（§3.8）。
- 版は **2.9.0**。2.8.0（タグ）と独立に進められる。
