# 運用: 配布と release の署名（2.14）

2026-09-22。設計 `設計_2.14.0_X投稿adapterと署名_2026-09-22.md` §5・masaru 裁定 4。

**この文書は配布担当（masaru の Mac）向け**です。VM 側は環境変数を 1 つ入れるだけで、
あとは `thth run` が毎回やります。

---

## 0. いま何が起きているか（署名を入れる前）

`thth run` は仕事の前に自分自身を `git fetch` → `git merge --ff-only origin/release`
します。確かめているのは「ff できるか」だけなので、**origin を握った者は次の timer
（10 分）で VM の上に任意のコードを置けます**。

`THTH_REQUIRE_SIGNED_RELEASE=1` を入れると、VM は取り込む前に配布 commit の SSH 署名を
確かめ、確かめられなければ**取り込まずに古いまま走ります**（止まりません）。

**既定は検証しません。** いまの release の commit は無署名なので、無条件に入れると
次の配布で VM が古いまま止まります。入れるのは配布担当の判断です。

---

## 1. 鍵を作る（masaru の Mac・1 回だけ）

```bash
ssh-keygen -t ed25519 -f ~/.ssh/thth-release -C "thth release"
```

- **秘密鍵（`~/.ssh/thth-release`）は Mac から出しません。** VM にも chat にも貼りません。
- 公開鍵は `~/.ssh/thth-release.pub` です。これは公開してよいものです。

## 2. 署名の設定（配布担当の Mac）

```bash
git config --local gpg.format ssh
git config --local user.signingkey ~/.ssh/thth-release.pub
```

**`commit.gpgsign true` は入れません。** 署名するのは **release へ進める commit だけ**
です。開発の commit まで署名すると、どれが配布の意思表示なのか判らなくなります。

release を進めるときだけ:

```bash
git commit -S -m "..."        # 署名付きで 1 本作る
git push origin HEAD:release  # これが本番反映
```

確かめ方（手元で）:

```bash
git log --show-signature -1
git verify-commit HEAD
```

## 3. VM に「誰の署名なら信じるか」を置く

VM の `~/.config/thth/allowed_signers` に **1 行**置きます（600）。

```
thth-release ssh-ed25519 AAAA...（~/.ssh/thth-release.pub の中身）
```

書式は `<主体> <鍵の種類> <鍵>` です。主体（左端）は任意の名前でよく、`git` は
commit の署名者名と突き合わせません（SSH 署名の allowed_signers の書式そのまま）。
`principals` を厳密にしたい場合は commit の `user.email` を左端に書きます。

```bash
install -m 600 /dev/stdin ~/.config/thth/allowed_signers <<'EOF'
thth-release ssh-ed25519 AAAA...
EOF
```

手で 1 度確かめます:

```bash
git -C /srv/thth/app -c gpg.ssh.allowedSignersFile=~/.config/thth/allowed_signers \
    verify-commit origin/release
```

置き場を変えたいときは `THTH_ALLOWED_SIGNERS` で指せます（既定は
`~/.config/thth/allowed_signers`）。

## 4. VM で検証を有効にする

timer／service の環境に 1 行足します。

```ini
[Service]
Environment=THTH_REQUIRE_SIGNED_RELEASE=1
Environment=THTH_ALLOWED_SIGNERS=/home/thth/.config/thth/allowed_signers
```

```bash
sudo systemctl daemon-reload
sudo systemctl restart 'thth@*.timer'
```

## 5. board に何が出るか

`thth board` の 1 行目に出ます。

| 記録 | 出る語 | 意味 |
|---|---|---|
| 検証していない（既定） | `署名: 未確認` | `THTH_REQUIRE_SIGNED_RELEASE` が入っていない |
| 検証して通った | `署名: 確認済み（SHA256:…）` | その鍵で確かめて取り込んだ |
| 署名が無かった | `署名: 未確認（取り込んでいません）` | 配布 commit が無署名。**古いまま走っています** |
| 署名が合わなかった | `署名: 不正（取り込んでいません）` | 鍵か commit が疑わしい。**人を呼んでください** |

括弧の中は**公開鍵の指紋**です（秘密ではありません）。形が読めなかったときは
`鍵ID未記録` と出ます。

`thth board --json` では `app.signature_state`（`off`／`verified`／`missing`／
`invalid`）と `app.signature_key` を読めます。

## 6. 止まる条件と、止まらない条件

- **止まりません。** 署名を確かめられない日は、VM は**古い版のまま**走り続けます
  （取りに行けない日に投稿を全部止めるのが重すぎるのと同じ理由）。
- ただし**黙って古いまま走りません**。`thth board` と取得の記録に理由が残ります。
- 署名を始めたあとで無署名の commit を release に置くと、**その回から取り込みが
  止まります**。release へ進めるときは必ず `git commit -S` を通してください。


## 月間投稿数の上限は account ごと

`thth admin budget x-posts --monthly N --by <名前>` の N は **X account ごと**に数えます（`state/<account>/x-posts-<YYYY-MM>.json`・UTC 月）。X が tier で課す上限は App（project）単位なので、同じ App に N 個の account を紐づけると thth の上限は合計 N×N になり得ます。Developer Portal の上限を account 数で割った値を入れてください。成功した投稿と結果不明の投稿の両方を数えます（結果不明も枠を消費します）。
