## 4. 実装の要点（設計との対応）

### 4.1 approved_sha（§1・受け入れ 1〜4・11）

`thth/approval.py::compute_approved_sha()` — `section`（媒体節・前後空白を落とす）・
`account`・`reply_to`・`topic`（先頭 `#` と空白を落として正規化）・`publish_at`
（`datetime.isoformat()` に揃える）を、この順で `\x1f`（ASCII unit separator）区切りに
連結した sha256。`thth approve` が書き、`select.select_one()` の条件 8b が
毎回計算し直して比較する。不一致・欠落は `approval_stale` で落とし、
`needs_review` にも入れる。

`thth approve` は CLI のみに実装した（`mcp/server.py` には追加していない。
`git diff 80d9a11 HEAD -- mcp/server.py` が空であることで確認できる）。

### 4.2 send の digest（§1b・受け入れ 6）

`thth/approval.py::compute_send_digest()` — `text`・`account`・`reply_to`・`topic`
（`publish_at` を含まない、というレビューの指示どおり）を同じ区切りで連結した
sha256 の先頭 12 桁。dry-run が表示し、`--production --confirm <digest>` が
一致しないと `core.send_once()`（内部は `_send_locked()`）が送信前に拒否する
（`confirm_missing`／`confirm_mismatch` を runs に記録）。

### 4.3 clone 単位のロック（§2・受け入れ 7・8）

`thth/accounts.py::repo_lock_path_for()` が `repo_dir` を `os.path.realpath()` で
正規化し、`state/_repos/<basename>-<sha256先頭12桁>.lock` を返す。
`thth/core.py::_account_locks()`（contextmanager）が repo ロック→account ロックの
順で取得し、`throw_once()`・`send_once()` の両方の入口をこれに統一した。
`bin/thth-run` 等のラッパにはロックを置いていない（既存の設計どおり、core の
入口 1 か所だけ）。

### 4.4 送った本文の完全性（§3・受け入れ 9・10）

`thth/core.py::_throw_chosen()`:
1. 公開の**直前**に `approval.compute_body_hash(section)` を `inflight.json` に書く。
2. 公開に成功したら、front-matter を書き換える**前**に
   `state/<account>/sent/<post_id>.json` へ実際に送った本文・hash・時刻を書く
   （これが正本）。
3. front-matter を書き換える**直前**に、ファイルを読み直して本文の hash を
   再計算し、`sent/<post_id>.json` の hash と突き合わせる。
4. 不一致なら front-matter を書き換えず、`commit_and_push()` も呼ばず、
   `inflight.json` を残したまま `exit_code=1`（`action="inflight"`・
   `error="text_mismatch_before_writeback"`）で戻す。

**この連鎖が二重投稿を防ぐ理由**: post_id が front-matter に書かれないので、
そのファイルは select の条件 1（`post_id` があれば落とす）に掛からない。
だが inflight が残っているので、次回の `throw_once()`／`run` は入り口の
inflight チェックで即座に exit 1 になり、select 自体が呼ばれない
（`tests/test_sent_integrity.py` の後半で「次に呼ばれたら
`AssertionError`」というアダプタを渡し、実際に呼ばれないことを確認した）。

# 統括の検収（Fable・2026-09-09）

## 判定: **合格。** ただし**本番の前にもう 1 件**（下の「見つけた穴」）。

手元で **204 件緑・終了コード 0**。そのうえで、**実装セッションのテストを一切通さず、CLI から独立に攻めた**（`scratchpad/attack.sh`。隔離した accounts・repo・state を使い、本物の API には触っていない）。

| 攻め方 | 期待 | 結果 |
|---|---|---|
| 1. 承認前（`draft`） | 出ない | ○ |
| 2. `thth approve` | `approved_sha` と `approved_at` が書かれる | ○（sha256 64 桁・JST） |
| 3. 承認直後 | 出る | ○（dry-run で本文が出た） |
| 4. **本文を 1 文字だけ書き換える** | **出ない** | ○ |
| 5. 本文を戻して **`topic` だけ足す** | **出ない** | ○ |
| 6. 手で `status: approved` と書いただけ（`approved_sha` 無し） | **出ない** | ○ |

**今日ずっと口にしていた不変条件（masaru が見たものだけ出る）が、ようやく機械で守られている。**

コードも読んだ。`compute_approved_sha()` の定義は docstring で 5 項目の順序と正規化まで明記され、区切りに ASCII unit separator を使っている（印字可能文字を避けたのは正しい。本文に区切りが現れてハッシュが化ける事故を防ぐ）。ロックは repo → account の順で固定。書き戻し前の照合で**ファイルが読めなかった場合も「食い違い」として止める**（`except OSError` → `current_section = None` → hash 不一致）。**fail-closed になっている。**

## 実装セッションが挙げた「穴かもしれない箇所」2 件への裁定

| 論点 | 裁定 |
|---|---|
| 書き戻し前の `except OSError` は理論上の防御で自信がない | **これでよい。** 読めなければ「食い違い」に倒れ、書き戻さず再公開せず inflight を残す。**迷ったら止まる**側に落ちているので、想定外の失敗が起きても安全側 |
| `send` の digest 12 桁の衝突耐性 | **問題ない。** 12 桁 16 進＝48 ビットで、しかも**攻撃者を想定する場面ではない**。守りたいのは「別の本文の digest を貼ってしまう」「前の実行の digest を使い回す」といった取り違えで、偶然の衝突は現実的に起きない。人が扱う長さとしてもこれ以上は不便 |

## 統括が見つけた穴（**本番の前に直す**）

**`thth board` に `approval_stale` が出ない。**

`thth queue` は理由をきちんと出す（`いま出ない: 2026-09-09-x.md — approval_stale`）。しかし **board には出ない**。board は「朝に見る 1 画面」で、**承認したのに出ないものこそ board に出るべき**。

いまの board の出力はこう（T1 の「骨だけ」のまま）:

```
{'account': 'atk', 'project': 'atk', 'last_post_at': None, 'approved_waiting': 1, 'type_mismatch': 0, 'inflight': None}
```

`approved_waiting: 1` としか出ないので、**「承認して待っている」のか「承認が古くて永久に出ない」のかが区別できない**。masaru が承認して、あとで本文を直して、そのまま何日も出ない——という筋が、**どこを見ても分からない**。今日ずっと避けてきた「黙って失敗する」の形そのもの。

**直すこと**: board に `approval_stale` の件数とファイル名を出し、**「要確認」の印を付ける**。あわせて `thth throw` を手で打ったときの出力も「出すものが無い」だけで終わらせず、**落ちた理由を添える**（人が手で打つのは何かを確かめたいときなので、黙って終わるのがいちばん困る）。board 全体の整形は T4 の仕事だが、**この 1 点は本番の前**に入れる。
