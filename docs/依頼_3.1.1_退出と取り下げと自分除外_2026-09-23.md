## 1. 退出（`thth account leave`）の「共有」判定を token の中身に限る（P2）

**実測**: kopicha-server-mastodon と kopicha-mastodon は同じ mastodon.social の同じ利用者（user_id 同一）。`thth/leave.py` の `inventory()` は `same_value or same_grant` を `shared` と扱い、Mastodon／X では `shared_credential_revoke_refused` を投げて **退出が最後まで通らない**（phase=worker_revoked で止まる）。実際は 2 つの token は別の bytes で、Mastodon の `/oauth/revoke` は渡した token だけを失効させる（他方に影響しない）。

**直し**:
- `same_grant`（同じ instance／service＋同じ user_id）は **Mastodon と X では shared にしない**。Threads と Bluesky は従前どおり（遠隔の失効は本人の手・`unconfirmed_manual`）。
- `same_value`（access_token／refresh_token／app_password の値が一致）・同じ path／inode・app directory 配下は従前どおり shared。
- `_run_locked` の `shared_credential_revoke_refused` は `same_value` 由来の shared のときだけ出る形を保つ。
- 退出が通ったあと、**同じ本人の別 account の token file と台帳に触っていない**ことを試験で固定。

**試験**（fake Mastodon の loopback）: (a) 同 instance・同 user_id・別 token の 2 台帳 → leave は `completed`・`/oauth/revoke` に来た token は自分の値だけ・他方の token file は byte 一致で残る・他方の台帳は `stopped` にならない。(b) 同じ token bytes の 2 台帳 → 従前どおり `shared_credential_revoke_refused`。(c) Threads で同 user_id → 従前どおり `token_shared`＝preserved。単変異: `same_grant` を shared に戻す 1 本（(a) が落ちること）。

## 2. Mastodon の取り下げ（投稿の削除）を足す（P2）

**実測**: `thth_retract_request`／`thth retract` は Mastodon で `unsupported_operation`（`adapters/mastodon.py` に `DELETE_PERMISSION` が無い）。Threads と X だけ実装済み。

**直し**（`thth/adapters/mastodon.py`）: `DELETE_PERMISSION = "write:statuses"`・`delete_post(post_id)` を Threads（`adapters/threads.py:474`）と同じ骨で。一次資料は Mastodon API `DELETE /api/v1/statuses/:id`（scope `write:statuses`・応答は削除した status の JSON・本文は `text` に入る）。**DELETE は 1 回・再試行しない**。`post_id` は数字だけ。403／401 は `_raise_if_permission` 相当で `PermissionMissing`、404 は静的理由 `post_missing`（既に無い）を `AdapterError` に。応答 JSON の `id` が要求した `post_id` と一致しなければ成功と言わない。
- `retract_cli`・`server_writes`・`approval_jobs` は `DELETE_PERMISSION` を見て分岐しているので、adapter を足せば通るはず。**通ることを試験で確かめる**（CLI の二段承認・MCP の `retract_request` → 承認 → worker が削除）。
- `thth/scopes.py` の `MASTODON_SCOPES` に `write:statuses` が入っているか確認。無ければ**足さない**（再認可を要するので別件）——その場合は `missing_permissions` で `permission_unavailable` の静的理由が出ることを試験にし、依頼書に明記。
- `media_capabilities` や doctor・`docs/使い方_*.md` に「取り下げ: Threads／X のみ」の記述があれば Mastodon を足す。

**試験**: fake Mastodon（loopback）で DELETE 200 → `retracted_at` が記録される／403 → 静的理由／404 → `post_missing`／`id` 不一致 → 成功と言わない。単変異: 応答 `id` の照合を外す 1 本。

## 3. 毎朝の一枚の「絡みに行く先」から自分を利用者 ID で除く（P3）

**実測**: `thth morning kopicha` の世間（Mastodon・語「コーヒー」）の絡む先に、同じ本人の別台帳（kopicha-server-mastodon＝@kopi_chaba）の投稿が「自分の履歴 いいえ」で出た。`where` の自分除外は台帳 1 つの author_key しか見ていない。

**直し**（`thth/morning.py` の `_world`、必要なら `where_cli.answer`）: project 内の**同じ媒体の全 account** の author_key（`adapter_base.author_key(medium, handle)`・user_id があれば user_id も）を集め、`targets` と `next_steps` の `engage` から除く。件数（`n`／`distinct_authors`）は変えない。除いた本数を `own_excluded` として cell に足す（分母の規律）。`morning <account>`（単体）でも同じ project の他 account を見る。

**試験**: 同じ handle の 2 台帳（mastodon）と、その handle の投稿を含む fake の `where` 結果 → `targets` に出ない・`own_excluded: 1`・`n` は変わらない・`next_steps` の `engage` にも出ない。単変異: 除外を外す 1 本。

## 4. 運用通知の案内（P3）

**実測**: `thth run` の stderr「運用通知に未完了があります: thth notifications status で確認してください」に account 名が無く、そのまま打つと `account_required` の ValueError が汎用文「通知操作に失敗しました…」に潰れて rc 2。正しくは `thth notifications status <account>`。

**直し**: (a) `thth/cli.py:2371` の案内に account 名を入れる。(b) `thth/incident.py` の `command()` で `account_required` は汎用文でなく静的に「`account_required`: `thth notifications status <account>` の形で account を指定してください」を stderr に出し rc 2（他の ValueError は従前どおり）。

**試験**: account 無しの `status`／`test` が `account_required` を出す・案内文に account 名が入る。単変異なし（文言）。
