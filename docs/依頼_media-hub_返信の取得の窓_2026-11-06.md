# 依頼: media-hub へ「返信の取得が無い」の鳴らし方を変えてほしい（2026-11-06）

THTH の開発セッションから、media-hub の担当へ。本線（メディアハブ本線）の了承は済んでいます。

## 頼みたいこと

`hub/snsobs.py` は口座ごとの `replies.last_fetch_hours` が `FETCH_WARN_H`（24 時間）を超えると「返信の取得が N 時間無い（THTH開発へ）」を鳴らしています。これを次のように変えてください。

- `replies.live_posts == 0` のときは鳴らさない。取り直しの窓の中に投稿が 1 本も無いので、取り直しが来ないのは正しい動きです。
- `replies.live_posts` が `null` のとき（取り直しが無効の口座・言えないとき）と、欄そのものが無いとき（古い THTH）は、今までどおり `last_fetch_hours` で判断する。
- `live_posts` が 1 以上のときも今までどおり。このときは `follow_last_hours` も添えると、どちらが止まっているかが分かります（下の「読み方の例」）。

THTH 側の欄は `thth observe <project> --json --no-mark --counts-only --no-world` の出力に入ります。呼び方は変えなくてよいです。

## 経緯（nigamilab-fb の件）

- nigamilab-fb は投稿が 1 本（11/03）しかありません。
- THTH は、会話が続いている投稿だけを 20 分おきに取り直します（`thth/reply_follow.py`）。会話が続いている＝投稿から 48 時間以内か、最後の返信（他人の返信か自分の返信）から 48 時間以内、です。この投稿は返信が無いまま 48 時間たち、取り直しの窓が閉じました。
- そのあとは投稿からの時間の刻み（1・6・24・72・168 時間）でしか取りに行きません。24 時間の次は 72 時間なので、その間は取得が無いのが正しい動きです。
- ところが hub は 42 時間で「返信の取得が無い」を鳴らしました。
- 原因は 2 つあります。
  1. `last_fetch_hours` は repo の台帳の `kind: fetch` の行だけから数えています。新しい返信の無い取り直しは repo に書かない決まりです（masaru 10/21）。最後に取り直した時刻は VM の `state/<口座>/reply_follow.json` にしかなく、hub からは見えませんでした。
  2. 窓が閉じたかどうかが observe の出力に無く、hub は「取りに行くはずなのに来ない」のか「取りに行かなくて正しい」のかを見分けられませんでした。
- hub の今の除外（最後の投稿が 168 時間より古い口座は鳴らさない）は、刻みの終わりしか見ていません。窓が閉じた 48〜168 時間の間が抜けていました。

## 新しい欄（`sections[unanswered].value.by_account.<口座>.value.replies.value` の中）

| 欄 | 意味 | 言えないとき |
|---|---|---|
| `live_posts` | 取り直しの窓の中にある自分の投稿の数。投稿から `live_hours` 以内か、最後の動き（返信・自分の返信）から `live_hours` 以内。20 分の間隔は見ない（今取り直したばかりでも窓の中なら数える）。採取が見ない古い投稿（`collect_days` を超えたもの）と未来の投稿は数えない。 | 取り直しが無効の口座（X の既定・台帳で `enabled: false`）は `null`。自分の送った記録が読めないときも `null`。 |
| `live_hours` | その口座の窓の長さ（台帳の `reply_follow.live_hours`・既定 48）。 | — |
| `follow_last_at` | VM の `reply_follow.json` にある、この口座で最後に取り直した時刻（ISO・JST）。 | ファイルが無い・壊れている・行が無いときは `null`。 |
| `follow_last_hours` | `follow_last_at` から今までの時間（小数 1 桁）。 | 同上で `null`。 |
| `follow_cannot_say` | 上の欄を言えない理由のコードの並び。言えれば空。`follow_disabled`（取り直しが無効）・`sent_unreadable`（送った記録が読めない）・`follow_state_missing`（reply_follow.json が無い）・`follow_state_unreadable`（JSON として読めない）・`follow_state_malformed`（形が違う）・`follow_state_empty`（行が無い）。 | — |

- 言えないときに黙って 0 にはしません。`live_posts == 0` は「数えた結果 0 本」だけです。
- `last_fetch_at`・`last_fetch_hours` の意味は変えていません（台帳の `kind: fetch` の行だけから数える）。
- `--counts-only` は数と状態の欄を残すので、上の欄はすべて出ます。投稿の id は出しません。
- `reply_follow.json` は取り直すたびに、`live_hours` の 2 倍より古い行を落として書き直します。窓が閉じてしばらくすると、`follow_last_at` が古いまま残るか、行が無くなって `follow_state_empty` になります。どちらも「窓が閉じたあと」なら正しい動きです。
- Webhook でコメントが届く口座では、採取は取り直しをしません（届いた分が台帳に入る）。この欄はそれを見ずに台帳の設定で数えるので、その口座では `live_posts` が 1 以上でも `follow_last_hours` が古くなりえます。今は該当の口座で困っていないので、そのままにしています。

## 読み方の例（hub 側の判断の叩き台）

```python
lp = replies.get("live_posts")
if lp == 0:
    pass                      # 窓の中に投稿が無い。鳴らさない
elif st is not None and st >= FETCH_WARN_H:
    # lp が None（言えない・古い THTH）か 1 以上。今までどおり鳴らす
    ...
```

`live_posts` が 1 以上で `follow_last_hours` が新しく、`last_fetch_hours` だけ古いときは、取り直しは動いていて新しい返信が無いだけです。鳴らすかどうかは hub の判断に任せます（今回の依頼の外）。

## THTH 側の変更

- `thth/reply_follow.py`: 窓の判定を `in_window()` に切り出し、採取の `candidate()` と observe が同じ判定を使う。`live_count()`・`last_followed()` を足した。
- `thth/unanswered.py`: `answer()` の結果に `live_posts`・`live_hours`・`follow_last_at`・`follow_cannot_say` を足した。
- `thth/morning.py`: observe の返信の段に上の欄と `follow_last_hours` を足した。
- 試験: `tests/test_observe_follow_window.py`。
- 本番に出るのは release のあと（masaru の「出して」待ち）。出るまでは欄が無いので、hub は「欄が無ければ今までどおり」で先に入れて構いません。
