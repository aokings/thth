### 1 — edit list は全媒体で警告（`fec68cc`）

**所見。** `media.manifest_for` が実機の MP4 を Mastodon と Bluesky で `MediaError('duration_unverifiable')` にし、Threads だけが受けていた（`format mp4 kind video 720×1280 5.0 s`）。原因は `MEDIUM_POLICY`（`thth/media.py`）で Threads だけが `allow_edit_lists=True` を持っていたこと。他の媒体は `thth/mediaformats.py` の `bmff` で `elst` を見た時点で「秒数を確認できない構造」として断っていました。

**裁定。** edit list はどの媒体でも拒否の理由にしません（設計 §0）。ffmpeg は AAC の priming と `+faststart` で普通に `elst` を書きます。断れば **thth だけが、媒体の受け取るものを落とす**ことになります。

**実装。**

- `bmff` / `inspect` から `allow_edit_lists` を外しました。構造検証済みの `elst`（version 0/1・entry 数と box 長の一致）は全媒体で受け、静的な警告 `edit_list_present` を `Inspection.metadata_notes` に足します。秒数は Threads と同じく movie header（`mvhd`）から取ります。隣接 metadata の走査（`uuid`・未知 box・`free/skip` の全 0・位置 key）は 1 文字も緩めていません。
- `duration_unverifiable` は本当に秒数の無い構造だけに残しました: fragment（`moof` / `mvex`）と、`mvhd` の timescale か tick が 0／未設定（`0xFFFFFFFF`）のもの。`bmff` が使っていた `duration_unavailable` は `duration_unverifiable` に統一しました（ほかの利用箇所はありません）。
- `media.prepared_component` の notes の許可集合に `edit_list_present` を足しました。`media.display` はこれを `warning: edit_list_present` として承認前に出します。Threads の `video_notes` が出す `warning: threads video has edit lists; provider may refuse`（媒体固有の見立て）はそのまま残ります。

**試験**（`tests/test_v213_threads_video.py`）:

1. `test_ffmpeg_edit_list_is_a_note_on_every_medium` — ffmpeg 形（`trak` 下の `edts`/`elst`・`moov` 先頭）の MP4 を threads / bluesky / mastodon の 3 媒体が `mp4 / video / 720×1280 / 5.0 秒`・notes が `['edit_list_present']` で受け、bytes が 1 byte も変わらないこと。
2. `test_movie_header_without_seconds_stays_unverifiable` — timescale 0 と tick 0 は 3 媒体とも `duration_unverifiable` のままであること。
3. `test_valid_edit_list_and_late_moov_warn_only`（改名）— 同じ file が Mastodon でも通り、notes が `['edit_list_present']` になること（従来はここで `duration_unverifiable`）。
4. `tests/test_v213_bluesky_webm_named.py::test_policy_table_names_every_medium` — `MEDIUM_POLICY` に edit list の分岐が残っていないこと。

**変異。** (a) `elif kind==b'elst':` の枝を殺す → 12 本が落ちる。(b) `metadata_notes.add('edit_list_present')` を消す → 4 本が落ちる。(c) `duration=None if not ticks or …` の `not ticks` を消す → 1 本が落ちる。

**影響（運用が知る必要のあるもの）。** `elst` を持つ MP4 の manifest に notes が 1 つ増えるので、**承認の digest が変わります**。2.13.0 で取った Threads の承認（`--confirm <digest>`）は、同じ file でも 2.13.1 では `approval_stale` になります。取り直してください。

### 2 — `send` が断るときは理由と次の一歩を必ず言う（`673cb1e`）

**所見。** dry-run が `mode: rehearsal` の 1 行だけ出して 2 で終わりました。`core._send_locked`（`thth/core.py`）は `manifest_for` の例外を `ThrowResult(exit_code=2, action='invalid_attachment', message=<理由>)` にして返していたのに、`cmd_send`（`thth/cli.py`）が `exit_code` しか見ていませんでした。

**実装。**

- `cmd_send` が `ThrowResult` を受け取り、exit が 0 でなければ理由を 1 行で言います（stderr）。core が既に `log` した行は二度言いません（同じ 1 行なので）。
- `media_delivery.MEDIA_NEXT_STEPS` / `next_step` / `refusal_lines`: 媒体の理由に**静的な**次の一歩を 1 行つけます。`duration_unverifiable` →「動画の構造から秒数を確認できません。ffmpeg -movflags +faststart で出し直す」。ほかに `dimensions_unavailable`・`location_metadata_present`・`location_metadata_unverifiable`・`invalid_attachment_structure`・`unsupported_attachment`・`media_limit_exceeded`・`media_capability_unavailable`・`media: alt_too_long`・`media: source_unreadable`・`media: source_changed`。既存の `UNSUPPORTED_ATTACHMENT_NOTES` と同じ規律で、**入力値・ファイル名・パスは 1 つも反射しません**。個別の次の一歩（`aac_adts` の「m4a に入れ直す」など）が既に出ていれば重ねません。

**試験**（`tests/test_v2131_send_dry_run.py`）: `test_dry_run_states_the_media_reason_and_a_next_step` — fragment（`moof`）の MP4 で dry-run が 2 を返し、出力の 1 行目が `mode: rehearsal` のまま、理由 `duration_unverifiable` と `+faststart` の次の一歩が出ること。出力に repo のパスも `v.mp4` という file 名も出ず、`/`+英字で始まる絶対パスが 1 つも無いこと。provider への呼び出しと upload が 0 件であること。

**変異。** `cmd_send` の `print(line, file=sys.stderr)` を `pass` にする → 1 本が落ちる。

### 3 — dry-run は publish が断るものをここで断る（`e753dd2`）

**所見。** 8,080,112 bytes の公開 JPEG に dry-run が digest を出しました。Threads の暫定バイト上限（`thth/adapters/threads_media.py` の `MAX_BYTES = 8_000_000`）は本番の preflight でしか見ていませんでした——**見せたものが出せない**という、一番困る形です。

**実装。**

- `core._send_locked` の rehearsal が、媒体の上限を lint と同じ 1 か所（`media_delivery.lint_notes`）で見ます。2 か所に書けば必ずずれるので、新しい検査は 1 行も足していません。`warning: ` で始まらない行が出たら digest を出さず exit 2 と理由を返します（Threads の bytes / 比 / 枚数、Bluesky の 2,000,000 と枚数、Mastodon の生 instance 上限）。警告は本文・添付の表示のあと digest の前に出します。
- `lint_notes(..., unreachable_warns=True)` が予行だけの 1 点の違いです。instance に**届かない**ときは断らず `media_delivery.CAPABILITY_UNOBSERVED`（`media limits: capability_unobserved (latest instance check required before upload)`）を警告として言います。予行は upload ではなく、上限は upload 直前にもう一度観測するためです。**届いた答えが不正・上限超過なら予行でも断ります**。接続の失敗とそれ以外は `_Unreachable` で区別してあるので、ローカルの添付が原因の失敗を巻き込みません（`pin_sources` は OSError を `MediaError` に畳んでいるので、素の OSError は網の外だけから来ます）。
- `cached_note` の「何も観測していない」文言を `CAPABILITY_UNOBSERVED` に括り出しました。保存済みの上限があっても、届かなかった run では「この run では何も観測していない」と言います（保存値を根拠に見せません）。

**試験**:

1. `tests/test_v2131_send_dry_run.py::test_threads_byte_cap_is_applied_in_the_dry_run` — 公開 8,000,001 bytes の JPEG は dry-run が exit 2 と `media_limit_exceeded: bytes`、8,000,000 は digest（どちらも provider 呼び出し 0 件）。entropy-coded data を詰めて**公開 bytes をちょうどその長さ**にしてあります。
2. `tests/test_v213_mastodon_media.py::test_lint_instance_failure_never_uses_permissive_cache`（追記）— 届かない instance は `unreachable_warns=True` で `capability_unobserved` の警告 1 行だけ。保存済みの上限は残っているのに使わないこと。lint（既定）は従来どおり `media_capability_unavailable` で断ること。
3. `tests/test_v213_mastodon_media.py::test_rehearsal_still_refuses_limits_the_instance_did_answer` — instance が答えた上限の超過（`media_limit_exceeded: bytes`）と、答えが欠けている場合（`media_capability_unavailable: image_size_limit`）は予行でも断ること。

**変異。** (a) rehearsal の `refusals` を `[]` に固定 → 1 本が落ちる。(b) `unreachable_warns` の枝を殺す → 1 本が落ちる。

**影響（運用が知る必要のあるもの）。** Mastodon の `send` dry-run が `/api/v2/instance` を 1 回読むようになりました（**公開 endpoint・`Authorization` を送らない・POST も upload もしない**）。既存の試験 `test_cli_source_only_stale_is_loud_and_has_no_provider` をこの前提に合わせて直してあります（予行の呼び出しが GET `/api/v2/instance` だけで資格情報を含まないことを見る）。

### 4 — FINISHED の直後に出さない・4xx は Graph の番号を名指す（`23a0805`）

**所見。** 画像の添付公開が、container が FINISHED になった直後の `threads_publish` で `media_publishing_http_400` になりました。journal の container はあとから見ても FINISHED で `error_message` はありません。

本文の経路（`thth/adapters/threads.py`）は container を作ったあと `wait_seconds`（`DEFAULT_WAIT_SECONDS` = 30 秒・env `THTH_THREADS_WAIT_SECONDS`）待ち、**待ったあとに** `before_publish` をもう一度通してから公開しています。添付の経路（`thth/adapters/threads_media.py`）だけが FINISHED を見た瞬間に公開していました。FINISHED は「もう出せる」ではありません。

**実装。**

- (a) `threads_media.publish` に `settle()` を足しました。最終 container（単体・TEXT・CAROUSEL のいずれも）が FINISHED になり `on_container_created` を通したあと、同じ `adapter.wait_seconds` を待ちます（env の上書きは `ThreadsAdapter.from_account` が既に読んでいるので自動で効きます）。待ちは**付与の期限を越えません**——越えれば URL が死んで必ず出せなくなるので、そのときは待たずに出します。待ったあとに既存の `veto()`（source の再検査・`before_publish`・付与の期限）を通してから publish します。journal の phase は増やしていません（`ready` のまま待ち、`publishing` で POST）。
- (b) 4xx の本文を `api_diagnostic.read_http_error` で読み、**番号だけ**を理由の尾に足します（`graph_codes`）: `media_publishing_http_400_code_100_subcode_2207032`。message・type・fbtrace は取りません（静的な理由の前提と redact を崩さない）。理由は journal の `reason` と CLI の `公開失敗: …` の両方に出ます。held／unknown／definite の区分は 1 文字も変えていません。

**試験**（`tests/test_v2131_threads_publish_wait.py`・固定時計）:

1. `test_publish_waits_the_same_wait_seconds_after_finished` — FINISHED を読むのは 0 秒、`threads_publish` は 30 秒待ったあとに 1 回だけ。眠りは 30 秒ちょうど 1 回。
2. `test_the_wait_never_outlives_the_grant` — 画像の付与 600 秒に対し `wait_seconds=1800` なら 0 秒で切り上げて出す。
3. `test_the_veto_after_the_wait_is_honoured` — 30 秒を過ぎてから断る veto が効き、`threads_publish` は呼ばれず journal は `held` ／ `reason=stopped_after_wait`。
4. `test_publish_4xx_names_the_graph_numbers_and_nothing_else` — 400 の本文の `code` / `error_subcode` が数字だけで理由に出て、`message` ・ `type` ・ `fbtrace_id` は journal にも理由にも出ない。
5. `test_a_4xx_without_numbers_keeps_the_plain_reason` — 番号の無い 4xx（本文なし・message だけ・error が文字列）は素の `media_publishing_http_400` のまま。
6. `test_the_env_override_reaches_the_attachment_path` — `THTH_THREADS_WAIT_SECONDS=7` が `from_account` 経由で adapter に載る。

**変異。** (a) `settle()` の呼び出しを消す → 1 本が落ちる。(b) `reason+=graph_codes(exc)` を消す → 1 本が落ちる。

**限界。** 実機の 400 が「まだ出せない」だったのか「その要求が不正」だったのかは、番号が取れていないので**判りません**。この直しは、次に同じことが起きたときに番号で見分けられるようにするものと、本文の経路と同じだけ待つことの 2 つで、原因の断定ではありません。
