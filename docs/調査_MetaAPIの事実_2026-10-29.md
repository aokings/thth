# 調査: Meta の API の事実（2026-10-29）

THTH で Meta の API を「使い倒す」計画の土台。**設計はしない**。Meta の公式文書（developers.facebook.com・facebook.com/business）から事実だけを集めた。

- 調べた日: 2026-10-29。調べた者: THTH開発のサブエージェント（Opus）。WebFetch で公式の頁を読み、要点を抜き出した（抜き出しには小さなモデルが挟まるので、数字は頁の原文で読み直すのが確実）。
- 印: **【公式】**＝公式の頁で読んだ。**【推測】**＝公式の頁からそう読める・つなぎ合わせただけ。**【二次】**＝公式でない記事にだけある。**【未】**＝読めなかった・書いてなかった。
- 原文の長い引用はしない。言い換えで書く。数字・API 名・権限名はそのまま。
- 前提（依頼文の通り）: アプリ THTH（1648991573463758）・Live・吾徳でビジネス認証済み・Graph API v26.0・Facebook Login for Business の構成で 19 権限＋public_profile を許可済み・Standard Access のまま・役割のある masaru の資産だけを使う。

## 0. 前提・既存の手順書との食い違い（見つけたもの）

1. **動画の投稿に `publish_video` は要らない見込み。** 手順書 §3-1 は `publish_video` を「動画の投稿」としているが、権限の参照では `publish_video` は**ライブ動画**を出すための権限。ページへの普通の動画（`/{page-id}/videos`）とリール（`/{page-id}/video_reels`）の公式の手引きが挙げる権限は `pages_show_list`・`pages_read_engagement`・`pages_manage_posts` だけ【公式】。ただし Pages API の「Posts」の頁には「動画には `publish_video`」と書いた行もあり、頁どうしで揺れている【公式・食い違い】。
   - 出典: https://developers.facebook.com/docs/permissions ・ https://developers.facebook.com/docs/video-api/guides/publishing ・ https://developers.facebook.com/docs/video-api/guides/reels-publishing ・ https://developers.facebook.com/docs/pages-api/posts
2. **公式の広告 MCP サーバーを THTH のアプリで使うには、今の 19 権限では足りない。** トークンに `ads_mcp_management` が要り、アプリにユースケース「広告 MCP サーバーで広告を作成・管理」を足す必要がある【公式】。手順書 §2 A は「広告 MCP サーバー」を足さないとした。ユースケースは足すと消せない（手順書 §0 の 2）。
   - 出典: https://developers.facebook.com/documentation/ads-commerce/ads-ai-connectors/ads-mcp-server/ads-mcp-server-get-started.md
3. **Marketing API の段階の名前が変わっている。** 「Ads Management Standard Access」は「Marketing API Access Tier」に、その中の Standard は **Limited Access**、Advanced は **Full Access** に改名【公式】。手順書 §3-3 の「Ads Management Standard Access」は旧名。中身は変わらない（コードの変更不要）と書いてある【公式】。
   - 出典: https://developers.facebook.com/docs/marketing-api/overview/authorization
4. **コメントの頁に `pages_read_user_engagement` という権限名が出るが、権限の参照には無い。** 参照にあるのは `pages_read_user_content`（THTH が許可を得ている方）と `pages_read_engagement`【公式・食い違い】。誤記と見るのが自然【推測】。
   - 出典: https://developers.facebook.com/docs/pages-api/comments-mentions ・ https://developers.facebook.com/docs/permissions
5. **予約投稿の上限日数が頁ごとに違う**（§1-2）。**Instagram の 1 日の公開上限も頁ごとに違う**（§2-2）。

## 1. Pages API（Facebook ページ）

### 1-1. 投稿の種類

| 種類 | 口 | 要るもの | 印 |
|---|---|---|---|
| 文 | `POST /{page-id}/feed` に `message` | ページトークン（CREATE_CONTENT の役目）・`pages_manage_posts`・`pages_read_engagement`・`pages_show_list` | 【公式】 |
| リンク | 同じ口に `link`（`message` か `link` のどちらかは必須） | 同上。リンクの見出し・画像を差し替えるには、そのリンクのドメインがページの持ち物である必要（`ownership_permissions{can_customize_link_posts}` で確かめる） | 【公式】 |
| 写真 1 枚 | `POST /{page-id}/photos` に `url`。写真 id と投稿 id が返る | 同上 | 【公式】 |
| 複数の写真 | 写真を `published=false` で上げ、`/feed` の `attached_media`（`media_fbid` の並び）で 1 本にまとめる | 同上 | 【二次】公式の頁では手順を見つけられなかった。開発者フォーラムに「写真は混ぜられるが動画は混ぜられない」という報告がある |
| リンクのカルーセル | `/feed` の `child_attachments` に 2〜5 件（`multi_share_optimized` なら 10 件まで上げられ、見せるのは上位 5 件） | 同上 | 【公式】 |
| 動画（普通） | 再開できるアップロード（`/{app-id}/uploads` → ハンドル）→ `POST graph-video.facebook.com/{page-id}/videos` | `pages_show_list`・`pages_read_engagement`・`pages_manage_posts`（CREATE_CONTENT） | 【公式】大きさ・長さの上限は頁に無かった【未】 |
| リール | `POST /{page-id}/video_reels`（`upload_phase=start`）→ `rupload.facebook.com` に送る → `upload_phase=finish`・`video_state` は `DRAFT`/`SCHEDULED`/`PUBLISHED` | 同上 | 【公式】 |
| ストーリー（動画） | `/{page-id}/video_stories` を start → 送る → finish。`is_ai_generated` を付けられる | 同上（システムユーザーなら `business_management` も） | 【公式】 |
| ストーリー（写真） | `/{page-id}/photos` に `published=false` で上げ → `/{page-id}/photo_stories` に `photo_id` | 同上 | 【公式】 |

- リールの仕様: mp4 推奨・9:16・1080x1920 推奨（最低 540x960）・24〜60fps・**3〜90 秒**・音声 AAC 48kHz ステレオ 128kbps 以上。ストーリーとして出すリールは 60 秒まで【公式】。
- **リールは 24 時間の移動窓で 30 本まで**（API から出した数・公開の口で数える）。共同制作の招待は 1 ページ 24 時間で 10 件【公式】。
- ストーリーの写真: jpeg・bmp・png・gif・tiff、10MB まで。動画は 60 秒まで。前に投稿に使った写真・動画はストーリーに使えない【公式】。
- 共通の落とし穴: 置き場のサーバーが robots.txt で Facebook の取得役（facebookexternalhit）を拒んでいると断られる。fbcdn の URL も断られる。ページへの公開はいつも「公開」で、公開範囲の選択肢は「Public」だけにせよ、と書いてある【公式】。
- 出典: https://developers.facebook.com/docs/pages-api/posts ・ https://developers.facebook.com/docs/graph-api/reference/page/feed ・ https://developers.facebook.com/docs/video-api/guides/publishing ・ https://developers.facebook.com/docs/video-api/guides/reels-publishing ・ https://developers.facebook.com/docs/page-stories-api ・（二次）https://developers.facebook.com/community/threads/468936873748863/

### 1-2. 予約投稿（`scheduled_publish_time`）

- `published=false` と `scheduled_publish_time`（UNIX 秒・ISO 8601・strtotime で読める文字列）で予約【公式】。
- **範囲が頁ごとに違う**:
  - Pages API「Posts」の手引き: 10 分後〜**30 日**後【公式】。
  - `/feed` の参照: 10 分後〜**75 日**後【公式】。
  - リール: 10 分より先〜**29 日**以内【公式】。
  - 安全側は「10 分〜29 日」【推測】。
- 出典: https://developers.facebook.com/docs/pages-api/posts ・ https://developers.facebook.com/docs/graph-api/reference/page/feed ・ https://developers.facebook.com/docs/video-api/guides/reels-publishing

### 1-3. 編集・削除

- 編集: `POST /{page-post-id}` に変える欄。**そのアプリで作った投稿しか編集できない**【公式】。
- 削除: `DELETE /{page-post-id}`【公式】。
- 出典: https://developers.facebook.com/docs/pages-api/posts

### 1-4. 読み取り

- `GET /{page-id}/feed`: 役目（CREATE_CONTENT・MANAGE・MODERATE のどれか）＋ `pages_read_engagement`・`pages_read_user_content`。過去 1 年の約 600 本（順位づけされたもの）まで、`limit` は 100 まで。期限切れの投稿は取れない。未公開の投稿も混ざるので `is_published` で分ける【公式】。
- 他人のページを読むには Page Public Content Access（機能・審査）【公式】。
- 出典: https://developers.facebook.com/docs/graph-api/reference/page/feed

### 1-5. コメント

- 読む: `GET /{page-post-id}/comments`（`fields=from,message`）。コメントした人は PSID（ページごとの id）で返る【公式】。
- ページとして書く: `POST /{page-post-id}/comments` か `POST /{comment-id}/comments`。作者はページになる【公式】。
- 人に言及した返事: 本文に `@[PSID]` の形。言及できるのは、その投稿にコメントした人か投稿した人だけ。ページの設定で「他の人がこのページをタグ付け」を許している必要。機能「Page Mentioning」が要る【公式】。
- 非表示: `POST /{comment-id}` に `is_hidden`（ページのコメントにだけ効く）。本文の編集は `message`【公式】。
- 削除: `DELETE /{comment-id}`【公式】。訪問者のコメントを消すのは `pages_read_user_content` の範囲、ページとしてのコメントの作成・編集・削除は `pages_manage_engagement`【公式・権限の参照】。
- `can_reply_privately`・`private_reply_conversation` という欄があり、コメントへの非公開の返事（Messenger）がありうる【公式】。手順は Messenger の側の文書【未】。
- 要る役目: MODERATE と CREATE_CONTENT【公式】。
- 出典: https://developers.facebook.com/docs/pages-api/comments-mentions ・ https://developers.facebook.com/docs/graph-api/reference/comment ・ https://developers.facebook.com/docs/permissions

### 1-6. メッセージ（Messenger。扱うかの判断材料だけ）

- `pages_messaging` が要る（THTH は許可を得ていない）。ページの役目 MESSAGING が要る【公式】。
- 開発者ポリシー: 返事は利用者が最後に送ってから **24 時間**の窓の中（Messenger・Instagram の広告から来た会話は最長 7 日）。窓の外はメッセージタグ・テンプレートを本来の用途でだけ。タグや utility メッセージで宣伝してはいけない（宣伝は Marketing Messages API）。法で要る同意があるときだけ連絡してよい、配信停止の求めはすぐ守る。メッセージの本文を前もって埋めない（アプリの利用者や事業者の社員が書いたものは別）。悪い反応が多いと制限・停止がありうる【公式】。
- Messenger の量の上限は「200 × 関わった人の数 / 24 時間」【公式】。
- 出典: https://developers.facebook.com/devpolicy/ ・ https://developers.facebook.com/docs/graph-api/overview/rate-limiting ・ https://developers.facebook.com/docs/graph-api/webhooks/getting-started/webhooks-for-pages

### 1-7. ページのインサイト（指標の廃止に注意）

- 口: `GET /{page-id}/insights`・`GET /{post-id}/insights`。権限 `read_insights`・`pages_read_engagement`、ANALYZE の役目のある人のページトークン【公式】。
- 期間: `day`・`week`・`days_28`・`month`・`lifetime`・`total_over_range`。**過去 2 年分まで**、`since`/`until` で一度に **90 日**まで、ほとんどの指標は 24 時間に 1 回の更新、ページ単位の数は「いいね」100 以上、属性は 100 人以上【公式】。
- **v25.0（2026-02-18）の告知**: 次の指標は v26.0 の出たときに**全版で外れ**、呼ぶとエラーになる【公式】。
  - ページ: `page_impressions_unique`・`page_posts_impressions`・`page_video_views_unique` など → 置き換えは `page_total_media_view_unique`（重複なしの表示）・`page_media_view`（有料・自然の内訳）。
  - 投稿・動画: `post_impressions_unique`・`post_video_views_unique`・`total_video_impressions` など → `post_total_media_view_unique`・`post_media_view`。
  - ストーリー: `PAGE_STORY_IMPRESSIONS_BY_STORY_ID`（_UNIQUE も）→ `STORY_MEDIA_VIEW`・`STORY_TOTAL_MEDIA_VIEW_UNIQUE`。
- 参照の頁には「2026-06-15 までに多くの指標が全版で廃止」とある【公式】。`page_impressions_unique*`・`post_impressions*`・`post_impressions_unique*`・`page_video_views_unique` などに「v25 以降は使えない」の印【公式】。
- 二次の記事では、置き換え先の数は前の「リーチ」と同じ値ではない（重複なしの表示は低めに出る）という注意がある【二次】。
- 今も参照に載っている例: `page_media_view`・`page_total_media_view_unique`・`page_views_total`・`page_post_engagements`・`page_follows`・`page_daily_follows`・`page_daily_unfollows_unique`・`post_media_view`・`post_total_media_view_unique`・`post_reactions_*_total`・`page_video_views`・`post_video_views` など【公式】。廃止の一覧と重なる名前（`page_posts_impressions` など）が参照にまだ載っているので、**呼ぶ指標は 1 つずつ本物で確かめる**【推測】。
- 出典: https://developers.facebook.com/docs/graph-api/reference/v26.0/insights ・ https://developers.facebook.com/docs/graph-api/changelog/version25.0 ・（二次）https://improvado.io/product-updates/connectors/facebook-pages-metrics-deprecation

### 1-8. 投稿の文字数の上限

- **公式の頁では見つけられなかった**（`/feed` の参照にも Posts の手引きにも無い）【未】。
- 二次の資料が揃って **63,206 字**を挙げる【二次】。表示は数百字で「もっと見る」に畳まれる【二次】。
- リンクの見出し（`name`）は 35 字ほど、説明（`description`）は 30 字ほどで切れる【公式・`/feed` 参照】。
- 出典: https://developers.facebook.com/docs/graph-api/reference/page/feed ・（二次）https://agoras.readthedocs.io/en/latest/facebook.html

### 1-9. v26 時点の Pages の変更

- 新しいページ体験のページで `current_location`・`genre`・`network`・`parking`・`start_info` が廃止、ページ設定の `auto_publish_page_info_updates` が外れる（v26 公開から約 90 日後・日付は未定）【公式】。
- Graph API 全体: 2026-07-29 から `pretty`・`debug` は無視、`date_format` はエラー、`GET /?ids=...` はエラー。`If-None-Match`・ETag・304 は 2026-10-27 に全版で無くなる。`debug_token` は影響なし【公式】。
- 版: v26.0 は 2026-07-29 公開・終わりは未定。v25.0 は 2028-07-29 まで。v24.0 は 2028-02-18 まで【公式】。
- 出典: https://developers.facebook.com/docs/graph-api/changelog/version26.0 ・ https://developers.facebook.com/docs/graph-api/changelog

## 2. Instagram Graph API（Facebook ログイン経由・ページに紐づくプロ口座）

### 2-1. 3 つのつなぎ方（THTH は「Facebook Login」の道）

| 道 | 権限 | 鍵 | 口の場所 |
|---|---|---|---|
| Instagram API with Facebook Login | `instagram_basic`・`instagram_content_publish`・`pages_read_engagement`（ページの役割がビジネスマネージャ経由なら `ads_management`・`ads_read` も） | ページトークン（ユーザートークンでもよい口がある） | graph.facebook.com・rupload.facebook.com |
| Unified Login（新しい「API setup with Unified login」） | `instagram_basic`・`instagram_content_publish` | Business Integration System User の鍵 | 同上 |
| Instagram Login | `instagram_business_*` | Instagram の利用者トークン | graph.instagram.com |

- どの道も Standard か Advanced のアクセスが要る。Page Publishing Authorization（PPA）が要るページは済むまで出せない【公式】。
- **ページの役割がビジネスマネージャ経由の人**は、多くの口で `ads_management` か `ads_read` を足して要求される【公式】。THTH は両方を許可済み。
- 出典: https://developers.facebook.com/docs/instagram-platform/content-publishing

### 2-2. 公開の流れと上限

- 流れ: ① `POST /{ig-id}/media` で入れ物（コンテナ）を作る（`image_url` か `video_url`・`media_type`）→ ② 大きい動画は `upload_type=resumable` で rupload に送る → ③ カルーセルは子の入れ物を並べて `media_type=CAROUSEL`・`children` → ④ `POST /{ig-id}/media_publish` に `creation_id` → ⑤ `GET /{container-id}?fields=status_code` で `FINISHED`/`IN_PROGRESS`/`ERROR`/`EXPIRED`/`PUBLISHED`。状態の問い合わせは 1 分に 1 回・5 分まで、が推奨【公式】。
- **入れ物は 24 時間で期限切れ**【公式】。
- 種類: 画像（**JPEG だけ**）・動画・リール（`REELS`）・試しのリール（`trial_params`）・ストーリー（`STORIES`）・カルーセル（**20 件まで**、画像と動画の混在可、最初の画像に合わせて切り抜き・既定 1:1）。リールはカルーセルに入れられない。出たあとの `media_type` ではリール・ストーリーが区別できないので `media_product_type` を見る【公式】。
- **1 日の公開上限が頁ごとに違う**:
  - 公開の手引きの本文: 24 時間の移動窓で **100 本**（カルーセルは 1 本）【公式】。
  - 同じ頁のカルーセルの節と、`content_publishing_limit` の参照: **50**（`quota_total`）・`quota_duration` 86400 秒【公式】。
  - 本物は `GET /{ig-id}/content_publishing_limit` の `config.quota_total` を読めば分かる【推測】。THTH の自前の上限は 50 で置くのが安全【推測】。
- できないこと: ショッピングタグ・フィルター・ストーリーのステッカー（リンク・投票・場所）。メディアは公開の時点で外から取れる場所に置く。MPO・JPS は不可【公式】。
- その他: `is_ai_generated=true`（AI で作った印。カルーセルは親にだけ）・`alt_text`（画像だけ、1000 字まで、2025-03-24 追加）・`collaborators`（3 人まで、ストーリー不可）・`user_tags`・`location_id`・`cover_url`・`thumb_offset`・`share_to_feed`（リール）【公式】。
- 仕様の数字【公式】:
  - キャプション: **2200 字・ハッシュタグ 30・@ 20**。カルーセルの子にはキャプション不可。
  - 画像: JPEG・8MB・縦横比 4:5〜1.91:1・幅 320〜1440px・sRGB。
  - リール: MOV/MP4・H264 か HEVC・23〜60fps・幅 1920px まで・**3 秒〜15 分**・300MB まで・9:16 推奨。
  - ストーリーの動画: 3〜60 秒・100MB まで。ストーリーは 24 時間で消える。
- 読む: `GET /{ig-user-id}/media` は新しい方から 1 万件まで、ストーリーは入らない（`/stories` で）【公式】。
- 出典: https://developers.facebook.com/docs/instagram-platform/content-publishing ・ https://developers.facebook.com/docs/instagram-platform/instagram-graph-api/reference/ig-user/media ・ https://developers.facebook.com/docs/instagram-platform/instagram-graph-api/reference/ig-user/content_publishing_limit

### 2-3. コメント・返事・メンション

- 読む: `GET /{ig-media-id}/comments`、表示順は `/ordered_comments`（Facebook ログインの道だけ）、返事は `GET /{ig-comment-id}/replies`【公式】。
- 返す: `POST /{ig-comment-id}/replies` に `message`【公式】。
- 隠す・戻す: `POST /{ig-comment-id}`。コメント欄の開け閉め: `POST /{ig-media-id}`。消す: `DELETE /{ig-comment-id}`【公式】。
- 権限: `instagram_basic`・`instagram_manage_comments`・`pages_read_engagement`（ビジネスマネージャ経由の役割なら `ads_management`・`ads_read`）。**非公開の返事（DM）は `instagram_manage_messages`**（THTH は許可なし）【公式】。
- 量の上限を避けるため、コメントは webhook で受けるのを強く勧めている【公式】。
- 広告になった投稿の `/comments` には元の投稿と広告の両方のコメントが入る【公式】。

## 3. Marketing API（広告）

### 3-1. 物の階層と作り方

- 広告アカウント（`act_<id>`）→ キャンペーン（目的）→ 広告セット（予算・対象・置き場）→ 広告（クリエイティブを付ける）。口は `/act_<id>/campaigns`・`/adsets`・`/adcreatives`・`/ads`【公式】。
- この 4 つの作成の口は**同じ要求を繰り返しても二重にならない**（idempotent）【公式】。
- 例では `status: PAUSED` でキャンペーンを作り、`daily_budget` を広告セットに置く【公式】。予算の単位・最低額・目的の一覧（`OUTCOME_*`）・`special_ad_categories` は、読んだ頁には無かった【未】。目的に `OUTCOME_AWARENESS` などがあることは Threads 広告の頁で確認【公式】。
- v25: Advantage+ ショッピング・Advantage+ アプリのキャンペーンは作成・複製・更新できない（2026-05-19 から全版）【公式】。v26: 投票広告の作成不可（2026-10-27）・配信見込みの一部の欄の削除（2026-10-27）・ある種の広告セットで `targeting_automation.advantage_audience` を明示しないとエラー【公式】。
- 出典: https://developers.facebook.com/docs/marketing-api/get-started/basic-ad-creation ・ https://developers.facebook.com/docs/graph-api/changelog/version25.0 ・ https://developers.facebook.com/docs/graph-api/changelog/version26.0

### 3-2. 既にある投稿を広告にする（boost に当たるもの）

- クリエイティブに `object_story_id`（`<PAGE_ID>_<POST_ID>`）を入れて `/act_<id>/adcreatives` に POST。同じ `object_story_id` のクリエイティブが既にあれば、新しく作らずそれの id が返る【公式・検索の抜粋】。
- Instagram の投稿は `source_instagram_media_id`（＋ページ id・`instagram_user_id`）【公式】。投稿の側に「広告にできるか」の印 `is_eligible_for_promotion` がある（旧 `promotion_eligibility` は廃止）【公式】。
- 権限: `ads_management`・`pages_manage_ads`（ページに紐づく広告の管理）。ページの役目 ADVERTISE（広告と未公開の投稿を作る）【公式】。
- 著作権のある音楽・フィルターなどの入った投稿は広告にできない（Threads 広告の頁の記述）【公式】。
- 既存の投稿を広告にする専用の手引き（`/docs/marketing-api/ad-creative/page-posts`）は **404 で読めなかった**【未】。
- 出典: https://developers.facebook.com/docs/marketing-api/reference/ad-account/adcreatives/ （検索の抜粋）・ https://developers.facebook.com/docs/graph-api/reference/page/feed ・ https://developers.facebook.com/docs/pages-api/overview

### 3-3. Ads Insights（成績）

- `/{広告アカウント|キャンペーン|広告セット|広告}/insights`。既定で過去 30 日の基本の数。権限 `ads_read`【公式】。
- 15 分ごとに更新・**28 日を過ぎると値が動かない**・13 か月より前の期間で内訳つきだと `reach` が返らない（非同期のジョブなら 1 広告アカウント 1 日 10 回まで取れる）・非同期のレポート id は 30 日で消える・まず同期で呼び、時間切れなら非同期に【公式】。
- 返す量が多すぎるとエラー 100 / 1487534。`x-fb-ads-insights-throttle` のヘッダを毎回見て、100% に近づいたら待つ【公式】。
- 保存期間（37 か月など）は読んだ頁に無かった【未】。
- 出典: https://developers.facebook.com/docs/marketing-api/insights ・ https://developers.facebook.com/docs/marketing-api/insights/best-practices

### 3-4. 支出の上限

- 広告アカウントの `spend_cap`: 使える最大額。届くと**全部の配信が止まる**。0 は上限なし。新しい上限はかけた時点より後の支出にだけ効く。`spend_cap_action=reset` で `amount_spent` を 0 に戻す、`delete` で上限を外す。POST `/act_<id>` で変える【公式】。
- **単位の書き方が頁の中で食い違う**: 読む欄は「通貨の最小単位（USD ならセント）」、更新の引数は「普通の単位の小数（23.50 ドル）」【公式・食い違い】。円は小数を持たないので、本物で 1 回確かめる【推測】。
- `amount_spent`（上限に対する支出、上限が無ければ総額）・`account_status`（1 ACTIVE・2 DISABLED・3 UNSETTLED・7 リスク審査待ち・9 猶予期間 など）・`min_daily_budget`・`minimum_budgets`（通貨ごとの最低日予算）がある【公式】。
- 「アカウントの支出上限（account spending limit）」は Business ヘルプの側の話として参照されるだけで、中身は読めていない【未】。
- 出典: https://developers.facebook.com/docs/marketing-api/reference/ad-account

### 3-5. アクセスの段階と量の制限

- 段階（新しい名前）【公式】:

| | Limited Access（旧 Standard・既定） | Full Access（旧 Advanced） |
|---|---|---|
| 得かた | Marketing API を足すと自動 | ダッシュボードで Upgrade・条件あり |
| 量 | 広告アカウントごとに強く絞られる・「開発用」 | 軽く絞られる |
| 広告アカウント | 数に制限なし（アプリの管理者・開発者が広告アカウントの管理者として動ける） | 制限なし（相手の許可があれば） |
| Business Manager の API | 一部だけ。広告アカウント・利用者の権限・ページの管理はできない | 全部 |
| システムユーザー | 1 ＋ 管理者 1 | 10 ＋ 管理者 1 |

- Full Access の条件: 過去 15 日で Marketing API の呼び出し **500 回以上**・直近 500 回のエラー率 **15% 未満**（保つ条件も同じ）【公式】。
- **自分の広告アカウントだけなら Standard（Limited）で足りる**、他人の広告アカウントは Advanced が要る【公式】。
- 量の式（1 時間）【公式】:
  - Ads Management: Standard **300 + 40 × 動いている広告の数**（Advanced は基数 100,000）。
  - Ads Insights: Standard **600 + 400 × 動いている広告の数 − 0.001 × 利用者のエラー**（Advanced は基数 190,000）。
  - Custom Audiences: 5,000 + 40 × オーディエンス数（上限 700,000）。
- 30 日以上使わないと、広告の API のアクセスが開発者の段に下げられることがある（開発者ポリシー 10.4）【公式】。
- 出典: https://developers.facebook.com/docs/marketing-api/overview/authorization ・ https://developers.facebook.com/docs/graph-api/overview/rate-limiting ・ https://developers.facebook.com/devpolicy/

### 3-6. システムユーザーとその鍵

- ビジネスマネージャ（ビジネスポートフォリオ）の中の、人でない利用者。管理者システムユーザーはシステムユーザー・広告アカウントの作成や権限の割り当てができる。普通のシステムユーザーは割り当てられた資産だけ。日々の呼び出しには管理者でない方を、と勧めている【公式】。
- 作れる数はアプリの Marketing API の段で決まる（Limited 1＋管理者 1）【公式】。
- **アプリとシステムユーザーは同じビジネスに属している必要**。アプリを入れられるのは Marketing API が Standard 以上のアプリだけ【公式】。
- 鍵の種類: **期限なし**（更新不要・漏れたときの危険が大きい）と **60 日**（推奨・`set_token_expires_in_60_days=true`・`oauth/access_token` の `fb_exchange_token` で更新、60 日以内に更新しないと失う）。ビジネスが期限つきを強制しているときは期限なしを作れない【公式】。
- 作りかた: ビジネスマネージャの画面か、`POST /{system-user-id}/access_tokens`（`business_app`・`scope`・`appsecret_proof`）【公式】。
- 前提に照らすと: THTH のアプリは吾徳にある。こぴちゃなどのページは Instagram ごとに自動で作られた別のポートフォリオにある（手順書 §1）。**吾徳のシステムユーザーに別のポートフォリオの資産を割り当てるには、資産を吾徳へ移すか共有する手が要る**【推測】。
- Facebook Login for Business で「システムユーザーのアクセストークン」の構成を選ぶと、Business Integration System User の鍵（既定で期限なし）がもらえる。ただしこれは **Tech Provider 向け**で、利用者はビジネスポートフォリオでログインする必要、自分で持たない・管理しないビジネスに出すには Advanced が要る【公式】。
- 出典: https://developers.facebook.com/docs/marketing-api/system-users/overview ・ https://developers.facebook.com/docs/marketing-api/system-users/install-apps-and-generate-tokens ・ https://developers.facebook.com/docs/facebook-login/facebook-login-for-business

## 4. トークンと期限

- **短いユーザートークン → 長いユーザートークン**: `GET oauth/access_token`（app id・app secret・短い鍵）。長い鍵は**約 60 日**。期限切れの鍵からは長い鍵を作れず、ログインし直し【公式】。
- **長いページトークン**: 長いユーザートークンから取ると**期限なし**（特定の条件で失効・無効になるだけ）。取る人はページに役割が要る【公式】。THTH の `expires_at=0` はこれに当たる【推測】。
- **データアクセスの期限（`data_access_expires_at`）**: 認証とは別の時計。**利用者が最後に使ったときから 90 日**。過ぎると利用者はログインしたままだが、アプリは権限で守られたデータに触れなくなる。延ばすには再認可（Web なら `auth_type=reauthorize`）。サーバー側は `debug_token` で見られる【公式】。
- **期限が来ない権限**（公式の一覧）: `ads_read`・`ads_management`・`business_management`・`configure_page_transactions`・`pages_manage_ads`・`pages_manage_cta`・`pages_manage_instant_articles`・`pages_manage_engagement`・`pages_manage_metadata`・`pages_manage_posts`・`pages_messaging`・`pages_read_engagement`・`pages_read_user_content`・`pages_show_list`・`read_audience_network_insights`・`read_insights`【公式】。
  - **`instagram_*` の 6 つ・`catalog_management`・`threads_business_basic` はこの一覧に無い**【公式】。つまり **Instagram の口は 90 日のデータアクセス期限に当たる見込み**で、ページと広告の口は当たらない見込み【推測】。
- **使わない権限は消えうる**: 利用者がいつ使ったかに関係なく、アプリが 90 日使わない権限は期限切れになりうる（審査で通った権限でも）【公式】。プラットフォーム規約 7e: 28 日使わない API・権限・機能は Meta が止めたり取り上げたりできる【公式】。広告 API の段は 30 日使わないと下げられうる【公式】。
- **再認可の流れ**: 構成（`config_id`）を使うログインで、`auth_type=reauthorize` を付けて開き直す【公式（auth_type）・推測（config_id と組み合わせられること）】。手順書 §0-5 の D のとおり、2 回目からは「前の設定を引き継ぐ」で済む【前提】。
- システムユーザーの鍵は §3-6。

## 5. Webhooks

### 5-1. 共通（受け口の作り）

- 確認の GET: `hub.mode=subscribe`・`hub.verify_token`（ダッシュボードで決めた文字列と照合）・`hub.challenge` をそのまま返す【公式】。
- 通知の POST には `X-Hub-Signature-256`（app secret で HMAC-SHA256、`sha256=` の後ろ）。照合は「すべき」【公式】。
- 正しい TLS 証明書が要る（自己署名は不可）。すべての通知に 200 を返す【公式】。
- まとめて最大 1000 件で届くことがあるが保証なし。失敗するとすぐ再送、その後 **36 時間**まで間隔を空けて再送、それでもだめなら捨てる。重複が来るので弾く【公式】。過去の分は取り直せないので要るものは保存【公式】。
- mTLS の証明書は 2026-03-31 から Meta の自前の CA（`meta-outbound-api-ca-2025-12.pem`）に替わった（照合している場合だけ関係）【公式】。

### 5-2. ページ

- 欄: `feed`（投稿・シェア・いいね・コメントなどほぼ全部。`item` は comment・photo・share・status・video・reaction など、`verb` は add・edit・remove・hide・unhide。**広告の投稿そのものは来ないが、広告の投稿へのコメントは来る**）・`mention`（コメント・投稿でページが言及された）・`ratings`・`messages`（Messenger）【公式】。

- 購読: `POST /{page-id}/subscribed_apps` に `subscribed_fields`（ページトークン）。アプリをページが入れていて、アプリ設定の「Apps」プラットフォームが切られていないときだけ届く【公式】。
- 中身（feed・新しい投稿の例）: `from`（id・名前）・`item`・`post_id`・`verb`・`created_time`・`is_hidden`・`message`【公式】。

### 5-3. Instagram

- 欄: `comments`・`live_comments`・`mentions`（コメントかキャプションで @ された）・`story_insights`（ストーリーが消えたときに数。5 未満は -1）・`messages` とその仲間【公式】。

## 6. 量の制限

- **2 つの仕組み**: プラットフォームの上限（アプリ単位・利用者単位、利用者トークンの呼び出し）と **Business Use Case（BUC）の上限**（Marketing API・Instagram・ページトークンかシステムユーザーの鍵での Pages API）。両方が当たるときは BUC が優先【公式】。
  - アプリ: 1 時間に 200 × 利用者数。利用者ごとの上限の数字は非公開【公式】。
  - **Pages（ページトークン）: 24 時間に 4800 × 関わった利用者の数**【公式】。
  - **Instagram（メッセージ以外）: 24 時間に 4800 × インプレッション数**。ビジネスディスカバリーとハッシュタグ検索はプラットフォームの上限側【公式】。
  - Threads: 24 時間に 4800 × インプレッション（最低 10）【公式】。
  - 広告: §3-5。
- **ヘッダ**【公式】:
  - `X-App-Usage`: `call_count`・`total_time`・`total_cputime`（%）。
  - `X-Business-Use-Case-Usage`: `business-id` ごとに `type`・`call_count`・`total_cputime`・`total_time`・`estimated_time_to_regain_access`（分）・`ads_api_access_tier`（広告だけ）。1 回で最大 32 個。
  - `X-Ad-Account-Usage` は Ads API v3.3 以前のもの。
  - 広告の成績は別に `x-fb-ads-insights-throttle`【公式】。
- **エラーの番号**: 4（アプリ）・17（利用者）・32（ページ・利用者トークン）・613（独自）・**80001（ページ・ページトークン）**・**80002（Instagram）**・80000（Ads Insights）・80004（Ads Management）・80003（Custom Audiences）・80006（Messenger）・80009/80014（カタログ）【公式】。
- **Instagram の公開の上限**は別枠（§2-2: 50 か 100 / 24 時間）。**リール（FB）30 本 / 24 時間**（§1-1）。ハッシュタグ 30 種 / 7 日（§2-4）【公式】。
- 出典: https://developers.facebook.com/docs/graph-api/overview/rate-limiting

## 7. 審査と段階

- **Standard Access**: アプリで役割のある人だけが求められる権限。役割のない人には働かない。ビジネスアプリは種類の範囲の全部の権限・機能を自動で Standard で持つ【公式】。
- **Advanced Access**: 誰でも求められる。権限・機能ごとにアプリレビューで承認、**ビジネス認証が要る**【公式】。Advanced から Standard に下げると、役割のない人には全部止まる【公式】。
- Pages API の概要: ライブのアプリでは、権限は審査のあとでないと（役割のない）利用者が許可できない。開発モードでは役割のある人なら何でも求められる【公式】。
- Instagram: 自分の持つ・管理する口座でアプリに足したものは Standard、他人の口座は Advanced【公式】。
- Marketing API: 自分の広告アカウントだけなら Standard（Limited）で足りる【公式】。
- 機能（Feature）は別の審査: Page Public Content Access（他人のページを読む）・Instagram Public Content Access（ハッシュタグ検索）・Page Mentioning など【公式】。
- **Data Use Checkup（年 1 回）**: 公開済みでユースケースがあるか Advanced を持つアプリは、管理者が年 1 回の点検を済ませる。**Standard だけのアプリには要らない**。開発モードでは要らないがライブに上げる前に要る【公式】。THTH はライブでユースケースがあるので対象と読める（前の手順書では「完了」）【推測】。締め切りの日数は頁に無かった【未】。
- **Tech Provider（アクセス認証）**: 他のビジネスのデータに触れて仕事を提供するビジネス。アプリを持つビジネスが Tech Provider として認証されているか、使う人がアプリに役割を持っていない限り、`ads_management`・`ads_read`・`business_management`・`catalog_management`・`instagram_basic`・`pages_manage_posts`・`pages_read_engagement` などは与えられない。これとは別に、役割のない人には Advanced が要る【公式】。吾徳は認証済み（前提）。
- 出典: https://developers.facebook.com/docs/graph-api/overview/access-levels ・ https://developers.facebook.com/docs/pages-api/overview ・ https://developers.facebook.com/docs/development/maintaining-data-access/data-use-checkup ・ https://developers.facebook.com/docs/development/release/tech-providers ・ https://developers.facebook.com/docs/permissions

## 10. THTH の計画で効く大事な事実 10 個

1. **自分の資産だけなら審査なしで足りる**: Standard は役割のある人の権限。Instagram は「自分の持つ・管理する口座」、Marketing API は「自分の広告アカウント」なら Standard でよいと公式が書く。役割のない人に出すとき初めて Advanced（審査・ビジネス認証）が要る。
2. **ページと広告の権限は 90 日のデータアクセス期限に当たらない。Instagram の 6 つは当たる見込み**（期限の来ない権限の公式一覧に `instagram_*` が無い）。Instagram の口は 90 日ごとの再認可（`auth_type=reauthorize`）か使い続けることが要る。別に「90 日使わない権限は消えうる」「28 日使わない API は止められうる」「広告の段は 30 日使わないと下がりうる」。
3. **長いユーザートークンから取ったページトークンは期限なし**（`expires_at=0` はこれ）。ユーザートークンは約 60 日。システムユーザーの鍵は期限なしか 60 日（推奨）で、アプリと同じビジネスに属すことが要る。ページが吾徳と別のポートフォリオにあるので、システムユーザーを使うなら資産の置き場の整理が要る（推測）。
4. **Instagram の公開は入れ物→公開の 2 段で、1 日の上限は 50（`content_publishing_limit` の `quota_total`）。手引きの本文には 100 とあり食い違う**。入れ物は 24 時間で切れる。画像は JPEG だけ、カルーセル 20 件、キャプション 2200 字・タグ 30・@ 20、リール 3 秒〜15 分。
5. **FB の予約は 10 分後から。上限は頁により 30 日・75 日・（リール）29 日と違う**。編集できるのは同じアプリで作った投稿だけ。FB リールは 24 時間で 30 本まで、3〜90 秒。
6. **ページのインサイトは v26 で「インプレッション」系がまとめて外れ、`*_media_view`・`*_total_media_view_unique` に置き換え**。Instagram も `impressions` は廃止で `views` が中心。数は最大 48 時間遅れ、カルーセルの子には数が無い、FB は 2 年・一度に 90 日まで。
7. **量の制限は BUC: ページは 24 時間に 4800×関わった人、Instagram は 24 時間に 4800×インプレッション**。`X-Business-Use-Case-Usage` の `estimated_time_to_regain_access` で待つ時間が分かる。広告は Standard で 1 時間に 300＋40×動いている広告（管理）・600＋400×（成績）。
8. **公式の広告 MCP サーバー（mcp.facebook.com/ads・2026-04 から公開ベータ）は `ads_mcp_management` という今の 19 権限に無い権限と、まだ足していないユースケースが要る**。開発者アプリなしで利用者が自分でつなぐ道もある。7 月から、ポートフォリオの管理者が AI のできること（予算の変更など）を縛る「rules」がある。システムユーザーの鍵は Employee の役割のものだけ通る。
9. **既にある投稿を広告にするのは `object_story_id`（FB）・`source_instagram_media_id`（IG）。`spend_cap` に届くと全配信が止まる**（0 は上限なし、単位の書き方が頁で食い違う）。作成の口は二重にならない作り。Threads 広告は IG の `connected_threads_user` で `threads_user_id` を取り、Threads の自然な投稿は広告にできない。
10. **規約は自動の投稿・返事・広告の自動化を一般には禁じていない**。禁じているのは、同意なく代わりに公開すること・高い頻度のボット作り・エンゲージメントの売り買い・メッセージの 24 時間の窓の外での宣伝、そして Instagram では「事前の許可なしに利用者のコンテンツの表示・取り込み・保存を簡単にする」使い方（6.2）。
