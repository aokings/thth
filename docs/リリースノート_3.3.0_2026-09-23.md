# リリースノート 3.3.0（止まったら知らせる・報告したくなる口）

2026-09-23。設計は [設計 3.3.0](設計_3.3.0_止まったら知らせる_報告したくなる口_2026-09-23.md)（masaru の裁定 7 件はすべて「はい」・§F を含む）。版を 3.3.0 に上げた（2026-09-23 20:00）。

材料の報告: **r20260923-f199078c**（世に出す前に塞ぐ穴）・**r20260923-2f5a1b2d**（LLM が報告したくなる作りに）。r20260923-08050195（投稿ごとのフォロー）は API に無いので実装しない（§C・返事で伝える）。

## なぜ

9/21、kopicha-bluesky／kopicha-mastodon の承認済み 46 本が `approval_stale` で 2 日出ませんでした。run は「出すものが無い」で成功扱いになり、死活通知も運用通知も何も言いませんでした（2.8.0 がタグを承認の指紋に入れたのに、版がそれを言わなかった）。**承認済みの原稿が出られなくなったら、道具が人に知らせる。黙って止まらない。** そして、道具を使う LLM が**つまずいたその場で 1 行で報告できる**ようにしました。

## kopicha のセッション向け（6 行）

1. セッションの始めと区切りごとに `thth observe kopicha --json`（MCP `thth_observe`）。`thth morning`／`thth_morning` は同じ 1 枚の別名です。第 2 段は「前回の観測から」。
2. 承認済みなのに出ない原稿は、予定の段の `held_items` と `thth board` の要確認（先頭 5 本）に名前・理由・予定・経過で出ます。`approval_stale` は `thth approve` の二段で再承認すれば出ます。
3. 時刻を過ぎて出られない原稿があると、`thth run` は `held` として死活通知と運用通知に知らせます（増えたときだけ・0 に戻ったら復旧）。
4. 断られたら、断りの最後の `report_channel:` の行を `--by` だけ足してそのまま打ってください。道具が控えた直前の断りが再現手順に付きます。
5. 迷った・分かりにくかった・同じ操作を繰り返した、は `--kind friction` で置けます。小さいものも歓迎です。重複は道具が束ねます。
6. 置いた報告がこの版で閉じたかは `thth observe` の 0 段「あなたの project の報告」に出ます。

## 入ったもの

### A. 止まったら知らせる（r20260923-f199078c）

- **A1 held**: `thth run` の終わりに、本番で timer に載る account の、publish_at を過ぎた承認済みで要確認に落ちた原稿を数えます（区分は `approval_stale`・`reply_to_unresolved`・`stale`・`invalid` の 4 つ・返信待ちと時刻前は数えない）。1 本以上なら状態 `held`・理由 `approved_but_held: <区分> <本数>`。死活通知は `/fail`（`state: held`）、運用通知は本数が前回の run より増えたときだけ・0 に戻ったら `held_cleared`。数えられないときは healthy を送りません。投稿の rc は変えません。
- **A2 名前**: `thth observe` の予定の段に `held_items`（`overdue_items` と同じ形・`due`・時刻前の approval_stale も名前は出す）、`next_steps` に `kind: "held"`（approval_stale は `candidate: reapprove`）。`thth board` の要確認は先頭 5 本の名前と残りの本数、`--json` に `held_count`・`held_upcoming_count`・`held_reason_code`。
- **A3 指紋の版**: `approval.FINGERPRINT_VERSION`（いまは 2＝2.8.0 の変更）と golden（`thth/fingerprint_golden.py`・見本 10 件）。指紋の計算が変わったのに版を上げなければ試験が落ちます。版が変わった版へ上がると、`handoff-report` の `tool` と `thth observe` の 0 段に「この版で再承認が要る原稿: n 本（account ごと）」、運用通知に 1 回だけ「再承認が必要」。
- **A4 経路なし**: 死活通知と運用通知の両方が無い scheduled の account は `no_notification_route`、片方だけなら `notification_route_partial: healthcheck|incident`（欠けている側）を、`thth observe` の 0 段と `thth doctor` が言います。
- **追加の裁定**: `reply_to_file` の指した原稿が `status: withdrawn` なら、待たずに `reply_to_unresolved: target_withdrawn`（held に数える）。

### B. LLM が報告したくなる口（r20260923-2f5a1b2d）

- **B1**: 固定の 1 文「つまずき・迷い・期待との違いの報告は、利用者の作業の一部として歓迎します。小さいものも。重複は道具が束ねます」を skill・使い方・`thth_report_file` の説明・断りの行に。
- **B2**: 断ったとき（CLI の rc≠0・サーバ型 MCP の isError）に、account ごとに直近 5 件の `{at, version, command, reason_code, account}` を `state/<account>/last_refusals.json`（0600）に控えます。本文・引数の値・パス・秘密は控えません。`thth report file <account> --from-last-refusal`（MCP `from_last_refusal: true`）でその account の控えだけを再現手順に添えます（種類の既定は friction・本文は省ける）。
- **B3**: 断りの行が `report_channel: thth report file <account> --kind friction --from-last-refusal --title "<理由> で断られた" --by <名前>（…）` の打てる形に。
- **B4**: 種類 `friction`（つまずき）。
- **B5**: `thth observe` の 0 段に「あなたの project の報告: 開いている n・この版で閉じた m（題）」。リリースノートには報告 id を添える（`docs/運用_配布_2.14.md` の「リリースノートの書き方」）。
- **B6**: 例 3 つ（「止まったのに気づかなかった」「断られた理由が分からなかった」「同じ操作を 3 回繰り返した」）を skill と `thth_report_file` の説明に。

### F. 観測（`thth observe`）

- 名前は `thth observe`・MCP `thth_observe`。`morning` は別名。JSON の `report_type` はどちらも `observe`、呼んだ名前は `invoked_as`。
- 第 2 段は前回の栞の時刻から今まで（栞が無い・7 日より古いときは前日 JST・`window.basis`）。段の id は `yesterday` のまま。

## 変えていないもの

承認の二段・`--production`・digest・承認の指紋の計算そのもの（golden は現状を固定しただけ）。死活通知の本文の 6 項目。読む口の規律（読むだけ・栞だけ進む）。
