- 【公式】 公式の頁（開発者向け文書・規約・ヘルプ）で確かめた

- 【分からない】 調べたが確かめられなかった

## 1. 一言で

実店舗の台帳は、**持ち主が書く行が主で、口から取り込む行が従**になる。オンラインの店（BASE・STORES・Shopify）は商品の事実のほとんどを口から読めたが、実店舗は営業の時間・臨時の休み・催し・店頭にしか無い品・店の思いが口に無い。だから最初に要るのは「口」ではなく「口の無い店でも回る、手で書く台帳と、聞いて埋める流れ」で、口はその台帳の一部を自動で埋める助けになる。

構想 §3 の 2 種類の行に当てはめると:

| 行 | 実店舗での中身 | 正本 |
|---|---|---|
| 自前の行 | 営業の時間・定休日・臨時の休み・催し・店頭の品の紹介・店の思い | 台帳（持ち主が書く・LLM が聞いて埋める） |
| 取り込みの行 | レジに登録した商品・値段・在庫の節目・店舗の名前と住所 | レジ（THTH はレジに書かない） |

営業の時間は、レジ（Square）や Google ビジネス プロフィールにも載っている。どちらを正本にするかは §6.3 で扱う（叩き台は「台帳が正本、外は写し」）。

## 2. 実店舗で THTH がすること・しないこと（案）

### すること

1. **手で書く台帳の形と点検を渡す**（§4）。店・営業の時間・臨時・催し・品・思いを 1 行 1 枚の .md に置き、頭の項目の点検を柵にする（構想 §5 の `thth register check`（仮）の最初の使い道）
2. **口のある店は、レジから商品と店舗の事実を読む**（読むだけ・今の `thth shop` と同じ手すり）
3. **台帳とレジの違いから、きっかけを出す**（新しい品・値下げ・再入荷・営業の時間が変わった・臨時の休みが近い・催しが近い）。中身（投稿の文）とは分けて持つ（構想 §9 の 2）
4. **きっかけから下書きを 1 本ずつ作る**（承認されていない queue の下書き・今の `draft.py` と同じ形）
5. **足りない事実と思いを、持ち主に聞く問いを作り、答えを印つきで記録する**（§4.3）
6. **出す前に台帳を読み直す**（臨時の休みや時間が変わっていたら断る・今の `recheck.py` の延長）

### しないこと

1. **売上・取引・会員（お客さん）・スタッフ・勤怠を読まない。** レジの口はこれらの道も持っている（スマレジは取引・会員・勤怠、Square は注文・顧客）。道の表で呼べなくする（今の `wire.ROUTES` と同じ柵）
2. **レジにも Google ビジネス プロフィールにも、店の情報を書かない**（初めの段）。Google ビジネス プロフィールへの投稿を「出し先」として足すかは別の段（§6.4）
3. **推測の印の事実で中身を作らない。** 営業の時間を「たぶん 10 時から」と書いた投稿は害になる。構想 §9 の 4 の柵（推測の行を引いて中身を作ろうとしたら断る）を実店舗の最初の柵にする
4. **お客さんの写った写真を自動で選ばない。** 店頭の写真は持ち主が選んで台帳に置いたものだけを使う
5. **口コミを読まない・返さない**（Google の口コミは書いた人の名前が付く。返信の自動化は Google の決まりでも縛られている・§9.4）
6. **レジの商品を全部ネットに出す前提にしない。** 実店舗のレジには「公開」の考えが無い（§5.2）

### 3.1 比べの表

詳しい根拠と出所は §9。

### 3.2 推し（案）

**最初に作るのは「口なし」（手で書く台帳）。そのうえで最初の口は Square。**

理由:

1. 実店舗で中身になる事実（営業の時間・臨時の休み・催し・思い）は、どのレジにもほぼ無い。口から作り始めると、いちばん大事な事実が後回しになる。手で書く台帳は、Airレジの店や、レジの無い店でもそのまま回る
2. Square は、個人の店主が審査なしで自分の鍵を取れて、1 つの口で商品・店舗ごとの在庫・**曜日ごとの営業の時間**まで読める（スマレジは営業の時間が無い）。日本で使えることも公式に書かれている
3. 今の `thth shop` の作り（種類の表 `kinds.py`・道の表 `wire.ROUTES`・行の部品 `rows.py`・違い `diff.py`）にそのまま種類を 1 つ足す形で入る

Square の弱み（推しの代償）:

- 個人の鍵は全部の権限を持つ。THTH が呼ぶ道を表で絞っても、鍵が漏れたときの広さは大きい（STORES のクレデンシャルと同じ話・設計 Shopify と STORES §2）。持ち主に知らせて、OAuth（scope を `ITEMS_READ`・`INVENTORY_READ`・`MERCHANT_PROFILE_READ` に絞る）を後の段で考える
- 規約の「Square のデータを AI の学習・強化に使わない」と、THTH が読んだ商品を持ち主の LLM に材料として渡すことの関係は、原文の読みが割れうる（学習ではなく、持ち主のための下書きの材料）。§7 で要確認にした
- 読みの上限の数が公開されていないので、THTH の側で控えめにする（BASE の β と同じ扱い）

### 3.3 前提が変わったら

| 変わる前提 | 結論の変わり方 | 代償 |
|---|---|---|
| 最初の実店舗がスマレジを使っている | 最初の口はスマレジ。scope を商品・在庫・店舗に絞れるので、鍵の広さの問題は Square より軽い | 営業の時間は手の台帳で持つ。自分の契約だけに入れる形（審査なし）が取れるかを先に確かめる。取れなければアプリマーケットの審査とスマレジとの手数料の話になり、masaru の承認が要る（お金が動く） |
| 最初の実店舗が Airレジを使っている | 口は作らない。手の台帳だけで回す | 新しい品の知らせはレジから取れないので、持ち主に「新しく入った物は？」と聞く拍子を増やす |
| 最初の実店舗が STORES レジを使っている | 今の STORES の口のまま、商品だけ読む。店舗の事実と営業の時間は手の台帳 | 店舗ごとの在庫は読めない |
| 営業の時間・臨時の休みの発信がいちばんの悩みの店 | 口より先に、Google ビジネス プロフィールへの「出し先」を考える（§6.4） | Google の申請（60 日以上・サイトが要る）と Cloud の project が要る。書き換えは自動にできない決まりがある |
| 実店舗を持つ利用者がまだいない | 実店舗の段そのものを後にし、手の台帳の形だけを自前のメディアの台帳と同じ決まりで先に固める | 実物の店が無いと、聞く問いと柵の線が机の上のものになる（構想 §6「実物から起こす」） |

## 4. 口の無い店の形

### 4.1 手で書く台帳の形（案）

構想 §5 の決まり（1 行 1 枚の .md・頭の項目に番号・状態・由来・見直し日・git の repo）をそのまま使う。置き場は持ち主が選ぶ（手元・Obsidian・`thth sync` の後の段）。

```
<台帳の repo>/
  店/
    店.md            店の名前・住所（出すか出さないかの印つき）・電話・地図の URL・店のサイト
    営業の時間.md     曜日ごとの時間・定休日・ラストオーダー
    臨時/
      2026-12-29_年末年始.md   1 回の臨時の休みや時間の変更が 1 枚
    催し/
      2026-12-14_試食会.md     1 回の催しが 1 枚
    品/
      <品の番号>.md            店頭の品（レジに無い品・レジの品に足す思い）
    思い.md           店の思い・誰に届けたいか・扱わない物
```

頭の項目の案（どの 1 枚にも）:

```
---
id: shop-kopicha-hours            # ずっと同じ
kind: hours                       # store・hours・special・event・item・voice
status: 本採用                    # 試し・本採用・退役
source: owner                     # owner（持ち主が書いた）・asked（聞いて埋めた）・guess（推測）・register（レジから）
confirmed: 本人が認めた           # 推測・本人が認めた・本人が違うと言った（構想 §9 の 2 の 3 つの印）
confirmed_at: 2026-11-13
review_by: 2027-02-13             # 見直し日
public: true                      # 外に出してよいか（住所・電話は既定で false）
---
```

営業の時間の本文は、人が読めて機械も読める形にする（例: 1 行に「月 10:00-18:00」、休みは「水 休み」）。形の点検は柵にする（時刻の形・閉める時刻が開ける時刻より前で日をまたがない・曜日の抜け）。

臨時の 1 枚は `date`（と `end_date`）・`closed`（終日休みか）・`open`・`close`・`reason_public`（理由を出すか・既定は出さない）を持つ。催しは `starts`・`ends`・`place`（店の中か外か）・`fee`・`booking`（要るか）を持つ。

### 4.2 印の柵（機械がすること）

構想 §9 の 4 の分け方のとおり、柵は THTH が持つ:

- `confirmed: 推測` の行の事実は、下書きの本文にも頭にも入れない。入れようとしたら前向きに断る（なぜ・通る直し方は「本人に聞いて認めてもらう」・より良くする一手は「聞く問いの案」）
- `public: false` の欄（住所・電話など）は下書きに載らない
- `review_by` を過ぎた営業の時間は「古いかもしれない」と断り、聞く問いを出す
- 臨時と催しは、日が過ぎたら `status: 退役` の候補として知らせる（消さない）

### 4.3 聞いて埋める流れ（案）

1. **穴を見つける（機械）**: 台帳の点検が、要る行の欠け（営業の時間が無い・定休日が無い・年末年始の臨時が 12 月に入っても無い・見直し日が過ぎた）と、レジの新しい品で思いの 1 枚が無いものを並べる
2. **推す（LLM）**: 品揃え・レジの部門・前の投稿から「この並びなら、こういう考えでは」と推し、`confirmed: 推測` で書く。中身には使えない
3. **聞く（LLM → 持ち主）**: 1 回に 1 問。答えやすい形（はい・いいえ・時刻）を先に。推しを添える（「年末は 29 日から 3 日まで休みでしょうか」）
4. **記録する（機械）**: 答えを `confirmed` の印と日付で書く。「違う」と言われた推測は消さずに残す（同じことを二度聞かない）
5. **使う**: 本人が認めた行だけが下書きの材料になる

聞く拍子と上限の叩き台: 1 日に 3 問まで・同じ穴は 7 日空ける・季節の問い（年末年始・お盆・大型連休）は 3 週間前に 1 回。会話の一言を「本人が認めた」とするか、承認の操作にするかは決めていない（構想 §9 の決めていないこと）。営業の時間と臨時の休みは間違えたときの害が大きいので、この 2 つだけは承認の操作（二段確認）にする案。

## 5. 今の thth shop へのつなぎ方

### 5.1 口のある店（Square・スマレジ）

今の作りに種類を足す形:

- `kinds.py` に `square`（後で `smaregi`）を足す。台帳の欄は `store`・`kind`・`project`・`token`＋`location`（読む店舗の id・1 つ）
- `wire.ROUTES` に読む道だけを足す。Square なら Catalog の一覧・Inventory の数・Locations の 1 件。注文・顧客・支払い・スタッフの道は表に入れず、GET 以外は断る（Square の Catalog の検索や在庫の数の取り出しは POST の道なので、**「読むための POST」を道ごとに許す**形が要る。今の「base と stores は GET だけ」の柵の書き替えになり、監査の範囲）【推測: 道の形は作るときに公式で確かめる】
- `rows.py` の行に直す。Square の品は `id`・`name`・値段・在庫（その店舗の数か「数えない」）・画像 1 枚・更新の時刻。商品頁の URL は無い【推測】ので、下書きには店の URL（手の台帳の `店.md`）を載せる
- 違い（`diff.py`）の種類はそのまま使える（new・price_down・sold_out・restock など）。在庫は今と同じく節目だけ（1 個ずつの動きは売上の写しになる）
- 下書き（`draft.py`）の一言は実店舗向けに「店頭に並びました」「店頭で再入荷しました」を足す

### 5.2 実店舗の商品に「公開」が無いこと

オンラインの店は `visible` で「公開で買える」を決められたが、レジの品は店の中の事情の品（「その他 500 円」・袋・取り置き）も混ざる。スマレジの `displayFlag` は端末に出すかの印で、外に出してよいかではない【公式】。だから:

- レジの品は、既定ではどれも「外に出さない」。持ち主が手の台帳の `品/` に 1 枚置いて `public: true` にした品、か、`店.md` で「出してよい部門」を決めた品だけが下書きの材料になる
- 写しには、出さない品は `id` だけを持つ（今の非公開の品と同じ）

### 5.3 店舗の事実の行

営業の時間・店舗の住所は「商品の行」ではないので、今の `ROW_FIELDS` に混ぜない。店舗の事実の写しを別に 1 枚持ち（`store_state/<名前>/place.json` の案）、違いの種類を足す:

- `hours_changed`: 曜日ごとの時間が変わった（レジの側で変わった・手の台帳と食い違った）
- `place_changed`: 名前・住所・電話が変わった（下書きは作らず、手の台帳との食い違いとして知らせるだけ）

### 5.4 口の無い店

`kinds.py` に `manual`（手の台帳）を足す案。口は網に出ず、手の台帳の `品/` を読んで行に直す。写し・違い・下書き・読み直しの部品はそのまま使える。網に出ないので `wire.py` を通らない（「網に出るのは wire.py だけ」の柵はそのまま）。

命令の名前は決めていない。今の `thth shop` に入れるか、店舗の事実を扱う別の命令（例 `thth place`）にするかは §8。

### 5.5 下書きの頭

今の出所（`from_store: store/<店>/item/<id>`）に、手の台帳の行の出所を足す（`from_register: <id>@<commit>`）。承認のときの読み直しで、台帳の行が変わっていないか（`confirmed` が推測に戻っていないか・臨時の 1 枚が退役していないか）を見る。

## 6. 実店舗に固有のきっかけ

### 6.1 きっかけの一覧（案）

| きっかけ | 出所 | 下書き | 拍子の案 |
|---|---|---|---|
| 臨時の休み・時間の変更 | 手の台帳の `臨時/` | 作る（「◯日はお休みします」） | 1 週間前と前日の 2 回の案。前日の分は予約に入れる |
| 年末年始・お盆・大型連休 | 暦（機械）＋手の台帳 | 台帳に 1 枚あれば作る。無ければ聞く問いを出す | 3 週間前に聞く・1 週間前に下書き |
| 定休日・曜日の時間の変更 | 手の台帳か Square の Locations | 作る（「◯月から時間が変わります」） | 変わる日の 2 週間前 |
| 催し | 手の台帳の `催し/` | 作る | 2 週間前・前日・当日の朝の案。終わったら退役 |
| 店頭に新しい品 | レジ（`new`）か手の台帳の `品/` | 作る（出してよい品だけ） | 違いを見たとき |
| 店頭で再入荷・売り切れ | レジの在庫の節目 | 再入荷だけ作る | 違いを見たとき |
| 季節の品の始まりと終わり | 手の台帳の `品/` の期間 | 作る | 始まりの日 |
| 見直し日を過ぎた | 手の台帳 | 作らない。聞く問いを出す | 毎朝の 1 枚（`thth morning`）に 1 行 |

### 6.2 実店舗で害になりうる下書き

- **臨時の休みの理由**（「店主が旅行で」など）は既定で書かない。家と店が同じ場所の店では、家が空くことの知らせになる
- **催しの後の告知**が残る。催しの下書きは終わりの日を頭に持ち、承認の時に過ぎていれば断る
- **間違った時間**。営業の時間と臨時の下書きは、承認の時に台帳を読み直し、変わっていたら断る（`store_item_changed` と同じ考えの `register_row_changed` の案）

### 6.3 営業の時間の正本

台帳・レジ（Square）・Google ビジネス プロフィールの 3 か所に同じ事実がありうる。叩き台は「**台帳が正本・外は写し**」。理由: 臨時の休みはレジに無く、Google には書けても持ち主が忘れやすい。台帳で持てば、投稿と Google の両方へ同じ事実を出せる。外と台帳が食い違ったら、どちらかを直すのではなく、食い違いを見せて持ち主に聞く（構想 §6 の合わせる働きの「外の今を読んで台帳の隣に写す」）。

### 6.4 Google ビジネス プロフィールを「出し先」にする案（後の段）

Google ビジネス プロフィールは店の情報の場なので、「読む口」より「出し先」が素直【推測】:

- 投稿（`localPosts`・催しと特典の型がある・商品の投稿は API で作れない）【公式】と、臨時の時間（`specialHours`）を台帳から出す
- 出し先なら `thth/adapters/` の新しい媒体（投げる先）になり、今の SNS の手すり（二段確認・上限）がそのまま乗る
- Google の決まりで、口から読んだ中身は 30 日を超えて持てない【公式】。台帳を正本にして Google を写しにすれば、Google から読んだ物を長く持たずに済む
- 書き換えと返信を自動にしない決まりがある【公式】。台帳から出すのは承認のあとだけにする（今の THTH と同じ）。ただし、**投稿がこの「自動にしない」に入るかは原文に書かれていない**【分からない】
- 先に masaru の手が要る: Google Cloud の project・申請の書式（申請はプロフィールの持ち主か管理者のメールで出す）【公式】

## 7. privacy と規約に増える物（案）

### 7.1 privacy の文に足す物

- レジから読む物: 品の名前・値段・在庫の節目・画像 1 枚・店舗の名前と住所と営業の時間。**読まない物**: 売上・取引・会員（お客さん）・スタッフ・勤怠
- 残す物: 写し 1 枚（品と店舗の事実）・下書き。残さない物: 在庫の 1 個ずつの動き
- 手の台帳は持ち主の手元にあり、THTH の運営者は預からない（構想 §5）
- 住所・電話は既定で外に出さない。出すかは持ち主が 1 枚ごとに選ぶ
- 店頭の写真に人が写っていれば、出す前に持ち主が確かめる（THTH は写真を自動で選ばない）
- 「privacy とコードの一致」の柵に、読む道の表（§5.1）を足す。`thth leave` で実店舗の写しと鍵が消えること

### 7.2 規約で気をつける物（各社）

- **Square**: Square のデータを AI の学習・強化に使わない【公式】。店の明示の同意なく店のデータを集めてデータベースを作らない【公式】（持ち主本人が使う形なので、店主向けの了承の 1 枚で同意を受ける案）。Square の代理人のように見せない（断り文と説明に「この道具（THTH）は Square が提供するものではありません。」を足す・今の `not_by` の形）。英語の規約には AI の使い方の節（AI が作った物を人が作ったように見せない、など）があるが、日本語の規約（2020 年の版）には見当たらず、別の「Square AI 規約」を読んでいない【分からない】。**THTH の下書きは持ち主の LLM が書き、持ち主が承認して持ち主の名前で出す。これが「AI が作った物を人が作ったように見せる」に当たるかは要確認**
- **スマレジ**: 利用者の承諾なく取引データや個人情報を使うアプリは登録できない（第 9 条 4 項 3 号）【公式】・営業や宣伝などの営利の行為は認めたもの以外禁止（第 14 条 1 項 10 号）【公式】・開発の環境に本物の個人情報や顧客のデータを入れない（第 7 条 3 項）【公式】。THTH が店の宣伝の下書きを作ることが「営利の行為」に当たるかは、条文の主語（開発者がスマレジ・デベロッパーズの上でする行為）から見て当たらないと読めるが【推測】、作る前にスマレジに確かめる
- **Google ビジネス プロフィール**: 口の中身を 30 日を超えて持たない・店の承諾なく書き換えと返信を自動にしない・Google との提携を匂わせない・他人に自分の project を使わせない・Google が求めたら 7 日以内に試しのアカウントを見せる【公式】
- **Airレジ**: 口が無いので規約の増えは無い。画面からの読み取り（スクレイピング）はしない

### 7.3 店主向けの 1 枚に足す物

今の BASE の 1 枚（設計 §6）に、実店舗の分として: 読む物と読まない物（売上・お客さんは読まない）・鍵の作り方（Square なら個人の鍵は全部の権限を持つこと）・手の台帳に書く物・聞かれる問いの数の上限・住所と電話は既定で出さないこと。

## 8. 決めていないこと

- 最初の実店舗は誰か（身近に実店舗があるか・どのレジか）。§3.3 の表の結論はここで決まる
- 命令の名前: 今の `thth shop` の種類に足すか、店舗の事実を扱う別の命令（`thth place` など）にするか
- 手の台帳の置き場と形: 構想 §5 の台帳の決まりと同じ点検で回すか、実店舗用の形を足すか。自前のメディアの台帳と同じ決まりにそろえる時期（構想 §9 の 5「自前のメディアが最初の使い手」）
- 「本人が認めた」の受け方（会話の一言か・承認の操作か）。営業の時間と臨時だけ承認の操作にする案（§4.3）の可否
- 営業の時間の正本（§6.3）: 台帳が正本の案のままでよいか
- Google ビジネス プロフィールを出し先にするか、いつか（§6.4）。申請と Cloud の project は masaru の手
- Square の個人の鍵（全部の権限）を受けるか、初めから OAuth で scope を絞るか
- Square の「読むための POST」を道の表で許す形（§5.1）と、その監査
- 聞く拍子と上限（§4.3 の 1 日 3 問・7 日空ける・3 週間前、は叩き台）
- 実店舗の品のうち外に出してよい物の決め方（品ごとか部門ごとか・§5.2）
- 有料と無料の線（構想 §8）に実店舗の分をどう入れるか

## 9. 下調べ（2026-11-13・公開の文書だけ）

### 9.1 スマレジ（プラットフォーム API）

- 【公式】API は 8 種類（共通・POS・在庫管理・受注管理・Waiter・Timecard・EC B2B・EC OMS）。開発パートナーは全部の API とデモのアカウントを無料で使え、サンドボックスもある。作ったアプリはスマレジ・アプリマーケットで公開・販売でき、リリースには審査がある。https://developers.smaregi.jp/
- 【公式】鍵: アプリの鍵は client credentials（`POST https://id.smaregi.jp/app/{契約ID}/token`・client id と secret を Basic で）。利用者の認可は認可コード（OpenID Connect・PKCE）で、リフレッシュの鍵は 30 日。契約 ID は利用者の通知で届く。https://developers.smaregi.dev/platform-api-reference/common/
- 【公式】上限: 読み（GET）は本番で毎秒 50 回・サンドボックスで毎秒 10 回。書き（POST など）は本番で毎秒 20 回。超えると 429 と `Retry-After`。鍵を取る呼び出しも数に入る。予告なく別の上限が付くことがある。同上
- 【公式】POS の道: 商品（`GET /products`・`/products/{id}`・店舗ごとの値段 `GET /stores/{store_id}/product_prices`・画像は別の道）・在庫（`GET /stock`・変動の履歴）・店舗（`GET /stores`・`/stores/{id}`）・取引（`GET /transactions` ほか）・会員（`GET /customers` ほか）。scope は `pos.products:read`・`pos.stock:read`・`pos.stores:read`・`pos.transactions:read`・`pos.customers:read` で分かれている。https://developers.smaregi.dev/platform-api-reference/apis/pos/
- 【公式】商品一覧の欄: `productId`・`productName`・`price`・`displayFlag`（端末に出すか）・`stockControlDivision`（在庫を数えるか）・`updDateTime` ほか。`limit` は 1〜1000（既定 100）。更新の日時で絞れる（最大 31 日の幅）。https://developers.smaregi.dev/platform-api-reference/apis/pos/operations/getproducts/
- 【公式】店舗の欄: `storeName`・`postCode`・`address`・`phoneNumber`・`homepage`・`pauseFlag` ほか。**営業の時間・休みの日・緯度経度の欄は無い。** https://developers.smaregi.dev/platform-api-reference/apis/pos/operations/getstoresstoreid/
- 【公式】規約: 登録はスマレジの承諾が要り、個人か法人かの決まりは開発者には無い（第 5 条）。禁止に、営利の行為（認めたもの以外・第 14 条 1 項 10 号）・個人情報の不正な収集（同 13 号）・開発の環境への本物の個人情報（第 7 条 3 項）。利用者の承諾なく取引データや個人情報を使うアプリは登録できない（第 9 条 4 項 3 号）。https://smaregi.jp/legal/terms_developers.php
- 【公式】料金: スタンダードは無料（1 店舗だけ）・プレミアム月 5,500 円ほか。「スマレジ API 利用」「アプリマーケット」の欄はどのプランにもあるが、どのプランで使えるかは表の印が画像で読めなかった【分からない】。https://smaregi.jp/price/
- 【分からない】自分の契約だけに入れるアプリ（審査なし）を作れるか。スタートガイド（`https://developers.smaregi.dev/documents/start_guide`）は本文を読み取れず、ほかの公式の頁でも見つからなかった
- 【記事】シェアは上位 2 社（スマレジ 24%・Airレジ 23%・400 人のアンケート）。比べのサイトの小さな調べ。https://saas.imitsu.jp/cate-pos-register/article/l-2261

- 【公式】Location に臨時の時間の欄は見当たらない（`business_hours` は曜日ごとの形の例だけ）。同上

- 【公式】個人の鍵: Developer Console のアプリごとに本番とサンドボックスの 1 本ずつ。「自分の Square アカウントだけを使う」連携のためのもの。**scope の無い全部の権限の鍵**。複数の店を扱うなら OAuth。https://developer.squareup.com/docs/build-basics/access-tokens

### 9.4 Google ビジネス プロフィール

- 【公式】使う前の条件: Google アカウント・プロフィールを使ってみる・Cloud の project・組織のアカウント・API の申請。申請できるのは「確認済みで 60 日以上動いているプロフィール」を管理し、「店を表すサイト」を持つ人。自分の店でもよい。申請は書式で「Application for Basic API Access」を選び、プロフィールの持ち主か管理者のメールで出す。上限が毎分 0 なら未承認・300 なら承認。https://developers.google.com/my-business/content/prereqs
- 【記事】審査は数日〜数週間・14 日以上待った例。https://discuss.google.dev/t/gbp-api-escalation-basic-access-pending-14-days-requests-per-minute-locked-at-0/393020
- 【公式】店の欄: `title`・`phoneNumbers`・`storefrontAddress`・`websiteUri`・`regularHours`・`specialHours`（「休日の時間など、ふだんの時間の外」・ふだんの時間が無いと書けない）・`moreHours`・`openInfo`・`profile`・`serviceItems` ほか。https://developers.google.com/my-business/reference/businessinformation/rest/v1/locations
- 【記事】臨時の時間の 1 件は `startDate`・`closed`（真なら終日休み）・`openTime`・`closeTime`（Google の client の文書から）。`openInfo` の値（一時休業など）は公式の頁で確かめられなかった【分からない】。https://pub.dev/documentation/googleapis/13.2.0/mybusinessbusinessinformation_v1/SpecialHourPeriod-class.html
- 【公式】投稿: v4 の `accounts/{id}/locations/{id}/localPosts`。催し・特典・行動の呼びかけの型・画像。商品の投稿は API で作れない。小さな店も大きなチェーンも投稿できる。https://developers.google.com/my-business/content/posts-data
- 【公式】終わる物の表: Q&A の API は 2025-11-03 に終わった。投稿の数の口は 2023 に終わった。投稿そのものの終わりの日は書かれていない。https://developers.google.com/my-business/content/sunset-dates
- 【公式】上限: 多くの口で project ごとに毎分 300 回・店ごとの書き換えは毎分 10 回（上げられない）・店の書き換えは 1 日 10,000 回。https://developers.google.com/my-business/content/limits
- 【公式】決まり: 持っているか任された店だけを扱う・口の中身を前もって取る・貯める・索引にすることはできず、性能のための一時の保存は 30 日まで・口コミの返信と Q&A と店の作成と書き換えを自動にしない（投稿については書かれていない）・店の代わりに口コミへ返すなら先に承諾・店に加えた変更は 48 時間以内に知らせる・Google との提携を匂わせない・自分の project を他人に使わせない・求められたら 7 日以内に試しのアカウント。https://developers.google.com/my-business/content/policies
