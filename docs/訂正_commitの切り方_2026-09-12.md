# 訂正: commit の切り方が中身と食い違っている（2026-09-12）

**`8887d2a` と `d9bec3b` の 2 つは、メッセージと中身が一致していません。**
内容は失われていませんが、**履歴を読む人が誤解する**ので記録します。

| commit | メッセージ | 実際の中身 |
|---|---|---|
| `8887d2a` | trial の申告も独立性の制約に使う（R2） | R2 の変更に加えて、**R5（日付の精度・種別）の `topic_models.py` の変更 13 行**が入っている |
| `d9bec3b` | 仮説は proposed まで／知らない日を作らない（R4・R5） | `topic_cli.py` と登録データとテストだけ。**`topic_models.py` が入っていない** |

## なぜ起きたか

**共有の working tree で、複数の担当が同時に作業していた。**

R4・R5 の担当が規約 9 の確認（直しをわざと戻す）のために `git stash` を使い、
**`git stash pop` で別の担当の stash を取り込んだ。** その状態の working tree を、
こちらが `git add` して commit した。

**担当は事故を正直に報告してきた**（「私の判断ミスです。今後は `git stash` を
使わず、ファイルコピーで退避する方式に変えます」）。**報告が無ければ、
こちらは気づかずに履歴を汚したままにしていた。**

## 何をしたか・しなかったか

- **履歴は書き換えない。** 既に push 済みで、他のセッションも同じ repo を見ている。
  **消して直すより、間違えた事実ごと残すほうがこの repo の流儀。**
- 全体テスト 928 件通過。**内容の欠落は無い**ことを確認した
  （`topic_models.py` に R2 と R5 の両方の変更が入っている）。

## 次からどうするか

1. **ミューテーション（直しをわざと戻す）に `git stash` を使わない。**
   ファイルを読み込んで文字列を差し替え、終わったら書き戻す
   （こちらが使っている方式）。**stash は共有の資源なので、並行作業では壊れる。**
2. **ほかの担当が全体テストを回している間に、ミューテーションをしない。**
   同じ理由で、**壊している数秒間を踏まれる。** 今夜これで 1 件、他の担当の
   全体実行に偽の失敗が出た。
3. **本来は `git worktree` で分けるべき。** いまは順番にやることで避けている。
