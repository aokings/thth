## 0. 一言

**測定は根っこで正しい。ただし「測定を先に作る」のではなく、「印の決まりを今日そろえ、読み手を決める」のが先。** 印（UTM）はもう 10/27 に決まって 4 つの窓口が原稿に書き始めている。GA4 も 4 サイトに入った。足りないのは 3 つだけ: (a) 誰も GA4 を機械で読んでいない、(b) 糸（キャンペーン）と GA4 の数が結ばれていない、(c) 流れ全体を LLM に示す skill が無い。この 3 つを、小さい順に 5 段で出す（§3）。

## 1. 方針の判断

### 1-1. 「測定が先」は正しいか

**正しい。ただ、意味を 1 つ絞る。** 測定を「後から取り直せないもの」と「後からでも取れるもの」に分けると:

| 取り直せない | 取り直せる |
|---|---|
| 投稿の URL に付ける印（UTM）。付けずに出した投稿の訪問は、あとで分けられない | GA4・Cloudflare の数の読み（保持 14 か月。読む道具はあとで作っても過去が読める） |
| 糸の札（原稿の `thread:`）。無ければ投稿が糸に結ばれない | 糸ごとの集計・プラザへの転記・ダッシュボードの欄 |
| 広告の `url_tags`（作るときに付ける。後から付け替えは作り直し） | 広告の成績の読み（Insights は過去も読める） |

だから **今日やるべきは左の列を規約として固め、skill に書くこと**（段 0）。右の列は順に作ればよい。開発の推し「UTM → 解析の読み → 糸ごとの集計 → プラザ → 糸の段と skill」は、左右を混ぜて「skill が最後」になっている。masaru の 4（読めとかやれの前に skill）に照らしても、**skill は最初**に出す。

### 1-2. 流れの順（masaru の 5・6）は良いか

「調査 → はてブ → はてなブログ更新 → 台帳更新 → 本体記事更新 → Threads 等から記事へ誘導（セルクマ含む）→ FB 広告でブースト」——**型としてはこれでよい。** 直す所は 3 つ。

1. **「台帳更新」は知識の側の仕事で、THTH の段ではない。** 構想 5.0 §8 のとおり THTH は台帳を読まない。糸の段には入れず、窓口の手順（各 repo の `docs/sns/README.md` など）に置く。糸のファイルには出来事の 1 行（`researched`・`hypothesis`）で跡だけ残る。
2. **「誘導」は 2 つの中身を持つ: 告知（Threads・X・FB・IG の投稿）とセルクマ。** 今の糸の語彙に `announce` はあるがセルクマが無い。セルクマは「記事が出た直後・1 日 1 件・運営者と書く」（S4 の柵）で、告知とは拍子も柵も違うので、段としては分けて書けるようにする（§3 段 1）。
3. **「広告でブースト」は最後に置くのが正しいが、条件を付ける。** 有機の告知を出して 48〜72 時間の反応（`after`・`--per-post-clicks`）を見てから、効いた 1 本だけを押し出す。THTH は選ばない（数を並べるだけ）。この順を skill に書く。

**前提が変わったら**: 窓口が「記事を書く前に SNS で問いを投げて反応を見る」（SNS 先行）を始めたら、`announce`／`warm` が `article` の前に来る糸も要る。5.0 の段は上から順に満たす形なので、そのときは「順不同の段」の印（`order: free`）を足す。今は要らない。

### 1-3. 3 つの置き場は正しいか

開発の推し（①手順の型＝THTH の skill と糸の宣言、②効いたか＝プラザ、③各メディア固有＝各 repo、hub は見せるだけ）は **おおむね正しい。2 つ直す。**

| 置き場 | 入れるもの | 直す所 |
|---|---|---|
| ① THTH の skill（`skills/thth-flow/`・新設）＋ 糸の宣言 | 流れの**型**（段の名と順・印の決まり・各段で叩く THTH の命令・広告に進む条件・セルクマの柵）。「THTH が触る所」と「流れの形」だけ | SKILL.md（321 行）に足さず、`thth-ads` と同じく**別の skill**に。`thth scenario`・`dashboard` の出力の先頭に skill の 1 行（masaru の 4） |
| ② THTH のプラザ | 「効いたか」の知見（施策＝糸 1 本の結果を分母つきで。再現した・しなかった媒体） | プラザは今 `--from analytics-report|after|study-report` しか観測を付けられない。**`--from scenario <project> <id>`** を足し、糸の段ごとの本数・反応・（段 3 の後は）訪問・広告の費用を道具が付ける（§3 段 4）。masaru の 4 project が同じ owner の組になっているかは未確認（§2-5） |
| ③ 各メディアの repo | 台帳の更新の手順・本体の記事の出し方・自分のサイトの GA4 の見方・プライバシーの文 | そのまま |
| **hub**（開発の推しは「見せるだけ」） | **GA4 と Cloudflare を読むのは hub（SEO レーン）。** これは「自前のもの同士の連携」（10/23 の線）で、THTH が GA4 を読む案は採らない（外の HTTP・サイトの形への依存・外の利用者に無関係） | 「見せるだけ」ではなく、**サイト側の数の読み手**。糸ごとに集計し、THTH へは決めた形の JSON で渡す（段 3・契約 1 本） |

**前提が変わったら**: 外の利用者（repo も hub も持たない人）が「記事へのクリック」を THTH の中で見たいと言うなら、THTH が GA4 Data API を読む口を持つ版が要る。そのときも masaru のサイトの分は hub が読む形を変えない（THTH の口は「利用者が自分の GA4 の鍵を置いたとき」だけ）。

### 1-4. ピクセル（masaru の 3）

**作りはもう別の書き手が 5.6.3 で入れている方向でよい**（`guide.pixel_steps`: 読むだけ・作らない・次の一手の先頭に skill・誘導先の頁に基本のコードが入っているかを確かめる）。この設計で足すのは skill の判断の表だけ:

| 広告の目的 | ピクセルが要るか | 無いとどうなるか |
|---|---|---|
| 反応（engagement・`POST_ENGAGEMENT`） | 要らない | 何も欠けない |
| サイト誘導（traffic・`LINK_CLICKS`） | 無くても出せる。`link_click`・`outbound_click` は取れる | `landing_page_view`（頁が開いた）が取れず `not_measured_or_left` |
| サイト誘導で `LANDING_PAGE_VIEWS` に最適化 | **要る**（Meta がピクセルの発火で最適化する） | 広告セットが作れない・または最適化が効かない |

ピクセルをサイトに入れるのは窓口の仕事で、**Meta への外部送信が増えるのでプライバシーの頁の更新が要る**（GA4 と同じ扱い）。入れるかは広告を出すときに窓口の LLM が上の表で判断し、入れる前に masaru に 1 行（方針を変えるため・§4 ではなく運用の中で）。

### 1-5. 広告の成績（masaru の 2「全て足す」）

別の書き手の 5.6.3 の範囲として扱い、ここでは**つなぎ目だけ**を前提として書く:

- 広告の `url_tags` の既定の形は **有機と同じ鍵に揃える**: `utm_source=facebook|instagram&utm_medium=paid&utm_campaign=<元の投稿の原稿のファイル名、拡張子なし>`。`utm_medium` だけ `social`→`paid` で分ける。こうすると GA4 で同じ記事の「有機」と「広告」が同じ `campaign` の下に並び、糸への結びも原稿のファイル名 1 本で済む（§2-2）。作業木の例（`utm_campaign=kopicha`）は口座名で、記事ごとに分けられないので勧めない。**書き手への 1 行**（開発が渡す）。
- `landing_url` は boost の `--landing-url` か台帳。糸との結びは、広告の `post_id` → `sent/` → 原稿 → `thread:` で THTH が引ける（新しい札は要らない）。

### 段 1: 糸の段の語彙を足し、出力の先頭に skill（THTH 5.7.0・書き手 1 日）
