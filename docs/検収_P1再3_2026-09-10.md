## 4. 実装の要点

### 4.1 A（P1）: sync_repo() を fail-closed の形に反転する

旧実装（`thth/writeback.py::sync_repo()`）は「こういう場合は同期しなくてよい」
という例外を数え上げる作りだった:

- `repo_dir` が存在しない → 成功扱い
- `repo_dir` が git repo でない（`.git` が無い）→ 成功扱い
- （2 巡目で修正済み）`origin` が無い → 同期失敗

3 つ目の枝は 2 巡目で直ったが、2 つ目の枝（`.git` が無ければ成功扱い）が
残っていた。queue ファイルは残っているのに `.git` だけ失われる・退避される
事故が起こると、旧実装はここを無条件で素通りさせ、同期を経ずに select →
公開まで進んでしまっていた（書き戻しの `git add` で初めて失敗する。公開は
もう取り消せない）。

**形を反転させた**: 同期は必ず成功しなければならない・例外はただ 1 つだけ
（`repo_dir` が存在しないこと。この場合 `core.list_queue_files()` は
`os.path.isdir(queue_dir)` で空を返すので、どのみち何も公開されない）。
それ以外はすべて `_confirm_synced()` に渡し、「確認できたときだけ」
`(True, "")` を返させる:

1. `git rev-parse --git-dir` で git repository であることを確認できなければ失敗
2. `git remote` で `origin` の存在を確認できなければ失敗
3. `git fetch origin` が失敗すれば失敗
4. `git pull --ff-only` が失敗すれば失敗
5. 最後に `HEAD` が `@{u}`（upstream）と一致することを直接確認できなければ
   失敗（「エラーが出なかった」ではなく「成功したと確認できた」で通すため。
   pull --ff-only が exit 0 を返しただけの状態に頼らない）

分岐を列挙して素通りさせるのではなく、確認できなかったものはすべて同じ
扱いで落ちる形にしたので、ここに載っていない新しい壊れ方が今後見つかっても、
`sync_repo()` を触らなくても安全側に倒れる。

### 4.2 B（P2）: select_one() を「妥当性」と「出せるか」の 2 段に分ける

旧実装は条件 5（`publish_at` 未来）の `continue` が 1 段目のループに残って
いた。承認後に本文だけを書き換えても、`publish_at` が未来である間は
`approval_stale`（8b の妥当性検査）に一度も届かず検知できなかった——board の
実行時刻によって「見える／見えない」が変わる事故（08:00 に予約したものを
承認後に書き換えると、06:20 の board は 0 件、10:20 の board は 1 件）。

`select_one()` を 2 つの関数に割り、呼び出し順序を固定した:

- `_validate_all(files, ...)`: **`now` を引数に取らない**。型外・account
  違い・post_id あり・status 違い・approval_stale・節が無い・文字数超過・
  トピック不正・重複本文・publish_at が壊れている、を**全ファイルについて
  必ず**計算する。ここで落ちたものは時刻に関係なく `needs_review`・
  `rejections` に出る。
- `_apply_timing_gate(validated, ..., now, ...)`: `_validate_all()` を通った
  候補にだけ、publish_at が未来か・stale_days 超か・静かな時間帯か・最短
  間隔内か、という「いま出すか」を適用する。診断には影響しない
  （`stale` だけは時刻に依存するのでこちら側に置くが、要確認としては出す
  ——現行どおり）。

`_validate_all()` が `now` を引数に取らないのは事故ではない——渡せば
「時刻を見る条件」を書ける余地ができてしまい、同じ穴がまた開く。コードの
docstring に「1 の前に時刻を見る条件を足さないこと」と明記した。

## 9. まだ穴が残ると思う箇所（正直に記録）

- **A は「確認できたときだけ通す」形にしたが、最後の `HEAD == @{u}` 確認は
  `git pull --ff-only` が exit 0 を返した直後に行っている。** `pull` と
  `rev-parse` の間で別プロセスが同じ repo を書き換えるような極端な競合
  （同一マシン上で同じ `repo_dir` を同時に触る別プロセス）までは考慮して
  いない。ただし `thth` 自体は repo 単位のロック（`thth/lock.py`・
  `test_repo_lock.py`）を同期より前に取っているので、THTH 自身の実行同士では
  起こらない。外部プロセスが同じ clone を無警告で触るケースは想定外。
- **B の 2 段分離により、静かな時間帯・最短間隔で落ちる際に報告される
  rejection の候補が増える**（妥当性を先に全部評価するため、`too_long` 等の
  他の理由と `quiet_hours`/`min_interval` の両方が `rejections` に積まれ
  うる——旧実装は先に候補を全滅させていたので後段の理由が付かなかった）。
  `thth/report.py::queue_summary()` の `next_rejections` はこれをそのまま
  返すため、表示件数が増える場合がある。指摘の要求どおりの変更だが、
  運用側の表示件数に影響がある点は明記しておく。
- **C の `mismatch_fields` は 5 項目（body・account・reply_to・topic・
  publish_at）の単位でしか区別しない。** 例えば本文の一部だけが変わっても
  `body` としか出ない（どの文字が変わったかまでは出さない）。要求
  （「どの項目が」）は満たしているが、項目内の差分までは出していない。
- **`board_summary()` は今回も `select_one()` をアカウントごとにもう一度
  実行する構造のまま**（前々回の検収文書から指摘済みの重複。今回も
  呼び出し構造自体は変えていない）。
- **`_confirm_synced()` は `git remote`・`git rev-parse` の stderr の中身
  までは解釈していない。** returncode のみで判定する（前回の検収文書 §7 で
  同種の指摘済み。今回もそこを広げていない）。
