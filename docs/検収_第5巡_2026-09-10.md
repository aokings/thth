## 直した形

### 1. 「確かめた commit」の OID をそのまま持ち回る

`sync_repo()` は `(ok, err)` しか返しておらず、**何を確かめたのか**を捨てていた。
照合のたびに `HEAD` を引き直す実装は、「確かめたもの」ではなく「いま指している
もの」を見ている。**別物である**。

- `sync_repo()` が**確かめた OID を返す**。
- `core.list_queue_files()` は `tree_sha` を**必須の引数**にした。**既定値を
  持たせない**——省略できると「その時の HEAD」に戻る実装が書けてしまい、同じ穴が
  また開く（`_validate_all()` に `now` を渡さないのと同じ流儀）。
- 投稿の経路は `sync_repo()` が返した OID を、`max_per_run` のループを通して
  **固定したまま**使う。board のように同期を伴わない読み手は
  `upstream_sha()`（HEAD が `@{u}` と一致していればその OID・していなければ
  **None**）を使う。

これで P2-3 も同時に閉じる: commit できて push を断られた状態は
`HEAD != @{u}` なので照合先が無くなり、**board は `unverified_content` を出す**。

### 2. `thth approve` が clone のロックに参加する

承認はこの clone の作業ツリー・index・HEAD を動かす。公開の最中に割り込めては
いけない。**front-matter を書く前に**ロックを取り、取れなければ何もせずに断る。

レビュアーの指摘どおり、**1 と 2 は別々の守り**である。ロックだけでは人が手で
`git commit` する経路が残り、OID の固定だけでは同じ index を同時に触る経路が残る。

### 3. commit の対象をそのファイルだけに限る

`git add -- <path>` の後の素の `git commit` は、**index に既に載っている無関係な
変更を全部巻き込む**。`--only <path>` にした。一時 index でそのパスだけを commit
し、**実 index の他のエントリはそのまま残す**（何も消さない・戻さない）。

## 往復を終わらせる（masaru の問い「この往復いつまで続くのかしら」への答え）

**続く理由は「直し方が悪い」ではなく「直し方の種類が悪い」。** 第 4 巡・第 5 巡の
指摘はすべて 1 か所に集まっている——**「git のどの状態を真とするか」**。そして
第 5 巡の 2 件は、第 4 巡の修正が足した仕組みが作った。**条件を足す直し方を
続ける限り、面は増え続ける。**

**面を減らす。** 次の 1 手はこれ 1 つ:

> **公開の入力を、固定した commit の tree からだけ読む。作業ツリーは公開の判断に
> 一切関与させない。**

いまは「disk を読む → tree と突き合わせる」の 2 本立てで、そのために未 commit・
staged・追跡外・無視・symlink の**場合分けを持っている**。tree からだけ読めば
**その場合分けが全部消える**（board は「disk と origin が食い違う」を助言として
出すだけになる）。**規約を足すのではなく、コードを減らす直し方。**

**そのうえで、レビューは範囲を絞って 1 巡だけ**（「git のどの状態を真とするか」
のみ）。それが通ったら **nigamilab 1 本だけ `production: true`** にして、実物で
様子を見る。全部を綺麗にしてから始めるのではなく、**壊れても 1 投稿で済む形**で
始める。

**いまリスクは無い。** 全アカウントが `production: false`、masaru のアカウントは
timer 無し。この 5 巡で失われたのは私の時間と masaru の忍耐であって、投稿事故では
ない。**「いつまで」の実体は「いつ本番に上げるか」であって、「いつ完璧になるか」
ではない。**
