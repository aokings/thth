## 2. いちばん報告したいこと — **正直に書くと落ちる**

記事 A で `provisional` になった理由はこれ 1 つでした。

```
shortfalls:
  - 未解決の不確かさが残っています: このアカウントでの実績（views）が
    まだ 0 本なので、観測から期待した反応が出るかは未検証。
```

そこで `uncertainties` を **空文字にしただけ**で、他は 1 文字も変えずに再実行しました。

```
uncertainties を空にした場合 → status: recommended  shortfalls: []
```

**根拠は 1 つも増えていないのに `recommended` になります。**

これは道具側の欠陥だと思います。手順書 §5 の条件は「未解決の不確かさが残っていない」
ですが、私が書いたのは**トピックが合うかどうかの不確かさではなく、結果（views）の
不確かさ**でした。初投稿のアカウントは必ずこれを書けますし、書けば落ちます。
**正直に書いた人が罰され、消した人が通る形**になっています。

提案: `uncertainties` を 2 つに分ける。

- `evidence_gaps` … 根拠が足りない（＝ `recommended` を止める理由）
- `residual_risk` … 根拠は揃っているが結果は分からない（＝止めない。記録するだけ）

いまのままだと、私を含めて誰もが「空にすれば通る」を学習します。**それを学習させない
ほうがいいと思います。**

## 4. `recommended` にならない理由に納得できるか

**記事 B（日本茶）の `観測の参照がありません` は納得。**そのとおりでした。

**ただし、満たす手段がありません。**`日本茶` の観測は私が 9/10 に入れていて、
`legacy_notes` には出ます。しかし `legacy_notes[].observation` に
**`observation_id` が入っていない**ので、`observation_refs` に書けません。

```
legacy_notes[].observation のキー:
  ['account', 'audience', 'checked_at', 'kind', 'recorded_by', 'status']
```

`topic_store.legacy_observations()` のコメントには、asmon 関東セッションの報告を受けて
**「ID が無いと observation_refs に書けず、満たす手段が存在しなかった」ので ID を与えた**
と書かれています。その修正は観測の棚には効いていますが、**`evidence.legacy_notes` の
射影には出ていません。**LLM の席から見ると、直っていないのと同じです。

あわせて、記事 B の `evidence.observations` に並んだのは**コーヒーの観測 3 件**でした。
その原稿のトピック（日本茶）の記録は 1 件も出ません。**その原稿に関係する観測を
先に出してほしい**です。

## 6. 小さいもの

**(a) `thth` は VM 側で走るので、`--article` のパスも VM 側で解決されます。**
手元の `/tmp/article.json` を指したつもりが、**asmon セッションが VM に置いた同名の
ファイル**（中学受験の記事）を読んでいました。エラーは
`記事証拠 に項目が足りません: [...]` で、**別のファイルを読んだとは書かれません。**
気づくまで数分かかりました。読んだファイルの `final_url` か先頭数十字を
エラーに添えると早いです。`--input-json-stdin` を使えば起きません。

**(b) `thth topics decision <account>` のエラーコードが実態と違います。**

```
thth topics decision kopicha-threads
→ {"code": "store_busy", "message": "ID の形が違います: 'kopicha-threads'"}
```

`store_busy`（棚が使用中）ではなく入力の形の誤りです。メッセージは正しいので実害は
小さいですが、コードで分岐する側が誤ります。あと、**account で最近の判断を引く口**が
あると便利です（いまは decision_id を控えていないと読み返せません）。

**(c) `--advise` の「使ってよい語」と `suggest` の `legacy_judgment` の関係。**
`--advise` は他プロジェクトの判断も「使ってよい語」として並べます（`コーヒー` は
nigamilab の記録から来ています）。`suggest` 側は他所の判断を隔離しているので、
**同じ情報が入口によって扱いが変わります。**`--advise` 側にも「これは他 account の
判断」と添えると、入口の違いで判断がぶれません。

## 7. 良かったところ

- **引用の照合**。読んだふりが機械的に落ちます。私が落ちました
- **`own_judgment` の分離**。`お茶` の件は、分離が無ければ黙って間違えていました
- **`record_payload`**。`suggest` の出力をそのまま `record-decision` に渡せます。
  封筒を組み直す必要がありませんでした
- **`abstained`（トピックを付けない）が正規の選択肢として在ること**。
  「無理に 1 位を作らない」がコードのコメントにも書いてあり、実際そう動きます
- **profile の `basis` が空だと `confirmed` にできない**。根拠なしの確定が作れません
