## 1. F1 への対応

**指摘のとおりでした。** `merge --ff-only origin/release` は相手が祖先なら
**何もせずに成功する**ので、ff 失敗時だけの枝分かれ検査には入りません。
**`HEAD..origin/release` も `0` になるので、board は「追いついています」と出して
いました。**

- `ahead_of_release()` を足し、**一致・遅れ・先行を区別**しました。
- ff が成功しても `HEAD != 配布の枝` なら
  「**配っていない commit で動いています**（`origin/release` より N commit 先。
  配布の枝: xxxxxxx / いま: yyyyyyy）」を返します。
- board では**遅れより先に**出します（いちばん重い状態なので）。
- **実行は継続します。** reset による復旧はしません。**通信失敗時に確認済みの旧版で
  走る方針とは別の欄**にしてあります（`behind` ではなく `ahead`）。

受け入れ条件に挙げられた 3 つを、そのままテストにしました。

| 頂いた受け入れ条件 | こちらのテスト |
|---|---|
| 通常 pull でも main を取らないこと | `test_mainへのpushでは本番が変わらない`（既存） |
| ahead を直接作った場合にも正常/追随済みと扱わない | `test_配っていないcommitで動いていたら黙って正常扱いにしない` |
| 正しい release の早送りは引き続き通る | `test_releaseへ進めた指定commitが届く`（既存） |

## 2. F2 への対応

**2 本とも、取りに行けたかどうかを見ずに手元の値から数えていました。**

- `behind_release(fetch=True)` は、**fetch が失敗したら `None`** を返します
  （古い値から数えません）。
- **枝が無いと判った時点で、手元の追跡 ref を削除**します
  （`git update-ref -d refs/remotes/origin/release`）。**判ったことを、判った時点で
  反映する**形にしました。残す限り、下流のどこかが必ずそこから数えます。
- `board` ごとのネットワーク取得は**義務づけていません**（`fetch=False` のまま）。
- **「欠落確認済み」と「通信失敗」の区別は保っています。** 前者は追跡 ref を落として
  `None`、後者は `ls-remote` が 2 を返さないので**落とさず**、更新処理の文言も
  「枝が無いのか、届かないのかは区別できていません」のままです。

受け入れ条件「正常に再取得できれば現在の状態に戻ること」は、追跡 ref を落としても
次の `fetch` で作り直されるので満たします（`test_遅れをcommit数で数える` が
`None` → `0` の順で通ることを見ています）。

## 4. 記録の訂正（頂いた指摘のとおり）

**「気持ち悪さだけ・動作に影響しない」は誤りでした。** VM のローカル枝の upstream が
`origin/main` のままだと、**保守で誰かが `git pull` を打った時点で配布の境界を迂回
します。しかも迂回したことが以後どこにも出ません。**

設計書 §3.2.1 を次のとおり直しました。

- **VM の追従設定の切り替えは、切り替え作業に含める。後回しにしない**
  （`git branch -u origin/release`）。
- **待ち条件**: 手順 2 で `main` を X へ進めたあと、**VM が実際に X を読み直した
  ことを確認するまで、`main` を X より先へ push しない。** 確認は VM 上で行い、
  **結果を証拠として残す。**
- **確認は `git fetch` の戻り値では行わない。** `for-each-ref` で ref の実在と
  HEAD を見ます。**rc は当てになりません**——これは今回 2 度確かめたことで、
  `git ls-remote`（オプション無しなら枝が無くても 0）と
  `git fetch origin <ref>`（単一枝 clone なら rc=0 かつ何も作らない）の**両方が
  「無いことを成功で返す」口**でした。

**現在の VM / remote HEAD が未実査である**というご指摘も受けます。こちらが書いた
`origin/main` = VM = `7e0cda0` は、**運用セッションが VM 上で実行した出力を受け取った
もの**で、**こちらが VM に入って確かめたものではありません。** 切り替えの手順 2 の
前に、改めて現物で確認します。

## 5. 権限と VM 稼働 commit（完了条件から外しません）

**「今回の範囲外」として本番移行の完了条件から削除しようとしたのは、こちらの誤り
です。** masaru の要件なので、移行の完了条件に残します。

**「人の明示操作だけが唯一の対策」と限定したのも、こちらが選択肢を狭めていました。**
ご指摘のとおり、資格情報や承認経路を分ける選択があります。いま masaru に出している
案は 2 つで、**まだ返事をもらっていません。**

1. `release` への push を GitHub Actions だけに許す ruleset ＋ 承認が要る
   environment（**masaru の操作は承認 1 回。こちらは本当に push できなくなる**）。
   ただし private repo で環境の承認規則を使えるのは有料 plan のはずで、
   **こちらの token では plan が読めず確認できていません。**
2. `thth release <sha>` に機械検査（検収記録の実在・`origin/main` の祖先・早送り・
   記録の残存）を付け、こちらが実行する。**これは masaru に対する保証にはなりません**
   ——検収記録を書くのもこちらなので。**塞げるのは「意図せず配ってしまう経路」まで**
   です。

**技術的に分離できていない範囲は、そのまま記録に残します。** VM の稼働 commit の
確認は、**手元専用の CLI を新設せず、VM 上の確認結果を証拠として残す方法**で足りると
いうご指摘に従います（運用セッションと手順を合わせてあります）。
