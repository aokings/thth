## (1) Platform Data か・保持と削除

**当たる。** §12(l) は匿名化・集計・派生を含む。本文・ID・投稿者を捨てても外れない（09-16・09-18 と同じ読み）。Restricted（§12(p)）には通常当たらないが、n=1・distinct=1・top3_share=1.0 の行は語と日付で特定の 1 投稿・1 人を指す。§3(d)(i)2(d) の例外 "cannot be associated with a particular User" に頼れるのは小標本を抑えた場合だけ。

- **期間**: T に日数の定めは無く、目的に必要な間だけ（(d)(i)2(a)）。「半年の推移で話題を選ぶ」を文書化すれば 180 日は説明可。ただし「超えた月は消す」だと最大約 210 日残る。日単位で削る。
- **退出**: 招待制で運営者の VM が扱う形は Tech Provider（§12(s)）と読む余地がある。その場合 (d)(i)2(d) 後半 "or for Tech Providers, when a User or the Client requests…" に集計の例外は**無い**。退出で project の地図を丸ごと消す設計は必須で、足りている。
- **Meta・User の要求（(d)(i)1）**: 集計の例外は無い。ID が無いので 1 投稿分は引けず、「project 単位・期間単位で行ごと消す」しかない。その受付と記録の手順が未定義。
- **投稿者の元投稿の削除**: 投稿者は §12(u) の User とは限らず、過去の集計を合わせる義務は条文から決まらない（09-18 と同じ）。180 日の失効で上限を切ると明記する。

## (2) 事前再審査

**判断できない。**
- 要らない寄り: (vii) 前半は「別のアプリに見える」変更、後半は "previously collected" の範囲変更。新しく取る集計は文言に直接は当たらない。審査の説明 "reports only aggregate observations"・"Post bodies… never saved" は設計でも真。
- 要る寄り: 審査は「人が打ってその場で見る」形。毎日自動・180 日保持は頻度・保存・保持が増える。前置き "It runs on the user's own machine; nothing is stored on our servers." は 3.0 の招待制（運営者の VM）で**既に実態と違い**、地図はそこに Platform Data を積む。
- どちらでも要る: Dashboard の説明を実態に合わせる（§7(a)）、`https://thth.me/privacy/` に集計の保存を書く（§4(b)。現行 privacy に search の語は 0 件・L1）。説明の変更が再提出でしかできないかは未確認（Dashboard 未見）。推薦は**説明を出してから有効化**。

## (3) 共起の本数

他人の本文に語 B があるかを数えた結果なので **§12(l) の derived**。点を人が決めると語の一覧は Platform Data でなくなり、その場で数えれば漏れの危険は下がる。それでも残る本数の分類は変わらない。co が小さい線は特定の投稿を指すので、閾値を線にもかける。

## (4) 前回の保留理由

1. 生データを保存しない実装: 項目の許可リスト・leak probe・単変異で答えているが、未実装で未検証。stdout・エラー・MCP・LLM 入力・バックアップへの同じ検査は書かれていない。
2. 削除への追随: 保持と退出は定義済み。要求時の手順・VM スナップショット・投稿者側の削除の方針が足りない。

## (5) Meta への説明の下書き（出すかは masaru）

1. THTH は招待した利用者の投稿を、運営者管理のサーバで人の承認を経て扱います。
2. threads_keyword_search で、利用者が登録した最大 20 語を 1 日 1 回検索し、話題選びに使います。
3. 保存は語・日ごとの件数、異なり投稿者数、上位 3 人の占有率、直近投稿までの時間の丸め、語の共起数だけです。
4. 本文・投稿 ID・ユーザー名・リンクは保存せず、小さい標本の値は欠測にします。
5. 記録は本人の project 内だけで見え、180 日で消え、退出や依頼で全部消します。

1. THTH lets invited users publish their own posts with human approval, on an operator-managed server.
2. With threads_keyword_search it searches once a day for up to 20 user-registered keywords to help choose topics.
3. It stores only daily per-keyword aggregates: count, distinct authors, top-3 share, rounded time since latest post, co-occurrence counts.
4. Post text, IDs, usernames and links are never stored; small-sample values are dropped as missing.
5. Records stay within the user's project, expire after 180 days, and are fully deleted on exit or request.

## (6) 設計に足す条件

1. 小標本の抑制: n・distinct・co が閾値（例 5）未満なら null・理由 `small_sample`。
2. 点に @ハンドル・個人名・URL を入れさせない（特定の人の監視にしない）。
3. search_type・limit・since/until を固定して記録。0 件は `zero_or_filtered`（K "The API will return an empty array for any requests that include keywords that we have deemed sensitive"）。
4. 保持の目的と 180 日の根拠を書き、日単位で削る。
5. git に入れない。バックアップ・ログ・MCP・LLM 入力を列挙し、削除で一緒に消えるのを試験する。
6. Meta・User・Client の削除要求の受付と、project・期間単位の全消去と記録。
7. 世間の層は当該 project の中だけ。広場（3.4.0）の外向け・他の持ち主・横断集計・販売に出さない（T §5(b)(ii)1・§3(a)(iv)）。
8. 外部 LLM に渡すなら Service Provider 条件（T §5(a)・09-18）。
9. Dashboard の説明と privacy を直すまで `THTH_MAP_WORLD` は無効。
10. Threads は API だけ。Web の自動取得はしない（https://www.threads.com/robots.txt "Collection of data on Threads through automated means is prohibited unless you have express written permission"）。
11. Bluesky は削除依頼の手順を 6 と共通に。Mastodon は全文検索がサーバ設定に左右されるので件数を「そのサーバで検索に出た数」と表示する（indexable の扱いは未確認）。
