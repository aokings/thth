## 0. 一言で

**ブックマークの正本は口座の `sent/bm:<sha>.json` 1 つにし、配信の台帳には書かない。** 主体の台帳に `owner`（例 `masaru`）を足し、同じ `owner` のすべての主体の `sent/bm:` をまたいで「同じページは 1 回だけ」を守る（柵は 2 つ: 台帳の照合と、公開のエントリー情報 API で masaru のはてな ID が既に付けていないかの確かめ。書く区間は `owner` のロックの中）。対象は、自分の記事（配信の台帳の `published_url`）と、レーンが参照している他人のページ（`--url`）の 2 種。別のレーンの記事（同じ `owner` の別の主体の配信）は断る。承認は今までどおり 2 段・公開のあと・打つのは今（timer には載せない）。自分の記事に付けるのは、公式のヘルプが「自身のアカウントで自身のサイト」を問題にしないと明記しているので続けるが、1 主体 1 日 1 件に絞り、コメントに運営者であることを書かせる。SNS の告知は、SNS の原稿の front matter に `announces: <配信 id>` を書くと、その配信が `published` になるまで timer が待ち（`reply_to_file` の待ちと同じ形）、本文の `{article_url}` を台帳の `published_url` に置き換えて出す。SNS の承認の指紋は、`announces` を「値があるときだけ末尾に足す任意項目」にするので、既存の `approved_sha` は 1 つも変わらない。結果不明は S2・S3 と同じく「出し直さない・人が照合して解く」——ブックマークは `sent/bm:` の行に `result: unknown` を残し、`thth bookmark reconcile` が GET で確かめる。

## 2. 言葉

- **owner**: masaru 個人。主体（はてなのメインとサブのアカウント）を束ねる名。規約の「同一のユーザー」に当たる単位。THTH には今まで無い。
- **自分の記事**（own）: 同じ主体のどれかの口座の配信の台帳に `state: published` と `published_url` がある URL。
- **参照先**（external）: レーンが参照している他人のページ。配信の台帳に無い URL。
- **別レーンの記事**: 同じ `owner` の**別の主体**の配信の台帳にある `published_url`。断る。
- **告知**: SNS（Threads・X・Bluesky・Mastodon）の口座の原稿で、`announces: <配信 id>` を持つもの。記事の公開を待って出す。
- **結ぶ**: 記録（`sent/`・配信の台帳）から「この投稿・このブックマークはこの記事のもの」が機械で引けること。S6（反応を記事へ戻す）がこれを読む。

## 3. ブックマークの正本

### 3.1 比べた案

| 案 | 正本 | 利点 | 欠点 |
|---|---|---|---|
| A（推し） | **口座の `sent/bm:<sha>.json` 1 つ**。配信の台帳には書かない（`bookmark` 欄も history の行も廃止）。出来事は `sent/bm:` から作る | 書く場所が 1 つ（非原子の隙間が消える）。参照先（配信の無い URL）も同じ形で持てる。`guard` の数え・`bookmark_once` は今も `sent/` を見ている | `_delivery_kind` の bookmark の枝と `MUTABLE_FIELDS` の `bookmark` を外す（本番にはまだ何も無いので移行は要らない） |
| B | 配信の台帳 1 つ（`sent/` には書かない） | 記事とのつながりが台帳の中で閉じる | 参照先に台帳が無い。`guard` の数えを台帳から取り直す。S1 §4.2「材料は口座の `sent/`」に反する |
| C | 今のまま 2 つ、書く順を決めて隙間は reconcile で拾う | 変更が最小 | 監査の指摘そのもの（同じことを 2 か所に書く） |

**A にする。** 計画 §2「写しを作らない」と S1 監査 §15 の 2 の指示どおり。

### 3.2 `sent/bm:<sha>.json` の形

`sent.write` の既存の引数（`post_id`・`text`＝コメント・`body_hash`・`sent_at`・`approved_fingerprint`・`kind`・`delivery`・`url`・`blog_id`・`origin`）に、**値があるときだけ**足す欄:

| 欄 | 値 | 意味 |
|---|---|---|
| `kind` | `bookmark_add`／`bookmark_delete` | 今のまま |
| `url` | 承認した URL そのまま（`.strip()` だけ） | 指紋の `url` と同じ文字列 |
| `url_canonical` | §4.3 の正規化のあとの URL | 照合の鍵。`post_id` はこれの sha256 から作る |
| `target` | `own`／`external` | 自分の記事か参照先か。上限（§5）と表示に使う |
| `delivery` | 配信 id | `own` のときだけ |
| `article` | 記事の名 | `own` のときだけ（台帳から写す。S6 が記事ごとに束ねるとき台帳を開かずに済む・**写しではなく索引**） |
| `tags` | 並べ替えたタグの配列 | — |
| `result` | `confirmed`／`unknown`／`not_found` | 打った結果。2xx で JSON が読めれば `confirmed`。§7 |
| `remote` | `{permalink, created_epoch, user}` | 応答のブックマークオブジェクトから。`confirmed` のときだけ |
| `retracted_at`・`retracted_by`・`retract_reason` | 既存の `mark_retracted` | 削除したとき（`bookmark_delete` の行は**別に作らず**、`add` の行に足す。§8） |
| `reconciled_at` | 時刻 | `reconcile` が `result` を書き換えたとき（`unknown` → `confirmed`／`not_found`） |

- `post_id` は `sent.bookmark_post_id(url)` のまま名前は変えず、中身を **`url_canonical` の sha256** にする（§4.3）。本番に `bm:` の行はまだ無いので、既存の値の互換は要らない。
- `sent.write` に `target`・`article`・`tags`・`result`・`remote`・`url_canonical` の引数を足す。SNS の行（`kind` 無し）にこれらが来れば `invalid_sent_kind`（`_hatena_fields` と同じ検査）。
- `sent.mark_bookmark_result(state_dir, post_id, *, result, at, remote=None)` を新しく作る（`mark_retracted` と同じく**足す**だけ。`result` は `unknown` からしか変えない。それ以外は `ValueError("result_fixed")`）。

### 3.3 配信の台帳からブックマークを外す

- `deliveries.MUTABLE_FIELDS` から `bookmark` を外し、`hatena_bookmark.execute_locked` の `deliveries.advance(... bookmark ...)` を消す。
- `events_cli._delivery_kind` の `bookmark` の枝を消し、代わりに **`_bookmark_events(name)`** を足す: 口座の `sent/` のうち `kind == "bookmark_add"` の行から `bookmarked`（`result` が `confirmed` のときだけ。`unknown`・`not_found` は出さない——「出た」と読ませない）、`retracted_at` があれば `bookmark_deleted`。`event_id = "ev_" + sha256("thth.bookmark/1|" + post_id + "|" + ("add"|"delete"))[:24]`（時刻を入れない・S1 §8.1 と同じ理由。`reconcile` で `confirmed` になった行も、落ちずに書けていたときと同じ id）。`ref` は `post_id`、`summary` は `url` と `target`、`at` は `sent_at`／`retracted_at`。`_HATENA_SENT_KINDS` で `_sent_events` が飛ばす決まりはそのまま。
- `thth deliveries` の 1 行と `--json` は、`sent/bm:` を `delivery` で引いて `ブクマ: 付けた（10/20）／未` を**読むときに**添える（台帳には書かない）。

## 4. 主体をまたいだ「同じページは 1 回だけ」

### 4.1 `owner` の欄

主体の台帳 `principals/<p>.json` に `owner`（必須にはしない。無ければ主体の名を owner とみなす＝今までと同じ範囲）を足す。値は `accounts.name_is_safe` を通る文字列。`principal-hatena.json` の雛形に `"owner": "masaru"` を書き、`thth principal add --owner <名>` で写す。`thth principal show` に出す。

`principals.siblings(principal_name) -> list[(名, 台帳)]`（新）: `principals/` を歩いて `owner` が同じ主体（自分を含む）を名前の順で返す。読めない台帳は飛ばす（その主体は `load_principal` で断られるので、今から打つことはできない——`accounts_of` と同じ考え）。

### 4.2 柵は 3 つ（どれか 1 つが抜けても止まる・別の材料を見る）

| # | 柵 | 材料 | どこで | 符丁 |
|---|---|---|---|---|
| 1 | **台帳の照合**: 同じ `owner` の全主体の全口座の `sent/` に、同じ `url_canonical` の `bm:` の行があれば断る（削除済み・`unknown` でも。`not_found` は除く） | `principals.siblings` → `accounts_of` → `sent.read(bm:…)` | `guard._check_hatena` の最後（今の `_principal_bookmarked` を `_owner_bookmarked` に広げる）。**`owner` のロックの中**（§4.4） | `bookmark_once`（詳細 `same_principal`／`other_principal:<主体名>`） |
| 2 | **公開の情報で masaru の ID を探す**: `GET https://b.hatena.ne.jp/entry/jsonlite/<URL>` の `bookmarks[].user` に、同じ `owner` のどれかの主体の `hatena_id` があれば断る。THTH の外（手・別の道具）で付けた分を拾う。**キャッシュなので「無い」は信じない**（柵 1 が主）。GET が失敗（4xx・5xx・時間切れ）したら断らずに 1 段目に「確かめられなかった」と出し、2 段目は通す（柵 1 と 3 がある） | 公開 API（認証なし・`httpsafe`・30 秒・1 回） | `prepare`（1 段目の表示にも出す）と、2 段目のロックの中でもう一度 | `bookmark_once`（詳細 `other_principal_remote:<hatena_id>`／`self_remote`） |
| 3 | **自分の主体で既に付いていないか**: `GET /rest/1/my/bookmark?url=`（この主体の token）が 200 なら断る（手で付けたものを THTH が**上書きしない**——POST は「既にあれば更新」なので黙って上書きできてしまう） | REST API・この主体 | 2 段目のロックの中・POST の直前 | `bookmark_exists_remote` |

柵 2 と 3 は HTTP を打つ。1 段目（`prepare`）で打つのは柵 2 だけ（公開 API・認証なし）。柵 3 は token を使うので 2 段目だけ。どちらも読む側なので上限に数えないが、間隔は 1 回の承認で各 1 回に限る（連打の道は無い: 1 段目は人が打つ・2 段目は digest が要る）。

### 4.3 URL の正規化 `hatena_bookmark.canonical_url(url) -> str`

照合（柵 1・`post_id`）に使う。指紋の `url` は変えない（承認した文字列どおり）。

1. `.strip()`。`urllib.parse.urlsplit`。scheme が `http`／`https` でなければ `invalid_url`。host が無ければ `invalid_url`。
2. scheme と host を小文字に。既定のポート（`:80`・`:443`）を落とす。
3. fragment（`#…`）を落とす。
4. path が空なら `/`。query はそのまま（並べ替えない——`?page=2` と `?page=1` は別のページ）。
5. 制御文字・空白が残っていれば `invalid_url`。

はてなが内部でどう正規化しているかは**未確認**（推測: `http` と `https`・`www` の有無を同じエントリーにまとめている可能性）。THTH の柵は THTH が付けた分に対してのものなので、THTH の正規化で足りる。はてな側の同一視は柵 2（`eid` が同じなら同じエントリー）が拾う。

### 4.4 `owner` のロック

柵 1 は同じ `owner` の 2 つの主体（2 レーン）が同時に同じ URL を打つと、両方が「無い」を見てすり抜ける（主体のロックは別）。書く区間を `owner` のロックで囲む。

- 置き場: `$THTH_ROOT/owner_state/<owner>/bookmark.lock`（`principal_state/` と同じく `state/` の外・0700・`server_files.directory` の規律）。`owner` が無い主体は `owner_state/<主体名>/`。
- 順: **repo → principal → account → owner**。`owner` は `hatena_bookmark.execute_locked` の中でだけ取り（`lock_mod.acquire(wait=0)`・待たない）、持っている間に他のロックを取らない。順が全順序で、owner を持って上位を待つ経路が無いので詰まらない。取れなければ `GuardRefused("bookmark_busy")`（`SAFE_ERRORS` に足す）。
- timer はブックマークを打たないので、`core._account_locks`・`server_files.account_locks` は触らない（ロックの段を増やすのは bookmark の 1 関数だけ）。

## 5. 自分の記事に付けるか・参照先の範囲・上限

### 5.1 自分の記事（セルクマ）: 付ける。ただし絞る

公式の原文（§1.2 のスパムの頁の「なお」書き）が「自身のアカウントで自身のサイト」を問題にしないと明記しているので、**付ける**。問題にされる側（同じ頁）は「スパム目的と判断される態様」「機械的な高頻度」「メインとサブで同じサイト」「同一サイトのページを大量に」。だから:

- 1 記事 1 回・同じ `owner` で 1 回（§4）。
- 主体ごとに **1 日 1 件**（`daily_max_self_bookmarks`・既定 1・`LIMIT_DEFAULTS` と `principal set` の鍵に足す。`target: own` の `bookmark_add` を数える）。全部で `daily_max_bookmarks`（3）の内側。
- 承認のときだけ（timer が記事の公開に続けて自動で打つ形は作らない——「ブックマーク数に応じた自動投稿」の例に近い自動の形を避ける）。
- コメントは必須（今のまま）。1 段目の表示に「運営者であることが分かる文にしてください（例: 自分の記事。…）」の 1 行を添える。THTH は中身を検査しない（利用者とその LLM を疑わない）。
- `private` は `false` 固定（今のまま）。非公開のブックマークは「参照している印」にならない。

### 5.2 参照先（他人のページ）: 付ける。条件は同じ 2 段

- 対象は `--url` で渡す URL。`http`／`https` だけ。配信の台帳と照合して、自分の記事なら `use_delivery`（`--delivery` で指す形に誘導）、別レーンの記事なら `bookmark_other_lane_article` で断る（§6.1）。
- 主体ごとに 1 日 `daily_max_bookmarks`（3）の内側。**同じホストに 1 日 1 件**（`bookmark_same_host_daily`・既定 1。「同一サイトのページを大量に」を避ける。`url_canonical` のホストで数える。自分の記事のブログのホストも同じ数え方）。
- 存在しないページを繰り返し付けない: 柵 2 の GET が `count: 0` で title が空でも断らない（新しいページはそう見える）が、1 段目に「はてなにまだエントリーが無いページ」と出す。
- タグは任意。コメントは必須のまま（「無関係なタグやコメントで誘導」の反対側＝そのページについて書く）。

### 5.3 上限の表（主体ごと・既定）

| 鍵 | 既定 | 数える行 | 符丁 |
|---|---|---|---|
| `daily_max_bookmarks` | 3 | `bookmark_add`（`retracted_at` も同じ枠）。`result` を問わない（`unknown` も数える＝安全側） | `bookmark_limit` |
| `daily_max_self_bookmarks`（新） | 1 | `target: own` の `bookmark_add` | `self_bookmark_limit` |
| `bookmark_same_host_daily`（新） | 1 | 同じ `url_canonical` のホストの `bookmark_add` | `bookmark_host_limit` |
| `burst` | 3 件/30 分（entry と合算） | 今のまま | `principal_stopped`（burst） |

`owner` をまたいだ合計の上限は置かない（S1 §17: メインとサブは別の人に見える形で出す。要れば `owner` の欄に足す）。

## 6. 承認の対象と段

### 6.1 対象の決め方 `hatena_bookmark.prepare`

引数を `delivery: str | None, url: str | None` にし、**どちらか 1 つ**（両方・どちらも無しは `invalid_request`）。

1. `delivery` あり（own）: 今のまま（`published` と `published_url`）。`url` は台帳から。`target = "own"`。
2. `url` あり（external）: `canonical_url` を通す。同じ `owner` の全主体の全口座の配信の台帳（`deliveries.list_for`）を歩き、`published_url` の `canonical_url` と一致するものを探す:
   - 同じ主体の口座の配信 → `use_delivery`（`--delivery <id>` を案内）
   - 別の主体の配信 → **`bookmark_other_lane_article`**（断る。別レーンの記事を参照先の顔で付けない）
   - 無い → `target = "external"`
3. 柵 2（§4.2）の GET を 1 回。結果を `p["others"]`（同じ `owner` の ID の一覧・`checked`／`unchecked`）に。
4. 指紋（§6.2）。残り枠（`daily_max_bookmarks`・`daily_max_self_bookmarks`・同じホスト）を `p` に。

### 6.2 指紋 `thth-hatena-bookmark-1` の緩め

`compute_hatena_bookmark_components` の `delivery` を**空を許す**に変える（空なら `""`。値があれば今までどおり `is_delivery_id`）。`url` は `canonical_url` を通ることを検査する（`invalid_url`）が、指紋に入るのは `.strip()` した元の文字列。

版の語は **`thth-hatena-bookmark-1` のまま上げない**。理由: 既知の入力（`delivery` あり）に対する出力は 1 バイトも変わらない（T-S4-4a で固定）。空の `delivery` は今まで断られていた入力なので、既存の指紋と衝突しない。`fingerprint_golden.GOLDEN["hatena_bookmark"]` に `bookmark_add_external`（`delivery: ""`）の行を**足す**。`target` は指紋に入れない（`delivery` の有無で決まる）。

### 6.3 1 段目の表示（手元・遠くの道・MCP で同じ材料）

```
ブックマーク  kopicha-hatenablog（主体 hatena-kopicha・owner masaru）
URL: https://example.com/coffee/arabica-2026

はてな側: ブックマーク 12 件・masaru の ID は付けていない（10/17 09:12 に確かめた・キャッシュ）
          ← 付いていれば「hatena-asmon（asmon-kanto-sub）が付けています → 断ります」
コメント: …

```

### 6.4 承認の時機（S1 §12・§14 との整合）

**公開のあと・URL が決まってから**（S1 の推しのまま）。自分の記事は `published` の配信だけ、参照先はいつでも。timer には載せない（打つのは今）。「記事の承認と一緒に承認して公開後に機械が打つ」形は 4.0 では作らない——§5.1 の「自動で打たない」とも揃う。

### 6.5 2 段目 `execute_locked`（順）

1. `guard.check(kind="bookmark", bookmark_url=url_canonical, bookmark_target=…)` — 主体の止め → 口座の止め → `bookmark.lanes` → `daily_max_bookmarks` → `self`／`host` の枠 → burst → **ここでは `bookmark_once` を見ない**（4 へ）
2. `principals.check_account`
3. adapter を作る（無ければ `unsupported_medium`・作れなければ `AdapterUnavailable(code)` → `BookmarkError(code)`・何も書かない）
4. **`owner` のロック**を取る（取れなければ `bookmark_busy`）。中で:
   1. 柵 1（台帳）→ `bookmark_once`
   2. 柵 2（公開 API）をもう一度 → `bookmark_once`（`*_remote`）。GET が失敗なら通す
   3. 柵 3（`get_bookmark`）→ 200 なら `bookmark_exists_remote`。404 なら進む。それ以外（401・5xx・時間切れ）は**打たない**（`bookmark_precheck_failed`・何も書かない。出ない側）
   4. `add_bookmark(url, comment, tags)` を 1 回
   5. 結果の写し（§7）: `ok` → `sent.write(result="confirmed", remote=…)`。`ambiguous` → `sent.write(result="unknown")`。断り → 何も書かず `BookmarkError(code)`
5. ロックを放す。返り値に `post_id`・`result`・`permalink`。

adapter の例外（`Exception`）は 4-4 の中で受けて **`ambiguous`** に写す（S1 監査 §15 の 2「adapter の例外は結果不明として扱う」）。`sent.write` が失敗したら（ディスク）例外をそのまま上げる——媒体には出ているので、ログに `url` と「`thth bookmark reconcile` で拾う」を出す。

## 7. 結果不明の扱い（S2 §3.5・S3 §6.4 に揃える）

adapter `thth/adapters/hatenabookmark.py` の `BookmarkResult(ok, ambiguous, error, status, bookmark: dict | None)`:

| 起きたこと | `ok` | `ambiguous` | `error` | `sent/bm:` |
|---|---|---|---|---|
| POST 200／201・JSON が読めて `user` が主体の `hatena_id` と同じ | 真 | — | — | `result: confirmed`・`remote` |
| POST 2xx・JSON が読めて `user` が違う | 偽 | **真** | `hatena_user_mismatch` | `unknown`（別の ID の token？ 人が見る） |
| POST 2xx だが JSON が読めない・`user` が無い | 偽 | 真 | `response_invalid` | `unknown` |
| 400 | 偽 | 偽 | `hatena_http_400` | 書かない |
| 401・403 | 偽 | 偽 | `hatena_auth_rejected` | 書かない。`thth principal auth <p> --force` を案内 |
| 404（POST） | 偽 | 偽 | `hatena_http_404` | 書かない |
| 429 | 偽 | 偽 | `provider_rate_limited` | 書かない。主体の止めは掛けない（S2 §3.6） |
| その他 4xx | 偽 | 偽 | `hatena_http_<code>` | 書かない |
| 5xx | 偽 | 真 | `hatena_http_<code>` | `unknown` |
| 時間切れ・`URLError`・`OSError`・接続断 | 偽 | 真 | `hatena_transport_failed` | `unknown` |
| `RedirectBlocked`（書き込みの要求は届いている） | 偽 | 真 | `redirect_blocked` | `unknown`（S2 監査 中-1 と同じ） |
| 応答が大きすぎる（上限 1 MiB） | 偽 | 真 | `response_too_large` | `unknown` |
| `EndpointRejected`（接続の前） | 偽 | 偽 | `endpoint_rejected` | 書かない |
| adapter の例外 | 偽 | 真 | `adapter_error`（`redact` を通した文） | `unknown` |

- **`unknown` は失敗とみなして打ち直さない**。`bookmark_once` が同じ URL の 2 回目を断る（`unknown` も「付いているかもしれない」）。
- 解く口 **`thth bookmark reconcile <口座> [--url <URL>] [--by <名前>]`**（新・CLI だけ・MCP と thth.me に出さない）: `result: unknown` の行ごとに `get_bookmark(url)`（この主体の token）を 1 回。200 で `user` が一致 → `confirmed`（`remote` を埋める）。404 → `not_found`（枠には数えたまま・`bookmark_once` は以後この行を無視するので打ち直せる）。それ以外 → そのまま（次回）。間隔は 1 件ごとに 2 秒（公式の「数秒空けて」）。`admin_log.append("bookmark_reconciled", …)`。
- `thth doctor <口座>` のはてなの枝に「ブックマーク: 結果不明 n 件（`thth bookmark reconcile`）」を足す。`thth morning`／`report` の要確認には**足さない**（4.0 では CLI の案内だけ。増やすなら S6）。
- inflight は使わない（timer の公開を止めるほどの事故ではなく、ブックマークは独立に照合できる）。

## 8. 削除・修正

- **削除** `thth bookmark delete <口座> (--delivery <id> | --url <URL>) [--confirm <digest> --by <名前> --production]`: 2 段。指紋は `op: delete`（既存の `bookmark_delete` の golden）。2 段目はロック（repo → principal → account・owner は要らない）の中で `guard.check(kind="bookmark_delete")`（`daily_max_bookmarks` の枠・burst）→ `delete_bookmark(url)`: 204 → `sent.mark_retracted(bm:…)`（`retract_reason` に `--reason`・無ければ `bookmark_delete`）。404 → **消えているので同じく `mark_retracted`**（`retract_reason: remote_missing`）——打ち直さない。5xx・時間切れ → 何も書かず `BookmarkError`（削除は冪等なので次に人がもう一度打てばよい。`unknown` の行は作らない）。401 → `hatena_auth_rejected`。対象は `sent/bm:` に `confirmed` か `unknown` の行がある URL だけ（無ければ `bookmark_not_found`。手で付けたものを THTH から消す口は作らない）。
- `bookmark_delete` の行は作らない（S1 §7.3 の `sent/bm:` の `kind: bookmark_delete` は使わない。`guard._classified` は `retracted_at` を同じ枠に数える——今のまま）。
- **修正（コメント・タグの直し）は 4.0 に入れない**。POST は「既にあれば更新」なので作れるが、「同じ URL を 2 度打つ」を柵で止めている側と矛盾する口になる。直すのははてなの画面から（THTH は打ったあとのコメントを追わない）。入れるなら `op: update`（指紋に `base_comment_sha256`）を 4.1 で。
- 削除のあとの再追加は `bookmark_once` で断る（今のまま・S1 §4.2）。

## 9. SNS の告知を記事に結ぶ

### 9.1 比べた案

| 案 | 形 | 利点 | 欠点 |
|---|---|---|---|
| A | 記事が出たあとに LLM が告知を書く（本文に URL を直書き）。front matter の `announces` で結ぶだけ | 置き換えが無い。承認した本文がそのまま出る | 予約の記事（朝 8 時公開）の告知を前の晩に承認できない。レーンの LLM が公開のあとに起きて書く段取りが要る |
| B（推し） | 告知の原稿に `announces: <配信 id>` と本文の `{article_url}`。timer は配信が `published` になるまで待ち、出す直前に `published_url` へ置き換える | 計画 §3.4「公開が `published` になってから timer が出す（公開した URL を告知に差し込む）」そのもの。記事と告知を一度に承認して寝られる | 承認した本文と出る本文が URL の 1 か所だけ違う。置き換える値は台帳の `published_url`（ホストが `blog_id` と違えば S1 で `conflict` になっている）に限る |
| C | 告知を記事の配信原稿の中（`## threads` の節）に同居させ、1 つの承認で両方 | 承認が 1 回 | はてなの指紋に SNS の本文が入る・口座が 2 つにまたがる原稿は今の queue の形（1 原稿 1 口座）を壊す |

**B にする。A の形も通る**（`{article_url}` が無ければ置き換えず、`announces` で結ぶだけ。URL を直書きしたら本文の指紋に入る）。

### 9.2 原稿の形（SNS の口座・既存の front matter に 2 つ足す）

```markdown
---
thth: 1
account: kopicha-threads
status: draft
publish_at: 2026-10-20T08:30:00+09:00
topic: price
announces: dl_3f9c2a7e1b4d
article: kopicha/2026-10-arabica
---

## threads

アラビカの 10 月の値動きをまとめました。{article_url}
```

| 欄 | 意味 | lint |
|---|---|---|
| `announces` | 結ぶ配信 id（`dl_…`）。**同じ project の**はてなの口座の配信（`deliveries.read` で `project` を突き合わせ・別レーンの配信は `announces_other_lane`） | `invalid_announces`（形）・`announces_not_found`（台帳に無い）・`announces_other_lane`。SNS の口座でだけ効く（はてなの口座に書けば `announces_not_allowed`） |
| `article` | 記事の名（任意。無ければ台帳から写す。あれば台帳と一致しなければ `article_mismatch`） | 表示と `sent/` の索引のため |
| 本文の `{article_url}` | 0 個か 1 個。2 個以上は `article_url_placeholder_twice`。`announces` が無いのに置けば `article_url_without_announces` | 文字数は **`https://<blog_id>/entry/0000/00/00/000000`（41 字）に置き換えて数える**（X は URL を 23 字に数える既存の `count_for` がそのまま効く。Threads・Bluesky・Mastodon は実際の URL の長さに近い値で数える——`published_url` は確定するまで分からないので、上限に近い本文は承認の段で `warning: length` が出る） |

- `publish_at` は記事の `publish_at` より前でもよい（待つ）。
- `reply_to_file`・`announces` の併用は許す（返信の形の告知）。

### 9.3 承認の指紋（SNS の v1・既存の `approved_sha` は変わらない）

`approval._OPTION_ORDER` の末尾に **`announces`** を足し、`publish_options(fm)` が `announces` の値（`.strip()`）を返す。値があるときだけ `announces=dl_…` が末尾に付く（3.19.0 の `community_id` と同じ形・`FINGERPRINT_VERSION` は**上げない**・`fingerprint_golden` に `announces` の行を足す）。`{article_url}` は本文の一部として指紋に入る（置き換えの**前**の本文）。`article` は指紋に入れない（表示用。`announces` が結びを固定する）。

承認のあとに `announces` を書き換えれば `approval_stale`。台帳の `published_url` が変わる経路は無い（S1: 1 配信に 1 つ・変えるなら `conflict`）。

### 9.4 timer の待ちと置き換え（`select.py`・`core._throw_chosen`）

1. `select_one` で、`announces` のある原稿は `resolve_announces(qf, account_cfg) -> AnnounceResolution(delivery, url, reason)`（新・`resolve_reply_to_file` と同じ形）:
   - 配信を**同じ project のはてなの口座**から探す（`accounts.list_account_names` → `project` が同じ・`media: hatenablog` → `deliveries.read`）。見つからない → `announces_unresolved: target_missing`（held）
   - `state: published` で `published_url` あり → 解決
   - `wanted`・`inflight`・`unknown` → `announces_unresolved: waiting_for <delivery>`（**待つ**・held には数えない・board に「記事 dl_… の公開待ち」）
   - `conflict`・`deleted`・`no_follow` → `announces_unresolved: target_<state>`（held・人が見る）
   - 台帳が読めない → `announces_unresolved: target_unreadable`（held）
   - `waiting_target`・`held_category` に `announces_unresolved` の前置きを足す（`HELD_CATEGORIES` に `announces_unresolved` を**足す**。既存の 4 語は変えない）
2. `_throw_chosen` で、`resolution` に `announces` の `url` があれば、指紋（置き換え**前**の `effective_section`）を固定したあと、**inflight に書く本文と adapter に渡す本文**を `effective_section.replace("{article_url}", url, 1)` にする。`inflight.text_fingerprint` も置き換え後。ログに「告知: dl_… → https://…」。
3. `sent.write` に `announces`・`article`・`article_url` を足す（値があるときだけ・SNS の行に初めて足す欄。無ければ 1 バイトも変えない。`_hatena_fields` とは別の `_announce_fields` で検査: `announces` は `is_delivery_id`）。
4. queue の書き戻しは今のまま（`post_id`・`url`）。
5. `thth deliveries <口座|project> --article …` は、同じ project の SNS の口座の `sent/` から `announces` が一致する行を集めて「告知: kopicha-threads 10/20 08:31（post_id）」を添える（読むときに集める・写しを作らない）。S6 はここから記事ごとに SNS の数を束ねる。

### 9.5 遠くの道・MCP・thth.me

- `draft_put`（遠くの道で SNS の下書きを書く）に `announces` と `article` の鍵を足す（`_schema` の許す鍵に足すだけ。本文の `{article_url}` は本文の一部）。`schedule_request`（SNS は 1 段で刻む・今のまま）は `publish_options` が `announces` を拾うので指紋に入る。
- `send_request`（その場で出す）は `announces` を**受けない**（`invalid_request`）——出す直前に待つ段が無い。告知は queue に刻んで timer が出す道だけ。
- MCP `thth_draft_put` に `announces`・`article` の引数を足す。新しい道具は足さない。
- thth.me の /activity（持ち主の取り消し）は今のまま効く。待っている告知は board・`thth morning` に「記事の公開待ち」で名前が出る（`waiting_for` と同じ扱い）。Worker の変更は無い。

## 10. adapter `thth/adapters/hatenabookmark.py`

- S2 の `hatenablog.py` と同じ作法（`base.Adapter` は継がない・`REGISTRY` に載せない・`_request` 1 つ・`httpsafe.urlopen`・`User-Agent: thth/<版> (+<user_agent_contact>)`・`redact`・再試行なし・sleep なし）。差し込みは `hatena_bookmark.ADAPTER_FACTORY or hatenabookmark.factory` を**`execute_locked` が呼ぶ直前**で解決（S2 §3.1 と同じ）。
- `factory(account_cfg, principal_cfg) -> HatenaBookmarkAdapter`: token・consumer の読み方は `hatenablog.factory` を使い回す（同じ主体の同じ token）。
- 口:

```
get_bookmark(*, url) -> dict | None                 # GET /rest/1/my/bookmark?url=  200 → ブックマークオブジェクト・404 → None・他は BookmarkHTTPError(status)
add_bookmark(*, url, comment, tags) -> BookmarkResult   # POST /rest/1/my/bookmark
delete_bookmark(*, url) -> BookmarkResult           # DELETE /rest/1/my/bookmark?url=  204 → ok・404 → ok（missing=True）
entry_info(*, url) -> dict | None                   # GET https://b.hatena.ne.jp/entry/jsonlite/<URL>（認証なし・柵 2）。失敗は None
probe() -> dict                                     # GET /rest/1/my（doctor・principal auth の段 7 に「ブックマーク: ID <name>」を足す）
```

- **パラメタの渡し方**: 公式の Ruby の例に合わせ、`url` は**クエリ**に（`urllib.parse.urlencode([("url", url)])`）。`comment`・`tags`・`private` は **form の body**（`application/x-www-form-urlencoded; charset=utf-8`）に入れ、`oauth1.authorization_header(body_params=…)` で base string に含める（RFC 5849 §3.4.1.3.1・`oauth1.py` は form の body を受ける）。`tags` は **`tags` を繰り返す**（`[("tags", "a"), ("tags", "b")]`）——公式に形の記述が無いので**推測**。実機の 24（§15）で確かめ、通らなければ 1 つの値（空白区切り）を試す。`private` は送らない（公開・既定）。
- 応答の読み: `json.loads`（UTF-8）。`dict` で `user` が `str` でなければ `response_invalid`。`tags` が list でなければ `[]` に倒す（記録には応答のまま入れる）。
- 時間切れ: GET 30 秒・POST／DELETE 60 秒（`min(口座の timeout, これ)`）。応答の上限 1 MiB（`jsonlite` は `bookmarks[]` が長くなりうる。超えたら柵 2 は「確かめられなかった」）。
- 公開 API（`entry_info`）は `Authorization` を**付けない**（`b.hatena.ne.jp` は別ホスト。token を別ホストに送らない）。`httpsafe` の同一 origin の決まりはそのまま（リダイレクトは追わない）。

## 16. masaru に伺うこと

1. **参照先のブックマークの「同じホストに 1 日 1 件」の既定。** 推し: **1 件**（§5.2・§5.3）。理由は、スパムの頁の「同一サイトのページを大量にブックマーク」に当たらない側に倒すため。代わりの形は「ホストの枠は置かず、全体の 3 件だけ」。前提が変わる点: レーンが 1 つのサイト（例: 相場の情報サイト）を毎日参照していて、同じホストの別のページを日に 2〜3 件付けたいなら、`bookmark_same_host_daily` を主体の台帳で上げる（既定を変えるのではなく主体ごとに）。
2. **遠くの道（レーンの LLM）に、別の主体の名を見せてよいか。** 推し: **見せる**（§6.3「hatena-asmon が付けています」）。理由は、どのレーンが先に付けたかが分かれば、レーンの LLM が「参照先が重なった」と気づけ、masaru に相談できる。代わりの形は「別の主体が付けています」に伏せる。前提が変わる点: レーンの鍵を masaru 以外の人（外の利用者）に渡すようになったら、伏せる形に変える（主体の名は `principals/` の台帳の名で、鍵の範囲の外）。

ほかは推しで決めた（正本は `sent/bm:` 1 つ・owner のロック・柵は 3 つ・自分の記事は 1 主体 1 日 1 件・参照先は許す・修正は作らない・削除は add の行に足す・結果不明は inflight でなく行の `result`・告知は `{article_url}` の置き換えと待ち・SNS の指紋は任意項目・版は上げない）。
