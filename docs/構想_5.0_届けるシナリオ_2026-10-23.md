# 構想: THTH 5.0 — 届けるシナリオ（2026-10-23・夢想の叩き台）

書いた人: THTH開発 第9（Claude Opus 5.5）。masaru との 10/23 の会話（「THTH5.0を夢想しようのコーナー」）をまとめたもの。

**この書の位置づけ**: 夢想の叩き台。**作ることはまだ何も決めていない。** 事実（いまある部品）と、夢（足したいもの）を分けて書く。

---

## 0. 一文で

はてブに調べた跡が残り、はてなブログに調査日記やこぼれ話が書き残され、本体に知識がたまって記事が出て、Threads や X で告知され、そこでファンが温まる——この一連の流れを、**シナリオとして宣言し、いまどこにいて次に何が要るかを THTH が出す**。

masaru 10/23:「一連の流れが、シナリオとしてコントロール出来るのがよいのではないでしょうか」

## 1. 線引き（masaru 10/23）

「THTHはコンテンツをデリバリーするのではないかな。ハブは自前のモノの連携・管理だよね」

- **THTH**: 中身を外へ届ける側。はてブ・はてなブログ・Threads・X をまたぐ**届け方の束ね（シナリオ）も THTH に置く**。
- **hub**: masaru の自前のもの（道具・サイト・セッション）同士の連携と管理。見せる画面。THTH のシナリオは、THTH が出す口を読んで朝の一枚に載せる。
- 10/15 の「ダッシュボードやメディア間連携なんかは、ハブに譲っちゃう」は、これで読み替える（外へ届ける媒体をまたぐのは THTH、自前のもの同士をつなぐのは hub）。

THTH の立場は変えない。**THTH は書かない・決めない**。原稿を書くのは窓口の LLM、出すのを決めるのは承認。THTH は材料と「次の一手」を出し、届け、数える。

## 2. 流れ

```
はてブ        調べた跡が残る（読んだ・拾った・一言）
  ↓
はてなブログ   調査日記・こぼれ話（途中の考え・寄り道）
  ↓
本体          知識がたまり、記事として出る
  ↓
Threads・X    記事を告知し、日々の小さな話で場を温める
  ↺
ファン        返信・反応 → 次に調べることの種へ
```

## 3. いまある部品（10/23 の事実）

| 段 | いまの THTH | 出典 |
|---|---|---|
| はてブ | `thth bookmark`（1 本ずつ・1 日分まとめて・2 段の承認）。第三者が付けたブックマークの採取（`bookmark_received`） | `thth/bookmark_cli.py`・`bookmark_batch.py`・`events_cli.py` |
| はてなブログ | 記事の配信の台帳（`thth deliveries`）、外での手直しの検出（`thth conflict`）、反応の採取（`thth hatena`） | 4.0 S5・S6 |
| 本体 → 告知 | 告知の投稿に、どの記事を告げたかを結ぶ（`announces`・`article`） | 4.0 S4 §9.5・§11 |
| SNS で温める | 返信の取り直し（4.4.0）、未返信（`unanswered`）、相手ごとの履歴（`who`）、次に絡みに行く所（`where`）、出したあとの受け取られ方（`after`） | 各リリースノート |
| 拍子と在庫 | 予約の在庫（`schedule_low`・4.5.2）、1 日の本数（`schedule_thin`・4.5.4） | `events_cli.py` |
| 流れを読む口 | `thth events`（公開・返信・言及・止まり・予算・在庫） | `events_cli.py` |

部品はそろってきた。**足りないのは、これらを 1 本の話としてつなぐ層。**

## 4. 足したいもの（夢）

### 4.1 話の糸

1 つのテーマに id を振り、はてブ・日記・本体の記事・告知・反応を同じ糸にぶら下げる。原稿の front-matter に `thread_of: <糸の id>` のような 1 行を足すだけで結べる形が、窓口の LLM にとって軽い。

### 4.2 段の宣言（シナリオのファイル）

糸の進め方をファイルで書く。例（形は仮）:

```yaml
scenario: 数字で淹れる
stages:
  - collect:  { medium: hatena_bookmark, until: 10 }        # はてブが 10 本たまったら次へ
  - diary:    { medium: hatenablog, count: 2 }              # 調査日記を 2 本
  - article:  { medium: site, signal: delivered }           # 本体の記事が出たら次へ（本体は出来事を渡すだけ）
  - announce: { media: [threads, x], over_days: 3,
                mix: { announce: 1, spillover: 2, question: 1 } }  # 告知 1・こぼれ話 2・問いかけ 1
  - warm:     { media: [threads, x], replies_within_hours: 6 }     # 返信は 6 時間以内に
loop: questions_with_most_replies -> next_collect             # 反応の多かった問いを次の糸の種へ
```

### 4.3 いまどこか

糸ごとに「どの段まで来たか・次に何が要るか・何が止まっているか」を 1 枚で出す（`thth scenario <糸>` のような口と、`events` の新しい種類）。窓口の LLM はそれを読んで次の原稿を書き、承認に回す。hub はそれを読んで朝の一枚に載せる。

### 4.4 戻りの輪

SNS の反応（どの問いに返信が多かったか・どの記事の告知がクリックされたか）を、次に調べるテーマの候補として糸に返す。THTH は候補を並べるだけで、選ぶのは窓口。

### 4.5 定期の型（シリーズ・枠）

masaru 10/23:「コピチャや関東がいま挑戦している定期配信系もこのシナリオの中に入ると思う」

シナリオには 2 つの種類がある。

- **糸**（4.1〜4.4）: 1 つのテーマが、調べる → 日記 → 記事 → 告知 → 温める と進んで終わる話。
- **型**: 決まった曜日・時間帯に、決まった形で出し続けるもの。終わりが無く、在庫（材料と承認済みの原稿）が尽きないことが大事。

いま窓口が挑戦している型（10/23 に各 repo と VM の原稿の名前で見たもの）:

| 窓口 | 型 | 形・拍子 | 材料の出所 |
|---|---|---|---|
| kopicha | シリーズ「数字で淹れる」（masaru 10/16 決定） | 3 段（問い → 出典の数字 → あなたは？）・最初の行に【数字で淹れる】・週 2 回くらい（Threads と X）・火・金の朝 | 知識の台帳 `data/knowledge/claims.csv` の主張（台帳に 8 回分＋束 res-cafe1） |
| kopicha | 質問募集の定期枠（案・9/29） | 週 1 本・答えられる問いの例を 2 つ添える・1 週間受け付ける | 窓口が書く |
| 関東 | 時間帯ごとの型（原稿の名前から読んだもの・窓口の文書では未確認） | 昼・夕は過去問、19 時は問い、21 時は悩み、8 時は週末の行事など。10/14〜20 は 1 日 4〜5 本 | 本体（asmon.ai/kanto）の記事・過去問の台帳 |

型を宣言すると、THTH が言えることが増える:

- **型ごとの在庫**: 4.5.4 の `schedule_thin` は口座全体の本数で鳴る。型が分かれば「21 時の悩みの枠の原稿が 10/21 から 0 本」と、どの型が尽きたかを名指せる（10/21 の関東はまさにこれ）。
- **材料の在庫**: 「数字で淹れる」なら、台帳の主張のうち、まだ出していない回があと何回分か。材料が尽きる前に「調べる」（糸の collect）を起こす合図になる。
- **型ごとの受け取られ方**: 型ごとに views・返信・フォローの動きを並べる（9/29 の質問募集の案で人が手で作った表を、道具が出す）。

型と糸はつながる。型の 1 回（例: 数字で淹れる No.2 煎茶）は、糸の告知や温める段の 1 本でもある。型の回に `series: 数字で淹れる`、糸に `thread_of:` を付ければ、両方から数えられる。

宣言の形（仮）:

```yaml
series: 数字で淹れる
account: [kopicha-threads, kopicha-x]
rhythm: { per_week: 2, days: [tue, fri], hour: 7 }
form: { head: "【数字で淹れる】", steps: 3, link: false }
material: { ledger: data/knowledge/claims.csv, unit: 回 }   # まだ出していない回を数える
stock_floor: { approved: 2, material: 4 }                    # 承認済み 2 本・材料 4 回分を切ったら知らせる
```

## 5. 例: kopicha「数字で淹れる」No.2 煎茶（10/23）

いまの姿から、糸 1 本をたどる。

1. **collect**: 全国茶生産団体連合会の「おいしいお茶を淹れる目安」などをはてブに残す。
2. **diary**: はてなブログに「煎茶の湯温をはかってみた」日記・「深蒸しはなぜ 30 秒か」のこぼれ話。
3. **article**: 本体にレシピカードと記事。
4. **announce**: 10/23 07:00 の Threads の投稿（`2026-10-23-th-num-02-sencha.md`・画像つき）と、そのあとのリンク投稿（`2026-10-23-th-num-02-link.md`）。いまは別々の原稿で、糸でつながっていない。
5. **warm**: 「急須で淹れるとき、時間は計っていますか？」への返信に返す。返信の多さを No.3 の題の候補へ。

いまでも 1〜5 は人と LLM の手で回っている。5.0 はそれを宣言にし、**どこで止まっているか（10/23 は 4 の告知が THTH の inflight で 1.5 時間止まった）を糸の上で見えるようにする**。

## 6. 先に決めたいこと（叩き台・未決）

1. 本体（サイト）との受け渡し: 本体は「記事が出た」を THTH に渡すだけにするか（`thth article` の検出を使う）、本体の記事も THTH の配信の台帳に載せるか。
2. 糸と段の宣言の置き場: 利用者の repo（原稿の隣）か、VM の台帳か。承認の記録を台帳に移した 4.4.1 の流れなら台帳、窓口が手で書く・読むなら repo。
3. 拍子（夢 1）との関係: 段の `over_days`・`mix` は、口座の 1 日の拍子（`schedule_thin` の物差し）と同じ物差しで数えるか。
4. 外の利用者: 外の人の LLM も同じシナリオを使えるか（THTH は道具の提供者）。
5. 型の材料の数え方: 材料の台帳（kopicha の claims.csv・関東の過去問の台帳）は窓口ごとに形が違う。THTH が台帳を読むか、窓口が「あと何回分」を THTH に渡すか。

## 7. 前提が変わったら

- 窓口が媒体ごとに別々のセッションで回す運用が続くなら、糸は「つなぐ札」だけにとどめ、段の宣言は各窓口の文書に置いたほうが軽い。代償は「いまどこか」を THTH が言えなくなること。
- hub が自前のサイト（本体）の記事の出来事を持つようになれば、4.2 の `article` の段は hub から出来事を受け取る形になる（THTH と hub の間の口は `events` の契約で）。
