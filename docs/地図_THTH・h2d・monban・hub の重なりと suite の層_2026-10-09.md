## 3. 層の分け方（たたき台）

| 層 | 持つもの | 正本 |
|---|---|---|
| 門 | 誰が・何を・どこまで（鍵・招待・承認・止める） | monban |
| 時 | いつ動くか（定時・待ち・起こす・期限の知らせ） | h2d |
| 声 | SNS との読み書きとその記録（出す・採る・会話・反応） | THTH |
| 場 | 人とエージェントの連絡（伝言・報告・返事待ち・申し送り） | hub |

例外（推薦）: **SNS の予約は THTH に残す。** 公開の時刻は承認（指紋に `publish_at` を含む）・ガード・inflight と一体で、h2d から叩くと「二重に送らない」を 2 か所で守ることになる。h2d は「THTH の予約が止まった・遅れた」を見張って起こす側に回る（今の sensors と同じ筋）。

## 4. 寄せる順（推薦・小さく安いものから）

1. **約束事（契約）を先に**: THTH の `observe --json` に schema の版と名前つきの節を持たせ、h2d と hub は名前で読む。並びに頼る読み方をやめる。THTH 側だけで済み、壊れる心配が一番大きいところを先に塞げる。
2. **端から端まで 1 往復（tracer）**: THTH の報告の口に報告が入ったら、hub の伝言で THTH 開発（と報告した人の窓口）に届く。今いちばん痛い穴（返事漏れ）を塞ぎ、THTH → hub のつなぎ目を 1 本作る。
3. **門の差し替え**: THTH の遠くの道（`thth login`・`/api/v1/*`・承認・鍵）を monban に寄せる。一番大きい。プライバシーポリシーと Meta への説明（鍵と承認の持ち主）を直す必要があり、monban の参加者 0 人・0.4 未配備のうちは急がない。
4. **記録と guard の共通化**: 3 のあと。形をそろえるのは、互換を崩してよい THTH 4.0 の機会に。

## 5. 気をつけること

- 一つが止まると全部が止まる形にしない。今の THTH は単独で予約を出せる。つなぎ目が切れたら「落とさない・二重に出さない」側に倒す。
- monban の申し送り（10/5）に、THTH の Worker（thth-callback）が 1 日約 5 万行を書いている件が masaru の判断待ちで残っている。門の差し替えの前に片付ける。
- THTH のデータは Jev に渡さない（10/5 の判断・Meta への約束）。h2d の判定の層（Jev）と THTH をつなぐときも同じ。

## 6. masaru に決めてもらうこと

1. suite を **1 つの製品**（名前・入口・説明を 1 つに）にするか、**ゆるい連合**（それぞれ単独で使え、約束事でつながる）にするか。推薦はゆるい連合から始める（各道具が単独で検収済み・外の利用者もそれぞれ違う）。
2. §4 の 1 と 2 を、3.15.0（再投稿）と並べて今から進めてよいか。
