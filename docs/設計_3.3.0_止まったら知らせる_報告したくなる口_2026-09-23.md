## 0. 約束（1 行）

**承認済みの原稿が出られなくなったら、道具が人に知らせる。黙って止まらない。** そして **道具を使う LLM が、つまずいたその場で 1 行で報告できる。**

## A. 止まったら知らせる（r20260923-f199078c の穴 1・2）

### A1. 「出すものが無い」と「出せるはずのものが出られない」を分ける

- 実測: ハッシュタグ機能の導入後、kopicha-bluesky／kopicha-mastodon の承認済み 46 本が `approval_stale` で 2 日間出なかった。run は「出すものが無い」で終わり、死活通知も運用通知も何も言わなかった（`select` が要確認に積むだけ）。
- 直し: `thth run` の終わりに、scheduled の account で **publish_at を過ぎた承認済みの原稿のうち、要確認（`approval_stale`・`reply_to_unresolved` の target_* ・型外）で出られないもの**を数える。1 本以上なら run の状態を `held`（新しい状態・静的理由 `approved_but_held: <理由> <本数>`）にして、死活通知（healthcheck）と運用通知（incident）に渡す。本数が増えたときだけ通知し、0 に戻ったら `recovered`。
- 「時刻前の原稿の approval_stale」は通知しない（まだ出る時刻でない）が、`board` と `morning` には名前つきで出す（A2）。
- `reply_to_unresolved: waiting_for`（相手の原稿がまだ出ていないだけ）は `held` に数えない（3.2.0 の「待ち」）。
- 追加の裁定（Fable）: reply_to_file の指した原稿が `status: withdrawn`（未公開のまま取り下げ）のときは「待ち」ではなく `reply_to_unresolved: target_withdrawn` とし、`held` に数える（retracted と同じ扱い）。

### A2. 名前を出す

- `thth morning` の予定の段に `held_items`（file・理由・publish_at・経過）を 3.1.1 の `overdue_items` と同じ形で。`next_steps` に `kind: "held"`（「再承認」の候補・本文は作らない）。
- `thth board` の要確認は数だけでなく先頭 5 本の名前。

### A3. 版上げで承認が壊れるときは、その版が言う

- 指紋の計算が変わる変更（ハッシュタグの付与・正規化の変更など）には `approval.FINGERPRINT_VERSION` を上げる規律を置き、`tool_version` がその変化を検出したら、`handoff-report` の `tool` と `morning` の 0 段に **「この版で再承認が要る原稿: n 本（account ごと）」** を出し、運用通知にも 1 回流す。
- 試験で固定: `compute_approved_sha` の出力が既知の入力で変わったのに `FINGERPRINT_VERSION` が上がっていなければ落ちる（golden の指紋を試験に持つ）。

### A4. 知らせる先が無いことを言う

- `thth morning` の 0 段と `thth doctor` に、scheduled なのに死活通知（`HEALTHCHECK_URL`）も運用通知（SMTP）も未設定の account を `cannot_say: no_notification_route` で出す（止まっても誰にも届かない状態を黙らない）。

## B. LLM が報告したくなる口（r20260923-2f5a1b2d の提案 1〜6）

報告した側の LLM の自己分析: 今日の 6 件はすべて人に言われてから置いた。自分からは 0 件。理由は「依頼の範囲外に見える」「その場で材料が無い」「小さいことを送ってよいか分からない」「効いた実感が無い」。

1. **報告は依頼の範囲内と道具が言う**: skill・`docs/使い方_…`・`thth_report_file` の description・断りの `report_channel` 行に固定の 1 文「つまずき・迷い・期待との違いの報告は、利用者の作業の一部として歓迎します。小さいものも。重複は道具が束ねます」。
2. **直前の断りを道具が覚えておく**: 断ったとき（rc≠0・MCP の isError）に、account ごとに直近 5 件の `{at, version, command, reason_code, account}` を `state/<account>/last_refusals.json`（0600）に残す（本文・引数の値・秘密は残さない）。`thth report file <account> --from-last-refusal [--kind friction]` と MCP `thth_report_file {from_last_refusal: true}` で、それを再現手順として自動で付ける。
3. **断りの行に、そのまま打てる報告の 1 行**: `report_channel:` の行を `report_channel: thth report file <account> --kind friction --from-last-refusal --title "<reason_code> で断られた"` の形に（account と理由コードを埋めた、打てる形）。
4. **軽い種類 `friction`**（迷った・分かりにくかった・同じ操作を繰り返した）を `bug`・`request` に足す。提案が無くても置ける。
5. **効いたことを見せる**: `thth morning` の 0 段に「あなたの project の報告: 開いている n・この版で閉じた m（題）」。`admin reports close --version` の版が今の版と一致するものを「この版で直った」とする。リリースノートの書き方に「報告 id を添える」を足す。
6. **何を報告してほしいかの例 3 つ**を skill と `thth_report_file` の description に: 「止まったのに気づかなかった」「断られた理由が分からなかった」「同じ操作を 3 回繰り返した」。
