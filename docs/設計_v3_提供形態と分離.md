# v3 インストール型とサーバ型の共通契約

2026-09-18、V3-05設計。サーバ型の一般提供は未実装。以下は採用を推奨する技術境界であり、ホスティング契約・料金・共有SNSアプリを決定したものではない。

## 同じものを使う部分

CLIとMCPが呼ぶ分析・運用概要・施策振り返りの計算は共通にする。report_type/schema_version、母数、期間、観測根拠、欠測、宣言と事実の区別は実行場所によって変えない。生成したレポートは利用者がJSON/Markdownで持ち出せる。

インストール型は利用者のOS権限と保存先に依存する。現在の環境変数 `THTH_ROOT` とローカルaccountファイルは、その実行環境の設定であり、ネットワークの認証/認可機構ではない。現在のstdio MCPをそのままHTTP公開してサーバ型完成とはしない。

## サーバ型の責任境界

| 項目 | 必要な契約 | 最低限の検証 |
|---|---|---|
| 認証 | 利用者を認証し、期限/失効を持つセッションを発行する | 未認証・期限切れ・失効済みは処理前に拒否 |
| 認可 | serverがtenant/account/projectの所有関係を決める。LLMの引数を所有の証拠にしない | 他tenantのaccount名・project名・投稿ID・ファイル参照を拒否 |
| 実行分離 | tenantごとに専用の実行環境とstate/repoを割り当てる | 並行要求で他tenantの台帳・環境変数・秘密・キャッシュが混入しない |
| 秘密 | SNSトークンをLLM・レポート・通常ログへ返さない。許可されたadapterだけが使う | stdout/JSON/例外/失敗時ログへの漏れがない |
| 公開承認 | 認証された人の画面に本文・宛先等を表示し、同じ内容の承認を検証 | LLMの自己申告や署名のない採用メモを公開承認に流用しない |
| 再実行 | 識別子と状態遷移で重複を防ぎ、公開結果不明は照合対象にする | timeout/retry時に同一投稿を二重公開しない |
| 通知 | 利用者/管理者の宛先と権限を分け、停止/復旧/通知配送状態を保持する | tenantごとの宛先、重複抑制、配送失敗、外部死活監視 |
| コスト | tenantごとのAPI予算・速度・利用量上限 | 上限到達の理由を返し、他tenantの枠を消費しない |
| 退出 | 接続解除・失効・エクスポート・削除依頼を区別する | 原本・派生集計・履歴・バックアップの対象と期限を確認 |

最初のサーバ型検証は利用者ごとの専用プロセス/コンテナと保存領域を推奨する。現行coreはプロセス全体の環境変数を読むため、単一プロセスで要求ごとに `os.environ` を切り替えて複数tenantを処理しない。プロセス分離だけでOS権限分離が完成したとは扱わず、ファイルアクセス権・実行identityも検証する。

## 段階

1. 共通のread-onlyレポート契約を完成させる（V3-01〜04）。現時点でインストール型から利用できる開発機能。
2. tenantに対応する実行contextと安全な入力/出力を定義し、ローカルの隔離fixtureで所有境界を検証する。
3. 認証基盤とホストを選び、少人数向けの非公開環境で認証/分離/退出/通知を一通り検証する。
4. 共有SNSアプリの許諾、費用、運用責任を確定した範囲で一般提供する。

現在は1と2、非公開loopbackのservice credential認証を実装し、ダミー2コンテナ分離試験まで実施した段階。人の本人認証や一般提供の基盤は含まない。OAuth提供主体・管理者identity・外部接続URL・料金・本番ホストは未確定。これらを未決のまま一般公開しない。

## 状態と利用者への説明

`generated_at` はレポート生成時刻、`data_updated_at` は明示した観測集合の最新時刻。前者で後者を代用しない。ローカル記録の参照時刻をサーバ生存の証拠にしない。healthcheckの受領とメールの実配達、人の閲覧は別の状態。

レポートは現在の記録のsnapshotであり、利用者のセッションを起動する機能ではない。休止したAIタスクへの通知連携は、対象クライアントの仕組みと利用者の明示設定を別に扱う。repoへの書き込みだけで休止タスクが気づくとは説明しない。
