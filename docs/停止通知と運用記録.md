# 全アカウント共通の停止通知と運用記録

v2.4.0 の機能です。利用者と管理者へのメール、原稿への運用記録を設定します。
THTH の account 新規登録時にこの手順を実施し、既存 account も同じ手順で移行します。
既存 account の通知設定不足で投稿を突然止めることはありません。

## 登録・移行

1. `thth account add` のとき `--notification-email-file /private/user-email.txt` で利用者メール1件を指定できます。管理者メールは全体設定です。通知先を含む新規台帳も Git repo 内には作成しません（repo 外の THTH_ROOT を使用）。旧 repo 内台帳へメールを追加せず、下記 private 設定を使用してください。
2. モード `0600` の JSON ファイルを repo の外に作ります。値をコマンド引数へ渡しません。

```json
{
  "user_email": "user@example.org",
  "admin_email": "admin@example.org",
  "smtp": {
    "host": "smtp.example.org",
    "port": "465",
    "tls": "ssl",
    "sender": "notifications@example.org",
    "username": "SMTP USER",
    "password": "SMTP PASSWORD"
  }
}
```

3. `thth notifications config ACCOUNT --input /private/notifications.json` を実行します。`--input -` なら stdin の JSON も受け付けます。保存先は `$THTH_ROOT/notifications.json`、モード `0600` です。**THTH_ROOT は Git repo の外に置いてください。** ローカル clone からの既定 root は repo 自身のため、通知設定の読み書きを拒否します。先に repo 外の運用 root を設定し、台帳・state・timer も同じ root を使ってください。Git worktree 内（親ディレクトリや symlink 経由を含む）には設定を作りません。利用者メールはアカウント別、管理者メールと SMTP は全体共有です。設定元ファイルも private な場所で管理してください。
4. `thth notifications status ACCOUNT` で利用者・管理者・SMTP の設定状態を確認します。値は表示しません。
5. `thth notifications test ACCOUNT` で両宛先に実際のテストメールを送ります。`accepted` は SMTP サーバ受領で、受信箱への到達を保証しません。**両宛先の受信箱で到達を確認**してください。設定変更後は再テストします。`tested_current_configuration` は現設定で両方が accepted だった記録です。
6. account 専用の `HEALTHCHECK_URL` を設定し、timer の実行間隔に合わせた period/grace と、利用者・管理者への外部監視通知を設定・テストします。VM/プロセス自体の停止は SMTP 送信コードも動かないため、外側からの missed-ping 監視が必要です。
7. 上記の通知確認を終えてから、新規 account の `production: true` / `scheduled: true` と timer を有効にします。既存 account は `board` の設定不足・未完了表示を見ながら同じ設定を追加します。

SMTP は TLS 必須です。ポート 465 の `ssl` または 587 等の `starttls` を選びます。STARTTLS 不可なら送信せず、平文への降格はしません。認証を使用する場合は username/password の両方が必要です。
SMTP 設定は private global JSON → process env → account env の順で上書きできます。env 名は `THTH_SMTP_HOST` / `PORT` / `TLS` / `FROM` / `USERNAME` / `PASSWORD`。管理者宛先は account env では変更できません。

## 原稿の記録

`thth run` が停止を検知すると、同じ `docs/sns/queue/*.md` の top-level front matter に次を追記します。

- `thth_run_state`: `blocked`（停止・要確認）または `recovered`
- `thth_run_at`: この状態に移った日時（毎回の timer 時刻ではありません）
- `thth_run_reason` / `thth_run_detail`: 安全な理由コードと固定の日本語説明
- `thth_run_action` / `thth_run_next`: 次の対応コードと日本語説明
- `thth_incident_id`: 通知と結び付ける識別子

投稿本文・公開予定・承認指紋・承認状態を変更しません。API の成否不明は要確認のまま扱い、inflight は消しません。復旧は「定期実行の停止が解消した」であり、「当該原稿が公開された」ではありません。投稿成功は既存の `status/post_id/posted_at` で確認します。v2 スレッドも、未解決 run が一意で承認指紋が一致するときだけ元原稿へ記録します。

dirty/staged/ahead/diverged、本文や公開項目の変更、別 account、queue 外、symlink、同期・既存公開記録の push 失敗など、原稿を安全に更新できない場合は触りません。原稿同一性が確認できない旧 inflight、複数の thread run、原稿を持たない操作は account 単位メールで知らせます。書戻し未完は private outbox に保持して後続 run で再試行し、メールにも repo 未反映と記載します。自己の既知 commit の push だけ失敗した場合は、その commit だけを再試行します。他者の作業を巻き込んで push しません。

メールは宛先別に送信し、利用者と管理者に互いのメールアドレスを見せません。同じアドレスなら1通です。停止状態が続く間は同じ通知・commit を増やしません。片方の失敗はその宛先だけ再試行し、もう片方の復旧通知は止めません。SMTP accepted 済み通知を宛先変更だけで過去にさかのぼって再送しません。未受領の role は現在の設定先へ再試行します。

SMTP accepted の直後・状態保存の直前に異常終了した場合は重複メールの可能性があります。同じ Message-ID を使用しますが、exactly-once は保証しません。壊れた outbox は勝手に初期化せず、通知を凍結して board で知らせます。Git commit と outbox 保存の間の異常終了も安全側で停止し、管理者が履歴と outbox を照合して復旧します。

## 各プロジェクトのセッション

開始・再開時には `git fetch` 後、リモートの queue の運用欄を読みます。作業中のファイルがある場合、無条件に pull しません。例えば `git show origin/main:docs/sns/queue/FILE.md` でリモート側を直接確認できます。repo 更新だけでは停止中のセッションを起こしません。利用者への気付きはメール、詳細と引継ぎは原稿の運用欄が担います。

## 投稿 API の詳細コード

Threads のコンテナ作成・公開 API が HTTP エラーを返した場合、HTTP 状態番号に加え、取得できた `code`・`error_subcode`・`is_transient` と既知の `type` を記録します。応答本文は最大 16 KiB まで解析し、任意のエラーメッセージ・本文・URL は詳細記録に含めません。単発投稿・連投の詳細は実行記録、当該実行の停止メール、原稿の `thth_run_detail` に残ります。`thth send` は実行記録に残します。連投では段ごとの実行記録にも詳細を残します。古い inflight の過去原因から詳細コードを推測して補いません。

この情報は原因確認用です。`is_transient` の値で再送や inflight 解除を決めることはありません。3.3.1 からは、公開が 5xx・時間切れ・接続断で終わったときに container の状態を問い合わせ、FINISHED のときだけ 1 回再試行し、PUBLISHED なら自分の最近の投稿から書き戻し、ERROR・EXPIRED なら出ていないとして inflight を解きます。問い合わせても決まらないときの停止は従来どおり維持し、理由は `inflight_unresolved`（次の手順は `thth inflight <account> resolve`）です。

運用通知の事象は、両方の宛先の SMTP が受領したあとも outbox に 30 日残します（送り終えた事象が 50 件を超えたら古い順に畳みます）。`thth board` と `thth observe` に「最後に送った運用通知: 時刻・状態・理由・受領した役割」を出します。SMTP の受領は受信箱への到達ではないので、届いたかどうかは受信箱（迷惑メールを含む）と照合してください。復旧通知には過去のエラー詳細を付けません。
