# 設計 3.2.0: `reply_to_file`——まだ出ていない自分の原稿への返信を先に仕込む

2026-09-23 13:20。masaru「1」（3.2 に進む）。正本の要望は kopicha の `docs/sns/要望_thth_reply_to_file_2026-09-21.md`（報告の口 r20260923-52b03960 にも同じ趣旨）。動機: 「今日は問いだけ・明日に答え」の企画で、答えの原稿は**出題の post_id が出るまで書けない**ため、毎回人の一手が残り、3 回連続で約束の時刻を過ぎた。

## 0. 約束（1 行）

**返信先を post_id ではなく「同じ queue の原稿の名前」で書け、その原稿が出るまで道具は待つ。黙って root に落とさない。** 承認の対象は「どの原稿への返信か」であり、解決後の post_id は承認に含めない。

## 1. 原稿の書き方

```yaml
thth: 1
account: kopicha-threads
publish_at: 2026-09-24T23:00:00+09:00
reply_to_file: 2026-09-23-q-decaf.md      # 同じ account・同じ queue の原稿の名前だけ
```

- `reply_to_file` は **ファイル名だけ**（`/`・`..`・`\` を含まない・`.md`・同じ `queue_dir` の中）。
- `reply_to` との**併用は lint で断る**（`reply_to_conflict`）。どちらか 1 つ。
- 指せるのは `thth: 1` の原稿だけ（束 `thth: 2` は `reply_to_file_bundle_unsupported`）。指した原稿がさらに `reply_to_file` を持っていてもよい（答えへの補足）。
- 自分自身を指す・指した原稿が無い・指した原稿の `account` が違う・`.md` でない・名前に区切りがある、は **lint で loud reject**（`reply_to_file_self`／`reply_to_file_missing`／`reply_to_file_account_mismatch`／`reply_to_file_invalid`）。

## 2. 解決と待ち（`select.select_one`）

候補が `reply_to_file` を持つとき、指した原稿の front matter を読む。

| 指した原稿の状態 | 候補の扱い | 理由（静的） |
|---|---|---|
| `status: posted` かつ `post_id` が usable かつ `retracted_at` 無し | **解決**: この run の `reply_to` = その `post_id` | — |
| まだ `post_id` が無い（未承認・承認済み待ち・時刻前・inflight） | **出さない。待つ**（要確認に静的理由で出す・次の run で再評価） | `reply_to_unresolved: waiting_for <file>` |
| `retracted_at` あり | 出さない。要確認 | `reply_to_unresolved: target_retracted` |
| 読めない・型外・`post_id` が usable でない | 出さない。要確認 | `reply_to_unresolved: target_unreadable` |
| ファイルが無い（承認後に消された） | 出さない。要確認 | `reply_to_unresolved: target_missing` |

- **root に落とす経路は作らない**（`reply_to_file` が解決できないのに `reply_to` 無しで送る分岐を持たない）。試験と単変異で固定。
- 待ちは **「時刻超過」に数えない**。`queue.overdue` の数え方（approved・post_id 無し・publish_at 超過）に「`reply_to_file` が未解決」を除外条件として足し、代わりに `queue.waiting_reply` に数える。`board` の要確認と `morning` の予定の段に **待っている原稿の名前と待ち先**を出す（3.1.1 の `overdue_items` と同じ形で `waiting_items`）。
- 指した原稿が予定より遅れれば、答えも自然に後ろへずれる（`publish_at` を過ぎてから解決した候補は、解決した run で出す。`quiet_hours`・`min_interval_hours` は従前どおり台帳が優先）。

## 3. 承認の指紋

- `compute_approved_sha` の 5 項目のうち `reply_to` の欄に、`reply_to_file` を持つ原稿は **`file:<名前>`** を入れる（解決後の post_id は入れない・要望どおり）。`reply_to` と `reply_to_file` は同じ欄を使うので、承認後にどちらかへ書き換えれば `approval_stale` で落ちる。
- 公開直前の `expected_fingerprint`（`core._throw_chosen`）も同じ値で照合する。adapter に渡す `reply_to` は解決した post_id。
- `sent` の記録と送信 digest（`compute_send_digest`）は**解決した post_id**で（記録は事実）。加えて `reply_to_file` と `resolved_from: {file, post_id}` を run の記録と `sent/` に残す（要望「どの原稿から解決したかを実行記録に」）。`found_by` は `manual` 相当。
- 公開後の書き戻しは `post_id`・`posted_at` に加えて **`reply_to_resolved: <post_id>`** を front matter に書く（`reply_to_file` は残す・承認の指紋は変えない項目）。

## 4. 入口と表示

- CLI: 新しい命令は無し。`thth lint`・`thth queue`・`thth board`・`thth morning` が待ちを見せる。`thth preview` は「返信先: <file>（未解決・待ち）」または「返信先: <file> → <post_id>」。
- MCP（サーバ型の下書き `thth_draft_put`）: この版では **`reply_to_file` を受けない**（下書きは draft_id で、ファイル名の概念が違う。`reply_to_draft` は要るときに別に起こす）。
- `handoff-report --since-last-read` の `queue` に `waiting_reply` の数。

## 5. 変えないもの

- 承認の二段・`--production`・digest・読む口の規律。
- `reply_to`（post_id 直書き）の道は従前どおり。`reply_to_root`・`reply_to_author_key` の扱いも従前どおり（解決後に同じ関数へ渡す）。
- 束（`thth: 2`）の仕様（設計_スレッド連投）は触らない。

## 6. 試験

lint 6 種（併用・自己参照・不在・account 違い・名前の形・束）・解決（posted → 出る・`reply_to` に post_id・記録に resolved_from）・待ち 4 種（未 post_id・retracted・読めない・消えた）で **1 文字も出ない**・待ちは overdue に数えず waiting に数える・board と morning に名前と待ち先・指紋（`reply_to_file` を変えると `approval_stale`・解決 post_id は指紋に入らない）・書き戻し `reply_to_resolved`・`preview` の表示。単変異 6 本（root に落とす分岐を足す／指紋から `reply_to_file` を外す／待ちを overdue に数える／account 違いを通す／retracted を解決する／自己参照を通す）。実機: kopicha の出題→翌日の答え 1 組（masaru の承認）。
