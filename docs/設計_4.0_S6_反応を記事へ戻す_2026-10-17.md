## 0. 一言で

**「戻す」は、記事の名（`article`）で引ける報告にする。正本の記事ファイルには書かない。** 口は `thth article reactions <口座|project> --article <名>`（読むだけ）で、配信の台帳（はてなブログ）→ 告知（SNS の `sent/` の `announces`）→ ブックマーク（`sent/bm:` の自分の分と、公開の情報の第三者の分）の線をたどり、出所ごとの数を `source`・`attribution`・`window` つきで**並べる**（足さない・順位を付けない）。はてな側で取るのは、公式の認証なしの読む口が 3 つ: **ブックマークの件数**（件数取得 API）・**ブックマークのコメント**（エントリー情報取得 API・キャッシュ）・**はてなスター**（スター取得 API・https で通るかは実機で確かめる）。**ブログのコメントとアクセス数は取らない**（公式の API が無い。画面を機械で読むことはしない。訪問は hub の側）。取る時機は SNS の採取と同じ: はてなの口座の `thth run` の末尾で、公開からの経過時間の刻み（1・6・24・72・168・720 時間）を跨いだ配信だけ 1 回読み、レーンの repo の `data/hatena/reactions/<delivery>.ndjson` に**追記だけ**で残す（取れなかった指標は書かない・0 と混ぜない）。自分の主体（同じ `owner` の全主体）の ID が付けたブックマークとスターは `self` に分け、第三者の数（`others`）にも、hub へ渡す `reactions[]` にも入れない。ブックマークの件数は API の値（`total`）と、自分の分を引いた値（`others`・引けないときは null と理由）の両方を出す。hub へは `thth article reactions --json`（`thth.article_reactions/1`）と、`thth events` の `bookmark_received`（第三者がブックマークした・コメントの本文は入れない）で渡す。承認の指紋・`sent/`・配信の台帳は 1 バイトも変えない。

## 2. 言葉

- **反応**（reaction）: 記事と、その記事から伸びる公開物（配信・告知・ブックマーク）に、**第三者**が返したもの。ブックマーク・スター・SNS の数（views・likes・replies …）・クリック。
- **登録の成立**（registration）: THTH が自分の主体で付けたブックマークが付いていること（`sent/bm:` の `result: confirmed`）。反応ではない（計画 §3.6）。
- **自分の分**（self）: 同じ `owner` の主体の `hatena_id` が付けたブックマーク・スター。`others` に入れない。
- **出所**（`source`）: 約束 §4 の 3 つを、媒体の API の名で細かくする。`sns`（SNS の媒体 API・`measured`）・`sns_clicks`（Threads の口座日次のクリック・`click_attribution`）・`hatena_bookmark`（件数取得 API とエントリー情報）・`hatena_star`（スター取得 API）・`site`（サイトの訪問・**THTH には無い**。hub が SC・CF から持つ。約束 §4 の `site` を名前だけ残し、値は出さない）。
- **帰属**（`attribution`）: `direct`（その公開物そのものの数）・`inferred`（条件つきの推定。条件を `attribution_basis` に）・`unknown`。
- **窓**（`window`）: いつの時点の・どの刻みの値か。欠測の理由（§5.3）。
- **束ねる**: 1 記事の行を並べること。足さない・順位を付けない。

## 3. はてな側の反応: 取れるもの・取らないもの（決めること 2）

### 3.1 表

| 何 | 取るか | 口 | 認証 | 頻度の上限 | 自分の分の除き方 |
|---|---|---|---|---|---|
| ブックマークの件数 | **取る** | 件数取得 API `count/entries`（50 URL まで 1 回） | 不要 | 数が無い。「数秒空けて」→ 1 run に 1 回・次の要求まで 2 秒 | 件数には自分の分が混ざる。`total` はそのまま、`others` はエントリー情報の `bookmarks[].user` に自分の ID があれば 1 引く（§5.2） |
| ブックマークのコメント（第三者） | **取る** | エントリー情報取得 API `entry/jsonlite/?url=`（1 URL 1 回） | 不要 | 同上 → 1 配信 1 回・2 秒 | `user` が同じ `owner` の `hatena_id` なら `self`（台帳には残すが `others` にも `reactions[]` にも入れない） |
| はてなスター | **取る（https で通れば）** | スター取得 API `entry.json?uri=`（複数 URL 1 回） | 不要 | 記述なし → 1 run に 1 回・2 秒 | `stars[].name` が自分の ID なら `self` |
| ブログのコメント | **取らない** | 公式の API が無い（§1.2） | — | — | — |
| アクセス数（はてなブログのアクセス解析） | **取らない** | 公式の API が無い。訪問は hub（SC・CF） | — | — | — |
| ブックマークの新着・人気への掲載 | **取らない** | 「何件で載るか」を観測する実験はしない（計画 §6・ガイドラインの作為的行動）。掲載の有無を機械で見ない | — | — | — |

### 3.2 スターの入口（https）

公式の頁の入口は `http://s.hatena.com/entry.json`（§1.2）。THTH は平文の http を使わない（`httpsafe`）。カウント API は `https://s.hatena.ne.jp/blog.json` で、同じホストに https の入口がある。**推測**: `https://s.hatena.ne.jp/entry.json?uri=` も通る。実機の 44（§13）で確かめ、通らなければ**スターは取らない**（`source: hatena_star` は `missing: not_supported`）。平文に倒さない。`s.hatena.com` への https も試す価値はあるが、リダイレクトは追わない（同一 origin だけ）ので、通った方を `hatenastar.BASE` に固定する。

`stars[].quote`（引用の文）は**台帳に残さない**（第三者の引用で、反応の数には要らない）。残すのは `name`・`count`・`color`。

### 3.3 ブログのコメントとアクセス数を取らない理由

- API が無い。画面の HTML を読む道を作ると、はてなの画面の変更で壊れ、規約（第 6 条 1 項 f「不正な操作」に当たるかの判断）を THTH が背負う。取らないものは取らないと言う（`not_supported`）。
- アクセス数は hub の領分（計画 §2: 媒体をまたいだ合計・ダッシュボードは hub）。THTH は `published_url` と公開時刻を出すので、hub は SC・CF の URL の行と結べる。

## 4. いつ取るか・どこに置くか（決めること 3）

### 4.1 比べた案

| 案 | 形 | 利点 | 欠点 |
|---|---|---|---|
| A（推し） | **はてなの口座の `thth run` の末尾**（SNS の `collect` の位置・`collect_applies` が飛ばしている所）で、公開からの経過時間の刻み（`AGE_MARKS_HOURS` と同じ）を跨いだ配信だけ読む。台帳に追記 | SNS の告知と**同じ経過時間**の値が並ぶ（collect の docstring の理由そのもの: 「いまの数字」を比べても意味がない）。timer が 10 分刻みで走っているので新しい仕組みが要らない。逃しても取り返せないわけではないが、同じ刻みで取れば比べられる | はてなの口座の run に HTTP が増える（読むだけ・認証なし） |
| B | 命令を打ったときだけ（`thth article reactions --fetch`）読んで、台帳には残さない | 作りが小さい | 経過時間が揃わない。24 時間の値が永久に無い。hub が朝に読む材料が人の手に依る |
| C | `thth maintain`（1 日 1 回）で全配信を読む | run に触らない | 1・6 時間の刻みが取れない。SNS と比べられない |

**A にする。** B の「打ったときに読む」は、A の台帳を読む口に `--fetch` を足せば同じことができるので、**手で読む口も付ける**（§4.4）。C は刻みが合わない。

### 4.2 刻みと対象

- 刻みは `collect.AGE_MARKS_HOURS`（1・6・24・72・168・720 時間）を**そのまま使う**（別の定数を作らない。`due_marks()` を使い回す）。起点は配信の台帳の `history[]` で最初に `state: published` になった行の `at`（結果不明から人が解いた配信も、その行の `at`）。
- 対象は口座の配信のうち `state` が `published`・`conflict`・`no_follow` のもの（`published_url` があるもの）。`deleted` は読まない（消えた記事の数を追わない）。`wanted`・`inflight`・`unknown` は URL が無いか決まっていない。
- 公開から `metric_window_days()`（38 日）を過ぎた配信は読まない（SNS と同じ窓）。
- 1 run の HTTP: 件数 `count/entries` 1 回（跨いだ配信の URL をまとめて・50 件まで）＋ スター `entry.json` 1 回（同じくまとめて）＋ エントリー情報 `jsonlite` を**跨いだ配信ごとに 1 回**（上限 10 配信/run・超えた分は次の run）。要求と要求の間は 2 秒（`hatena_bookmark.RECONCILE_INTERVAL_SECONDS` と同じ値・`sleep` は差し替え可）。`User-Agent` は `hatena_common.user_agent(contact)`。
- 失敗は配信ごと・出所ごとに独立。取れなかった出所は**その刻みの行に書かない**（次の run が同じ刻みを再び試す・SNS と同じ「各窓内で未達刻みを再試行」）。失敗の理由は run のログと runs の行（`errors`）に。
- 主体の止め（`principal_stopped`）・口座の止めは**読む側なので掛けない**（SNS の collect も止めで止まらない）。

### 4.3 置き場と形 `data/hatena/reactions/<delivery>.ndjson`

| 案 | 置き場 | 利点 | 欠点 |
|---|---|---|---|
| A（推し） | **レーンの repo の `data/hatena/reactions/<delivery>.ndjson`**（`accounts.data_dirs()` に鍵 `hatena_reactions` を足す。repo が無い口座は `state/<口座>/data/hatena/reactions/`） | SNS の実測（`data/sns/insights/`）と同じ流儀（利用者の repo に残る・commit と push も `_collect_entry` と同じ）。hub がレーンの repo から直に読むこともできる | はてなの口座の run が repo に書く（今は front matter の書き戻しだけ）。`_collect_entry` の同期・push の道をはてなの口座でも通す |
| B | `state/<口座>/deliveries/<delivery>.reactions.ndjson`（配信の台帳の隣） | 台帳と並ぶ | THTH の中にだけ残る（利用者の repo に無い）。SNS と置き場が割れる |
| C | 配信の台帳 `deliveries/<delivery>.json` の中に `reactions[]` | 1 本で済む | 台帳は状態の変わり目の記録。採取のたびに `replace_at` で書き換えると `history`・`seq` の意味が濁る（S1 §3.4） |

**A にする。** 名前は `reactions` だが `state/<口座>/reactions/`（THTH が付けたいいね・`guard.reactions_today`）とは**別の木**（repo の `data/hatena/`）なので衝突しない。

1 行（1 回の採取・1 配信）:

```json
{"schema": "thth.hatena_reaction/1", "delivery": "dl_3f9c2a7e1b4d", "account": "kopicha-hatenablog",
 "article": "kopicha/2026-10-arabica", "url": "https://kopicha.hatenablog.com/entry/2026/10/20/080000",
 "published_at": "2026-10-20T08:00:41+09:00", "collected_at": "2026-10-21T08:10:03+09:00",
 "age_hours": 24.16, "marks": [24],
 "bookmark": {"total": 3, "others": 2, "self": ["kopichaba"], "comments_n": 1, "cached": true,
              "bookmarks": [{"user": "someone", "timestamp": "2026/10/20 21:03", "comment": "…", "tags": ["コーヒー"]}]},
 "star": {"others": 2, "self": 0, "by_color": {"yellow": 2}},
 "missing": []}
```

| 欄 | 決め |
|---|---|
| `marks`・`age_hours` | SNS の実測と同じ意味（どの刻みとして採ったか・実際の経過時間）。刻みは最大 10 分遅れて拾われる（`measured.load` の docstring）。判断には `age_hours` を使う |
| `bookmark.total` | 件数取得 API の値（`direct`）。自分の分が混ざる |
| `bookmark.others` | `total` − エントリー情報の `bookmarks[].user` のうち同じ `owner` の `hatena_id` の数。エントリー情報が取れなければ **null**（`missing` に `bookmark_others: own_unknown`）。推して埋めない |
| `bookmark.self` | 自分の ID のうち付けていたもの（登録の成立の裏付け。`sent/bm:` と食い違えば `thth bookmark reconcile` の案内） |
| `bookmark.bookmarks[]` | 第三者の分だけ（`self` は除く）。`user`・`timestamp`（API の文字列のまま）・`comment`・`tags`。**本文を残すかは §11 の問い 1**（推し: 残す） |
| `bookmark.cached` | 固定 `true`（エントリー情報はキャッシュ） |
| `star.others`／`self`／`by_color` | スター取得 API の `stars[]`（＋`colored_stars[]`）の `count` の和を、`name` が自分の ID かで分ける。`quote` は残さない |
| `missing[]` | その行で取れなかったもの（`bookmark`・`star`・`bookmark_others`）と理由（`not_fetched:<符丁>`・`own_unknown`・`not_supported`）。**取れなかった指標の鍵は置かない**（SNS と同じ）。`missing` は空配列でも必ず置く |

- 追記だけ・冪等: 同じ `delivery` に同じ刻みを 2 度書かない（`due_marks()` が台帳の `marks` を見る）。
- 書く前に repo を同期し、書いたら commit と push（`_collect_entry` の流儀をはてなの口座でも通す。push できない状態なら読まない・書かない＝fail-closed）。
- 読む口（§5）は台帳を読むだけ。

### 4.4 手で読む口

`thth hatena collect <口座> [--delivery <dl>] [--by <名前>]`（新・CLI だけ・MCP と thth.me に出さない）: run と同じ採取を今 1 回。`--delivery` で 1 配信だけ。刻みを跨いでいなければ「跨いでいない（次は 24h・10/21 08:00 ごろ）」と出して読まない。`--force` は**作らない**（刻みの外の値は比べられないので台帳に入れない。今の値を見たいだけなら `thth article reactions --fetch`・§5.4）。

### 4.5 runs の記録

`runs_mod.append_run` に `action: "hatena_collect"`（`collect` と同じ形・`collected` は見に行った配信の数・`errors`）。board の `collecting` の数えは `repo_running` を見るので変えない。

## 5. 記事ごとの反応を束ねる口（決めること 1）

### 5.1 比べた案

| 案 | 口 | 利点 | 欠点 |
|---|---|---|---|
| A（推し） | **`thth article reactions <口座\|project> --article <名> [--delivery <dl>] [--json] [--fetch]`**（S5 の `thth article diff` と同じ `article_cli.py` に足す） | 「記事」の口に「修正」と「反応」が並ぶ（計画 §3.5・§3.6 の対）。対象の決め方（口座か project・`--article` で絞る）を S5 と共有 | S5 がまだ実装されていなければ `article_cli.py` を S6 が先に作る（`diff` は S5 が足す） |
| B | `thth article show <名>` に全部（配信・修正・反応） | 1 画面 | 1 枚が重い。修正（git を読む）と反応（台帳を読む）は読む材料が違い、欠測の理由も違う。hub が欲しいのは反応の JSON だけ |
| C | `thth deliveries --article` に `reactions` を足す | 新しい口が無い | `deliveries` は配信の台帳の口（読む範囲を広げない・S4 §3.3）。SNS の実測まで読むのは別の口 |

**A にする。** `thth deliveries` の 1 行には**台帳の最新の行の要約だけ**添える（§6.1）。

### 5.2 線のたどり方 `article_reactions.build(target, *, article, delivery=None, now, allowed_names=None) -> dict`

読むだけ（配信の台帳・`sent/`・`sent/bm:`・`data/hatena/reactions/`・SNS の実測と返信とクリックの台帳）。媒体の API は呼ばない（`--fetch` のときだけ §5.4）。

1. 対象の口座: `deliveries_cli.build()` と同じ（口座か project・`allowed_names`）。`--article` は**必須**（記事の名で束ねる口。無ければ `article_required`）。
2. **配信**: 対象の口座の配信の台帳から `article` が一致するもの（`deleted` も並べる・反応は読まない）。各配信に `published_url`・公開の時刻（§4.2 の起点）・`state`。
3. **はてな側の反応**: 配信ごとに `data/hatena/reactions/<dl>.ndjson` を読み、刻みごとの行を並べる（`rows[]`）。いちばん新しい行を `latest`。
4. **登録の成立**: `hatena_bookmark.by_delivery()` の行（`result`・`sent_at`・`retracted_at`）。`reactions[]` には入れない。
5. **告知**: `deliveries_cli.announcements(project, {配信 id})`（同じ project の SNS の `sent/`・`allowed_names` の中だけ）。告知ごとに:
   - `measured.load(告知の口座)` の `posts` から `post_id` が一致する投稿の `rows[]`（`marks`・`age_hours`・`metrics`）。所有の裏付けが無い行は `measured` が既に外している。
   - 返信の数: `replies.load(口座, post_id=…)` の行数（他人の本文は**出さない**・数だけ）。
   - クリック: `click_attribution.Index.attribute(post_id, posted, views)`（`basis` が None なら `cannot_say` の符丁をそのまま）。Threads の口座だけ。
6. **並べる**: 配信・告知ごとの `reactions[]`（§5.3 の形）。**足さない**（記事の `total` という鍵は作らない）。
7. **言えないこと** `cannot_say[]`: `deliveries_unreadable`・`sent_unreadable`・`measured_unreadable`・`scope_unavailable`（遠くの道で告知の口座が鍵の範囲の外）・`site_not_in_thth`（固定・毎回）。

### 5.3 `reactions[]` の 1 行（hub へ渡す形）

```json
{"source": "hatena_bookmark", "metric": "bookmark_others", "value": 2,
 "object": {"kind": "delivery", "id": "dl_3f9c2a7e1b4d", "account": "kopicha-hatenablog",
            "url": "https://kopicha.hatenablog.com/entry/2026/10/20/080000"},
 "attribution": "direct", "attribution_basis": null,
 "window": {"kind": "age_mark", "mark": 24, "age_hours": 24.16, "at": "2026-10-21T08:10:03+09:00",
            "origin_at": "2026-10-20T08:00:41+09:00", "cached": true, "missing": null}}
```

| 欄 | 値 |
|---|---|
| `source` | `hatena_bookmark`・`hatena_star`・`sns`・`sns_clicks`。`site` は出さない（`cannot_say: site_not_in_thth`） |
| `metric` | `hatena_bookmark`: `bookmark_total`・`bookmark_others`・`bookmark_comments_n`。`hatena_star`: `star_others`。`sns`: `measured.POST_METRIC_NAMES` の各名と `replies_received`（返信の台帳の行数）。`sns_clicks`: `clicks_72h` |
| `value` | 整数か null（null のときは `window.missing` に理由） |
| `object` | 数が付いている公開物。`kind` は `delivery`（はてなの配信）か `announcement`（SNS の投稿・`id` は `post_id`・`announces` に配信 id）。**記事そのものに付く数は無い**（記事に付くのは hub の訪問） |
| `attribution` | `direct`: その公開物そのものの数（ブックマーク・スター・SNS の指標）。`inferred`: `clicks_72h`（`attribution_basis: unique_url_72h`・`click_attribution.BASIS`）と `bookmark_others`（`attribution_basis: total_minus_self`・自分の分の判定がキャッシュに依る）。`unknown`: 使わない（言えないものは `value: null` と `missing`） |
| `window.kind` | `age_mark`（刻み）・`post_day_plus_2`（クリック・`click_attribution.WINDOW`） |
| `window.missing` | null（値あり）・`not_yet`（刻みにまだ達していない）・`not_fetched`（達したが取れていない・理由の符丁を `:` で添える）・`zero`（**使わない**——0 は `value: 0` で出す。約束 §4 の `zero` は「0 件だった」を `value: 0` と `missing: null` で表す。推測で `zero` を書かない）・`not_supported`（スターが https で通らない等）・`own_unknown`（`bookmark_others` でエントリー情報が無い）・クリックは `click_attribution.CANNOT_SAY` と `WINDOW_OPEN` 等の符丁をそのまま |

出す刻みは、各出所の**いちばん新しい刻み**と、**24 時間の刻み**（SNS の `after`・`analytics-report` が 24h を基準にしているのに揃える）の 2 行。全部の刻みは `rows[]`（§5.2 の 3・5）に残っているので、hub が要れば JSON から読む。

### 5.4 `--fetch`（今の値を 1 回読む・台帳には書かない）

はてなの出所だけ、件数・エントリー情報・スターを**今** 1 回読んで `now` の行として添える（`window.kind: now`・`at` は今の時刻・`age_hours` は実値）。台帳には書かない（刻みの外の値を混ぜない）。SNS の実測は読まない（SNS の API は口座の予算と刻みの決まりがあるので、今まで通り `thth collect`）。MCP・thth.me では `fetch` を受けない（読む口から媒体を呼ばない）。

## 7. 「戻す」の意味（決めること 5）

### 7.1 比べた案

| 案 | 形 | 利点 | 欠点 |
|---|---|---|---|
| A（推し） | **記事の名で引ける報告（§5）＋ レーンの repo の `data/hatena/reactions/` の台帳（§4.3）。正本の記事ファイルには書かない** | THTH は記事の第二の正本を持たない（計画 §2・約束 §0）。記事ファイルの blob の sha（`article_rev`・`checked_rev`）が変わらないので、**S5 の修正の検出（`behind`）が反応の書き込みで偽の「直した」を出さない**。承認の指紋（`body_sha256` は変換後の本文）にも影響しない。レーンの repo に残るので、人も LLM も hub も読める | 記事ファイルを開いただけでは反応が見えない（`thth article reactions` を打つ） |
| B | 記事ファイルの front matter に `reactions:` を書き戻す | 記事を開けば見える | 書き戻すたびに記事の blob の sha が変わり、S5 の `article diff` が「直した」と言う（本文は同じなのに）。timer が公開の直前に変換し直す本文は front matter を含まないとしても、`committed_rev` が動く。THTH がレーンの記事ファイルを書く道が増える（今あるのは queue の front matter だけ） |
| C | 記事の隣に `<記事>.reactions.json` を書く | 記事ファイルは触らない | 置き場が記事の数だけ散る。`data/hatena/reactions/` と二重 |

**A にする。** 「戻す」＝記事の id で引けること。計画 §3.6 の「記事ごとに束ねる」はこれで満たす。

### 7.2 反応から次へ（4.0 ではしない）

反応を見て「次の記事の種」を出す（案_4.0 の目玉 §0 の矢印）は、morning の `next_steps` の候補の列挙の線で後の版。S6 は材料を並べる所まで。

## 11. masaru に伺うこと

1. **第三者のブックマークのコメントの本文を、レーンの repo の台帳（`data/hatena/reactions/`）に残してよいか。** 推し: **残す**（`user`・`timestamp`・`comment`・`tags`）。理由は、(a) 公開の情報で、SNS の返信を `data/sns/replies/` に残している前例と同じ線、(b) 「どんなコメントが付いたか」は記事の次の種で、数だけでは読めない、(c) 見せる口は絞る（既定の `--json`・1 行の表示・`events`・`observe` には本文を出さず、`--comments` のときだけ）。代わりの形は「`user` と有無だけ残し、本文はそのとき `--fetch` で読む」——これだと消されたコメントは二度と読めず、hub が朝に読む材料にならない。前提が変わる点: レーンの repo を masaru 以外に見せるようになったら、本文を残す台帳を `state/` 側（THTH の中）に移す（置き場の鍵 1 つ）。

ほかは推しで決めた（戻すのは報告であって記事ファイルには書かない・はてな側で取るのは認証なしの 3 つで、ブログのコメントとアクセス数は取らない・採取は run の末尾で SNS と同じ刻み・台帳はレーンの repo の `data/hatena/reactions/`・自分の分は `self` に分けて `others` から引く・`total` の鍵は作らない・24h と最新の 2 行・出来事は `bookmark_received` だけ・スターは https で通らなければ取らない・`--fetch` は台帳に書かない・MCP と遠くの道に読む口を 1 つ）。

## 15. 実装で決めたこと（2026-10-17・書き手 Opus 5.5）

| # | どこ | 決めたこと | 理由 |
