# 設計: 自分の泉——その場で読み、残すのは自分の行為と反応（2026-09-16・開発セッション Fable・発注者 masaru）

**裁定 2026-09-16 朝（masaru）: §10 の 1〜7 は推薦どおり。** Facebook・Instagram は「他の利用価値が見いだせないと今のところかなり微妙」（masaru）。実装は T0 から（§7）。 証拠段階: **L1**＝この repo で実測・現物確認、**L2**＝一次資料、**L3**＝設計・推測。

## 0. 一枚で言うと

利用者横断の泉はやめた（裁定 2026-09-16・`docs/照合_MetaPlatformTerms_泉_2026-09-16_Codex.md`）。残るのは**自分の泉**——自分のアカウントが Threads で何をして、何が返ってきたかの記録。masaru の言葉: 「自分の泉は、とことん使えるモノにする必要がある。LLM が参考にするのに使いやすいモノに」「誰がどのような発言をスレッド内でしているのか、誰がどういうポジションを取っているのかを把握しながら、返信を考えたり、返信後のリアクションを測ったりする。どこのスレッドに現れてどう発言するべきかも考えられる必要がある」。

設計の芯は 1 行: **枝はその場で読む。残すのは自分の行為と反応。判断は LLM。**（裁定 2026-09-16「1 だと思います。LLM の賢さを効かせる部分」）

| 場面（masaru の順） | LLM が要るもの | THTH が出す口 | THTH が残す水 |
|---|---|---|---|
| 枝の中で誰が何を言い、どんな立場かを把握して返信を考える | その枝の会話を**生で**（要約しない） | `thread_read`（読むだけ・保存しない） | なし（読んで捨てる） |
| 返信後のリアクションを測る | 自分の返信ごとの閲覧・いいね・返信と、枝の中での位置 | `after_you_posted` | **絡みの台帳**（§4・自分の行為と反応だけ） |
| どこのスレッドに現れてどう言うかを考える | 候補の枝の一覧＋自分の履歴（この語・この仮名で何が起きたか） | `where_to_appear` | なし（材料は上の 2 つから導く） |
| 相手を知る | この仮名と何度・いつ・どんな反応だったか | `who_is_this` | 絡みの台帳から導く（発言内容は持たない） |
| 同じ問い・内容が**他の媒体**でどう扱われているかを材料にする（masaru 2026-09-16） | 同じ語を Threads・Bluesky・Mastodon で引いた枝と、媒体ごとの自分の反応を**並べて**見る | `where_to_appear`・`after_you_posted` を **project 単位**で（§2.6） | なし（数は媒体ごとに閉じる・v2 §2.1） |

前提の権限: 世間の投稿の検索・他人のプロフィール・言及は App Review の結果待ち（提出 2026-09-15）。他人の公開投稿の会話（`/conversation`）が `threads_read_replies` で読めるかは**一次資料で未確認・L3**——審査後にテスター外の投稿で実測してから `thread_read` を作る（§9）。

## 1. 裁定と前提（何を変え、何を変えないか）

| 設計 v2 の条文 | 扱い | 理由 |
|---|---|---|
| §1 `before_you_post` の答えの契約（n・期間・`cannot_say`・`one_thing_to_change`・引用できる形） | **維持・全部の口に適用** | 数を単独で返さない規律は自分の泉でも同じ（数の出所と時間条件を連れて歩く） |
| §1 規約 4「本文・返信の本文・返信者の名前は問いにも答えにも入らない」 | **口ごとに分ける**: `after_you_posted`・`where_to_appear`・`who_is_this` は維持。`thread_read` だけ**本文と名前を返す**（保存はしない） | 「誰が何を言っているか」を LLM が判断するには生の会話が要る。横断の泉が無いので、答えを他人に見せる経路も無い |
| §2 泉に落とす水・§3 `thth share`・§5 決裁・§6 v2-5 | **対象を失った**（裁定 2026-09-16） | `thth share` は既定 off・送る先なしのまま。消すかは別裁定（§10-4） |
| 「本文は保存しない」（検索結果・`threads_read_cli.py` 冒頭・App Review §2.3 の説明文） | **維持** | Meta に説明した用途。`thread_read` も同じ線——画面に出すだけで台帳に落とさない |
| 自分の投稿への返信の台帳（`data/sns/replies/<post_id>.ndjson`・`username` あり） | **維持**（既存のまま） | App Review の説明「言及は利用者自身の Git に記録する」と同じ範囲。自分の投稿への公開返信 |
| 人物像の蓄積 | **しない** | 他人の公開発言から立場を溜めると、審査で申告した用途から外れて見える（照合 §4）。仮名との接触の履歴（回数・時刻・反応）までにする |

## 2. 口の定義（MCP tool と CLI の両方に同じ名前で）

MCP の説明文はそのまま売り文句（v2 §1 規約 6）。実装が 1 語でも足したら設計書でなく実装を戻す。

### 2.1 `thread_read`——枝をその場で読む（保存しない）

- **説明文**: 「返信を書く前に呼ぶ。この投稿の枝を、誰が・いつ・何を・誰に向けて言ったかの順で返す。何も保存しない」
- **入力**: `account`・`post_id`（または permalink）・`since`（任意）・`max_messages`（既定 200・上限 1000）。
- **出力**（生・要約しない・順序は根から時刻順）:
  ```json
  {"root": {"post_id": "…", "author_key": "…", "is_own": false, "timestamp": "…", "text": "…"},
   "messages": [{"message_id": "…", "replied_to": "…", "depth": 1, "author_key": "…",
                 "username": "…", "is_own": false, "timestamp": "…", "text": "…",
                 "already_replied": {"post_id": "…", "at": "…"}}],
   "counts": {"messages": 57, "participants": 23, "own": 2, "truncated": false},
   "you_and_them": [{"author_key": "…", "met": 3, "last": "2026-09-10", "last_reaction": {"likes": 2, "replies": 1}}],
   "provenance": {"fetched_at": "…", "source": "threads:/conversation", "permission": "threads_read_replies"}}
  ```
- **規約**: (a) **台帳に 1 バイトも書かない**（runs にも本文を出さない。runs には `action: thread_read`・post_id・件数だけ）。(b) `already_replied` は自分の queue の `reply_to` と絡みの台帳（§4）から引く——「この枝にはもう返した」を LLM が見落とさない。(c) `you_and_them` は `who_is_this` の要約（発言内容は無い）。(d) `truncated: true` なら `since` で続きを取れる。(e) 権限が無ければ `PermissionMissing` を**そのまま**返す（「読めません」を「返信が無い」に化かさない・v2.1.1 の規律）。
- **立場の判断は LLM がその場でやる。** THTH は「誰が誰に何を言ったか」の構造だけ揃える。

### 2.2 `after_you_posted`——自分の行為と反応

- **説明文**: 「出したあとに呼ぶ。この語・この型・この枝で、自分の投稿と返信がどう受け取られたかを、件数と期間つきで返す」
- **入力**: `account`・絞り込み（`topic`・`kind`・`hour_band`・`reply_to`・`author_key`・`window_days` 既定 30・`min_n` 既定 5）。
- **出力**（v2 §1 の形を継承）:
  ```json
  {"summary": "行動型・平日朝: 自分の投稿 12 本、24h 中央値 views 310。絡みに行った返信 9 本のうち反応あり 4",
   "posts": {"n": 12, "views_24h": {"median": 310, "p25": 120, "p75": 800, "n": 12}, "branches_24h": {"median": 2, "n": 12}},
   "engagements": {"n": 9, "reacted": 4, "likes_24h": {"median": 1, "n": 9}, "replies_back_24h": {"median": 0, "n": 9},
                   "by_branch": [{"reply_to": "…", "root": "…", "posted_at": "…", "author_key": "…",
                                  "views_24h": 40, "likes_24h": 3, "replies_back_24h": 1, "covered": true}]},
   "comparable": {"window_days": 30, "aligned_on": "age_hours=24", "medium": "threads"},
   "cannot_say": ["返信の 72h（covered=false が 6 本）"],
   "one_thing_to_change": "夕方の返信は 24h で反応ゼロが 5/5。朝に回す",
   "provenance": {"source": "own-ledgers", "updated": "…"}}
  ```
- **規約**: 取れていない刻みは `null`・`covered: false`（0 と混ぜない・`threadshape` の `growth.covered` と同じ）。`min_n` 未満は `cannot_say`。`one_thing_to_change` は 1 個。

### 2.3 `where_to_appear`——次にどこへ

- **説明文**: 「絡みに行く先を選ぶ前に呼ぶ。検索の一覧に、自分の履歴（この語・この相手で何が起きたか）を重ねて返す。選ぶのは呼ぶ側」
- **入力**: `account`・`words`（1〜5 語）・`recent`（既定 false＝Meta の TOP 順）・`limit`。
- **出力**: B-1 の一覧（post_id・permalink・時刻・`author_key`・返信の有無・`[返信済]/[承認済]/[下書き]` の印）に、語ごとの `after_you_posted` の要約 1 行と、投稿者ごとの `you_and_them` を添える。**本文は 1 行プレビューのみ・保存しない**（今の `--search` と同じ）。
- **規約**: 順位付けをしない（「おすすめ」を作らない）。材料を並べ、選ぶのは LLM。「Threads API にトレンドの口は無い」（09-15 の事実）はここでも同じ——熱さは TOP 順・時刻・返信数から LLM が読む。

### 2.4 `who_is_this`——仮名の履歴

- **説明文**: 「返信する相手を確かめる。この仮名と自分のアカウントの接触の回数・時期・反応を返す。発言の内容は持たない」
- **入力**: `account`・`author_key`（または `username`→ その場で `author_key` に写す。username は保存しない）。
- **出力**: `{"author_key": "…", "met": 3, "first": "…", "last": "…", "threads": [{"root": "…", "role": "they_replied_to_me|i_replied_to_them", "at": "…", "reaction": {...}}], "profile": null}`。
- **規約**: `profile` は App Review 通過後に `thth profile` の公開 field を**その場で引く**だけ（保存しない）。

### 2.6 媒体をまたいで材料を並べる（masaru の提案 2026-09-16・**利用者横断ではなく自分の媒体横断**）

masaru の言葉: 「プラットフォームを横断していることも判断の材料に。同じような質問や内容が他のプラットフォームでどう扱われているのかも合わせて引いてきて、最適な回答や投稿を出す材料にする」。

- **単位は account でなく project**（台帳の `project`。`kopicha` に Threads と Bluesky の account があれば両方）。`where_to_appear`・`after_you_posted`・`who_is_this` は `account` の代わりに `project` を受け取れ、**媒体ごとの節を並べて**返す:
  ```json
  {"project": "kopicha", "by_medium": {"threads": {...}, "bluesky": {...}, "mastodon": {...}},
   "cannot_say": ["threads の検索（keyword_search 未承認）"]}
  ```
- **数は媒体をまたいで比較しない**（v2 §2.1 の規約を維持）。`comparable` は媒体で閉じる。Threads の 24h と Bluesky の 24h を足さず、割らず、順位も付けない。**並べるだけ**——「Bluesky では同じ問いに 3 本の枝が立ち、こういう答え方が多い」を LLM が読んで、Threads での言い方の材料にする。
- `thread_read` は媒体ごとの枝を読むので、そのまま。LLM が「同じ内容の枝」を媒体ごとに `thread_read` して読み比べる。
- **本文は保存しない**はどの媒体でも同じ。Bluesky（公開・AT Protocol）・Mastodon（インスタンスの公開 TL）は読む規約が緩いが、THTH の線は媒体で変えない（**同じ道具が媒体で行儀を変えると信用が割れる**）。
- 副産物: Bluesky・Mastodon には審査の壁が無いので、**Threads の審査を待つ間に `where_to_appear`・`thread_read` を本物のデータで通せる**。T1 をそちらで先にやる理由がもう 1 つ増える。

### 2.5 CLI

`thth thread <account> <post_id>`・`thth after <account|--project P> [--topic …]`・`thth where <account|--project P> <語…>`・`thth who <account|--project P> <author_key>`。すべて `--json` あり。`--project` は媒体ごとの節を並べる（§2.6）。MCP は CLI を呼ぶ（今の `mcp/server.py` の形・core は媒体を見ない）。

## 3. 読む口の権限と媒体

| 口 | Threads | Bluesky | Mastodon |
|---|---|---|---|
| `thread_read`（他人の根） | `GET /{id}/conversation`。**他人の投稿に効くかは未確認（L3）**。効かなければ、根が自分の投稿の枝だけ | `getPostThread`（公開・無認可でも可・L2） | `/statuses/:id/context`（公開・`visibility` は C-1 の規律で public/unlisted のみ） |
| `where_to_appear` | `keyword_search`（審査待ち） | `searchPosts` | `/api/v2/search`（インスタンスごと） |
| `who_is_this` | 自分の台帳から。`profile` は審査待ち | 自分の台帳から | 同 |

Bluesky・Mastodon は審査の壁が無いので、**`thread_read`・`where_to_appear` の tracer はそちらで先に通せる**（09-15 夕の引継ぎ §3-C 末尾と同じ判断）。

### 3.1 Facebook・Instagram（masaru の問い 2026-09-16・一次資料は同日読解）

| | Instagram（Graph API） | Facebook（Pages） |
|---|---|---|
| 出す・測る・自分への返信に返す | できる（ビジネス／クリエイターのアカウント・自分のメディアのコメントと insights・言及）。**L3**（一次資料の再読は設計時に） | **Page だけ**（個人プロフィールへの API 投稿は無い・L3）。Page の投稿・コメント・insights |
| 材料（他人の公開投稿を引く） | **ハッシュタグ検索のみ**: 7 日で 30 個まで・公開メディアだけ・**`username` は取れない**（**L2**・`ig-hashtag/top-media` の Limitations）。語の自由検索は無い | **Page Public Content Access**（他 Page の公開投稿・コメントを**読むだけ**・App Review＋**ビジネス認証**が要る・**L2**）。語の検索は無い（L3） |
| 現れて発言する（他人の投稿に返信） | 一次資料に他人のメディアへのコメント作成の記述が無い。**できない前提で設計する**（L3） | 他 Page の投稿へのコメントは feature の範囲外（読み取り専用・L2） |
| 規約 | Meta Platform Terms（Threads と同じ。横断の泉は無い・自分の用途は可） | 同 |
| 費用 | 無料 | 無料 |

**結論**: どちらも「門」の媒体（出す・測る・自分の枝に返す）であって、**材料の媒体ではない**。§0 の 3 場面のうち「どこに現れてどう言うか」が API では成り立たない。足す価値は、その project に Instagram／Facebook の読者がいるかで決まる（v2 §7-6 の裁定「Facebook ページは Meta アプリの流用で 3 番目」のまま）。Meta アプリは Threads と同じ族なので、App Review は権限ごとに 1 回で済む。

## 4. 残す水——絡みの台帳（新規・最小）

いまある台帳で足りるもの: 自分の投稿の実測（`data/sns/insights/posts/*.ndjson`）・自分の投稿への返信（`data/sns/replies/<post_id>.ndjson`）・原稿の `reply_to`（queue）・公開記録（`sent`）。**足りないのは「絡みに行った返信」を枝と相手に結ぶ 1 行**——出した返信は自分の投稿なので実測は既に採れているが、「どの根の・誰の投稿への返信か」が実測の側に無い。

`data/sns/engagements/<YYYY-MM>.ndjson`（1 行 1 返信・**書くのは公開が確定した瞬間に `core` が 1 回**）:

```json
{"post_id": "<自分の返信の id>", "reply_to": "<相手の投稿 id>", "root_post": "<根の id・判れば>",
 "author_key": "<相手の仮名>", "account": "kopicha-threads", "topic": "コーヒー", "form": "…（原稿の form。実装は `kind` でなく `form`・T7 の検収で訂正）",
 "hour_band": "朝", "posted_at": "…", "found_by": "where_to_appear|manual|mention", "schema": "thth.engagement.v1"}
```

- 反応は書かない——`collect` が自分の返信の実測を採る（既に採っている）。`after_you_posted` が `post_id` で結ぶ。
- **落とさないもの**: 相手の本文・username（`author_key` だけ）・自分の判断（`verdict`）。既存の `_assert_clean` の禁止鍵をそのまま流用してテストにする。
- `who_is_this` は、この台帳（自分→相手）と返信台帳（相手→自分・`username` から `author_key` を写す）の 2 つから導く。

## 5. 答えの契約（全部の口に共通）

1. 数は `n`・期間・`aligned_on` と一緒に。取れていない刻みは `null`、`covered` を付ける。
2. 言えないことは `cannot_say`。閾値は自分の泉なので低く（`min_n` 既定 5・v2 の 20 は横断の値）。
3. `one_thing_to_change` は 1 個（`after_you_posted` だけ）。
4. `thread_read` は**要約しない**。LLM が読むための生。長さの上限と `truncated` で守る。
5. 答えは引用できる形（「自分の泉（n=9・直近 30 日）ではこう」）。
6. **順位付け・おすすめ・立場のラベルを THTH が作らない。** 材料と構造だけ。判断は LLM。
7. **媒体をまたぐ答えは「並べる」だけ**（§2.6）。媒体をまたいだ集計・比率・順位を作らない。

## 6. skill の書き直し（`skills/thth/SKILL.md`）

「使う順番」を場面で書き直す: **探す**（`where_to_appear`・`--project` で全媒体を一度に）→ **読む**（`thread_read`・立場を把握）→ **書く**（`reply_to` 付きの下書き・`before_you_post` は語を選ぶときだけ）→ **承認**（二段・digest）→ **測る**（`after_you_posted`）→ **相手を知る**（`who_is_this`）。各段に「呼ばなくてよいとき」を書く（LLM は説明文で呼ぶかを決める）。

## 7. 段階（各段 1 検収対象・受け入れをテストに）

| 段 | 何 | 受け入れ |
|---|---|---|
| T0 tracer | 絡みの台帳（§4）＋ `after_you_posted` の `engagements` だけ。テスターの投稿への返信で round-trip | 返信を出す → `collect` → `thth after --reply-to` に反応が並ぶ。台帳に本文・username が無い（`_assert_clean` 流用） |
| T1 | `thread_read`——**Bluesky か Mastodon で先に**。Threads は権限の実測後 | 他人の根の枝が生で返る・runs に本文が無い・`already_replied` が効く・`PermissionMissing` が化けない |
| T2 | `where_to_appear`——B-1 の一覧に履歴を重ねる。**`--project` で Bluesky・Mastodon も同時に**（Threads は審査次第） | 順位付けが無い・本文は 1 行のみ・語ごとの要約に `n` がある・媒体をまたぐ数が無い |
| T3 | `who_is_this`＋ `thread_read` の `you_and_them` | 発言内容が無い・`username` を渡しても保存されない |
| T4 | skill の書き直し＋ LLM に選ばせる試験（v2-4 の型）: まっさらな Claude に「この枝に絡んで」と頼み、口を正しい順で呼ぶか | 呼ぶ順・呼ばない判断が記録に残る |

実装は Sonnet に段ごとに発注、検収は開発セッション（変異・全件）。T0 は半日、T1〜T3 は各 1 日程度（L3）。

## 8. 何を裏返さないか（境界の規律）

- `thth/adapters/` の境界は変えない。読む口は各 adapter の既存メソッド（`conversation`・`keyword_search`・`recent_posts`）の組み合わせで、core は媒体を見ない。
- 承認の経路（`approve`・digest・`select`）に触らない。`reply_to` は既にある。
