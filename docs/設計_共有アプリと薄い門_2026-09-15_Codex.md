## 0. 一枚で言うと

**まず Threads は情報提供と無料利用の交換で参加者を増やし、泉を育てる。初期 Threads の課金機能は作らない。X を導入する場合は API 原価を賄う課金を当初から設計する案とし、泉の商品化を待つ課金とは分ける。推薦は案 A「薄い門」から。ただし、共有アプリの認可と、泉へのデータ利用の許可は別である。両方の条件が揃うまで外部利用者向けに稼働させない。**

## 2. 案 A 薄い門

### 構成と流れ

```text
利用者：git原稿 → CLIの検査・二段承認 → via: thth.me アダプタ
                                             │ HTTPS・端末資格・操作ID
                      thth.me：認証 → 利用資格 → 準備 → 最終許可 → Meta
                                   │                    │
                        暗号化トークン・送信状態・利用量・監査記録
利用者：gitへ結果を書き戻す ← 操作IDで取得する確定結果／結果不明
利用者：shareの送信内容を確認 → 貢献受付 → 泉の許可されたデータだけ
```

1. 招待を認証済み利用者と端末に結ぶ。Worker が一回限りの OAuth `state` を作り、利用者・端末・期待する Threads ID・期限 10 分に束縛する。
2. Meta の HTTPS callback で state を消費し、Worker がコード→短期→長期トークン交換、本人 ID と実際の権限を確認する［M1〜M3］。ID 不一致・不足・不明を成功表示しない。
3. **Meta トークンは CLI・ブラウザに返さない。** CLI には当該利用者・当該 Threads ID・許可操作に限定した失効可能な端末資格を発行する。資格も秘密で、ログ・git・LLM 文脈には出さない。
4. CLI は既存の承認・同期・選択を通し、操作 ID をローカル inflight に永続化してから準備要求を送る。サーバが本文・返信先・場所・Instagram 共有等を固定し、コンテナを作る。
5. アダプタは準備結果を受け、必要な待機後に `before_publish` をローカルで呼ぶ。許可された場合だけ commit 要求を送る。Worker は期限・資格・停止・制限を**公開直前に**再確認して Meta に公開要求を 1 回送る。
6. Worker は結果を永続化して返す。CLI は従来の `sent`・指紋照合・書き戻し・rebase 後照合・push を行い、成立したら ACK する。サーバから利用者 git へは push しない。

**認可の戻り URL を表示する既存 `/callback/` は別経路として残し、共有用 callback を分ける。** サーバの state と CLI の端末紐付けを照合し、別端末への認可の横取りを防ぐ。これは Meta の PKCE 対応を仮定しない独自の紐付けである。

### サーバが持つもの／持たないもの（期間は推薦値）

| データ | A での扱い | 削除・制限 |
|---|---|---|
| Meta token・expiry・実権限・Threads ID | 接続単位で暗号化保管 | 接続削除時に利用停止、稼働 DB から 24 時間以内に消去 |
| app secret・暗号化鍵 | 専用 Worker の secret binding。DB・ソース・CI 出力に置かない | 鍵 version を記録、ローテーションと再暗号化を検収 |
| 端末資格 | 検証用ハッシュ・対象・expiry・失効世代 | 本文送信と管理権限を分離。管理画面は別認証＋MFA |
| 原稿本文・API の返信本文・検索結果・プロフィール | 処理中のメモリだけ。本文キャッシュ・本文ログなし | 要求終了でアプリ保持終了。Meta 側のコンテナ保存とは別 |
| 送信状態 | 操作 ID、接続 ID、送信契約全体の HMAC・鍵版・schema版、container ID、post ID、状態、時刻 | 準備は 10 分で失効。結果・重複防止記録は 30 日、未解決は解決まで保持・人に通知 |
| 制限・監査 | 利用者、操作種、理由 code、時刻、資格変更、同意版。重複照合用 keyed hash | 通常 30 日。本文・token・code・URL query・生の例外を保存しない |
| 利用者の repo・未承認原稿・Git 資格・私信 | 受け取らない | API の白名簿で拒否 |
| 泉の観測 | 別の明示した貢献 API・別 schema・別ストア | 門の通過データを自動転用しない。§4 の制限に従う |

「トークンだけを持つ」は概念図の略語に留める。**重複防止と停止を実効化するには状態と名簿も要る。本文を保存しないことと、本文が通らないことも別。**
認証付き暗号（例：AES-GCM、レコードごとに一意 nonce、利用者・接続・鍵版を AAD に束縛）を使う。鍵は DB と別の secret binding に置く［C3］。DB 単独流出の緩和であり、Worker の実行権限やデプロイ権限まで奪われると復号されうる。
20 人段では利用者単位の DO/トランザクションで並列制限・資格・送信状態を直列化する構成を候補とする。静的サイトと token を扱う実行環境の権限を分け、任意 URL・任意 Graph API 転送口は作らない。

### 失効・削除の口

- **停止**：端末・利用者・アプリ全体の停止世代を、全書込の commit 直前に照合。停止受付完了後に新たな公開 dispatch を許さない。既に Meta へ渡した要求は取り消せない。
- **Meta 側失効**：ユーザーによる連携解除と、アプリ側からの失効 API の有無を分ける。後者は未確認［M2］。サーバ DB の削除や app secret の変更だけで、盗まれた長期 token が無効になるとは約束しない。
- **削除**：認証済みの接続削除 API、私的な問い合わせ先、署名検証した Meta deauthorize/data-deletion 通知を同じ削除処理へつなぐ。現行の 200/確認番号だけの応答は流用できない（`callback/src/index.js:136`）。通知仕様の実読・署名 fixture が着手ゲート。
- 削除完了を示す受付 ID と状態照会を返す。資格失効→未 dispatch 操作取消→token/対応表/予約消去→バックアップ期限満了を別状態で表示する。バックアップは最大 30 日、復元時も削除台帳を先に適用し、旧 token・旧資格を復活させない。
- 法的に必要な最小監査の例外保持は項目・理由・期限を個別記録する。本文と token は例外保持しない。アカウント接続の解除と公開済み投稿の削除は別操作。

`whoami`・検索・プロフィール・場所・会話・insights・mentions・削除も門経由にする。token を手元に戻して読み取りだけ直結する抜け道は作らない。媒体の capability と実権限、審査前のデータ制限は別々に表示する。

### 導入と故障

導入は **6 手**（Python/git 導入済みの人、提案コマンドの具体名は未実装）：①インストール ②接続作成・招待照合 ③ブラウザで Meta 認可 ④最初の観測を確認し明示提供 ⑤資格・本人・権限の診断 ⑥原稿 dry-run。tester 期間は別に役割招待の受諾 1 手。最初の実投稿には既存の二段承認と送信が別途必要。予約用 VM は A では残る。

| 故障 | 動作 |
|---|---|
| 認証・利用資格・DB・鍵・制限の判定不能 | 新規公開を拒否。空結果・成功・資格ありに丸めない |
| 準備成功後に CLI が消える | commit がなければ公開しない。期限切れの準備を公開しない |
| commit の応答断／5xx／不正 JSON／不正 post ID | `publish_ambiguous` として inflight を残す。操作 ID で状態照会し、再公開しない |
| 門の 4xx | 門が永続記録に基づき「未 dispatch」を明示した場合だけ確定失敗。HTTP 番号だけで inflight を消さない |
| 公開成功・git push 失敗 | 公開済み状態を保持して書き戻しだけ復旧。別の操作 ID で再送しない |
| 門停止 | own-app へ自動切替しない。ローカル lint/preview は使える |

同一性は tenant・接続・media・via・本文・reply・topic・場所・IG共有・期限・schema版を含む canonical envelope 全体の HMAC で判定する。用途別の鍵導出と鍵版を保持し、commit では同じ envelope の再提出を照合する。本文以外の実行条件・container ID は準備状態に保持する。同じ操作 ID・同じ envelope の prepare 再送は既存状態を返し、異なる場合は 409。状態は `prepared → dispatching → published / failed_definite / unknown`、dispatch 前のみ `cancelled / rejected`。Meta の公開応答が確定拒否と確認できた場合は `failed_definite` とし、その証拠を返したときだけ local inflight を解放できる。門自身の HTTP 4xx と区別する。期限切れ操作 ID は未知の新規操作に戻さず拒否する。Meta と DB の原子的 commit はできないため、**exactly-once 成功は保証せず、不明なら止めて重複を避ける**。

## 3. 案 B 門＋時計

```text
git → 二段承認 → 予約登録（本文・承認指紋・期限・取消条件）→ 門の暗号化予約庫
                                                                │ 時計
git ← CLIで結果同期 ← 実行結果 ← 実行直前の資格・予約版・停止確認 ←┘ → Meta
```

A の token・本人照合・制限・失効・削除は共通。増えるものは**予約本文、承認者の申告、承認日時、全文指紋、実行可能時間窓、予約版、結果の受領待ち**。未承認原稿・git の全 clone・Git 資格は持たない。

| 項目 | 契約（L3） |
|---|---|
| 予約登録 | 人が見た内容と予約契約全体（接続、本文、reply、topic、場所、IG共有、時刻、期限、停止条件）を結合。最初は `pending_activation`（実行不可）。CLI が受領書を git に保存・push・照合後、同じ操作 ID で activate して `scheduled` にする。応答断は状態照会、未有効化は10分で失効。活性化確認後に登録完了と表示 |
| 正本の切替 | 登録後の実行可否は予約版が正本。**git の status を変えただけではサーバ予約を撤回できない**。この差を承認画面で明示 |
| 撤回 | CLI revoke を取消 API と連携。サーバの取消確定前は「撤回要求中」。取消と dispatch は同じ直列化点で競合解決し、既 dispatch は「取消不能・結果照会」 |
| 編集 | 予約版一致による取消が先。本文・時刻・対象を変える場合は再承認。旧版と新版が同時に有効にならない |
| 時計 | DO alarm 等は再実行されうる［C2］。起床時に状態を読んでから動き、alarm の再試行を Meta publish の再試行にしない |
| 不在実行 | 実行直前に期限・停止世代・貢献資格・中央上限を判定。ローカルの Python callback は代行できず、継続条件を共通 schema にする |
| 期限 | 初期は登録から 7 日以内、実行猶予 10 分。入力の+09:00を保存しつつ判定はサーバUTCに固定、時計異常時は止める。超過は `expired`、復旧後のまとめ出しなし。継続投稿は各段の期限と取消を検収するまで未対応と loud reject |
| 保管 | 本文は未実行予約中だけ（登録から最大7日＋実行猶予10分）。公開・取消・期限切れ・確定失敗後24時間以内に稼働DBから削除し、結果不明でも実行期限後24時間で本文を消す。指紋・post ID・受領書はAの結果保持規則に従い、未同期でも本文期限を延長しない |
| 結果同期 | post ID・実送信時刻・指紋・署名した受領書を CLI が取得。ローカル原稿に同じ内容があるか確かめ、違えば上書きせず要確認。サーバ受領＝git 保存済みとは言わない |

**VM が不要になるのは、預けた Threads 予約の送信と token 保守まで。** 1/6/24/72/168h の採集、返信保存、git 同期、他媒体 timer は別。B だけで「PC を閉じても観測がすべて揃う」とは言えない。採集の時計まで預かるなら保存範囲と同意の再設計が要る。
導入は A の 6 手＋①時計を選び予約規約を確認 ②予約登録と受領確認＝**8 手**。最初の予約試験を確認してから対象 timer を停止し、同じ原稿を二つの時計が投げない移行ゲートを設ける。

## 4. 共通：利用資格・スパム・審査・料金と泉

### 招待とスパム防止

| 層 | 強制できること | 限界 |
|---|---|---|
| Worker／共有の実行状態 | 許可名簿、接続所有権、資格停止、投稿数・重複・fan-out・入力上限、機能単位の拒否 | token 流出後の Meta 直叩きや、別アプリ・Threads 本体での投稿は制御できない |
| CLI | 既存承認・指紋・編集上の時刻条件・見やすい拒否理由 | 書き換え可能。中央上限を免除する根拠にしない |
| skill | LLM に量産・偽承認・自動返信をしないよう指示 | 助言。認証や強制力の代わりにしない |

招待は期限 7 日・一回限り、認可後の Threads ID と利用者 ID を結ぶ。tester と運営管理者を混同せず、一般試験者に admin/developer 権限を与えない。20 人は運営側の試験上限で、Meta の公式上限ではない［M3,M6］。一般 tester は従業員または開発者のために試験する合意がある人が対象［M6］。審査回避の恒常顧客枠にはしない。
初期上限案：1 人最大 3 接続、1 接続の新規投稿＋返信を合計 20 件/rolling 24h、利用者合計 40 件、60 秒間隔、同一本文 30 日拒否、同一利用者の複数接続への同文 24h 拒否、@言及 3・URL 2 まで。すべて L3 の試験値。Meta 側の制限が厳しければそちらも守る。
これは旧 v1 §3.6 の「頻度は編集判断」の**共有サービスに限る変更**。勝手に本文を直さず、中央制限の理由を返す。料金で緩和せず、誤検知は人が見直す。安全上の投稿取り下げ・予約取消・接続削除は貢献不足でも受け付ける。

### gotoq が負う審査

11 権限：`threads_basic`、`threads_content_publish`、`threads_manage_replies`、`threads_manage_insights`、`threads_read_replies`、`threads_keyword_search`、`threads_manage_mentions`、`threads_profile_discovery`、`threads_location_tagging`、`threads_delete`、`threads_share_to_instagram`。
「gotoq が 1 回負う」は**利用者ごとに自前審査を繰り返さない**という意味。11 権限は個別の承認状態を管理し、永久免除・一括合格を保証しない。現在の 5 権限の提出記録は、共有型 11 権限の承認ではない。
用途説明・録画・privacy・データ処理者・削除手順を実装と揃える。「自社利用のみ」の技術提供者認証は、他者にサービスを提供する実態へ訂正し、必要な認証と各権限の Review をそれぞれ完了する。現行の「サーバに保存しない」という録画前置きを再利用しない。中核機能・処理範囲の重大変更には事前の再提出・承認が求められる［M4 §3a(vii)］。
Data Use Checkup は Live 公開 use case／Advanced Access を持つ app に年次で必要。権限・許可用途・規約遵守・データ処理・テスト手順を admin が確認する［M5］。担当 masaru・代替担当 1 人を置き、Dashboard の期限と公式通知（60/30/10/3日前）で管理。期限超過は app 停止・延長なし（FAQ）。年 1 時間で必ず終わるとは見積もらない。

### 泉と水車：追加指示を実行条件にする

**提供しない者は利用できない。お金だけでは提供の代わりにならない。** `share:on` の自己申告だけでは利用資格を発行しない。

| 状態 | 泉の回答 | 共有の投稿・予約実行 | 常に残す操作 |
|---|---|---|---|
| 未同意／未提供／受理されない | 不可 | 不可 | ローカル作業、観測提出、接続・取消・削除・自分の結果取得 |
| 同意有効＋有効な貢献あり | 証拠と分母が揃った範囲 | 承認・権限・安全上限を満たす範囲 | 同上 |
| share off／提供撤回／資格失効 | 新規回答を停止 | 未 dispatch を停止、予約は保留ではなく再承認待ち | 同上。退出を妨げない |
| 泉・資格判定が故障 | 不可・判定不能と表示 | fail-closed | 取消・削除は別の受付を用意 |

資格の初期案：明示同意が有効で、**直近 30 日に受理された貢献が 1 件以上**。1 件は単なる送信成功でなく、出所・観測日時・媒体・取得状態が揃い、重複・禁止データ・明らかな捏造がないもの。真偽は schema だけで証明できないため、招待期は全件を人が検収する。閾値・量への換算は未裁定で、追加指示そのものとは分ける。
最初の一滴は、本人がブラウザ等で観測した記録を手元で整え、内容を確認して提出できる。**投稿しないと貢献できない／貢献しないと投稿できない循環を作らない。** 提供のために不要な投稿や作り話を要求しない。水がない月は共有機能を止め、own-app を選べる。
既存 share はローカル outbox のみ（`thth/share.py:1`）。ネット送信への更新で、昔の `share:on` を新しい第三者提供同意とみなさない。目的・受け手・保存期限・資格への影響を示して再同意を得る。off を無断で on にしない。
門の運用ストアと泉は別の白名簿・別権限。接続と貢献者の対応は資格判定側だけに持ち、泉の回答に識別子を出さない。ただし**運営側で対応を結べるため、完全匿名とは呼ばない**。既存 salted post hash の塩を門に送らない。自由文には他人の名前・本文が紛れ得るので人の確認も必要。
**Meta の許可は重大な未解決点**：Platform Data には匿名化・集計・派生と token も含まれ、Tech Provider には client ごとの分離と目的制限がある［M4］。App Review 通過や本人の同意だけで、利用者横断の泉への再利用が許されたとは言えない。
貢献と無料実行の交換も、許された目的・売買禁止と整合するか確認が要る。**不適合なら共有機能を止める。提供条件を消して有料開放する回避はしない。** 人の観測も、API 由来を言い換えただけなら規約外の水にはならない。
**当面の Threads は情報提供バーターで無料利用。初期 Threads の決済・料金表・有料枠は実装範囲に入れない。** gotoq が試験予算を負い、導入成功・継続提供・答えられる問いの増加を先に測る。旧「非提供者は月 30 回無料」「足さない人は払う」は削除する。
**X は別の費用構造**：公式 API は従量課金［X1］。導入する場合は、泉の蓄積を待たず API の仕入れ費を賄う料金を当初から用意する案を推薦する。料金はアクセス・処理の提供に対するもので、データ再販売の権利を意味しない。情報提供の条件も免除しない。X の規約・権限・原価と決済は別設計・別検収とし、本書の Threads A/B に実装を混ぜない。
泉の商品化に伴う課金再検討の入口案は、異なる提供者10人が4週間継続し、主要3種類の問いで各n>=20・時間条件が揃い、利用者5人中4人が実際の判断に役立った例を記録した時。これは商品性確認の試験値で、達しても自動課金しない。具体的商品・価格はその時に別裁定し、非提供者の有料免除は設けない。

## 6. 代償と限界

## 8. 止まる条件

1. Meta の他者token処理・共有データ用途・貢献条件の適法性を確認できない、または［M4］に抵触する。token中継が許可されても泉の横断利用は別に止める。今回は共有資格が泉に依存するため、外部向け水車も開始しない。
2. client側へ Meta token を配る必要が出る、汎用proxyを開く、禁止データを泉に保存する。sharedとown-appの自動fallbackも不可。
3. 停止・削除・backup復元時の再有効化防止を証明できない。漏洩tokenのMeta側失効経路を確認できないまま、被害の封じ込めを保証する。
4. 応答断を未公開と決めつける、alarm再試行が再投稿する、単発だけ検収してsend/連投/削除を通す。
5. Bでgit撤回だけを取消完了と表示する、未同期結果を保存済みと表示する、予約期限を勝手に延長する。
6. 貢献受付が形式だけになり虚偽の水を受理する、非提供者が課金で利用できる、share offでも予約が新たに実行される。
7. 運営当番が0人、未解決事故が1件以上、予算超過の見込み、11権限の一部却下。該当機能と新規受付を止め、既存利用者の取消・退出を確保する。1権限の却下だけで全案が永久に不成立とは決めない。
