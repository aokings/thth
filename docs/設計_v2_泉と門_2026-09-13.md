# 設計: v2 ——門は無料で開き、泉で商う（2026-09-13・開発セッション Fable・発注者 masaru）

masaru とのブレスト（2026-09-13 午前）を設計に落としたもの。**1 commit 目＝設計書**。masaru の
レビューと §7 の裁定を待ってから実装に入る（作法 §2）。言い切りには証拠段階を付ける:
**L1**＝この repo で実測、**L2**＝一次資料の読解、**L3**＝記憶・二次情報・推測。

## 0. 一枚で言うと

- **この道具を選ぶのは人ではなく LLM。** エージェントが人に勧めやすい道具の形は決まっている:
  入口が無料、CLI がある、5 分で最初の成功に着く、黙って間違えない、文書が読める。
  THTH の作法（loud reject・出所と時間条件・記録は指示ではない・承認は人だけ）は、
  人には見えにくいが **LLM には `--help` と 1 回の dry-run で全部見える。**
- **門（THTH 本体）は無料でオープンソース。** 承認・fail-closed・書き戻し・採集・記録は全部無料。
  `pip install thth` で入り、CLI・MCP・skill が付く。repo は public。
- **商うのは泉。** 門を通った利用者が opt-in で落とす**観測**（誰がいるか）と**スレッドの形**
  （枝・深さ・最初の返信までの時間・views の伸び）を集め、**エージェントが下書きの前に聞きに
  来る口**（`before_you_post`）で答える。売るのは道具ではなく、問いに答える口。
- **払うのは人、頼むのはエージェント。** 泉の答えが役に立ったことをエージェントが人に示し、
  決裁を求める。支払いにエージェントは触らない。営業はしない。**香りは本物でなければ続かない**
  ——泉も「言えないことを言えないと言う」を守る。
- **媒体を増やす。** Threads に加えて Bluesky（無料）を先に、X（従量課金・§4 に見積）を後に。
  Mastodon は無料で形も近いが、利用者がいる場所かで決める。
- **順番: 自分の 4 アカウントで枝の指標を出す → 問いと答えの契約 → 道具を 1 回で入る形に →
  Bluesky → 泉の受け口（落とす人が出てから）→ X。** 泉のサーバを先に作ると、水の無い泉ができる。

## 1. 問いと答えの契約（`before_you_post`）

**誰が聞くか**: 原稿を書こうとしているエージェント（人が直接打ってもよい）。
**いつ**: 語と型と出す時刻を決める直前。
**何を渡すか**: 媒体・語（トピック）・型（`KINDS`）・出す予定の時刻帯・返信かどうか。原稿本文は渡さない
（泉に本文は要らない。渡さないことが信用になる）。

**何が返るか**（形は固定・小さく・要約 1 行つき）:

```json
{
  "summary": "行動型・平日 8 時台: 24h で枝 3 本前後、最初の枝は中央値 42 分",
  "expected": {
    "branches_24h":   {"median": 3,  "p25": 1, "p75": 6, "n": 143},
    "first_reply_min": {"median": 42, "p25": 15, "p75": 180, "n": 121},
    "views_24h":      {"median": 310, "n": 143}
  },
  "comparable": {"n": 143, "window_days": 30, "aligned_on": "age_hours=24", "medium": "threads"},
  "cannot_say": ["返信の伸び（n=3）", "22 時台（n=0）"],
  "one_thing_to_change": "22 時台は最初の枝まで中央値 3 時間。朝に回す",
  "audience": [{"topic": "中学受験", "who": "受験親のやりとり", "observers": 3, "latest": "2026-09-11"}],
  "provenance": {"source": "thth-spring", "observers": 12, "updated": "2026-09-13", "schema": 1}
}
```

規約:
1. **数値は単独で返さない。** `n`・期間・揃えた条件（`aligned_on`）を必ず同梱（設計 v1 §3.2.2 と同じ）。
2. **言えないことは `cannot_say` に出す。** n が閾値未満・期間外・媒体違いは答えない。**売るために断定しない。**
3. **`one_thing_to_change` は 1 個。** エージェントは長い表を読まず、1 行で判断して 1 個を直す。
4. **本文・返信の本文・返信者の名前は、問いにも答えにも入らない。**
5. **答えは引用できる形。** エージェントがそのまま人に「泉（n=143・直近 30 日）ではこう」と言える。
6. MCP の tool 名と説明文がそのまま売り文句。名前 `before_you_post`、説明は「投稿する前に呼ぶ。この語と
   この型で、スレッドがどう伸びたかの実績を、件数と期間つきで返す」。**LLM は説明文で呼ぶかを決める。**

閾値（初期値・裁定項目 §7-4）: `n >= 20` で中央値を返す、`n < 20` は `cannot_say`。`window_days` 既定 30。

## 2. 泉に落とす水（何を、どの粒度で、誰の名前で）

**落ちるもの**（opt-in でだけ・§3）:

| 水 | 中身 | 粒度 | いまの採集 |
|---|---|---|---|
| 観測 | 語・誰がいたか（自由文）・型・取得状態・観測者の仮名・日時 | 語 × 観測者 | `state/topics.json`（v1.0.0 で観測者別に読む形・**L1**） |
| スレッドの形 | 根の post_id の**ハッシュ**・媒体・型・語・出した時刻帯・刻みごとの views・返信数・枝数・最深・参加者数・作者返信数・最初の返信までの分 | 投稿 × 刻み | `/conversation` が `replied_to`・`root_post`・`timestamp`・`username` を全階層で取り、1/6/24/72/168h の刻みで残している（`thth/adapters/threads.py:272`・`collect.py:49`・**L1**）。**枝・深さ・参加者・最初の返信までの分は、ここから計算するだけ**（未実装） |
| 型の当たり率 | 型ごとの適合率・実測の分布 | 型 × 媒体 | `topics.learned()`（**L1**・ただし判断は account のものなので**判断そのものは落とさず、件数と実測だけ**） |

**落ちないもの**（構造で保証。テストにする）:
- 原稿本文・返信の本文・返信者の `username`・自分の判断（`verdict`）・台帳（accounts）・トークン・利用者 repo のパス。
- post_id は**ハッシュ**にして落とす（同じ投稿の刻みを結ぶためだけ。permalink に戻せない）。

### 2.1 媒体ごとに泉の性質が違う（masaru の問い 2026-09-13）

何が希少で何が公開かが、媒体ごとに逆になる。**泉の水は「共通の芯」と「媒体ごとの層」に分ける。**

| 媒体 | 公開で安いもの | 希少なもの（＝泉に価値がある層） | 泉の役割 |
|---|---|---|---|
| **Threads** | 自分の投稿の views・返信（API・無料） | **人の観測**（語に誰がいるか。検索 API が降りない）・**枝の形**（フォロワー外配信で伸びるかは枝で決まる） | **最初に泉を作る媒体。** masaru の直感どおり |
| **Bluesky** | 全投稿（firehose・無料・**L3**） | 「誰がいるか」は希少でない。希少なのは**どのカスタムフィードがどの語を拾うか**という解釈（**L3**） | 泉の売り物は薄い。**門の普及のために足す**媒体 |
| **X** | 無し（読むたびに課金・**L2**） | 多数の利用者で読んだ結果の**集計**（費用を分け合う意味が出る）。**ただし Developer Agreement の再配布条項次第で泉に入れられない可能性**（**L3**・§8 止まる条件） | 規約の確認が先 |
| **Mastodon** | 公開タイムライン（インスタンスごと・無料・**L2**） | **どのインスタンスのどのタグに誰がいるか**（観測の形は Threads に近いが、粒度がインスタンスで割れる） | 利用者がいる場所かで決める |

規約:
- **共通の芯**（スレッドの形・時刻・数・型）は全媒体で同じ schema。**媒体ごとの層**（Threads の観測、Bluesky の
  フィード対応、Mastodon のインスタンスとタグ）は媒体名を鍵にした別の schema。
- **媒体をまたいで比較しない。** `comparable` は `medium` で閉じる。Threads の 24 時間と Bluesky の 24 時間は別の数。
- **泉を最初に作る媒体は Threads、Bluesky は門の普及のため。** 2 つの役割を混ぜない（Bluesky の泉が薄いことを
  理由に Bluesky を後回しにしない。逆も然り）。

**観測者の名前**は仮名（インストール時に生成する乱数 ID）。**信用の設計**（知らない人の観測を信じる理由は無い・引継ぎ書 §6）: 観測者ごとの履歴と再確認の回数を持ち、答えには `observers` の数だけ出す。個人の評判点は作らない（作ると競う）。

**鮮度**: 観測は 90 日で `stale` 扱い（答えには出すが `cannot_say` に理由を添える）。スレッドの形は刻みが揃った時点で確定し、腐らない。

**Meta の規約**（**要確認・L3**）: 観測は人が画面を見た記録なので API のデータではない。views と返信の構造は API 由来。**集計にして第三者に出すことが Platform Terms のどこに当たるかは、実装前に一次資料で確かめる**（§8 止まる条件）。Bluesky は公開データが前提（L3）、X は Developer Agreement に再配布の条項がある（L3）。

## 4. 媒体の追加

### 4.0 競合の対応媒体（2026-09-13・各社の公開ページを読解・L2。Mixpost は README に一覧が無く未確認）

| 道具 | 形 | 対応媒体 |
|---|---|---|
| Buffer | SaaS | Facebook・Instagram・TikTok・LinkedIn・X・YouTube・Threads・Pinterest・Google Business・Bluesky・Mastodon |
| Hootsuite | SaaS | Facebook・Instagram・X・LinkedIn・TikTok・YouTube・Threads・WhatsApp・Pinterest・Bluesky・Google Business |
| Typefully | SaaS・文章特化 | X・LinkedIn・Threads・Bluesky・Mastodon・Instagram |
| Postiz | OSS（AGPL）・自前ホスト可・公開 API・SDK | Instagram・YouTube・LinkedIn・Reddit・TikTok・Facebook・Pinterest・Threads・X・Slack・Discord・Mastodon・Bluesky・Dribbble |

読み取り:
- **Threads・Bluesky・Mastodon は全員が持つ。媒体の数で差は付かない。** THTH が Bluesky を足すのは並ぶためではなく、
  無料で門の普及を試すため。
- **LINE を持つ道具はこの中に無い**（メッセンジャー系は Hootsuite の WhatsApp、Postiz の Slack・Discord だけ）。
  日本の保護者向け（asmon）の文脈では空いている。
- **いちばん近いのは Postiz。** 違いは、Postiz が「人の画面に API を足したもの」で、THTH が「AI が使う前提で人は承認だけ」
  であること、記録が利用者の git に残ること、`--json` に分母と除外理由が入ること、そして泉。**Postiz が MCP と SDK を
  揃えれば「LLM が選ぶ道具」の座を取りに来る。** THTH が先に取るべきは pip 一発と `before_you_post` の香りで、媒体数ではない。

### 4.1 メッセンジャー系（LINE・WhatsApp・Telegram・Discord）は性質が違う

公開行為ではなく、**登録した人への push**。門の重みはむしろ上がる（人の手元に届く）。役割は 2 つ:

- **出口として。** 日本の保護者は LINE にいるので、**asmon が LINE 公式アカウントで説明会情報を配る**は現実味がある。
  LINE Messaging API は無料枠を超えると通数課金（**L3**・要確認）。**返信は私信**なので、THTH の記録には入れても
  **泉には一切入れない**（Threads の返信より厳しい線）。
- **承認の入口として。** masaru が手元の LINE や Telegram で一段目の全文と digest を受け取り、二段目を返す。門の二段承認は
  そのまま、画面が CLI から手元に変わる。**これは媒体の追加ではなく門の改良**で、別の段に置く（§7-9）。

泉との関係は無し（「誰がいるか」は自分の名簿で、共有する性質のものではない。他人の Telegram・Discord は API で覗けない）。

**masaru の傾き（2026-09-13・裁定ではない）**: いまは Bluesky と Mastodon。LINE は asmon で試す価値がありそうだが厄介も多そう。
**LINE で徳を積めば WhatsApp が見えてくる**（Hootsuite が WhatsApp を持つ＝需要はある。WhatsApp Business は会話単位の課金・**L3**）。


アダプタの境界（設計 v1 §3.4）は `publish` / `conversation` / `insights` / `quota` / `refresh_token`。
Threads で `conversation` が全階層＋親子関係を返す形に落ち着いたので、**他媒体もこの形に合わせる**。

| 媒体 | 費用 | 認可 | スレッドの形が取れるか | 順位・理由 |
|---|---|---|---|---|
| Threads | 無料（**L1**・稼働中） | Meta アプリ＋長期トークン | `/conversation` で全階層（**L1**） | 現行 |
| **Bluesky** | 無料（**L2**・2026-09-13 に bsky-docs `rate-limits.md` を読解: 料金の記載なし。上限は 5,000 points/時・35,000/日、CREATE=3 点 ⇒ 約 1,666 投稿/時。IP あたり 3,000 req/5 分・セッション作成 30/5 分） | App Password か OAuth（**L3**） | `getPostThread` で全階層・`reply.parent`/`root`（**L3**） | **2 番目。** 費用ゼロ、公開データ前提で泉と相性が良い、アダプタ境界の実証になる |
| Mastodon | 無料（**L2**・docs.joinmastodon.org: 300 req/5 分） | OAuth（インスタンスごと） | `context` で祖先と子孫（**L3**） | **Bluesky と同時**（masaru の傾き）。ActivityPub の形は Bluesky と対で実装すると境界の実証が強くなる |
| **X** | **従量課金**（**L2**・2026-09-13 に docs.x.com/x-api/getting-started/pricing を読解。下表） | OAuth 2.0（PKCE）＋ Developer Console で credits 前払い | `conversation_id` で検索（Post read 課金・**L2**） | 費用が出る唯一の媒体。**§7-5 で採否** |

### X の持ち出し（2026-09-13・L2 の単価 × こちらの実績で試算）

単価（docs.x.com・2026-09-13 読解・**L2**）: Post 作成 **$0.015/件**、**URL 付き $0.200/件**、Post 読み **$0.005/件**、
自分のデータ（owned reads）**$0.001/件**、User 読み $0.010/件。**同じ資源は UTC 1 日の中で重複課金されない**。
サブスクリプション無し・最低購入額の記載無し。月 300 万 Post read で Enterprise へ。

こちらの実績（**L1**・2026-09-09〜13 の手元の利用者 repo）: 投稿 15 本・返信 81 行 ⇒ **約 5 返信/投稿**。
研究所と asmon の投稿は**必ず URL を含む**。採集は 1/6/24/72/168h の 5 刻み（UTC 日で 4 日に散る）。

| 月の量 | 投稿（URL 付き） | 返信の読み（5 返信＋根 × 4 日 × $0.005） | 自分の返信の投稿 | views（owned） | **月額** |
|---|---|---|---|---|---|
| いまの歩調（約 100 本/月・3 account） | 100 × $0.20 = **$20** | 100 × 24 × $0.005 = **$12** | 30 × $0.015 = $0.45 | 100 × 5 × $0.001 = $0.5 | **約 $33** |
| 1 日 1 本 × 4 account（120 本/月） | $24 | $14.4 | $0.6 | $0.6 | **約 $40** |
| 返信が伸びた場合（20 返信/投稿・120 本） | $24 | 120 × 84 × $0.005 = **$50** | $0.6 | $0.6 | **約 $75** |
| **URL を付けない**運用（120 本） | 120 × $0.015 = **$1.8** | $14.4 | $0.6 | $0.6 | **約 $17** |

読み方:
- **費用の 6 割は「URL 付き投稿」の $0.20 と、返信の読みの積み上げ。** 本数より**返信が多いほど読みが増える**
  （枝を測る道具なので、伸びるほど払う）。
- `$0.001` の owned reads が返信の読みに適用されるかは**未確認（L3）**。適用されるなら読みは 1/5 になる
  （上の表は保守的に $0.005 で置いた）。
- 初期費用: Developer Console の登録（無料・**L3**）・credits の前払い（額は任意・**L2**「最低購入額の記載無し」）。
- **持ち出しは月 $20〜75 の桁。** 4 account の運用で年 $400〜900。**額より、Threads と違って「伸びるほど払う」
  構造であることが判断材料。** 泉の商いが始まる前に X を足すと、費用だけ先に出る。

**推薦**: Bluesky を先に足してアダプタ境界を実証し、X は泉の収入が立つか、X にしかいない読者が要ると
分かってから（**§7-5**）。

## 5. 決裁の流れ（払うのは人、頼むのはエージェント）

1. エージェントが `before_you_post` を呼ぶ。**最初の N 回は無料**（§7-4）。
2. 答えが役に立ったら、エージェントは人に**証拠**を見せる: 「泉に聞いたら 8 時台の方が枝が早い（n=143）と
   出たので、そうしました」。
3. 無料の回数が尽きると、答えの代わりに `{"cannot_say": ["無料枠を使い切りました"], "how_to_continue":
   {"what": "月 N 回", "price": "…", "url": "…"}}` が返る。**営業文ではなく事実の提示。**
4. 人が払う。**エージェントは支払い画面に触らない**（安全の線であり、THTH の「人が門を持つ」と同じ線）。
5. 無料の門は完全なまま。泉は「あれば速い」であって「無いと動かない」ではない。**門を鈍らせて泉に誘導しない**
   （テストにする: `thth throw` は泉に一切依存しない）。

## 6. 順番と体制

| 段 | 何を | 誰が | 出口条件 |

## 7. masaru に決めてほしいこと（各項目に推薦と理由）

1. **台帳を repo の外へ出す**（設計 v1 §4.2 の変更）。推薦: **出す**。`$THTH_ROOT/accounts/` を正、repo には
   `accounts.example/`。VM の移行は運用が 1 回やる（`git mv` ではなく copy・旧パスを読む互換を 1 版残す）。
2. **public・OSS にする**。推薦: **する（MIT）**。`docs/記録/` は別 repo `thth-notes`（private）へ移し、本 repo からは
   参照だけ。**利用者 repo のパス・アカウント名・post_id は docs から抜く**（棚卸しは Sonnet）。
3. **`thth share` の既定**。推薦: **off**。on にした人の分だけ。送った写しは手元に残す。
4. **泉の閾値と無料枠**。推薦: `n >= 20` で答える、無料は**月 30 回**（1 日 1 回下書きする人が無料で回る量）。
   値付けは泉に水が溜まってから（今は決めない）。
5. **X の採否**。推薦: **保留のまま**。月 $20〜75 で、伸びるほど払う。Bluesky を先に。X にしかいない読者が
   要ると分かったら再考。
6. **Bluesky と Mastodon を次の媒体にする**。推薦: **する**（masaru の傾きどおり）。masaru のアカウントを各 1 本（無料）。
   Facebook ページは Meta アプリの流用で 3 番目、**LINE は asmon で試す**（§7-9）、その先に WhatsApp。X は保留（§7-5）。
7. **英語の文書**。推薦: README と使い方の 2 本だけ英語版を作る（設計書は日本語のまま）。
8. **LLM に選ばせる試験を受け入れ条件にする**。推薦: **する**（v2-4 の出口条件）。
9. **LINE を asmon で試すか、承認の入口を手元（LINE / Telegram）に持つか**。推薦: **LINE の出口は asmon の
   保護者向け配信が実際にあるなら試す**（料金と規約を L2 で引いてから・私信は泉に入れない線をテストに）。
   **承認の入口は別段で小さく**（二段承認と digest はそのまま・画面だけ手元に）。どちらも v2-3 の後。

## 8. 止まる条件

- 泉に「落ちないもの」（§2）を落とす設計が必要になったら止まる。
- Meta / X / Bluesky の規約で、集計の第三者提供に制約が見つかったら止まる（着手前に一次資料）。
- 台帳の移行で VM の稼働が止まる形になったら止まる（運用と段取りを決めてから）。
- 泉の受け口を「落とす人がいない」うちに作りたくなったら止まる（§6 v2-5）。

## 9. 作法 §9 self-check

- 原理地図を先に: §0（LLM が選ぶ・門は無料・泉で商う）→ 各節。
- 設計書 1 commit → review → 次段階: この文書。
- tracer PoC: v2-0（自分の 4 アカウントで枝の指標）が tracer。
- 機械 lint: 「落ちないもの」はテストにする（§2）。門が泉に依存しないこともテスト（§5）。
- 「○○によると」は書かない: 出典は URL と節番号で。
- 証拠階層: L1/L2/L3 を各主張に付けた。X の単価と Bluesky の上限は L2、Bluesky の認可とスレッド取得の形は L3（実装前に引き直す）。
- schema 再設計・意味論変更・cross-repo: 台帳の置き場（§7-1）と `thth share` の送る形（§2）で止まって裁定を待つ。
