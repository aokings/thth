## 0. 要約

1. 口は 4 種類に分ける: **ページ（facebook・ある）**・**Instagram（instagram・新しい媒体）**・**広告（媒体ではなく別の種類の口）**・**Webhook（受け口）**。Threads 広告とカタログは広告の中の枝で、後回し。
2. 媒体の adapter の下に **Meta の共通層 `thth/meta/`** を 1 つ切る（Graph の呼び出し・`appsecret_proof`・エラーの振り分け・量の制限のヘッダ・`debug_token` と期限）。facebook.py の中身を抜き出して作り、Instagram と広告はそれに載せる。Threads（graph.threads.net）は触らない。
3. 「媒体名の表が 15 か所」は、**表を 1 か所に移すのでなく、1 か所の宣言と全部の表が一致することを縛る試験を先に張る**。移すのは試験が赤を指した所から。運用と同じ repo を触るので大移動はしない。
4. 広告は「1 口座 = 1 媒体の投稿先」の枠に入らない。はてなの主体（principals）の前例に倣い、**広告アカウントの台帳 `adaccounts/<名前>.json` と状態 `adaccount_state/`** を別に持ち、CLI は `thth ads …`。鍵はページの鍵では呼べないので、**ユーザーの長い鍵（60 日）を広告の口座の `.token` に持つ**。システムユーザーへの乗り換えは広告アカウントの置き場が決まってから（F の問い 1）。
5. お金の柵は **非対称**: 読む・止める・減らすは承認なしでいつでも通す。作るのは `PAUSED` で作るところまでは承認なし、**配信を始める・予算を増やす・再開するだけが承認**（金額を指紋に入れた digest ＋ hub の承認番号 ＋ THTH 側の月の上限（既定 0）＋ Meta 側の `spend_cap`）。見積もりと `amount_spent` の日次の照合を events に出す。
6. 鍵と期限: ページの鍵は期限なし【確】。ただし **`data_access_expires_at`（90 日）が Instagram の権限に効く見込み【推】**で、今は `.token` に書くだけで誰も読まない【確】。下ごしらえで doctor／maintain に読ませ、残り 14 日で知らせる。
7. 公式の広告 MCP サーバーは **THTH のアプリには足さない**（`ads_mcp_management` と消せないユースケースが要る【確】・THTH の柵を通らない支出の道ができる）。masaru 個人が探索に使うなら、開発者アプリなしの道で別に繋ぐ（F の問い 2）。
8. 段は 8 つ。順は **下ごしらえ → FB の仕上げ → 共通層 → Instagram → 広告（読む）→ 広告（書く）→ Webhook → 外の人の道**。広告（読む）と Webhook は独立なので、2 人の writer で並べられる。
9. 各段に「できあがりの条件・柵（わざと壊す対象）・本番の確かめ・masaru が押すもの・運用に渡すもの」を書いた（E）。本番の確かめは **読むだけの呼び出しから**、お金が動くものは撮影の日に masaru の承認。
10. masaru に決めてもらうのは 3 つ（F）: 広告アカウントの置き場と鍵の主体・公式 MCP を THTH のアプリに足すか・最初のお金の上限の数字。ほかは推しで進める。

### A-3. 公式の広告 MCP サーバーを使う道と、THTH に口を作る道

| | 公式の広告 MCP（mcp.facebook.com/ads） | THTH に口を作る |
|---|---|---|
| できること | 報告・作成と管理・カタログ・A/B・リフト調査まで 7 分類【確】。細かい探索に強い | boost・止める・予算・読む、に絞る |
| 要るもの | 鍵に `ads_mcp_management`＋`ads_read`／`ads_management`。THTH のアプリで使うなら消せないユースケースを足し、構成を直して **D（許可の画面）をやり直す**【確】 | 今の 19 権限で足りる【確】 |
| 承認と記録 | Meta の「rules」でポートフォリオの管理者が AI のできることを縛れる【確】。THTH の承認・台帳・hub の番号は通らない | 投稿と同じ 2 段の digest・VM の承認台帳・hub の番号・guard |
| 止める | MCP の道具で止める（LLM が動いている間だけ） | `thth ads pause` と `/activity` の「止める」・timer の見張り |
| 支出の見張り | 自前では無い | 日次の照合（D-5） |
| 鍵 | システムユーザーの鍵は Employee の役割だけ【確】・利用者トークンでも可 | 広告の口座の `.token`（C-3） |
| 利用者（外の人）への道 | 利用者が自分で繋げる（開発者アプリなしの道）【確】 | THTH の招待と同じ道（段 8） |

推し: **両方使うが、置き場を分ける**。THTH には boost・止める・読むの口を柵つきで作る（利用者の LLM からの道を 1 本にするため・支出の全部が THTH の台帳と hub を通るため）。公式 MCP は masaru が自分で「広告マネージャの代わりに探索する」道具として、**THTH のアプリでなく開発者アプリなしの道**で繋ぐ。THTH のアプリに足さない理由: ユースケースが消せない・D のやり直し・THTH の柵を通らない支出の道が THTH の鍵でできる。→ F の問い 2。

## B. 構造

### B-1. 層の切り方

```
利用者の LLM ── thth CLI（MCP・skill は補助）
   │
   ├─ 媒体の adapter（投稿先）           ├─ 広告の口（別の種類）        ├─ 受け口
   │   adapters/facebook.py（ある）      │   thth/ads/                 │   callback/（Worker）/webhook/
   │   adapters/instagram.py（新）       │     ledger.py  台帳・状態     │   thth/worker.py が取りに来る
   │                                     │     ops.py     読む・作る・止める
   │                                     │     budget.py  上限（予約→確定）
   └──────────────┬──────────────────────┴──────────────┬──────────────┘
                  ▼                                     ▼
          thth/meta/（Meta の共通層・新）
            graph.py   呼び出し・版 1 か所・appsecret_proof・redact・時間切れ
            errors.py  エラーの振り分け（permission / rate_limited / definite / ambiguous）
            usage.py   X-App-Usage・X-Business-Use-Case-Usage・x-fb-ads-insights-throttle を読み state に残す
            tokens.py  debug_token・data_access_expires_at・再認可の URL（auth_type=reauthorize）
            media.py   公開 URL の置き場（Threads の relay を Meta 向けに貸す）
```

- **Threads は触らない。** `graph.threads.net` は別のアプリ・別の鍵・別の文書で、今は本番で動いている。共通層は `graph.facebook.com`（＋ `graph-video`・`rupload`）だけを扱う。
- 共通層の中身は **facebook.py から抜き出して作る**（`facebook.py:103-125` の宛先の検査・`_request`・エラーの振り分け `407-463`・`auth_facebook.py` の `debug_token`）。抜き出しの前後で `tests/test_facebook_adapter.py` 31 本・`tests/test_facebook_auth.py` 21 本が同じ結果になることが条件。
- 共通層が新しく持つもの:
  - **量の制限のヘッダを読む**: `X-Business-Use-Case-Usage` の `estimated_time_to_regain_access`（分）と `call_count` を `state/<口座>/meta_usage.json` に残し、80001（ページ）・80002（IG）・80004（広告の管理）・80000（広告の成績）・4・17・32 は `rate_limited` に振り分けて、**その分だけ待って**から次の timer で再試行（今の FB は再試行しない【確・現状 §2-1】のまま。待つのは timer の側）。
  - `x-fb-ads-insights-throttle` は広告の読みで毎回見る【確】。
  - **`appsecret_proof`** を全部の呼び出しに付ける（今は付けていない【確・grep】。システムユーザーの鍵では必須【確・事実 §3-6】）。
  - **秘密の扱い**は今の作法のまま（鍵は `redact` に登録・例外文に URL を入れない `facebook.py:30-34`）。

### B-2. 媒体の adapter（ページ・Instagram）

- 枠は今の `Adapter`（`base.py:339`）のまま。Instagram は `adapters/instagram.py` を足し、REGISTRY に 1 行（`__init__.py:26-32`）。
- `KNOWN_CAPABILITIES`（`base.py:170-205`）に足す語: **`carousel`**（複数の画像を 1 本にできる・FB の `attached_media`・IG の `CAROUSEL`）、**`hide_reply`**（返信を隠せる・戻せる）、**`edit_post`**（出した投稿の本文を直せる）。広告は媒体の語にしない（広告は adapter ではない）。
- Instagram の口座の台帳: `media: instagram`・`ig_user_id`（数字・正本）・`page_id`（親のページ・認可で `/{page-id}?fields=instagram_business_account` から引いて照合【推・公式の IG 文書の一般の手順。本物で確かめる】）・`handle` は IG のユーザー名。
- Instagram の鍵: **ページの鍵でよい**（Facebook Login の道では「ページトークン」が口の鍵【確・事実 §2-1】）。ただし口座ごとに `.token` を別に持つ（THTH の「1 口座 1 鍵」の形を崩さない・ページの口座を消しても IG の口座が生きる）。認可の流れは `auth_facebook.py:203-278` の延長で、ページを選んだあと `instagram_business_account` を取り、台帳の `ig_user_id` と照合して保存。
- Instagram の画像・動画は Meta が公開の URL を取りに来る【確】。Threads が使う relay（`media_relay.py`・Worker の `/media/`）を **Meta 向けに貸す**（`media_delivery.py:94` が relay を threads にしか渡していない【確】→ 媒体の性質「`media_fetch: pull`」で分岐させる）。FB は multipart で直に送る（今のまま）。
- 入れ物（コンテナ）の 2 段は Threads の `publish_container`（`threads.py:505-558`）と同じ型。入れ物は 24 時間で切れる【確】・状態の問い合わせは 1 分に 1 回で 5 分まで【確】。「入れ物は作ったが公開の結果が分からない」は `publish_ambiguous` にして inflight の記録に残す（Threads と同じ）。

### B-3. 「媒体名の表が 15 か所」問題

現状 §1-3 の表のとおり、媒体を足すと 15 か所ほど触る。選べる道は 3 つ。

| 道 | 中身 | 利点 | 代償 |
|---|---|---|---|
| (a) 今のまま、1 か所ずつ手で足す | IG を足すとき 15 か所を直す | 変更が小さい | 漏れる（FB で実際に 6 か所漏れた【確】）。漏れても試験が赤にならない所がある（scenario・dashboard・thread_read） |

## D. お金の柵の設計

### D-1. 原則

1. **非対称**: 止める・減らす・読むは承認なしで、止まっている口座からでも通す。作る・増やす・始める・再開するだけが柵の内側。
2. **既定は止めた状態**: 台帳は `production: false`・`ads_enabled: false`。THTH 側の月の上限は **既定 0**（X の投稿の本数と同じ型【確・`budget_x_posts.py:5-6`】）。新しい広告は **必ず `PAUSED` で作る**（公式の例もそう【確】）。配信を始めるのは別の操作。
3. **二重の上限**: Meta 側の `spend_cap`（届くと全配信が止まる【確】）と THTH 側の月の上限。THTH 側は見積もりで、「Meta の請求書ではない」と明記（`budget_x.py:1` と同じ）。
4. **金額を指紋に入れる**: 承認の digest に金額・通貨・期間・対象の id を入れる。本文の指紋（`approval.py`）とは別の版 `thth-ads-1`（`FINGERPRINT_VERSION` は上げない。はてなと同じ扱い【確・`approval.py:496`】）。
5. **masaru の承認**: `require_gate: true` の口座は hub の承認番号が無い確定を断る（今の仕組み `cli.py:750-779`【確】）。広告の口座は **既定で `require_gate: true`**。

### D-2. 操作の分類

| 操作 | 承認 | 上限の確認 | 記録 |
|---|---|---|---|
| 読む（アカウント・成績・支出） | なし | — | `ops/` に残さない（量だけ `meta_usage.json`） |
| 止める（`status=PAUSED`・キャンペーン／広告セット／広告） | **なし・いつでも** | — | `ops/` |
| `spend_cap` を下げる・既支出の額にする（緊急停止） | なし | — | `ops/` |
| 予算を減らす・終了日を早める | なし | — | `ops/` |
| 削除（`status=DELETED`） | なし（取り下げと同じ扱い・digest は要る） | — | `ops/` |
| 作る（キャンペーン・広告セット・クリエイティブ・広告・全部 `PAUSED`） | なし（`production` の旗だけ） | 1 操作の上限（日予算・期間）を超える指定は作らない | `ops/` |
| **配信を始める（`status=ACTIVE`）・再開** | **2 段の digest ＋ hub の番号** | 月の上限の予約（見積もり＝日予算×残り日数）・`spend_cap` が入っていること | `ops/`・承認台帳 |
| **予算を増やす・期間を延ばす** | **2 段の digest ＋ hub の番号** | 同上（差分で予約） | 同上 |
| `spend_cap` を上げる・外す | **2 段の digest ＋ hub の番号** | THTH 側の月の上限以下 | 同上 |

- 「作る」を承認なしにする理由: `PAUSED` ではお金が動かない【確】。作成の口は idempotent【確】なので連打の害も小さい。利用者の LLM が下書き（広告の形）を作って、masaru が `thth ads show` で見てから始める、が投稿の「queue → approve → send」と同じ形になる。
- 「始める」の digest に入れる物: `act_id`・対象の id・`object_story_id`／`source_instagram_media_id`・`daily_budget` か `lifetime_budget`（最小単位の整数と通貨）・`start_time`・`end_time`・`targeting` の sha・`publisher_platforms`。どれかが変わると digest が変わる。

### D-3. 上限の 3 層

| 層 | どこ | 誰が決める | 既定 |
|---|---|---|---|
| Meta の `spend_cap`（広告アカウント） | Meta | masaru（`thth ads cap set` は承認つき） | THTH は「入っていないと始めない」 |
| THTH の月の上限 `ceilings.monthly`（通貨の最小単位） | 台帳 | masaru（`thth ads budget set --monthly --by`） | **0**（始められない） |
| 1 操作の上限 `ceilings.daily_budget_max`・`ceilings.days_max` | 台帳 | masaru | 0・0 |

- 月の上限の消費: X の予算と同じ **予約 → 発射 → 確定** の状態機械（`budget_x.py:20`）。「始める」で見積もり（日予算 × 終了までの日数、終了日が無ければ `days_max`）を予約。日次の照合（D-5）で実支出に置き換える。結果不明は使ったものとして残す。
- 通貨の最小単位: `spend_cap` の読む欄と書く引数で単位が食い違う【確・食い違い】。円は小数を持たないので、**最初の 1 回は読むだけで `spend_cap` と `amount_spent` の値を見て、管理画面の表示と比べる**（G の 1）。THTH の中は「最小単位の整数＋通貨」で統一し、書くときの変換は共通層の 1 か所。

### D-4. 止める

- `thth ads pause <名前> [--all | --campaign <id>]`: Meta に `status=PAUSED`。**承認なし・口座が止まっていても通す**。`guard.stop` と `leave_gate` の停止は「THTH からの要求を止める」だけ【確・現状 §4-3】なので、**`thth ads stop <名前>` は Meta 側の `pause --all` ＋ THTH の停止 ＋ `spend_cap` を `amount_spent` の額にする**、の 3 つをまとめて行う。
- `/activity` の「止める」（Worker → VM の `thth worker`）に広告の口座も載せる（段 8 で外の人の道と一緒に）。それまでは CLI と MCP の道具。
- 緊急の順: ① `spend_cap` を既支出に（全配信が Meta 側で止まる【確】）→ ② `pause --all` → ③ THTH の停止。①が通れば②③が失敗しても止まる。

### D-5. 見積もりと実際の支出の照合

- 日次の collect（timer）で広告の口座も回す: `/act_<id>?fields=amount_spent,spend_cap,account_status,balance` と `/act_<id>/insights?fields=spend,impressions,clicks,reach&date_preset=yesterday`、動いている広告ごとの `insights`。
- 比べる: 予約した見積もり vs `amount_spent` の増分。差が見積もりの 20% を超えたら events `ads_spend_over_estimate`、`amount_spent / spend_cap` が 80% を超えたら `ads_spend_cap_near`、`account_status` が 1（ACTIVE）以外になったら `ads_account_status`、月の上限の残りが 10% を切ったら `ads_budget_low`。全部 `thth morning`・dashboard の要対応に載せる。
- 数は 15 分ごとに更新・28 日を過ぎると動かない【確】。照合は「昨日」の値で行い、28 日前までを対象に遡って直す。

危ないところ（事故の芽・設計で避けた所）:
- **「止める」が Meta 側を止めない**: THTH の停止は要求を止めるだけ。D-4 の `stop` が `spend_cap`→`pause`→停止の 3 つを行う。
- **`spend_cap` 0 は「上限なし」**【確】: THTH は 0 を「入っていない」と読み、`activate` を断る。
- **`spend_cap` は「かけた時点より後の支出にだけ効く」**【確】: 既支出の額にすると「それ以上は使わない」になる（全配信が止まる）。
- **作成の口は idempotent**【確】だが、THTH の `ops/` の記録と Meta の物の対応は id で取る。結果不明（時間切れ）のときは `GET /act_<id>/campaigns?filtering=[name]` で探してから再送。
- **広告の鍵はユーザーの鍵**: ページの口から広告は呼べない・広告の鍵でページに出さない（口座の `.token` を分ける）。
- **IG の入れ物は 24 時間で消える**【確】: inflight の記録に残し、翌日 collect が「公開されていない」と確かめたら `publish_definite` に落とす。
- **FB のリールは 24 時間に 30 本**【確】・IG は 50: media_traits の根拠に書き、THTH の `post.daily` 8 は内側。
- **規約 6.2（IG の利用者のコンテンツの表示・取り込み・保存を簡単にする使い方の禁止）**【確】: business_discovery は数だけ保存し、本文・画像を THTH の台帳に残さない。自分の口座の投稿の採取は「自分のデータ」なので当たらない【推】。
- **`appsecret_proof` を付け忘れると、アプリの設定で「app secret を要求」を入れた瞬間に全部止まる**: 段 2 で全部の呼び出しに付ける。
