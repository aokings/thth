## 2. 配布の仕組み（いちばん大事な変更）

**`main` への push では本番は変わりません。** `release` を進める操作が配布です。

```
git push origin <検収済みの SHA>:refs/heads/main       # 保存
git push origin <同じ SHA>:refs/heads/release          # **配布**
```

**VM は `release` だけを追います**（`thth/selfupdate.py`）。`thth board` の先頭に
道具の版と、**確かめた時点**が出ます。

**切り替えの順番と待ち条件は設計 §3.2.1。** VM の upstream は
`origin/release` に付け替え済み（運用セッションが 2026-09-12 午前に実施）。

### 観測の棚に、account 固有のものが混ざっている（**未着手・masaru の判断待ち**）

**運用セッションが 2026-09-12 夕方に見つけました。** いま `topics.json` にこういう
行があります。

    中学受験［行動］ — 受験親のやりとり。自アカウントの既存 6 投稿が全部この語で views 202〜574

- 「受験親のやりとり」＝ **誰がいるか。共有できる事実**
- 「自アカウントの既存 6 投稿が 202〜574」＝ **その account の実績**

**`observation()` は「語ごとに最後の行が勝つ」造り**で、**`account` を持つ行と持た
ない行を同じ土俵に並べます**（`thth/topics.py`）。意図は「**誰がいるかは共有の事実**
だから分けない」で、**その意図自体は正しい**と思います。

**穴は、`audience` に何を書いてよいかを決めていないこと。** account 固有の実績が
共有の棚に乗り、**別の account が書き直すと前の実績が消えて入れ替わります。**
**判断（`judgment`）は account で分けたのに、観測は分けていません。**

**直し方の候補**（どちらも未着手）:

1. **`audience` に書いてよいものを決めて検査する。** 「誰がいるか」だけ。実績・
   数字・自分の投稿の話は別の欄か、観測ではなく判断側へ。**こちらのほうが筋が
   良いと考えています**（分けるのではなく、棚の意味を守る）。
   **ただし既存の 46 件＋今日の記録が、その検査を通らないはず。** 既存を壊さずに
   どう入れるかを決める必要があります。
2. 観測も account ごとに持ち、読むときに共有部分だけ重ねる。**分けすぎると、同じ
   確認を全員がやり直すことになります。**

**この行を新しい観測で上書きするのは勧めません。** 運用セッションは「経過時間と
現在値は確かめたが、**その語に誰がいるかは見ていない**」と言っています。**最後勝ち
なので、入れると「確かめていないもの」が共有の棚に乗ります。**「古い」ことと「確かめ
ていないもので上書きする」ことは別です。

## 5. この repo の作法（引き継ぐ人へ）

- **全件テストは `python -m pytest tests/ -q -n auto`**（約 70 秒。`pytest-xdist` を
  入れてあります）。`| tail` で受けると**終わるまで 1 バイトも出ません。**
- **直したら変異をかける。** 直した箇所を戻して、**意図したテストが落ちること**を
  確かめる。**落ちなければ、そのテストは何も守っていません。**
- **変異の置換には必ず `assert` を付ける。** 今日 3 回、置換が当たっていないのに
  「通った＝効いていない」と読みかけました。
- **対象を絞って回さない。** 個別実行では 3 ファイルしか落ちず、全件で 8 件出た
  ことがあります。**全件を回すまで「通った」と言わない。**
- **1 つの検収対象に 1 つの変更。** 別件を混ぜると、判定が遅くなるうえ、**本体が
  未コミットのまま別の commit に紛れ込みます**（今日やりました）。
