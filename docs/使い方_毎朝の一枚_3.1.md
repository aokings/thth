# 毎朝の一枚（`thth morning`・3.1.0）

朝いちばんに 1 回。**昨日から何があって、今日なにをすればよいか**を、道具が事実だけで 1 枚にします。

```bash
thth morning kopicha              # project（その project の account 全部）
thth morning kopicha-threads      # account 1 本
thth morning kopicha --json       # JSON だけ
thth morning kopicha --no-mark    # 栞（前回読んだ時点）を進めない
```

MCP なら `thth_morning {"target": "kopicha"}`（`mark: false` で栞を進めない）。LLM セッションの**最初の 1 回**はこれです（`handoff-report --since-last-read` を含むので、版の確認も同時に済みます）。

---

## 6 つの段

| 段 | 何を言うか |
|---|---|
| 0 道具 | いま入っている版・前回読んだときから変わったか・読むべきリリースノート。版が変わったときだけ「出せるもの表」（媒体ごとの添付の対応表）も出します |
| 1 返していないもの | 自分の根投稿に付いた**未回答の返信**（台帳から）と、**まだ返していない言及**（媒体に 1 回だけ聞く）。誰から・何に対して・経過時間・permalink。未回答の返信の窓は台帳の `collect_days`（既定 14 日・3.1.0 までは 7 日固定）で、窓の残りが 24 時間を切った行に `window_edge: true` と「⚠ 窓まで <n>h」 |
| 2 昨日の自分 | **昨日（JST）出した投稿ごと**の views／likes／replies／reposts と、採取の回数。およそ 24 時間前の採取があれば、その差も |
| 3 世間 | **監視語ごと**に、件数・異なり投稿者・上位 3 人の占有率・直近の時刻と、**絡みに行く先 3 件**（permalink・返信の有無・自分の履歴の有無）。絡む先からは、同じ project の同じ媒体の全 account（同じ本人の別台帳を含む）の投稿を除き、除いた本数を `own_excluded` に出す。件数と異なりは除く前のまま（3.1.1） |
| 4 予定 | 今日出る予定（承認済み・下書きとも）・承認待ちの数・時刻超過・inflight・X の予算（読取の残り USD と投稿の本数）。時刻超過は数だけでなく**名前**も出す（`overdue_items`: file・publish_at・経過時間・先頭 60 字を古い順に最大 10 件、`n` に全体の数・3.1.1） |
| 5 次の一手 | 定型 4 種の**候補だけ**: 「返す」（1 段の各行）・「絡む」（3 段の各行）・「出す」（4 段で今日の予定が無い account）・「超過」（4 段の時刻超過の各行・3.1.1） |

数にはすべて分母が付きます。取れなかったものは **`0` ではなく `null`** で、理由が 1 語付きます。

| 理由 | 意味 |
|---|---|
| `provider_timeout` | 媒体が時間内に返さなかった（検索は 40 秒・他は 10 秒待ちます） |
| `budget_exhausted` | X の読取予算（推定 USD）が残っていない。1〜3 段を飛ばし、4 段の予算の行だけ出します |
| `scope_missing` | 権限がトークンに乗っていない／標準アクセスでは対象が絞られる |
| `no_watch_words` | その account に監視語が入っていない（3 段だけ） |
| `not_supported` | その媒体にその口が無い（例: X に語の検索はありません） |
| `unavailable` | 上のどれでもない理由で取れなかった |

---

## 監視語（3 段の材料）

**語は管理者が入れます。道具は語を選びません**（推測で選んだ語の「世間」は、世間ではないので）。

```bash
thth admin watch set kopicha-threads コーヒー 自家焙煎 --by masaru
thth admin watch show kopicha-threads
```

- 1 account あたり**最大 5 語・1 語 40 字**まで。`set` は**入れ替え**（追記ではありません）。
- 変更は管理記録に `watch_set` として残りますが、**語そのものは記録に書きません**（在った／無かっただけ）。
- 語が無い account は 3 段を `no_watch_words` で飛ばします。

---

## この口が**絶対にしないこと**

- **本文を作らない。** 5 段は候補の列挙だけで、返す文も出す文も 1 字も作りません（作るのはあなたと LLM の会話の側です）。
- **SNS 台帳に書かない。** 読むだけです。進むのは**栞**（前回読んだ時点）だけで、`--no-mark` なら，それも進みません。
- **語を選ばない。** 監視語は管理者が入れたものだけを使います。
- **空欄を推測で埋めない。** 取れなかったところは `null` と理由で、`0` とは混ぜません。
- **絶対パスも本文全文も返さない。** 本文は先頭 60 字の抜粋だけです（`thth where` と同じ）。
- **順位を付けない。** 並べるだけで、「これに絡め」とは言いません。

---

## 叩いた回数

`--json` の `calls` に、媒体ごと・endpoint ごとの回数が出ます（例: `{"threads": {"mentions": 1, "keyword_search": 2}}`）。1 回の `morning` で叩くのは **言及 1 回／account** と **語の検索 1 回／語**（Bluesky・Mastodon はタグの観測が 1 回／語 増えます）。実測は手元の台帳を読むだけなので 0 回です。

**世間の検索は 40 秒待ちます**（2026-09-23 実測。10 秒では Meta の索引引きが間に合わず、切られた側からは 0 件と区別が付きませんでした）。他の口は 10 秒のまま。`THTH_THREADS_TIMEOUT_SECONDS` で両方まとめて上書きできます。

---

## 栞（前回読んだ時点）

既定で `handoff-report --mark-read` 相当に栞を進めます（名乗りは `morning`）。次に呼んだとき、0 段の「前回から変わったか」がこの栞を基準に答えます。**読むだけで進めたくないときは `--no-mark`**（MCP は `mark: false`）。招待されたサーバ MCP からの `thth_morning` は**栞を進めません**（`cannot_say` に `server_mode_read_only` が出ます）。
