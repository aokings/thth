## 1. 直さないと危ない

### 1-1. 月の上限が、月をまたぐ配信を翌月に数えない（翌月に満額の予約が通る）

- 重さ: **直さないと危ない**（月の上限が、配信が月をまたぐたびに 1 操作の上限の分だけ漏れる。配信 2 本なら翌月の実支出が月の上限の 2 倍になりうる）
- 中身: `activate` は通しの予算の全額を**打った月**の `budget-<月>.json` に予約する（`thth/ads/ops.py:479`・`thth/ads/budget.py:108-114`）。翌月の `usage()` は翌月のファイルの予約しか見ない（`budget.py:145-157`）。そのうえ `thth_campaigns()` が**前の月の予約のキャンペーンも「自分の物」**として外の支出から除く（`budget.py:128-138`・`:148`・`:160`）ので、翌月に実際に使った額は **予約にも・確定にも・外の支出にも入らない**。つまり 10/31 に始めた 5,000 円の配信が 11/1〜11/7 に 5,000 円使っても、11 月の `used_minor` は 0 で、11 月にさらに 10,000 円（月の上限の満額）を予約できる。
- 証拠（再現・緑＝穴あり）: `test_D1_月またぎ_前の月に予約した配信の今月の支出がどこにも数えられない` — 月の上限 10,000・5,000 の配信を 2 段で始める → 翌月 15 日の `budget.usage(..., campaign_spend={cid: 5000})` が `reserved 0・settled 0・outside 0・used 0` → `budget.check(view, 10000)` が通る。同じ月では `used_minor == 5000` と正しく数える（対照）。
- 影響の範囲: F 問い 2 の数（月 10,000・1 操作 5,000・7 日）だと、月末の 7 日間に始めた配信の分だけ翌月が甘くなる。`spend_cap` 30,000 の天井と `ads_budget_low`（実支出の 90%・`watch.py:357-363`）の知らせはこの穴の外側で効く。
- 直し方の案（どれか 1 つ）:
  1. **実支出で縛る**（D-3 の「月の照合は insights の spend を月の範囲で取る」に合わせる）: `usage()` の `used` を「今月の予約の残り（終わっていない物）＋ **口座の今月の実支出の全部**（`insights level=account this_month`）」にし、予約の外／内の区別をやめる。実支出はもう `campaign_spend_this_month` で読んでいるので、`sum(campaign_spend.values())` を使えば 1 行。終わっていない予約は「残りの見込み」として `amount - その campaign の今月の実支出`（負なら 0）にする。
  2. 予約を **月で割る**: `reserve()` で `start_time`〜`end_time` を月ごとに按分して、またぐ月のファイルにも予約の行を書く。
  - 1 の方が単純で、「月の照合は実支出」という D-3 の言葉そのものになる。試験は D1 の台本をそのまま repo に入れて赤→緑を見る。

### 1-2. THTH が止めた（または一度始めた）物を、外で再開しても `ads_active_outside_thth` が鳴らない

- 重さ: **直さないと危ない**（A-6 の「THTH の外で配信が始まったとき気づく」が、いちばん起きやすい形——`thth ads stop` で止めた物を Ads Manager で誰かが再開——で鳴らない。止めの印は立っているので運用は「止まっている」と思っている）

- 証拠（再現・緑＝穴あり）:
  - `test_D2_stopのあと管理画面で再開しても_外の配信と言わない` — 2 段で始める → `stop`（`confirmed True`・全部 PAUSED）→ 偽の Meta で全部を ACTIVE に戻す（管理画面の代わり）→ `collect` → `events` に `ads_active_outside_thth` が**無い**（動いている物は 3 件）。

## 2. 直したほうがよい

### 2-1. 広告セットが複数のキャンペーンでは、1 回の `activate` の合計が `lifetime_budget_max` を越える

- 中身: `_tree_money()` は広告セット**ごと**に `lifetime_budget_max` と比べ（`ops.py:380-383`）、合計 `total` は月の上限とだけ比べる（`budget.check`）。THTH の `boost` は広告セット 1 つしか作らないが、管理画面や公式 MCP で広告セットを 3 つ持つキャンペーンを作って THTH で始めると、1 操作で 15,000 円（上限 5,000 の 3 倍）が通る。月の上限（10,000）が別に効くので実害は月の上限までだが、「1 操作の上限」が名前どおりに効いていない。
- 証拠（再現・緑＝穴あり）: `test_D3_広告セットが複数なら1回のactivateの合計がlifetime_budget_maxを越える` — 月 20,000・1 操作 5,000・5,000×3 の広告セット → 1 段目が `amount_minor 15000` で通る。
- 直し方: `_tree_money()` の最後で `total > ceilings["lifetime_budget_max"]` も断る（`ads_lifetime_over_ceiling`）。`extend` も同じ関数を通るので一緒に直る。

### 2-2. `stop` が木を全部読めていなくても「止まった」と言う

- 中身: `stop` の ①（止める対象）と ②（読み直し）はどちらも `reader.tree(urgent=True)` を使うが、`tree()` が返す `complete`（`MAX_PAGES`＝10 頁×100 件を越えると False・`graphread.py:152-171`・`:215-225`）を見ていない（`ops.py:701`・`:709`）。1,000 件を越える口座では、読めなかった物が ACTIVE のままでも `confirmed: True` になる。こぴちゃの口座では起きないが、「止まったと言うのは読み直しが通ったときだけ」（D-4 の 2）の条件が 1 つ足りない。
- 証拠（再現・緑＝穴あり）: `test_D6_stopは木を全部読めていなくても止まったと言う` — `Reader._list` を「全部は読めていない」を返すようにして `stop` → `confirmed True`。
- 直し方: `unpaused()` に `complete` を渡し、False なら `verify.ok = False`（理由 `ads_tree_incomplete`）にして hub の 1 行を出す。`activate` 側は `ads_tree_incomplete` で断っている（`ops.py:416-417`）ので、同じ扱いにそろえる。

### 2-3. `extend` のあと終了すると、実支出が予約の数だけ重ねて数えられる（多く数える側）

- 中身: `usage()` は終わった予約ごとに「その campaign の今月の実支出」を足す（`budget.py:154-155`）。`activate` と `extend` は同じ `campaign_id` で別の予約の行を書くので、終わると実支出が 2 回（`extend` を 2 回したら 3 回）数えられる。安全側（多く数える）だが、月の上限の残りが見かけより小さくなり、運用が驚く。
- 証拠（再現・緑＝穴あり）: `test_D4_extendのあと終了すると実支出が2回数えられる` — 500 で始めて 800 に延ばし、終了後に実支出 700 → `settled_minor == 1400`。
- 直し方: §1-1 の案 1（実支出で縛る）にすると自然に消える。別に直すなら campaign ごとに 1 回だけ足す。

### 2-4. 止めの印と台帳の柵は「ファイルの権限の柵」で、`THTH_ROOT`／`THTH_ADACCOUNTS_DIR` で差し替えられる

- 中身: 台帳の置き場は `$THTH_ADACCOUNTS_DIR`（`ledger.py:75-83`）、止めの印・予約・記録の置き場は `$THTH_ROOT/adaccount_state/`（`ledger.py:97-100`・`accounts.py:353`）。VM で `thth ads` を打てて鍵のファイル（0600）を読める人は、環境変数で別の台帳（`production: true`・上限大）と空の状態の置き場を指して `activate` を通せる。設計 D-1 の 3「利用者の LLM は VM の台帳に手が届かない」はこの前提を言っていて、MCP は `run_cli()` の環境を利用者の LLM が触れない（`mcp/server.py:785-787`）し、`-` で始まる値を断る（`:732-759`）ので、**MCP からは越えられない**。つまり設計の前提の内側では穴ではない。
- 直し方: コードでなく言葉。`ops.py` の冒頭と運用の手順に「上げられない・戻せないのは、VM の鍵と台帳を読める人以外に対して」と 1 行書く。環境変数を本番で固定したいなら、`/srv/thth/app/bin/thth` の包みで `THTH_ROOT` を固定し、台帳の置き場の差し替えは試験のときだけ使う。

### 2-5. digest に `effective_status` が入っていて、Meta 側の審査の進みで 2 段目が `ads_tree_changed` になる

- 中身: 作った者が推して入れた物（§7 の 9）。`effective_status` は Meta が審査（`PENDING_REVIEW` → `PAUSED`／`DISAPPROVED`）で勝手に変える欄（`digest.py:24-28`）。1 段目と 2 段目の間に審査が進むと、木は誰も触っていないのに断られ、1 段目からやり直しになる。安全側なので危なくはないが、「変わった」の理由が運用に分からない。
- 直し方: 2 段目の断りの文に「どの欄が変わったか」を添える（`components()` の差分を出す）。`effective_status` を digest から外す案もあるが、`DISAPPROVED` の物を知らずに ACTIVE にする（お金は動かないが）のを避ける意味で、入れたままで差分を見せる方を推す。
