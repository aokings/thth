読むだけの下調べ。repo の他のファイルは変えていない。WebFetch で一次資料を読み、読めなかった所は「未確認」と書いた。

確かめた深さの記号: 【読】公式の頁を読んだ ／【検索】検索結果の要約だけ（原文未読） ／【未】確認できず

## 1. はてなブログ AtomPub

出所: https://developer.hatena.ne.jp/ja/documents/blog/apis/atom 【読】

- 認証: OAuth（read_private と write_private の承認が要る）、WSSE（ユーザ名＝はてな ID、パスワード＝詳細設定の API キー）、Basic（はてな ID と API キー。https のときだけ）。
- 投稿は POST（201）、編集は PUT（200）、削除は DELETE（200）。
- 下書き: `app:control/app:draft` に yes。指定がなければ公開。下書きの共有 URL（プレビュー）も出せる。
- 予約投稿: 下書きに `hatenablog:scheduled` を yes にすると、`updated` の時刻に公開される。原文「updated要素で指定した時刻に記事の投稿を予約します」。
- カテゴリ: `category` の `term` に複数指定できる。一覧は `GET /atom/category`。
- 記事の URL と id: 201 の Location ヘッダに記事の編集 URI。entry の `link rel="edit"` が編集 URI、`rel="alternate"` が公開 URL。id は `tag:blog.hatena.ne.jp,2013:blog-…` 形式。
- 回数の上限: この頁に記述なし（上限が無いとは書いていない）。
- 一覧取得は 1 頁 7 件。
- 画像: ブログ API の頁には無い。はてなフォトライフの Atom API（https://developer.hatena.ne.jp/ja/documents/fotolife/apis/atom 【読】）で、`/atom/post` に base64 の画像を POST（201）。返りの `hatena:syntax`（`f:id:<user>:<ID>:image`）をブログ本文に書くと埋め込める。認証は OAuth か WSSE（GET は read_private、POST などは write_private）。画像の差し替えは不可（削除して再投稿）。仕様は「ドラフト」で変わりうると書いてある。
- 食い違い: OAuth 対応 API 一覧（https://developer.hatena.ne.jp/ja/documents/auth/apis/oauth/apis 【読】）にフォトライフが載っていない。フォトライフに OAuth で通るかは実際に試すまで【未】。WSSE なら通る書き方。
- 【未】: 予約投稿で過去・未来の時刻の制限、記事の本文の長さ上限、ブログ側の個別の規約（はてなブログのガイドライン）は読んでいない。

## 2. はてなブックマーク REST API

出所: https://developer.hatena.ne.jp/ja/documents/bookmark/apis/rest ほか 【読】

- 認証は OAuth。scope は `read_public / write_public / read_private / write_private` の 4 つだけ（https://developer.hatena.ne.jp/ja/documents/auth/apis/oauth/scopes 【読】）。
- 取得 `GET /rest/1/my/bookmark?url=`（read_public か read_private）。
- 追加・更新 `POST /rest/1/my/bookmark`（write_public か write_private）。パラメータ: `url`、`comment`（長さ制限の記載なし）、`tags`（最大 10）、`post_twitter`・`post_mixi`・`post_evernote`（外への共有）、`private`。既にあれば更新になる。
- 削除 `DELETE /rest/1/my/bookmark?url=`（204）。
- ほかに エントリー API（`GET /rest/1/entry`）、タグ API、ユーザー情報 API。エントリー API の詳細頁は未読【未】。
- 旧 `api.b.hatena.ne.jp` は 2020-03-04 以降使えず、`bookmark.hatenaapis.com` を使う。
- 回数の上限: 数値の上限なし。原文「過剰な連続アクセス、User-Agent を正しく指定しないアクセスなどは予告なしに制限をかける場合があります」。User-Agent は必ず付ける。
- 件数取得: `https://bookmark.hatenaapis.com/count/entry?url=`、複数は `/count/entries`（1 回 50 URL まで、超えると 414）。実験的 API で予告なく変わりうる。「数秒空けて」と頼んでいる（https://developer.hatena.ne.jp/ja/documents/bookmark/apis/getcount 【読】）。
- エントリー情報（コメント一覧）: `https://b.hatena.ne.jp/entry/json/<URL>`（関連なしの軽い版は `/entry/jsonlite/`）。返りの `bookmarks` 配列に user・tags・timestamp・comment が入る。キャッシュなので実際とずれうる（https://developer.hatena.ne.jp/ja/documents/bookmark/apis/getinfo 【読】）。
- 人気・新着のフィード（RSS）と検索: 一次資料の頁を読めていない【未】。（人気エントリーの頁は hotentry の URL があることまでは検索結果で見えた【検索】。RSS の URL と使ってよい条件は別に当たる必要あり。）

## 3. 規約・ガイドライン

### 3-1. 自動投稿・プログラムからの操作
- はてな利用規約（https://policies.hatena.ne.jp/rule 【読】）に、プログラム・自動化を直接禁じる条はない。関係する条: 第6条1項f「不正な操作」、第6条3項a「宣伝や商用を目的とした広告・勧誘その他の行為」（ただし各サービスのヘルプ・ガイドラインで別に定める場合を除く）。
- ブックマークのスパムの頁（https://b.hatena.ne.jp/help/entry/spam 【読】）に「公正性に影響するような特定条件での自動ブックマーク（例：ブックマーク数に応じた自動投稿）」「機械的な高頻度のブックマーク」が出る。つまり API で出すこと自体は禁じられていないが、「機械的な高頻度」「条件で回る自動」は対象になりうる。
- API 専用の利用規約・商用利用の条件は、開発者向けの頁には見当たらなかった【未】。規約第1条3項は「アプリケーションごとの利用規約が適用される」とだけ書く。

### 3-2. セルクマ（自分の記事を自分でブックマーク）
- スパム行為の頁の原文（【読】）: 「自身が運営するサイトを自身のアカウントでブックマークすること自体は問題視されておらず、措置の対象ともしていません」。ただし「サイトの内容や態様からスパム目的と判断される場合や、機械的な高頻度のブックマークなど通常の利用から逸脱している場合」は表示制限・利用停止の対象になりうる。
- つまり masaru の言うとおり、セルクマは公式に認められている。条件は「自分のアカウントで」「通常の使い方の範囲で」。
- 禁じられている例（同じ頁）: メインとサブの複数アカウントで同じサイトをブックマーク／複数アカウントが共謀して同じ URL をブックマーク／同一サイトのページを大量にブックマーク／広告・宣伝・SEO を目的としたブックマーク／依頼や報酬／対象と無関係なタグやコメントで誘導。
- FAQ（https://b.hatena.ne.jp/help/entry/faq 【読】）: 「複数のアカウントを使用して同一のページにブックマークを行う（メインアカウントとサブアカウントの使い分けも含みます）」は過剰な最適化行為。「複数のユーザーで協力してブックマークを集める」も同じ。見つかれば「スパムとして新着エントリーや検索結果から外す」。
- 同じ人の複数アカウント: 規約第3条2項a「メインアカウントとサブアカウントは…同一のユーザーにより利用する」、第3条2項d「自作自演行為、ブックマーク数の水増し…は禁止」、第3条6項／第6条3項c「メインアカウントは原則 1 つ・許諾数を超えるサブは不可」。サブの許諾数は「はてなが別途定める数」で条文に数は無い【未】（古い Q&A に 4 とあるが現行は未確認【検索】）。
- レーンごとに別のアカウントを持つ問題: 運営者が同じ別 project のレーン（例: コーヒーのレーンのアカウントが、同じ運営者の別 project の記事をブックマーク）は、はてなから見れば「同一ユーザーの複数アカウントで同じサイトに関わる」形に見えうる。公式の頁はこの場合を直接扱っていない【未】。確実に安全と言える原文は無い。安全側の線は次のとおり。
  1. 1 つの記事に対してブックマークするのは、その記事を出したレーン 1 アカウントだけ。他レーンのアカウントでは同じ記事を触らない。
  2. 別 project の記事（同じ運営者）を他レーンのアカウントでブックマークするのは「複数アカウントでの水増し」に近いので避ける。
  3. そもそも複数のメインアカウントを持つこと自体が第6条3項c に触れうる。レーンのアカウントが「メイン 1 つ＋許諾内のサブ」なのか、別々の人（団体）のメインなのかを先に決める。同じ運営者が複数メインを持つのは規約違反になりうる。サブにすると、ガイドライン上は同じ人が使う前提なので、他レーンの記事を触ることが「同一ユーザーの複数アカウント」に直結する。ここは masaru が決め、はてなに問い合わせて確認するのが確実。
- 表示の制限: ガイドライン（https://b.hatena.ne.jp/guide/guideline 【読】）に「組織的な順位操作やスパム行為については機械的に監視・措置を行っています」「アカウントの削除と作成を過度に短期間で繰り返している場合」は利用をお断りすることがある、とある。使い捨てのアカウントは避ける。

### 3-3. ステマ・宣伝
- 規約にステルスマーケティングの専用条はない【読】。近い条: 第6条2項e（事実がないのに提携・協力関係があると偽る）、第6条3項a（宣伝・商用）、第6条3項b（検索サイトが認めない手段の SEO）。
- 宣伝・SEO を目的としたブックマークはスパム例に入る（上記）。自分の記事のセルクマは「自分のサイトの運営者として自分のアカウントで」であれば問題視しないが、運営者であることを隠して他人のふりをするのは避ける（アカウントのプロフィールに運営者であることを書く、が安全。これは推測）。
- 日本の景品表示法のステマ規制（2023-10 施行）は今回の調査対象外。ただし第三者のふりをした宣伝はここでも危ない、という方向は同じ。

### 3-4. ホッテントリ（人気エントリー）・新着エントリーに載る条件
公式に書いてあること:
- 人気エントリー: 「一定期間にブックマークを多く集めたエントリー」。新着より長い期間で測る（https://b.hatena.ne.jp/help/entry/walking 【読】）。FAQ では「ここ最近たくさんブックマークされたもの。ブックマークされた数でのランキング」。
- 新着エントリー: 「新着ブックマークのうち一定数以上ブックマークされているもの。人気入り予備軍」（FAQ【読】）。
- 具体的な期間・ブックマーク数のしきい値・自分のブックマークが数えられるか: どの頁にも書いていない。
- 外される条件: スパム・不正なブックマーク、成人向け・衝撃的な内容。ガイドラインによれば、特定のエントリーに注目を集めるための作為的な行動は評価されず、一定期間または恒久的に人気に載せない措置もある。

推測・通説（公式に書いていない。根拠にしない）:
- 「セルクマの 1 ブクマが入れば新着に出やすい」「はてなブログの記事は人気入りしやすい」という話は、公式の頁には無い。1 ブクマの効き方もしきい値も不明。
- セルクマが人気のスコアに数えられるかは未確認。数えられないか、割り引かれる可能性もある。
- カテゴリ（テクノロジー・学び・暮らし等）、記事の本文の質、公開の時刻、はてなブログの購読者（読者登録）の人数、他サイトからの流入が効く、とよく言われる。いずれも公式の記述は確認できていない。
- 「ノンスパムでホッテントリに載りやすくなる」と言えるのは、公式からは「スパムとして外されにくい」までで、「載りやすくなる」とまでは言えない。計画では目標にせず、結果として載ることがあるくらいに置く。載せるための小細工（知人への依頼、複数アカウント）は禁止例そのもの。

## 4. note の公開の投稿 API の確認
- note の公式の頁（ヘルプ・API 文書）では「公開の投稿 API が無い」とも「ある」とも原文で確認できなかった【未】。
- 検索で見えたこと【検索のみ・原文未読】: 外部サービス向けに note 社が「note API」を提携先に出していて、第一弾は下書きの送信まで、公開は note の画面で人が行う（オリコンのプレスリリース https://www.oricon.co.jp/pressrelease/3027859/）。一般の開発者が使っているのは Cookie と CSRF トークンを使う非公式 API で、下書き作成が中心、Cookie は 1〜2 週間で切れる、という開発者の報告がある。
- 結論: 一般の開発者が使える公式の公開投稿 API は、確認できた範囲では無い。非公式 API は規約と壊れやすさの両面で THTH の載せ方に向かない。note は「下書きを人が貼って人が公開する」のままが妥当。note 公式の言い切りを取るなら note へ問い合わせるか note の最新のヘルプを別途読む。

## 5. THTH に載せるならこう（案）

### 5-1. 命令の形
既存の `thth` の型（lint のあと --production で出す、台帳に残す）に合わせる。

- `thth blog hatena draft --lane <lane> --file 記事.md --title … --category … [--schedule <ISO日時>]` ：下書きを作る。この時点では公開されない。`--schedule` は `hatenablog:scheduled` に載せる。
- `thth blog hatena publish --lane <lane> --id <台帳の id> --production`：承認済みの下書きを公開（または予約）。
- `thth blog hatena retract …`：削除（DELETE）。
- `thth bookmark add --lane <lane> --url … --comment … [--tags a,b]`：ブックマーク（comment 必須、tags は最大 10）。`--production` が無ければ lint だけ。
- `thth bookmark retract`：DELETE。
- `thth bookmark count --url …`／`thth bookmark comments --url …`：読む側。count は /count/entries（50 URL まで）、コメントは /entry/jsonlite。ここは承認は要らず、上限と間隔だけ守る。
- 画像: `thth blog hatena image --file …`（フォトライフ）。OAuth で通るか未確認なので、最初は WSSE で試す。

### 5-2. 承認の段
- 段 1「記事の承認」: 本文・題・カテゴリ・公開（予約）日時を人が見て承認。承認した版の内容の雑湊を台帳に残し、承認後に本文が変わったら公開を止める（既存の型に合わせる）。
- 段 2「セルクマ」: 案は 2 つ。
  - 案 A（別の承認、こちらを推す）: ブログ公開のあとに、実際の記事 URL を入れた形でコメントを人が承認する。理由は、(1) 記事の URL・公開の成否は公開してみないと決まらない、(2) 予約投稿だと公開時刻まで URL が使えない、(3) コメントは「運営者であること」を書く文で、人が見る価値がある。実際の動きは、承認済みのセルクマを `--after-publish` で台帳に結びつけ、公開の確認（公開 URL が 200）が取れてから 1 回だけ打つ。
  - 案 B（1 つの承認でまとめる）: 段 1 の承認画面に「公開後に同じレーンで、この文でセルクマする」を含め、承認 1 回で ブログ公開→URL 確認→セルクマ 1 回を連続で行う。人の手間は減るが、コメント文に実 URL が出ない・公開が失敗したときのセルクマの扱いなど条件が増える。
  - 推し: 案 A の「承認は 1 回、実行は 2 段」の中間。段 1 で記事とセルクマ文を一緒に承認し（人が見るのは 1 回）、実行は公開の確認が取れた後だけ、セルクマ 1 回だけ。コメント文が承認後に変わったら止める。前提が変わる点: セルクマが人気の効きに数えられないと分かった場合は、セルクマ自体を省く選択肢を残す。
- セルクマは 1 記事につき 1 回・そのレーンのアカウントだけ。同じ URL への 2 回目は拒否（台帳で見る）。
- ネタ元のブックマーク（他人の記事を選んでコメントつき）は、人が選んだ 1 件ごとの承認。THTH が候補を探すのは構わないが、押すのは人。

### 5-3. 上限の既定（案。規約は数値を決めていない。THTH の側で絞る）
- ブックマーク追加: 1 レーン 1 日 5 件まで（セルクマとネタ元の合計）、連続の間隔は 10 分以上。「機械的な高頻度」を避ける線。超えたら止まり、上げるのは masaru の承認。
- セルクマ: 1 レーン 1 日 1 件。1 記事 1 回。
- ブログの公開: 1 レーン 1 日 1 本。
- API の呼び出し: 書き込みは上の件数のみ。読み取り（count・コメント）は間隔を数秒空ける（公式の依頼）。User-Agent に THTH と連絡先を入れる。
- 429 や制限の応答が出たら即停止して台帳に記録（再試行しない）。
- 数値は私の案で、はてなの公式値ではない。

### 5-4. 台帳の欄
- レーン、媒体（hatena_blog / hatena_bookmark）、はてな ID、種別（draft / scheduled / published / bookmark / retract）。
- ブログ: エントリの edit URI、公開 URL、記事 id、公開（予約）日時、カテゴリ、承認した本文の雑湊、承認者と日時。
- ブックマーク: 対象 URL、comment、tags、private の有無、セルクマかネタ元か、結びつく記事の台帳 id、承認者と日時。
- 共通: 打った日時、応答の番号、取り下げの有無。count・コメントの取得結果は別の欄（取得日時つき、キャッシュだと分かるように）。
- 鍵（API キー・OAuth トークン）は `~/.config/<project>/` に置き、台帳には書かない。OAuth は scope を `read_public,write_public` あたりの必要最小にする（非公開ブックマークや下書きの操作を使うなら private 系）。ブログは read_private＋write_private が要る。

### 5-5. 先に決めること（masaru へ）
1. レーンごとのアカウントを、別のメインアカウントにするのか、サブにするのか（規約第3条・第6条3項c）。規約の読みが割れるので、はてなサポートへ確認してから作るのを推す。
2. 別 project の記事（同じ運営者）を、他レーンのアカウントでブックマークするのは避ける（上の安全側の線）。
3. ホッテントリ狙いを目標にしない（公式の記述が無く、狙った行為は禁止例に近い）。
