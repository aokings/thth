## 設計から外れた点・判断した点

1. **打てる 1 行に `--by <名前>` を足した**（B3）。設計の形は `--by` を含まないが、`report file` は誰が置いたかを必須にしている（3.1.2 の規律・`THTH_ACTOR` のような既定も無い）。名前だけ打ち足せば通る（試験で固定）。`--by` を任意にするかは判断が要る。
2. **held の区分を 4 つにした**（`approval_stale`・`reply_to_unresolved`・`stale`・`invalid`）。設計の列挙（approval_stale・target_*・型外）に加え、`stale`（stale_days 超）と、文字数超過・重複本文・未照合の中身などの要確認を `invalid` として数える——承認済みで時刻を過ぎて出られないなら理由を問わず知らせるため。publish_at が読めない原稿は「いつまでも出ない」として時刻を問わず数える。
3. **held は本番（`production: true`）で timer に載る（`scheduled`）account だけ**。rehearsal はもともと何も出さず、運用通知も黙る（既存の `incident.notify`）。
4. **運用通知の「増えたときだけ」は前回の run の本数と比べる**（最高値ではない）。直して減ったあとに新しく増えればまた知らせる。同じ run で 1 本直って 1 本増えた（本数が同じ）ときは知らせない。
5. **死活通知（Healthchecks）は held の間 `/fail` を毎回送る**。成功 ping を送ると UP に戻って「復旧」と通知され、何も送らないと「ping 未着」になるため。Healthchecks は状態が変わらない限り再通知しない（`docs/運用_停止通知.md`）。本数が増えても Healthchecks 側は再通知しない——増えたことはメール（運用通知）が言う。
6. **SMTP が使えないときは held の事象を outbox に積まない**（本数だけ記録）。送る先の無い事象が溜まって `outbox_full` で他の知らせまで止めないため。held のメールは原稿を 1 本に結ばない（`file: null`・repo に書かない）ので、本文の「repo 未反映（後続実行で再試行…）」の行は held には当てはまらない（既存の文面・直していない）。
7. **指紋の版の「1 回だけ」**は outbox に最後に数えた版を控えて比べる。初めての run（記録なし）は控えるだけで知らせない——3.3.0 を入れた最初の run では 2.8.0 の変化は知らせない。handoff／observe の「この版で再承認が要る」は栞の道具の版から判定するので、2.8.0 より前の栞を持つ account には出る。
8. **golden は指紋の先頭 16 桁**（64 桁のままだと秘密の検査 `tests/test_secrets_grep.py` の 32 桁以上の 16 進に当たる）。変化の検出には足りる。
9. **直前の断りの `reason_code` は stderr の 1 行目の先頭の英小文字＋`_` の語だけ**。日本語の断り（多くの CLI の断り）は `exit_<rc>` になる。1 行目が自己更新の注意書き等のときも `exit_<rc>`。控えるのは台帳にあり止まっていない account だけ・`report …` の断りと `auth --rehearse`（何も書かない約束）は控えない。サーバ型 MCP は credential が許した account の断りだけ。
10. **§F の段の id は `yesterday` のまま**（JSON の契約）。題だけが「前回の観測から」／「昨日の自分」に変わる。複数 account で窓が混ざるときは、1 本でも栞の窓なら題は「前回の観測から」。栞の名乗りは呼んだ名前（`observe`／`morning`）。
11. **A4 の片方だけの表記**は欠けている側を名指しする（`notification_route_partial: healthcheck` は死活通知が無い）。運用通知の「ある」は SMTP と宛先（利用者か管理者）が揃っていること。
