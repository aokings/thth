# 設計 3.15.0: 再投稿といいね（2026-09-30）

masaru の指摘（09-30）: 「再投稿や、いいね！が出来ないの？」。THTH は投稿・返信・削除と読み取りだけで、4 つの SNS のどれにも再投稿といいねの操作が無い。THTH は「SNS を調べたり投稿したり予約したりできる CLI」なので、反応（再投稿・いいね）が無いのは道具としての欠け。

**時期**: この書は設計だけ。実装とリリースは Meta の判定のあと（凍結中・審査員は提出した 6 権限の手順を試している）。

## 0. 一行

`thth repost` と `thth like`（と取り消しの `unrepost`・`unlike`）を足す。所有者か所有者のアシスタントが頼んだときだけ動き、投稿と同じくガードに数え、アクティビティに出す。SNS が口を持たない操作は `unsupported_on_platform` で断る。

## 1. 事実（2026-09-30 に一次資料で確かめた）

| SNS | 再投稿 | 再投稿の取り消し | いいね | いいねの取り消し | 必要な権限 | 根拠 |
|---|---|---|---|---|---|---|
| Threads | `POST /{threads_id}/repost` → `{"id": …}` | 文書に記載なし | **API に無い** | 無い | 文書に明記なし（`threads_content_publish` の範囲と推定・未確認） | L1: Meta 開発者文書 Reposts・Publishing reference |
| Bluesky | `com.atproto.repo.createRecord`（collection `app.bsky.feed.repost`・`subject` は strongRef＝uri＋cid） | `deleteRecord`（その記録の rkey） | 同じく `app.bsky.feed.like` | `deleteRecord` | App Password で足りる | L1: atproto の lexicon `app/bsky/feed/like.json`・`repost.json` |
| Mastodon | `POST /api/v1/statuses/:id/reblog` | `POST …/unreblog` | `POST …/favourite` | `POST …/unfavourite` | 再投稿は `write:statuses`（いま持っている）。いいねは `write:favourites`（**いま持っていない**） | L1: docs.joinmastodon.org statuses |
| X | `POST /2/users/{id}/retweets`（`tweet_id`） | 文書を未確認（`DELETE /2/users/{id}/retweets/{tweet_id}` と推定） | `POST /2/users/{id}/likes` | 未確認 | 再投稿は `tweet.write`（いま持っている）。いいねは `like.write`（**いま持っていない**） | L1: docs.x.com repost-post・like-post。料金の段ごとの可否は未確認 |

補足:

- Mastodon は非公開・DM の投稿を再投稿できない（404）。
- Bluesky は削除（`thth retract`）もまだ未対応（`DELETE_PERMISSION` が無い）。反応の取り消しと同じ `deleteRecord` なので、この版で削除も足すかは §6 の 3。
- Threads の再投稿の取り消しと、他人の投稿を再投稿できるかは、文書に書かれていない。実装の最初に試験用アカウントで確かめる（L2 にする）。

## 2. 形（薄い MCP・厚い CLI・skill で包む）

### 2.1 CLI

```
thth repost   <account> <post>      # 再投稿する
thth unrepost <account> <post>      # 再投稿を取り消す
thth like     <account> <post>      # いいねする
thth unlike   <account> <post>      # いいねを取り消す
```

- `<post>` は投稿 ID か投稿の URL。Bluesky は URL か at-uri から `getPosts` で uri と cid を引く。
- 出力は既定で 1 行（何に何をしたか・投稿の先頭 60 字・リンク）。`--json` で構造。
- 同じ投稿にもう一度頼まれたら、SNS に送らず `already_done` で答える（冪等）。取り消しで反応が無ければ `not_found`。
- 手元の台帳を使う運営者の CLI でも、承認の二段（見せる → digest）は要らない。反応は本文を作らないので、投稿の承認とは性質が違う。削除と同じ扱いにするかは §6 の 1。

### 2.2 リモート（招待のアカウント）

- `/api/v1/` に `repost_request`・`unrepost_request`・`like_request`・`unlike_request` を足す。Worker は operation の名前を正規表現で受けるので、Worker の変更は要らない。
- VM の `server_writes.WRITE_OPERATIONS` と `serve()` の振り分けに足し、`direct_retract` と同じ形（ガード → SNS に 1 回 → 記録）で実行する。

### 2.3 MCP と skill

- MCP は `thth_repost`・`thth_like`（取り消しは引数 `undo: true`）を足し、CLI を呼ぶだけ。
- skill に 1 段落: 「反応は会話への参加。所有者に頼まれたとき、または所有者が決めた方針の範囲でだけ使う。いいねで返事の代わりにしない」。

### 2.4 記録

- アカウントの状態に `reactions/` を足す。1 件 1 行（`kind`: repost/like・`post_id`・`platform_id`（SNS が返した反応の ID）・`at`・`undone_at`・`by`・`via`）。
- 取り消しは同じ行に `undone_at` を足す（`sent/` の `retracted_at` と同じ流儀）。
- 相手の投稿の本文は保存しない。先頭 60 字は表示にだけ使う。
- 退会（`thth account leave`）で消す対象に `reactions/` を足す。privacy の保存の表にも 1 行足す。

### 2.5 ガード

いまの既定は「公開 8・削除 5・10 分に 3 件で停止」。反応をこの連投停止に数えると、返信 4 件にいいねしただけで止まる。だから反応は**別の枠**にする。

- `daily_max_reactions`（既定 50）: 再投稿といいねと取り消しの合計。超えたら `reaction_limit`（翌日 0 時を添える）。
- `reaction_burst`（既定 20 件 / 10 分）: 超えたら停止（理由 `burst`）。暴走したアシスタントが一気に押し続けるのを止める。
- 夜間（`quiet_hours`）は再投稿にだけ掛ける（再投稿はフォロワーのタイムラインに出るため）。いいねには掛けない。
- アシスタントは厳しくする向きにだけ変えられる（いまと同じ）。

### 2.6 アクティビティ（thth.me/activity）

- 一覧の種類に「再投稿した / Reposted」「いいねした / Liked」と取り消しを足す（`activity.js` の `KIND_WORDS` と VM の要約 `activity.py`）。
- 今日の数に反応を足す。所有者が見て止められることは変わらない。
- Worker の画面の文言が変わるので deploy は masaru の手（1 行）。

## 3. SNS ごとの作業

1. **Threads**: `repost()` を足す。いいねは `unsupported_on_platform`（理由: 「Threads の API にいいねがありません」）。取り消しは §1 の確認次第で、無ければ `unsupported_on_platform`。
2. **Bluesky**: 4 つとも。`createRecord`・`deleteRecord`。rkey は `reactions/` の `platform_id` に保存する。
3. **Mastodon**: 再投稿と取り消しはいまの権限で。いいねは `write:favourites` を `MASTODON_SCOPES` に足し、既存のアカウントは再認可が要る。再認可まではいいねを `scope_missing` で断り、`thth auth` を案内する。
4. **X**: 再投稿はいまの権限で。いいねは `like.write` を足して再認可。料金の段でいいねが使えないときは、SNS の答えをそのまま `upstream_refused` で返す。

## 4. Meta の審査との関係

- Threads の再投稿は、提出済みの `threads_content_publish` の説明に書いていない使い方。判定のあと、実装の前に次のどちらかをする。
  1. 次の審査（または説明の更新）で「所有者が頼んだとき、選んだ投稿を再投稿する」を 1 文足す。
  2. 文書どおり別の権限が要るなら、その権限を申請する。
- どちらにするかは、実装の最初に試験用アカウントで「どの権限で通るか」を確かめてから決める（L2）。
- 判定の前には何も出さない。

## 6. 決めること（推薦つき）

1. **運営者の CLI で承認の二段を掛けるか** → 掛けない（推薦）。反応は本文を作らず、取り消せる。前提: 取り消しの口が無い Threads の再投稿だけは、取り消せないことを出力の 1 行目に出す。取り消しが無いと分かって慎重にしたいなら、Threads の再投稿だけ二段にする。
2. **ガードの既定**（反応 1 日 50・10 分に 20 で停止）→ この値で始め、使ってみて直す（推薦）。
3. **Bluesky の削除をこの版で足すか** → 足す（推薦）。反応の取り消しと同じ `deleteRecord` で、足さないと Bluesky だけ「消せない」が残る。前提: 削除には承認の二段とガード（`retract`）がそのまま掛かる。
