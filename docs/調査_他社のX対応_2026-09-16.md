## 4. 運用の実態（C の読解・開発は再確認していない）

- **AI 返信 bot の事前承認制**は 2025-10 に Automation Rules へ新設（Wayback の 2025-09 版と 2025-11 版の比較）。キーワード検索だけで自動返信する禁止は 2017 年版から。
- **Developer Agreement の AI 学習禁止**は 2025-06-04 版で追加。2026-04-27 版で学習禁止・第三者提供の条項は不変、新たに III.L・III.M（安い tier は「エンドユーザーが限られる用途」向け、超えるなら Enterprise）。**Grok の例外**は Agreement 本文ではなく制限用途ページにあり、学習だけを対象にする。
- **取り締まり**（二次資料・L3）: 2025-10 返信スパム bot 170 万を削除、2026-01 投稿に報酬を払うアプリ（InfoFi）の API を剥奪、2026-02 製品責任者 Nikita Bier が「人が画面を押していなければ凍結」と警告、2026-07 チャットボットで返信を自動化していた 4.2 万アカウントを「without a human in the loop」を理由に削除。
- **「人の承認」の扱い**: X は「人が関与しない自動化」を問題にするが、「人が承認すれば対象外」とは条文でも発言でも明言していない。
- **表示要件**: CLI や分析を除く規定なし・執行の公開事例も見つからず。
- **スクレイピング**: Bright Data 訴訟で X の請求は却下（2024）→ 和解（2025）。代わりに利用規約で違約金（100 万投稿あたり 1.5 万ドル）と、違反を助ける製品の配布の禁止。

## 5. THTH が取れる道（L3）

**唯一明示された道**: (1) 対象は**自分宛て**（メンション・引用で呼ばれた・自分の投稿への返信）だけ、(2) 返信の投稿は **API でなく X の投稿画面（Web Intent の URL を開いて本人が押す）**——`tweet.write` を求めない、(3) **他人の投稿本文を外部 LLM に送らない**（8/31）。さらに (4) 配布は利用者各自の app でなく **gotoq が 1 つの app を登録して OAuth で認可させる**（8/18）。

**それで残る価値**: 自分宛ての返信の下書きは、本文を LLM に送れないので「LLM が枝を読んで考える」ができない。**X を足したかった理由（材料として最も厚い公開の場・どこに現れるかを選ぶ・媒体をまたいで読み比べる）は、ほぼ全部この道の外にある。** 加えて (4) は Meta で見送った「薄い門」と同じ運用責任（gotoq が app の持ち主になる）を X でも負う。

**保留を解く条件の目安（L3）**: 次のどれかが起きたら見直す——(a) X が「第三者の道具が API 由来の本文を LLM の推論に渡してよい」と**文書で**示す（職員の個別回答ではなく規約か公式ガイド）、(b) 返信の技術的制限が self-serve tier で緩む、(c) 利用者各自の app を持ち込む配布が認められる、(d) gotoq が Enterprise 契約を持つ事業判断をする。

## 0. 先に結論（三つの障害より大きい「四つめ」がある）

1. **2026-02-23 から、X API で他人のスレッドに返信できない（Enterprise 以外）。** 人が承認してもこの制限は変わらない。X スタッフの告知には「元の投稿者が @メンションするか引用しない限り、API からの返信は拒否する」とある。対象は旧 Free/Basic/Pro と Pay-per-use で、Enterprise だけが外れる。**THTH の「公開スレッドを読む → 返信する」を API で送る道は、Enterprise 契約がない限り技術的に閉じている。** (L2)
2. 「AI が下書きし、人が一件ずつ承認する返信」に承認が要るかについて、**X スタッフのフォーラム回答はそろっていない**。
   - 「人がクリックしても事前の書面承認が要る」(8/17)
   - 「自分宛てに来た返信だけに一件ずつ返すなら追加の承認は不要」(8/27)
   - 同じ種類のアプリを「承認済み」とした回答もある (8/18)

   (L2。ただしどれも「正式な事前承認ではない」と断ったフォーラム回答)
3. 取ってきた投稿の本文を外部の LLM に送ることについて、X スタッフははっきり止めている。「第三者の投稿本文を外部の LLM・翻訳 API に送るな」(2026-08-31)。ただし文脈は、Web サイトに X の投稿を埋め込むウィジェットの翻訳機能。一方で X 自身が「MCP に対応した AI ツールならどれでも」投稿を取ってこられる hosted MCP を出している (2026-06-30)。(L2)

## 4. THTH への含み（L3・推論）

1. **API で返信する道は、承認より手前の技術的な制限で閉じている。** THTH が返したいのは「他人の公開スレッド」で、THTH のアカウントが呼ばれているとは限らない。これは 2026-02-23 の制限にそのまま当たる（1-1）。人が 2 段階で承認しても外れない。例外は Enterprise だけで、THTH（OSS、個人利用）には現実的でない。三つの障害を解く前に、この一点で「API で返信する」案は止まる。
2. **他社で「API で取る → 外部 LLM → 人が承認して返信」を公にしているのは Circleboom だけで、Enterprise の立場に頼っている。** しかも LLM の提供元、事前承認、表示要件のどれについても、公の説明は見当たらない。三つの障害を「解いた」と言える前例ではなく、「大きな契約の内側で黙ってやっている」例と読むのが妥当。
3. **大手は X で AI 返信を出さない方向に動いている。** Buffer は X だけ提案を止め、Hypefury は X から撤退し、Typefully は大量返信をしないと明記した。「API の制約」とだけ言い、規約の条項は名指ししていない。
4. **障害 2（第三者への提供）について、X スタッフの口頭の解釈は厳しい側に一件ある。** 「第三者の投稿本文を外部 LLM に送るな」（1-4、翻訳の文脈）。一方で X 自身が hosted MCP で、外部の AI ツールに投稿を読ませる道を公式に出している。後者は「利用者自身の権限で、利用者の AI ツールが読む」形で、THTH（利用者のローカル CLI が利用者の Claude に渡す）はこちらに近い。ただしこれを規約上の許可と読める一次資料は見つかっていない。
5. **障害 3（AI 返信ボットの承認）について、X スタッフの線引きはおおよそ次のとおり。**
   - 自分宛てに来たもの（mentions や自分の投稿への返信）に、1 件 1 返信、人が Send を押す → 承認不要 (8/27) か、承認が出た (8/18)。
   - 返信全般を API で送る → 人が押しても事前承認が要る (8/17)。
   - キーワード検索でこちらから声をかける → 不可。

   THTH が「探して返す」形なら、いちばん厳しい区分に入る。
6. **残っている道は二つで、どちらも「API で書き込まない」形。**
   - (a) web intent（`x.com/intent/tweet?in_reply_to=`）で X 公式の composer に下書きを渡し、人が X 上で投稿する。X スタッフは 8/17 に「公式の composer だけを使い、tweet.write を要求しないなら返信制限は当たらない」と答えている。ただし、同じ設計の承認を求めた 271958 には回答がない。
   - (b) 拡張機能のように、利用者のブラウザで読み、下書きを入れるだけにする（reply-guy 型）。こちらは X の利用規約（スクレイピング）の問題が別に立つ。

   (a) でも読み取りを API で行うなら、障害 1（表示要件）と障害 2（LLM への送付）はそのまま残る。
7. BYOK（利用者ごとに dev app を作らせる）は、SaaS の形では X スタッフが規約違反と答えている（1-5）。THTH の配布の形（利用者が自分の鍵で自分の CLI を動かす）が同じ扱いになるかは、判断を保留すべき論点。
8. 表示要件（障害 1）について、CLI や個人利用を例外にする公の記述や前例は、他社を調べても見つからなかった。

## 6. THTH にとっての意味（L3）

**許可の先例はあるか。** X 自身の hosted MCP が、API で取った投稿を Claude などの外部 LLM に流す形を、公式に案内している。これが最も強い「実際には許されている」先例になる。ただし次の三つの理由で、**「推論のために外部 LLM へ送ってよい」と明言した文書はない**。
1. MCP の案内には、規約・表示・AI の条件が一行もない。
2. Developer Agreement と Developer Guidelines は推論に触れていない。
3. 職員は 2026-08-31 に「第三者の投稿本文を外部 LLM に送るな」と逆のことを言っている。

二つを整合させる読み方はこうなる。hosted MCP は「利用者が自分の認証で、自分の LLM クライアントに、自分のために読ませる」形なので黙認されている。一方、**アプリが第三者の投稿を外部 LLM に送る**のは、第三者提供（III.A(d)）として扱われる。THTH は前者に近いが、Anthropic の API へ送る点は後者そのもの。

**THTH の設計に直接当たる制約**（どれも一次資料があり、推論ではない）:
- **AI の返信は、事前に書面の承認が要る。** 人の二段階の承認があっても免除されない（t/273466）。承認の例の条件は、メンションか引用がきっかけであること、1 回の関わりに 1 返信、元の投稿への返信、公式 API、自動化の明示（t/273526）。申請先はフォーラムで、SLA はない。
- **セルフサーブの tier では、呼ばれていない返信は API が拒否する**（2026-02-23 から）。「公開のスレッドを読んで返信する」という THTH の中心の流れは、X では、メンションか引用で呼ばれた場合か Enterprise でないと、技術的に成り立たない。
- **配布の形**: 「各自が自分の Developer App を作って動かす完成品のキット」は不可と答えられている（t/273564）。THTH を OSS として配るなら、一つの app を登録して OAuth で認可させる形が求められる。そうすると、表示要件と第三者提供の責任を THTH 側が負う（ただし X 自身の xurl／MCP も「自分の app」を求めており、食い違いがある）。
- **表示**: 職員の運用では、投稿の要約や抜き出しを X の外へ出すことも再配布にあたる（t/274395）。CLI で本文を加工して見せることは、厳しく読まれる可能性が高い。

**結論**: X 自身の MCP は「LLM が X を読む」ことを事実上許している。しかし、THTH の形（他人の投稿を外部 LLM に渡し、AI の返信を API で投稿する）について、X が**条件付きで許可すると明言した文書の先例はない**。書面の承認を得て、許可された条件（呼ばれたときだけ・1 回・明示）に絞るのが、唯一の明示された道になる。

- 2025-11-25 のスナップショットは「Updated October 2025」で、**「3. AI-Powered Automated Replies」が新設されている**。
  > "the deployment or operation of any AI reply bot requires prior written and explicit approval from X. Contact your dedicated point of contact or submit a request through the developer portal for review."
- 2026-04-23 のスナップショットは「Updated April 2026」。差分は「Automated likes」が「Automated likes **or hide replies**」になった 1 か所だけ。
- 2017 年版から変わらない規則:
  - "sending automated replies to posts based on keyword searches alone is not permitted."
  - 自動返信が許されるのは、相手が事前にオプトインした場合（返信や DM で連絡を求めた、など）。
  - OAuth で連携しただけでは、自動操作への同意にならない。
  - "Use non-API-based forms of automation, such as scripting the X website" は永久凍結の対象になりうる。

### 2-2. 承認の手続きの実態
- **申請フォームは見つからなかった（L3）**。devcommunity の「Rules and Policies」カテゴリに「Approval request: AI-powered reply bot …」という題のスレッドが 2026 年に多数ある。例:
  - https://devcommunity.x.com/t/how-do-i-get-ai-bot-account-approval/264768
  - https://devcommunity.x.com/t/approval-request-ai-assisted-reply-drafts-for-juliansdev-app-id-33296798/273202
  - https://devcommunity.x.com/t/approval-request-ai-powered-mention-triggered-fact-check-reply-bot-isthisbs/270834
- 検索の抜粋によると、開発者たちは「2026-05 時点で開発者ポータルに提出フォームが見当たらない」ためフォーラムに書き込んでいる。
- **承認や却下が公表された例は、確認できた範囲では 0 件**。スレッド本文が読めないため「X の担当者が返答していない」とまでは言えない（未確認）。
- 注目点: 題名に "AI-assisted reply drafts"（人が確認する下書き型）を掲げた申請もある。つまり、下書き型でも承認が要るのではと考える開発者がいる（L3）。

## 3. 「人が間に入る」かどうかの区別

- **書かれた規則（L2）**: Automation Rules に「人が承認すれば自動ではない」とする定義は**無い**。スケジューラ（予約投稿ツール）への言及も無い。
- ただし、判断の手がかりになる文言はある。
  - Automation Rules: "Automated activity should honor users' expectations. Ask for the user's permission before taking an action if you aren't sure."
  - Developer Policy: "non-automated means" による少量の配布は許す、という区別がある（https://docs.x.com/developer-terms/policy ）。
  - このように「自動か否か」は条文の中で区別されているが、定義はされていない。
- **X 側の発言（L3）**: Bier の "without a human in the loop"（2026-07-24）や "a human is not tapping on the screen"（2026-02-14）は、**人が操作していない自動化**を問題にしている。「人が関与していれば可」とまでは明言していない。
- **二次資料の解釈（L3。X の公式見解ではない）**:
  - https://startupfortune.com/x-removes-42000-ai-reply-bot-accounts-and-the-warning-to-growth-marketers-is-impossible-to-ignore/ は「人が承認する AI 支援は許容、無人の大量返信は禁止」と整理している。
  - https://fireply.ai/blog/x-api-reply-restriction-2026 によると、Buffer や Typefully などのスケジューラは自分の投稿の予約は続けられたが、他人の投稿に返信する機能は 2026-02-23 以降止まった。「a human clicks Post」型の下書きツールは影響を受けない、とも書いている。
- **矛盾する事情（L3）**: X 自身は投稿画面から Grok に下書きさせる機能を推している（https://almcorp.com/blog/x-ai-bot-crackdown-grok-human-only-rules/ ）。「人が見て押す AI 下書き」そのものを禁じているとは読みにくい。

## 4. 表示要件はどこまで執行されているか

- **書かれた規則（L2）**: https://docs.x.com/developer-terms/display-requirements
  > "The following general principles apply to all display mediums."
  - 求められるのは、アイコン・@username・表示名とそのリンク、本文を改変しないこと、タイムスタンプ、X のロゴなど。
  - 媒体別の規定は「オンライン」「放送」「音声（Verbal or voice over）」の 3 つだけ。音声で読み上げる場合はロゴ不要で、「X の投稿だ」と口頭で示せばよい。
  - **CLI・テキストのみ・分析・社内利用を除外する FAQ は無い**。
  - 守れない場合は "contact us directly via our Policy Support form before displaying X content" と書かれている。
- 分析については、Restricted use cases に "Aggregate analysis of X content that does not store any personal data … is permitted" とある（L2）。ただしこれは**表示要件の除外ではない**。
- **執行の実例**: CLI・分析・社内表示に対して表示要件が執行された公開事例は**見つからなかった**。「無い」とは言えず、「見つからない」にとどまる。
- 実際に強く執行されたのは、スクレイピング・返信スパム・InfoFi・iframe 埋め込み（条項の新設）の側である（§2・§6）。

## 5. Pay-Per-Use と AI 用途

- **L2**: 料金ページ（https://docs.x.com/x-api/getting-started/pricing ）に、AI や LLM の用途を制限する文言は無い。
  - 月あたり 300 万 Post 読み取りの上限がある。
  - 逆に「xAI API クレジットの最大 20% 還元」が書かれている。
- **L2**: 2026-04-27 改定の III.L・III.M により、Pay-Per-Use は「エンドユーザーが限られるアプリ」「試作」向けと位置づけられ、それを超えるなら Enterprise に移る義務がある。
- **用途説明（use case description）で AI の使用を尋ねる設問**: 実物は確認できなかった（開発者ポータルはログインが必要。検索でも見つからない）。
  - Developer Agreement で「use case を審査に出す」と書かれているのは、政府系の利用者の節（XIV.C）だけ（L2）。
  - Developer Policy は「use case」を "a consistent set of analyses, displays, or actions performed via an application" と定義し、同じ用途でアプリを複数登録することを禁じている（L2）。

## 6. スクレイピングとブラウザ拡張による代替

- **L2（利用規約 2026-10-09 版）**: 公開インターフェース以外からのアクセスを禁止し、事前の書面同意なしのクローリング・スクレイピングを禁止している。
  - "facilitate or assist others in violating these Terms, including by distributing products or services that enable or encourage violation" も違反と明記。**拡張機能やツールを配布する側も対象になりうる**。
  - 違約金は 100 万投稿あたり 15,000 ドル。
- **L2（Automation Rules）**: X のウェブサイトをスクリプトで操作する自動化は、永久凍結の対象になりうる。
- **X Corp. v. Bright Data（L3）**:
  - 2024-05-09: N.D. Cal.（Alsup 判事）が、公開データのスクレイピングを契約違反とする X の請求を、著作権法による先占を理由に却下した（https://www.skadden.com/insights/publications/2024/05/district-court-adopts-broad-view ）。
  - 2025-06: 和解。条件は非公開で、Bright Data は「サービスを続ける」と表明した（https://news.bloomberglaw.com/ip-law/musks-x-settles-data-scraping-dispute-against-israeli-data-firm ）。
  - **法廷では X が負け筋、和解後は規約と技術的な検知で締める**、という構図。
- **L3**: 2026-02 のボット検知強化では、AI エージェントによる検索負荷も理由に挙げられている（https://techweez.com/2026/09/03/x-ai-generated-bot-replies/ ほか）。ブラウザ自動操作型の返信ツールは、アカウント凍結の直接の対象と見るべき。

## THTH にとっての意味（すべて L3＝推論）

**(a) API で読み、LLM で推論する**
- **学習ではない**ので III.A(k) には当たらない、と読むのが自然。
- 論点は III.A(d) の「第三者への提供」。投稿本文を推論 API（Anthropic）に送ることが「provide access … to any third party」にあたるかは、条文からも運用の実例からも決められない。
- この点で X が開発者を処分した公開事例は見つからなかった。取り締まりはスパム・スクレイピング・InfoFi に集中している。
- **現実のリスクは低〜中**。ただし、書面での明示的な許可は無い。
- 規模の面では、III.L により Pay-Per-Use は「エンドユーザーが限られる」用途に限られる。OSS として多数の人に配ると、この枠を超えうる。

**(b) 人が承認した返信を投稿する**
- **最大の障害は規約の解釈より技術的な制限**。2026-02-23 以降、Self-Serve の API では「元の投稿者が呼んだ場合」しか返信できない（L2 で確認済み）。
- THTH の「公開スレッドを読んで返信する」使い方は、**API 経由ではほぼ成立しない**。
- AI 返信ボットの事前承認制（2025-10〜）は、条文上「AI reply bot の運用」に適用される。X は「人が承認すれば対象外」とは明言していない。承認の窓口も実態が不透明。
- X 幹部の発言が問題視しているのは「human in the loop が無い」自動化。2 段階の人間承認は、その**精神には沿う**。
- 取れる手段は二つ。
  - 投稿を API ではなく **Web Intent（x.com/intent/post の返信用 URL）で人が自分で開いて押す**方式にする。API による自動化から外れ、Bier の言う「人が画面を押す」に近づく。ただし、この方式を X が公式に是認した文書は無い。
  - API で投稿するなら、事前承認を申請する。

**(c) CLI での表示**
- 表示要件は "all display mediums" に適用されるが、CLI・テキスト向けの規定も除外規定も無い。執行された事例も見つからない。
- 規約の規定例のうち最も近いのは「音声」で、ロゴは求めず出典を示すだけでよい。これに倣い、CLI でも最低限次を出すのが防御的。
  - @username
  - 表示名
  - 改変しない本文
  - タイムスタンプ
  - 投稿の permalink（「View on X」相当）
  - X の投稿であることの明示
- 懸念が残るなら Policy Support フォームで照会する（規約自身がそう案内している）。

**慎重な開発者ならこうする**
1. 最初は「読む＋下書き」だけにし、投稿は Web Intent で人が X の画面上で押す。API での返信投稿は実装しない。
2. アプリの用途説明を正確に書く。例: 「利用者本人が選んだ公開スレッドを読み、LLM で返信の下書きを作る。学習には使わない。投稿は利用者本人が確認して手で行う。自動返信・キーワード検索による返信は行わない」。**学習をしないこと、自動返信をしないこと**を明記する。
3. API での返信投稿を将来入れるなら、Automation Rules の案内どおり開発者ポータルか担当者経由で書面の承認を求める。承認前は出荷しない。フォーラムに申請が滞留していることを踏まえ、承認は期待しない前提で設計する。
4. LLM への送信について、III.A(d) との関係を Policy Support に照会する。回答が得られなければ、送る本文を最小限にし、保存しない。
5. スクレイピングやブラウザ自動操作（拡張機能を含む）は使わない。凍結・違約金・「配布した側の違反」条項があり、THTH の配布者自身がリスクを負う。
6. 配布規模が「限られたエンドユーザー」を超えそうなら、III.L・M に照らして Enterprise が必要になりうることを README に書く。
