## 設計から外れた点・設計に書いていなかったので決めた点

1. **媒体は Threads だけ**。設計 §0 は「（と Bluesky・Mastodon）」と書いていますが、Bluesky は App Password を本人が打つ形で、招待のページに通すと秘密が Worker を通ります。Mastodon は本人の instance が要ります。`--media` にほかを渡すと `invite_media_unsupported` と次の一手（従前の `account add`・`auth`）で断ります。
2. **承認 secret は Worker が完了ページで作ります**（VM は作らず見ない）。VM が作って Worker に渡すと、secret が Worker の保存を通るためです。`ApprovalPerson.provision` が verifier だけを置き、既存の承認者（運営者の `approver set`・失効・別の招待の人）は上書きしません。承認ページの人（person）は**口座名**です。
3. **口座の枠は名前だけ先に決めます**（create のとき `inv-<project>-<6 桁>`）。台帳と token は認可が済んでから O_EXCL で書きます。認可が途中で終わっても、口座の抜け殻を残さないためです。書いたあとで常駐が止まっても、次の巡で台帳から続けます。
4. **「ページが認可 URL へ進む」は、新しいタブで開くリンクにしました**。同じタブで Threads へ移ると、戻り（`/callback/`）から招待のページへ戻る道がありません（戻りは code を知らない）。準備中・認可中は meta refresh で再読込し、招待の認可から戻ったときの `/callback/` は「最初のタブに戻ってください」と言います（預かり所に招待の印を付ける）。従来の `thth auth` の戻りの言葉は変えていません。
5. **招待が求める権限は既定から `threads_share_to_instagram` を外した 10 個**です（計画の「外すもの」）。ページはこの一覧をそのまま見せます（VM が create で送る）。
6. **運用通知は、常駐が戻って押された招待を拾ったとき**に 1 回（`invite_stalled`）。Worker からはメールを送れず、常駐が止まっている間は誰も送れません。止まった VM そのものは外部の死活監視の役目のままです。
7. **招待 URL は tty に出します**（`approver set` と同じ）。stdout に出すと LLM が打つ命令の出力に載るためです。tty が無ければ code を作る前に断ります。
8. **口座の用意が済んだ招待は取り消しません**（Worker は `ready`・`done` で 409、VM は `invite_already_used`）。止めるのは `thth account leave` です。
9. 招待のページは日本語の下に英語を 1 行ずつ添えました（審査員が読むため）。承認ページも裁定 2 で同じ作りにしました（第6段）。
10. token の `auth_via` は `relay`（預かり所を通ったのは事実なので doctor の既存の値に合わせる）。変更ログの `account_added`・`token_set` に `via_invite` を足しました。`approver_set` は via `http`（変わったのはブラウザのページ）。

## 裁定のあとに残る点（判断ではなく、知っておいてほしいこと）

- 自動で足す資格情報の bearer は誰も持っていません。承認 job を作る口（MCP・HTTP）は bearer を出した資格情報の文脈でしか動かないので、**この 1 件だけでは、運営者の手を挟まずに承認 URL を出すことはできません**。MCP で使うときは、裁定のとおり運営者が既存の手順で bearer を入れ直します（その 1 件の `sha256` を差し替え、起動口に値を置く）。審査の間に運営者の手を 0 回にするには、bearer を VM の 0600 のファイルに置くか、資格情報を使わずに運営者の CLI から承認を求める口が要ります。どちらも今回は作っていません。
