相談が上がらなかった訳（仕組みを読んでの見立て）:

- `thth analytics-report` は、わざと原因と推奨を出さない。これはこのままでよい（判断は利用者の LLM がする）
- ただ、週の結果を前と比べて「落ちた」と言う所が、どこにも無い。担当は承認済みの原稿を何週も先まで並べて出す流れで、本数は見ても結果を見ない
- hub の見張りは止まったセッションを見るもので、結果の落ち込みは見ない

## 頼みたいこと

### 1. 週の材料を 1 回で渡す口（THTH の命令）

例 `thth review weekly <口座|project> [--week YYYY-MM-DD] [--json]`。今ある `analytics-report`（`--compare-previous`・`--weekly-goals`・`--by`）と `study-report` を束ねる。原因と推奨は今と同じく出さない。材料は次のとおり。

- 週の合計と、前の 2〜4 週との並び: 本数（根・返信・他の人への返信）・表示・いいね・返信・拡散・フォロワーの増え・クリック（取れる媒体だけ）
- 1 本あたりの 24 時間の中央値と最大。「その週の当たり（上位 5 本）」と「外れ（下位 5 本）」の原稿のファイル名・型（topic・goal・時刻帯・リンクの有無・添付）・数
- 層別（型・時刻帯・リンクの有無・goal）の、今週と前の週の中央値
- **落ち込みの印**: 週の表示かフォロワーの増えが、前の 2 週の平均の半分を切ったら `drop: true` と、どの数がどれだけ下がったか。2 週続いたら `drop_streak: 2`
- 先週の宣言（下の 2 の study）があれば、その `study-report` の結果を同じ束に入れる
- 欠測・未成熟（24 時間に満たない投稿）は 0 と数えず、別に並べる（今の決まりのまま）

### 2. 「次の週に何を変えるか」を記録する口

`study add` がある。週の振り返りで決めた 1 つの変更を、仮説・変更・対象の期間で宣言できればよい。今の入力は投稿の id の列なので、「この日からこの型を変えた」を期間で書けるとよい（無理なら今の形のままでよい）。

### 3. skill（回し方）

THTH の skills に 1 つ（例 `skills/thth-weekly-review`）。各プロジェクトの SNS の担当（こぴちゃ・関東・染めと化学など。外の利用者も）が毎週読む。

- **P（計画）**: 先週決めた変更を読む（study）
- **D（実行）**: その週の原稿に変更が入っているかを、queue の原稿で確かめる
- **C（確かめ）**: `thth review weekly` の材料を読み、当たり・外れ・落ち込みの印を見る
- **A（次の手）**: 次の週に変える所を 1 つだけ決め、`study add` で宣言する。判断の根拠の数字を 1〜3 行添える
- 落ち込みの印が立ったら、その週のうちに本線へ伝える（自分の判断で直せない「本数・型を大きく変える」は本線と masaru へ）
- 結果の 1 行を hub に送る

### 4. 起こし（h2d・THTH の外）

毎週月曜の朝に h2d が `thth review weekly` を口座ごとに打ち、各担当を起こす。`drop: true` の口座は本線も起こす。これは THTH の命令ができたあと、THTH運用 が H2D に頼む。

## できあがりの条件

- 1 の命令が、関東・こぴちゃの今の数字で「11/16 の週は drop: true」を出す（上の表の値と照らせる）
- 欠測と未成熟が 0 に混ざらない試験がある
- 3 の skill を読んだ LLM が、材料から次の週の変更を 1 つ決めて `study add` まで打てる

## 決まり

- THTH運用 は THTH のコードを直さない（この依頼で渡す）
- 順番と版の切り方は開発に任せる（release はまとめて・masaru 11/13）
