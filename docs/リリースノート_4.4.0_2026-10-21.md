# リリースノート 4.4.0（会話の続く投稿は 20 分おきに返信を取り直す）

2026-10-21。kopicha の依頼「SNS の返信が付いてから起こしまでの遅れ」（10/21 朝 kopicha-threads で約 2 時間半）への直し。設計は [設計 4.4.0 会話の続く投稿の取り直し](設計_4.4.0_会話の続く投稿の取り直し_2026-10-21.md)。

## 起きていたこと

返信は投稿から 1・6・24・72・168 時間の刻みでしか採っていなかったので、刻みの間に付いた返信は次の刻みまで台帳に入らず、台帳の「返していない返信の数」を読む h2d の起こしも遅れていました。

## 変わったこと

- **timer（`thth run`）の採取で、会話が続いている投稿だけ、前の取得から 20 分たったら会話を取り直します。** 会話が続いている＝投稿から 48 時間以内、または直近 48 時間に返信（他人の返信か自分の返信）が付いた投稿です。新しく見つけた返信は台帳に入り、`thth unanswered`・`thth observe` の数にそのまま効きます。手で打つ `thth collect` でも同じです。
- **刻みと数の記録は変わりません。** 取り直しは `thth replies --refresh` と同じ性質で、刻みを進めず（取得の行は `marks: []`・`trigger: "follow"`）、数（表示・いいねなど）を読みません。1h・6h・24h の数はこれまでどおり刻みで採ります。
- **1 回の run で取り直すのは最大 10 本**で、いちばん新しい動きの順に選びます。その回に刻みで取る投稿は取り直しません。
- **取り直しの失敗で採取の終了コードも投稿の道も悪くしません。** 理由は log に 1 行出し、次の回（10 分後）にまた取りに行きます。
- **数字は口座ごとに台帳で変えられます**: `"reply_follow": {"enabled": true, "every_minutes": 20, "live_hours": 48, "max_posts": 10}`（どれも省略できる・範囲外は台帳の読み込みで `invalid_reply_follow` と断ります）。
- **X は既定で外します。** X の枝の読み取りは 1 本 0.005 USD の従量で回数の上限も厳しく、20 分おきに読むと 1 本の投稿の 48 時間で 144 回になるためです。台帳で `"reply_follow": {"enabled": true}` と明示したときだけ、THTH から出した自分の投稿に限り 1 回 10 本で読みます（読みの予算の中だけ）。

## 変わらないもの

承認の指紋・投稿の道・刻みの数の記録・返信の台帳の形（取得の行の `trigger` に `follow` という値が増えただけ）。

## webhook の口

Threads には返信の webhook（`replies`）があります。使うには `threads_read_replies` の App Review と Advanced Access、事業者の確認、公開の受け口（thth.me の Worker）が要ります。Mastodon の webhook はサーバー管理者向けで、Bluesky には webhook が無く常時つなぐ流れ（firehose／Jetstream）だけです。4.4.0 はポーリングだけを作りました（詳細は設計の文書）。

## thth.me（Worker）

**Worker の deploy は要りません。** 変わったのは VM の Python だけです。

## 確かめた範囲

試験（偽物の媒体と時刻の注入・`tests/test_v440_reply_follow.py` 18 件）と、柵を 11 か所 1 つずつ壊して赤を見たこと（設計の文書に表）。本番の媒体ではまだ確かめていません。Threads の 1 回の run で増える呼び出しは最大 10 本（口座ごと）です。
