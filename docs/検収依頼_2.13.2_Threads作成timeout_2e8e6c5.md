## 0. 所見（実機 2026-09-22・masaru-threads）

`thth send … --media docs/media/photo.jpg` の container 作成（`POST /{user}/threads` に `image_url`）が `media_creating_failed` で落ちました。journal は phase `unknown`・`remote_ids=[]`。

この POST は**こちらとの往復ではありません**。Meta はこの POST を開いたまま `thth.me`/R2 から画像を**同期で取りに行き**、取り込みが終わってから id を返します。`thth/adapters/threads_media.py` の `_json` は全部の呼び出しに `adapter.timeout`（`thth/adapters/threads.py` の `DEFAULT_TIMEOUT_SECONDS = 10.0`）を渡していました。2.13.0 の同じ経路・同じ添付は通っていたので、壊れたのは**形ではなく時間**——揺れているのは Meta の取り込みで、10 秒がこちらの見積もり違いです。Meta 自身の文書も、媒体の処理は画像で最大 1 分・動画はさらに長いと書いています。

その落ち方が残す inflight を、そのあと人が最初に見るのが `thth send` です。そこが黙っていたので、あわせて直しました（4）。

## 2. 項目ごと（実装・試験・変異）

### 1 — 作成だけ専用の socket 期限（`7eaf91d`）

**実装**（`thth/adapters/threads_media.py`）。

- `CREATE_TIMEOUT_SECONDS = 90.0`。環境変数 `THTH_THREADS_CREATE_TIMEOUT_SECONDS` で上書きでき、**[10, 600] に丸めます**。読めない値・有限でない値（`''`・`abc`・`inf`・`nan`）は既定に戻します——この上書きは遅い日に窓を広げるためのもので、送信を止めるためのものではありません。
- `_json(..., socket_timeout=…)` を足しました。`socket_timeout` は adapter の数字を**置き換え**（作成）、既存の `timeout` は**どちらの数字も狭めるだけ**（poll が自分の残り時間を渡す既存の使い方）。作成は IMAGE / VIDEO の item と CAROUSEL の親の 3 か所。**TEXT container（typed attachment）は媒体の取り込みが無いので `adapter.timeout` のままです。**
- 状態の問い合わせ（poll）と公開（`threads_publish`）は `adapter.timeout` のまま。あれは普通の往復です。
- **待ちの期限は作成を始めた時刻から数えます**（`wait(..., since=…)`）。画像 120 秒（`POLL_SECONDS`）・動画 1800 秒（`VIDEO_POLL_SECONDS`）は変えていません。作成に 40 秒使えば問い合わせに残るのは 80 秒。**付与の期限（画像 600 秒・動画 1800 秒）は 1 秒も延ばしていません**——`veto()` と `wait()` の中の付与期限の比較は 1 文字も変えていません。

**試験**（`tests/test_v2132_threads_create_timeout.py`・偽 Graph は既存の `tests/test_v213_threads_media.py` の `wire`）:

1. `test_a_creation_slower_than_the_adapter_timeout_still_lands` — `adapter.timeout = 0.3` のまま作成だけ 1.0 秒眠る偽 Graph で、公開まで通って journal が `published` になること（2.13.1 ではここで落ちます）。
2. `test_only_the_creation_gets_the_long_budget` — socket に渡った秒数を数えて、作成の POST だけが 90 秒、GET と `threads_publish` は `adapter.timeout` のままであること。
3. `test_the_override_is_read_and_clamped`（14 例）— 未設定 90、`120`→120、`9`/`0`/`-5`→10、`601`/`86400`→600、`''`/`abc`/`inf`/`nan`→90。
4. `test_the_override_reaches_the_creation_socket` — `THTH_THREADS_CREATE_TIMEOUT_SECONDS=900` が丸められて 600 秒として**実際に socket に届く**こと。
5. `test_the_poll_deadline_counts_the_time_the_creation_took` — 固定時計。作成が 40 秒かかると、問い合わせは 8 回で fake 時刻 120 秒ちょうどに `media_processing_timeout` になること（作成を数えなければ 160 秒・12 回）。公開は 0 回、付与は引き上げ済み。

**変異。** (a) 作成の `socket_timeout=create_timeout()` を外す → 1。(b) `wait(..., since=since)` の `since` を外す → 1。(c) `min(max(value,…),…)` の丸めを外す → 1。

### 2 — 作成の時間切れは「出ていない」ではない（`8a1bb22`）

**裁定。** 作成で socket が時間切れになったとき、**container ができたかどうかは分かりません**。Meta は POST を開いたまま媒体を取りに行くので、こちらが諦めたあとに向こうで作成が終わっていることがあります。phase は `unknown` のまま（そこは変えていません）。しかし理由が generic な `media_creating_failed` のままだと、運用は「出ていない・作り直してよい」と読みます。同じ添付の container が二重に残ります。

**実装。**

- `socket_timed_out(error)`: 接続の時間切れは `urllib` が `URLError` に包み、読み取りの時間切れは裸の `TimeoutError` で来るので両方を見ます。`HTTPError` は遅くても「答え」なので時間切れではありません。**provider の文面は 1 文字も読みません。**
- 作成の phase（`creating` / `creating_carousel`）の socket 時間切れだけ、理由を `media_creating_timeout` / `media_creating_carousel_timeout` にします。他の OSError / URLError は `media_creating_failed` のまま。held / unknown / definite の区分と、付与を引き上げるかどうかの判断は 1 文字も変えていません（作成の phase は `held` に入らないので、**付与は引き上げません**——引き上げれば向こうにできた container が確実に死にます）。
- `media_delivery.MEDIA_NEXT_STEPS` に次の一歩を 1 行（両方の理由に同じ文）: 「媒体が画像/動画を取り込むのに時間がかかっています。しばらくして inflight を確認し、投稿が無ければ消してから再実行」。既存の規律どおり**静的**で、入力値・ファイル名・パスを 1 つも反射しません。

**試験**（`tests/test_v2132_threads_create_unknown.py`）:

1. `test_only_a_socket_timeout_counts_as_one`（5 例）— 裸の `TimeoutError`・`URLError(TimeoutError)` は真、`URLError(ConnectionResetError)`・素の `OSError`・`HTTPError(408)` は偽。
2. `test_a_creation_that_never_answers_is_unknown_and_named_as_a_timeout` — 答えない偽 Graph で `media_creating_timeout`・`media_ambiguous`・journal `unknown`・`remote_ids == []`・`threads_publish` 0 回・**付与の引き上げ 0 回**・次の一歩が出ること。
3. `test_the_carousel_parent_timeout_is_named_the_same_way` — 2 枚の item は通り、CAROUSEL の親だけ答えない場合に `media_creating_carousel_timeout`・journal `unknown`・`remote_ids == ['11','12']`。
4. `test_other_creation_failures_keep_the_generic_reason` — 作成で `URLError(ConnectionResetError)` なら `media_creating_failed` のままで、次の一歩は付かないこと。
5. `test_a_slow_poll_is_not_a_creation_timeout` — 問い合わせの時間切れは従来どおり `media_processing_failed` ／ `media_held`。

**変異。** (d) `'_timeout' if timed_out else '_failed'` を `'_failed'` に戻す → 1。(e) `timed_out` から phase の限定を外す（どの phase でも timeout と名指す）→ 1。

### 4 — inflight が残っていれば `send` は dry-run でも断る（`2e8e6c5`）

**所見（実際に確かめたこと）。** `state/alpha/inflight.json` に phase `unknown`・`reason: media_creating_timeout` の journal を置いて `thth send alpha --media a.png --alt 説明` を打つと、2.13.1 では:

- `--production` なし → inflight を**一度も読まず**、本文の下見と digest まで出して **0** で終わる。残っていることを一言も言わない。
- `--production` あり → **1** で止まり `inflight が残っています: (send)` の 1 行だけ。どうすればいいかは言わない。

不在の様態（`core._throw_locked`）は最初から様態に関わらず断っています。同席の様態（`core._send_locked`）だけが `if production_flag` の中で読んでいました。

**実装。**

- `core._send_locked` の inflight の検査を `production_flag` から外しました。dry-run でも断ります（exit 1）。
- `inflight.NEXT_STEP`（静的な 1 行・アカウント名もパスも値も埋めない）:
  「次の一歩: 前回の結果が分かっていません。媒体の画面で出たかどうかを確かめ、出ていれば記録してから、出ていなければ state/<アカウント>/inflight.json を消してからもう一度（確かめずに消さない）」
- `cli.cmd_send` が inflight で止まったときにこれを stderr に出します。媒体の理由が既に具体的な次の一歩を持っているとき（`media_creating_timeout` 等）は重ねません（次の一歩は常に 1 行）。

**試験**（`tests/test_v2132_send_inflight_hint.py`）:

1. `test_send_refuses_and_says_what_to_do`（dry-run と `--production` の 2 例）— どちらも 1 で止まり、`inflight が残っています` と `NEXT_STEP` の両方が出て、`digest: ` は出ず、媒体への呼び出しと upload が 0 件で、`次の一歩` で始まる行がちょうど 1 行であること。
2. `test_the_refusal_stays_static` — 出力に repo の実パスも state の実パスも映らないこと。
3. `test_the_inflight_is_left_exactly_as_it_was` — dry-run も `--production` も journal を 1 byte も変えないこと。
4. `test_without_an_inflight_the_dry_run_still_shows_the_digest` — inflight が無ければ従来どおり digest が出て、この案内は出ないこと。

**変異。** (f) dry-run の gate を `if production_flag` に戻す → 1。(g) `NEXT_STEP` を足す行を消す → 1。

**masaru に諮ること。** dry-run が 0 → 1 になるのは**様態の変更**です。inflight が残ったまま digest を出すのは「見せたものが出せない」形（2.13.1 の 3 と同じ理由）なので断る方を採りましたが、`thth send` の dry-run を script から 0 前提で呼んでいる運用があるなら言ってください。戻します。

## 3. 限界（断定していないこと）

- **実機の `media_creating_failed` が本当に socket の時間切れだったかは、記録からは断定できません。** 2.13.1 の理由は時間切れも接続断も同じ `media_creating_failed` に畳んでいたからです。この直しは「10 秒は作成には短い」という見立てに基づくもので、次に同じことが起きたときに `media_creating_timeout` として見分けられるようにするものでもあります。
- 90 秒・[10, 600] は**観測された API の数字ではありません**。Meta の文書の言い方（画像で最大 1 分、動画はもっと）から置いた暫定の裁定です。実機で足りなければ環境変数で広げられます。
- 実 Graph・実 token での作成時間は測っていません。試験は隔離したローカル HTTP fixture だけです。
