# リリースノート 4.0.0（記事をはてなへ届けて、直したら反映する）

2026-10-17。[計画_4.0](計画_4.0_2026-10-15.md) の S1〜S6。本物のはてなで確かめた結果は [記録_はてなの実機の確かめ](記録_はてなの実機の確かめ_2026-10-17.md)。

4.0 は「記事を書いたら各媒体へ届け、直したら反映できる」版。利用者の repo にある記事を、承認してはてなブログへ出し、SNS の告知とはてなブックマークをその記事に結び、記事を直したら差分を承認して出した先を更新し、反応を記事ごとに読み返せる。記事の正本は利用者の repo のままで、THTH は承認した配信原稿と配信の記録だけを持つ。

## はてなの口座の作り（S1）

- **主体（はてな ID）と口座を分けた。** 主体の台帳 `$THTH_ROOT/principals/<主体>.json`（`thth principal add`）に、はてな ID・使えるブログとレーンを書く。口座は `thth account add <口座> --media hatenablog --principal <主体> --blog <blog_id>` で主体のブログに結ぶ。メイン 1 つ＋レーンごとのサブアカウントの形を前提にしている。
- **別のブログへの誤送信を 3 か所で止める**: 主体に無いブログ（`blog_unknown`）・レーンに許していないブログ（`blog_not_allowed_for_lane`）・台帳を手で書き換えたとき（読み込みで `blog_unknown`・何も送らない）。
- **止めと上限は口座・ブログ・主体の 3 段。** 1 つの主体が止まれば、その主体のすべてのブログとブックマークが止まる。`thth principal show`・`set`・`resume`。
- **配信の台帳** `state/<口座>/deliveries/dl_….json`: 1 本の記事を 1 つのブログに出す 1 件ごとに、`wanted → inflight → published` などの状態と、出した URL・`entry_id`・読み戻した本文の指紋を持つ。`thth deliveries <口座|project> [--article <記事>]` で読む。結果が分からない（`unknown`）ときは失敗とみなして出し直さない（SNS の inflight と同じ考え）。
- **はてなの承認は SNS と別の指紋**（`thth-hatena-entry-1`）。変換したあとの本文・画像・ブログ・新規か更新か・題・カテゴリが入る。1 段目に行き先・操作・記事・題・画像・本文の全文を出す。

## はてなブログ（S2）

- **認可**: `thth principal auth <主体> --by <名前>`（OAuth 1.0a・端末から打つ）。consumer は伏せ字で入れ、token は `~/.config/thth/<主体>.token`（0600）。認可の画面ではてな ID を照合し、違う ID なら書かない。サブアカウントも、メインで登録した 1 つの OAuth アプリで認可できた。
- **公開・予約・更新・削除**: 記事（Markdown）を配信原稿にして `thth approve`（2 段）→ timer が出す。予約ははてな側の予約を使わず、THTH の timer が時刻に公開を送る（予約の台帳は THTH の 1 か所）。
- **変換**: 記事の相対リンクは口座の `link_base` で絶対 URL にする（無ければ相対リンクのある記事は `relative_link_unresolvable` で断る）。commit していない記事は `article_not_committed` で断る。
- **出られない配信原稿**は `thth events` に `delivery_held`（承認が古い・台帳が人待ちなど）として出る。
- `thth send` ははてなの口座には使えない（`unsupported_operation`）。はてなは承認して timer が出す道だけ。

## フォトライフ（S3）

- 記事の画像は**公開の直前に**はてなフォトライフへ上げ、本文の画像を `[f:id:…:image]` に置き換える。同じ画像は使い回す（上げ直さない）。`thth fotolife <主体>` で台帳を読む。
- 画像の形式・容量・枚数は lint で断る（`image_type_unsupported`・`image_too_large`・`too_many_images`・`images_too_large`）。
- **気をつけること**: 公開範囲が「自分のみ」のブログでも、上げた画像の URL はログインなしで読めた（実機の 15'）。下書きや限定公開の記事に画像を使うレーンは、URL を知る人には画像が見えると思っておく。

## 告知とブックマーク（S4）

- **SNS の告知を記事に結ぶ**: SNS の原稿の front matter に `announces: <配信 id>` を書き、本文に `{article_url}` を置く。timer は記事が `published` になるまで待ち（held には数えない）、公開した URL に置き換えて出す。記事が `conflict`・`deleted` などなら出さずに held（`announces_unresolved`）。文字数は仮の URL で数え、本物の URL で上限を越えれば出さない。
- **承認の 1 段目に告知の行**（見つけたこと 14 の直し）: 「記事 dl_… の公開を待って出ます（いまは wanted）・`{article_url}` は公開した URL に置き換わります」。記事が公開済みなら置き換えたあとの URL を見せる。予定時刻を過ぎていても、記事がまだなら「承認するとすぐ出ます」とは言わない。
- **はてなブックマーク**: `thth bookmark add <口座> --delivery <配信 id>`（自分の記事）か `--url <URL>`（レーンが参照している他人のページ）。2 段の承認・`thth bookmark delete`・`reconcile`（結果不明を確かめる）・`list`。
- **柵**: 同じページを masaru の 2 つ以上の主体で付けない（主体をまたいで断る・規約と FAQ）・1 ページに 1 回（消したあとも付け直さない）・自分の記事は 1 日 1 件・同じホストへは 1 日 1 件・ブックマークを打てるレーンは主体の台帳の `bookmark.lanes`（`thth principal set <主体> bookmark.lanes <lane>,…`）。
- `thth deliveries … --article <記事>` に、その記事の告知の行とブックマークの行が並ぶ。

## 修正の検出と衝突（S5）

- **修正の検出**: `thth article diff <口座|project>` が、出した版と repo の HEAD の版を比べて、直した記事の差分（本文・画像）を出す。`--draft` で更新の原稿の文面を出す（ファイルは書かない）。board・morning・`thth events`（`delivery_behind`）にも「正本を直した記事」が出る。
- **差分の承認と更新**: 更新の承認の 1 段目に、前に出した本文との差分を出す。本文・題・カテゴリ・画像のどれも変わっていない更新は `update_no_change` で断る。
- **外での手直しを上書きしない**: 更新の前に読み戻し、はてなの画面で手直しされていれば `conflict`（`readback_changed`）で止める。`thth conflict <口座> show|check|resolve`: `--adopt`（はてなの今の本文を取り込む）・`--gone`（外で消えていた）・`--no-follow`（追従しない）。上書きしたいときは取り込んでから承認し直す（2 重の承認）。
- **結果不明の照合**: 公開の結果が分からないとき、`thth inflight` がはてなの一覧から候補（entry_id・題・公開時刻・本文が同じか）と解く命令を出す。
- **burst の数え方**: はてなの記事は、同じ配信への操作（公開 → 直して更新 → 消す）を窓の中で 1 件と数える。別の記事の連投は今までどおり止まる。
- 削除が安全装置に当たったときの言い出しを「公開しません／更新しません／削除しません」にした（SNS の「取り下げません」のままだった）。

## 反応を記事へ戻す（S6）

- `thth run` の末尾で、はてなの口座は**反応を採る**（ブックマークの件数と中身・スター）。公開から 1h・6h・24h などの刻みを跨いだ配信だけを読み、`data/hatena/reactions/<配信 id>.ndjson` に 1 行ずつ書く（同じ刻みは 2 回書かない）。`thth hatena collect` で今 1 回。
- `thth article reactions <口座|project> --article <記事>` が、記事の名でブログ・告知・ブックマークの反応を出所と窓つきで並べる。自分の主体のブックマークとスターは「他」に入れない。自分の分がまだはてなのキャッシュに載っていないときは、他を 0 と言い切らず空にする。`--comments` で第三者のコメントの本文。
- morning の「昨日」に記事ごとの数（ブクマ 他・スター・告知の本数）、`thth events` に `bookmark_received`（第三者がブックマークを付けた）。

## MCP と thth.me の道

- 手元の MCP に `thth_article_diff`・`thth_conflict_status`・`thth_conflict_resolve`・`thth_article_reactions` を足した。`thth_bookmark_request` は `url`・`op` を受ける。`draft_put` は `announces`・`article` を受ける。
- thth.me の鍵の道（VM が答える）も同じ操作を受ける。はてなの予約（`schedule_request`）は 2 段。
- 主体の認可・止めを戻す・上限を変えるは CLI だけ（MCP からはできない）。

## 変わらないもの（SNS だけの口座）

3.25.0 → 4.0.0 の差分を読んで確かめた（kopicha・asmon-kanto・nigamilab など、はてなの口座を持たない口座）。

- **承認の指紋**: 変わらない。`announces` は値があるときだけ指紋の末尾に足す任意項目で、書いていない原稿の指紋の入力は 1 バイトも変わらない（固定の指紋の試験 `fingerprint_golden` の既存の値は同じ・告知の 1 件を足しただけ）。再承認は起きない。
- **timer**: `announces` の無い原稿の選び方・出し方は変わらない（告知の段は `announces` があるときだけ）。
- **burst の数え方**: 窓の中の「鍵」の数で数えるようにしたが、SNS の行の鍵は `post_id` ごとの公開と削除なので、数は今までと同じ（`sent/` の行は `post_id` ごとに 1 つ）。同じ配信を 1 件と数えるのははてなの記事だけ。返信の順番待ち（3.25.0）も同じ。
- **採取**: `thth run` の末尾の SNS の採取は今までどおり走る（はてなの口座だけ飛ばして反応の採取に替える）。
- **board・morning・events の出力**: はてなの口座にだけ欄と出来事を足した（`deliveries_*`・`hatena_collect_*`・`behind_items`・記事ごとの数・`delivery_*`・`bookmark*`）。SNS の口座の行の形は変わらない。
- **`thth send`・`thth schedule`・返信・取り下げ**: 変わらない。安全装置の文も SNS の符丁では同じ。

**変わる所が 1 つだけある**（SNS の原稿の書き方）: front matter の `announces:`・`article:` と本文の `{article_url}` が意味を持つようになった。

- 本文に `{article_url}` を書いて `announces` を書かない原稿は、lint が `article_url_without_announces` で断る（前は文字どおり `{article_url}` と出た）。
- `article:` を `announces` なしで書いた原稿も同じ符丁で断る（前は読まずに無視していた）。
- `announces:` に配信 id でない値を書いた原稿は `invalid_announces` で断る。

この 3 つの書き方をしているレーンが無ければ、SNS の口座の振る舞いは変わらない。

## 出し方

**VM だけでよい。Worker を出し直す要は無い。**

- `git diff 97908fc..HEAD -- callback/` は空（Worker のコードは 3.25.0 のまま・thth.me には 3.25.0 の Worker が出ている）。
- VM が Worker に送る要約（`/activity`）の形は変わらない: `thth/activity.py` は 3.25.0 から変わっておらず、行の kind（`published`・`retracted`・`scheduled`・`held`・`queued`・`stopped`）・止めの理由・上限の欄は同じ。はてなの新しい出来事は `thth events` の側で、要約には入らない。
- thth.me の新しい操作（`article_diff`・`article_reactions`・`conflict_status`・`conflict_resolve`、`bookmark_request` の `url`・`op`、`draft_put` の `announces`・`article`）は、Worker が操作の名前を形（英小文字と `_`）だけで見て VM へ渡すので、Worker を変えずに通る。
- したがって順番は release の枝を進める（VM が拾う）→ tag `v4.0.0` の push（PyPI と MCP registry）。利用者の CLI の新しい命令（`thth article`・`thth conflict`・`thth bookmark delete` など）は 4.0.0 を入れてから。

**VM ではてなを使い始めるには**（4.0.0 を出しただけでは、はてなには何も送らない）:

1. 主体の台帳を書く: `thth principal add <主体> --hatena-id <id> --blog <blog_id>=<lane> --owner masaru --by <名前>`（`$THTH_ROOT/principals/` に置かれる）。
2. 認可: **端末から** `ssh -t wt 'env THTH_ROOT=/srv/thth /srv/thth/app/bin/thth principal auth <主体> --by <名前>'`。consumer key と secret を伏せ字で入れ、表示される URL をブラウザで開いて許可し、verifier を貼る。秘密は VM の `~/.config/thth/<主体>.consumer`・`.token`（0600）に書かれ、画面には出ない。MCP からはできない。
3. 口座を書く: `thth account add <口座> --media hatenablog --principal <主体> --blog <blog_id> --project <lane> --by <名前>`。相対リンクのある記事を出すなら `link_base`。
4. `thth doctor <口座>` で、ブログの一覧・フォトライフ・ブックマークが ○ になるのを見てから、配信原稿を承認する。

上限（主体の burst 3/30 分・1 日 6 件、口座の burst 3/10 分・1 日 3 件など）は雛形のまま始め、必要なら `thth principal set`・`thth account set` で変える。
