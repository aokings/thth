# 設計 3.0: クローズドのサーバ型——招待した人が「承認を押す」だけで回る THTH

2026-09-20。masaru の裁定（同日昼）: 3.0 はクローズドのサーバ型。招待制・masaru のアプリ・masaru のサーバ。利用者は VM も Meta アプリも持たない。X を生やすのも 3.0 の要件。masaru「作業が済んだらそのまま 3.0 の設計に」。

本書は 3.0 に至る版（2.12.0・2.13.0・3.0.0）をまとめた契約。実装は Codex。裁定は §9。

## 1. 変えない原則（サーバ型でも）

1. **人が承認していない本文は 1 文字も出ない。** LLM が HTTPS／MCP で書く口を持っても変わらない。承認は**人の画面**で行い、LLM は digest を渡して承認を完了できない（§3.2）。
2. **秘密は人も LLM も触らない。** トークンは VM の 600 のファイル、client は masaru の置き場、預かり所は短命の code だけ。
3. **読む口は SNS 台帳に書かない。** 最小の runs は残す（2.10.0 の裁定）。
4. **すべて記録。** 誰が・いつ・何を（`--by`・変更ログ・来歴）。
5. **数値には分母。** 取れないものは `null`＋理由。

## 2. 招待の形

- 招待の単位は「人＋媒体アカウント」。masaru が `thth account add <account> --media … --handle … --project <人> --by masaru` で台帳を作り、`thth auth <account> --by masaru` の URL を本人に届け、本人が承認を押す（2.11.0）。
- 本人には **資格情報 1 つ**（`serve-reports` の credential・`scope: user`・その人の account 群）を渡す。本人は自分の LLM セッションの MCP 設定にそれを置くだけ（`THTH_REPORT_CREDENTIALS`／`THTH_REPORT_TOKEN`・2.9.0 と同じ形）。
- 招待者の原稿の置き場は **masaru のサーバの中の git**（`repos/_server/<account>/`・thth が commit する）。本人の repo は要らない。既存の「自分の repo を持つ project」（kopicha 等）は今までどおり（`thth pull`）。

## 3. 2.12.0: 書く口を利用者 scope に開く

### 3.1 HTTPS／MCP の書く操作（利用者 scope・自分の account だけ）

| 操作 | MCP 道具 | 何をするか | 記録 |
|---|---|---|---|
| 下書きを置く | `thth_draft_put` | 本文・topic・publish_at・reply_to を **サーバの queue** に `status: draft` で書く（lint を通す・通らなければ `invalid_draft` と理由） | git commit（by=本人・via=mcp） |
| 下書きを見る | `thth_draft_list`／`thth_queue` | 既存 | — |
| 承認を求める | `thth_approval_request` | 一段目: 公開される本文と digest を確定し、**承認ページの一回限り URL** を返す（§3.2）。LLM はそれを人に渡す | `approval_requested` |
| その場で出す（同席） | `thth_send_request` | dry-run と同じ表示＋承認ページの URL。承認されたらサーバが公開 | `send_requested`→`sent` |
| 取り消し・削除 | `thth_retract_request` | 同じく承認ページ経由 | `retract_requested` |

- **digest を MCP で受け取る口は作らない**（`approve --confirm` 相当を HTTPS／MCP に出さない）。人が押した記録が無い限り `approved` にならない。
- 利用者 scope は自分の account 以外に触れない（既存の `report_isolation`）。管理者 scope は書く口を持たない（読むだけ・2.9.0 §0）。

### 3.2 承認ページ（thth.me `/approve/<token>`・人が押す）

- サーバが承認 session を預かり所（2.11.0 の Durable Object）に登録: `{text（公開される本文そのもの）, digest, account, kind(approve|send|retract), expires（10 分）}`。人が URL を開くと Worker が本文と digest を表示し、**本人の承認 PIN**（招待時に masaru が本人へ別経路で渡す・thth.me には hash だけ）を入力して「承認」を押す。Worker は `{digest, approved_at, approver}` を session に記録。
- VM は 2 秒おきに最長 10 分 poll（2.11.0 の relay と同じ骨）。届いた digest が一段目の digest と一致したときだけ `approved`／公開へ。届かなければ `approval_timeout`（原稿は draft のまま）。
- 承認ページは **本文を短時間だけ持つ**（10 分・承認か失効で削除）。秘密は持たない。1 回限り。PIN の照合失敗は 5 回で session を失効。
- これで「LLM が本文を作り、LLM が承認する」は不可能になる: 承認は PIN を知る人の画面でしか完了しない。PIN は将来 passkey（WebAuthn）に置き換える（3.x）。

### 3.3 退出

`thth account leave <account> --by masaru`（管理者 CLI のみ・HTTPS／MCP に出さない）:
1. 媒体側の失効: Mastodon `POST /oauth/revoke`・X `POST /2/oauth2/revoke`・Threads は API 無し（本人が Threads の設定で解除・案内を出す）・Bluesky はアプリパスワードを本人が削除（案内）。
2. ローカル: token・env・台帳・`state/<account>`・`repos/_server/<account>` を削除（**変更ログには `account_removed` と削除した対象の一覧・件数を残す**・本文は残さない）。
3. thth.me の `/data-deletion` の要求は受付番号と時刻を DO に記録し、`admin log` に `deletion_requested` として見え、masaru が `leave` を打つ。`/data-deletion-status` は「受付／完了（`leave` の記録時刻）」を返す。

### 3.4 X の予算口（masaru の要望「LLM と対話的に上限を設定」）

- `thth admin budget x --monthly <額> --currency USD|JPY --by masaru`（CLI）と、**管理者 MCP の唯一の書く道具 `thth_admin_budget_set`**（admin scope・`by` 必須）。記録は変更ログ `budget_set`（前後の額）。既定は 0（読み取りしない）。
- 消費の計上: X の読み取り要求ごとに単価表（`docs/X料金_<日付>.md`・一次資料と取得日）から見積もり、`state/_admin/budget_x.json` に月次で加算。上限に達したら X の読み取りを止め `cannot_say: budget_exhausted`（投稿は止めない・別裁定）。`thth admin budget x` で残額と実績、X 側の usage API があればそれも併記（食い違いは `cannot_say`）。
- 「対話的に」の意味: masaru が LLM に「今月は 3,000 円まで」と言えば、LLM が `thth_admin_budget_set` を呼び、記録が残る。額の裁定は毎回 masaru。

## 4. 2.13.0: X の adapter と配布物の署名

- **X adapter**（予算口の下で）: 投稿・返信・削除（`tweet.write`）・自分の投稿の実測（`public_metrics`）・`mentions`・`where`（recent search・有料）。`where` は既定 off。採集は既存の by_mark の刻みに合わせる。X の 3000 文字と数え方（`COUNT_UNIT`）。承認・digest・production の門は同じ。
- **署名**: tag に署名（sigstore の gitsign か GPG・裁定）。VM の selfupdate は署名が確かめられた release だけを取り、`board` に「署名: 確認済み（鍵 ID）」。確かめられなければ更新せず通知。
- Bluesky の atproto OAuth（DPoP）は 3.x（別設計・任意依存の裁定）。

## 5. 3.0.0: 条件の確認だけ

新機能なし。§0 の表が全部○であることを、**招待した 1 人の通し**で確かめる: 台帳作成 → 承認を押す → 資格情報を置く → 自分のセッションから下書き → 承認ページで押す → 公開 → 24h 後の実測 → 退出。文書は `導入_招待されたら.md`（本人向け・1 枚）と `運用_招待する側.md`（masaru 向け）。App Review の結果と C3／C4 の裁定はこの版の前に。

## 6. 秘密と隔離（確認事項）

- 承認ページの本文は 10 分だけ DO に置く。秘密ではないが私的なので、`Cache-Control: no-store`・観測ログ off・失効で削除。
- 利用者の資格情報は 2.9.0 の user scope をそのまま拡張（`writes: true` を足す）。既存の read-only credential は書けない。
- MCP の書く道具は user scope の credential でだけ現れる（admin scope には出さない）。
- 秘密の走査テスト（token・client・PIN hash・承認 token）を全経路で固定。

## 9. masaru の裁定が要る点

1. 承認は thth.me の承認ページで人が押す（LLM は digest を渡して承認できない）。本人の識別は招待時に渡す **承認 PIN**（将来 passkey）。
2. 招待者の原稿は masaru のサーバ内の git（`repos/_server/<account>/`）に置く。本人の repo は要らない。
3. 退出は媒体側の失効（API があるもの）とローカルの削除を 1 操作にし、削除した対象の一覧を変更ログに残す（本文は残さない）。管理者 CLI だけ。
4. X の予算口は管理者 MCP の唯一の書く道具として置く（`by` 必須・記録）。上限到達で止めるのは読み取りだけ（投稿は止めない）。
5. 署名は sigstore（gitsign）か GPG か。
6. 版は 2.12.0／2.13.0／3.0.0 の 3 段。
