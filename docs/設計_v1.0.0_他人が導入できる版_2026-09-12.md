# 設計: v1.0.0 ——他人が自分の Meta アプリで導入できる最初の版（2026-09-12・開発セッション Fable）

masaru の指示（2026-09-12 夜）: 「BG を適切なモデルで使い、並列で役割分担し、
開発セッションは証拠ベースで監査し、自分も監査を受ける。現状を把握したうえで
手を付ける順番を定め、メジャーバージョン 1 つ分進める。」

## 0. 版の定義

いまの本番（`release` = `0870bc0`）は**版を持たない**（`VERSION` も tag も無い）。
これを **0.x** と見なし、次を **1.0.0** と定める。

**1.0.0 の意味: 「masaru 以外の人が、自分の Meta アプリと自分の VM で導入できる」。**
そのために越えるべき線は 3 つで、この版はその 3 つだけを扱う。

| 線 | いま | 1.0.0 で |
|---|---|---|
| トピックの棚が「最後に書いた人が勝つ」 | 上書き・他人の実績の混入・消せない誤記録 | **観測者ごとに全部並べる**・打ち消しの口・行数上限 |
| 導入手順が masaru の手の中にしか無い | `app.env が無い（masaru が書く）` | **導入文書**・`thth --version`・`doctor` が次の一手を言う |
| docs に運用日誌と製品文書が混在（95 本中 61 本が依頼・検収） | 読む人が製品文書を見つけられない | **`docs/記録/` に日誌を移す**・リンク検査を機械 lint に |

**含めないもの**（理由つき）:
- 配布権限（deploy key の read-only 化・GitHub Pro）——masaru の操作と支払い。
  （運用日誌 thth-notes: `記録/調査_配布の権限分離_2026-09-12.md`）のまま待つ。
- 棚の**保存形式**の変更（語単位ファイル・SQLite）——VM の現物の移行が要り、
  4 アカウントでは性能問題が無い。読み出しを直せば保存は追記型のままでよい。
- 集計だけを他ユーザーに出す口（型ごとの当たり率の export）——受け手がまだ無い。
- 旧棚（`topics.json`）と構造化棚（`state/topic_advice/`）の統合——両方の読み出しに
  同じ規則（観測者別・打ち消し反映）を入れるところまで。統合は次の版。

## 1. 棚の読み出し（Track A・Opus 5）

**壊れているのは保存ではなく読み出し。** `topics.observation()` と
`topic_store.legacy_observations()` の両方が「語ごとに最後の 1 行」で潰している。

規則:
1. **観測者ごとの最新**を返す。観測者の鍵は `account`、無ければ `by`、それも無ければ
   `"(記録なし)"`。同じ観測者の古い行は履歴として `topics.json` に残るが読まれない。
2. **打ち消し**。各行に `note_id`（行の中身から決まる `sha256:` 64 桁・保存時に付ける。
   旧行は読むときに同じ規則で計算する）。`thth topics retract-note <note_id> --reason
   --by` が `{"retracts": note_id, "reason", "by", "checked_at"}` を追記する。
   読み出しは打ち消された行を飛ばす。**消さない。**
3. **上限**。`--advise` の 1 語につき人向け画面は 2 件＋「ほか k 件」、`--json` は
   `observations`（最大 5 件・新しい順）＋ `observations_more`。全件は
   `thth topics history <語>`。
4. **`--json` の契約を変える**（規約 5・名前を変えないと古い読み手が旧意味で読む）。
   `audience` / `audience_account` / `audience_by` を**廃止**し、`observations: [{note_id,
   audience, account, by, checked_at, status, kind}]` にする。`kind` は自分の記録を
   優先する現行規則のまま。
5. `legacy_observations()` も観測者別・打ち消し反映にする（`observation_id` は現行の
   計算のまま）。

受け入れ（テストにする）:
- T-A1 別 account が同じ語を書いても、前の観測が画面と `--json` から消えない
- T-A2 打ち消した行は `--advise`（画面・`--json`）/ `legacy_observations()` / `judgment` /
  `kind_of` のどれにも出ない。`history` には**打ち消し済みの印つきでだけ**出る（打ち消した
  事実を後から検証できるように）。`topics.json` の行数は減らない
- T-A3 3 観測者が書いた語で、人向け画面が 2 件＋「ほか 1 件」になる
- T-A4 `--json` に旧 3 鍵が無く `observations` がある。`docs/引継ぎ_トピックの棚_…` と
  `docs/使い方_…` の該当節が新しい鍵を書いている（`test_value_domains_shown.py` の型で）
- 変異: 「観測者別」を「最後勝ち」に戻すと T-A1 が落ちる。打ち消しの skip を外すと
  T-A2 が落ちる

## 2. 導入（Track C1・Sonnet 5 ／ Track C2・Opus 5）

C1（機械的）:
- `thth/VERSION` に `1.0.0`。`thth --version` は `1.0.0 (<head7>)`。`thth board` の
  先頭に版を出す（いまは head だけ）。
- 利用者向けメッセージから固有名 `masaru` を外し役割語（運用者）にする。**コメント・
  docstring・設計の引用は触らない**（履歴は事実）。対象は `print` / `raise` / `help=` /
  `warnings` の文字列だけ。
- `thth doctor` が `app.env`・`accounts/<account>.json`・トークンの有無を順に見て、
  **足りないものごとに次の一手（導入文書の節番号）を言う**。

C2（判断あり）:
- `docs/導入_自分のMetaアプリで動かす.md`。Meta アプリの作成（開発モード・tester）、
  `~/.config/thth/app.env`、`accounts/<account>.json`、`thth auth`、timer の順。
  **各手順に出典（設計 §2.2 / §8-8 / §8-14 / §8-17 など）と証拠段階（L1/L2/L3）を付ける。**
  masaru しか確かめていない手順は L3 と正直に書く。
- **まっさらな導入の乾式試験**: 一時ディレクトリに clone し、偽の `app.env` と
  `accounts/` を置いて `thth doctor` → `thth lint` → `thth board` まで通す。トークン
  取得の手前で止まることを**期待どおりの停止**として記録する。これをテストにする
  （`tests/test_fresh_install.py`）。

## 3. docs の分離（Track B・Sonnet 5）

- `docs/記録/` を作り、接頭辞 依頼・検収・発注・回答・レビュー・レビュー依頼・使用報告・
  相談・監査・申請・訂正・仮説 を移す（`git mv`）。**製品文書は動かさない**: 設計・
  使い方・手順・語彙・型・定型・引継ぎ・調査・記録_URL・出口条件・資料・実装・導入。
- 移動は `tools/docs_reorg.py` に書き、**再実行できる**ようにする（他 Track の merge 後に
  もう一度当てるため）。
- 全 `.md` と `README.md`・`tests/conftest.py` の相対リンク・パス文字列を書き換える。
- `tests/test_docs_links.py`: docs 配下の相対リンクが全部実在することを検査する
  （**loud reject**・作法 5）。
- `docs/README.md`: 製品文書の索引（何を誰が読むか）。日誌は 1 行で場所だけ。

## 4. 監査の体制

| 役 | モデル | 見るもの |
|---|---|---|
| 実装 A / B / C1 / C2 | 上記 | 自分の worktree で commit。全件テスト＋変異の証拠（コマンドと出力）を報告 |
| 開発セッション（Fable） | — | 各 Track の diff を読む・merge 後に全件テスト・変異の再現を**自分で 1 つ以上**やる |
| 監査 1 | Opus 5・まっさらな文脈 | merge 後の main を**壊しにいく**（Track A 中心。同時実行・打ち消しの迂回・旧行） |
| 監査 2 | Opus 5・まっさらな文脈 | **開発セッションの最終報告の各主張**をコマンドで検証する。文書と実装の食い違い |

**監査の指摘は証拠つきで受け、直したものと直さなかったもの（理由つき）を最終報告に
両方書く。** 合格の自己申告はしない。

## 5. 順番

1. この文書を commit（いま）
2. A・B・C1・C2 を並列に起動（worktree 分離・枝は `v1/<track>`）
3. 上がった順に監査して main へ merge。B は最後（他 Track の docs 変更に再適用）
4. 全件テスト・`thth --version`・`thth doctor` の実物確認
5. 監査 1・2 を並列に起動 → 指摘を処理 → 再度全件
6. `v1.0.0` を tag・`main` へ push。**`release` は進めない**（配布は masaru の一言）
