## 1. 何が起きていたか

**`push` が本番反映と同義でした。**

`thth run` は仕事の前に自分自身を `git pull --ff-only` します。それまでは
**checkout している枝の上流**（＝`main`）を引いていたので、**`main` に push した
時点で、次の timer（10 分ごと）で本番の道具が入れ替わっていました。** 実測で
タイマー発火の **4〜7 秒後**に降りています（5 回計測: 7/7/4/7/7 秒）。

2026-09-11 の 1 日で **20 回以上 push**しており、**公開経路の P1 が入っていた版も
同じ経路で本番に降りていました。** 実害が出なかったのは連投が 1 本も承認されて
いなかったからで、**仕組みが止めたわけではありません。**

**この件は、こちらが最初に取り違えています。** 運用セッションに「配布はまだ
しないでください」と伝えたところ、「**push がもう配布です**」と訂正され、コードを
読んで確かめて撤回しました。**「まだ配っていない」と思っていた期間、ずっと配って
いました。**

## 2. masaru の裁定と受け入れ条件

> **本番用の枝を分けましょう。** `main` への push は開発の保存・共有とし、VM は
> `release` だけを追従する。**検収済みの特定 commit を `release` へ進める操作が
> 「配布」**。配布時点の main を無条件で取り込まないこと、配布操作の権限を決める
> こと、VM の稼働 commit を確認できることまで含める。

受け入れ条件は 3 つと明示されています。**そのまま 3 本のテストにしました。**

| 受け入れ条件 | テスト |
|---|---|
| **`main` への push では本番が変わらない** | `test_mainへのpushでは本番が変わらない` |
| **`release` へ進めた指定 commit が届く** | `test_releaseへ進めた指定commitが届く` |
| **届かない場合に分かる** | `test_届いていなければ遅れとして数えられる`（数）／`test_thth_boardの人向け出力に道具の版と遅れが出る`（画面） |

受け入れ条件 2 のテストは、**`main` を 2 つ進めておいて、1 つ手前の commit だけを
`release` に進める**形にしてあります。「配布時点の `main` を無条件に取り込まない」が
効いているかを見るためです。

## 4. こちらが作り込んで、こちらで見つけて直した穴（2 件）

**どちらも「読めない ≠ 無い ≠ 0 件」の型です。** 今夜ずっと潰してきた型を、
その最中に自分で作りました。

### 4-1. 「届かない」を「枝が無い」と言ってしまう形（変異 D）

`fetch` が落ちたとき、`git ls-remote` の**戻り値が 0 以外なら「枝が無い」と
読んでいました**。しかし**届かないときも 0 以外になります**。つまり **GitHub に
繋がらない日に「配布されていません」と言い切る**形でした。

`git ls-remote --exit-code` は**一致する ref が無いときだけ 2** を返し、繋がらない
等は別の値（128 など）です。**2 のときだけ言い切る**ようにしました。それ以外は
「**枝が無いのか、届かないのかは区別できていません**」と出します。

### 4-2. 単一枝 clone に永久に届かない形（変異 E）

`git fetch origin release` は、**clone の refspec が拾っている場合にだけ**
`refs/remotes/origin/release` を作ります。`--single-branch` / `--depth` 付きの
clone では refspec が `+refs/heads/main:refs/remotes/origin/main` だけになります。

**実際に単一枝 clone を作って確かめました**（想像していたより静かな壊れ方でした）:

    $ git fetch origin release                    → **rc=0（失敗しない）**
    $ git rev-parse refs/remotes/origin/release   → **作られない**
    $ git merge --ff-only origin/release          → not something we can merge
    $ git rev-list --count HEAD..origin/release   → **rc=128**（＝遅れは None）

**`fetch` が失敗しないのが要点です。** 4-1 で書いた「枝が無い」の検出は `fetch` が
落ちたときにしか走らないので、**この形では一度も呼ばれません。** board に出るのは
「配布の枝への ff に失敗しました（古いまま走ります）」だけで、遅れは `None` なので
commit 数も付きません。**止まりはするし黙りもしませんが、原因（clone の作られ方）に
辿り着ける情報が何も出ません。**

`+refs/heads/release:refs/remotes/origin/release` と明示して、clone の設定に依存
させないようにしました。

**いまの VM は普通の clone です**（wildcard refspec・shallow でない・運用セッションが
現物で確認。`git config --get-all remote.origin.fetch` → `+refs/heads/*:refs/remotes/origin/*`）。
**今日は刺さりません。** ここを塞いだのは、**VM を作り直す人が `--depth 1` を打たない
保証がない**からであって、いま壊れているからではありません。

## 7. 切り替えの順番（まだ実行していません）

X ＝ この検収の対象 commit とします。

1. **`release` を X に作る**（`git push origin <X>:release`）。`main` はまだ動かないので
   **VM は何もしません。**
2. **`main` を X へ進める。** VM の次の timer で、**古いコードが `main` を引いて X に
   上がります**——ここで初めて新しいコードが動き出し、以後は `release` だけを追います。
3. 以降、`main` がどれだけ進んでも本番は変わりません。

**逆順にすると**、VM が新しいコードに上がった時点で `release` がまだ無く、
「配布の枝が origin にありません」と言い続けます。止まりはしませんが無用の警告です。

**注意が 1 つあります。** 現在 `origin/main` と VM はともに `7e0cda0` で、こちらの
手元には未 push の commit が 3 件あります（`29670af`＝Codex 合格済み、`50b1e22`・
`203a8ec`＝文書のみ）。**手順 2 で `main` を push すると、この 3 件も一緒に古い仕組みで
本番へ降ります。** したがって **`main` の先端が X ちょうどであること**が条件です。
**X より先の commit を `main` に載せた状態で切り替えてはいけません。**

**残る気持ち悪さ**（動作には影響しません）: VM の clone は `main` という名前の枝を
checkout したまま、中身は `release` を追う形になります。ローカル `main` の upstream が
`origin/main` のままなので、SSH で入って `git status` を見ると「`origin/main` より
遅れている」と出ます。**`git branch -u origin/release` で比較先だけ変えれば済みます**が、
切り替えが済んでからの判断で足りると考えています。**ここも見ていただけると助かります。**
