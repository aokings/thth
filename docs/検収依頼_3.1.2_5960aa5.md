## 設計から外れた点・判断が要る点

1. **`next_steps` の `kind: "report"` は入れていない**（設計 §3）。3.1.1 の writer が同時に `thth/morning.py` を触っているため、morning への変更を 0 段「道具」と limitations に限った。代わりに 0 段の `reports.next` に `thth admin reports list --status open` を出す。3.1.1 の合流後に `next_steps()` と描画へ足すかは裁定待ち。
2. **stdio（手元の pip 版）の MCP には利用者の報告の口を出さない**。手元で置いても VM の実装側には届かないため。サーバ型の user credential と VM の CLI（`thth` のラッパ）だけに出す。stdio の isError には案内の 1 行を添える（CLI の `thth report file` は手元にもある）。
3. **CLI の `thth morning` は管理者とみなす**（資格情報の概念が無いため）。kopicha のセッションが VM の CLI で `morning` を打つと、他 project を含む件数（件数だけ・本文は出ない）が見える。CLI では `thth admin reports list` も打てるので、新しい漏れではない。
4. **重複の検査は同じ account の中だけ**。全体で見ると、他 project の報告の id を返してしまう（利用者 scope の漏れ）。
5. **件数の上限は「直近 24 時間」**で数える（暦日ではない）。
6. **32 桁以上の 16 進は設計どおり秘密として断る**。`draft_id`（64 桁）や git の完全な sha（40 桁）も断られる。断りの次の一手に「sha は先頭 12 桁までで足ります」と添えた。
7. **本文の `$THTH_ROOT` とホームの絶対パスは置く時点で `$THTH_ROOT`・`~` に畳む**（設計に無い）。leak probe（書き出しと JSON 応答に絶対パスが無い）を満たすため。手元の Mac のパスなど、VM の外のパスは畳まない。
8. **書き出し先について判断が要る**: 設計は THTH の repo の `docs/報告/` だが、THTH の repo は公開なので、利用者が書いた本文がそのまま公開される。`export --to` で行き先を選べる形にし、help と管理者 skill に「公開の repo に置く前に中身を人が確かめる」と書いた。private の `thth-notes` に置くかは masaru の裁定。
9. **退出（`thth account leave`）は報告を消さない**。`thth/leave.py` は 3.1.1 のレーンなので触っていない。退出時に報告も消すかは裁定待ち。
10. **断りの案内の 1 行は、CLI の JSON の断り（`read_coordination.refusal` 等）には足していない**。stderr の理由行の後ろに 1 行だけ。`report` 自身の断りの JSON には `report_channel` を入れた。既存の JSON の完全一致の試験 4 本と 3.1.1 との衝突を避けた。
