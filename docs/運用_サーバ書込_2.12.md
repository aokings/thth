# サーバの書く口（masaru 向け）

この設定は招待する管理者のサーバで行います。招待者が VM や git repo を持つ必要はありません。
2.12 のローカル実装手順であり、本番配布や招待者の通し検収が完了したことを示しません。
先に [承認 relay の管理](運用_承認relay_2.12.md) で署名鍵と本人の承認 secret を設定します。

## 専用原稿と資格情報

新しい招待 account は、通常の account add に明示的な配置を足します。
既定の `repos/<project>` は managed repo ではありません。

```sh
thth account add <account> --media threads --handle <handle> --project <person> \
  --repo-dir '$THTH_ROOT/repos/_server/<account>' --by masaru
```

実際の account 名で `<account>` を置き換えます。台帳の `project` と資格情報の account→project を一致させ、
既存の認可・production 設定を済ませます。account add の env/token は `~/.config/thth/…` が既定です。
serve-reports の既存隔離条件では台帳の env/token も `THTH_ROOT` 内である必要があるため、
管理者が認可前に台帳の両パスを例えば `$THTH_ROOT/secrets/<account>.env` と
`$THTH_ROOT/secrets/<account>.token` へ設定します。git の中へ置かず、所有者だけが読める mode 600 にします。
既存の資格情報がある account をこの例だけで移動してはいけません。置き場と認可の整合を管理者が確認します。
この設定を省いて上記 account add だけでサーバへの接続が完了するわけではありません。queue_dir は既定の `docs/sns/queue` を使えます。最初の下書きで専用 clone と
`state/<account>/git-origin.git` の local bare origin を初期化します。
既存 repo は移動・repoint しません。初期化が途中で失敗した場合は自動上書きせず管理者の点検を求めます。
既存 project の CLI と `thth pull` は従来どおりです。

管理者だけが触れる mode 600 の serve-reports 資格情報に、本人の credential の
`writes: true` と `actor: <person>` を加えます。actor は approver set の person と同じ名前です。
省略した credential は read-only のままです。admin scope に writes を付けることはできません。
Bearer の実値は従来どおり配布経路で扱い、設定ファイルには sha256 のみを置きます。
本文引数から actor、by、person を選ぶことはできません。

## 二つの常駐プロセス

非公開 Unix socket の `serve-reports --credentials <設定> --socket <path>` と、
同じ隔離環境・資格情報ファイルで `thth approval-worker --credentials <設定>` を運営者が起動します。
worker は 2 秒ごとに永続 job を検査し、`--once` なら一巡だけで終わります。
HTTP または MCP の生存期間に worker を結び付けません。worker を起動しなければ承認後も操作は実行されません。
HTTP を公開する場合の TLS・接続認証・Unix socket の私有ディレクトリは既存の配布担当の設定です。

`POST /write` は JSON の operation と account を受け、承認 request は URL を返して終了します。
600 秒の承認待ちを HTTP の接続内では行いません。中継の通信には 10 秒の timeout があり、
登録結果が不明なら成功とは返しません。

| operation / MCP 道具 | 入力 |
|---|---|
| draft_put / thth_draft_put | account, body, publish_at。任意 topic, reply_to。更新時は draft_id と expected_revision の両方 |
| approval_request / thth_approval_request | account, draft_id |
| send_request / thth_send_request | account, body。任意 topic, reply_to |
| retract_request / thth_retract_request | account, post_id, reason |

publish_at は既存 queue と同じ `+09:00` 付き日時です。下書きは lint と本文の往復照合を通し、
queue の媒体節にそのまま表現できない本文は `invalid_draft` で断ります。勝手に切り詰めたり別の節を公開したりしません。
更新は draft だけで、revision 不一致なら上書きしません。commit は by と via を残し、
他の staged ファイルを巻き込まない既存の限定 commit・同期・push 後の verified を使います。
managed Git は専用 local origin に限定し、ホストの template/hooks/署名/credential helper を継承しません。

`POST /report` の `draft_list` / `queue` は account が必須、`request_status` は account と job_id が必須です。
MCP は `thth_draft_list` / `thth_queue` / `thth_request_status` です。いずれも自分の account だけです。
ファイルパスや `confirm` を渡す口はありません。承認 URL は request の `approval_url` だけに返し、
status・変更ログへ再掲しません。URL 所持者は本文を読めるので、本人へ渡す際も私的に扱います。

MCP の credential 環境変数が一つでもあるとサーバ mode です。欠落・空・失効・不正でも
無認証ローカル CLI mode に戻りません。道具一覧と直接呼出の両方で同じ権限を確かめます。
資格情報の無い既存ローカル MCP mode とは別です。

## 失効・中断・不明結果

job は private な `state/<account>/approval-jobs/` に mode 600 で保存します。
資格情報の失効/期限/actor/許可 account、台帳・SNS token・原稿の変更、production と本人の承認世代を
実行直前にも検査します。公開・削除の最終照合は既存 repo→account ロックの内側です。
承認の間はこれらのロックを保持しません。

pending は元の 600 秒まで再開でき、ready は消費済み receipt が保存済みで、実行前の再検査から再開できます。
registering / consuming / executing で停止した場合は unknown です。承認の再消費・公開・DELETE を自動再実行しません。
API 成功後の記録失敗も unknown になります。人が媒体とローカル記録を照合する必要があります。
すでに始まった媒体操作を、後からの資格情報失効で巻き戻せるという保証ではありません。

停止判定は削除する account state の外にある共通 journal を使います。旧 CLI・timer・SNS read と新しい書く口が同じ停止状態を参照します。詳細と再試行の制約は次の退出手順を参照してください。

## 停止・退出

退出は管理者 CLI の `thth account leave <account> --by <actor>` です。通常の SNS 通信・認可保存・job は account の停止記録を確認し、同じ credential の他 account は継続します。共有物の切り分け、remote 未確認と再試行、媒体からの削除要求の照合は [退出手順](運用_サーバ退出_2.12.md) を参照してください。

X の認可・refresh を行う前に、[X 読取予算](運用_X読取予算_2.12.md) を管理者が設定してください。既定 0 のため、本人読取を伴う token 交換も先に拒否します。
