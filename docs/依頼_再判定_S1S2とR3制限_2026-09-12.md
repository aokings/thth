## 2. S1 — `root_post_id` の値の一致（閉鎖したつもり）

`thth/threadrun.py` の `run_problem()` に、root がある場合の**値の一致**を足しました。

```
if first["post_id"] != root:
    return "root_post_id（…）と 1 段目の post_id（…）が違います（**同じ投稿を指していません**）"
```

「あるか」「1 段目が published か」の 2 つの検査はそのままで、**その後ろに 1 つ足した
だけ**です。初回の `root=None` と、pending 再試行は通します。

### **ここだけ、こちらの判断で反例の期待を変えています（要判定）**

収録した反例 `tests/test_audit_b_r1_closure.py` の
`test_root_post_id値の不一致は親を汚さないが記録契約は未達` で、そちらの元の期待は
**「誤った root でも公開は続く」**でした。**こちらは止める側に倒しています。**
理由は 3 つです。

1. **信用できない記録に追記しながら公開を続ける**のが、あの晩 3 回続けて P1 を出した
   形そのものでした（読めない → 形が違う → 中身が矛盾）
2. `unreadable_runs()` は**公開と承認の共通の関門**なので、ここだけ「診断はするが
   止めない」にすると、**関門が 2 種類になる**
3. 止めたときのエラーには**絶対パスと戻し方**が出るので、人が動ける

**元の入力・失敗経路・他の assertion は変えていません。** 変えたのは「止まるか
続くか」の期待だけで、その旨は**テストファイル内にコメントで残しています**
（`tests/test_audit_b_r1_closure.py:141-154`）。

**「止めすぎ」と判定されたら戻します。**（戻す場合、`run_problem()` は値の不一致を
診断だけして `unreadable_runs()` には出さない形になると思いますが、その場合
**関門が 2 種類になること**をどう扱うかも併せて指示ください。）

## 4. **依頼外の追加**: R3 が残した実装上の制限（要判定）

前回の返却でこう書いて頂きました。

> 判定は行ごとではなく先頭行の account によるファイル単位である。先頭が legacy なら、
> 後から account 付きの新しい測定行が追加されても、その post 全体は不明のまま。
> 「当面だけ」ではなく既存ファイルに続く制限である。今回は不正混入を避ける保守的制限
> として合格を妨げない。**将来必要なら、所有が確認できる行だけ選別する改善を別作業に
> できる。**

**この「将来」が、すぐに来ていました。** VM の実物で `thth measured kopicha-threads` が

```
実測がありません —— 投稿 0 件
所有不明: 3 件  18120892756809994, 18341062471253025, 18626314573036692
```

と出ます。**既存の投稿ファイルはすべて先頭行が R3 より前**なので、以後どれだけ
`account` 付きの行が積まれても**この道具は永久に空のまま**になります。そこで
「所有が確認できる行だけ選別する改善」を、今回同時に入れました。

### 変えたこと（`thth/measured.py` / `thth/cli.py`）

1. **選別を行ごとにした。** その account の `account` を持つ行だけを系列に入れる。
   **裏付けの無い行は、これまで通り 1 行も混ぜない。**
2. **外した行の数を出す**（`rows_unattributed`、人向け出力にも）。0 でなければ
   **系列は途中から始まっている**——黙って落とすと「6h から始まった」と読めてしまう
   ので、欠けていることを言います。
3. `posts_unknown_ownership` の条件を「先頭行に `account` が無い」から
   **「裏付けのある行が 1 行も無い」**に変えました。
4. **1 つの台帳ファイルに 2 つの account の行が同居していたら `broken`**（1 行も
   使わない）。前回「後続行の整合性は検査されない／全面耐性を認定していない」と
   書かれた箇所です。**改竄防御を作ったつもりはなく**、行ごとに見る以上この矛盾は
   目に入るので、**混ぜるか壊れと言うかの二択で、壊れと言う側に倒しただけ**です。

### **判定をお願いしたいこと**

- **足しすぎではないか。** 今回の閉鎖条件は S1・S2 だけで、そちらは「R2〜R4 の機能
  拡張や過去データ復元を追加条件にしない」と明記していました。**これは「過去データ
  復元」に当たりますか。** 当たるなら戻します。
- **4 の `broken` 化が「止めすぎ」ではないか。** 同居を混ぜないのは確かですが、
  **投稿 1 件分の実測が丸ごと見えなくなります。**
- **`rows_unattributed` の出し方で、欠けが伝わるか。**

## 7. **push していません**（今回から運用を変えました）

**`dddba8d` は commit だけで、`origin` に push していません。** 前回までと違うので
申告します。

今日、運用セッションから指摘を受けて確認したところ、**この app は push した時点で
本番に反映されます。**

- `thth/cli.py:1266` — `cmd_run()` の冒頭で `selfupdate.pull_and_reexec()` を呼ぶ
- `thth/selfupdate.py:60-100` — `git pull --ff-only` し、進んでいたら同じ引数で
  exec しなおす（**lock を取る前**に）
- timer は 10 分ごとに `thth run` を叩く

**つまり commit と push の間に何も無く、push から 10 分以内に本番の道具が入れ替わり
ます。** 運用側が手で pull するかどうかは関係ありません。こちらも運用も、配布を
握っているのは人間の側だと思っていました。

**今日 1 日で 20 回以上 push しており、そのたびに本番が入れ替わっていました——
公開経路の P1 が入っていた版も、直った版も、同じ経路で降りていました。** 実害が
出なかったのは連投が 1 本も承認されていなかったからで、仕組みが止めたのでは
ありません。

そこで**判定が返るまで push しない**ことにしました。前回の返却に「判定対象は別の
固定 clone」と書かれているとおり、**push しなくても検収は回せる**という理解です。
違っていたら指示ください。

（逆向きの事故も実在します。`thth/selfupdate.py` の docstring に「pull しないまま
4 巡分の修正が入らずに timer が回っていた」とあり、この自己更新はその対策です。
**この構造自体をどうするかは、こちらの裁量ではありません**——依頼者に報告済みです。）
