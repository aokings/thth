- 下調べ: [調べ_ショップのAPI_BASE_STORES_Shopify_2026-11-12.md](調べ_ショップのAPI_BASE_STORES_Shopify_2026-11-12.md)・[調べ_APIのあるブログサービス_2026-11-12.md](調べ_APIのあるブログサービス_2026-11-12.md)
- 背景: [構想_台帳ベースの総合サイト運営_2026-11-12.md](構想_台帳ベースの総合サイト運営_2026-11-12.md)（叩き台。台帳の 1 行＝1 つのもの）

## 1. 目的

1. **ショップを読む**: 店主の商品（名前・値段・在庫・画像・商品頁の URL）を読み、前に読んだときとの違い（新しい商品・値段の変化・在庫の変化・売り切れ・公開の切り替え）を出す。違いから、SNS に出す投稿の**下書き**を作る。出すのは今までどおり持ち主の承認のあとだけ。
2. **WordPress に出す**: はてなブログと同じ道（原稿 → 承認 → 1 回出す → 記録）で、WordPress（自分で置く型と WordPress.com）に記事を出す。

最初の利用者は masaru の家族の BASE の店（持ち主本人が鍵を作る）。

## 2. 決まり（守ること）

- **お客さんの個人の情報を読まない・残さない。** 初めの版では注文を読まない（BASE・Shopify とも）。Shopify の `ordersCount` のような「数だけ」の口は、要るとなったときに別に足す（買い手の情報の許可が絡むものは使わない）。
- **ショップの側には書かない。** 初めの版は読むだけ。鍵も読むだけの権限で作ってもらう（BASE は `items.read`・`user.read`、Shopify は `read_products`・`read_inventory`）。書く権限の鍵を渡されたら、断るか、少なくとも警告する（鍵の権限が読めるなら）。
- **出すのは承認のあとだけ。** ショップの違いから作るのは queue の下書きのファイル（承認されていない）まで。WordPress への公開は、はてなブログと同じ承認の指紋と二段の柵を通る。
- **鍵は会話・出力・追跡されるファイルに出さない。** 置き場は今の token の置き場（`thth token set` の流れ・0600）。
- **前向きな断り**（`docs/原則_前向きな断り.md`）: 鍵が切れた・権限が足りない・β の口が変わった、をなぜ・通る直し方・より良くする一手で返す。BASE の PAT は期限が発行時に決まり、変えられない（期限切れは 401）ので、期限の前に知らせる。
- **CLI が先・MCP はその写し**（9/26 masaru）。MCP に出すのは読む口だけでよい（下書きを作る・公開するは CLI）。

## 3. ショップの口（`thth shop`）

### 3.1 形

- 新しいまとまり `thth/shop/`（例: `base.py`・`shopify.py`・共通の形）。媒体の adapter（`thth/adapters/`）とは別の種類（投げる先ではなく、読む元）。
- 台帳: 店ごとに 1 つの名前（例 `shop:<名前>`）で、種類（`base`・`shopify`）・店の識別・鍵の参照を持つ。今のアカウントの台帳の形に寄せる（作るときに一番素直な所を選ぶ）。
- 命令（名前は作るときに整えてよい）:
  - `thth shop add` / `thth shop token set`（鍵の受け取り。標準入力か隠した入力。引数に鍵を取らない）
  - `thth shop whoami <店>`（鍵の確かめ・店の名前と URL）
  - `thth shop items <店> [--json]`（商品の一覧）
  - `thth shop diff <店> [--json]`（前の写しとの違い。写しを更新する）
  - `thth shop draft <店> --to <アカウント> ...`（違いから queue の下書きを作る。承認されていない形で書く）
- 写し: 状態の置き場に店ごとの商品の写し（ID・名前・値段・在庫・公開・画像の URL・商品頁の URL・更新の時刻）だけ。**商品の説明の本文（`detail`）は写しに残さなくてよい**（下書きに使うなら、使うときに読む。BASE の `detail` は利用者の入力のままなのでエスケープが要る・公式）。

### 3.2 BASE（v2・β）

公式（2026-11-12、`https://apiv2.thebase.com/docs/` ほか）で確かめたこと:

- ベース URL `https://apiv2.thebase.com`。認証は PAT だけ（`Authorization: Bearer <token>`）。OAuth は予定（正式版は 2026 年末が目標）。
- PAT の期限は発行時に決まり、あとで変えられない。期限切れは 401。
- 商品一覧 `GET /api/items`（scope `items.read`）。`limit` 1〜100（既定 20）・`offset`。総件数は返らない（`limit` 未満なら終わり）。`visible`・`order`（`list_order`・`created`・`modified`）・`sort`。
- 応答の欄: `id`・`name`・`detail`・`price`・`proper_price`・`stock`・`visible`・`sales_status`・`images[]`（`url`・`scaled_url`・`square_url`）・`variations[]`（`stock` など）・`modified_at` ほか。`type` は `normal`・`digital`・`takeout`・`subscription`・`lottery`。
- **商品頁の URL は応答に無い。** `GET /api/user`（認証の利用者とショップの情報）から店の URL を取り、商品の URL を組む形を作るときに確かめる（組めなければ、URL なしで下書きを作り、その旨を出す）。
- β のため予告なく変わることがある。呼び出しの上限は今は無いが、正式版の前に設ける予定。**THTH の側で控えめにする**（1 回の diff で読むのは数ページ・間を空ける）。

### 3.3 Shopify

- 初めの版は**1 店向けのカスタムのアプリ**（店主が自分の店の管理画面で作る・審査なし）の Admin API の鍵で読む。外の店主に配る公開アプリ（OAuth・審査）は、試しが回ってから考える。
- Admin GraphQL（新しい公開アプリは GraphQL だけ・REST はレガシー。下調べ【公式】）。商品・種類・在庫・画像・`onlineStoreUrl`（商品頁の URL。下調べでは【推測】なので作るときに確かめる）。
- 呼び出しは費用の点数方式（下調べ）。応答の点数の残りを見て控えめにする。
- 試しの店: Shopify の開発用の店（Partner の登録が要る・masaru の手）。それまでは、公式の応答の形に沿った試験の材料で作る。

## 4. WordPress の口

- はてなブログの記事の道（queue の原稿・承認の指紋・`hatena_publish` などの流れ）に、2 つめの出し先として WordPress を足す。**新しい道を作らず、今の道に乗せる**のが目的。媒体名で分岐する所を増やさない（`thth/adapters/__init__.py` の考え方）。
- REST API `/wp-json/wp/v2/posts`。認証は**アプリケーションパスワード**（Basic・自分で置く型）。WordPress.com は OAuth2 だが、初めの版は自分で置く型を先にし、WordPress.com は後でもよい（作る者が判断して、やらない場合は書いて残す）。
- 出せるもの: 題・本文・下書き／公開／予約（`status=future` と `date`）・カテゴリとタグ（あれば）・アイキャッチの画像（後でもよい）。出したあとに記事の ID と URL を記録する（はてなブログと同じ）。直す・消すは、はてなブログの道にある範囲で。
- 試しの場所: 手元の Docker の WordPress（localhost）。試しの鍵は試しの場所で作り、置き場の決まりに従う。本物の WordPress のサイトに出すのは masaru の「出して」のあと。
