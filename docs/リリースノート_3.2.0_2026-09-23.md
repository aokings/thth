# リリースノート 3.2.0（reply_to_file）— 下書き

2026-09-23。設計は [設計 3.2.0](設計_3.2.0_reply_to_file_2026-09-23.md)（masaru の裁定 5 件はすべて「はい」・§4.5 を含む）。**版は据え置きです**（`thth/VERSION`・`server.json` は 3.1.2 のまま・tag も未作成）。上げるのは検分と masaru の一言のあとです。

## なぜ

「今日は問いだけ・明日に答え」の企画で、答えの原稿は出題の post_id が出るまで書けませんでした。毎回人の一手が残り、3 回続けて約束の時刻を過ぎました。**返信先を post_id ではなく「同じ queue の原稿の名前」で書け、その原稿が出るまで道具が待ちます。黙って root に落としません。**

## kopicha のセッション向け（5 行）

1. 答えの原稿の front-matter に `reply_to_file: 2026-09-23-q-decaf.md` と書く（**同じ queue・同じ account の原稿のファイル名だけ**・パスは書けない・`reply_to` とは併用しない）。書いたら `thth lint` で形を確かめ、いつもどおり `thth approve`（二段）。承認するのは「どの原稿への返信か」で、問いが出たあとに承認し直す必要はありません。
2. 問いが出て post_id が書き戻されると、**次の実行**（最大 10 分）で答えがその投稿への返信として出ます。答えの `publish_at` を過ぎていれば解決した実行で出ます（`quiet_hours`・`min_interval_hours` は従前どおり）。
3. 問いが出るまでの答えは「時刻超過」ではなく「返信待ち」です。`thth board` の要確認に「<答え> — 返信待ち: <問い> が出たら返信します」、`thth morning` の予定の段に「返信待ち: <答え> → <問い>」、`handoff-report` の `queue.counts.waiting_reply` に数が出ます。
4. 問いが取り下げられた・読めない・消えたときも答えは**出ません**（root には落ちません）。`reply_to_unresolved: target_retracted`／`target_unreadable`／`target_missing` として board の要確認に出るので、原稿を直すか取り下げてください。
5. `thth preview <答え>` の末尾に「返信先: <問い>（未解決・待ち）」か「返信先: <問い> → <post_id>」が出ます。出たあとの答えの front-matter には `reply_to_resolved: <post_id>` が足されます（`reply_to_file` は残ります）。

## 入ったもの

### 1. 原稿の書き方と lint（設計 §1）

- `reply_to_file: <ファイル名>`。`thth lint` が断るもの: `reply_to` との併用（`reply_to_conflict`）・自分自身（`reply_to_file_self`）・同じ queue に無い（`reply_to_file_missing`）・account 違い（`reply_to_file_account_mismatch`）・名前の形（`/` `\` `..` を含む・`.md` でない＝`reply_to_file_invalid`）・スレッド連投の原稿（`reply_to_file_bundle_unsupported`）・在るが `thth: 1` として読めない（`reply_to_file_unreadable`）。
- `reply_to: file:…` も `reply_to_file_invalid` で断ります（同じ指紋になるため）。
- 指した原稿がまだ出ていないことは断りません（待つのは誤りではない）。指した原稿がさらに `reply_to_file` を持っていてもかまいません（答えへの補足）。

### 2. 解決と待ち（設計 §2）

- 指した原稿が `status: posted`・post_id が使える形・`retracted_at` 無しなら解決します。まだ post_id が無ければ `reply_to_unresolved: waiting_for <名前>` で待ちます。
- 同期を確かめた commit と一致しない指した原稿は信じず、待ちます（同じ実行で問いを出した直後の答えは次の実行で出ます）。
- 公開の直前にも指した原稿を読み直し、解決が無い・食い違う候補は出しません（二重の守り）。

### 3. 承認の指紋と記録（設計 §3）

- 指紋の reply_to 欄は `file:<名前>`（解決した post_id は入りません）。承認のあとに `reply_to_file` を変える・`reply_to` に書き換えると `approval_stale`。既存の `approved_sha` は 1 つも変わりません。
- `sent/` と runs に `reply_to_file` と `resolved_from: {file, post_id}`。絡みの台帳の `found_by` は、書かれていなければ `manual`。

### 4. 報告の口の直し 3 件（設計 §4.5）

- 報告した側の追記: `thth report add <report_id> --body-file <path|-> --by <名前>`（MCP `thth_report_add {report_id, text}`）。自分の project の開いている報告にだけ。閉じた報告は `report_closed`。返事と同じ列に「報告した側の追記」として並び、`thth report show` と `handoff-report --since-last-read` の `tool.reports` に出ます。
- 置く前の似た報告: `thth report file` の応答に `similar`（同じ project の開いている報告で題の語が重なるもの・最大 5 件）。置くのは止めません。
- `thth report list`・`thth admin reports list` の行に「置いた人」。

## 変えていないもの

承認の二段・`--production`・digest・読む口の規律。`reply_to`（post_id 直書き）の道。スレッド連投（`thth: 2`）の仕様。サーバ型の下書き（MCP `thth_draft_put`）はこの版では `reply_to_file` を受けません。
