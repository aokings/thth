## 1. 直さないと危ない

### A-1. 承認の番号・上限・旗を、利用者の LLM が自分で満たせる

- 中身: 計画 D-1-5 は「`require_gate: true` の口座は hub の承認番号が無い確定を断る」をお金の柵の 1 層にしている。だが THTH が見ているのは**番号の形だけ**で、照合はしない（`thth/approval_ledger.py:87-88` の `valid_gate` は正規表現だけ・`thth/cli.py:759-779` の注「番号の照合（`hub approve verify`）は THTH ではしない」）。2 段の digest も、1 段目の出力を同じ LLM が 2 段目に貼れば通る（取り違えを防ぐ柵であって、本人でない者を止める柵ではない）。さらに計画は、月の上限（`thth ads budget set --monthly --by`）・`spend_cap` を上げる（`thth ads cap set`）・台帳の `ads_enabled`／`production` を、どれも THTH の CLI か台帳の書き換えで変えられる形にしている（D-3 の表・段 5 の 1 と 5）。`--by` は名前を書くだけ（`thth/budget_x.py:209-210` の `configure` は `admin_log.actor(by)` で記録するだけ）。
- なぜ危ない: 全体の決まり（`~/.claude/CLAUDE.md` §2「お金が動くものは masaru の承認」）を満たしているように見えて、LLM が誤って、または指示を取り違えて、上限を上げ → 番号の形の文字列を付けて → 始める、を 1 人で通せる。THTH の「利用者の LLM を疑わない」は投稿の話で、お金の承認とは別に扱う必要がある。
- 証拠: 上の 3 か所（実物）。
- 直し方の案: 「上げる」操作を THTH から外す。**`spend_cap` を上げる・外すのは Meta の管理画面で masaru だけ**（THTH は読む・下げるだけ）。段 4 の「最初は THTH から書かない」をずっとの決まりにする。こうすると、THTH の側の柵がどう破られても、支出は masaru が画面で入れた `spend_cap` で止まる。月の上限・`ads_enabled` を THTH に残すなら「LLM の誤りを減らす柵」と位置づけを書き直し、お金の最後の柵とは呼ばない。hub の番号は THTH が照合しない限り「記録」であって柵ではない、と D-1 に明記する。

### A-2. 終了日の無い配信を許している

- 中身: D-3「見積もり（日予算 × 終了までの日数、**終了日が無ければ `days_max`**）を予約」。THTH は `days_max` 日分しか予約しないが、Meta 側は終了日が無ければ日予算で配信を続ける。月の上限は見積もりなので、実支出が上限を越えても THTH は止めない（D-5 は events を出すだけ）。
- 証拠: 計画 D-3・D-5（計画の本文）。日予算の配信が終了日まで続くことは Meta の一般の仕組み（原文の頁では確かめていない・読めず）。
- 直し方の案: `boost`／`activate` は **`end_time` を必須**にし、`start_time + days_max` を越える指定は作らない。さらに **`lifetime_budget`（通しの予算）＋ `end_time`** を既定にする（日予算の上振れ B-13 も消える）。延ばすのは承認つきの `extend` だけ。

### A-3. 緊急停止の順番が、確かめていない読みに頼っている

- 中身: D-4「緊急の順: ① `spend_cap` を既支出に（全配信が Meta 側で止まる【確】）→ ② `pause --all` → ③ THTH の停止。①が通れば②③が失敗しても止まる」。段 5 の柵も「① が通れば②③の失敗でも『止まった』と報告する」。
- 原文: 「Setting a new spend cap only applies to spend AFTER the time at which you set it.」（https://developers.facebook.com/docs/marketing-api/reference/ad-account ・原文）。これは「上限をかけた時点から後の支出を数える」とも読め、その読みなら既支出の額に下げても、そこからさらに同じ額まで使える。下げられる最低の額があるか（Ads Manager の画面では最低額があるという二次の記事あり）も頁に無い（読めず）。届いてから実際に配信が止まるまでの遅れも頁に無い（読めず）。
- なぜ危ない: 止まっていないのに「止まった」と報告する道を、試験で縛って作ることになる。
- 直し方の案: 順番を **① `pause`（キャンペーン・広告セット・広告の全部）→ ② Meta から `effective_status` を読み直して全部 `PAUSED` を確かめる → ③ `spend_cap` を下げる（補助）→ ④ THTH の停止** に替え、「止まった」と言ってよいのは ② が通ったときだけにする。①② が失敗したら、すぐ hub に `waiting_on_masaru`「管理画面で止めてください」と出す。`spend_cap` を既支出に下げたときの振る舞いは段 5 の撮影の日に読んで確かめ、G の表に載せる。

### A-4. 止める道そのものが失敗したときの柵が無い

- 中身: 止める操作は広告の鍵で Meta を呼ぶ。計画では次のどれでも止められなくなる。
  1. **鍵の期限切れ**: 広告の鍵は 60 日のユーザーの鍵（C-1）。切れても Meta 側の配信は続く。計画 C-2-5 は「maintain の既存の `EXPIRING` に乗る」と書くが、maintain は口座の台帳の `media` から adapter を引き（`thth/maintain.py:145`）、広告は adapter ではない（計画 B-4）ので、`adaccounts/` の鍵は見えない（はてなに別の分岐がある `maintain.py:218` と同じ扱いが要る）。
  2. **量の制限**: Limited の段の広告の管理は「1 時間に 300 + 40 × 動いている広告」（https://developers.facebook.com/docs/graph-api/overview/rate-limiting ・原文「Calls within one hour = 300 + 40 * Number of Active ads」）。計画 B-1 は 80004 を `rate_limited` にして「その分だけ待って次の timer で再試行」とする。止める操作にもこれが当たると、止まるのが 1 時間遅れる。
  3. ページが別のポートフォリオ（G-11）で、権限が後から外れたとき。
- 証拠: 上（実物・原文）。
- 直し方の案: 止める操作は量の制限で待たない（すぐ失敗として返し、A-3 の hub への知らせに落とす）。広告の口座の鍵の期限を maintain／doctor が読む分岐を、段 4 の「できあがりの条件」に入れる（広告を始められる条件にする: 残り 14 日未満の鍵では `activate` を断る）。A-2 の `end_time` 必須が、止める道が全部だめなときの最後の柵になることを D-4 に書く。

### A-5. 承認した中身と、実際に始まる中身がずれうる

- 中身: D-2 は「始める」の digest に `act_id`・対象の id・予算・期間・対象の sha などを入れるとするが、**何から digest を作るか**（THTH の `ops/` の記録か、確定の時点の Meta の実物か）を書いていない。また「作る」は承認なし（D-2）なので、1 段目の digest を出したあと、確定までの間に、同じキャンペーンの下に広告セットを足す・管理画面や公式 MCP で予算を変える、ができる。キャンペーンを ACTIVE にすると、その下で ACTIVE になっている物は全部配信される（Meta の作成例でも、キャンペーンは `PAUSED`、広告は `status=ACTIVE` で作っている https://developers.facebook.com/docs/marketing-api/get-started/basic-ad-creation ・原文）。
- 直し方の案: 2 段目の確定の時点で **Meta から木の全体（キャンペーン・その下の全部の広告セットと広告の状態・予算・期間・対象）を読み直して digest を取り直し**、1 段目と違えば断る。`activate` は digest に入れた id だけを ACTIVE にし、ほかの子は触らない。試験: 1 段目のあと偽サーバで広告セットを 1 つ足し、2 段目が断ることを縛る。

### A-6. THTH の外で配信が始まったとき、日次まで気づかない

- 中身: THTH が `PAUSED` で作った物（と、THTH の外で作られた物）を、Ads Manager・公式 MCP（A-3 で masaru 個人が繋ぐ推し）・ほかの役割の人が始めると、THTH の月の上限の予約に載らない。計画 D-5 の照合は日次（「昨日」の値）だけ。
- 証拠: 計画 D-5・A-3（計画の本文）。
- 直し方の案: 広告の口座の読み（`effective_status`・`amount_spent`）を collect のたびに回し、「THTH の `activate` の記録が無いのに ACTIVE」を events の最優先（`ads_active_outside_thth`）にして `thth morning`・dashboard・hub に出す。月の消費には、予約の外の実支出も数える。お金の最後の柵は masaru の入れた `spend_cap` だけ、と D-1 に書く（A-1 と同じ結論）。
